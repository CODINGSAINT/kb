## Problem

Design a distributed rate limiter that protects APIs across a fleet of gateway or service instances: limit each user, API key or IP to N requests per window, consistently, no matter which instance a request hits. The LLD algorithms (token bucket and friends) are assumed. Here the questions are **where state lives**, **atomicity across nodes**, **latency**, and **failure behaviour**.

## Requirements

**Functional**
- Per-key and per-endpoint limits, configurable by tier. Respond `429` with `Retry-After` and `X-RateLimit-Remaining`.
- Multiple rules per request (per-user and per-IP and global).

**Non-functional**
- Adds < 1–2 ms p99 to every request. Highly available.
- Approximately accurate is acceptable (a few % over the limit under races), but no unbounded leaks.

**Scale:** 1M req/s peak across 200 gateway nodes, and 50M active keys at ~100 bytes of state each, which is 5 GB. That fits a Redis cluster.

## Architecture

- The limiter runs **in the gateway** (or as a sidecar). There's no extra network hop to a separate limiter service.
- State is in a **Redis cluster** sharded by key. The check runs as a **Lua script** (atomic per key): read the bucket, refill, decrement, set the TTL, and return allowed plus remaining.
- Rules come from a config service, cached in each gateway and hot-reloaded.

```lua
-- KEYS[1]=bucket  ARGV: capacity, refill_per_ms, now_ms
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or tonumber(ARGV[1]); local ts = tonumber(b[2]) or tonumber(ARGV[3])
tokens = math.min(tonumber(ARGV[1]), tokens + (tonumber(ARGV[3]) - ts) * tonumber(ARGV[2]))
local ok = tokens >= 1; if ok then tokens = tokens - 1 end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3]); redis.call('PEXPIRE', KEYS[1], 60000)
return {ok and 1 or 0, math.floor(tokens)}
```

## Key design decisions & trade-offs

**1. Centralised vs. local counters.** A central store (Redis) is accurate but costs a network round-trip per request. Local-only counters (limit/N per node) are fast but inaccurate when traffic is skewed across nodes. The **hybrid**: each node holds a local token allowance leased from Redis in batches (take 10 tokens at a time), syncing asynchronously. That trades a bit of accuracy for far fewer Redis calls.

**2. Race conditions.** `GET` then `INCR` from two nodes over-admits. Use atomic Lua, or `INCR` plus `EXPIRE` for fixed windows. Never do read-modify-write from the client.

**3. Algorithm choice at scale.** A sliding-window counter (two fixed-window counts, weighted) is O(1) memory and avoids boundary bursts. The token bucket allows bursts. A sliding log is too memory-heavy at 50M keys.

**4. Failure mode: fail open or closed?** If Redis is unreachable, most public APIs **fail open** with a local in-memory fallback limit, because availability matters more than precise limits. Payment or abuse-sensitive endpoints may fail closed. State it per endpoint.

**5. Hot keys.** A single abusive key hammers one Redis shard. A local pre-filter (deny keys already over limit for the rest of the window, cached in-process) protects Redis.

**6. Multi-region.** Global limits across regions need either a per-region quota split (simple and slightly inaccurate) or async CRDT counter replication. Exact global limits would add cross-region latency, which is rarely worth it.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** A quota decision is atomic within its declared scope; regional approximations and overshoot are stated explicitly.

Assume 200,000 checks/s and 2 million active principal-route buckets. At an illustrative 100 bytes of logical state per bucket: 200 MB raw, before Redis overhead/replicas. With 20 uniform shards, average load is 10,000 checks/s each; hot tenants break uniformity.

These are illustrative planning assumptions, not published traffic statistics or benchmark results. Recalculate the model when retention, payload size, tenant mix or peak factor changes. Show units throughout: average QPS is operations divided by seconds, bandwidth is bytes per operation multiplied by operations per second, and stored bytes are arrivals multiplied by retention and record size. Keep decimal GB/TB distinct from binary GiB/TiB when comparing vendor capacity. Replication, indexes, compaction/write amplification, backups and spare capacity are separate multipliers, not free implementation details.

Use the estimate to identify the first bottleneck, not to justify every distributed component. Ask which single key or customer can dominate the average. Measure a simple durable baseline before adding partitions. If a design serves a different workload than the stated assumption, explain the change rather than quietly inventing a larger number.

## API contracts and data ownership

```text
Internal allow(key,cost,policyVersion) returns allowed,remaining,retryAfter; gateway returns 429 only for known quota exhaustion
```

```text
Logical records (outline, not complete DDL):
bucket(key,tokens,last_refill,policy_version); policy(id,capacity,refill_rate,fail_mode)

Primary access/partitioning boundary:
tenant_id + principal_id + route + policy_version
```

Specify authentication, authorization, body limits and idempotency at the API boundary. The same idempotency key with the same payload returns the original result; the same key with a different payload is a conflict. Persist the payload fingerprint and outcome where retries can cross process restarts. Return stable resource/operation IDs so clients can query a pending or unknown outcome. Use cursor-based continuation for changing datasets and define the sort/snapshot semantics.

An API sketch is incomplete without its authoritative records. Distinguish transactional state from projections and caches. A projection can be rebuilt; the committed ownership/history cannot. Define who may mutate each record and which fields must change atomically. A convenient cache key is not necessarily a safe database partition key, and a healthy load balancer does not choose primary-versus-replica reads on behalf of the database client.

## Build the architecture in stages

**Stage 1 — Correct baseline.** Keep one service boundary around the core transaction, durable records indexed for the dominant access path, explicit dependency adapters and basic operational metrics. Exercise the stated invariant with concurrent requests before introducing asynchronous replicas. Avoid coupling the primary user result to optional analytics, notifications or recommendation work.

**Stage 2 — Measured scaling.** Add stateless request handlers and connection pools to absorb concurrent work. Cache only data whose freshness/authorization policy allows it. Introduce a durable queue when asynchronous work has an independent lifetime; define acceptance and completion separately. Autoscaling handlers cannot fix a single hot partition or an overwhelmed external provider.

**Stage 3 — Partition and isolate.** Partition around tenant_id + principal_id + route + policy_version. Track ownership with a routing epoch or a database-native partition mechanism. Move virtual buckets or copy/backfill data with a verified cutover, rather than changing a modulo divisor and assuming records move themselves. Isolate bulk/background workloads from the latency-sensitive path and test the busiest tenant independently.

**Stage 4 — Regional resilience when required.** State the recovery point objective (acceptable lost acknowledged data) and recovery time objective (acceptable outage duration). A second region is useful only if it has usable data, credentials, capacity and a tested failover route. Prefer one write authority per conflicting resource until the product genuinely needs multi-writer conflict resolution.

## Trace the critical request

Authenticate identity before choosing a key; resolve a cached policy version; route the key to one authority; atomically refill and consume tokens in one script or transaction; return decision metadata; invoke downstream only when allowed. Expire idle buckets only after their state can safely be reconstructed.

At each hop name the input, output, timeout and durable fact. A synchronous success response should follow the promised commit point. If work continues in the background, return an operation ID and status rather than implying completion. Publish committed work through a transactional outbox or a comparably reliable mechanism; a database write followed by a best-effort publish has a failure gap.

Do not place optional telemetry on the critical dependency chain. At the same time, “asynchronous” does not mean unbounded, durable or free: select queue capacity, retry deadlines, ordering scope and a poison-message policy. Consumers should record stable event identities or use conditional domain transitions so a redelivery has a safe effect. Broker-level transaction features do not automatically make an external payment, SMS or file write exactly once.

## Deep dive: the decision that changes this system

A token bucket with capacity B and refill r allows at most B+r*t tokens over interval t from a full bucket. Fixed windows can allow nearly twice the quota around a boundary. Sliding logs are exact but retain request timestamps; counters approximate with less memory. Client-provided timestamps cannot be trusted to refill tokens.

The important partitioning question is not merely where bytes are stored but where conflicting operations meet. Different partitions may progress independently, while operations touching the same authority need ordering or conflict detection. A stale cache/read replica can improve latency, but its allowed staleness must match the operation. A user-facing ownership/payment decision often requires a stronger path than a browsing view.

Do not use “eventual consistency” as a blanket explanation. Name the observable anomaly, the acceptable window and the remedy: stale reads, lost updates, duplicate effects, reordered events, or incomplete projections are different problems. Version/tombstone checks, conditional writes, durable deduplication and reconciliation solve different parts of that list. Include the client-visible response when a guarantee cannot be met.

## Failure and race-condition walkthrough

Redis timeout means the decision may have executed. Retrying can double-spend quota unless request identity is included. For read-only public content fail-open may be acceptable; billing or expensive model requests often need conservative fail-closed or local emergency budgets.

| Failure point | Question to answer | Recovery evidence |
|---|---|---|
| Before durable commit | Did anything become authoritative? | No committed operation means a safe fresh attempt |
| Commit succeeds, response is lost | How does the client avoid duplication? | Stable request/operation identity and stored result |
| Cache/projection is stale | Can it decide this operation? | Read policy, version, tombstone or authoritative fallback |
| Worker lease expires | Can the old worker still mutate state? | Fencing epoch checked at the resource boundary |
| Dependency is unavailable | Is work rejected, queued or degraded? | Bounded deadline, queue and explicit product outcome |
| Recovery replays events | How is a repeated effect detected? | Event identity or idempotent domain transition |

A timeout does not prove the remote side failed. Keep unknown outcomes distinct from rejected ones, especially around external side effects. Retry within a shared deadline, with jitter and one clear retry owner. If a gateway, SDK and worker each retry independently, a small outage becomes a load amplifier. Circuit breakers stop some repeated calls but do not create downstream capacity or reverse an already committed effect.

## Security, tenancy and lifecycle

Authorize the resource before reading private records or generating signed references. Derive tenant/principal from authenticated context rather than a freely supplied body field. Scope cache keys, events and deduplication identities by the relevant ownership boundary. Validate untrusted URLs and payloads at egress/parser boundaries. Avoid putting credentials, full personal payloads or signed access tokens in normal logs.

Retention is part of architecture. Define when source records, indexes, object blobs, replicas, caches and backups stop exposing deleted data; deleting one primary row is not a complete lifecycle policy. Keep the minimum history necessary to diagnose/reconcile operations under the product's requirements. Admin repair paths need authorization and audit just as much as public APIs.

## Trade-offs and a starting recommendation

Global serialization gives a tighter quota but adds cross-region latency and partition dependence. Per-region token leases bound overshoot by outstanding lease budgets and reduce round trips. A distributed lock around each check adds unnecessary contention when the store supports atomic operations.

Present each alternative as a cost paid for a guarantee. SQL versus a KV store is about access paths, consistency and operating constraints, not a slogan that relational databases cannot scale. Caching buys latency at a freshness/invalidation cost. A queue decouples throughput at the cost of lag, replay and monitoring. Cross-region writes buy local write availability at the cost of coordination or application conflict resolution. A system does not become more correct merely by adding a named infrastructure product.

For migrations, version schemas and event payloads; deploy readers that accept both compatible forms before writers emit the new form. Backfill in bounded batches, compare counts/checksums or domain invariants, move a small cohort, monitor, and retain rollback data until the cutover is proven. Rollback must account for writes made during the new version; restoring an old binary alone may not restore an old data model.

## Problem

Design a distributed in-memory cache like Memcached or Redis Cluster: a key-value store spread over many nodes, with sub-millisecond reads, that scales horizontally, survives node failures and evicts data when memory fills. The key topics are **partitioning with consistent hashing**, **replication**, **eviction**, and **cache patterns** with their consistency problems.

## Requirements

**Functional**
- `get(key)`, `set(key, value, ttl)`, `delete(key)`. Values up to ~1 MB.
- TTL expiry and LRU/LFU eviction under memory pressure.

**Non-functional**
- p99 < 1 ms within a datacentre. 1M+ ops/s. Add or remove nodes with minimal data movement.
- Survive a node failure without a thundering herd on the database.

**Scale:** 10 TB of hot data at 64 GB per node is roughly 160 nodes (plus replicas). At ~100k ops/s per node, 1M ops/s needs only about 10 nodes for throughput, so **memory drives the node count**.

## Architecture

- **Partitioning:** a consistent hash ring with ~100–200 **virtual nodes** per physical node, which smooths the distribution. Adding a node moves only ~1/N of the keys.
- **Routing:** a smart client library holds the ring (as in Memcached clients or Redis Cluster's slot map), or a proxy (twemproxy, Envoy). The client avoids a hop; the proxy simplifies clients.
- **Replication:** each shard has a primary plus 1–2 async replicas. Failover is promoted by a membership service (Sentinel, ZooKeeper or etcd).
- **Node internals:** a hash table plus an LRU doubly linked list (or Redis's approximated LRU by sampling). A single-threaded event loop per shard, or sharded locks.

## Key design decisions & trade-offs

**1. Consistent hashing vs. hash slots.** Redis Cluster uses 16,384 fixed slots assigned to nodes. Rebalancing moves whole slots, which is easier to reason about and migrate. A virtual-node ring is equivalent in spirit. Both beat `hash % N`, which reshuffles almost everything when N changes.

**2. Cache-aside vs. read-through vs. write-through vs. write-behind.**
- *Cache-aside* (the app reads the cache, falls back to the DB, then fills the cache) is the most common. Stale data is possible, so you need a TTL plus invalidation.
- *Write-through* keeps the cache fresh but adds write latency. *Write-behind* is fast but risks data loss.

**3. Invalidation races.** A read fills the cache with an old value right after a writer deletes it. Mitigations: delete after the DB commit, a short TTL, versioned values, or "delete twice" (delayed double delete). Facebook's *leases* stop stale sets and thundering herds.

**4. Thundering herd / stampede.** A hot key expires and 10k requests hit the DB. Use request coalescing (single-flight), probabilistic early refresh, and serve stale while revalidating.

**5. Hot keys.** One key on one node gets 200k req/s. Replicate hot keys to several nodes (key#1..k), or add a small in-process L1 cache in front.

**6. Consistency on failover.** With async replication, recent writes can be lost on promotion. For a cache, that's usually acceptable: the DB is the source of truth.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** The cache is expendable; losing cached bytes must not silently lose the authoritative record.

Assume 100,000 reads/s and 95% hits: 5,000 misses/s reach storage. Ten million 1 KB values consume about 10 GB raw, excluding keys, allocator overhead, replicas and headroom. At zero hits the origin sees a 20x increase.

## Problem

Design a notification platform that many internal services use to send email, SMS, push and in-app notifications to millions of users: transactional (OTP, order shipped) and bulk (campaigns). It must be reliable, respect preferences and rate limits, retry failures and never block the callers. The topics are **queues and fan-out**, **retries and DLQ**, **priority isolation**, and **multi-channel delivery**.

## Requirements

**Functional**
- `POST /notify {userIds|segment, template, data, channels?, priority}`.
- Per-user preferences, opt-outs, quiet hours, localisation, templates.
- Delivery status tracking (sent, delivered, opened), and a campaign scheduler.

**Non-functional**
- At-least-once delivery with deduplication, so users see effectively-once.
- OTP latency < 5 s even during a 50M-user campaign.

**Scale:** 1B notifications per day is ~12k/s average and 100k/s peak during campaigns. A campaign to a segment fans out 1 request into 50M messages.

## Architecture

1. The **Notification API** validates, assigns a `notificationId` and writes to **Kafka**, with separate topics per priority (`critical`, `transactional`, `bulk`).
2. A **fan-out service** expands segments into per-user messages (paged from the user DB) for bulk campaigns.
3. **Channel workers** (separate consumer groups per channel) load preferences and the template, render, apply per-user rate limits and dedup, then call the vendor.
4. Failures go to a **retry topic** with exponential backoff, then a **DLQ** after N attempts for inspection and replay.
5. Vendor callbacks (delivered, bounced) update the **status store** (Cassandra/DynamoDB keyed by notificationId and by userId+time).

## Key design decisions & trade-offs

**1. Queue between producers and senders.** It decouples callers from vendor latency and outages, absorbs spikes, and makes retry and replay possible. Kafka gives ordering per partition plus replay; SQS/RabbitMQ are simpler for per-message ack and delay.

**2. Priority isolation.** Separate topics and worker pools per priority stop a campaign from starving OTPs. Bulk workers get a hard cap on vendor throughput.

**3. Idempotency.** Workers may process a message twice (at-least-once). Record `notificationId` in a dedup store with a TTL before sending, and pass an idempotency key to vendors that support one.

**4. Retries done right.** Exponential backoff with jitter. Classify errors (4xx permanent vs. 5xx or timeout transient). Use per-vendor **circuit breakers** and failover vendors (SES down, so SendGrid).

**5. Rate limits both ways.** Per-user (no spamming) and per-vendor (respect provider quotas). Token buckets in Redis.

**6. Templates and preferences cached** in workers with short TTLs. Each is read for every message, so this is where the database load comes from.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** One accepted business notification has a durable identity even if several delivery attempts occur.

Assume 10 million notifications/day: 116/s average. At 20x campaign bursts: about 2,315/s. A provider sustaining 1,000/s needs over two hours for an 8-million-message campaign even without retries; enqueue speed is not delivery speed.

These are illustrative planning assumptions, not published traffic statistics or benchmark results. Recalculate the model when retention, payload size, tenant mix or peak factor changes. Show units throughout: average QPS is operations divided by seconds, bandwidth is bytes per operation multiplied by operations per second, and stored bytes are arrivals multiplied by retention and record size. Keep decimal GB/TB distinct from binary GiB/TiB when comparing vendor capacity. Replication, indexes, compaction/write amplification, backups and spare capacity are separate multipliers, not free implementation details.

Use the estimate to identify the first bottleneck, not to justify every distributed component. Ask which single key or customer can dominate the average. Measure a simple durable baseline before adding partitions. If a design serves a different workload than the stated assumption, explain the change rather than quietly inventing a larger number.

Specify authentication, authorization, body limits and idempotency at the API boundary. The same idempotency key with the same payload returns the original result; the same key with a different payload is a conflict. ## Build the architecture in stages

**Stage 1 — Correct baseline.** Keep one service boundary around the core transaction, durable records indexed for the dominant access path, explicit dependency adapters and basic operational metrics. Autoscaling handlers cannot fix a single hot partition or an overwhelmed external provider.

**Stage 3 — Partition and isolate.** Partition around recipient or tenant for fairness; notification_id for deduplication; provider/account for rate budgets. **Stage 4 — Regional resilience when required.** State the recovery point objective (acceptable lost acknowledged data) and recovery time objective (acceptable outage duration). ## Trace the critical request

At each hop name the input, output, timeout and durable fact. A synchronous success response should follow the promised commit point. Consumers should record stable event identities or use conditional domain transitions so a redelivery has a safe effect. Broker-level transaction features do not automatically make an external payment, SMS or file write exactly once.

## Deep dive: the decision that changes this system

Queue delivery is normally at least once. Deduplicating worker records does not guarantee exactly-once external SMS when a timeout follows provider acceptance. Use provider idempotency/reference lookup where available; otherwise expose the residual duplicate risk. Separate transactional password resets from bulk marketing queues.

The important partitioning question is not merely where bytes are stored but where conflicting operations meet. Different partitions may progress independently, while operations touching the same authority need ordering or conflict detection. A stale cache/read replica can improve latency, but its allowed staleness must match the operation. A user-facing ownership/payment decision often requires a stronger path than a browsing view.

Do not use “eventual consistency” as a blanket explanation. Name the observable anomaly, the acceptable window and the remedy: stale reads, lost updates, duplicate effects, reordered events, or incomplete projections are different problems. Version/tombstone checks, conditional writes, durable deduplication and reconciliation solve different parts of that list. Include the client-visible response when a guarantee cannot be met.

Provider outage grows backlog and can make messages obsolete. Expire one-time codes and cancel superseded notifications instead of delivering stale work after recovery. A poison template is quarantined rather than retried forever.

## Trade-offs and a starting recommendation

Push channels differ in delivery receipts and device availability; failover to SMS changes cost and consent requirements. Partitioning per recipient preserves useful order but requires fairness so one tenant cannot occupy every worker.

Present each alternative as a cost paid for a guarantee. SQL versus a KV store is about access paths, consistency and operating constraints, not a slogan that relational databases cannot scale. Caching buys latency at a freshness/invalidation cost. A queue decouples throughput at the cost of lag, replay and monitoring. Cross-region writes buy local write availability at the cost of coordination or application conflict resolution. A system does not become more correct merely by adding a named infrastructure product.

For migrations, version schemas and event payloads; deploy readers that accept both compatible forms before writers emit the new form. Backfill in bounded batches, compare counts/checksums or domain invariants, move a small cohort, monitor, and retain rollback data until the cutover is proven. Rollback must account for writes made during the new version; restoring an old binary alone may not restore an old data model.

## Problem

Design a social news feed (like Facebook, X or LinkedIn): users post, follow others, and see a ranked, reasonably fresh feed of posts from people they follow, at a scale where some accounts have millions of followers. The classic discussion is **fan-out on write vs. fan-out on read**, **ranking**, **caching** and **pagination**.

## Requirements

**Functional**
- Create posts (text or media). Follow and unfollow.
- `GET /feed?cursor=` returns a ranked feed, paginated, with new posts appearing within seconds.

**Non-functional**
- Feed reads are p99 < 200 ms and read-heavy (≈ 100 reads per post).
- A celebrity posting must not cause a write storm that degrades everything.

**Scale:** 300M DAU, each opening the feed 10 times a day, is 3B feed reads/day ≈ 35k/s (peak ~100k/s). 50M posts/day ≈ 600 writes/s. Average 200 followers per user means **fan-out ≈ 120k feed inserts/s**.

## Architecture

- **Post service** writes the post to a posts store (sharded by postId) and emits `PostCreated` to Kafka.
- **Fan-out service** consumes the event, reads the author's followers (graph store), and pushes `postId` into each follower's **feed cache** (a Redis list or sorted set capped at ~800 IDs).
- **Feed service** reads the user's precomputed IDs, merges in posts from followed celebrities (pull), hydrates the posts (cache plus batch get), ranks, and paginates.

## Key design decisions & trade-offs

**1. Push (fan-out on write).** Reads are fast (precomputed). The cost is write amplification: a 10M-follower account means 10M inserts per post, plus wasted work for inactive followers.

**2. Pull (fan-out on read).** No write amplification. The cost is expensive reads: merging hundreds of followees' timelines on each request.

**3. Hybrid (the expected answer).** Push for normal users. Pull for accounts above a follower threshold (e.g. 100k) and merge their recent posts at read time. Also skip pushing to inactive users and rebuild their feed on next login.

**4. Ranking.** Reverse-chronological is simplest. Ranked feeds score a candidate set (precomputed IDs plus celebrity posts, a few hundred items) with features such as recency, affinity, engagement and content type. Two-stage: cheap candidate generation, then a heavier ranker on the top few hundred.

**5. Pagination.** Use **cursor-based** (last seen score or ID), not offset. New posts arriving at the top don't shift pages, and it's O(1) to resume.

**6. Storage.** Feed cache in Redis holds IDs only (small). Posts are hydrated from a post cache. The follow graph lives in a sharded store with both `followers(user)` and `following(user)` indexes.

## Problem

Design a chat system like WhatsApp: 1:1 and group messaging, real-time delivery, delivery and read receipts (✓✓), online presence, offline delivery, and history on multiple devices. The core topics are **persistent connections (WebSockets)**, **message ordering**, **delivery guarantees** and **presence**.

## Requirements

**Functional**
- 1:1 and group chat (≤ 1024 members). Text plus media (via object storage).
- Sent ✓, delivered ✓✓ and read receipts. Last seen and online status.
- Offline users receive messages on reconnect, plus a push notification.

**Non-functional**
- Delivery latency < 200 ms when both users are online. No message loss. Per-chat ordering.

**Scale:** 500M DAU and 50B messages/day ≈ 600k msgs/s average, more at peak. Around 100M concurrent connections; at ~100k per gateway box, that's ~1,000+ gateway servers.

## Architecture

- **Connection gateways** hold WebSocket (or MQTT) connections. A **session registry** (Redis: `userId → gatewayId`) tracks where each user is connected.
- **Chat service** receives a message, assigns a per-conversation **sequence number**, persists it, then routes it to the recipient's gateway (looked up in the registry) via an internal pub/sub or RPC.
- **Message store:** Cassandra/HBase partitioned by `conversationId`, clustered by `seq`. Efficient "messages after seq X" queries.
- **Offline path:** if the recipient isn't connected, the message waits in the store or an inbox, plus a push notification. On reconnect, the client syncs from its last acked seq.
- **Media:** upload to object storage via a pre-signed URL. The message carries the URL (and an encryption key in E2E designs).

## Key design decisions & trade-offs

**1. WebSocket vs. long-polling.** WebSockets give bidirectional, low-overhead messaging, which suits chat. Long-polling is a fallback. Gateways are stateful, so you need draining on deploy and reconnect with resume.

**2. Ordering.** Global ordering is unnecessary and expensive. Order **per conversation** with a server-assigned monotonic seq (a counter per conversation, or a Snowflake ID plus tiebreak). Clients sort by seq, not by device clock.

**3. Delivery guarantees.** Client sends with a `clientMsgId` (for dedup on retry). Server persists, then acks "sent ✓". The recipient's device acks, giving "delivered ✓✓". Read acks travel the same way. That's at-least-once plus idempotent IDs, which gives effectively-once.

**4. Groups.** Fan-out on write to each member's gateway or inbox for small groups. For large groups, write once to the group log and have members pull by seq.

**5. Presence.** Heartbeats every ~30 s update `lastSeen` in Redis with a TTL. Fan presence changes out only to contacts who are currently viewing that chat, to avoid presence storms.

**6. Multi-device.** Each device keeps its own cursor (last seq) and syncs independently.

These are illustrative planning assumptions, not published traffic statistics or benchmark results. Recalculate the model when retention, payload size, tenant mix or peak factor changes. ## Requirements

## Architecture

**Upload path:**
1. The client gets a **pre-signed, resumable upload URL** and uploads chunks directly to object storage (S3/GCS), bypassing app servers.

**4. CDN strategy.** Popular videos are cached at edge PoPs worldwide. The long tail is served from regional origin caches (most videos are rarely watched). Pre-warm the CDN for big launches.

**5. Storage tiers.** Hot renditions on standard storage. Old, rarely watched videos move to cheaper tiers, and some renditions (4K of an unwatched video) can be dropped and regenerated on demand.

```text
title_id + rendition_version for objects; account_id/session_id for entitlement and concurrency
```

Specify authentication, authorization, body limits and idempotency at the API boundary. The same idempotency key with the same payload returns the original result; the same key with a different payload is a conflict. Persist the payload fingerprint and outcome where retries can cross process restarts. Return stable resource/operation IDs so clients can query a pending or unknown outcome. Use cursor-based continuation for changing datasets and define the sort/snapshot semantics.

An API sketch is incomplete without its authoritative records. Distinguish transactional state from projections and caches. A projection can be rebuilt; the committed ownership/history cannot. Define who may mutate each record and which fields must change atomically. A convenient cache key is not necessarily a safe database partition key, and a healthy load balancer does not choose primary-versus-replica reads on behalf of the database client.

## Build the architecture in stages

**Stage 1 — Correct baseline.** Keep one service boundary around the core transaction, durable records indexed for the dominant access path, explicit dependency adapters and basic operational metrics. Exercise the stated invariant with concurrent requests before introducing asynchronous replicas. Avoid coupling the primary user result to optional analytics, notifications or recommendation work.

**Stage 2 — Measured scaling.** Add stateless request handlers and connection pools to absorb concurrent work. Cache only data whose freshness/authorization policy allows it. Introduce a durable queue when asynchronous work has an independent lifetime; define acceptance and completion separately. Autoscaling handlers cannot fix a single hot partition or an overwhelmed external provider.

**Stage 3 — Partition and isolate.** Partition around title_id + rendition_version for objects; account_id/session_id for entitlement and concurrency. Track ownership with a routing epoch or a database-native partition mechanism. Move virtual buckets or copy/backfill data with a verified cutover, rather than changing a modulo divisor and assuming records move themselves. Isolate bulk/background workloads from the latency-sensitive path and test the busiest tenant independently.

**Stage 4 — Regional resilience when required.** State the recovery point objective (acceptable lost acknowledged data) and recovery time objective (acceptable outage duration). A second region is useful only if it has usable data, credentials, capacity and a tested failover route. Prefer one write authority per conflicting resource until the product genuinely needs multi-writer conflict resolution.

## Trace the critical request

Authenticate account/device; check geographic rights and plan; enforce concurrency lease; return short-lived manifest/license references; client selects adaptive segments from CDN; report bounded playback telemetry; persist watch position asynchronously.

At each hop name the input, output, timeout and durable fact. A synchronous success response should follow the promised commit point. If work continues in the background, return an operation ID and status rather than implying completion. Publish committed work through a transactional outbox or a comparably reliable mechanism; a database write followed by a best-effort publish has a failure gap.

Do not place optional telemetry on the critical dependency chain. At the same time, “asynchronous” does not mean unbounded, durable or free: select queue capacity, retry deadlines, ordering scope and a poison-message policy. Consumers should record stable event identities or use conditional domain transitions so a redelivery has a safe effect. Broker-level transaction features do not automatically make an external payment, SMS or file write exactly once.

## Deep dive: the decision that changes this system

A CDN caches immutable segments at enormous scale; tokenized manifests and DRM/license services control access. DRM is not just encrypting a URL. The playback dependency chain must avoid synchronous calls to recommendations, analytics and billing for every segment.

The important partitioning question is not merely where bytes are stored but where conflicting operations meet. Different partitions may progress independently, while operations touching the same authority need ordering or conflict detection. A stale cache/read replica can improve latency, but its allowed staleness must match the operation. A user-facing ownership/payment decision often requires a stronger path than a browsing view.

Do not use “eventual consistency” as a blanket explanation. Name the observable anomaly, the acceptable window and the remedy: stale reads, lost updates, duplicate effects, reordered events, or incomplete projections are different problems. Version/tombstone checks, conditional writes, durable deduplication and reconciliation solve different parts of that list. Include the client-visible response when a guarantee cannot be met.

## Failure and race-condition walkthrough

A control-plane region fails while streams are already playing. Existing signed media access can continue until expiry; new session creation fails over according to replicated entitlement freshness. Very short token TTLs improve revocation but increase control-plane dependence.

| Failure point | Question to answer | Recovery evidence |
|---|---|---|
| Before durable commit | Did anything become authoritative? | No committed operation means a safe fresh attempt |
| Commit succeeds, response is lost | How does the client avoid duplication? | Stable request/operation identity and stored result |
| Cache/projection is stale | Can it decide this operation? | Read policy, version, tombstone or authoritative fallback |
| Worker lease expires | Can the old worker still mutate state? | Fencing epoch checked at the resource boundary |
| Dependency is unavailable | Is work rejected, queued or degraded? | Bounded deadline, queue and explicit product outcome |
| Recovery replays events | How is a repeated effect detected? | Event identity or idempotent domain transition |

A timeout does not prove the remote side failed. Keep unknown outcomes distinct from rejected ones, especially around external side effects. Retry within a shared deadline, with jitter and one clear retry owner. If a gateway, SDK and worker each retry independently, a small outage becomes a load amplifier. Circuit breakers stop some repeated calls but do not create downstream capacity or reverse an already committed effect.

## Security, tenancy and lifecycle

Authorize the resource before reading private records or generating signed references. Derive tenant/principal from authenticated context rather than a freely supplied body field. Scope cache keys, events and deduplication identities by the relevant ownership boundary. Validate untrusted URLs and payloads at egress/parser boundaries. Avoid putting credentials, full personal payloads or signed access tokens in normal logs.

Retention is part of architecture. Define when source records, indexes, object blobs, replicas, caches and backups stop exposing deleted data; deleting one primary row is not a complete lifecycle policy. Keep the minimum history necessary to diagnose/reconcile operations under the product's requirements. Admin repair paths need authorization and audit just as much as public APIs.

## Trade-offs and a starting recommendation

Pre-position popular titles near demand; origin fetch reduces storage but increases first-view latency and egress. Availability and consistency goals differ between catalogue browsing, licence grants and progress updates.

Present each alternative as a cost paid for a guarantee. SQL versus a KV store is about access paths, consistency and operating constraints, not a slogan that relational databases cannot scale. Caching buys latency at a freshness/invalidation cost. A queue decouples throughput at the cost of lag, replay and monitoring. Cross-region writes buy local write availability at the cost of coordination or application conflict resolution. A system does not become more correct merely by adding a named infrastructure product.

For migrations, version schemas and event payloads; deploy readers that accept both compatible forms before writers emit the new form. Backfill in bounded batches, compare counts/checksums or domain invariants, move a small cohort, monitor, and retain rollback data until the cutover is proven. Rollback must account for writes made during the new version; restoring an old binary alone may not restore an old data model.

## SLOs, failure drills and lab

Start-up latency, rebuffering, error-free playback, licence p99, origin egress and entitlement decision errors.

**Test matrix:** Playback under bandwidth changes, CDN origin loss, expired entitlement, concurrent device limit, regional rights change and licence-service degradation.

Build a load generator that models hot keys, retries and realistic arrival bursts rather than a uniform loop over random IDs. Separate p50, p95 and p99 latency, success/error/degraded outcomes, and cache-hit/miss paths. Test at steady state, after cold start, during one component failure and throughout recovery. A system that survives the outage but collapses while replaying backlog has not completed its failure test.

Make a drill reproducible: state the starting dataset, failure time, expected invariant, maximum backlog and recovery criterion. Capture an operation trace that includes versions and identities, then verify the durable result after restart. Verify correctness and data-loss policy in addition to response latency; an API that returns quickly while double-selling or dropping acknowledged work has failed.

## Follow-up questions with answers

**What cannot be eventually consistent here?** The operation establishing this guarantee: Playback authorization is checked in the control plane; protected media access expires according to entitlement policy.

**What is the first scaling pressure to test?** Use the actual workload: Assume 5 million concurrent streams at 5 Mb/s: 25 Tb/s delivery. A 2-hour title encoded at an aggregate 20 Mb/s consumes about 18 GB before additional audio/subtitle tracks. These planning numbers exclude CDN redundancy.

**Which failure would invalidate the naive design?** A control-plane region fails while streams are already playing. Existing signed media access can continue until expiry; new session creation fails over according to replicated entitlement freshness. Very short token TTLs improve revocation but increase control-plane dependence.

**Why not introduce every distributed component immediately?** Pre-position popular titles near demand; origin fetch reduces storage but increases first-view latency and egress. Availability and consistency goals differ between catalogue browsing, licence grants and progress updates.

**How would you demonstrate the design works?** Playback under bandwidth changes, CDN origin loss, expired entitlement, concurrent device limit, regional rights change and licence-service degradation. Keep the expected invariant and recovery outcome visible in the results.

Conclude a walkthrough by narrating one successful critical request, one concurrent conflict and one uncertain failure. Name the durable authority, the partition key, the commit point and the observable recovery policy. Those four facts are more useful than a diagram whose boxes all say “highly available”.
