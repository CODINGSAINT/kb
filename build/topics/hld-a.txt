## Problem

Design a rate limiter for a public API. Each customer may send a limited number of requests – for example 100 per minute to the search API. Requests over the limit are rejected with HTTP `429 Too Many Requests` before they reach the backend.

The API runs on many gateway servers, so the limit must be shared: a customer must not get a fresh allowance on every server.

## Requirements

**Functional**

- Limit requests per client (API key or user ID) and per route, using configurable rules.
- Reject excess requests with `429` and tell the client when to retry.
- Allow short bursts while limiting the sustained rate.

**Non-functional**

- Very low latency: the check adds only a few milliseconds.
- Shared across all gateway servers.
- Highly available: a limiter outage must not take the whole API down.
- Scale: about 1 million active clients and 50,000 requests per second at peak.

Out of scope: billing quotas, DDoS protection at the network layer.

## Step 1: Clarify the requirements

> **💡 Tip**
> A rate limiter question is really "what exactly do we promise?". Pin that down before choosing an algorithm.

**Candidate:** Where does the limiter run – in the client or on our side?

**Interviewer:** On our side, before the API.

**Candidate:** Do we limit by user, by API key or by IP?

**Interviewer:** By API key, per route. Search might allow 100 requests a minute.

**Candidate:** Should short bursts be allowed?

**Interviewer:** Yes, a small burst is fine, but the average must stay under the limit.

**Candidate:** We have many gateway servers. Should they share one limit?

**Interviewer:** Yes. A customer must not get a fresh limit on every server.

**Candidate:** What if the limiter's storage is down?

**Interviewer:** Your call. Explain the trade-off.

**Functional requirements**

1. Limit requests per API key and route, using configurable rules.
2. Reject excess requests with `429 Too Many Requests` and a retry hint.
3. Allow short bursts while limiting the average rate.

**Non-functional requirements**

1. Adds only a few milliseconds per request.
2. Shared across all gateway servers.
3. A limiter outage must not take the whole API down.

## Step 2: Estimate the scale

> **💡 Tip**
> Round the numbers. The goal is to learn what the numbers mean for the design, not to be precise.

| Quantity | Calculation | Result |
| --- | --- | --- |
| Checks per second | one per request | 50,000/s peak |
| Memory per client-route | ~2 numbers + key ≈ 100 bytes | 1M clients × 3 routes × 100 B ≈ 300 MB |
| Redis capacity | one node does ~100k simple ops/s | 1–2 shards, plus replicas |

What it means: 50,000 checks a second fits one or two Redis shards, and the state is small enough to keep entirely in memory.

## Step 3: Choose the algorithm

Know these five and when each fits:

| Algorithm | Idea | Pros | Cons |
| --- | --- | --- | --- |
| **Fixed window counter** | Count requests in the current minute; reset at the boundary | Simplest, tiny memory | A burst at 0:59 and 1:00 can double the limit |
| **Sliding window log** | Store a timestamp for every request; count those in the last 60 s | Exact | Memory grows with traffic |
| **Sliding window counter** | Blend this minute's and last minute's counts by overlap | Smooth, small memory | Approximate |
| **Token bucket** | A bucket holds up to *C* tokens, refilled at *R* per second; each request spends one | Allows bursts, small memory, simple | Two parameters to tune |
| **Leaky bucket** | Requests enter a queue that drains at a fixed rate | Very smooth output | Bursts wait or are dropped; adds a queue |

> **⚖️ Design choice**
> Token bucket: it allows short bursts, needs only two numbers per client, and is what large API providers describe using.

**We choose the token bucket.** It is what AWS API Gateway and Stripe describe using, and it matches the requirement "allow bursts, limit the average".

How it behaves with capacity 5 and refill 2 tokens per second:

- 5 requests at the same instant: all allowed, bucket empty.
- 6th request at that instant: rejected with `429`.
- Half a second later: 1 token has refilled, so one more request is allowed.

![Animation: a token bucket with capacity 5 spends one token per request; five immediate requests empty it, the sixth is rejected with 429, and after half a second one refilled token admits one more request.](learning-figures/hld-2-bucket.gif)

The bucket only needs two numbers per client: current tokens and the last refill time. Refilling is calculated lazily when a request arrives:

```java
class TokenBucket {
    private final double capacity, refillPerSecond;
    private double tokens;
    private long lastRefillMillis;

    TokenBucket(double capacity, double refillPerSecond, long nowMillis) {
        this.capacity = capacity; this.refillPerSecond = refillPerSecond;
        this.tokens = capacity; this.lastRefillMillis = nowMillis;
    }

    synchronized boolean tryConsume(long nowMillis) {
        double elapsedSeconds = (nowMillis - lastRefillMillis) / 1000.0;
        tokens = Math.min(capacity, tokens + elapsedSeconds * refillPerSecond);
        lastRefillMillis = nowMillis;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
```

This works perfectly inside one server. The rest of the design is about making it work across many.

## Step 4: High-level design

[![Selected design: the client calls the API gateway, which runs the limiter, performs an atomic check in Redis using a Lua script and forwards the request to the backend only if allowed; limits come from a rules config.](designs/hld-2.svg)](designs/hld-2.svg)

**Where should the limiter run?** In the API gateway (or as middleware in front of every service). The gateway already sees every request and can reject early, so the backend never does wasted work. A separate "rate limiter service" adds a network hop; use one only if many non-gateway clients need it.

**Request flow**

1. A request arrives at any gateway server.
2. The gateway identifies the client (API key) and route, and finds the rule, e.g. search: capacity 100, refill 100/60 per second.
3. It runs one atomic check in Redis for the key `rl:key-42:search`.
4. Allowed: forward to the backend and add headers. Rejected: return `429`.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

**Rules** live in a config store (a YAML file or database) and are cached in each gateway, refreshed every few seconds. They are not read from the database on every request.

[![A shared admission decision before the backend: an authenticated gateway uses a cached policy and a small script on the Redis primary for the subject and route; allowed requests are forwarded, exhausted quota returns 429, and an unavailable store follows the route's failure policy.](learning-figures/ratelimit-flow.svg)](learning-figures/ratelimit-flow.svg)

## Step 5: Deep dive: counting across many servers

**Why not keep a bucket in each gateway's memory?** With 10 gateways, each would allow 100 per minute – the client gets 1,000. The state must be shared, so we put it in Redis, which is fast (sub-millisecond) and in memory.

**The race condition.** A naive version reads tokens, decides, then writes back:

| Time | Gateway A | Gateway B |
| --- | --- | --- |
| t1 | reads tokens = 1 | |
| t2 | | reads tokens = 1 |
| t3 | allows, writes 0 | |
| t4 | | allows, writes 0 – **two requests used one token** |

**The fix: do the read-refill-spend in one atomic step inside Redis.** Redis runs a Lua script without interleaving other commands, so it behaves like a tiny transaction:

```lua
-- KEYS[1] = bucket key, ARGV = capacity, refill per second, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local t        = redis.call('TIME')                       -- Redis's own clock, same for all gateways
local now      = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local ts     = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)

local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', now)
-- expire only after the bucket would have refilled to full anyway
redis.call('PEXPIRE', KEYS[1], math.ceil((capacity - tokens) / rate * 1000) + 1000)
return { allowed, math.floor(tokens) }
```

Two details worth saying:

- **Use Redis's clock (`TIME`), not each gateway's.** Gateways' clocks drift; one shared clock keeps refills consistent.
- **Choose the expiry carefully.** Idle buckets should disappear to save memory, but deleting a bucket too early recreates it *full*, handing out free tokens. Expire it only after it would have refilled to full anyway.

[![Expiry trap: a bucket with capacity 1000 refilling one token per second has only 60 tokens after 60 idle seconds; deleting it then would recreate it with 1000; the safe expiry waits until it would be full.](learning-figures/ratelimit-expiry.svg)](learning-figures/ratelimit-expiry.svg)

## Step 6: Scaling and failure handling

**Scaling Redis.** Shard by key (Redis Cluster hashes keys to slots), so different clients live on different shards. All gateways send the same key to the same shard, so the count stays shared. Add replicas for failover, not for decisions – a replica may be slightly behind.

**Hot clients.** One huge client always hits one shard. If that becomes a problem, give that client a few sub-buckets (e.g. split its limit across 4 keys and pick one at random) – an approximation, but it spreads load.

**When Redis is down or slow**, the gateway must still answer quickly:

| Policy | Behaviour | Use for |
| --- | --- | --- |
| Fail open | Allow the request (maybe with a local, per-gateway emergency limit) | Low-risk public reads |
| Fail closed | Return `503` | Expensive or sensitive routes (payments, login) |

Set a tight timeout (a few milliseconds) on the Redis call so a slow limiter does not slow every request.

**Multiple regions.** Keep a Redis per region and give each region a share of the limit, or accept that a global limit is approximate. A globally synchronized counter would add cross-region latency to every request.

**Monitoring.** Track allowed vs rejected counts per route, Redis latency, and how often fail-open is used. A sudden spike of `429`s may mean a broken client or a too-tight rule.

## Interviewer follow-ups

**Why not a fixed window – it's simpler?** A client can send 100 at 0:59 and 100 at 1:00: 200 in two seconds. Token bucket bounds bursts by its capacity. Fixed window is acceptable when that edge burst does not matter.

**Should we rate limit by IP or by user?** By authenticated key or user when possible. IPs are shared (offices, mobile carriers) and easy to rotate. Use IP limits only for unauthenticated endpoints such as login.

**How do clients behave well?** Return `Retry-After` and `X-RateLimit-Remaining`. Good clients back off with jitter instead of retrying immediately.

**Can a request cost more than one token?** Yes – an expensive export can cost 10. The Lua script already takes `cost` as an argument.

**What about limiting concurrent requests instead of rate?** That is a different limiter: a counter incremented at start and decremented at finish (with a timeout in case the request dies). Rate and concurrency answer different questions.

**Should a failed backend request get its token back?** Usually no – the attempt still used capacity, and refunds can be abused.

**How do you change a limit without restarting?** Rules are in a config store; gateways reload them periodically. A new capacity applies on the next request.

## Wrap up

We put a token-bucket limiter in the gateway, shared its state in Redis, and made the check atomic with a Lua script.

> **📝 Key takeaways**
> - Know the five algorithms; pick token bucket for bursts plus an average limit.
> - Limit in the gateway, before the backend does any work.
> - Share state in Redis and refill-check-spend atomically in one Lua script.
> - Decide fail-open or fail-closed per route, with a tight timeout.

## Problem

Design a distributed in-memory cache like Memcached or Redis Cluster. An online store shows the same product cards thousands of times per second; reading the database every time is slow and expensive. The cache keeps copies of hot data in memory across several machines.

The interview is about: how a key finds its machine, what happens when memory is full, how the cache stays consistent with the database, and what happens when a node dies.

## Requirements

**Functional**

- `get(key)`, `put(key, value, ttl)`, `delete(key)`.
- Entries expire after their TTL.
- When memory is full, evict the least recently used entries.

**Non-functional**

- Low latency: about 1 ms per operation inside a data centre.
- Scale: 200,000 reads per second at peak and about 20 GB of hot data, growing.
- High availability: losing one machine must not take the cache down.
- The database stays the source of truth; the cache can lose data without losing correctness.

Out of scope: persistence to disk, transactions across keys, pub/sub.

**Interviewer:** Product cards, about 1 KB each.

**Candidate:** How stale can the data be?

**Interviewer:** A few seconds is fine for display. Checkout always reads the database.

**Candidate:** Who loads data on a miss – the cache or the application?

**Interviewer:** Your choice.

**Candidate:** What happens when memory is full?

**Interviewer:** Evict something sensible.

**Candidate:** Must the cache survive a machine failure?

**Interviewer:** Losing some cached data is fine, but the cache must stay available.

**Functional requirements**

1. `get(key)`, `put(key, value, ttl)`, `delete(key)`.

**Non-functional requirements**

1. About 1 ms per operation.

## Step 3: API and the single-node design

```java
interface Cache {
    Optional<byte[]> get(String key);
    void put(String key, byte[] value, Duration ttl);
    void delete(String key);
}
```

Inside one node, the cache is a **hash map for O(1) lookup** plus a **doubly linked list ordered by recent use**. On every get or put, move the entry to the front; when memory is full, remove from the back. In Java, `LinkedHashMap` with access order gives exactly that:

```java
class LruCache<K, V> {
    private record Entry<V>(V value, long expiresAtMillis) {}

    private final int capacity;
    private final LinkedHashMap<K, Entry<V>> map;

    LruCache(int capacity) {
        this.capacity = capacity;
        this.map = new LinkedHashMap<>(16, 0.75f, true) {          // true = access order
            protected boolean removeEldestEntry(Map.Entry<K, Entry<V>> eldest) {
                return size() > LruCache.this.capacity;            // evict least recently used
            }
        };
    }

    synchronized V get(K key, long nowMillis) {
        Entry<V> e = map.get(key);                                 // also marks it recently used
        if (e == null) return null;
        if (nowMillis >= e.expiresAtMillis()) { map.remove(key); return null; }   // lazy expiry
        return e.value();
    }

    synchronized void put(K key, V value, long ttlMillis, long nowMillis) {
        map.put(key, new Entry<>(value, nowMillis + ttlMillis));
    }

    synchronized void delete(K key) { map.remove(key); }
}
```

![Animation: an LRU cache with room for three entries stores A, B and C; reading A makes it most recent; adding D evicts B, the least recently used entry.](learning-figures/hld-3-lru.gif)

Expired entries are removed **lazily** when read, plus a background sweep that samples keys (Redis does this) so memory does not fill with dead entries. Real caches bound by bytes, not entry count, but the idea is the same.

## Step 4: High-level design

[![Selected design: app servers call a cache client that maps each key to a shard using a hash ring built from the node list in a config service; shards keep data in memory with LRU; on a miss or a write the app goes to the database.](designs/hld-3.svg)](designs/hld-3.svg)

- **Cache client library** inside each app server. It hashes the key to find the right shard and talks to it directly – no extra hop.
- **Cache shards**: each owns part of the key space, stores it in memory with LRU and TTL, and has a replica.
- **Config service** (ZooKeeper, etcd or a cluster bus as in Redis Cluster): knows which nodes are alive and pushes the node list to clients.
- **Database**: the source of truth.

**Read (cache-aside)**: `get` from the cache; on a miss, read the database, `put` into the cache with a TTL, return.

**Write**: update the database first, then **delete** the cache key. The next read loads the fresh value.

[![Cache-aside flow: the app reads the cache; on a hit it returns the value; on a miss it reads the database and fills the cache with a TTL; on a write it updates the database and then deletes the cache key.](learning-figures/hld-3-cache-aside.svg)](learning-figures/hld-3-cache-aside.svg)

## Step 5: Deep dive: which shard owns a key? (the routing algorithm)

**Naive: `hash(key) % N`.** Works until N changes. Going from 4 to 5 nodes changes the shard for about 80% of keys – nearly the whole cache misses at once and the database is flooded.

**Consistent hashing.** Put nodes on a ring of hash values (0 to 2³²). A key belongs to the first node clockwise from its hash. Adding a node only takes keys from its neighbour: about 1/N of the keys move.

**Virtual nodes.** With only 4 points on the ring, the arcs are uneven. Give each physical node ~100 virtual points so the load evens out, and a removed node's keys spread over all remaining nodes instead of one.

```java
class HashRing {
    private final TreeMap<Long, String> ring = new TreeMap<>();
    private static final int VIRTUAL_NODES = 100;

    void addNode(String node) {
        for (int i = 0; i < VIRTUAL_NODES; i++) ring.put(hash(node + "#" + i), node);
    }

    void removeNode(String node) {
        for (int i = 0; i < VIRTUAL_NODES; i++) ring.remove(hash(node + "#" + i));
    }

    String nodeFor(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));    // first point clockwise
        return (e != null ? e : ring.firstEntry()).getValue();      // wrap around the ring
    }

    private static long hash(String s) {                             // Guava's Murmur3: fast and well spread
        return Integer.toUnsignedLong(Hashing.murmur3_32_fixed().hashString(s, UTF_8).asInt());
    }
}
```

![Animation: four nodes sit on a hash ring and each key goes to the next node clockwise; when node E is added between B and C, only the keys in that arc move to E while all other keys stay put.](learning-figures/hld-3-ring.gif)

Redis Cluster uses a similar idea with a fixed 16,384 hash slots that are assigned to nodes; moving a slot moves only its keys.

## Step 6: Deep dive: consistency, replication and hot spots

**Caching strategies** – know the names and the trade-offs:

| Strategy | Write path | Good for | Risk |
| --- | --- | --- | --- |
| **Cache-aside** (our choice) | App writes DB, deletes cache | Read-heavy data, simple | Short stale window |
| **Read-through** | Cache itself loads from DB on a miss | Hiding load logic | Cache needs DB access |
| **Write-through** | Write to cache and DB together | Data read right after writing | Slower writes |
| **Write-behind** | Write to cache, DB later | Very write-heavy data | Data loss if the cache dies |

> **⚠️ Common mistake**
> Updating the cache with the new value after a write. Two writers can update the cache in the opposite order to the database and leave the old value cached. Delete instead.

**Why delete instead of update on write?** If two writers update the cache in a different order than the database, the cache can keep the older value forever. Deleting is safer; the TTL is the safety net if a delete is lost.

**Replication and failover.** Each primary shard asynchronously copies writes to its replica. If a primary dies, the config service promotes the replica and clients update their ring. Some very recent writes may be lost – acceptable, because the database still has them.

**Thundering herd (cache stampede).** A hot key expires and 1,000 requests miss at once, all hitting the database. Fixes:

- **Request coalescing**: only one request per key loads from the database; the others wait for its result.
- **TTL jitter**: add a random few seconds to TTLs so many keys do not expire together.
- **Early refresh**: refresh a hot key shortly before it expires.

**Hot keys.** One product goes viral, and its single shard is overwhelmed. Options: a small in-process cache in each app server for the hottest keys (with a short TTL), or copy the key to several shards (`key#1`, `key#2`, …) and read a random copy.

**Cache down?** Reads go to the database, but limit how many concurrent misses the database receives and shed the rest; a full cache outage would otherwise become a database outage.

## Interviewer follow-ups

**LRU or LFU?** LRU keeps recently used items – good for most workloads. LFU keeps frequently used items – better when a few items stay popular for a long time, and it resists one-off scans. Redis supports both.

**Why not `hash % N`?** Adding or removing one node remaps most keys. Consistent hashing moves only about 1/N.

**What if the cache and database disagree?** The database wins. Keep TTLs as an upper bound on staleness, and never use the cache for decisions that need the latest value, such as stock at checkout.

**How do clients learn about node changes?** They subscribe to the config service (or, in Redis Cluster, get a `MOVED` redirect and refresh their slot map).

**How do you size memory?** Values plus keys plus per-entry overhead (often 50–100 bytes), plus fragmentation. Leave headroom; a full cache evicts constantly.

**How is this different from a CDN?** A CDN caches HTTP responses at the network edge near users. This cache sits next to the application and stores data objects.

## Wrap up

We built each node as a hash map with an LRU list, spread keys with consistent hashing, and used cache-aside with delete-on-write.

> **📝 Key takeaways**
> - One node = hash map + LRU list + TTL (lazy expiry plus a sampled sweep).
> - Consistent hashing with virtual nodes moves only ~1/N of keys when a node changes.
> - Cache-aside: read the cache, load on a miss, delete the key after a database write.
> - Protect the database from stampedes with request coalescing and TTL jitter.

## Problem

Design a notification system that sends push notifications, SMS and emails for an e-commerce app: "Your order has shipped", "Your OTP is 482193", "Flash sale starts in 1 hour".

Many internal services trigger notifications. The system must deliver them through external providers (Apple, Google, SMS gateways, email services) reliably, respect user preferences, and not spam anyone.

## Requirements

**Functional**

- Send push (iOS and Android), SMS and email.
- Other services trigger notifications through one API, using templates ("order_shipped" + order details).
- Respect user preferences (opted out of marketing email, quiet hours).
- Support scheduled notifications and priority (an OTP must not wait behind a marketing blast).
- Track status: sent, failed, delivered (when the provider tells us).

**Non-functional**

- Scale: about 10 million push, 5 million email and 1 million SMS per day; marketing campaigns cause large bursts.
- Reliable: an accepted notification is not lost; retries must not spam users.
- Soft real-time: OTPs within seconds; marketing can take minutes.

Out of scope: building the providers themselves, in-app inbox UI, campaign management tools.

## Step 1: Clarify the requirements

**Candidate:** Which channels do we support?

**Interviewer:** Push on iOS and Android, SMS and email.

**Candidate:** Who sends notifications to us?

**Interviewer:** Other internal services – orders, payments, marketing.

**Candidate:** Must every notification arrive exactly once?

**Interviewer:** None may be lost. A rare duplicate is acceptable.

**Candidate:** Can users opt out?

**Interviewer:** Yes, per channel and per category, and they can set quiet hours.

**Candidate:** Are some notifications more urgent than others?

**Interviewer:** Yes. An OTP must never wait behind a marketing campaign.

**Functional requirements**

1. Send push, SMS and email through one internal API, using templates.

**Non-functional requirements**

1. 10M push, 5M email and 1M SMS a day, with big campaign bursts.
2. No accepted notification is lost; retries must not spam users.

> Round the numbers. The goal is to learn what the numbers mean for the design, not to be precise.

| Quantity | Calculation | Result |

## Step 4: High-level design

[![Selected design: business services call the notification service, which reads preferences and devices, records the notification and enqueues one message per channel; channel workers consume, deliver through APNs, FCM, SMS and email providers, and record status and retries.](designs/hld-4.svg)](designs/hld-4.svg)

Walk through "order 847 shipped" for user 42:

1. The order service calls `POST /v1/notifications`.
2. The notification service checks `eventId` (already seen → return the existing id), loads user 42's preferences and devices, and drops channels the user opted out of.
3. It saves the notification and one `delivery` row per channel, then puts one message per channel on the right **queue** (Kafka topics or SQS queues): `push.normal`, `email.normal`.
4. **Workers** for each channel read from their queue, render the template, and call the provider: APNs for iPhones, FCM for Android, an SMS gateway such as Twilio, an email service such as SES or SendGrid.
5. Workers record SENT or FAILED. Providers later report delivery and opens through webhooks.

![Animation: the order service sends one event; the notification service checks preferences and enqueues a push message and an email message; separate workers deliver each through its provider; a provider timeout puts the email back for a retry with backoff.](learning-figures/hld-4-fanout.gif)

**Why queues in the middle?**

- **Decoupling**: the order service returns in milliseconds and never waits for Apple or an SMS gateway.
- **Absorbing bursts**: a 5-million-email campaign waits in the queue instead of overwhelming workers or the provider.
- **Isolation**: one queue per channel (and priority) means an SMS outage does not block push notifications, and marketing cannot delay OTPs.
- **Retries**: a failed message can be retried later without involving the caller.

[![Notification pipeline: an event is accepted once, preferences decide the channels, one message per channel goes to its own queue, workers render templates and call providers, and failures go back with backoff or to a dead-letter queue.](learning-figures/hld-4-pipeline.svg)](learning-figures/hld-4-pipeline.svg)

## Step 5: Deep dive: reliability without spamming

**Don't lose notifications.** Save the notification and delivery rows **before** acknowledging the caller, and only remove a message from the queue after the worker has recorded the result. If a worker crashes mid-send, the message becomes visible again and another worker picks it up.

**Retries with backoff.** Providers fail temporarily (timeouts, 5xx, rate limits). Retry with exponential backoff and jitter – for example 1 s, 4 s, 16 s, … – up to a limit. Permanent errors (invalid device token, bad email address) are not retried: mark FAILED and, for a dead token, delete it from `device`. After the last attempt, send the message to a **dead-letter queue** for inspection.

**At-least-once means possible duplicates.** If the provider accepted a push but our worker timed out before recording it, a retry sends it again. Reduce this by:

- de-duplicating callers with the unique `eventId`;
- passing a stable idempotency key to providers that support one (many email and SMS APIs do);
- checking the `delivery` row status before sending (skip if already SENT).

A rare duplicate "your order shipped" is acceptable; a lost OTP is worse. Say this trade-off out loud.

> **⚖️ Design choice**
> At-least-once delivery with de-duplication. A rare duplicate "order shipped" is acceptable; a lost OTP is not.

**Rate limiting per user.** No user should get 30 marketing pushes a day. Keep a counter per user per category (token bucket in Redis) and drop or delay notifications over the cap. OTP and security messages bypass marketing limits.

**Preferences and quiet hours.** Check them when the notification is accepted *and* again in the worker just before sending – the user may have opted out in between. During quiet hours, low-priority messages are rescheduled instead of sent.

## Step 6: Scaling and operations

| Concern | Approach |
| --- | --- |
| Throughput | Notification service and workers are stateless; add instances. Partition queues by userId. |
| Provider limits | Each provider allows N requests/s; workers use a shared rate limiter per provider so they do not get blocked. |
| Priorities | Separate high/normal/low queues; give high-priority workers dedicated capacity. |
| Scheduled sends | Store `sendAt`; a scheduler polls due notifications every few seconds and enqueues them. |
| Big campaigns | A campaign job reads the audience in pages and enqueues in batches, so it does not flood the queue at once. |
| Templates | Versioned; a message records the template version it used, so audits show exactly what was sent. |
| Monitoring | Queue depth and age, send rate, failure rate per provider, delivery and open rates, dead-letter count. |

**Provider outage.** If SMS gateway A fails, workers can switch to a backup gateway B (keep two for critical channels like OTP).

## Interviewer follow-ups

**How do you get device tokens?** The mobile app registers with APNs or FCM on install, receives a token, and sends it to our backend, which stores it in `device`. Tokens change and expire; refresh them on app start and delete tokens the provider rejects.

**Why not call providers directly from the order service?** It would slow the order flow, duplicate retry logic in every service, and let a provider outage break checkout.

**Kafka or SQS/RabbitMQ?** Either works. Kafka is great for very high throughput and replay; SQS or RabbitMQ give per-message acknowledgements and delays that make retries simple. Say what you would use and why.

**How do you guarantee order (e.g. "shipped" before "delivered")?** Partition the queue by userId so one user's messages are processed in order by one consumer. Strict order across channels is not guaranteed and usually not needed.

**How do you track opens and clicks?** Email: a tracking pixel and redirect links. Push: the app reports opens. Store events in an analytics pipeline, not in the main delivery table.

**What about users with many devices?** Send a push to each active device token. Remove tokens not seen for months.

We accepted notifications through one API, queued one message per channel and priority, and delivered through workers that retry safely.

## Problem

Design the news feed of a social network like Facebook, Instagram or LinkedIn. Users follow other users. When someone posts, their followers should see it in their home feed, newest (or most relevant) first, and scroll back through older posts.

The core problem: a feed is read far more often than posts are written, and some accounts have tens of millions of followers. Do we build each feed when a post is written, or when the feed is read?

## Requirements

**Functional**

- Publish a post (text, image links).
- Follow and unfollow users.
- View a home feed of posts from people you follow, newest first, with infinite scroll (pagination).

**Non-functional**

- Fast feed loads: under 200 ms.
- Scale: 100 million daily active users; each opens the feed about 10 times a day; 10 million new posts per day.
- New posts may take a few seconds to appear (eventual consistency is fine).
- Some users have 50 million followers.

Out of scope: comments and likes, ads, the ranking model itself, media storage and CDN details.

## Step 1: Clarify the requirements

**Candidate:** Is the feed chronological or ranked?

**Interviewer:** Start with newest first. Ranking is a follow-up.

**Candidate:** How quickly must a new post appear in followers' feeds?

**Interviewer:** A few seconds is fine.

**Candidate:** How many followers does a typical user have?

**Interviewer:** About 200 – but some celebrities have 50 million.

**Candidate:** How far back can people scroll?

**Interviewer:** Infinite scroll, but most people read only the latest few hundred posts.

**Candidate:** Do we need likes, comments and ads?

**Interviewer:** No, just posts, follows and the feed.

## Step 4: High-level design

[![Selected design: the post service saves posts and emits a new-post event; fanout workers read followers from the follow graph and push the post ID into each follower's feed cache; the feed service reads IDs from the feed cache and hydrates them from the post store, adding celebrity posts on read.](designs/hld-5.svg)](designs/hld-5.svg)

**Publish path**

1. The user creates a post; the post service stores it and returns.
2. It publishes a "new post" event to a queue.
3. Fanout workers look up the author's followers and add the post ID to the front of each follower's feed list in Redis (trimming each list to 500 IDs).

**Read path**

1. The feed service reads the first 20 post IDs from the user's feed list.
2. It fetches the posts (and author names, avatars) from caches in one batch – called **hydration**.
3. It returns them with a cursor for the next page.

[![Feed read path: the feed service reads post IDs from the user's precomputed feed list, merges recent posts from followed celebrities, fetches post bodies and author details in one batch, filters deleted or hidden posts, and returns a page with a cursor.](learning-figures/hld-5-read.svg)](learning-figures/hld-5-read.svg)

## Step 5: Deep dive: the fanout algorithm – on write vs on read

| | **Fanout on write (push)** | **Fanout on read (pull)** |
| --- | --- | --- |
| When work happens | When a post is created: copy its ID into every follower's feed | When a feed is opened: fetch recent posts from everyone you follow and merge |
| Feed read | Very fast – feed is precomputed | Slow – one query per followee, then merge |
| Write cost | High for authors with many followers | Cheap |
| Wasted work | Inactive users' feeds are updated anyway | None |
| Problem case | A celebrity post means 50 million inserts | A user following 2,000 accounts |

**Use a hybrid**, as large social networks describe doing:

- **Normal authors** (say, under 10,000 followers): fanout on write.
- **Celebrities**: no fanout. Their posts are kept in their own recent-posts list.
- **On read**: take the precomputed feed, then merge in recent posts from the few celebrities the user follows, sorted by post ID.

![Animation: Asha, with 200 followers, posts and fanout workers push the post ID into each follower's feed list; a celebrity with 50 million followers posts and nothing is pushed; when Ben opens his feed, his precomputed list is merged with the celebrity's recent posts.](learning-figures/hld-5-hybrid.gif)

```java
public List<Post> getFeed(long userId, int limit, Cursor cursor) {
    List<Long> ids = new ArrayList<>(feedCache.range(userId, cursor, limit));     // pushed posts
    for (long celeb : followGraph.celebritiesFollowedBy(userId)) {
        ids.addAll(recentPosts.range(celeb, cursor, limit));                      // pulled posts
    }
    List<Long> page = ids.stream()
            .distinct()
            .sorted(Comparator.reverseOrder())        // time-sortable IDs: newest first
            .limit(limit)
            .toList();
    return postCache.getAll(page).stream()             // batch hydrate
            .filter(p -> p != null && visibility.canSee(userId, p))   // deleted or hidden posts drop out
            .toList();
}
```

> **⚖️ Design choice**
> Store only post IDs in feeds. A post shared to 200 feeds is stored once, and editing or deleting it changes one row.

**Inactive users.** Skip fanout to users who have not logged in for 30 days; when they return, build their feed by pulling (a one-time cost).

**Fanout workers** are stateless and read from a partitioned queue. A celebrity threshold keeps any single post's fanout bounded, so one post cannot clog the workers for everyone else.

## Step 6: Pagination, ranking and failures

**Cursor pagination, not offsets.** `?page=2` breaks when new posts arrive – the user sees duplicates as everything shifts down. Use a cursor: "give me 20 posts with ID smaller than `p17`". Because IDs are time-sorted, new posts at the top do not disturb the next page.

**Ranking.** For a ranked feed, take a few hundred candidate IDs from the same sources, score them with a model (recency, closeness to the author, engagement), and cache the ranked order for this session so scrolling is stable.

**Deletes and privacy changes.** The feed cache may still hold a deleted post's ID. Hydration checks the post store, so deleted or newly private posts are dropped at read time. That is another reason to store IDs, not copies.

**Unfollow.** Stop showing the author's posts by filtering at read time against the current follow graph; a background job can remove old IDs from the cached list later.

**Failures**

- *Fanout lag*: posts appear a few seconds late; feeds still work.
- *Redis feed shard down*: rebuild that user's feed by pulling from followees (slower, but correct).
- *Hot celebrity post*: millions of hydrations of the same post hit one cache key; replicate hot posts in a local in-process cache.

## Interviewer follow-ups

**Why not just query "posts from everyone I follow ORDER BY time" on every load?** At 50k feed loads per second, each joining hundreds of followees, the database cannot keep up. Precomputing feeds trades write work for fast reads.

**How do you choose the celebrity threshold?** Measure fanout cost. Typical answers are 10k–100k followers; it can also depend on how often the author posts.

**How big is the feed cache and can we lose it?** About 400 GB of IDs here. It is a cache – if lost, rebuild feeds by pulling. Keep replicas to avoid a slow, mass rebuild.

**How do you show a new post to its author immediately?** Insert it into the author's own feed synchronously, or merge the author's latest posts on read. Followers see it after fanout.

**What about a user who follows 5,000 people?** Fanout on write handles it well – their feed is just a list. Pull would be expensive for them, which is why push is the default.

**How would you add likes and comment counts?** Store counters separately and fetch them during hydration; they change too often to copy into feed entries.

## Wrap up

We stored posts once, pushed post IDs into followers' feeds for normal authors, and pulled celebrity posts at read time.

> **📝 Key takeaways**
> - Fanout on write makes reads fast; fanout on read keeps writes cheap.
> - Hybrid: push for normal authors, pull for celebrities.
> - Feeds hold post IDs; hydrate and filter deleted posts at read time.
> - Paginate with an ID cursor, not page numbers.

## Problem

Design a chat system like WhatsApp: 1:1 and group messaging, real-time delivery, delivery and read receipts (✓✓), online presence, offline delivery, and history on multiple devices. The core topics are **persistent connections (WebSockets)**, **message ordering**, **delivery guarantees** and **presence**.

## Requirements

**Functional**
- 1:1 and group chat (≤ 1024 members). Text plus media (via object storage).
- Sent ✓, delivered ✓✓ and read receipts. Last seen and online status.
- Offline users receive messages on reconnect, plus a push notification.

**Non-functional**
- Delivery latency < 200 ms when both users are online. No message loss. Per-chat ordering.

**Scale:** 500M DAU and 50B messages/day ≈ 600k msgs/s average, more at peak. Around 100M concurrent connections; at ~100k per gateway box, that's ~1,000+ gateway servers.

## 1. Scope and selected guarantees

I support direct/group chat, offline replay, device delivery and read receipts. I choose one logical conversation owner for sequence allocation; independent conversations scale across partitions. Payload media lives in object storage. End-to-end encryption is a separate key-management requirement and is not implied by TLS.

## 2. Message protocol and persistence

```text
SEND(conversationId,clientMessageId,body) -> ACCEPTED(serverSeq,messageId)
RESUME(conversationId,afterSeq,deviceId) -> ordered messages
ACK_DELIVERED(deviceId,conversationId,seq); ACK_READ(userId,conversationId,seq)
Message PK(conversationId,seq), UNIQUE(senderId,clientMessageId)
DeviceCursor PK(deviceId,conversationId): deliveredSeq
```

The owner validates membership, returns a matching prior send on retry, allocates sequence and commits before ACCEPTED. Outbox/delivery fan-out pushes to live connections; reconnect fetches durable gaps. Concurrent senders receive one committed order independent of device clocks. At 100,000 envelopes/s and 500 bytes, raw history grows 4.32 TB/day before indexes/replication. Cursor updates are monotonic and scoped to device; a laptop cannot inherit proof of delivery from a phone. Presence expiry changes routing efficiency, not durability. Membership changes are checked before replay to avoid exposing removed-group history beyond the chosen policy.

A **conversation sequence** orders messages within one conversation. A **client message ID** deduplicates retries from the sender. A **delivery cursor** records what a particular device has received; multiple devices can have different cursors.

### Calculate and partition

At 100,000 messages/s and 500 bytes per stored envelope, raw message data grows about 50 MB/s or 4.32 TB/day before media, indexes and replicas. Store media objects separately and send authorized references. Partition message ownership by conversation to make ordering local rather than inventing one global sequence for every user.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

- **Connection gateways** hold WebSocket (or MQTT) connections. A **session registry** (Redis: `userId → gatewayId`) tracks where each user is connected.
- **Chat service** receives a message, assigns a per-conversation **sequence number**, persists it, then routes it to the recipient's gateway (looked up in the registry) via an internal pub/sub or RPC.
- **Message store:** Cassandra/HBase partitioned by `conversationId`, clustered by `seq`. Efficient "messages after seq X" queries.
- **Offline path:** if the recipient isn't connected, the message waits in the store or an inbox, plus a push notification. On reconnect, the client syncs from its last acked seq.
- **Media:** upload to object storage via a pre-signed URL. The message carries the URL (and an encryption key in E2E designs).

### Key design decisions & trade-offs

**1. WebSocket vs. long-polling.** WebSockets give bidirectional, low-overhead messaging, which suits chat. Long-polling is a fallback. Gateways are stateful, so you need draining on deploy and reconnect with resume.

**2. Ordering.** Global ordering is unnecessary and expensive. Order **per conversation** with a server-assigned monotonic seq (a counter per conversation, or a Snowflake ID plus tiebreak). Clients sort by seq, not by device clock.

**3. Delivery guarantees.** Client sends with a `clientMsgId` (for dedup on retry). Server persists, then acks "sent ✓". The recipient's device acks, giving "delivered ✓✓". Read acks travel the same way. That's at-least-once plus idempotent IDs, which gives effectively-once.

**4. Groups.** Fan-out on write to each member's gateway or inbox for small groups. For large groups, write once to the group log and have members pull by seq.

**5. Presence.** Heartbeats every ~30 s update `lastSeen` in Redis with a TTL. Fan presence changes out only to contacts who are currently viewing that chat, to avoid presence storms.

**6. Multi-device.** Each device keeps its own cursor (last seq) and syncs independently.

### Scope, guarantees and sizing assumptions

**Correctness requirement:** Messages have stable IDs and a defined per-conversation order; delivery and read receipts mean different things.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

**Upload path:**
1. The client gets a **pre-signed, resumable upload URL** and uploads chunks directly to object storage (S3/GCS), bypassing app servers.
2. Upload complete triggers an event, which enqueues a **transcode job** (DAG: split, then encode per resolution/codec in parallel, then package as HLS/DASH segments, plus thumbnails, content-ID scan).
3. Workers write the segments to object storage, update the **metadata DB** (`video → status, renditions, manifest URL`), and the video becomes public.

**Playback path:** the client fetches the manifest from the API, then the segments from the **CDN**. The player switches bitrate per segment based on measured bandwidth (ABR).

### Key design decisions & trade-offs

**1. Direct-to-storage uploads.** App servers never proxy video bytes. Resumable chunked upload (tus or S3 multipart) survives flaky mobile networks.

**2. Parallel transcoding.** Split the video into GOP-aligned chunks and encode them in parallel across workers, then stitch. A 1-hour video finishes in minutes instead of hours. The queue plus idempotent jobs (keyed by `videoId + rendition`) allows safe retries.

**3. Adaptive bitrate.** HLS/DASH segments (2–6 s) per rendition plus a manifest. Shorter segments adapt faster but mean more requests and less efficient caching.

**4. CDN strategy.** Popular videos are cached at edge PoPs worldwide. The long tail is served from regional origin caches (most videos are rarely watched). Pre-warm the CDN for big launches.

**5. Storage tiers.** Hot renditions on standard storage. Old, rarely watched videos move to cheaper tiers, and some renditions (4K of an unwatched video) can be dropped and regenerated on demand.

**6. View counts.** Don't update a DB row per view. Stream view events to Kafka, aggregate (with dedup and fraud filtering) and flush periodically. Counts are eventually consistent.

### Architecture

- **Control plane (cloud):** API gateway, auth, catalogue and metadata, the playback service (licence/DRM, manifest, choosing the CDN node), recommendations, billing. Microservices with bulkheads.

### Key design decisions & trade-offs
