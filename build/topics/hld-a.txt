## Problem

Design a rate limiter for a public API. Each customer may send only a certain number of requests – for example 100 per minute to the search API. Extra requests are rejected with HTTP `429 Too Many Requests` before they reach the backend.

The API runs on many gateway servers, so the limit must be shared. A customer must not get a fresh allowance on every server.

## Requirements

- Limit requests per API key and per route, using configurable rules.
- Allow short bursts, but limit the average rate.
- Reject extra requests with `429` and tell the client when to retry.
- Work the same across all gateway servers.
- Add only a few milliseconds to each request.

## Step 1: Clarify the requirements

> **💡 Tip**
> A rate limiter question is really "what exactly do we promise?". Pin that down before choosing an algorithm.

**Candidate:** Where does the limiter run – in the client or on our side?

**Interviewer:** On our side, before the API.

**Candidate:** Do we limit by user, API key or IP address?

**Interviewer:** By API key and route. Search might allow 100 requests a minute.

**Candidate:** Are short bursts allowed?

**Interviewer:** Yes, a small burst is fine, but the average must stay under the limit.

**Candidate:** We have many gateway servers. Do they share one limit?

**Interviewer:** Yes.

**Candidate:** What if the limiter's storage goes down?

**Interviewer:** Your call. Explain the trade-off.

**Functional requirements**

1. Limit requests per API key and route, using configurable rules.
2. Reject extra requests with `429` and a `Retry-After` hint.
3. Allow short bursts while limiting the average rate.

**Non-functional requirements**

1. Low latency: a few milliseconds per check.
2. Shared across all gateway servers.
3. A limiter outage must not take the whole API down.

## Step 2: Estimate the scale

> **💡 Tip**
> Round the numbers. The goal is to learn what they mean for the design.

**Traffic**

```text
Active API keys          ≈ 1 million
Peak requests per second ≈ 50,000
Limiter checks           = 1 per request ≈ 50,000 per second
```

What it means: one Redis node handles about 100,000 simple operations per second, so one or two shards are enough.

**Memory**

```text
State per key and route  = 2 numbers + key name ≈ 100 bytes
Keys × routes            = 1 million × 3 routes = 3 million buckets
Total                    = 3 million × 100 bytes ≈ 300 MB
```

What it means: all limiter state fits comfortably in memory.

## Step 3: Choose the algorithm

There are five classic algorithms. Know all five, then pick one.

**Option 1: Fixed window counter.** Count requests in the current minute; reset the count when the minute changes.

- Good: simplest possible, one number per key.
- Problem: a client can send 100 at 0:59 and 100 more at 1:00 – 200 in two seconds.

**Option 2: Sliding window log.** Store the time of every request and count those in the last 60 seconds.

- Good: exact.
- Problem: memory grows with traffic – one entry per request.

**Option 3: Sliding window counter.** Blend this minute's and last minute's counts by how much the window overlaps them.

- Good: smooth and small.
- Problem: an approximation.

**Option 4: Token bucket.** A bucket holds up to *C* tokens and refills at *R* tokens per second. Each request spends one token; no token, no entry.

- Good: allows bursts up to *C*, limits the average to *R*; only two numbers per key.
- Problem: two settings to tune.

**Option 5: Leaky bucket.** Requests join a queue that drains at a fixed rate.

- Good: perfectly smooth output.
- Problem: bursts wait or are dropped; adds a queue.

> **⚖️ Design choice**
> We use the **token bucket**. It matches "allow a burst, limit the average", needs two numbers per key, and is what large API providers describe using.

With capacity 5 and a refill of 2 tokens per second:

- 5 requests arrive together: all allowed, the bucket is empty.
- A 6th request at the same instant: rejected with `429`.
- Half a second later, 1 token has refilled: one more request is allowed.

![Animation: a token bucket with capacity 5 spends one token per request; five immediate requests empty it, the sixth is rejected with 429, and after half a second one refilled token admits one more request.](learning-figures/hld-2-bucket.gif)

The bucket refills lazily – only when a request arrives:

```java
class TokenBucket {
    private final double capacity, refillPerSecond;
    private double tokens;
    private long lastRefillMillis;

    TokenBucket(double capacity, double refillPerSecond, long nowMillis) {
        this.capacity = capacity;
        this.refillPerSecond = refillPerSecond;
        this.tokens = capacity;
        this.lastRefillMillis = nowMillis;
    }

    synchronized boolean tryConsume(long nowMillis) {
        double elapsedSeconds = (nowMillis - lastRefillMillis) / 1000.0;
        tokens = Math.min(capacity, tokens + elapsedSeconds * refillPerSecond);
        lastRefillMillis = nowMillis;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
```

This works inside one server. The rest of the design makes it work across many.

## Step 4: Define the API and the rules

The limiter is not a public API – it sits inside the gateway. Its contract is one call:

```text
check(apiKey, route) -> ALLOW (tokens left) | REJECT (retry after N ms)
```

Rejected requests get:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

Rules live in a config store and are cached in every gateway, refreshed every few seconds:

```yaml
- route: /search
  capacity: 100
  refillPerSecond: 1.67     # 100 per minute
- route: /orders
  capacity: 20
  refillPerSecond: 0.33
```

[![High-level design: the client calls the API gateway, which runs the limiter, does an atomic check in Redis with a Lua script, and forwards the request to the backend only if allowed; limits per route come from a rules config.](designs/hld-2.svg)](designs/hld-2.svg)

1. A request reaches any gateway server.
2. The gateway finds the API key and the rule for the route.
3. It runs one atomic check in Redis for the key `rl:key-42:search`.
4. **Allowed:** forward to the backend. **Rejected:** return `429` straight away.

> **⚖️ Design choice**
> Run the limiter inside the API gateway. The gateway already sees every request and can reject early, so the backend never does wasted work. A separate "limiter service" only adds a network hop.

[![A shared admission decision before the backend: the gateway uses a cached policy and a small script on the Redis primary for the key and route; allowed requests are forwarded, exhausted ones get 429, and an unavailable store follows the route's failure policy.](learning-figures/ratelimit-flow.svg)](learning-figures/ratelimit-flow.svg)

## Step 6: Go deep

### Why not keep the bucket in each gateway's memory?

With 10 gateways, each would allow 100 a minute – the customer gets 1,000. The state must be shared, so it lives in Redis: in memory, sub-millisecond, and shared by all gateways.

### The race condition

A naive version reads tokens, decides, then writes back:

1. Gateway A reads tokens = 1.
2. Gateway B reads tokens = 1.
3. A allows the request and writes 0.
4. B also allows its request and writes 0 – **two requests spent one token**.

> **⚠️ Common mistake**
> Using a separate `GET` and `SET` in Redis. Another gateway can run between them. The read, refill and spend must be one atomic step.

### The fix: one Lua script

Redis runs a Lua script without interleaving other commands, so read-refill-spend becomes a tiny transaction:

```lua
-- KEYS[1] = bucket key; ARGV = capacity, refill per second, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local t        = redis.call('TIME')                  -- Redis's clock: same for every gateway
local now      = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(state[1]) or capacity
local ts     = tonumber(state[2]) or now
tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)

local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', now)
-- forget the bucket only once it would have refilled to full anyway
redis.call('PEXPIRE', KEYS[1], math.ceil((capacity - tokens) / rate * 1000) + 1000)
return { allowed, math.floor(tokens) }
```

Two details worth saying:

- **Use Redis's clock**, not each gateway's. Gateway clocks drift; one clock keeps refills fair.
- **Expire idle buckets carefully.** Deleting a half-empty bucket too early recreates it *full*, handing out free tokens. Expire only once it would have refilled anyway.

[![Expiry trap: a bucket with capacity 1000 refilling one token per second has only 60 tokens after 60 idle seconds; deleting it then would recreate it with 1000, so the safe expiry waits until it would be full.](learning-figures/ratelimit-expiry.svg)](learning-figures/ratelimit-expiry.svg)

### Scaling Redis

Shard by key: Redis Cluster hashes each key to a shard, so different customers live on different shards and every gateway sends the same key to the same shard. Replicas are for failover only – a replica may be slightly behind.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| Redis is down or slow | Every request needs a check | Tight timeout (a few ms), then the route's policy: fail open (allow) for low-risk reads, fail closed (`503`) for payments or login |
| One huge customer | All its checks hit one shard | Split its limit across a few sub-keys and pick one at random – approximate but spread out |
| Clients retry immediately on `429` | Traffic gets worse | `Retry-After` header; well-behaved clients back off with jitter |
| Several regions | A global counter adds cross-region latency | A Redis per region with a share of the limit each |
| A rule is too tight | Many `429`s for a good customer | Monitor allowed vs rejected per route; rules reload without restarts |

## Putting it together

- **Check:** gateway → rule from cache → one Lua script in Redis → allow or `429`.
- **State:** two numbers per key and route, in memory, sharded by key, expiring when idle.
- **Failure:** tight timeout and an explicit fail-open or fail-closed policy per route.

## Interviewer follow-ups

**Should we limit by IP or by user?** By API key or user where possible. IPs are shared (offices, mobile networks) and easy to change. Use IP limits only for anonymous endpoints such as login.

**Can a request cost more than one token?** Yes – an expensive export can cost 10. The script already takes `cost`.

**What about limiting concurrent requests?** That is a different limiter: increment on start, decrement on finish, with a timeout in case a request dies.

**Should a failed backend request get its token back?** Usually no. The attempt still used capacity, and refunds can be abused.

## Wrap up

We put a token-bucket limiter in the gateway, shared its state in Redis, and made the check atomic with a Lua script.

> **📝 Key takeaways**
> - Know the five algorithms; pick token bucket for "bursts plus an average limit".
> - Limit in the gateway, before the backend does any work.
> - Share state in Redis and refill-check-spend atomically in one Lua script.
> - Decide fail-open or fail-closed per route, with a tight timeout.

## Problem

Design a distributed in-memory cache like Memcached or Redis Cluster. An online store shows the same product cards thousands of times a second; reading the database every time is slow and expensive. The cache keeps copies of hot data in memory across several machines.

The interview is about four questions: which machine holds a key, what happens when memory is full, how the cache stays in step with the database, and what happens when a machine dies.

## Requirements

- `get(key)`, `put(key, value, ttl)`, `delete(key)`.
- Entries expire after their time-to-live (TTL).
- When memory is full, remove the least recently used entries.
- About 1 ms per operation; 200,000 reads per second.
- Losing one machine must not take the cache down.

## Step 1: Clarify the requirements

**Candidate:** What are we caching, and how big is each item?

**Interviewer:** Product cards, about 1 KB each.

**Candidate:** How stale can the data be?

**Interviewer:** A few seconds is fine for display. Checkout always reads the database.

**Candidate:** Who loads data on a miss – the cache or the application?

**Interviewer:** Your choice.

**Candidate:** What happens when memory is full?

**Interviewer:** Evict something sensible.

**Candidate:** Must the cache survive a machine failure?

**Interviewer:** Losing some cached data is fine, but the cache must stay available.

**Functional requirements**

1. `get`, `put` with TTL, `delete`.
2. Expire entries after their TTL.
3. Evict the least recently used entries when memory is full.

**Non-functional requirements**

1. About 1 ms per operation.
2. 200,000 reads per second and ~20 GB of hot data, growing.
3. The database stays the source of truth; the cache may lose data but must stay available.

## Step 2: Estimate the scale

> **💡 Tip**
> Size memory, operations and database load. The database load *without* the cache is the number that scares people.

**Memory**

```text
Hot items         = 20 million product cards
Size per item     ≈ 1 KB (+ ~30% overhead)
Total             = 20 million × 1.3 KB  ≈ 26 GB
Usable per node   ≈ 8 GB  →  4 primary shards (with headroom)
With one replica  = 8 nodes
```

What it means: the data needs several machines, so we must decide which machine owns which key.

**Load**

```text
Reads per shard        = 200,000 / 4  = 50,000 per second   (easy for one node)
Database at 98% hits   = 200,000 × 2% = 4,000 reads per second
Database with no cache = 200,000 reads per second
```

What it means: if the whole cache disappears, the database load jumps 50 times. Protecting the database matters as much as the cache itself.

## Step 3: Define the API

```java
interface Cache {
    Optional<byte[]> get(String key);
    void put(String key, byte[] value, Duration ttl);
    void delete(String key);
}
```

Keys include a version of the format, for example `product-card:v1:784`, so a new card format never reads old bytes.

## Step 4: Design one cache node

Inside one node, the cache is a **hash map** (fast lookup) plus a **doubly linked list ordered by recent use**. Every get or put moves the entry to the front; when memory is full, remove from the back. Java's `LinkedHashMap` in access order gives exactly that:

```java
class LruCache<K, V> {
    private record Entry<V>(V value, long expiresAtMillis) {}

    private final int capacity;
    private final LinkedHashMap<K, Entry<V>> map;

    LruCache(int capacity) {
        this.capacity = capacity;
        this.map = new LinkedHashMap<>(16, 0.75f, true) {         // true = access order
            protected boolean removeEldestEntry(Map.Entry<K, Entry<V>> eldest) {
                return size() > LruCache.this.capacity;           // evict least recently used
            }
        };
    }

    synchronized V get(K key, long nowMillis) {
        Entry<V> e = map.get(key);                                // also marks it recently used
        if (e == null) return null;
        if (nowMillis >= e.expiresAtMillis()) {                   // expired: remove lazily
            map.remove(key);
            return null;
        }
        return e.value();
    }

    synchronized void put(K key, V value, long ttlMillis, long nowMillis) {
        map.put(key, new Entry<>(value, nowMillis + ttlMillis));
    }

    synchronized void delete(K key) { map.remove(key); }
}
```

![Animation: an LRU cache with room for three entries stores A, B and C; reading A makes it most recent; adding D evicts B, the least recently used entry.](learning-figures/hld-3-lru.gif)

Expired entries are removed when someone reads them, plus a background sweep that samples keys (Redis does this), so memory does not fill with dead entries.

> **⚖️ Design choice**
> LRU is the sensible default. LFU (least *frequently* used) suits items that stay popular for a long time and resists one-off scans. Redis offers both.

## Step 5: Draw the high-level design

[![High-level design: app servers call a cache client that maps each key to a shard using a hash ring built from the node list in a config service; shards keep data in memory with LRU; on a miss or a write the app goes to the database.](designs/hld-3.svg)](designs/hld-3.svg)

- **Cache client** – a library inside each app server. It hashes the key to find the shard and talks to it directly.
- **Cache shards** – each owns part of the keys, keeps them in memory with LRU and TTL, and has a replica.
- **Config service** – ZooKeeper, etcd or Redis Cluster's own gossip. It knows which nodes are alive and tells the clients.
- **Database** – the source of truth.

**Read path (cache-aside):** get from the cache; on a miss, read the database, put the value in the cache with a TTL, return it.

**Write path:** update the database first, then **delete** the cache key. The next read loads the fresh value.

[![Cache-aside flow: the app reads the cache; on a hit it returns the value; on a miss it reads the database and fills the cache with a TTL; on a write it updates the database and then deletes the cache key.](learning-figures/hld-3-cache-aside.svg)](learning-figures/hld-3-cache-aside.svg)

## Step 6: Go deep

### Which shard owns a key? (the routing algorithm)

**Option 1: `hash(key) % N`.**

- Good: trivial.
- Problem: change N from 4 to 5 and about 80% of keys move. The cache is suddenly empty and the database is flooded.

**Option 2: Consistent hashing.** Place the nodes on a ring of hash values. A key belongs to the first node clockwise from its hash.

- Good: adding a node only takes keys from its neighbour – about 1/N of keys move.
- Problem: with few nodes the arcs are uneven, so some nodes get more keys.

**Option 3: Consistent hashing with virtual nodes.** Give every machine ~100 points on the ring.

- Good: load evens out, and a removed node's keys spread over all the others.
- Problem: a slightly bigger routing table – trivial in practice.

> **⚖️ Design choice**
> Consistent hashing with virtual nodes. Redis Cluster uses the same idea with 16,384 fixed "slots" assigned to nodes; moving a slot moves only its keys.

```java
class HashRing {
    private static final int VIRTUAL_NODES = 100;
    private final TreeMap<Long, String> ring = new TreeMap<>();

    void addNode(String node) {
        for (int i = 0; i < VIRTUAL_NODES; i++) ring.put(hash(node + "#" + i), node);
    }

    void removeNode(String node) {
        for (int i = 0; i < VIRTUAL_NODES; i++) ring.remove(hash(node + "#" + i));
    }

    String nodeFor(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));   // first point clockwise
        return (e != null ? e : ring.firstEntry()).getValue();     // wrap around the ring
    }

    private static long hash(String s) {                            // Guava Murmur3: well spread
        return Integer.toUnsignedLong(Hashing.murmur3_32_fixed().hashString(s, UTF_8).asInt());
    }
}
```

![Animation: four nodes sit on a hash ring and each key goes to the next node clockwise; when node E is added between B and C, only the keys in that arc move to E while all other keys stay put.](learning-figures/hld-3-ring.gif)

### Keeping the cache in step with the database

| Strategy | Write path | Good for | Risk |
| --- | --- | --- | --- |
| **Cache-aside** (our choice) | App writes the DB, deletes the key | Read-heavy data | A short stale window |
| **Read-through** | The cache loads from the DB itself | Hiding load logic | The cache needs DB access |
| **Write-through** | Write cache and DB together | Data read right after writing | Slower writes |
| **Write-behind** | Write cache now, DB later | Very write-heavy data | Data loss if the cache dies |

> **⚠️ Common mistake**
> Updating the cache with the new value after a write. Two writers can update the cache in the opposite order to the database and leave the old value cached. Delete instead – the TTL is the safety net if a delete is lost.

### Replication and failover

Each primary shard copies writes to its replica in the background. If a primary dies, the config service promotes the replica and the clients update their ring. A few recent writes may be lost – fine, because the database still has them.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| A hot key expires (stampede) | 1,000 requests miss at once and all hit the database | Request coalescing: one request loads, the others wait for it; plus random jitter on TTLs |
| One product goes viral | Its single shard is overloaded | A tiny in-process cache on each app server, or copy the key to several shards and read a random copy |
| A shard dies | Its keys miss until the replica takes over | Automatic replica promotion; clients refresh their ring |
| The whole cache is down | Database load jumps 50× | Limit concurrent database reads and shed the rest instead of collapsing the database |
| Memory fills up | Constant eviction, low hit rate | Size for values + keys + overhead; leave headroom; watch the hit rate |

## Putting it together

- **Node:** hash map + LRU list + TTL; lazy expiry plus a sampled sweep.
- **Cluster:** consistent hashing with virtual nodes; config service for membership; one replica per shard.
- **Usage:** cache-aside reads; update the database, then delete the key; protect the database from stampedes.

## Interviewer follow-ups

**What if the cache and database disagree?** The database wins. TTLs cap how stale data can get, and decisions that need the latest value – stock at checkout – always read the database.

**How do clients learn about node changes?** They watch the config service, or (in Redis Cluster) receive a `MOVED` reply and refresh their slot map.

**How is this different from a CDN?** A CDN caches HTTP responses at the network edge, near users. This cache sits next to the application and stores data objects.

**Why delete on write instead of letting the TTL handle it?** Deleting makes the new value visible on the next read; waiting for the TTL would show stale data for its whole length.

## Wrap up

We built each node as a hash map with an LRU list, spread keys with consistent hashing, and used cache-aside with delete-on-write.

> **📝 Key takeaways**
> - One node = hash map + LRU list + TTL (lazy expiry plus a sampled sweep).
> - Consistent hashing with virtual nodes moves only ~1/N of keys when a node changes.
> - Cache-aside: read the cache, load on a miss, delete the key after a database write.
> - Protect the database from stampedes with request coalescing and TTL jitter.

## Problem

Design a notification system for an e-commerce app. It sends push notifications, SMS and emails such as "Your order has shipped", "Your OTP is 482193" and "Flash sale starts in 1 hour".

## Step 1: Clarify the requirements

**Interviewer:** Other internal services – orders, payments, marketing.

3. Priorities and scheduled sends; track delivery status.

**Non-functional requirements**

1. 10 million push, 5 million email and 1 million SMS a day, with big campaign bursts.
2. No accepted notification is lost; retries must not spam users.
3. OTPs arrive within seconds.

## Step 2: Estimate the scale

> **💡 Tip**
> For notification systems, the average is small – the bursts are what you design for.

**Traffic**

```text
Sends per day      = 10M + 5M + 1M      = 16 million
Average            = 16M / 86,400 s     ≈ 185 per second
Campaign burst     = 5M emails / 30 min ≈ 2,800 per second
```

What it means: the average is easy; bursts are 15 times bigger. Queues absorb bursts – not bigger servers.

**Storage**

```text
Log per notification ≈ 500 bytes
Per day              = 16M × 500 bytes ≈ 8 GB
90 days              ≈ 720 GB
```

What it means: delivery logs need a database built for lots of writes, and old logs should be archived.

Internal services call one endpoint:

```http

  "userId": 42,
```

`202 Accepted` means "we have it and will deliver it", not "delivered". `eventId` lets us ignore the same event if a caller sends it twice.

> **🎯 In the interview**
> Point out the difference between 200 and 202. The caller must never wait for Apple or an SMS gateway.

## Step 5: Draw the high-level design

[![High-level design: business services call the notification service, which reads preferences and devices, saves the notification and enqueues one message per channel; channel workers deliver through APNs, FCM, SMS and email providers and record status and retries.](designs/hld-4.svg)](designs/hld-4.svg)

Follow "order 847 shipped" for one user:

1. The order service calls `POST /v1/notifications`.
2. The notification service checks `eventId` (seen before → return the same ID), loads the user's preferences and devices, and drops channels the user switched off.
3. It saves the notification and one `delivery` row per channel, then puts one message per channel on its **queue**: `push.normal`, `email.normal`.
4. **Workers** for each channel read their queue, fill in the template, and call the provider: APNs for iPhones, FCM for Android, an SMS gateway, an email service.
5. Workers record SENT or FAILED. Providers later report delivery and opens through webhooks.

![Animation: the order service sends one event; the notification service checks preferences and enqueues a push message and an email message; separate workers deliver each through its provider; an email timeout goes back to the queue and is retried after a backoff.](learning-figures/hld-4-fanout.gif)

> **⚖️ Design choice**
> Queues in the middle. The caller returns in milliseconds, campaign bursts wait in the queue, an SMS outage cannot block push, and a failed message can be retried later without involving the caller.

## Step 6: Go deep

### Don't lose notifications

Save the notification **before** answering `202`. A worker removes a message from the queue only **after** it has recorded the result. If a worker crashes mid-send, the message becomes visible again and another worker picks it up.

### Retries with backoff

Providers fail temporarily: timeouts, 5xx errors, rate limits.

- Retry with exponential backoff and jitter: about 1 s, 4 s, 16 s…, up to a limit.
- Do **not** retry permanent errors (invalid device token, bad email address). Mark FAILED; delete dead device tokens.
- After the last attempt, move the message to a **dead-letter queue** for inspection.

[![Notification pipeline: an event is accepted once, preferences decide the channels, one message per channel goes to its own queue, workers render templates and call providers, and failures retry with backoff or go to a dead-letter queue.](learning-figures/hld-4-pipeline.svg)](learning-figures/hld-4-pipeline.svg)

### Duplicates

At-least-once delivery means a rare duplicate: the provider accepted a push, but our worker timed out before recording it, so the retry sends it again. Keep duplicates rare by:

- ignoring repeated `eventId`s from callers;
- passing a stable key to providers that support one (many SMS and email APIs do);
- skipping a send if the `delivery` row already says SENT.

> **⚖️ Design choice**
> At-least-once with de-duplication. A rare duplicate "your order shipped" is acceptable; a lost OTP is not.

### Priorities and spam control

- Separate high / normal / low queues, with workers reserved for high priority, so OTPs never wait.
- Rate-limit per user and category (a token bucket in Redis): nobody gets 30 marketing pushes a day. OTPs bypass marketing limits.
- Check preferences again in the worker just before sending – the user may have opted out in between. During quiet hours, low-priority messages are rescheduled.

> **⚠️ Common mistake**
> Calling providers directly from the order service. It slows checkout, repeats retry logic in every service, and lets an SMS outage break orders.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| A provider is down | Its channel stalls | Retries with backoff; a backup provider for critical channels like OTP SMS |
| A 5-million-email campaign | Huge burst | The campaign job enqueues in batches; the queue absorbs the rest |
| Provider rate limits | Requests rejected | Workers share a per-provider rate limiter |
| A worker crashes mid-send | Message seems lost | It reappears in the queue and another worker retries |
| Messages keep failing | Retries never end | Attempt limit, then the dead-letter queue and an alert |

## Putting it together

- **Accept:** de-duplicate by `eventId`, check preferences, save, return `202`.
- **Deliver:** one queue per channel and priority → workers → providers → record status.
- **Protect:** retries with backoff, dead letters, per-user rate limits and quiet hours.

**How do we get device tokens?** The mobile app registers with APNs or FCM on install and sends us the token. Tokens change; refresh them on app start and delete ones the provider rejects.

**Kafka or SQS/RabbitMQ?** Either. Kafka suits very high throughput and replay; SQS or RabbitMQ give per-message acknowledgement and delays that make retries easy.

**How do we track opens and clicks?** Email: a tracking pixel and redirect links. Push: the app reports opens. Send these events to analytics, not the delivery table.

We accepted notifications through one API, queued one message per channel and priority, and delivered them through workers that retry safely.

## Problem

Design the home feed of a social network like Instagram, Facebook or LinkedIn. Users follow other users. When someone posts, their followers see it in their feed, newest first, and can scroll back through older posts.

The big question: do we build each person's feed when a post is **written**, or when the feed is **read**? And what about accounts with tens of millions of followers?

## Requirements

- Publish a post; follow and unfollow users.
- View a home feed of posts from people you follow, newest first, with infinite scroll.
- Feed loads in under 200 ms.
- 100 million daily users; some accounts have 50 million followers.
- A new post may take a few seconds to appear.

## Step 1: Clarify the requirements

**Candidate:** Is the feed newest-first or ranked?

**Interviewer:** Start with newest first. Ranking is a follow-up.

**Candidate:** How quickly must a new post show up for followers?

**Interviewer:** A few seconds is fine.

**Candidate:** How many followers does a typical user have?

**Interviewer:** About 200. Some celebrities have 50 million.

**Candidate:** How far back do people scroll?

**Interviewer:** Infinite scroll, but most people read only the latest few hundred posts.

**Candidate:** Do we need likes, comments and ads?

**Interviewer:** No. Posts, follows and the feed.

> **🎯 In the interview**
> The celebrity question is the heart of this problem. Ask it in your first five minutes.

**Functional requirements**

1. Publish a post.
2. Follow and unfollow users.
3. View a home feed, newest first, with infinite scroll.

**Non-functional requirements**

1. Feed loads in under 200 ms.
2. 100 million daily users, about 10 feed loads each.
3. Eventual consistency: a post may take a few seconds to appear.

## Step 2: Estimate the scale

> **💡 Tip**
> Compare reads with writes. The ratio tells you where to spend effort.

**Traffic**

```text
Feed loads     = 100M users × 10 / 86,400 s ≈ 11,600 per second (peak ~50,000)
New posts      = 10M per day / 86,400 s     ≈ 115 per second
Ratio          ≈ 100 feed reads for every post
```

What it means: reads dominate, so it pays to prepare feeds ahead of time.

**Fanout**

```text
Feed inserts if every post is pushed = 10M posts × 200 followers = 2 billion per day ≈ 23,000/s
One celebrity post                   = 50 million inserts
```

What it means: pushing works for normal users, but not for celebrities.

**Feed cache**

```text
Per user  = 500 post IDs × 8 bytes = 4 KB
All users = 100M × 4 KB            ≈ 400 GB  → a Redis cluster
```

What it means: storing only post IDs keeps the cache affordable.

## Step 6: Go deep

### The fanout algorithm: on write or on read?

**Option 1: Fanout on write (push).** When Asha posts, copy the post ID into every follower's feed.

- Good: reading a feed is one fast lookup.
- Problem: a celebrity post means 50 million writes; inactive users' feeds are updated for nothing.

**Option 2: Fanout on read (pull).** When Ben opens his feed, fetch recent posts from everyone he follows and merge them.

- Good: posting is cheap.
- Problem: every feed load queries hundreds of accounts – too slow at 50,000 loads a second.

**Option 3: Hybrid.** Push for normal authors; pull for celebrities.

- Good: fast reads and bounded writes.
- Problem: two code paths to maintain.

> **⚖️ Design choice**
> The **hybrid**, as large social networks describe doing. Authors under a threshold (say 10,000 followers) are pushed; celebrities' posts stay in their own recent-posts list and are merged in when a follower reads the feed.

![Animation: Asha, with 200 followers, posts and fanout workers push the post ID into each follower's feed list; a celebrity with 50 million followers posts and nothing is pushed; when Ben opens his feed, his prepared list is merged with the celebrity's recent posts.](learning-figures/hld-5-hybrid.gif)

```java
public List<Post> getFeed(long userId, int limit, Cursor cursor) {
    List<Long> ids = new ArrayList<>(feedCache.range(userId, cursor, limit));   // pushed
    for (long celeb : followGraph.celebritiesFollowedBy(userId)) {
        ids.addAll(recentPosts.range(celeb, cursor, limit));                    // pulled
    }
    List<Long> page = ids.stream()
            .distinct()
            .sorted(Comparator.reverseOrder())       // time-sortable IDs: newest first
            .limit(limit)
            .toList();
    return postCache.getAll(page).stream()            // one batch fetch
            .filter(p -> p != null && visibility.canSee(userId, p))
            .toList();
}
```

### Store IDs, not posts

The feed cache holds only post IDs. A post shared to 200 feeds is stored once, and deleting or editing it changes one row. Deleted or newly private posts drop out at read time, when we fetch them.

### Cursors, not page numbers

`?page=2` breaks when new posts arrive: everything shifts down and Ben sees the same posts twice. A cursor says "give me 20 posts older than this ID". New posts at the top never disturb the next page.

> **⚠️ Common mistake**
> Using `OFFSET 20 LIMIT 20` for an infinite feed. It repeats or skips posts as new ones arrive, and gets slower the deeper you scroll.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| A celebrity posts | Pushing would mean 50M writes | Don't push; pull and merge at read time |
| Fanout workers fall behind | Posts appear late | Acceptable for a few seconds; scale workers on queue depth |
| A feed-cache shard is lost | Those users have no prepared feed | Rebuild by pulling from the accounts they follow |
| A hot post is read millions of times | One cache key is hammered | Copy it into small in-process caches on the feed servers |
| Inactive users | Fanout wasted on them | Skip users inactive for 30 days; build their feed on return |

## Putting it together

- **Write:** save the post → queue → fanout workers push its ID to followers (not for celebrities).
- **Read:** prepared IDs + celebrity posts → merge by ID → batch fetch → filter → page with a cursor.
- **Scale:** feeds are caches of IDs; anything lost can be rebuilt by pulling.

## Interviewer follow-ups

**How do you choose the celebrity threshold?** Measure fanout cost; 10,000–100,000 followers is typical. How often the author posts matters too.

**How do you show my own post to me immediately?** Insert it into my own feed straight away, or merge my latest posts on read. Followers see it after fanout.

**How would you rank the feed?** Take a few hundred candidate IDs from the same sources, score them with a model (recency, closeness to the author, engagement), and keep that order for the scrolling session so pages stay stable.

**How do you handle unfollow?** Filter at read time against the current follow graph; a background job can clean old IDs out of the list later.

## Wrap up

We stored posts once, pushed post IDs into followers' feeds for normal authors, and pulled celebrity posts at read time.

> **📝 Key takeaways**
> - Fanout on write makes reads fast; fanout on read keeps writes cheap.
> - Hybrid: push for normal authors, pull for celebrities.
> - Feeds hold post IDs; fetch and filter deleted posts at read time.
> - Paginate with a cursor, not page numbers.

## Problem

Design a chat system like WhatsApp: 1:1 and group messaging, real-time delivery, delivery and read receipts (✓✓), online presence, offline delivery, and history on multiple devices. The core topics are **persistent connections (WebSockets)**, **message ordering**, **delivery guarantees** and **presence**.

## Requirements

**Functional**
- 1:1 and group chat (≤ 1024 members). Text plus media (via object storage).
- Sent ✓, delivered ✓✓ and read receipts. Last seen and online status.
- Offline users receive messages on reconnect, plus a push notification.

**Non-functional**
- Delivery latency < 200 ms when both users are online. No message loss. Per-chat ordering.

**Scale:** 500M DAU and 50B messages/day ≈ 600k msgs/s average, more at peak. Around 100M concurrent connections; at ~100k per gateway box, that's ~1,000+ gateway servers.

## 1. Scope and selected guarantees

I support direct/group chat, offline replay, device delivery and read receipts. I choose one logical conversation owner for sequence allocation; independent conversations scale across partitions. Payload media lives in object storage. End-to-end encryption is a separate key-management requirement and is not implied by TLS.

## 2. Message protocol and persistence

```text
SEND(conversationId,clientMessageId,body) -> ACCEPTED(serverSeq,messageId)
RESUME(conversationId,afterSeq,deviceId) -> ordered messages
ACK_DELIVERED(deviceId,conversationId,seq); ACK_READ(userId,conversationId,seq)
Message PK(conversationId,seq), UNIQUE(senderId,clientMessageId)
DeviceCursor PK(deviceId,conversationId): deliveredSeq
```

The owner validates membership, returns a matching prior send on retry, allocates sequence and commits before ACCEPTED. Outbox/delivery fan-out pushes to live connections; reconnect fetches durable gaps. Concurrent senders receive one committed order independent of device clocks. At 100,000 envelopes/s and 500 bytes, raw history grows 4.32 TB/day before indexes/replication. Cursor updates are monotonic and scoped to device; a laptop cannot inherit proof of delivery from a phone. Presence expiry changes routing efficiency, not durability. Membership changes are checked before replay to avoid exposing removed-group history beyond the chosen policy.

### Calculate and partition

At 100,000 messages/s and 500 bytes per stored envelope, raw message data grows about 50 MB/s or 4.32 TB/day before media, indexes and replicas. Store media objects separately and send authorized references. Partition message ownership by conversation to make ordering local rather than inventing one global sequence for every user.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

- **Connection gateways** hold WebSocket (or MQTT) connections. A **session registry** (Redis: `userId → gatewayId`) tracks where each user is connected.
- **Chat service** receives a message, assigns a per-conversation **sequence number**, persists it, then routes it to the recipient's gateway (looked up in the registry) via an internal pub/sub or RPC.
- **Message store:** Cassandra/HBase partitioned by `conversationId`, clustered by `seq`. Efficient "messages after seq X" queries.
- **Offline path:** if the recipient isn't connected, the message waits in the store or an inbox, plus a push notification. On reconnect, the client syncs from its last acked seq.
- **Media:** upload to object storage via a pre-signed URL. The message carries the URL (and an encryption key in E2E designs).

### Key design decisions & trade-offs

**1. WebSocket vs. long-polling.** WebSockets give bidirectional, low-overhead messaging, which suits chat. Long-polling is a fallback. Gateways are stateful, so you need draining on deploy and reconnect with resume.

**2. Ordering.** Global ordering is unnecessary and expensive. Order **per conversation** with a server-assigned monotonic seq (a counter per conversation, or a Snowflake ID plus tiebreak). Clients sort by seq, not by device clock.

**3. Delivery guarantees.** Client sends with a `clientMsgId` (for dedup on retry). Server persists, then acks "sent ✓". The recipient's device acks, giving "delivered ✓✓". Read acks travel the same way. That's at-least-once plus idempotent IDs, which gives effectively-once.

**4. Groups.** Fan-out on write to each member's gateway or inbox for small groups. For large groups, write once to the group log and have members pull by seq.

**5. Presence.** Heartbeats every ~30 s update `lastSeen` in Redis with a TTL. Fan presence changes out only to contacts who are currently viewing that chat, to avoid presence storms.

**6. Multi-device.** Each device keeps its own cursor (last seq) and syncs independently.

### Scope, guarantees and sizing assumptions

**Correctness requirement:** Messages have stable IDs and a defined per-conversation order; delivery and read receipts mean different things.

Assume 1 million concurrently connected clients and 50,000 messages/s. At 1 KB/message, ingress is 50 MB/s before replication and group fanout. A 1,000-member group can amplify one message into 1,000 delivery attempts.

### API contracts and data ownership

```text
POST /conversations/{id}/messages with clientMessageId; GET /messages?after=sequence; authenticated WebSocket events and receipt acknowledgements
```

```text
Logical records (outline, not complete DDL):
message(conversation_id,sequence,message_id,sender_id,ciphertext_or_body_ref); device_cursor(user,device,conversation,last_delivered,last_read)

Primary access/partitioning boundary:
conversation_id for ordering; user_id/device_id for connection routing and inbox cursors
```

### Build the architecture in stages

**Stage 3 — Partition and isolate.** Partition around conversation_id for ordering; user_id/device_id for connection routing and inbox cursors. Track ownership with a routing epoch or a database-native partition mechanism. Move virtual buckets or copy/backfill data with a verified cutover, rather than changing a modulo divisor and assuming records move themselves. Isolate bulk/background workloads from the latency-sensitive path and test the busiest tenant independently.

### Trace the critical request

Authenticate session and membership; deduplicate client message ID; persist with conversation sequence; acknowledge durable acceptance; publish delivery events; gateways send to online devices; offline devices catch up using sequence cursors. Read receipts update only after an explicit user/device read signal.

### Deep dive: the decision that changes this system

WebSockets provide a transport, not durable delivery. Reconnect can replay messages and receipts; clients deduplicate by message ID and request gaps. Per-conversation sequencing avoids an unnecessary global order. End-to-end encryption changes searchable metadata, key management and multi-device history design.

### Failure and race-condition walkthrough

A gateway dies after persistence but before client acknowledgement. Retrying the same client message ID returns the original message. A presence cache can be wrong without losing the durable inbox.

### Security, tenancy and lifecycle

### Trade-offs and a starting recommendation

Small groups can fanout on write; very large channels favor shared logs and read cursors. Ordering across two independent conversations is usually unnecessary. Push notification delivery is not a read receipt.

**Which failure would invalidate the naive design?** A gateway dies after persistence but before client acknowledgement. Retrying the same client message ID returns the original message. A presence cache can be wrong without losing the durable inbox.

**Why not introduce every distributed component immediately?** Small groups can fanout on write; very large channels favor shared logs and read cursors. Ordering across two independent conversations is usually unnecessary. Push notification delivery is not a read receipt.

**How would you demonstrate the design works?** Reconnect after a lost acknowledgement, duplicate send, device clock skew, group membership change during delivery, gaps in sequence and offline device catch-up. Keep the expected invariant and recovery outcome visible in the results.

### Work through ordering and presence

Two concurrent senders can each show optimistic local messages, but the server must choose the conversation's committed order. Device clocks are not a reliable total-order authority. Gaps in a receiver's sequence should trigger replay rather than an assumption that missing messages were deleted.

Presence is soft state with expiry: a disconnected mobile app can appear online briefly. Do not make durable delivery depend on a perfectly accurate online flag. End-to-end encryption changes what servers can inspect and index; explain its key/device model separately from transport TLS.

## 6. Interviewer follow-ups

**Does a WebSocket write prove delivery?** No. It may only enqueue bytes locally; require protocol-level evidence for stronger claims.

**Can Bob's laptop reuse his phone's cursor?** Not blindly. Device delivery state differs even if read state is shared by policy.

## 7. Closing answer

I acknowledge a message after durable conversation-ordered storage, deduplicate by sender message identity and replay from per-device cursors. Persistent messages survive offline recipients; presence is only a soft hint. Accepted, delivered and read acknowledgements remain separate.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

**Upload path:**
1. The client gets a **pre-signed, resumable upload URL** and uploads chunks directly to object storage (S3/GCS), bypassing app servers.
2. Upload complete triggers an event, which enqueues a **transcode job** (DAG: split, then encode per resolution/codec in parallel, then package as HLS/DASH segments, plus thumbnails, content-ID scan).
3. Workers write the segments to object storage, update the **metadata DB** (`video → status, renditions, manifest URL`), and the video becomes public.

**Playback path:** the client fetches the manifest from the API, then the segments from the **CDN**. The player switches bitrate per segment based on measured bandwidth (ABR).

### Key design decisions & trade-offs

**1. Direct-to-storage uploads.** App servers never proxy video bytes. Resumable chunked upload (tus or S3 multipart) survives flaky mobile networks.

**2. Parallel transcoding.** Split the video into GOP-aligned chunks and encode them in parallel across workers, then stitch. A 1-hour video finishes in minutes instead of hours. The queue plus idempotent jobs (keyed by `videoId + rendition`) allows safe retries.

**3. Adaptive bitrate.** HLS/DASH segments (2–6 s) per rendition plus a manifest. Shorter segments adapt faster but mean more requests and less efficient caching.

**4. CDN strategy.** Popular videos are cached at edge PoPs worldwide. The long tail is served from regional origin caches (most videos are rarely watched). Pre-warm the CDN for big launches.

**5. Storage tiers.** Hot renditions on standard storage. Old, rarely watched videos move to cheaper tiers, and some renditions (4K of an unwatched video) can be dropped and regenerated on demand.

**6. View counts.** Don't update a DB row per view. Stream view events to Kafka, aggregate (with dedup and fraud filtering) and flush periodically. Counts are eventually consistent.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

- **Control plane (cloud):** API gateway, auth, catalogue and metadata, the playback service (licence/DRM, manifest, choosing the CDN node), recommendations, billing. Microservices with bulkheads.
- **Data plane (Open Connect CDN):** Netflix's own cache appliances placed **inside ISPs** and at IXPs. Content is **pre-positioned overnight** based on predicted popularity, so peak traffic stays inside the ISP network.

### Key design decisions & trade-offs

**1. Own CDN vs. a commercial CDN.** At this volume, owning the edge (free appliances for ISPs) cuts cost and improves quality. YouTube-like long-tail catalogues benefit less from pre-positioning, while Netflix's catalogue is fixed and predictable.

**3. Per-title encoding.** An animated show looks great at a low bitrate; an action film needs more. Tailored ladders save bandwidth for the same perceived quality.

**4. Recommendations.** Viewing events go through Kafka into a data lake, then offline model training (collaborative filtering plus deep models). Results are precomputed per profile and cached, with real-time context re-ranking. Even artwork is personalised.

**5. Resilience.** Multi-region active-active. Circuit breakers, timeouts, fallbacks (if recommendations are down, show popular titles). **Chaos engineering** proves it. Playback must keep working even when the home page degrades.

**6. Resume across devices.** Heartbeat events write the playback position to a fast KV store keyed by profile and title.
