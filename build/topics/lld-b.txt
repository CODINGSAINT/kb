## Problem

Design the core of a cab-booking app like Uber or Ola. A rider asks for a ride from a pickup point to a drop point. The app finds a nearby driver, the driver accepts, picks the rider up, finishes the trip, and the rider pays a fare.

The hard part: many riders request at once, and **one driver must never be assigned to two trips**.

## Requirements

- Request a ride with pickup, drop and vehicle type (mini, sedan, SUV).
- Find nearby available drivers of that type; a driver accepts or declines.
- Track the trip: driver assigned, arrived, in progress, completed.
- Calculate the fare from distance and time.
- A rider has at most one active trip.

## Step 1: Clarify the requirements

**Candidate:** How do we pick a driver for a request?

**Interviewer:** Nearby, available, and with the vehicle type the rider asked for.

**Candidate:** Does the driver have to accept?

**Interviewer:** Yes. If they don't, try the next driver.

**Candidate:** Can a rider have two trips at once?

**Interviewer:** No.

**Candidate:** How is the fare calculated?

**Interviewer:** ₹40 base, ₹12 per km, ₹2 per minute. Surge is a follow-up.

**Candidate:** Should I cover maps and payments?

**Interviewer:** No. Assume a distance function and a payment step.

> **🎯 In the interview**
> Say the core risk out loud early: "one driver must never be assigned to two trips". Then design towards it.

| Functional | Non-functional |
| --- | --- |
| Request a ride with pickup, drop and type | One driver, one trip – always |
| Match nearby drivers; driver accepts | Matching and pricing rules are replaceable |
| Track the trip; calculate the fare | Fast matching with many online drivers |

## Step 2: Identify the core objects

- **Location** – a point on the map, with a distance function.
- **Driver** – name, vehicle type, current location and status (offline, available, on trip).
- **Trip** – one ride: rider, pickup, drop, status, assigned driver and fare.
- **MatchingStrategy** – how we choose candidate drivers.
- **FareStrategy** – how we price a trip.
- **RideService** – the coordinator: request, accept, arrive, start, end.

[![Selected design: the Rider requests a ride from RideService, which asks a MatchingStrategy for nearby drivers, claims one Driver atomically, creates and updates the Trip and uses a FareStrategy for the final fare.](designs/lld-7.svg)](designs/lld-7.svg)

> **⚖️ Design choice**
> A driver is assigned when they **accept**, not when the search finds them. Search results are only suggestions; the accept step is where we guarantee one driver, one trip.

## Step 3: Design the classes

### Trip and its states

A trip moves forward through fixed states. Each step is only allowed from the state before it, so a trip can never be "completed" before it started.

[![Trip lifecycle: REQUESTED to DRIVER_ASSIGNED when a driver accepts, to DRIVER_ARRIVED, to IN_PROGRESS when the rider is picked up, to COMPLETED at the drop; cancellation is allowed before the trip starts.](learning-figures/lld-7-states.svg)](learning-figures/lld-7-states.svg)

### Driver

A driver's status is an `AtomicReference`. Claiming a driver is one atomic step: "become ON_TRIP, but only if still AVAILABLE".

### MatchingStrategy and FareStrategy

Both are interfaces. "Nearest driver" can later become "fastest arrival time"; standard fares can later get surge pricing – without touching `RideService`.

### RideService

Holds the drivers and the strategies, and runs every step of a trip.

[![Class diagram: RideService manages Trips and uses a MatchingStrategy and a FareStrategy; a Trip links a rider and, after acceptance, one Driver; a Driver has a vehicle type, a location and an atomic status.](learning-figures/lld-7-classes.svg)](learning-figures/lld-7-classes.svg)

### Enums and Location

```java
enum VehicleType { MINI, SEDAN, SUV }
enum DriverStatus { OFFLINE, AVAILABLE, ON_TRIP }

    REQUESTED, DRIVER_ASSIGNED, DRIVER_ARRIVED, IN_PROGRESS, COMPLETED, CANCELLED
```

```java
record Location(double lat, double lng) {
    /** Straight-line distance in km (haversine). Real apps use road ETA. */
    double distanceKm(Location o) {
        double dLat = Math.toRadians(o.lat - lat), dLng = Math.toRadians(o.lng - lng);
        double a = Math.pow(Math.sin(dLat / 2), 2) + Math.cos(Math.toRadians(lat))
                * Math.cos(Math.toRadians(o.lat)) * Math.pow(Math.sin(dLng / 2), 2);
        return 6371 * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a));
    }
}
```

### Driver

```java
class Driver {
    private final String name;
    private final VehicleType type;
    private volatile Location location;
    private final AtomicReference<DriverStatus> status =
            new AtomicReference<>(DriverStatus.OFFLINE);

    Driver(String name, VehicleType type, Location location) {
        this.name = name; this.type = type; this.location = location;
    }
    void goOnline()           { status.set(DriverStatus.AVAILABLE); }
    /** Atomic: becomes ON_TRIP only if still AVAILABLE. */
    boolean tryClaim() {
        return status.compareAndSet(DriverStatus.AVAILABLE, DriverStatus.ON_TRIP);
    }
    void release()            { status.set(DriverStatus.AVAILABLE); }
    String getName()          { return name; }
    VehicleType getType()     { return type; }
    Location getLocation()    { return location; }
    DriverStatus getStatus()  { return status.get(); }
}
```

### Trip

```java
class Trip {
    private final String rider;
    private final Location pickup, drop;
    private final VehicleType type;
    private TripStatus status = TripStatus.REQUESTED;
    private Driver driver;
    private long fareRupees;

    Trip(String rider, Location pickup, Location drop, VehicleType type) {
        this.rider = rider; this.pickup = pickup; this.drop = drop; this.type = type;
    }
    /** Moves to the next status only from the expected one. */
    void transition(TripStatus from, TripStatus to) {
        if (status != from) {
            throw new IllegalStateException("Trip is " + status + ", not " + from);
        }
        status = to;
    }
    void assign(Driver d) {
        transition(TripStatus.REQUESTED, TripStatus.DRIVER_ASSIGNED);
        driver = d;
    }
    String getRider()        { return rider; }
    Location getPickup()     { return pickup; }
    VehicleType getType()    { return type; }
    TripStatus getStatus()   { return status; }
    Driver getDriver()       { return driver; }
    long getFare()           { return fareRupees; }
    void setFare(long fare)  { fareRupees = fare; }
}
```

### The matching algorithm and fare strategy

```java
interface MatchingStrategy {
    List<Driver> findCandidates(Trip trip, Collection<Driver> drivers);
}

class NearestDriverStrategy implements MatchingStrategy {
    public List<Driver> findCandidates(Trip trip, Collection<Driver> drivers) {
        return drivers.stream()
                .filter(d -> d.getStatus() == DriverStatus.AVAILABLE)
                .filter(d -> d.getType() == trip.getType())
                .filter(d -> d.getLocation().distanceKm(trip.getPickup()) <= 5)
                .sorted(Comparator.comparingDouble(
                        d -> d.getLocation().distanceKm(trip.getPickup())))
                .toList();
    }
}

interface FareStrategy {
    long fare(double km, Duration time);
}

/** Rs 40 base + Rs 12 per km + Rs 2 per minute. */
class StandardFare implements FareStrategy {
    public long fare(double km, Duration time) {
        return Math.round(40 + 12 * km + 2 * time.toMinutes());
    }
}
```

### RideService

```java
class RideService {
    private final List<Driver> drivers;
    private final MatchingStrategy matching;
    private final FareStrategy fares;
    private final Set<String> ridersOnTrip = new HashSet<>();

    RideService(List<Driver> drivers, MatchingStrategy matching, FareStrategy fares) {
        this.drivers = drivers; this.matching = matching; this.fares = fares;
    }

    synchronized Trip requestRide(String rider, Location pickup, Location drop,
                                  VehicleType type) {
        if (!ridersOnTrip.add(rider)) {
            throw new IllegalStateException(rider + " already has a trip");
        }
        return new Trip(rider, pickup, drop, type);
    }

    List<Driver> candidates(Trip trip) { return matching.findCandidates(trip, drivers); }

    /** Called when a driver taps Accept. Only one driver per trip, one trip per driver. */
    boolean accept(Trip trip, Driver driver) {
        synchronized (trip) {
            if (trip.getStatus() != TripStatus.REQUESTED) return false;  // trip taken
            if (!driver.tryClaim()) return false;                         // driver busy
            trip.assign(driver);
            return true;
        }
    }

    void arrive(Trip trip) {
        synchronized (trip) {
            trip.transition(TripStatus.DRIVER_ASSIGNED, TripStatus.DRIVER_ARRIVED);
        }
    }

    void start(Trip trip) {
        synchronized (trip) {
            trip.transition(TripStatus.DRIVER_ARRIVED, TripStatus.IN_PROGRESS);
        }
    }

    long end(Trip trip, double km, Duration time) {
        synchronized (trip) {
            trip.transition(TripStatus.IN_PROGRESS, TripStatus.COMPLETED);
            trip.setFare(fares.fare(km, time));
            trip.getDriver().release();                     // ready for the next ride
            synchronized (this) { ridersOnTrip.remove(trip.getRider()); }
            return trip.getFare();
        }
    }
}
```

| What happens | Result |
| --- | --- |
| Candidates for Asha | Ravi first (nearest mini); Meena is skipped (sedan) |
| Ravi accepts Asha's trip | Assigned. Ravi is ON_TRIP |
| Ravi also taps accept for Bilal's trip | Rejected – Ravi is busy |
| Sunil tries to take Asha's trip | Rejected – it already has a driver |
| Sunil accepts Bilal's trip | Assigned |
| Asha's trip ends: 2.1 km, 8 minutes | ₹40 + ₹25.20 + ₹16 = ₹81. Ravi is available again |

## Step 5: One driver, one trip

Two races can break assignment:

1. **Two trips, one driver.** Ravi is nearest for both Asha and Bilal and accepts both offers almost together.
2. **One trip, two drivers.** Asha's offer times out at Ravi and goes to Sunil – then Ravi's late "accept" arrives just as Sunil accepts.

![Animation: Ravi accepts Asha's and Bilal's trips almost together; the first compareAndSet from AVAILABLE to ON_TRIP succeeds and assigns Asha's trip, the second fails, so Bilal's trip stays REQUESTED and is offered to the next driver.](learning-figures/lld-7-race.gif)

`accept` solves both:

- `driver.tryClaim()` uses `compareAndSet`: only one claim on Ravi can succeed. That fixes race 1.
- `synchronized (trip)` plus the REQUESTED check means only the first accept for a trip wins. That fixes race 2.

We check the trip **before** claiming the driver. If the trip is already taken, we never touch the driver, so no driver is left stuck as ON_TRIP with no trip.

> **⚠️ Common mistake**
> Checking `driver.getStatus() == AVAILABLE` and then setting ON_TRIP in a second statement. Two accepts can both pass the check. `compareAndSet` does both in one atomic step.

> **🎯 In the interview**
> With several servers, the claim becomes a conditional update: `UPDATE driver SET status = 'ON_TRIP' WHERE id = ? AND status = 'AVAILABLE'`. One updated row means you won the driver.

## Step 6: Deep dives

### Finding nearby drivers fast

Scanning 100,000 online drivers per request is too slow. Divide the map into cells (geohash or Uber's H3) and keep a map from cell to available drivers. Search the rider's cell and its neighbours.

### Surge pricing

Wrap the fare strategy: `SurgeFare` multiplies whatever `StandardFare` returns. This is the **Decorator pattern** – surge is added without changing the base fare.

### Cancellation

Allow it before the trip starts: move the trip to CANCELLED and release the driver. A `CancellationPolicy` decides the fee, for example ₹50 after the driver has arrived.

### Notifications

"Driver assigned", "driver arrived" and "trip completed" are events. The rider's and driver's apps are **observers**.

## Interviewer follow-ups

**Is the nearest driver always the fastest?** No – roads, traffic and one-way streets matter. Start with straight-line distance, then swap in a `MatchingStrategy` that ranks by road ETA from a maps service.

**Why ask drivers to accept instead of assigning automatically?** A driver may be on a break or about to go offline. Accepting avoids sending someone who will not come; the cost is a few seconds of waiting.

**What if the driver's phone loses network mid-trip?** The trip stays IN_PROGRESS; only location updates pause. A timer must never hand the driver to another rider.

**What if the rider cancels while a driver is accepting?** Both go through `synchronized (trip)`. Whichever runs first wins; the other sees the new status and stops.

## Wrap up

We modelled riders, drivers and trips, matched them with a strategy, and made assignment safe with a trip lock plus an atomic driver claim.

> **📝 Key takeaways**
> - Assignment happens on accept, not on search.
> - Trip lock: only the first accept for a trip wins.
> - Driver `compareAndSet(AVAILABLE, ON_TRIP)`: one driver, one trip.
> - Matching and fare are strategies; surge is a decorator; notifications are observers.

## Closing answer

"I'd model Location, Driver, Trip and a `RideService`, with matching and fares as strategies. A trip moves REQUESTED → DRIVER_ASSIGNED → DRIVER_ARRIVED → IN_PROGRESS → COMPLETED, and each step is only allowed from the previous one. ## Problem

Design the core classes of a food delivery app like Swiggy or Zomato. Asha orders a Chicken Biryani and a Paneer Biryani from Meghana Foods. The restaurant accepts, Ravi – the nearest free delivery partner – is assigned, the food is cooked, picked up and delivered.

The interesting parts are the **order's life cycle** (what may happen next, and when cancelling is still allowed) and **assigning one partner to one order** when many orders arrive at once.

## Requirements

- Customers browse a restaurant's menu and place an order with several items.
- The restaurant accepts the order; a free delivery partner is assigned.
- The order moves through clear statuses: placed → accepted → preparing → ready → picked up → delivered.
- Customers can cancel with a full refund until cooking starts.
- A partner carries one order at a time; delivery is free above ₹499.

## Step 1: Clarify the requirements

**Candidate:** Is this the whole Swiggy, or the core ordering flow?

**Interviewer:** The core: menu, order, status changes, partner assignment.

**Candidate:** Can one order contain items from several restaurants?

**Interviewer:** No. One restaurant per order.

**Candidate:** When can a customer cancel?

**Interviewer:** Free cancellation until the restaurant starts cooking. After that, no.

**Candidate:** How do we choose a delivery partner?

**Interviewer:** The nearest free one. We may change the rule later.

**Candidate:** Can a partner carry two orders together?

**Interviewer:** Not for now – one at a time.

**Candidate:** Is there a delivery fee?

**Interviewer:** ₹30, free if the food costs ₹499 or more.

> Ask about cancellation and assignment early. They decide the two most important parts of the design: the state machine and the concurrency fix.

| --- | --- |
| Menu, place order, accept, assign partner | One partner never gets two orders at once |
| Status updates through delivery | Illegal status jumps are impossible |
| Cancel with refund before cooking | Easy to change the assignment rule |

## Step 2: Identify the core objects

- **Restaurant** – has a menu and can be open or closed.
- **MenuItem** – a dish with a price and a veg flag.
- **Order** – one customer, one restaurant, some order lines, a status and a partner.
- **OrderLine** – a menu item and a quantity.
- **OrderStatus** – the allowed statuses and which moves are legal.
- **DeliveryPartner** – a rider who carries at most one order.
- **AssignmentStrategy** – the rule for picking a partner (nearest free, for now).

> **⚖️ Design choice**
> Put the allowed status changes in **one place** – the `OrderStatus` enum – instead of scattering `if` checks across the code. Every change goes through `order.moveTo(next)`, which refuses illegal jumps.

## Step 3: Design the classes

### Restaurant and MenuItem

A `MenuItem` is a small immutable record. A `Restaurant` owns its menu and refuses items that aren't on it.

### OrderStatus

An enum with a table of legal next statuses. `PLACED` may go to `ACCEPTED` or `CANCELLED`; `PREPARING` may only go to `READY` – that is how "no cancelling after cooking starts" is enforced.

### Order and OrderLine

An `Order` keeps a copy of its lines and calculates totals. Its status can only change through `moveTo`.

### DeliveryPartner and AssignmentStrategy

A partner holds at most one current order. Picking a partner is a **Strategy**, so "nearest free" can later become "best rated" or "batch two orders" without touching the order code.

[![Class diagram: a Restaurant has MenuItems; an Order has OrderLines, an OrderStatus and a DeliveryPartner; FoodDeliveryService places and moves orders and uses an AssignmentStrategy, implemented by NearestFreePartner, to pick a partner.](learning-figures/lld-8-classes.svg)](learning-figures/lld-8-classes.svg)

### OrderStatus: the state machine

```java
enum OrderStatus {
    PLACED, ACCEPTED, PREPARING, READY, PICKED_UP, DELIVERED, CANCELLED;

    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
            PLACED,    EnumSet.of(ACCEPTED, CANCELLED),
            ACCEPTED,  EnumSet.of(PREPARING, CANCELLED),
            PREPARING, EnumSet.of(READY),
            READY,     EnumSet.of(PICKED_UP),
            PICKED_UP, EnumSet.of(DELIVERED),
            DELIVERED, EnumSet.noneOf(OrderStatus.class),
            CANCELLED, EnumSet.noneOf(OrderStatus.class));

    boolean canMoveTo(OrderStatus next) { return NEXT.get(this).contains(next); }
}
```

### Order and OrderLine

```java
record OrderLine(MenuItem item, int qty) {
    long totalPaise() { return item.pricePaise() * qty; }
}

class Order {
    private final String id;
    private final String customer;
    private final Restaurant restaurant;
    private final List<OrderLine> lines;
    private final long deliveryFeePaise;
    private OrderStatus status = OrderStatus.PLACED;
    private DeliveryPartner partner;

    Order(String id, String customer, Restaurant r, List<OrderLine> lines, long feePaise) {
        this.id = id; this.customer = customer; this.restaurant = r;
        this.lines = List.copyOf(lines); this.deliveryFeePaise = feePaise;
    }

    long itemTotalPaise() { return lines.stream().mapToLong(OrderLine::totalPaise).sum(); }
    long totalPaise()     { return itemTotalPaise() + deliveryFeePaise; }

    void moveTo(OrderStatus next) {
        if (!status.canMoveTo(next))
            throw new IllegalStateException(status + " -> " + next + " is not allowed");
        status = next;
    }

    String getId()                   { return id; }
    String getCustomer()             { return customer; }
    Restaurant getRestaurant()       { return restaurant; }
    OrderStatus getStatus()          { return status; }
    DeliveryPartner getPartner()     { return partner; }
    void setPartner(DeliveryPartner p) { partner = p; }
}
```

### DeliveryPartner and assignment

```java
class DeliveryPartner {
    private final String name;
    private final double kmFromRestaurant;
    private Order current;                                  // at most one active order

    DeliveryPartner(String name, double km) { this.name = name; this.kmFromRestaurant = km; }
    String getName()      { return name; }
    double distanceKm()   { return kmFromRestaurant; }
    boolean isFree()      { return current == null; }

    /** Check-and-take in one step, so two orders can never get the same partner. */
    synchronized boolean tryAssign(Order order) {
        if (current != null) return false;
        current = order;
        return true;
    }
    synchronized void finish() { current = null; }
}

interface AssignmentStrategy {
    Optional<DeliveryPartner> pick(Order order, List<DeliveryPartner> partners);
}

class NearestFreePartner implements AssignmentStrategy {
    public Optional<DeliveryPartner> pick(Order order, List<DeliveryPartner> partners) {
        return partners.stream()
                .filter(DeliveryPartner::isFree)
                .sorted(Comparator.comparingDouble(DeliveryPartner::distanceKm))
                .filter(p -> p.tryAssign(order))            // first one we actually win
                .findFirst();
    }
}
```

### FoodDeliveryService

```java
class FoodDeliveryService {
    private final List<DeliveryPartner> partners;
    private final AssignmentStrategy strategy;
    private final Map<String, Order> orders = new HashMap<>();
    private int nextId = 1;

    FoodDeliveryService(List<DeliveryPartner> partners, AssignmentStrategy strategy) {
        this.partners = partners; this.strategy = strategy;
    }

    Order placeOrder(String customer, Restaurant r, Map<String, Integer> cart) {
        if (!r.isOpen()) throw new IllegalStateException(r.getName() + " is closed");
        List<OrderLine> lines = cart.entrySet().stream()
                .map(e -> new OrderLine(r.item(e.getKey()), e.getValue())).toList();
        long itemTotal = lines.stream().mapToLong(OrderLine::totalPaise).sum();
        long fee = itemTotal >= 49_900 ? 0 : 3_000;         // free delivery from Rs 499
        Order o = new Order("ORD-" + nextId++, customer, r, lines, fee);
        orders.put(o.getId(), o);
        return o;
    }

    void restaurantAccepts(Order o) {
        o.moveTo(OrderStatus.ACCEPTED);
        DeliveryPartner p = strategy.pick(o, partners)
                .orElseThrow(() -> new IllegalStateException("No partner free; retry soon"));
        o.setPartner(p);
    }

    void startPreparing(Order o) { o.moveTo(OrderStatus.PREPARING); }
    void foodReady(Order o)      { o.moveTo(OrderStatus.READY); }
    void pickedUp(Order o)       { o.moveTo(OrderStatus.PICKED_UP); }

    void delivered(Order o) {
        o.moveTo(OrderStatus.DELIVERED);
        o.getPartner().finish();
    }

    /** Customer cancel: full refund before cooking starts, otherwise refused. */
    long cancel(Order o) {
        o.moveTo(OrderStatus.CANCELLED);                    // throws once PREPARING
        if (o.getPartner() != null) o.getPartner().finish();
        return o.totalPaise();                              // refund amount
    }
}
```

## Step 5: The assignment algorithm: two orders, one partner

Meghana accepts Asha's and Bilal's orders at the same moment, on two threads.

1. Thread A sees Ravi is free and nearest.
2. Thread B also sees Ravi is free and nearest.
3. Both assign Ravi. He now has two orders – and one customer waits forever.

The fix is to **check and take in one step**. `tryAssign` is `synchronized`: it sets Ravi's current order only if he has none, and returns whether it won. The strategy walks partners from nearest to farthest and keeps the first one it actually wins, so Thread B simply moves on to Chetan.

![Animation: two orders are accepted at the same moment and both see Ravi as the nearest free partner; Asha's order wins tryAssign and gets Ravi; Bilal's order fails on Ravi, moves to the next nearest partner and gets Chetan.](learning-figures/lld-8-assign.gif)

> **⚠️ Common mistake**
> Checking `isFree()` and then assigning in a separate step. Another thread can take the partner between the two lines. The check and the update must be one atomic operation.

> **🎯 In the interview**
> With many servers, `synchronized` is not enough. Use a conditional database update – `UPDATE partner SET order_id = ? WHERE id = ? AND order_id IS NULL` – and treat "0 rows" as "try the next partner".

## Step 6: Deep dives

### A new assignment rule

Add a class `BestRatedNearby implements AssignmentStrategy` and pass it to the service. Nothing else changes – that's the point of the Strategy pattern.

### Payments and refunds

A `Payment` record per order (amount, method, status). `cancel` returns the refund amount; a `PaymentService` issues the refund. After cooking starts, support can still issue a partial refund manually.

### Live tracking and notifications

Each `moveTo` can publish an event ("order ORD-1 is READY"). Notification and tracking services subscribe (Observer pattern) – the order class doesn't need to know about SMS or maps.

### Batching orders

To let a partner carry two orders from the same restaurant, change "one current order" to "a small list with a limit", and let the strategy prefer partners already heading to that restaurant.

## Interviewer follow-ups

**Why an enum with a transition table, not the State pattern?** The statuses have no behaviour of their own – only rules about what comes next. A table is shorter and easy to read. If each status had different behaviour, the State pattern would fit.

**What if no partner is free?** Keep the order accepted and retry assignment every few seconds, or put it in a queue that partners pull from when they finish.

**How do you handle the restaurant rejecting an order?** Add `PLACED → REJECTED` and refund in full.

**Where does the delivery fee rule live?** In one place in the service. If it grows (surge, distance), move it into a `PricingPolicy` strategy.

## Wrap up

We modelled restaurants, menus and orders, enforced the order's life cycle with one transition table, and assigned partners with an atomic check-and-take behind a strategy.

> **📝 Key takeaways**
> - One transition table makes illegal status jumps impossible.
> - Cancellation rules fall out of the state machine.
> - Assign a partner with an atomic check-and-take; in a database, a conditional update.
> - Strategy for assignment rules; events for tracking and notifications.

## Problem

Design a library management system. Members search the catalogue, borrow physical books, return them, renew loans and join a waiting list when every copy is out. Late returns are fined.

The key idea is that a *book* (a title in the catalogue) is not the same as a *copy* on the shelf. Get that right and the rest falls into place.

## Requirements

- Members borrow up to a limit set by their plan, for a fixed number of days.
- Return a book; charge a fine for every late day.
- Renew a loan, unless someone else is waiting for that title.
- If every copy is out, a member can place a hold. The first person in the queue gets the next returned copy and has 2 days to collect it.
- Several library desks work at the same time.

## Step 1: Clarify the requirements

**Candidate:** Do we track each physical copy, or just titles?

**Interviewer:** Each copy has its own barcode.

**Candidate:** Are borrowing limits the same for everyone?

**Interviewer:** No. Basic members get 3 books for 14 days; Premium get 5 books for 21 days.

**Candidate:** If every copy is out, can members wait for it?

**Interviewer:** Yes. First come, first served, with 2 days to collect.

**Candidate:** How are fines calculated and paid?

**Interviewer:** ₹10 a day for Basic, ₹5 for Premium. Record it on return; payment is separate.

**Candidate:** Can two desks lend the last copy at the same time?

| Functional | Non-functional |
| --- | --- |
| Borrow, return, renew, place a hold | The last copy is never lent twice |
| Fines for late returns | New membership plans need no new code |
| Holds served in order | Search stays fast for a large catalogue |

## Step 2: Identify the core objects

- **Book** – a title in the catalogue (ISBN, title, author). It also keeps the waiting list.
- **BookItem** – one physical copy with a barcode and a status: available, on loan, on the hold shelf.
- **Member** and **MembershipPlan** – who is borrowing, and their rules.
- **Loan** – one member borrowing one copy, with a due date.
- **Hold** – a member waiting for a title.
- **LibraryService** – the only place that lends, returns and hands out held copies.

## Step 3: Design the classes

### MembershipPlan and Member

### Book and BookItem

### Loan and Hold

### LibraryService

### LibraryService

```java
class LibraryService {
    private final Map<String, BookItem> items = new HashMap<>();
    private final Map<String, Loan> activeLoans = new HashMap<>();   // barcode -> loan
    private final Map<BookItem, Hold> heldFor = new HashMap<>();     // copies on hold shelf

    void addCopy(BookItem item) { items.put(item.getBarcode(), item); }

    synchronized Loan checkout(Member member, String barcode, LocalDate today) {
        BookItem item = items.get(barcode);
        long borrowed = activeLoans.values().stream()
                .filter(l -> l.getMember() == member).count();
        if (borrowed >= member.plan().maxBooks()) {
            throw new IllegalStateException(member.name() + " has reached the limit");
        }
        Hold hold = heldFor.get(item);
        boolean waitingForThisMember = hold != null && hold.getMember() == member;
        if (item.getStatus() != ItemStatus.AVAILABLE && !waitingForThisMember) {
            throw new IllegalStateException("Copy " + barcode + " is not available");
        }
        if (waitingForThisMember) heldFor.remove(item);
        Loan loan = new Loan(item, member, today);
        item.setStatus(ItemStatus.ON_LOAN);
        activeLoans.put(barcode, loan);
        return loan;
    }

    /** Returns the fine in rupees. */
    synchronized long returnBook(String barcode, LocalDate today) {
        Loan loan = activeLoans.remove(barcode);
        if (loan == null) throw new IllegalStateException("Copy is not on loan");
        long daysLate = Math.max(0, ChronoUnit.DAYS.between(loan.getDueDate(), today));
        giveToNextInQueue(loan.getItem(), today);
        return daysLate * loan.getMember().plan().finePerDay();
    }

    synchronized Hold placeHold(Member member, Book book) {
        Hold hold = new Hold(member);
        book.holds().addLast(hold);
        return hold;
    }

    synchronized Loan renew(String barcode, LocalDate today) {
        Loan loan = activeLoans.get(barcode);
        if (today.isAfter(loan.getDueDate())) throw new IllegalStateException("Overdue");
        if (loan.getRenewals() >= loan.getMember().plan().maxRenewals()) {
            throw new IllegalStateException("No renewals left");
        }
        if (!loan.getItem().getBook().holds().isEmpty()) {
            throw new IllegalStateException("Someone is waiting for this book");
        }
        loan.extend();
        return loan;
    }

    /** Daily job: a copy nobody collected goes to the next person in the queue. */
    synchronized void expireHolds(LocalDate today) {
        for (Map.Entry<BookItem, Hold> e : new ArrayList<>(heldFor.entrySet())) {
            if (today.isAfter(e.getValue().getPickupBy())) {
                heldFor.remove(e.getKey());
                giveToNextInQueue(e.getKey(), today);
            }
        }
    }

    private void giveToNextInQueue(BookItem item, LocalDate today) {
        Hold next = item.getBook().holds().pollFirst();       // first come, first served
        if (next == null) {
            item.setStatus(ItemStatus.AVAILABLE);
            return;
        }
        next.readyUntil(today.plusDays(2));                    // 2 days to collect
        heldFor.put(item, next);
        item.setStatus(ItemStatus.ON_HOLD_SHELF);
    }
}
```

`giveToNextInQueue` is used by both `returnBook` and the daily expiry job. Either a waiting member gets the copy for 2 days, or the copy goes back on the shelf.

> **⚠️ Common mistake**
> Counting days late from milliseconds. Use calendar dates (`LocalDate` and `ChronoUnit.DAYS`) so midnight and daylight-saving changes cannot add or lose a day.

## Interviewer follow-ups

**Why not `StudentMember` and `FacultyMember` subclasses?** They behave identically; only limits differ. Composition with a `MembershipPlan` keeps one `Member` class.

## Problem

Design an expense-sharing app like Splitwise. Friends record shared expenses ("I paid ₹900 for dinner, split three ways"), see who owes whom, and settle up.

The design must keep every paisa accounted for, support different ways of splitting, and suggest a short list of payments that settles everyone.

## Requirements

- Add an expense paid by one person and shared by some people.
- Split equally, by exact amounts, or by percentages.
- Show how much each person owes or is owed.
- Record a payment ("Ben paid Asha ₹300").
- Suggest a short list of payments that settles everyone.

## Step 1: Clarify the requirements

**Candidate:** Does one person pay for each expense?

**Interviewer:** Yes. Multiple payers can be a follow-up.

**Candidate:** Which split types do we need?

**Interviewer:** Equal, exact amounts and percentages.

**Candidate:** What about ₹100.01 split three ways?

**Interviewer:** Every paisa must be accounted for. You choose who gets the extra.

**Candidate:** Must the settle-up list be the shortest possible?

**Interviewer:** Short and simple is enough.

**Candidate:** Can expenses be edited later?

**Interviewer:** Yes, but balances must still make sense.

> **🎯 In the interview**
> The leftover-paisa question shows you think about money precisely. Say: "I'll store money as whole paise in a `long`".

| Functional | Non-functional |
| --- | --- |
| Add expenses with equal, exact or percentage splits | Shares always add up exactly to the total |
| Show who owes whom | Balances always sum to zero |
| Record payments; suggest how to settle up | New split types are easy to add |

## Step 2: Identify the core objects

- **User** – a person in the group.
- **Expense** – what was bought, who paid, the amount, and each person's share.
- **Split** – one person's share of one expense.
- **SplitStrategy** – how an amount is divided: equal, exact or percent.
- **BalanceSheet** – who owes whom, and how much.
- **ExpenseService** – records expenses and payments and updates balances.
- **DebtSimplifier** – suggests a short list of payments.

> **⚖️ Design choice**
> Splitting and balances are separate jobs. A split strategy only returns shares; the service then updates balances. A new split type never touches balance code.

## Step 3: Design the classes

### User, Split and Expense

Simple records. An expense is never changed after it is saved – a mistake is fixed by adding a reversal, so history stays explainable.

### SplitStrategy

One interface, three implementations. Every implementation must return shares that add up **exactly** to the total.

### BalanceSheet

A map of maps: `owes[Asha][Ben] = 3,334` means Ben owes Asha ₹33.34. Every entry is written twice, once each way, so the sheet always balances.

### ExpenseService and DebtSimplifier

The service is the only writer. The simplifier only reads net balances and suggests payments – it changes nothing.

### Split strategies

```java
interface SplitStrategy {
    List<Split> split(long amountPaise, List<User> users, List<Long> inputs);
}

class EqualSplit implements SplitStrategy {
    public List<Split> split(long amount, List<User> users, List<Long> ignored) {
        long base = amount / users.size();
        long leftover = amount % users.size();                  // e.g. 2 paise
        List<Split> result = new ArrayList<>();
        for (int i = 0; i < users.size(); i++) {
            result.add(new Split(users.get(i), base + (i < leftover ? 1 : 0)));
        }
        return result;
    }
}

class ExactSplit implements SplitStrategy {
    public List<Split> split(long amount, List<User> users, List<Long> exact) {
        if (exact.stream().mapToLong(Long::longValue).sum() != amount) {
            throw new IllegalArgumentException("Exact shares must add up to the total");
        }
        List<Split> result = new ArrayList<>();
        for (int i = 0; i < users.size(); i++) {
            result.add(new Split(users.get(i), exact.get(i)));
        }
        return result;
    }
}

/** Inputs are percentages in basis points: 100% = 10,000. */
class PercentSplit implements SplitStrategy {
    public List<Split> split(long amount, List<User> users, List<Long> basisPoints) {
        if (basisPoints.stream().mapToLong(Long::longValue).sum() != 10_000) {
            throw new IllegalArgumentException("Percentages must add up to 100");
        }
        long[] shares = new long[users.size()];
        long used = 0;
        for (int i = 0; i < shares.length; i++) {
            shares[i] = amount * basisPoints.get(i) / 10_000;    // rounds down
            used += shares[i];
        }
        for (int i = 0; used < amount; i++, used++) shares[i]++;   // leftover paise
        List<Split> result = new ArrayList<>();
        for (int i = 0; i < shares.length; i++) {
            result.add(new Split(users.get(i), shares[i]));
        }
        return result;
    }
}
```

Asha pays **₹100.01 = 10,001 paise** for a taxi, split equally among three. 10,001 ÷ 3 = 3,333 with 2 paise left. The first two people get one extra paisa each:

| Person | Share |
| --- | --- |
| Asha | 3,334 |
| Ben | 3,334 |
| Cara | 3,333 |
| **Total** | **10,001** |

Percentages use **basis points** (100% = 10,000), so 12.5% is exactly 1,250 – no decimals. ₹1.01 split 50/30/20 gives 51, 30 and 20 paise.

> **⚠️ Common mistake**
> Using `double` for money. `0.1 + 0.2` is not `0.3` in binary floating point, so shares stop adding up to the total. Whole paise in a `long` never drift.

### BalanceSheet

```java
class BalanceSheet {
    // owes.get(a).get(b) > 0 means b owes a that many paise
    private final Map<User, Map<User, Long>> owes = new HashMap<>();

    void add(User creditor, User debtor, long paise) {
        if (creditor.equals(debtor) || paise == 0) return;       // you never owe yourself
        owes.computeIfAbsent(creditor, k -> new HashMap<>())
            .merge(debtor, paise, Long::sum);
        owes.computeIfAbsent(debtor, k -> new HashMap<>())
            .merge(creditor, -paise, Long::sum);
    }

    /** Positive: is owed money. Negative: owes money. */
    long net(User user) {
        return owes.getOrDefault(user, Map.of()).values().stream()
                   .mapToLong(Long::longValue).sum();
    }
}
```

### ExpenseService

```java
class ExpenseService {
    private final BalanceSheet sheet = new BalanceSheet();
    private final List<Expense> expenses = new ArrayList<>();

    synchronized Expense addExpense(String description, User paidBy, long amountPaise,
            List<User> users, SplitStrategy strategy, List<Long> inputs) {
        if (amountPaise <= 0) throw new IllegalArgumentException("Amount must be positive");
        List<Split> splits = strategy.split(amountPaise, users, inputs);
        for (Split s : splits) sheet.add(paidBy, s.user(), s.paise());
        var expense = new Expense(description, paidBy, amountPaise, List.copyOf(splits));
        expenses.add(expense);
        return expense;
    }

    /** "from" paid "to" back: their debt goes down. */
    synchronized void settle(User from, User to, long paise) {
        sheet.add(from, to, paise);
    }

    synchronized long net(User user) { return sheet.net(user); }
}
```

After the taxi: Asha is owed 3,334 + 3,333 = ₹66.67 (her own share is skipped – you never owe yourself). Ben owes ₹33.34, Cara owes ₹33.33. Then Ben buys ₹30 of snacks for Ben and Cara, ₹15 each:

| Person | After taxi | After snacks |
| --- | --- | --- |
| Asha | +₹66.67 | +₹66.67 |
| Ben | −₹33.34 | −₹18.34 |
| Cara | −₹33.33 | −₹48.33 |
| **Sum** | **0** | **0** |

The balances always sum to zero – a great check to mention and to test.

## Step 5: Settle up with fewer payments

Say the net balances are Asha +₹70, Ben −₹30, Cara −₹40. Instead of everyone paying everyone, repeatedly match the biggest debtor with the biggest creditor.

```java
record Payment(User from, User to, long paise) {}

class DebtSimplifier {
    /** Greedy: biggest debtor pays biggest creditor, repeat. At most n - 1 payments. */
    List<Payment> simplify(Map<User, Long> net) {
        Comparator<Map.Entry<User, Long>> byAmount = Map.Entry.comparingByValue();
        var creditors = new PriorityQueue<>(byAmount.reversed());   // largest credit first
        var debtors = new PriorityQueue<>(byAmount);                // most negative first
        net.forEach((user, amount) -> {
            if (amount > 0) creditors.add(Map.entry(user, amount));
            if (amount < 0) debtors.add(Map.entry(user, amount));
        });
        List<Payment> payments = new ArrayList<>();
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            var c = creditors.poll();
            var d = debtors.poll();
            long amount = Math.min(c.getValue(), -d.getValue());
            payments.add(new Payment(d.getKey(), c.getKey(), amount));
            if (c.getValue() > amount) {
                creditors.add(Map.entry(c.getKey(), c.getValue() - amount));
            }
            if (-d.getValue() > amount) {
                debtors.add(Map.entry(d.getKey(), d.getValue() + amount));
            }
        }
        return payments;
    }
}
```

Result: Cara pays Asha ₹40, then Ben pays Asha ₹30. Two payments. Each step settles at least one person, so *n* people need at most *n − 1* payments; the two heaps make it O(n log n).

![Animation: net balances Asha +70, Ben −30, Cara −40; the largest debtor Cara pays the largest creditor Asha 40; then Ben pays Asha 30; everyone reaches zero in two payments.](learning-figures/lld-10-simplify.gif)

> **🎯 In the interview**
> Say clearly that greedy is not always the theoretical minimum. Finding the true minimum means finding sub-groups whose balances cancel out, which is NP-hard. Greedy is what real apps use.

## Step 6: Deep dives

### Multiple payers

Each person's change for an expense = what they paid − their share. Asha pays ₹600 and Ben ₹400 for a ₹1,000 dinner split four ways (₹250 each): Asha +₹350, Ben +₹150, the other two −₹250 each.

### Editing an expense

Do not rewrite history. Add a reversal (the same splits with opposite signs), then the corrected expense.

### A new split type

Splitting by shares (for example 1:2) is one new `SplitStrategy` class. A **factory** can pick the strategy from the API's `"EQUAL"`, `"EXACT"` or `"PERCENT"` value.

### Notifications

"Ben added an expense" messages are **observers** of the expense-added event.

## Interviewer follow-ups

**Why store pairwise debts and not just one number per person?** Pairwise debts show *who* owes *whom*. Net balances (one number per person) are enough to suggest payments; keep both views.

**Two people add expenses at the same moment?** `addExpense` is synchronized (one lock per group in a real system), or each expense and its balance changes are written in one database transaction.

**How would you store this?** Tables for `expense` and `expense_split`; balances either stored and updated in the same transaction, or calculated from splits and cached.

## Wrap up

We separated how an expense is split from how balances change, kept every amount in exact paise, and used a greedy heap-based simplifier to settle up.

> **📝 Key takeaways**
> - Store money as whole paise; hand out leftover paise by a fixed rule.
> - Split types are strategies that always add up exactly to the total.
> - Balances always sum to zero – a great test.
> - Greedy settle-up needs at most n − 1 payments; the true minimum is NP-hard.

## Closing answer

"I'd model User, Expense and Split, with split types as strategies – equal, exact and percent – that always return shares adding up exactly to the total in whole paise, giving leftover paise by a fixed rule. `ExpenseService` records an expense and updates a pairwise `BalanceSheet`; every entry is written both ways, so balances always sum to zero. A payment is just an entry in the other direction. To settle up, a greedy simplifier matches the biggest debtor with the biggest creditor using two heaps – at most n − 1 payments, though not always the theoretical minimum. Edits are reversals plus new expenses, so history stays explainable."

## Problem

Design the software for a coffee vending machine in an office. It serves Espresso (₹30), Cappuccino (₹60) and Latte (₹70). Each drink uses coffee, water and sometimes milk. People pay with coins and get change back.

Asha picks a Cappuccino and inserts ₹70. The machine must make sure it has the milk **and** the ₹10 change *before* it keeps her money and brews – a half-served customer is the bug everyone remembers.

## Requirements

- Show drinks with prices; a drink is unavailable if any ingredient is short.
- Accept coins (₹1, 2, 5, 10, 20); return change.
- Brew only if both the ingredients and the change are available; otherwise refund.
- Let the user cancel and get their coins back.
- Staff can refill ingredients and coins; adding a new drink should be easy.

## Step 1: Clarify the requirements

**Candidate:** Which drinks, and what do they need?

**Interviewer:** Espresso, Cappuccino and Latte. Each has a recipe of coffee, water and milk.

**Candidate:** How do people pay?

**Interviewer:** Coins only for now.

**Candidate:** What if the machine can't give change?

**Interviewer:** Don't serve, and give the coins back.

**Candidate:** Can one machine serve two people at once?

**Interviewer:** No, one user at a time.

**Candidate:** Will new drinks be added later?

**Interviewer:** Yes – a Mocha next month.

> **🎯 In the interview**
> The key question is "what if we can't give change?". It shows you're thinking about the order of operations, not just the classes.

| Functional | Non-functional |
| --- | --- |
| Select, insert coins, brew, cancel | Never keep money without serving |
| Change and refunds | New drinks without code changes |
| Refill ingredients and coins | Clear, testable states |

## Step 2: Identify the core objects

- **Drink** – a name, a price and a recipe (ingredient → amount).
- **Ingredient** – coffee, milk, water, sugar.
- **Inventory** – how much of each ingredient is left.
- **CoinBox** – how many coins of each value the machine holds; plans change.
- **CoffeeMachine** – the state (idle or drink selected), the coins inserted, and the brew flow.
- **Result** – what happened: served or not, coins returned, a message.

[![Selected design: the user selects a drink and inserts coins; the machine checks the inventory for ingredients and the coin box for change; only if both are possible does it brew and return change, otherwise it refunds the inserted coins.](designs/lld-11.svg)](designs/lld-11.svg)

> **⚖️ Design choice**
> A drink is **data** (a recipe), not a subclass. A Mocha is a new `Drink` value with chocolate in its recipe – no new class, no new `if`.

## Step 3: Design the classes

### Drink and Ingredient

A `Drink` record holds its price and recipe. Prices are whole rupees here because only coins are used; with digital payments, use paise.

### Inventory

Knows ingredient levels, answers `canMake(drink)` and `consume(drink)`.

### CoinBox

Holds coins by value. `planChange(amount)` works out which coins to give **without changing anything**; `pay(plan)` then removes them. Planning first is what lets us refuse safely.

### CoffeeMachine

Two states – `IDLE` and `DRINK_SELECTED` – and three actions: `select`, `insert`, `brew` (plus `cancel`).

[![Class diagram: CoffeeMachine uses an Inventory and a CoinBox and has a State; a Drink has a recipe of Ingredients; brew returns a Result with the drink, the coins given back and a message.](learning-figures/lld-11-classes.svg)](learning-figures/lld-11-classes.svg)

### Inventory

```java
class Inventory {
    private final Map<Ingredient, Integer> stock = new EnumMap<>(Ingredient.class);

    void refill(Ingredient i, int amount) { stock.merge(i, amount, Integer::sum); }
    int level(Ingredient i)               { return stock.getOrDefault(i, 0); }

    boolean canMake(Drink d) {
        return d.recipe().entrySet().stream().allMatch(e -> level(e.getKey()) >= e.getValue());
    }
    void consume(Drink d) {
        if (!canMake(d)) throw new IllegalStateException("Not enough for " + d.name());
        d.recipe().forEach((i, amt) -> stock.merge(i, -amt, Integer::sum));
    }
}
```

### CoinBox

```java
/** Coins the machine holds, largest first. */
class CoinBox {
    private final TreeMap<Integer, Integer> coins = new TreeMap<>(Comparator.reverseOrder());

    void add(int coin, int count) { coins.merge(coin, count, Integer::sum); }
    int count(int coin)           { return coins.getOrDefault(coin, 0); }

    /** Plan change without touching the box; empty if exact change is impossible. */
    Optional<Map<Integer, Integer>> planChange(int amount) {
        Map<Integer, Integer> plan = new LinkedHashMap<>();
        for (var e : coins.entrySet()) {
            int use = Math.min(amount / e.getKey(), e.getValue());
            if (use > 0) { plan.put(e.getKey(), use); amount -= use * e.getKey(); }
        }
        return amount == 0 ? Optional.of(plan) : Optional.empty();
    }
    void pay(Map<Integer, Integer> plan) {
        plan.forEach((c, n) -> coins.merge(c, -n, Integer::sum));
    }
}
```

### CoffeeMachine

```java
enum State { IDLE, DRINK_SELECTED }

record Result(boolean served, String drink, Map<Integer, Integer> coinsBack, String msg) {}

class CoffeeMachine {
    private final Inventory inventory;
    private final CoinBox coinBox;
    private State state = State.IDLE;
    private Drink selected;
    private final Map<Integer, Integer> inserted = new LinkedHashMap<>();

    CoffeeMachine(Inventory inventory, CoinBox coinBox) {
        this.inventory = inventory; this.coinBox = coinBox;
    }

    void select(Drink d) {
        if (state != State.IDLE) throw new IllegalStateException("Finish or cancel first");
        if (!inventory.canMake(d)) throw new IllegalStateException(d.name() + " unavailable");
        selected = d; state = State.DRINK_SELECTED;
    }

    void insert(int coin) {
        requireSelected();
        if (!Set.of(1, 2, 5, 10, 20).contains(coin)) throw new IllegalArgumentException(
                "Unknown coin: " + coin);
        inserted.merge(coin, 1, Integer::sum);
    }

    int paid() {
        return inserted.entrySet().stream().mapToInt(e -> e.getKey() * e.getValue()).sum();
    }

    /** Check everything first; only then take the money and brew. */
    Result brew() {
        requireSelected();
        int changeDue = paid() - selected.priceRupees();
        if (changeDue < 0) return new Result(false, null, Map.of(), "Insert ₹" + -changeDue);

        inserted.forEach(coinBox::add);              // their coins can be used for change
        Optional<Map<Integer, Integer>> change = coinBox.planChange(changeDue);
        if (change.isEmpty() || !inventory.canMake(selected)) {
            coinBox.pay(inserted);                   // give back exactly what they put in
            return reset(new Result(false, null, Map.copyOf(inserted), "Refunded"));
        }
        coinBox.pay(change.get());
        inventory.consume(selected);
        return reset(new Result(true, selected.name(), change.get(), "Enjoy!"));
    }

    Result cancel() {
        requireSelected();
        return reset(new Result(false, null, Map.copyOf(inserted), "Cancelled"));
    }

    private void requireSelected() {
        if (state != State.DRINK_SELECTED) throw new IllegalStateException("Select a drink");
    }

    private Result reset(Result r) {
        inserted.clear(); selected = null; state = State.IDLE;
        return r;
    }
    State getState() { return state; }
}
```

### Worked example

The machine starts with 100 g coffee, 500 ml water, 300 ml milk and **no coins**.

| Step | Check | Result |
| --- | --- | --- |
| Asha: Cappuccino (₹60), inserts 20 + 20 + 20 + 10 | Change ₹10: her own ₹10 coin can be used | Served, ₹10 back, milk 300 → 180 ml |
| Someone selects Latte (200 ml milk) | Only 180 ml left | "Latte unavailable" |
| Bilal: Espresso (₹30), inserts 20 + 20 | Change ₹10: no ₹10 coin in the box | Not served, both ₹20 coins back, no coffee used |
| Bilal again: inserts 20 + 10 | Exact money | Served |
| Chetan selects Espresso, inserts ₹10, cancels | – | ₹10 back, machine idle |

### Edge cases

| Case | Behaviour |
| --- | --- |
| Not enough money | "Insert ₹X more"; coins stay in until cancel |
| Unknown coin | Rejected |
| Brew before selecting | Refused by the state check |
| Ingredient runs out between select and brew | Checked again in `brew`; refund |

## Step 5: The brew algorithm: check everything, then commit

The order of operations is the whole design:

1. Is enough money inserted? If not, ask for more.
2. Add the inserted coins to the box (they can be used for change).
3. **Plan** the change without touching the box.
4. Check the ingredients **again**.
5. If either check fails: give back exactly the coins inserted. Nothing else has changed.
6. Only now: pay out the change, consume the ingredients, brew.

![Animation: Bilal selects an Espresso for 30 rupees and inserts two 20-rupee coins; the machine plans ten rupees of change, finds no ten-rupee coin, and returns both coins without using any coffee; he inserts 20 plus 10, which needs no change, and the espresso is served.](learning-figures/lld-11-brew.gif)

> **⚠️ Common mistake**
> Brewing first and calculating change afterwards. If change turns out to be impossible, the coffee is already in the cup and the money is already in the box – there is no clean way back.

> **🎯 In the interview**
> Real machines add one more step: the brewer can fail mid-way (a jam). Record "money taken, brewing" before starting, and on failure refund – physical evidence decides whether to retry or refund.

## Step 6: Deep dives

### Better change-making

Greedy (largest coin first) works for Indian coin values when every coin is in stock. With limited coins it can fail even when change is possible – for example ₹6 from {5, 2, 2, 2}: greedy takes 5 and is stuck, but 2 + 2 + 2 works. A small dynamic-programming search over coin counts fixes this (see the ATM lesson, LLD-6).

### More payment methods

Introduce a `PaymentMethod` interface (coins, UPI, card). The machine asks it to `authorise(amount)` and later `capture` or `release` – the same check-then-commit idea.

### The State pattern

With only two states, an enum and a few checks is clearest. If you add states like `MAINTENANCE` or `OUT_OF_ORDER` with different behaviour for every action, move to the State pattern (as in the ATM lesson).

### Low-stock alerts

After each brew, if an ingredient drops below a threshold, notify staff (Observer). The machine can also hide drinks that can't be made.

## Interviewer follow-ups

**Why is Drink a record and not an abstract class with subclasses?** Drinks differ only in data – price and recipe. Subclasses would add classes without adding behaviour.

**How would you add sugar levels?** A `Customisation` (sugar: 0–3 spoons) that adjusts the recipe for this order before the inventory check.

**What if the power fails mid-brew?** Keep a small persistent log of the current transaction; on restart, refund if brewing didn't complete.

**How do you test it?** Like the demo: set inventory and coins, run a sequence of actions and assert the results, the coins returned and the remaining stock.

## Wrap up

We modelled drinks as recipes, kept ingredients and coins in their own classes, and made brewing a check-everything-then-commit operation so nobody pays without being served.

> **📝 Key takeaways**
> - Drinks are data: price + recipe; new drinks need no new classes.
> - Plan change without changing the coin box; refuse safely if impossible.
> - Check ingredients and change before taking money or brewing.
> - A simple enum state is enough until states gain different behaviour.

## Closing answer

"I model a Drink as a record with a price and a recipe of ingredients, so new drinks are just data.
