## Problem

Design the core of a cab-booking app such as Uber or Ola. A rider requests a ride from a pickup point to a drop point. The system finds a nearby driver, the driver accepts, picks the rider up, completes the trip, and the rider pays a fare.

The core challenge: many riders request at the same time, and **one driver must never be assigned to two trips**.

## Requirements

- Riders request a ride with pickup, drop and vehicle type (mini, sedan, SUV) and see a fare estimate.
- Drivers go online or offline and share their location every few seconds.
- Match the request to a nearby available driver of the right type. The driver can accept or decline.
- Track the trip: driver assigned, driver arrived, trip started, trip completed.
- Calculate the final fare from distance and time. Allow cancellation before the trip starts.

Out of scope: payments integration, ratings, ride sharing/pooling, surge pricing details, maps and routing internals.

## 1. Clarify the scope

| Question to ask | Answer we choose | Why it matters |
| --- | --- | --- |
| How do we pick a driver? | The nearest available driver of the requested type within 5 km. | Matching is a replaceable strategy. |
| Does the driver have to accept? | Yes, within 15 seconds; otherwise try the next driver. | Assignment happens on accept, not on search. |
| Can a rider have two active trips? | No. | Reject a second request while one is active. |
| How is the fare calculated? | Base + per km + per minute, per vehicle type. | Pricing is a strategy; surge is a follow-up. |
| One server or many? | Design one service in memory, then discuss scale. | Keeps the class design clear. |

## 3. Request, match and accept (the matching algorithm)

Walk through one ride. Asha requests a mini from MG Road. Drivers D1 (400 m away), D2 (900 m) and D3 (3 km) are online.

1. `requestRide` creates trip T1 in REQUESTED and asks the matching strategy for candidates: D1, D2, D3 in order of distance.
2. The app sends D1 an offer. D1 has 15 seconds to accept.
3. D1 accepts. `acceptRide` assigns D1 to T1 and marks D1 ON_TRIP.
4. If D1 declines or does not answer, the offer goes to D2.

Matching is a strategy, so "nearest driver" can later become "fastest ETA" or "highest rated":

```java
interface MatchingStrategy {
    List<Driver> findCandidates(Location pickup, VehicleType type, Collection<Driver> drivers);
}

class NearestDriverStrategy implements MatchingStrategy {
    private static final double MAX_KM = 5.0;

    public List<Driver> findCandidates(Location pickup, VehicleType type, Collection<Driver> drivers) {
        return drivers.stream()
                .filter(d -> d.getStatus() == DriverStatus.AVAILABLE)
                .filter(d -> d.getVehicle().getType() == type)
                .filter(d -> d.getLocation().distanceKm(pickup) <= MAX_KM)
                .sorted(Comparator.comparingDouble(d -> d.getLocation().distanceKm(pickup)))
                .limit(5)
                .toList();
    }
}
```

`distanceKm` is the straight-line (haversine) distance. That is fine for a first answer; real apps use road ETA from a maps service.

```java
public class RideService {
    private final Map<String, Driver> drivers = new ConcurrentHashMap<>();
    private final Map<String, Trip> trips = new ConcurrentHashMap<>();
    private final Map<String, String> activeTripByRider = new ConcurrentHashMap<>();
    private final MatchingStrategy matching;
    private final FareStrategy fares;
    private final NotificationService notifications;

    public Trip requestRide(Rider rider, Location pickup, Location drop, VehicleType type) {
        Trip trip = new Trip(UUID.randomUUID().toString(), rider, pickup, drop, type,
                fares.estimate(pickup, drop, type));
        if (activeTripByRider.putIfAbsent(rider.getId(), trip.getId()) != null) {
            throw new IllegalStateException("Rider already has an active trip");
        }
        trips.put(trip.getId(), trip);
        List<Driver> candidates = matching.findCandidates(pickup, type, drivers.values());
        notifications.sendOffers(trip, candidates);   // one at a time, 15 s each
        return trip;
    }

    public boolean acceptRide(String tripId, String driverId) {
        Trip trip = trips.get(tripId);
        Driver driver = drivers.get(driverId);
        synchronized (trip) {
            if (trip.getStatus() != TripStatus.REQUESTED) {
                return false;                               // someone else accepted, or rider cancelled
            }
            if (!driver.tryClaim()) {
                return false;                               // driver is already on another trip
            }
            trip.assignDriver(driver);                      // status -> DRIVER_ASSIGNED
        }
        notifications.driverAssigned(trip);
        return true;
    }
}
```

## 4. The hard part: one driver, one trip

Two races can break assignment:

1. **Two trips, one driver.** D1 is the nearest driver for both Asha and Bilal and accepts both offers almost together.
2. **One trip, two drivers.** Asha's offer reaches D1, times out, goes to D2, and then D1's late "accept" arrives just as D2 accepts.

Both are check-then-act races. The fix is to make each "claim" a single atomic step:

```java
class Driver {
    private final AtomicReference<DriverStatus> status = new AtomicReference<>(DriverStatus.OFFLINE);

    boolean tryClaim() {
        return status.compareAndSet(DriverStatus.AVAILABLE, DriverStatus.ON_TRIP);
    }

    void release() {
        status.set(DriverStatus.AVAILABLE);
    }
}
```

- `compareAndSet` changes AVAILABLE to ON_TRIP **only if** the driver is still AVAILABLE. If D1 has already been claimed for Bilal's trip, the second claim returns false. That solves race 1.
- `synchronized (trip)` with the `REQUESTED` check means only the first accept for a trip wins. D1's late accept finds the trip already DRIVER_ASSIGNED and returns false. That solves race 2.

![Animation: driver D1 accepts two trips almost together; the first compareAndSet from AVAILABLE to ON_TRIP succeeds and assigns trip T1, the second fails, so trip T2 stays REQUESTED and is offered to the next driver.](learning-figures/lld-7-race.gif)

Order matters: we check the trip first, then claim the driver. If the trip check fails, we never touch the driver, so we never leave a driver stuck as ON_TRIP with no trip.

[![A driver candidate receives one exclusive offer; acceptance checks the offer and then sets the trip to assigned and the driver to on-trip together, so a location match alone never assigns a driver.](learning-figures/lld-7-assignment.svg)](learning-figures/lld-7-assignment.svg)

## 5. Finishing the trip and the fare

```java
public void startTrip(String tripId) {            // rider is in the car
    Trip trip = trips.get(tripId);
    synchronized (trip) { trip.transition(TripStatus.DRIVER_ARRIVED, TripStatus.IN_PROGRESS); }
}

public Trip endTrip(String tripId, double distanceKm, Duration duration) {
    Trip trip = trips.get(tripId);
    synchronized (trip) {
        trip.transition(TripStatus.IN_PROGRESS, TripStatus.COMPLETED);
        trip.setFinalFare(fares.calculate(trip.getType(), distanceKm, duration));
        trip.getDriver().release();                  // driver can take the next ride
        activeTripByRider.remove(trip.getRider().getId());
    }
    return trip;
}
```

`transition(from, to)` throws if the trip is not currently in `from`. That keeps the lifecycle honest: you cannot complete a trip that never started.

The fare is another strategy:

```java
interface FareStrategy {
    long estimate(Location pickup, Location drop, VehicleType type);
    long calculate(VehicleType type, double distanceKm, Duration duration);
}

class StandardFare implements FareStrategy {
    // mini: ₹40 base + ₹12 per km + ₹2 per minute (values in paise)
    public long calculate(VehicleType type, double distanceKm, Duration duration) {
        long base = 4_000, perKm = 1_200, perMinute = 200;
        return base + Math.round(distanceKm * perKm) + duration.toMinutes() * perMinute;
    }
    // estimate() calls calculate() with the route's expected distance and time
}
```

Example: an estimate of 2 km and 5 minutes gives ₹40 + ₹24 + ₹10 = ₹74. The actual trip took 2.1 km and 8 minutes: ₹40 + ₹25.20 + ₹16 = ₹81.20. The estimate is a guide; the final fare uses what really happened.

## 6. Design patterns and extensibility

| Pattern | Where | Why it helps |
| --- | --- | --- |
| **Strategy** | `MatchingStrategy`, `FareStrategy` | Nearest vs ETA-based matching; normal vs surge pricing. |
| **State** (lightweight) | `TripStatus` with `transition(from, to)` | Illegal jumps are rejected in one place. Full State classes are possible if each state gains a lot of behaviour. |
| **Observer** | `NotificationService` | Rider and driver apps get "driver assigned", "arrived", "completed" events. |
| **Decorator** | `SurgeFare` wraps `StandardFare` and multiplies it | Surge added without changing the base fare class. |

```java
class SurgeFare implements FareStrategy {
    private final FareStrategy inner;
    private final double multiplier;
    public long calculate(VehicleType t, double km, Duration d) {
        return Math.round(inner.calculate(t, km, d) * multiplier);
    }
    // estimate() delegates the same way
}
```

## 7. Interviewer follow-ups

**How do you find nearby drivers quickly with 100,000 drivers online?** Do not scan everyone. Divide the map into cells (a geohash or Uber's H3 grid) and keep a map from cell → available drivers. Look in the rider's cell and the neighbouring cells. Drivers move cells as their location updates arrive.

**Why not assign the nearest driver immediately, without asking?** Drivers may be on a break or prefer not to go somewhere. An accept step avoids sending a driver who will not come. The cost is a few seconds of waiting.

**Why send offers one driver at a time?** It keeps the rule "one pending offer per driver" simple. Sending to several drivers at once is faster but needs a first-accept-wins step and cancelling the other offers – which our `synchronized (trip)` check already supports.

**What happens if the rider cancels while a driver is accepting?** Both go through `synchronized (trip)`. Whichever runs first wins: if cancel wins, the accept sees CANCELLED and returns false; if accept wins, cancel releases the driver as part of cancelling.

**What if the driver's phone loses network during the trip?** The trip stays IN_PROGRESS; location updates simply pause. A timer does not hand the driver to another rider. Support can end the trip manually if needed.

**How would you add a cancellation fee?** A `CancellationPolicy` strategy: free before the driver arrives, ₹50 after arrival.

**How would this scale across servers?** Location updates go to a fast in-memory store (Redis with geo commands). Driver status moves to a database or Redis, and the claim becomes a conditional update: `UPDATE driver SET status='ON_TRIP', trip_id=? WHERE id=? AND status='AVAILABLE'`. One updated row means you won the driver.

## 8. Going deeper (optional)

The full reference design models offers explicitly, which matters once you discuss timeouts in detail:

- Each offer has an ID and a deadline. A driver accepts **an offer**, not just a trip, so an old offer that expired cannot be accepted later.
- Expiry, decline and cancel all check the exact offer ID, so a delayed timer for offer O1 cannot free a driver who has since received offer O2.
- The rider's cancel carries the trip version they saw, so a fee is never charged for a state the rider did not see.

## 9. Closing answer

"I model Rider, Driver, Vehicle, Location and Trip, with `RideService` coordinating request, accept, start, end and cancel. A matching strategy finds the nearest available drivers of the right type; offers go out one at a time. Assignment happens on accept: under the trip's lock I check that the trip is still REQUESTED, then claim the driver with a compare-and-set from AVAILABLE to ON_TRIP, so one driver never gets two trips and one trip never gets two drivers. The trip moves through clear states, the fare is a strategy with surge as a decorator, and notifications are observers. At scale, drivers are found through a geo grid and claimed with a conditional database or Redis update."

## Problem

Design a food delivery system like Swiggy or Zomato: browse restaurants, place an order, the restaurant accepts and prepares it, an agent is assigned and picks it up, and the customer tracks it live. The heart of it is the **order state machine**, with **Strategy** for agent assignment and **Observer** for notifications.

## Requirements

**Functional**
- Browse restaurants and menus (with availability), build a cart from **one** restaurant, place an order, pay.
- Restaurant accepts or rejects. Agent assignment, pickup, delivery and live tracking.
- Cancellation rules that depend on the stage. Ratings for food and delivery.

**Non-functional**
- Only valid state transitions are allowed.
- An agent carries at most N orders. Assignment rules differ by city.

## 1. Scope and chosen solution

I support a single-restaurant basket, restaurant acceptance, payment, preparation and delivery. I choose an Order aggregate with immutable line/address/price snapshots; fulfilment, payment and delivery keep independent identities and state. Restaurant inventory and courier navigation are external services.

## 2. Submission and recovery contracts

```text
placeOrder(checkoutId,customer,acceptedQuote,address) -> Order
restaurantDecision(orderId,decisionId,ACCEPT|REJECT) -> CurrentState
recordPayment(orderId,providerRef,outcome) -> CurrentState
cancel(orderId,actor,expectedVersion) -> CancellationDisposition
```

Submission validates the quote and records order plus outbox event in one transaction. A relay requests payment authorization and restaurant acceptance using stable operation references. The workflow starts preparation only when its chosen acceptance/payment prerequisites hold. Duplicate callbacks are deduplicated and rejected if inconsistent with a terminal state. Kitchen acceptance after cancellation cannot restart preparation through this service.

For two ₹300 pizzas and a ₹60 drink, subtotal is ₹660; with ₹50 delivery and ₹40 discount the pre-tax total is ₹670. That quote is frozen. Restaurant rejection voids an uncollected authorization or creates a refund intent after capture. If capture outcome is unknown, reconciliation resolves the original payment before deciding which compensation applies. Courier replacement changes delivery assignment, not food-order identity. Cancellation after preparation records the applicable charge and remaining refund rather than deleting the order.

Separate the **order** (the commercial agreement), **restaurant fulfilment** (acceptance and preparation), **payment** and **delivery assignment**. They are related lifecycles, not interchangeable enums. I start with a modular application and explicit transitions between these responsibilities.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Restaurant`, `Menu`, `MenuItem` | Catalogue with an `isAvailable` flag |
| `Cart` → `Order` | Order snapshots item prices at placement time |
| `OrderState` | `PLACED → ACCEPTED → PREPARING → READY_FOR_PICKUP → PICKED_UP → DELIVERED`; `CANCELLED`, `REJECTED` |
| `DeliveryAgent` | Location, capacity, current orders |
| `AssignmentStrategy` | `Nearest`, `BatchingAware`, `LeastLoaded` |
| `OrderObserver` | `CustomerNotifier`, `RestaurantNotifier`, `AgentNotifier` |
| `PaymentService`, `RefundPolicy` | Refund amount by state |

```java
enum OrderStatus {
    PLACED, ACCEPTED, PREPARING, READY_FOR_PICKUP, PICKED_UP, DELIVERED, CANCELLED, REJECTED;
    private static final Map<OrderStatus, Set<OrderStatus>> NEXT = Map.of(
        PLACED, Set.of(ACCEPTED, REJECTED, CANCELLED),
        ACCEPTED, Set.of(PREPARING, CANCELLED), /* ... */);
    boolean canGo(OrderStatus to) { return NEXT.getOrDefault(this, Set.of()).contains(to); }
}
```

### Design decisions & trade-offs

**1. Transition table vs. full State classes.** A transition map on an enum is compact and easy to audit. Full State classes pay off when each state has *behaviour* (cancellation refunds, allowed edits). A common answer is the enum for legality plus a `RefundPolicy` keyed by state.

**2. When to assign the agent.** Assigning at `PLACED` wastes agent time if the restaurant is slow. Assigning at `READY` makes the customer wait. Assign when `remainingPrepTime ≈ agentTravelTime`. That's a Strategy, and it's the trade-off interviewers want discussed.

**3. Price snapshot.** Copy price and name into `OrderItem`. Menu edits after ordering must not change the bill.

**4. Observer for fan-out.** Each transition publishes `OrderStatusChanged`. Notifiers, ETA recompute and analytics subscribe independently.

**5. Concurrency.** The restaurant's accept and the customer's cancel can race. Guard transitions with a conditional update (`compareAndSet` on status, or `UPDATE … WHERE status = :expected`), so only one wins.

### Ownership, boundaries and invariants

**Central design question:** An order coordinates restaurant, courier and payment states without pretending they are one atomic action.

Restaurant owns menu versions; Cart holds selections; Order snapshots item names, options, prices and delivery address. RestaurantOrder records acceptance and preparation; Delivery records assignment and proof of delivery. FeePolicy and PaymentGateway are separate ports.

**Correctness rule:** An accepted order retains the agreed price and items even when the live menu changes. A delivered order must not return to preparing because a late event arrives.

```text
orders(id,menu_version,total_minor,state,version); order_line(snapshot); delivery(order_id,courier_id,status); payment_attempt(id,status)
```

### End-to-end execution trace

Validate menu and service area; create price snapshot; authorize payment; ask restaurant to accept; capture according to policy; assign a courier; record pickup and delivery; handle cancellation/refund through explicit compensating operations.

### Concurrency and recovery walkthrough

A restaurant accepts while the customer cancels. Compare the order version and use cancellation rules for the resulting state. Deduplicate provider and courier events by event identity, not by matching message text.

### Policy choices and extension seams

Separate payment, preparation and delivery state axes avoid one enormous enum with impossible combinations. A coordinator keeps legal combinations explicit. Observer-style notifications may update views but must not commit payment state.

### Edge cases that change the design

One unavailable menu item may require partial acceptance with customer approval. An address change after courier assignment affects fees and serviceability. No courier available is a recoverable dispatch problem, not evidence that food was never prepared.

**Topic-specific cases:** Menu price changes do not alter an order; duplicate pickup ignored; cancel/accept race; partial item rejection; payment uncertainty; invalid address change.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through retries and cancellation

The same restaurant acceptance event may arrive twice. Apply it once by decision identity and legal source state. An acceptance arriving after cancellation must not resurrect the order. Similarly, reassigning a courier should not create a second restaurant preparation request.

Cancellation before preparation may be free; cancellation after food is prepared may have a charge. Put this rule in a cancellation policy using recorded milestones. Do not inspect a stale UI label and guess whether the kitchen has started.

Keep network calls outside database locks. Record intent, call the provider, then record the result. If the process stops between those steps, resume using the original operation reference. A void and a refund are different actions depending on whether money was only authorized or already captured.

## 6. Interviewer follow-ups

**Why snapshot the address?** Editing a profile after dispatch must not redirect an already accepted delivery without an explicit change operation.

**Does a payment success mean restaurant acceptance?** No. Financial and fulfilment outcomes are separate.

## 7. Closing answer

My order freezes accepted commercial terms and coordinates separate restaurant, financial and delivery states. Recorded milestones decide cancellation and compensation. Idempotent events advance only legal transitions, so duplicate acceptance or courier events cannot resurrect a cancelled order or repeat payment.

## Problem

Design a library management system. Members search for books, borrow physical copies, return them, renew loans and join a waiting list when every copy is out. Late returns are fined.

The design question underneath: a *book* (a title in the catalogue) is not the same thing as a *copy* on the shelf. Getting that distinction right makes everything else simple.

## Requirements

- Search the catalogue by title, author or ISBN.
- A member can borrow up to 3 books at a time, for 14 days each.
- Renew a loan once, unless another member is waiting for that book.
- Return a book; charge ₹10 for every day it is late.
- If all copies are out, a member can place a hold. When a copy comes back, the first person in the queue gets it and has 2 days to collect it.
- Librarians add books and copies.

Out of scope: e-books, multiple branches, payments for fines, membership sign-up.

## 1. Clarify the scope

| Do we track each physical copy? | Yes, by barcode. | We need `Book` (title) and `BookItem` (copy). |
| Are limits the same for all members? | Different plans (Basic: 3 books, 14 days; Premium: 5 books, 21 days). | Limits live in a `MembershipPlan`, not in subclasses. |
| Is the waiting list per copy or per title? | Per title: any copy can satisfy it. | The hold queue belongs to `Book`. |
| How are fines paid? | Recorded on return; payment is separate. | A return never waits for a payment. |
| How many librarians at once? | Several desks at the same time. | Checkout must be safe when two desks scan the last copy. |


Why a `MembershipPlan` instead of `StudentMember` and `FacultyMember` subclasses? The members behave the same way; only the numbers differ. Composition lets the library add a new plan without writing a new class.

## 3. Checkout and return

Example: Asha (Basic plan) borrows copy C17 of *Practical Java* on 1 October. It is due on 15 October.

```java
public class LibraryService {
    private final Map<String, BookItem> itemsByBarcode;
    private final Map<String, Loan> activeLoanByBarcode = new HashMap<>();
    private final Notifier notifier;
    private final Clock clock;

    public synchronized Loan checkout(Member member, String barcode) {
        BookItem item = itemsByBarcode.get(barcode);
        MembershipPlan plan = member.getPlan();
        if (member.activeLoanCount() >= plan.maxBooks()) {
            throw new LimitReachedException(member.getId());
        }
        boolean collectingHold = item.getStatus() == ItemStatus.ON_HOLD_SHELF
                && item.getBook().isReadyFor(member, today());
        if (item.getStatus() != ItemStatus.AVAILABLE && !collectingHold) {
            throw new ItemNotAvailableException(barcode);
        }
        if (collectingHold) item.getBook().fulfilHold(member);

        LocalDate today = today();
        Loan loan = new Loan(UUID.randomUUID().toString(), item, member, today, today.plusDays(plan.loanDays()));
        item.setStatus(ItemStatus.ON_LOAN);
        activeLoanByBarcode.put(barcode, loan);
        member.addLoan(loan);
        return loan;
    }

    private LocalDate today() { return LocalDate.now(clock); }
}
```

`synchronized` matters at a busy library: two desks scanning the last copy (or the same member at two desks taking their last allowed book) must not both succeed. The check and the change happen together.

Returning closes the loan, records the fine, and decides where the copy goes next:

```java
public synchronized long returnBook(String barcode) {
    Loan loan = activeLoanByBarcode.remove(barcode);
    if (loan == null) throw new IllegalStateException("Copy is not on loan");
    LocalDate today = today();
    loan.close(today);
    loan.getMember().removeLoan(loan);

    long daysLate = Math.max(0, ChronoUnit.DAYS.between(loan.getDueDate(), today));
    long fine = daysLate * loan.getMember().getPlan().finePerDayRupees();

    BookItem item = loan.getItem();
    Optional<Hold> next = item.getBook().nextWaitingHold();
    if (next.isPresent()) {
        next.get().markReady(today.plusDays(2));     // 2 days to collect
        item.setStatus(ItemStatus.ON_HOLD_SHELF);
        notifier.bookReady(next.get());               // Observer
    } else {
        item.setStatus(ItemStatus.AVAILABLE);
    }
    return fine;
}
```

Asha returns C17 on 18 October. `DAYS.between(15 Oct, 18 Oct)` is 3, so the fine is 3 × ₹10 = ₹30. Returning on the 15th itself costs nothing: the due date is still on time.

Use `LocalDate` and calendar days, not milliseconds divided by 86,400,000. Dates avoid off-by-one surprises around midnight and daylight-saving changes.

## 4. Holds: a fair waiting list

Bilal and then Chetan place holds on *Practical Java* while Asha has the only copy. Each `Book` keeps a FIFO queue:

```java
class Book {
    private final Deque<Hold> holds = new ArrayDeque<>();

    Hold placeHold(Member member, LocalDate today) {
        if (holds.stream().anyMatch(h -> h.getMember().equals(member) && h.isOpen())) {
            throw new IllegalStateException("Already waiting");
        }
        Hold hold = new Hold(member, this, today);
        holds.addLast(hold);
        return hold;
    }

    Optional<Hold> nextWaitingHold() {
        return holds.stream().filter(h -> h.getStatus() == HoldStatus.WAITING).findFirst();
    }
}
```

**Renewal** extends the same loan instead of creating a new one. It is refused if the loan is overdue, the plan's renewals are used up, or someone is waiting for the title:

```java
public synchronized Loan renew(Loan loan) {
    MembershipPlan plan = loan.getMember().getPlan();
    if (today().isAfter(loan.getDueDate())) throw new RenewalDeniedException("Overdue");
    if (loan.getRenewals() >= plan.maxRenewals()) throw new RenewalDeniedException("No renewals left");
    if (loan.getItem().getBook().nextWaitingHold().isPresent()) throw new RenewalDeniedException("Someone is waiting");
    loan.extendBy(plan.loanDays());
    return loan;
}
```

## 6. Interviewer follow-ups

**Can two members take the last copy at the same time?** No. Checkout checks status and changes it inside one synchronized method (or one database transaction with a row lock on the copy). The second desk sees ON_LOAN.

**Why is the hold on the `Book`, not the `BookItem`?** The member wants the title, not a particular barcode. A hold on a copy would leave them waiting for that one copy while another copy sits on the shelf.

**What if a returned book is damaged?** Mark the copy as being repaired (an extra status) and do not offer it to the hold queue. The waiting member stays in the queue for the next healthy copy.

**What if the first person in the queue has reached their borrowing limit?** Skip them for now (or cancel their hold with a reason) and offer the copy to the next eligible member. State whichever policy you choose.

**Why doesn't return wait for the fine to be paid?** The physical book is back on the desk. Accepting it and recording the fine are local steps; payment can fail or take time and should never block the next reader.

**How would you store this in a database?** Tables for `book`, `book_item`, `member`, `loan`, `hold`. A copy may appear in many historical loans, so do not put a unique constraint on `loan.item_id`; instead allow only one loan per item with `return_date IS NULL` (a partial unique index in PostgreSQL).

## 3. Splitting without losing a paisa

Asha, Ben and Cara take a taxi. Asha pays **₹100.01 = 10,001 paise**, split equally. 10,001 / 3 = 3,333 with 2 paise left over. Give the extra paise to the first two members in a fixed order:

| Member | Share |
| --- | --- |
| Asha | 3,334 |
| Ben | 3,334 |
| Cara | 3,333 |
| **Total** | **10,001** |

```java
interface SplitStrategy {
    List<Split> split(long amountPaise, List<User> users, List<Long> inputs);
}

class EqualSplit implements SplitStrategy {
    public List<Split> split(long amount, List<User> users, List<Long> ignored) {
        long base = amount / users.size();
        long remainder = amount % users.size();
        List<Split> result = new ArrayList<>();
        for (int i = 0; i < users.size(); i++) {
            result.add(new Split(users.get(i), base + (i < remainder ? 1 : 0)));
        }
        return result;
    }
}

class ExactSplit implements SplitStrategy {
    public List<Split> split(long amount, List<User> users, List<Long> exactPaise) {
        if (exactPaise.stream().mapToLong(Long::longValue).sum() != amount) {
            throw new IllegalArgumentException("Exact shares must add up to the total");
        }
        List<Split> result = new ArrayList<>();
        for (int i = 0; i < users.size(); i++) result.add(new Split(users.get(i), exactPaise.get(i)));
        return result;
    }
}

class PercentSplit implements SplitStrategy {
    // inputs are basis points: 100% = 10,000, so 12.5% = 1,250
    public List<Split> split(long amount, List<User> users, List<Long> basisPoints) {
        if (basisPoints.stream().mapToLong(Long::longValue).sum() != 10_000) {
            throw new IllegalArgumentException("Percentages must add up to 100");
        }
        List<Split> result = new ArrayList<>();
        long used = 0;
        for (int i = 0; i < users.size(); i++) {
            long share = amount * basisPoints.get(i) / 10_000;    // rounds down
            result.add(new Split(users.get(i), share));
            used += share;
        }
        for (int i = 0; used < amount; i++, used++) {             // hand out leftover paise
            Split s = result.get(i);
            result.set(i, new Split(s.user(), s.amount() + 1));
        }
        return result;
    }
}
```

Every strategy ends with shares that **add up exactly to the total**. That single rule is what keeps the group's books balanced. (For very large amounts, use `Math.multiplyExact` or `BigInteger` for the multiplication.)

## 4. Updating balances

The balance sheet stores pairwise debts. When Asha pays and Ben's share is ₹33.34, Ben owes Asha ₹33.34 more, which is the same as Asha owing Ben ₹33.34 less:

```java
class BalanceSheet {
    // balances.get(a).get(b) > 0  means  b owes a that many paise
    private final Map<String, Map<String, Long>> balances = new HashMap<>();

    void add(String creditor, String debtor, long amount) {
        if (creditor.equals(debtor) || amount == 0) return;   // you don't owe yourself
        balances.computeIfAbsent(creditor, k -> new HashMap<>()).merge(debtor, amount, Long::sum);
        balances.computeIfAbsent(debtor, k -> new HashMap<>()).merge(creditor, -amount, Long::sum);
    }

    long netBalance(String user) {                 // positive: is owed, negative: owes
        return balances.getOrDefault(user, Map.of()).values().stream().mapToLong(Long::longValue).sum();
    }
}

public class ExpenseService {
    private final BalanceSheet sheet = new BalanceSheet();
    private final List<Expense> expenses = new ArrayList<>();

    public synchronized Expense addExpense(String description, User paidBy, long amount,
                                           List<User> users, SplitStrategy strategy, List<Long> inputs) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        List<Split> splits = strategy.split(amount, users, inputs);
        Expense expense = new Expense(UUID.randomUUID().toString(), description, paidBy, amount, splits);
        for (Split s : splits) {
            sheet.add(paidBy.getId(), s.user().getId(), s.amount());
        }
        expenses.add(expense);
        return expense;
    }

    public synchronized void settle(User from, User to, long amount) {
        sheet.add(from.getId(), to.getId(), amount);   // paying reduces what "from" owes "to"
    }
}
```

After the taxi, `add` skips Asha's own share (you never owe yourself), so Asha is owed 3,334 + 3,333 = **6,667 paise = ₹66.67**. Ben owes ₹33.34 and Cara owes ₹33.33. The net balances add to zero: 6,667 − 3,334 − 3,333 = 0. **Net balances always sum to zero** – a great invariant to mention and to test.

`settle(Ben, Asha, 3334)` adds 3,334 to "Asha owes Ben", cancelling Ben's debt exactly.

[![Ben reports paying Asha; when Asha confirms receipt, one balanced entry credits Ben and debits Asha, and a repeated confirmation creates no second entry.](learning-figures/lld-10-payment.svg)](learning-figures/lld-10-payment.svg)

## 5. Simplifying debts

Suppose after many expenses the net balances are: Asha +₹70, Ben −₹30, Cara −₹40. Instead of everyone paying everyone, settle with net amounts. Greedy rule: repeatedly match the person who owes the most with the person owed the most.

```java
record Payment(String from, String to, long amount) {}

class DebtSimplifier {
    List<Payment> simplify(Map<String, Long> net) {
        PriorityQueue<Map.Entry<String, Long>> creditors =
                new PriorityQueue<>((a, b) -> Long.compare(b.getValue(), a.getValue()));
        PriorityQueue<Map.Entry<String, Long>> debtors =
                new PriorityQueue<>((a, b) -> Long.compare(a.getValue(), b.getValue()));
        net.entrySet().forEach(e -> {
            if (e.getValue() > 0) creditors.add(new AbstractMap.SimpleEntry<>(e));
            if (e.getValue() < 0) debtors.add(new AbstractMap.SimpleEntry<>(e));
        });

        List<Payment> payments = new ArrayList<>();
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            var c = creditors.poll();
            var d = debtors.poll();
            long amount = Math.min(c.getValue(), -d.getValue());
            payments.add(new Payment(d.getKey(), c.getKey(), amount));
            if (c.getValue() - amount > 0) creditors.add(new AbstractMap.SimpleEntry<>(c.getKey(), c.getValue() - amount));
            if (d.getValue() + amount < 0) debtors.add(new AbstractMap.SimpleEntry<>(d.getKey(), d.getValue() + amount));
        }
        return payments;
    }
}
```

Result: Cara pays Asha ₹40, Ben pays Asha ₹30. Two payments. Each step settles at least one person fully, so with *n* people there are at most *n − 1* payments, and the heaps make it O(n log n).

![Animation: net balances Asha +70, Ben −30, Cara −40; the largest debtor Cara pays the largest creditor Asha 40; then Ben pays Asha 30; everyone reaches zero in two payments.](learning-figures/lld-10-simplify.gif)

| Pattern | Where | Why it helps |

## 7. Interviewer follow-ups

**Is the greedy simplification always minimal?** Not guaranteed. The true minimum is *n* minus the largest number of separate sub-groups whose balances each sum to zero (for example, if Ben owes exactly what Dev is owed, they can settle between themselves). Finding those sub-groups is NP-hard in general, so real apps use greedy. Say clearly: greedy gives at most *n − 1* payments and is good enough in practice.

**How do you handle multiple payers?** Each person's change = what they paid − their share. Asha paid ₹600 and Ben ₹400 for a ₹1,000 dinner split four ways (₹250 each): Asha +₹350, Ben +₹150, Cara −₹250, Dev −₹250. Work with these net changes per expense.

**How do you edit or delete an expense?** Do not silently change history. Add a reversal (the same splits with opposite signs) and then a new corrected expense. Balances stay explainable.

**Why `long` paise and not `double`?** `0.1 + 0.2 != 0.3` in binary floating point. Integer paise make "shares add up to the total" exactly checkable.

**Two members add expenses at the same time?** `addExpense` is synchronized per group (one lock per group in a real system), or each expense is written in one database transaction together with its balance changes.

**How would you store this?** Tables for `expense`, `expense_split` and either a `balance` table updated in the same transaction, or compute balances from splits on demand and cache them.

## 8. Going deeper (optional)

The full reference implementation goes further on correctness:

- **Journal entries.** Every expense, confirmed payment and reversal is an immutable balanced entry; balances are rebuilt from the journal.
- **Two-step payments.** The sender reports a payment; it changes balances only when the receiver confirms it.
- **Retry safety.** An expense ID retried with the same data returns the original expense; the same ID with different data is rejected.

"I model User, Group, Expense and Split, with split types as strategies – equal, exact and percent – that always return shares adding up exactly to the total in paise, giving leftover paise by a fixed rule. `ExpenseService` records an expense and updates a pairwise `BalanceSheet`; net balances always sum to zero. Design a coffee vending machine that serves espresso, cappuccino, latte and so on. Each drink consumes ingredients (water, milk, beans, sugar). ### Worked calculation and implementation

A recipe requiring 10 g beans and 150 ml water allows `min(beans/10, water/150, cups)` servings. With 95 g beans, 1,000 ml water and 20 cups, water limits capacity to six drinks. Inventory checks must reserve the whole recipe together; separately decrementing beans and then discovering no cup leaves inconsistent stock.

```text
VendSession: IDLE -> SELECTED -> FUNDED -> DISPENSING -> COMPLETE
Failures: SELECTED/FUNDED -> CANCELLED
          DISPENSING -> DELIVERY_UNCERTAIN -> RECONCILIATION
```

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `VendingMachine` | Context and facade; holds the current `MachineState` |
| `MachineState` | `Idle`, `Selecting`, `PaymentPending`, `Dispensing`, `Maintenance` |
| `Beverage` / `Recipe` | name, price, `Map<Ingredient, Integer>` quantities |
| `BeverageFactory` | `create(type)` builds a beverage from the recipe registry |
| `Inventory` | `hasEnough(recipe)`, `deduct(recipe)` (atomic), `refill` |
| `PaymentHandler` | Strategy: `CoinPayment`, `CardPayment`; change calculation |
| `InventoryObserver` | Low-stock alert |

```java
class Inventory {
    private final Map<Ingredient, Integer> stock = new EnumMap<>(Ingredient.class);
    synchronized boolean tryDeduct(Recipe r) {
        if (!r.needs().entrySet().stream().allMatch(e -> stock.get(e.getKey()) >= e.getValue())) return false;
        r.needs().forEach((ing, q) -> stock.merge(ing, -q, Integer::sum));
        return true;
    }
}
```

### Design decisions & trade-offs

**1. Recipes as data.** Don't make `Cappuccino extends Coffee` with hard-coded quantities. A recipe registry (loaded from config) plus a Factory means a new drink is a config entry. Use a Decorator only for user add-ons (extra shot, extra sugar).

**2. Check and deduct atomically.** "Check, then deduct" as two calls races if two dispense paths exist. A single `tryDeduct` under a lock is all-or-nothing.

**3. When to deduct versus when to charge.** Order: confirm availability, collect payment, reserve and deduct ingredients, dispense. If dispensing fails, refund and restore ingredients. Never take money for a drink you can't make.

**4. State pattern.** In `Maintenance`, selections are rejected. In `Dispensing`, cancel is rejected. Each state handles only its legal events.

**5. Menu availability is derived.** Recompute which drinks are selectable from inventory after every deduct or refill, and push that to the display (Observer).

### Ownership, boundaries and invariants

**Central design question:** Inventory reservation, money acceptance and physical dispensing are separate observable steps.

Machine owns SlotInventory and a VendSession. Product describes a SKU; Recipe or Selection maps it to ingredients when appropriate. PaymentAcceptor tracks tender; ChangePolicy selects available denominations; DispenserPort reports success or jam. RefundJournal records incomplete recovery.

**Correctness rule:** Never decrement sellable stock twice for one vend request. Do not claim successful delivery before the hardware confirms it. Accepted money must end in purchase, change, refund or an explicit recoverable balance.

```text
slot(id,sku,available,reserved); vend(id,sku,price_minor,tender_minor,state); cash(denomination,count)
```

### End-to-end execution trace

Select a product; validate stock and price; reserve stock; accept sufficient tender; verify change availability; journal the vend; dispense; on confirmation consume stock and return change; on jam reverse the reservation and initiate refund.

### Concurrency and recovery walkthrough

Two sessions select the last unit while an operator restocks. One inventory owner serializes reserve/commit/release; restocking must not overwrite reserved counts. Network payment callbacks use the vend operation ID.

### Policy choices and extension seams

State is helpful for selection/payment/dispense transitions. Different products can use Strategy for preparation. Do not let product factories control cash or mutate global inventory.

### Edge cases that change the design

Enough total money does not imply the machine can make change. Power loss after dispensing needs journal reconciliation. A refund actuator can fail too, so expose an operator-review state instead of looping forever.

**Topic-specific cases:** Last-item race; exact change; impossible change; jam; duplicate confirmation; refund failure; restart during dispense.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through the important decisions

Coin selection is a bounded change problem: available denominations and counts matter. A ₹20 difference does not prove a ₹20 coin is present. Reserve a feasible change plan before consuming money, or show an exact-change policy before purchase.

Once hot water has entered a cup, cancelling cannot restore the original ingredients. Record consumed quantities and waste; do not “roll back” physical brewing by incrementing every ingredient counter. Maintenance mode should block new sessions and reconcile cash/stock under an operator identity.

## 6. Interviewer follow-ups

**Does a new drink require another machine state?** Usually no. A new recipe changes data; new physical behaviour may need a new dispenser strategy.

**Can a failed sensor mean zero delivery?** Not necessarily. Distinguish known none from unknown.

## 7. Closing answer

I reserve a complete recipe and feasible change plan before vending. Session state distinguishes financial acceptance from physical delivery, and unknown dispense outcomes require evidence rather than an automatic second drink. Recipes are data; hardware and payment are explicit adapters.
