## Problem

Design the shopping cart and pricing engine of an online store. Asha adds 3 pairs of running socks (₹299 each) and trail shoes (₹3,499). There's a "buy 2 socks, get 1 free" deal and she has a coupon **RUN10**: 10% off orders of ₹999 or more, up to ₹200.

The cart must show her an exact price breakdown, apply deals in a predictable order, and make sure the price she pays at checkout is the price she saw.

## Requirements

- Add items, change quantities, remove items.
- Apply pricing rules: item deals (buy X get Y), coupons with minimums and caps, delivery fee.
- Show a clear breakdown: subtotal, each discount with its reason, delivery, total.
- New promotion types can be added without rewriting the cart.
- At checkout, charge the quoted price – or show a new quote if it changed.

## Step 1: Clarify the requirements

**Candidate:** Which kinds of promotions do we need?

**Interviewer:** Buy-X-get-Y on items, percentage coupons with a cap, free delivery above a threshold.

**Candidate:** Can promotions stack?

**Interviewer:** Item deals first, then one coupon on what's left.

**Candidate:** What if a price changes while the item sits in the cart?

**Interviewer:** The customer must never pay more than they saw without being told.

**Candidate:** How is money represented?

**Interviewer:** Your choice – but no rounding surprises.

**Candidate:** Do we handle tax?

**Interviewer:** Assume prices include GST.

> **🎯 In the interview**
> Ask about stacking order. "10% off, then ₹299 off" and "₹299 off, then 10% off" give different totals; the order must be a deliberate rule.

| Functional | Non-functional |
| --- | --- |
| Cart operations | Exact money (no floating point) |
| Pricing rules and breakdown | Predictable rule order |
| Quote and checkout | Easy to add new promotions |

## Step 2: Identify the core objects

- **Product** – SKU, name, price, category.
- **Cart** – products and quantities; produces cart lines.
- **PricingRule** – one promotion; returns a discount or nothing.
- **Discount** – an amount and a reason shown to the customer.
- **PricingEngine** – runs the rules in order and builds a quote.
- **Quote** – the full breakdown plus an expiry time.
- **Checkout** – accepts a quote only if it's still valid.

[![Selected design: the cart holds products and quantities; the pricing engine runs an ordered list of pricing rules over the cart lines to produce a quote with every discount and an expiry; checkout re-prices and accepts the quote only if nothing changed.](designs/lld-12.svg)](designs/lld-12.svg)

> **⚖️ Design choice**
> Each promotion is a **Strategy** (`PricingRule`) and the engine applies a list of them in order – a simple **chain**. A new promotion type is a new class added to the list; the cart and engine don't change.

## Step 3: Design the classes

### Product and Cart

A `Product` is an immutable record. The `Cart` maps SKUs to quantities and hands out `Line`s (product + quantity).

### PricingRule and Discount

The interface has one method: given the lines and the subtotal left so far, return an optional `Discount`. `BuyTwoGetOne` and `PercentCoupon` are two implementations.

### PricingEngine and Quote

The engine starts from the item subtotal, applies each rule in order, reduces the subtotal after each one, then adds delivery. The `Quote` keeps everything the customer saw and when it expires.

### Checkout

Re-prices the cart; if the total differs or the quote expired, it refuses with a new quote.

[![Class diagram: a Cart has Lines of Products; PricingEngine holds an ordered list of PricingRules, implemented by BuyTwoGetOne and PercentCoupon, and produces a Quote with Discounts; Checkout uses the engine to confirm a quote.](learning-figures/lld-12-classes.svg)](learning-figures/lld-12-classes.svg)

## Step 4: Write the code

### Cart

```java
record Product(String sku, String name, long pricePaise, String category) {}

class Cart {
    private final Map<String, Integer> qty = new LinkedHashMap<>();
    private final Map<String, Product> products = new HashMap<>();

    void add(Product p, int n) {
        if (n <= 0) throw new IllegalArgumentException("Quantity must be positive");
        products.put(p.sku(), p);
        qty.merge(p.sku(), n, Integer::sum);
    }
    void setQuantity(String sku, int n) {
        if (n <= 0) { qty.remove(sku); products.remove(sku); } else qty.put(sku, n);
    }
    List<Line> lines() {
        return qty.entrySet().stream()
                .map(e -> new Line(products.get(e.getKey()), e.getValue())).toList();
    }
    record Line(Product product, int qty) {
        long totalPaise() { return product.pricePaise() * qty; }
    }
}
```

### Pricing rules

```java
record Discount(String reason, long amountPaise) {}

/** One pricing rule. Each looks at the cart and the subtotal left after earlier rules. */
interface PricingRule {
    Optional<Discount> apply(List<Cart.Line> lines, long subtotalPaise);
}

/** Buy 2, get 1 free on one SKU: every third unit is free. */
record BuyTwoGetOne(String sku) implements PricingRule {
    public Optional<Discount> apply(List<Cart.Line> lines, long subtotal) {
        return lines.stream().filter(l -> l.product().sku().equals(sku)).findFirst()
                .filter(l -> l.qty() >= 3)
                .map(l -> new Discount("Buy 2 get 1: " + l.product().name(),
                        (l.qty() / 3) * l.product().pricePaise()));
    }
}

/** Percentage coupon with a cap, e.g. 10% off up to Rs 200 on orders from Rs 999. */
record PercentCoupon(String code, int percent, long minOrderPaise, long capPaise)
        implements PricingRule {
    public Optional<Discount> apply(List<Cart.Line> lines, long subtotal) {
        if (subtotal < minOrderPaise) return Optional.empty();
        long off = Math.min(subtotal * percent / 100, capPaise);
        return Optional.of(new Discount("Coupon " + code, off));
    }
}
```

### PricingEngine and Quote

```java
record Quote(List<Cart.Line> lines, List<Discount> discounts, long subtotalPaise,
             long deliveryPaise, long totalPaise, Instant expiresAt) {}

class PricingEngine {
    private final List<PricingRule> rules;     // order matters: item deals, then coupons
    private final long freeDeliveryFromPaise = 49_900, deliveryFeePaise = 4_000;

    PricingEngine(List<PricingRule> rules) { this.rules = List.copyOf(rules); }

    Quote quote(Cart cart, Instant now) {
        List<Cart.Line> lines = cart.lines();
        long subtotal = lines.stream().mapToLong(Cart.Line::totalPaise).sum();
        List<Discount> applied = new ArrayList<>();
        for (PricingRule rule : rules) {
            Optional<Discount> d = rule.apply(lines, subtotal);
            if (d.isPresent()) {
                long off = Math.min(d.get().amountPaise(), subtotal);  // never below 0
                applied.add(new Discount(d.get().reason(), off));
                subtotal -= off;
            }
        }
        long delivery = subtotal >= freeDeliveryFromPaise ? 0 : deliveryFeePaise;
        return new Quote(lines, applied, subtotal, delivery, subtotal + delivery,
                now.plusSeconds(15 * 60));
    }
}
```

### Checkout

```java
class Checkout {
    private final PricingEngine engine;
    Checkout(PricingEngine engine) { this.engine = engine; }

    /** The customer pays the quote they saw – or sees a new one if it changed. */
    Quote confirm(Cart cart, Quote shown, Instant now) {
        Quote fresh = engine.quote(cart, now);
        if (now.isAfter(shown.expiresAt()) || fresh.totalPaise() != shown.totalPaise())
            throw new QuoteChangedException(fresh);
        return shown;
    }
}

class QuoteChangedException extends RuntimeException {
    final Quote newQuote;
    QuoteChangedException(Quote q) { super("Price changed: please review"); newQuote = q; }
}
```

### Worked example

Money is in paise (`long`): ₹299 = 29,900.

| Step | Calculation | Result |
| --- | --- | --- |
| 3 socks | 3 × ₹299 = ₹897 | |
| Buy 2 get 1 | 1 free × ₹299 | − ₹299 → ₹598 |
| RUN10 | ₹598 < ₹999 minimum | not applied |
| Delivery | ₹598 ≥ ₹499 | free → **₹598** |
| + trail shoes ₹3,499 | ₹897 + ₹3,499 = ₹4,396 | |
| Buy 2 get 1 | − ₹299 | ₹4,097 |
| RUN10 | 10% of ₹4,097 = ₹409.70, capped | − ₹200 → ₹3,897 |
| Checkout after 1 minute | same total, not expired | charged ₹3,897 |
| Checkout after 16 minutes | quote expired | new quote shown (₹3,897) |
| Asha drops to 1 pair of socks | deal no longer applies | new quote ₹3,598 |

### Edge cases

| Case | Behaviour |
| --- | --- |
| Quantity 0 or negative | Remove the line / reject |
| Discount larger than the subtotal | Capped so the total never goes below 0 |
| Coupon minimum not met | Rule returns nothing; breakdown doesn't show it |
| Product price changes after quoting | Checkout sees a different total and shows the new quote |

## Step 5: The pricing algorithm: order and honesty

Two rules make pricing predictable:

1. **Rules run in a fixed order**, and each one sees the subtotal left by the rules before it. Item deals come first; cart-level coupons apply to what remains. That's why RUN10 is calculated on ₹4,097, not ₹4,396.
2. **The customer pays the quote they saw.** At checkout, re-price. If the total changed (a price update, a coupon expiring, a cart change) or the quote is older than 15 minutes, show the new quote instead of silently charging a different amount.

![Animation: three socks get the buy-two-get-one discount, the coupon is skipped because the subtotal is below 999 rupees; adding shoes raises the subtotal so the coupon applies, capped at 200 rupees; at checkout the quote is confirmed, but after the cart changes a new quote is shown instead of a silent charge.](learning-figures/lld-12-pricing.gif)

> **⚠️ Common mistake**
> Using `double` for prices. `0.1 + 0.2` is not `0.3` in binary floating point, and a percentage discount can be off by a paisa. Use `long` paise or `BigDecimal` with explicit rounding.

> **🎯 In the interview**
> If asked about "best discount for the customer", say you'd try the valid combinations of stackable rules and pick the lowest total – but keep it deterministic and explainable on the receipt.

## Step 6: Deep dives

### A new promotion type

"₹100 off any footwear" is a new `PricingRule` that sums footwear lines and returns a `Discount`. Add it to the engine's list in the right position.

### Exclusive coupons

Give rules a `group` (e.g. "coupon"). The engine applies at most one rule per group – the first that matches, or the one giving the biggest discount.

### Inventory at checkout

Pricing doesn't reserve stock. Checkout also asks inventory to reserve the items (see the e-commerce lesson, HLD-12) before taking payment.

### Saving the cart

Store carts by user ID (logged in) or a cookie ID (guest), and merge the guest cart into the user's cart at login.

## Interviewer follow-ups

**Why return a Discount instead of changing prices directly?** The receipt needs every reason and amount, and rules stay independent and testable.

**How do you round a percentage?** Decide once – usually round down in the customer's favour – and do it in one place (here, integer division of paise).

**How long should a quote last?** Long enough to pay comfortably – 15 minutes is common – and never longer than the shortest promotion or price guarantee behind it.

**How would you test the engine?** Table-driven tests: cart contents + rules → expected breakdown, exactly like the worked example.

## Wrap up

The cart holds products and quantities; an ordered chain of pricing rules turns it into a quote with every discount explained; checkout charges that quote or shows a new one.

> **📝 Key takeaways**
> - Money in paise (`long`) or `BigDecimal` – never `double`.
> - Each promotion is a `PricingRule`; the engine applies them in a fixed order.
> - The quote is the contract: show it, then charge exactly it.
> - Re-price at checkout; changes produce a visible new quote.

## Problem

Design a notification library (or a small service) that other parts of an app call to send messages over email, SMS and push. The order service says: *"Tell Asha that order 847 ships today"* – and the library works out the text, the channels Asha has turned on, and delivers each one.

Providers fail. Email servers time out; a user may have no phone number. The library must retry what can succeed later, give up on what can't, and never send the same notification twice because a caller retried.

## Requirements

- One call to notify a user through one or more channels (email, SMS, push).
- Messages come from templates filled with data ("Hi {name}, order {orderId} ships today!").
- Respect each user's channel preferences.
- Retry temporary failures with backoff; don't retry permanent ones.
- A repeated event (same event ID) is sent only once; adding a channel is easy.

## Step 1: Clarify the requirements

**Candidate:** Is this the large-scale notification system or the class design?

**Interviewer:** The class design inside one service. HLD-4 covers the distributed version.

**Candidate:** Which channels?

**Interviewer:** Email and SMS now, push soon, maybe WhatsApp later.

**Candidate:** What counts as a failure worth retrying?

**Interviewer:** Timeouts and server errors. A missing phone number won't fix itself.

**Candidate:** Can callers send the same event twice?

**Interviewer:** Yes, if their own request is retried.

**Candidate:** Do we send synchronously?

**Interviewer:** Keep it synchronous for now, but design so it can move to a queue.

> **🎯 In the interview**
> Ask "which failures are retryable?" early. Retrying a permanent error wastes time; not retrying a timeout loses messages.

| Functional | Non-functional |
| --- | --- |
| Templates, channels, preferences | No duplicate sends for the same event |
| Retry with backoff | Adding a channel touches no existing code |
| Report what happened per channel | Easy to test without real providers |

## Step 2: Identify the core objects

- **Template** – named text with placeholders; renders with data.
- **User** – contact details and the channels they've enabled.
- **Message** – one rendered text for one user on one channel.
- **Channel** – an interface; `EmailChannel`, `SmsChannel`, `PushChannel` implement it.
- **TemporaryFailure** – the exception type that means "try again later".
- **NotificationService** – renders, checks preferences, sends with retry, de-duplicates events.
- **Attempt** – the result per channel: SENT, FAILED or SKIPPED, with the number of tries.

[![Selected design: a caller sends an event to the notification service, which renders the template, checks the user's preferences and sends one message per channel through a channel interface; temporary failures are retried with backoff and every attempt is recorded.](designs/lld-13.svg)](designs/lld-13.svg)

> **⚖️ Design choice**
> Each channel is a **Strategy** behind one `Channel` interface. The service doesn't know how SMS works; adding WhatsApp is one new class registered with the service.

## Step 3: Design the classes

### Template, User and Message

Small immutable records. `Template.render` fails loudly if a placeholder has no value, so nobody receives "Hi {name}".

### Channel and TemporaryFailure

`send(message)` either returns (sent), throws `TemporaryFailure` (retry), or throws anything else (permanent).

### NotificationService

Holds the channels by type, the templates, and the set of event IDs already handled. `notify` returns one `Attempt` per requested channel.

## Step 4: Write the code

### Messages and templates

```java
enum ChannelType { EMAIL, SMS, PUSH }

record Template(String name, String text) {
    String render(Map<String, String> data) {
        String out = text;
        for (var e : data.entrySet()) out = out.replace("{" + e.getKey() + "}", e.getValue());
        if (out.contains("{")) throw new IllegalArgumentException("Missing value in " + name);
        return out;
    }
}

record User(String id, String email, String phone, String deviceToken,
            Set<ChannelType> enabled) {}
```

### Channels

```java
/** Thrown for failures worth retrying (timeouts, 5xx). Others are permanent. */
class TemporaryFailure extends RuntimeException {
    TemporaryFailure(String why) { super(why); }
}

interface Channel {
    ChannelType type();
    void send(Message m);              // throws TemporaryFailure or another exception
}

class EmailChannel implements Channel {
    final List<String> sent = new ArrayList<>();
    int failNextCalls;                 // lets the demo simulate an outage
    public ChannelType type() { return ChannelType.EMAIL; }
    public void send(Message m) {
        if (failNextCalls-- > 0) throw new TemporaryFailure("SMTP timeout");
        sent.add(m.to().email() + ": " + m.text());
    }
}

class SmsChannel implements Channel {
    final List<String> sent = new ArrayList<>();
    public ChannelType type() { return ChannelType.SMS; }
    public void send(Message m) {
        if (m.to().phone() == null) throw new IllegalArgumentException("No phone number");
        sent.add(m.to().phone() + ": " + m.text());
    }
}
```

### NotificationService

```java
enum Status { SENT, FAILED, SKIPPED }

record Attempt(Message message, Status status, int tries, String note) {}

class NotificationService {
    private final Map<ChannelType, Channel> channels = new EnumMap<>(ChannelType.class);
    private final Map<String, Template> templates;
    private final Set<String> seenEvents = new HashSet<>();   // de-duplicates retries
    private final int maxTries;
    final List<Long> backoffsMillis = new ArrayList<>();      // recorded, not slept

    NotificationService(List<Channel> list, Map<String, Template> templates, int maxTries) {
        list.forEach(c -> channels.put(c.type(), c));
        this.templates = templates; this.maxTries = maxTries;
    }

    List<Attempt> notify(String eventId, User user, String template,
                         Map<String, String> data, Set<ChannelType> wanted) {
        String text = templates.get(template).render(data);    // fails before anything is sent
        if (!seenEvents.add(eventId)) return List.of();          // already handled
        List<Attempt> results = new ArrayList<>();
        for (ChannelType type : wanted) {
            Message m = new Message(eventId, user, type, text);
            if (!user.enabled().contains(type)) {
                results.add(new Attempt(m, Status.SKIPPED, 0, "user turned it off"));
                continue;
            }
            results.add(sendWithRetry(channels.get(type), m));
        }
        return results;
    }

    private Attempt sendWithRetry(Channel channel, Message m) {
        for (int attempt = 1; attempt <= maxTries; attempt++) {
            try {
                channel.send(m);
                return new Attempt(m, Status.SENT, attempt, "ok");
            } catch (TemporaryFailure e) {
                backoffsMillis.add(1000L << (2 * (attempt - 1)));  // 1 s, 4 s, 16 s
            } catch (RuntimeException e) {
                return new Attempt(m, Status.FAILED, attempt, e.getMessage());  // permanent
            }
        }
        return new Attempt(m, Status.FAILED, maxTries, "gave up after retries");
    }
}
```

## Step 5: The retry algorithm: retry the right failures

For each channel:

1. Try to send.
2. **Success** → record SENT with the number of tries.
3. **TemporaryFailure** → wait longer each time (1 s, then 4 s, then 16 s) and try again, up to 3 tries.
4. **Any other exception** → permanent: record FAILED immediately.
5. Out of tries → FAILED, "gave up".

![Animation: Asha's order-shipped notification goes to email and SMS; email times out, waits one second, times out again, waits four seconds and succeeds on the third try; SMS succeeds at once; push is skipped because Asha turned it off; a repeated event ID sends nothing.](learning-figures/lld-13-retry.gif)

> **⚠️ Common mistake**
> Retrying every exception. Retrying "no phone number" three times just delays the failure, and retrying a 400 Bad Request can't succeed. Classify failures first.

> **🎯 In the interview**
> A retry after a timeout can still create a duplicate: the provider may have sent the email before timing out. Pass a stable key (the event ID + channel) to providers that support idempotency, and accept a rare duplicate otherwise.

## Step 6: Deep dives

### Sending asynchronously

Put each `Message` on a queue and let workers call `sendWithRetry`. The caller returns immediately; retries no longer block it. Backoff becomes "re-queue with a delay". (That's the HLD-4 design.)

### Priorities and quiet hours

Add a `priority` to the request. OTPs bypass quiet hours and rate limits; marketing messages wait until 9 a.m.

### Rate limiting per user

Before sending marketing messages, check a per-user token bucket (see the Rate Limiter lesson, LLD-14) so nobody gets 20 pushes a day.

### Templates per language and channel

Key templates by name + channel + language: SMS needs a 160-character version, email a subject and HTML body.

## Interviewer follow-ups

**Why not one big `send(type, ...)` with a switch?** Every new channel would edit that switch. With the `Channel` interface, new channels are added, not edited in (open/closed principle).

**How do you test without sending real SMS?** Inject fake channels, like the demo's `EmailChannel` that fails a set number of times and records what it "sent".

**Where do preferences come from?** A preferences store keyed by user, read for each event – checked again just before sending if delivery is delayed.

**How do you keep the "seen events" set from growing forever?** Store event IDs with a time-to-live (for example 24 hours) in a database or Redis.

## Wrap up

A notification service renders templates, respects preferences, sends through pluggable channels, retries only temporary failures with backoff, and ignores repeated events.

> **📝 Key takeaways**
> - One `Channel` interface; each provider is a strategy.
> - Fail early on template errors – before anything is sent.
> - Retry temporary failures with exponential backoff; never retry permanent ones.
> - De-duplicate by event ID; report a result per channel.

## Problem

Design a rate limiter class in Java (the LLD version, inside one JVM): `boolean allow(String key)` limits each user or API key to N requests per time window. You must implement the algorithms correctly, make them **thread-safe**, and make the algorithm swappable (**Strategy**).

## Requirements

**Functional**
- Per-key limits (user ID, IP, API key), with different limits per tier or endpoint.
- Algorithms: fixed window, sliding window log, sliding window counter, token bucket, leaky bucket.
- Return allowed or denied, plus metadata (remaining requests, retry-after).

**Non-functional**
- O(1) per call where possible, safe under many concurrent threads, and bounded memory (evict idle keys).

## 1. Scope and chosen solution

I enforce capacity 5 and refill 2 permits/second per authenticated caller in one JVM. `RateLimiter` resolves keys, `TokenBucket` owns state, and an injected monotonic clock makes arithmetic testable. Costs are positive and no larger than capacity.

## 2. Atomic decision

```text
synchronized tryAcquire(cost,nowNanos):
  elapsed = max(0,nowNanos-lastNanos)
  tokens = min(capacity,tokens + elapsed/1e9*rate)
  lastNanos = max(lastNanos,nowNanos)
  if tokens >= cost: tokens -= cost; return ALLOW
  return DENY with retryAfterNanos = ceil((cost-tokens)/rate * 1e9)
```

After depletion, 1.25 seconds refills 2.5 permits: two unit requests pass, then the next waits 0.25 seconds before HTTP-header rounding. I use fine-grained retry durations internally; a whole-second header rounds upward. Registry lookup is thread-safe but bucket synchronization covers the multi-field calculation. Idle eviction occurs only after a period long enough to restore a full bucket under the policy; premature deletion would grant another burst. Twenty-four simultaneous calls with frozen time admit exactly five. Multiple servers do not share this lock, so I do not claim global enforcement from this implementation.

### Worked calculation and implementation

With capacity 5, rate 2/s and an empty bucket at t=0, t=1.25 has 2.5 tokens. Two unit-cost requests succeed, leaving 0.5. The next needs another 0.5 token, so its earliest retry is 0.25 seconds later. Do not round retry delay downward.

```text
elapsed = max(0, nowNanos - previousNanos)
tokens = min(capacity, tokens + elapsedSeconds * rate)
if tokens >= requestCost: tokens -= requestCost; ALLOW
else: DENY, retryAfter = (requestCost - tokens) / rate
```

Handle nonpositive capacity/rate and cost greater than capacity explicitly. Floating-point arithmetic can be acceptable for an educational bucket with bounded values; fixed-point arithmetic is an alternative when exact quotas and reproducibility require it.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `RateLimiter` | Facade: `allow(key)`; looks up the key's limiter |
| `RateLimitAlgorithm` (Strategy) | `allow()` on one key's state |
| `TokenBucket`, `SlidingWindowLog`, `SlidingWindowCounter`, `FixedWindow` | Implementations |
| `RateLimitConfig` | capacity, refill rate or window, per tier |
| `LimiterRegistry` | `ConcurrentHashMap<String, RateLimitAlgorithm>` plus idle eviction |
| `Clock` | Injected time source, so tests are deterministic |


### Design decisions & trade-offs

| Algorithm | Pros | Cons |
|---|---|---|
| Fixed window | Tiny state, simple | Up to 2× burst at window edges |
| Sliding log | Exact | O(N) memory per key |
| Sliding counter | ~Exact, O(1) memory (weighted previous window) | Approximation |
| Token bucket | Allows controlled bursts, smooth refill | Two params to tune |
| Leaky bucket | Smooths output rate | Queues add latency |

**1. Lazy refill.** Never use a background thread to add tokens. Compute the refill from elapsed time on each call. That's O(1) and scales to millions of keys.

**2. Thread safety.** `synchronized` per bucket means contention only on the same key, which is usually fine. For a lock-free version, pack state into an `AtomicLong` or use `AtomicReference<State>` with a CAS loop. `computeIfAbsent` on the registry avoids creating duplicate buckets.

**3. Memory.** Evict keys idle longer than the window (a Caffeine cache with `expireAfterAccess`, or a periodic sweep).

**4. Testability.** Inject a `Clock`. Never call `System.currentTimeMillis()` inside the algorithm.

**5. Distributed version (preview of HLD #2).** State moves to Redis, and the logic runs atomically as a Lua script.

### Ownership, boundaries and invariants

**Central design question:** Time measurement and atomic token accounting define a limiter more than the chosen class pattern.

RateLimitKey identifies principal, route and policy version. RatePolicy contains capacity and refill rate. TokenBucket owns tokens and last refill time. Clock is monotonic for elapsed time. LimiterRegistry supplies bounded per-key state; Decision includes allowed, remaining and retry delay.

**Correctness rule:** At a fixed instant, accepted requests never spend more tokens than available. Refilling cannot exceed capacity, and elapsed-time calculations cannot create tokens from a backward wall clock jump.

```text
key(principal,route,policy_version); bucket(tokens,last_refill_nanos); policy(capacity,rate_per_second)
```

### End-to-end execution trace

Resolve policy; locate the bucket; acquire its synchronization boundary; calculate elapsed monotonic time; refill with a cap; consume if enough; return a retry delay based on the deficit; release the lock before request processing.

### Concurrency and recovery walkthrough

One hundred threads request the final token simultaneously. Refill and consume must be one critical section; a thread-safe map does not make a read-modify-write bucket sequence atomic.

### Policy choices and extension seams

Token bucket permits bounded bursts; leaky bucket smooths output; fixed windows permit boundary bursts; sliding logs offer exact windows at higher memory cost. Single-JVM correctness does not imply global quotas across replicas.

### Edge cases that change the design

Idle-key eviction can reset quota if implemented carelessly. Fractional refill needs numeric care and overflow-safe elapsed handling. Costs must be positive; reject configuration with zero refill when retry calculation divides by rate.

**Topic-specific cases:** Initial burst cap; concurrent last-token race; fractional refill; clock behavior; bounded key eviction; exact retry-after calculation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through deployment boundaries

Three servers each allowing five immediate requests can collectively allow fifteen. For a global five-request burst, use a shared atomic decision store, route each key to one owner, or explicitly allocate sub-budgets. The latter can underuse quota and needs reassignment rules.

Use monotonic elapsed time for a local bucket; wall-clock corrections must not mint tokens. Evicting idle callers is safe only when the recreated state matches the policy. Deleting an exhausted bucket and recreating it full immediately grants another burst.

## 6. Interviewer follow-ups

**Does a thread-safe map make the whole bucket algorithm atomic?** No. Coordinate state calculation and consumption for each key.

**Does a denied request consume a token?** Define it; a common admission policy consumes only allowed work.

## 7. Closing answer

I choose a per-key token bucket with atomic refill-and-consume, monotonic time and explicit retry delay. The local implementation serializes one bucket without blocking unrelated keys. A global quota needs one shared decision authority or consciously allocated local sub-budgets.

## Problem

Design a digital wallet like Paytm or PhonePe: users top up from a bank or card, pay merchants, transfer to other users, and see a history. Money moves must be **atomic**, **idempotent** and **auditable**. This combines a transaction **State machine**, **Strategy** for payment instruments, and careful concurrency.

## Requirements

**Functional**
- Create a wallet, top up via a gateway, pay a merchant, P2P transfer, withdraw to a bank, view the statement.
- Limits (per-transaction, daily, KYC tier). Refunds and reversals.

**Non-functional**
- Never lose or create money. Balances must match the ledger exactly.
- Client retries must not double-charge. Concurrent transfers must not overdraw.

## 1. Scope and chosen solution

I transfer INR minor units between internal wallets with no overdraft. Wallet identity and transfer identity are separate; the ledger explains balances. External top-up/cash-out uses a separate provider workflow, not the internal atomic transfer transaction.

## 2. Internal transfer transaction

```text
transfer(id,from,to,amount,currency):
  validate positive amount, same currency, distinct wallets and actor permission
  return existing result for matching id/payload, reject conflicting reuse
  lock wallets in stable ID order
  verify spendable balance; insert transfer and debit/credit entries
  update protected balance projection and commit
```

For ₹500 in A and a ₹200 transfer, entries are A −20,000 paise and B +20,000. The sum is zero and A becomes ₹300. Two ₹400 debits against ₹500 cannot both pass the locked funds check. Fee collection adds balanced entries to an explicit fee account. Reversal is another uniquely identified transfer linked to the original. A provider timeout remains pending under its original reference; reconciliation confirms whether collection happened before another attempt or refund is authorized.

### Worked calculation and implementation

If A has 50,000 paise and transfers 20,000 to B, A ends with 30,000 and B increases by 20,000. The signed entry sum for the internal transfer is zero. Fees require explicit entries to a fee account; otherwise conservation appears to break.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Wallet` | id, user, `balance` (derived or cached), status, version |
| `LedgerEntry` | Immutable: txnId, walletId, `DEBIT/CREDIT`, amount, balanceAfter |
| `Transfer` | id, type, amount, from, to, `TransferState`, idempotencyKey |
| `TransferState` | `POSTED → REVERSED`; external funding intents separately track pending/unknown results |
| `PaymentInstrument` (Strategy) | `Card`, `UPI`, `NetBanking` for top-ups |
| `IdempotencyStore` | key → result (first result wins) |
| `LimitPolicy` | Chain of checks: KYC tier, daily cap, velocity |

### Design decisions & trade-offs

**1. Double-entry ledger as the source of truth.** Each transfer writes two entries (debit A, credit B) that sum to zero, in one transaction. A balance is the sum of entries. Cache it on the wallet row for speed, but you can always rebuild and reconcile it.

**2. Atomic transfer without deadlocks.**
```java
void transfer(Wallet a, Wallet b, Money amt) {
    Wallet first = a.id().compareTo(b.id()) < 0 ? a : b, second = first == a ? b : a;
    synchronized (first) { synchronized (second) {
        if (a.balance().lt(amt)) throw new InsufficientFunds();
        a.debit(amt); b.credit(amt); ledger.append(/* two entries */);
    }}
}
```
Lock in a global order (by ID) to avoid A→B / B→A deadlock. In a DB: `SELECT … FOR UPDATE` in ID order, or a conditional `UPDATE wallet SET balance = balance - :x WHERE id=:a AND balance >= :x`.

**3. Idempotency.** The client sends `Idempotency-Key`. The first request stores `key → PROCESSING`, then the result. Retries return the stored result. The key's insert must be atomic (unique constraint).

**4. External top-ups are a State machine.** Gateway calls are slow and may time out with an unknown outcome. Mark the transaction `PROCESSING`, credit the wallet only on a confirmed webhook or status poll, and reconcile pending ones on a schedule.

**5. Reversal, never deletion.** A refund is a new transaction with opposite entries. The ledger is append-only for audit.

### Ownership, boundaries and invariants

**Central design question:** An append-only balanced ledger is the authority; a wallet balance is a projection of that ledger.

Wallet holds owner and currency. Transfer identifies source, destination, amount and idempotency key. LedgerTransaction owns balanced Debit/Credit entries. PaymentGateway handles external funding; ReconciliationService resolves uncertain external outcomes. Money stores currency plus integral minor units.

**Correctness rule:** Each posted transfer balances to zero per currency, and a wallet cannot go negative unless overdraft is explicitly permitted. A repeated operation key with the same payload returns the same transfer; a different payload is rejected.

```text
wallet(id,currency,balance_minor,version); transfer(id,request_key,payload_hash,status); entry(transfer_id,wallet_id,delta_minor)
```

### End-to-end execution trace

Authenticate and authorize; validate positive amount and currency; lock wallet rows in stable ID order; check balance; insert transfer and balanced entries atomically; update cached balances; commit; publish events using an outbox. External funding follows a separate pending/settled protocol.

### Concurrency and recovery walkthrough

Concurrent debits both observe enough funds. A database conditional debit or row lock serializes the balance check with the debit. An in-memory synchronized method cannot protect other service instances.

### Policy choices and extension seams

Storing just a mutable balance is quick but loses auditability. Ledger entries enable reconstruction and reconciliation. Avoid distributed transactions with a card provider; use operation identities and compensation.

### Edge cases that change the design

Timeout after bank acceptance means UNKNOWN. Reversal is a new balanced transaction, never deletion of the original. Currency conversion needs an explicit rate snapshot and balancing entries in each currency domain.

**Topic-specific cases:** Concurrent overdraft prevention; payload mismatch; self-transfer policy; arithmetic overflow; balanced reversal; provider timeout; ledger-to-balance reconciliation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through contention and corrections

Two transfers of ₹400 each compete against ₹500. Checking the balance before entering the transaction permits both. Serialize the spendable-funds decision or use a conditional debit; one must lose. Locking A then B in one transfer and B then A in another can deadlock, so establish a consistent order and a retry policy for transaction conflicts.

A correction is a reversing transaction linked to the original, never deletion of posted ledger history. For an external provider timeout, record `PENDING` or `UNKNOWN` and reconcile by provider reference. A database rollback cannot reverse a successful card charge.

## 6. Interviewer follow-ups

**Can different currencies share one arithmetic balance?** No. Model conversion with explicit amounts, currency pair, rate and rounding.

**Can the same transfer ID carry another amount?** Reject it as conflicting intent, even if the original operation succeeded.

## 7. Closing answer

I use immutable balanced ledger entries, stable transfer identities and one transactional spendable-funds decision. Corrections reverse rather than erase entries. External provider uncertainty has a pending reconciliation state because a database rollback cannot undo a captured payment.

## Problem

Design a game of tic-tac-toe. Two players, X and O, take turns placing their mark on an empty cell of a 3×3 board. Three in a row, column or diagonal wins. If the board fills up with no winner, it is a draw.

This is often the first LLD question in an interview. The board is tiny on purpose: the interviewer is watching how you split responsibilities, validate moves, detect a win, and extend the design.

## Requirements

- Two players take turns; X moves first.
- Reject a move that is outside the board, on an occupied cell, by the wrong player, or after the game is over. A rejected move changes nothing.
- Detect a win or a draw after every move.
- Keep the rules independent of how moves arrive (console, web, bot).

## Step 1: Clarify the requirements

**Candidate:** Is the board always 3×3?

A record with a name and a symbol. A human and a bot behave the same way here – they just choose moves differently (see Step 6).

### Board

An N×N grid of symbols. It can say whether a cell is inside and empty, place a symbol, and check whether a move completed a line.

### Game

## Step 4: Write the code

### Enums and Player

```java
enum Symbol { X, O, EMPTY }
enum GameStatus { IN_PROGRESS, X_WON, O_WON, DRAW }
enum Decision { ACCEPTED, GAME_OVER, WRONG_TURN, OUT_OF_BOUNDS, OCCUPIED }

record Player(String name, Symbol symbol) {}
```

### Board

```java
class Board {
    private final int n;
    private final Symbol[][] cells;

    Board(int n) {
        this.n = n;
        cells = new Symbol[n][n];
        for (Symbol[] row : cells) Arrays.fill(row, Symbol.EMPTY);
    }

    int size()                         { return n; }
    boolean isInside(int r, int c)     { return r >= 0 && r < n && c >= 0 && c < n; }
    boolean isEmpty(int r, int c)      { return cells[r][c] == Symbol.EMPTY; }
    void place(int r, int c, Symbol s) { cells[r][c] = s; }

    /** A new win must pass through the cell just played: check only its lines. */
    boolean winsThrough(int r, int c, Symbol s) {
        return line(r, 0, 0, 1, s)                              // row r
            || line(0, c, 1, 0, s)                              // column c
            || (r == c && line(0, 0, 1, 1, s))                  // main diagonal
            || (r + c == n - 1 && line(0, n - 1, 1, -1, s));    // other diagonal
    }

    private boolean line(int r, int c, int dr, int dc, Symbol s) {
        for (int i = 0; i < n; i++) {
            if (cells[r + i * dr][c + i * dc] != s) return false;
        }
        return true;
    }

    String row(int r) {
        StringBuilder sb = new StringBuilder();
        for (Symbol s : cells[r]) sb.append(s == Symbol.EMPTY ? '.' : s.name().charAt(0));
        return sb.toString();
    }
}
```

Before this move there was no winner, so a new winning line **must pass through the cell just played**. Checking only that row, that column and the diagonals is O(N) – instead of scanning every line.

### Game

```java
class Game {
    private final Board board;
    private final Player[] players;
    private int current = 0;                       // index of the player to move; X first
    private int moves = 0;
    private GameStatus status = GameStatus.IN_PROGRESS;

    Game(int size, Player x, Player o) {
        board = new Board(size);
        players = new Player[] { x, o };
    }

    synchronized Decision makeMove(Player player, int row, int col) {
        // 1. Validate everything first. A rejected move changes nothing.
        if (status != GameStatus.IN_PROGRESS) return Decision.GAME_OVER;
        if (player != players[current])       return Decision.WRONG_TURN;
        if (!board.isInside(row, col))        return Decision.OUT_OF_BOUNDS;
        if (!board.isEmpty(row, col))         return Decision.OCCUPIED;

        // 2. Change state.
        Symbol s = player.symbol();
        board.place(row, col, s);
        moves++;

        // 3. Decide the result: win before draw, then switch turns.
        if (board.winsThrough(row, col, s)) {
            status = (s == Symbol.X) ? GameStatus.X_WON : GameStatus.O_WON;
        } else if (moves == board.size() * board.size()) {
            status = GameStatus.DRAW;
        } else {
            current = 1 - current;
        }
        return Decision.ACCEPTED;
    }

    GameStatus getStatus() { return status; }
    Board getBoard()       { return board; }
}
```

Three things worth saying out loud:

- **All checks come before `place`.** A rejected move leaves the board, turn and status untouched.
- **Win is checked before draw.** If the ninth move completes a line, it is a win.
- **`synchronized`** makes check-and-place one step, so two quick clicks cannot both be accepted.

> **⚠️ Common mistake**
> Checking for a draw before checking for a win. A full board can still contain a winning line made by the last move.

Try it with Asha (X) and Bilal (O):

| Move | Result |
| --- | --- |
| Asha (0,0) | Accepted |
| Bilal (0,0) | OCCUPIED – Bilal tries again |
| Asha (1,1) | WRONG_TURN – it is still Bilal's turn |
| Bilal (3,0) | OUT_OF_BOUNDS |
| Bilal (1,0), Asha (0,1), Bilal (1,1) | Accepted |
| Asha (0,2) | Accepted – row 0 complete, X_WON |
| Bilal (2,2) | GAME_OVER |

```text
      col 0  1  2
row 0     X  X  X
row 1     O  O  .
```

## Step 5: An O(1) win check for big boards

Interviewers love this follow-up. Keep a counter for every row, every column and both diagonals. X adds +1, O adds −1. A line is complete when its counter reaches **+N or −N** – a mixed line can never get there, because X and O cancel out.

```java
/** O(1) win check for N x N: X adds +1, O adds -1 to its row, column and diagonals. */
class WinCounters {
    private final int n;
    private final int[] rows, cols;
    private int diag, antiDiag;

    WinCounters(int n) { this.n = n; rows = new int[n]; cols = new int[n]; }

    boolean record(int r, int c, Symbol s) {
        int v = (s == Symbol.X) ? 1 : -1;
        rows[r] += v;
        cols[c] += v;
        if (r == c) diag += v;
        if (r + c == n - 1) antiDiag += v;
        return Math.abs(rows[r]) == n || Math.abs(cols[c]) == n
            || Math.abs(diag) == n || Math.abs(antiDiag) == n;
    }
}
```

This uses O(N) extra memory and checks a win in O(1). On a 3×3 board the line check is already instant, so mention the counters as the scalable version.

> **🎯 In the interview**
> For "K in a row" on a big board (like Gomoku), counters no longer work – they only detect full lines. From the last move, count matching marks in both directions along each of the four axes.

## Step 6: Deep dives

### A computer player

Give `Player` a `MoveStrategy` interface with `chooseMove(board, symbol)`. A human strategy reads input; a bot picks a random empty cell or uses **minimax** (try every move, assume the opponent replies with their best move, pick the best outcome). The bot still calls `game.makeMove`, so it obeys exactly the same rules. This is the **Strategy pattern**.

### Undo

Keep a stack of accepted moves. Undo pops the last one, empties the cell, decrements `moves`, gives the turn back and sets the status to IN_PROGRESS. Each move as an object is the **Command pattern**.

### N×N boards

Already supported: `Game` takes the size, and the win and draw checks use `n`, never a hard-coded 3.

## Interviewer follow-ups

**Why not let the UI read and change the board array directly?** It could overwrite a cell or "unwin" a game without validation. The UI only calls `makeMove` and reads a copy for display.

**What if two clicks arrive at once?** `makeMove` is synchronized, and the second click by the same player is rejected as WRONG_TURN because the turn has already switched.

**Why return a `Decision` instead of throwing exceptions?** Invalid moves are normal in a game. A result value lets the UI show a friendly message without exception handling.

**Do we need `HumanPlayer` and `BotPlayer` subclasses?** No – only how they choose a move differs. A `MoveStrategy` field keeps one `Player` class.

## Wrap up

We kept the rules in `Game`, the cells in a private `Board`, and made the win check fast by looking only at the lines through the last move.

> **📝 Key takeaways**
> - Validate everything first, then change state, then decide the result.
> - Check only the row, column and diagonals through the last move – O(N).
> - Per-line counters make the win check O(1) for N×N.
> - Players get moves from a `MoveStrategy`, so bots plug in without changing the rules.

## Closing answer

"I use a `Game` that owns a private `Board`, two `Player`s, the current turn and the status. `makeMove` validates game-over, turn, bounds and occupancy before changing anything, then places the mark, checks for a win through the last cell before checking for a draw, and only then switches turns. Win detection is O(N) by checking just the row, column and diagonals through the last move, or O(1) with per-line counters for big boards. Players get their moves from a `MoveStrategy`, so a minimax bot plugs in without changing the rules, and undo can be added with a stack of move commands."
