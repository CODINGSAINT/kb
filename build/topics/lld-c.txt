## Problem

Design the shopping cart and pricing engine of an e-commerce site: add or remove items, change quantities, apply promotions (coupons, BOGO, category discounts, cart-value thresholds) and compute the final price, then check out. The real test is a **pricing rules engine** that's extensible and gives predictable results when multiple promotions apply.

## Requirements

**Functional**
- Add, update and remove items. The cart persists for logged-in users and merges with the guest cart on login.
- Promotions: percentage or flat off on an item or category, buy X get Y, cart-level "₹200 off above ₹1500", coupon codes, free shipping.
- Show a price breakdown: subtotal, each discount line, tax, shipping, total.
- At checkout, validate stock and prices again, then create an order.

**Non-functional**
- Totals are deterministic and reproducible: money in minor units (paise), never floating point.
- New promotion types plug in without changing the pricing engine (open/closed).
- Correct when the same cart is edited from two devices at once.
- Checkout re-validation is fast (well under 200 ms), as it sits on the purchase path.

## 1. Scope and chosen solution

I support variant quantities, coupons, price quotation and conversion to an order. `Cart` owns selection; `PricingService` calculates a bounded quote; Checkout coordinates stock and order creation. Product ID alone is insufficient when size/colour variants have distinct inventory.

## 2. Checkout contract and algorithm

```text
setQuantity(cartId,expectedVersion,variantId,quantity) -> CartVersion
quote(cartId,cartVersion,address) -> Quote(id,total,lines,expiry)
checkout(checkoutId,quoteId,customer) -> ExistingOrder | NewOrder | Requote
```

An edit validates positive bounded quantities and advances the version. Quote snapshots item, discount, shipping, currency and tax-policy inputs. Checkout locks the quote/cart boundary, rejects expired or mismatched versions, and records one accepted intent. Inventory reservation follows its authoritative conditional contract; a failed reservation resolves payment/order state explicitly. Two ₹950 shirts with 10% discount give ₹1,710; ₹50 shipping gives ₹1,760 before stated taxes. A retry returns the same order; another payload under the same checkout identity conflicts. Catalogue repricing does not silently change the accepted quote.

A **cart line** represents a product variant and quantity. A **price quote** includes prices, discounts, tax assumptions and expiry. An **order** freezes accepted commercial facts. Inventory is a separate authority: adding something to a cart does not necessarily reserve it.

### Key abstractions

```java

    int priority();                      // item-level before cart-level
    boolean isApplicable(PricingContext ctx);
    void apply(PricingContext ctx);      // adds DiscountLine(s) to ctx

```

### Design decisions & trade-offs

**1. Rules are Strategies in an ordered pipeline.** Apply item-level rules first, then category, then cart-level, then shipping. Order matters: 10% off then ₹200 off is not the same as ₹200 off then 10% off. Make the order explicit with `priority()` rather than relying on insertion order.

**2. Stacking and exclusivity.** Mark rules `stackable` or put them in an exclusive group. For exclusive groups, either pick the best discount for the customer (evaluate each and keep the max) or the first by priority. State which business rule you're assuming.

**3. Never trust cached prices.** The cart stores product IDs and quantities. Price is computed at view time and **recomputed at checkout**. If the price changed, show it before payment.

**4. Eligibility as Specification.** `MinCartValue(1500).and(CategoryIn("shoes")).and(FirstOrder())` composes conditions without one huge `if`.

**5. Explainable output.** Return a `PriceBreakdown` with a line per discount. That's needed for the UI, for refunds on partial returns (allocate discounts per line), and for debugging.

**6. Inventory at checkout, not at add-to-cart.** Reserving on add-to-cart lets carts hog stock. Reserve with a TTL during checkout.

### Ownership, boundaries and invariants

**Central design question:** A cart is editable intent; checkout is a validated price-and-inventory commitment.

Cart owns CartLines keyed by product and selected options. ProductCatalogue and InventoryPort are external views. PricingEngine applies an ordered set of rules and returns a Quote with expiry. CheckoutService creates Order snapshots; CouponPolicy does not mutate inventory.

**Correctness rule:** Line quantities are positive and bounded; totals use one currency; the same checkout request cannot create two orders. A stale cart price cannot establish the payable amount.

```text

```

### End-to-end execution trace

Add or merge a line; validate option compatibility; calculate an explanatory quote; at checkout refresh price and inventory; reserve stock; obtain payment authorization; create an immutable order with line snapshots; mark the cart checked out or expose a recoverable pending state.

### Concurrency and recovery walkthrough

Two browser tabs edit the same cart version, or both submit checkout. Optimistic cart versioning prevents lost updates; a durable checkout idempotency key prevents duplicate orders.

### Policy choices and extension seams

A pricing chain is useful when rule ordering is explicit: item promotions, order discount, tax and delivery may not commute. Keeping price as a single stored mutable cart total creates unexplained drift.

### Edge cases that change the design

Coupons may have per-user limits requiring atomic redemption. Product deletion leaves an unavailable line rather than silently dropping intent. Refunds use order snapshots, not current catalogue prices.

**Topic-specific cases:** Concurrent tab update; empty checkout; coupon cap; price change; inventory shortage; duplicate order prevention; currency validation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through concurrent changes

Two browser tabs edit cart version 7: one changes quantity, another removes the line. Require an expected cart version or use clearly defined merge operations. A stale “set quantity to 3” must not silently resurrect an intentionally removed item.

Two checkout retries with identity X9 should return the same order. A different cart or accepted quote under the same identity is a conflict. If stock reservation later fails, record order failure and resolve payment rather than deleting history and losing the explanation.

Do not use product ID alone when size/colour variants have separate stock. Bound quantity, distinct lines and coupon applications so pricing complexity cannot grow without limit.

## 6. Interviewer follow-ups

**Does removing a cart line cancel a submitted order?** No. They are separate lifecycles.

**Where does the accepted address belong?** In the order snapshot; subsequent profile edits should not mutate it.

## 7. Closing answer

I treat the cart as mutable intent and the accepted quote as the commercial contract. Versioned edits prevent stale tabs from silently overwriting selections, while idempotent checkout creates one order with frozen prices and address. Adding to a cart does not claim stock.

## Problem

Design a notification system (as an in-process library or service) that sends messages over email, SMS, push and in-app channels, respects user preferences, renders templates, retries failures and is easy to extend with new channels. It's an extensibility problem: **Strategy** per channel, **Factory** to create senders, and **Observer** to decouple producers from delivery.

## Requirements

**Functional**
- `send(userId, eventType, payload)`. The system picks channels from user preferences and event priority.
- Template per event and channel, with variables and localisation.
- Retry with backoff. Fallback (push fails, so use SMS for critical events).
- Rate-limit per user. Respect quiet hours. Deduplicate.

**Non-functional**
- High throughput (millions per day) and asynchronous: `send()` never blocks the caller.
- At-least-once delivery with idempotency keys, so retries don't produce duplicate messages.
- Adding a channel (e.g. WhatsApp) needs no change to existing senders.
- Observable: delivery status can be tracked per message and channel.

## 1. Scope and chosen solution

I deliver email, SMS and push for typed business events. NotificationIntent freezes template version, recipient scope, urgency and expiry. `DeliveryChannel` is an interface implemented per provider/channel; rendering and route policy remain separate so adding a channel does not modify domain events.

## 2. Dispatch and retry algorithm

```text
notify(eventId,recipient,templateVersion,parameters) -> notificationId
deliver(notificationId) -> Accepted | RetryScheduled | PermanentFailure | Unknown
Attempt: attemptId, notificationId, providerRef, outcome, nextAttemptAt
```

I deduplicate the intent, validate consent/expiry, render bounded channel content and record the attempt before the provider call. Definitive invalid addresses terminate; throttling schedules bounded backoff; timeout-after-acceptance remains uncertain and uses provider query/idempotency where available. Expired OTPs are not replayed later. At 200 SMS/minute against a 100/minute provider quota, backlog grows 100/minute, so channel admission must honor quota rather than adding unlimited threads. ### Design decisions & trade-offs

**1. Open/closed via registry.** Adding WhatsApp is one class implementing `NotificationChannel`, registered with the factory. No `switch` to edit. Vendor adapters (SES vs. SendGrid) sit behind each channel as a second Strategy level.

**2. Pre-send filters as a chain.** Dedup, rate limit, quiet hours and preference checks are independent rules. A chain lets you reorder them and add new ones, and each filter can short-circuit (drop or delay).

**3. Async dispatch.** Producers call `send`, which enqueues work (`BlockingQueue`, or Kafka in HLD). A worker pool delivers. Producers never block on a slow SMS gateway.

**4. Retries and idempotency.** Keep a notification ID through retries so vendors or your dedup can drop duplicates. Classify failures: transient (timeout, 5xx) gets retried; permanent (invalid number) fails fast.

**5. Priority.** OTPs and security alerts skip quiet hours and use a separate high-priority queue, so a marketing blast can't delay them.

### Ownership, boundaries and invariants

**Central design question:** Creating a notification and delivering it through an unreliable provider are different responsibilities.

NotificationRequest contains recipient, template version, channel preference and deduplication key. Renderer produces channel-specific payloads; ChannelAdapter calls email/SMS/push providers. DeliveryAttempt records outcome and retry schedule; PreferencePolicy decides consent and quiet hours.

**Correctness rule:** A request identity maps to one logical notification. Retries may create several provider attempts but must not be misreported as several user intents. A successful enqueue is not confirmed delivery.

### End-to-end execution trace

### Concurrency and recovery walkthrough

A timeout occurs after the provider accepts a message. Query using provider reference or retry with its idempotency key; when unsupported, document possible duplicate delivery. Local deduplication alone cannot undo an already sent SMS.

### Policy choices and extension seams

Factory selects an adapter; Strategy expresses channel fallback. Decorators can add metrics and retries only if retry policy understands idempotency. Avoid a generic retry decorator around every side effect.

### Edge cases that change the design

Unsubscribe takes precedence over queued marketing work under a documented cut-off policy. Missing template variables are permanent validation failures. Quiet hours depend on the recipient zone, not server local time.

**Topic-specific cases:** Duplicate intent; missing variables; opt-out; retry budget; permanent provider error; out-of-order delivery callback; timezone quiet hours.

### Work through policy choices

I separate notification intent from channel-specific attempts and delivery evidence. Strategy chooses the channel, adapters integrate providers, and stable identities make retries inspectable. Accepted, delivered and read are separate outcomes; consent and expiry are checked before sending.

## Problem

Design a rate limiter class in Java (the LLD version, inside one JVM): `boolean allow(String key)` limits each user or API key to N requests per time window. You must implement the algorithms correctly, make them **thread-safe**, and make the algorithm swappable (**Strategy**).

## Requirements

**Functional**
- Per-key limits (user ID, IP, API key), with different limits per tier or endpoint.
- Algorithms: fixed window, sliding window log, sliding window counter, token bucket, leaky bucket.
- Return allowed or denied, plus metadata (remaining requests, retry-after).

**Non-functional**
- O(1) per call where possible, safe under many concurrent threads, and bounded memory (evict idle keys).

## 1. Scope and chosen solution

I enforce capacity 5 and refill 2 permits/second per authenticated caller in one JVM. `RateLimiter` resolves keys, `TokenBucket` owns state, and an injected monotonic clock makes arithmetic testable. Costs are positive and no larger than capacity.

## 2. Atomic decision

```text
synchronized tryAcquire(cost,nowNanos):
  elapsed = max(0,nowNanos-lastNanos)
  tokens = min(capacity,tokens + elapsed/1e9*rate)
  lastNanos = max(lastNanos,nowNanos)
  if tokens >= cost: tokens -= cost; return ALLOW
  return DENY with retryAfterNanos = ceil((cost-tokens)/rate * 1e9)
```

After depletion, 1.25 seconds refills 2.5 permits: two unit requests pass, then the next waits 0.25 seconds before HTTP-header rounding. I use fine-grained retry durations internally; a whole-second header rounds upward. Registry lookup is thread-safe but bucket synchronization covers the multi-field calculation. Idle eviction occurs only after a period long enough to restore a full bucket under the policy; premature deletion would grant another burst. Twenty-four simultaneous calls with frozen time admit exactly five. Multiple servers do not share this lock, so I do not claim global enforcement from this implementation.

I start with one JVM and one caller. Then add multiple callers and finally multiple servers. The algorithm's arithmetic and its deployment authority are separate lessons; a correct local bucket does not automatically become a global quota.

### Worked calculation and implementation

With capacity 5, rate 2/s and an empty bucket at t=0, t=1.25 has 2.5 tokens. Two unit-cost requests succeed, leaving 0.5. The next needs another 0.5 token, so its earliest retry is 0.25 seconds later. Do not round retry delay downward.

```text
elapsed = max(0, nowNanos - previousNanos)
tokens = min(capacity, tokens + elapsedSeconds * rate)
if tokens >= requestCost: tokens -= requestCost; ALLOW
else: DENY, retryAfter = (requestCost - tokens) / rate
```

Handle nonpositive capacity/rate and cost greater than capacity explicitly. Floating-point arithmetic can be acceptable for an educational bucket with bounded values; fixed-point arithmetic is an alternative when exact quotas and reproducibility require it.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|

| `RateLimitAlgorithm` (Strategy) | `allow()` on one key's state |

| `RateLimitConfig` | capacity, refill rate or window, per tier |
| `LimiterRegistry` | `ConcurrentHashMap<String, RateLimitAlgorithm>` plus idle eviction |

### Design decisions & trade-offs

| Algorithm | Pros | Cons |
|---|---|---|
| Fixed window | Tiny state, simple | Up to 2× burst at window edges |
| Sliding log | Exact | O(N) memory per key |
| Sliding counter | ~Exact, O(1) memory (weighted previous window) | Approximation |
| Token bucket | Allows controlled bursts, smooth refill | Two params to tune |
| Leaky bucket | Smooths output rate | Queues add latency |

**1. Lazy refill.** Never use a background thread to add tokens. Compute the refill from elapsed time on each call. That's O(1) and scales to millions of keys.

**2. Thread safety.** `synchronized` per bucket means contention only on the same key, which is usually fine. For a lock-free version, pack state into an `AtomicLong` or use `AtomicReference<State>` with a CAS loop. `computeIfAbsent` on the registry avoids creating duplicate buckets.

**3. Memory.** Evict keys idle longer than the window (a Caffeine cache with `expireAfterAccess`, or a periodic sweep).

**4. Testability.** Inject a `Clock`. Never call `System.currentTimeMillis()` inside the algorithm.

**5. Distributed version (preview of HLD #2).** State moves to Redis, and the logic runs atomically as a Lua script.

### Ownership, boundaries and invariants

**Central design question:** Time measurement and atomic token accounting define a limiter more than the chosen class pattern.

RateLimitKey identifies principal, route and policy version. RatePolicy contains capacity and refill rate. TokenBucket owns tokens and last refill time. Clock is monotonic for elapsed time. LimiterRegistry supplies bounded per-key state; Decision includes allowed, remaining and retry delay.

**Correctness rule:** At a fixed instant, accepted requests never spend more tokens than available. Refilling cannot exceed capacity, and elapsed-time calculations cannot create tokens from a backward wall clock jump.

```text
key(principal,route,policy_version); bucket(tokens,last_refill_nanos); policy(capacity,rate_per_second)
```

### End-to-end execution trace

Resolve policy; locate the bucket; acquire its synchronization boundary; calculate elapsed monotonic time; refill with a cap; consume if enough; return a retry delay based on the deficit; release the lock before request processing.

### Concurrency and recovery walkthrough

One hundred threads request the final token simultaneously. Refill and consume must be one critical section; a thread-safe map does not make a read-modify-write bucket sequence atomic.

### Policy choices and extension seams

Token bucket permits bounded bursts; leaky bucket smooths output; fixed windows permit boundary bursts; sliding logs offer exact windows at higher memory cost. Single-JVM correctness does not imply global quotas across replicas.

### Edge cases that change the design

Idle-key eviction can reset quota if implemented carelessly. Fractional refill needs numeric care and overflow-safe elapsed handling. Costs must be positive; reject configuration with zero refill when retry calculation divides by rate.

**Topic-specific cases:** Initial burst cap; concurrent last-token race; fractional refill; clock behavior; bounded key eviction; exact retry-after calculation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through deployment boundaries

Three servers each allowing five immediate requests can collectively allow fifteen. For a global five-request burst, use a shared atomic decision store, route each key to one owner, or explicitly allocate sub-budgets. The latter can underuse quota and needs reassignment rules.

Use monotonic elapsed time for a local bucket; wall-clock corrections must not mint tokens. Evicting idle callers is safe only when the recreated state matches the policy. Deleting an exhausted bucket and recreating it full immediately grants another burst.

## 6. Interviewer follow-ups

**Does a thread-safe map make the whole bucket algorithm atomic?** No. Coordinate state calculation and consumption for each key.

**Does a denied request consume a token?** Define it; a common admission policy consumes only allowed work.

## 7. Closing answer

I choose a per-key token bucket with atomic refill-and-consume, monotonic time and explicit retry delay. The local implementation serializes one bucket without blocking unrelated keys. A global quota needs one shared decision authority or consciously allocated local sub-budgets.

### Worked calculation and implementation

If A has 50,000 paise and transfers 20,000 to B, A ends with 30,000 and B increases by 20,000. The signed entry sum for the internal transfer is zero. Fees require explicit entries to a fee account; otherwise conservation appears to break.

Transfer(id, fromWallet, toWallet, currency, amountMinor, payloadHash)

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Wallet` | id, user, `balance` (derived or cached), status, version |
| `LedgerEntry` | Immutable: txnId, walletId, `DEBIT/CREDIT`, amount, balanceAfter |
| `Transfer` | id, type, amount, from, to, `TransferState`, idempotencyKey |
| `TransferState` | `POSTED → REVERSED`; external funding intents separately track pending/unknown results |
| `PaymentInstrument` (Strategy) | `Card`, `UPI`, `NetBanking` for top-ups |
| `IdempotencyStore` | key → result (first result wins) |
| `LimitPolicy` | Chain of checks: KYC tier, daily cap, velocity |

### Design decisions & trade-offs

**1. Double-entry ledger as the source of truth.** Each transfer writes two entries (debit A, credit B) that sum to zero, in one transaction. A balance is the sum of entries. Cache it on the wallet row for speed, but you can always rebuild and reconcile it.

**2. Atomic transfer without deadlocks.**
```java
void transfer(Wallet a, Wallet b, Money amt) {
    Wallet first = a.id().compareTo(b.id()) < 0 ? a : b, second = first == a ? b : a;
    synchronized (first) { synchronized (second) {
        if (a.balance().lt(amt)) throw new InsufficientFunds();
        a.debit(amt); b.credit(amt); ledger.append(/* two entries */);
    }}
}
```
Lock in a global order (by ID) to avoid A→B / B→A deadlock. In a DB: `SELECT … FOR UPDATE` in ID order, or a conditional `UPDATE wallet SET balance = balance - :x WHERE id=:a AND balance >= :x`.

**3. Idempotency.** The client sends `Idempotency-Key`. The first request stores `key → PROCESSING`, then the result. Retries return the stored result. The key's insert must be atomic (unique constraint).

**4. External top-ups are a State machine.** Gateway calls are slow and may time out with an unknown outcome. Mark the transaction `PROCESSING`, credit the wallet only on a confirmed webhook or status poll, and reconcile pending ones on a schedule.

**5. Reversal, never deletion.** A refund is a new transaction with opposite entries. The ledger is append-only for audit.

### Ownership, boundaries and invariants

**Central design question:** An append-only balanced ledger is the authority; a wallet balance is a projection of that ledger.

Wallet holds owner and currency. Transfer identifies source, destination, amount and idempotency key. LedgerTransaction owns balanced Debit/Credit entries. PaymentGateway handles external funding; ReconciliationService resolves uncertain external outcomes. Money stores currency plus integral minor units.

**Correctness rule:** Each posted transfer balances to zero per currency, and a wallet cannot go negative unless overdraft is explicitly permitted. A repeated operation key with the same payload returns the same transfer; a different payload is rejected.

```text
wallet(id,currency,balance_minor,version); transfer(id,request_key,payload_hash,status); entry(transfer_id,wallet_id,delta_minor)
```

### End-to-end execution trace

Authenticate and authorize; validate positive amount and currency; lock wallet rows in stable ID order; check balance; insert transfer and balanced entries atomically; update cached balances; commit; publish events using an outbox. External funding follows a separate pending/settled protocol.

### Concurrency and recovery walkthrough

Concurrent debits both observe enough funds. A database conditional debit or row lock serializes the balance check with the debit. An in-memory synchronized method cannot protect other service instances.

### Policy choices and extension seams

Storing just a mutable balance is quick but loses auditability. Ledger entries enable reconstruction and reconciliation. Avoid distributed transactions with a card provider; use operation identities and compensation.

### Edge cases that change the design

Timeout after bank acceptance means UNKNOWN. Reversal is a new balanced transaction, never deletion of the original. Currency conversion needs an explicit rate snapshot and balancing entries in each currency domain.

**Topic-specific cases:** Concurrent overdraft prevention; payload mismatch; self-transfer policy; arithmetic overflow; balanced reversal; provider timeout; ledger-to-balance reconciliation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through contention and corrections

Two transfers of ₹400 each compete against ₹500. Checking the balance before entering the transaction permits both. Serialize the spendable-funds decision or use a conditional debit; one must lose. Locking A then B in one transfer and B then A in another can deadlock, so establish a consistent order and a retry policy for transaction conflicts.

A correction is a reversing transaction linked to the original, never deletion of posted ledger history. For an external provider timeout, record `PENDING` or `UNKNOWN` and reconcile by provider reference. A database rollback cannot reverse a successful card charge.

## 6. Interviewer follow-ups

**Can different currencies share one arithmetic balance?** No. Model conversion with explicit amounts, currency pair, rate and rounding.

**Can the same transfer ID carry another amount?** Reject it as conflicting intent, even if the original operation succeeded.

## 7. Closing answer

I use immutable balanced ledger entries, stable transfer identities and one transactional spendable-funds decision. Corrections reverse rather than erase entries. External provider uncertainty has a pending reconciliation state because a database rollback cannot undo a captured payment.

## Problem

Design the software behind a game of tic-tac-toe. X and O take turns putting a mark in an empty square. Three matching marks in a row, column or diagonal win. If every square is filled without a winner, the game is a draw.

The board is small. The design challenge is keeping the rules consistent: an invalid click must not lose a turn, two clicks must not create two moves, and nobody may continue playing after a win.

## Requirements

I will choose these rules before writing classes:

- Two players share one 3×3 board. One controls X, the other O; X moves first.
- A player may mark one empty cell on their turn. Coordinates run from 0 to 2.
- Reject the wrong player, an occupied cell, an out-of-range coordinate or a request based on an older position. Rejection changes nothing.
- After an accepted move, check for a win, then a draw, then pass the turn.
- Return the board, result, next player and position version together. A finished game has no next player.
- Keep game rules independent of input and display. Protect a game if two threads submit moves together in one Java application.

A restart creates a new game. Matchmaking, player accounts, persistence, undo, timers and AI search are outside this first solution. They can be added when requested; none is needed to make the basic game work.

## 1. Start with one board and one rule

Suppose X chooses `(0,0)`, the top-left cell. The game places X and gives O the turn. If O clicks that same square, the game must say “occupied” and let O try again.

That gives us our most useful rule: **accepting a move changes the cell, turn and result together; rejecting a move changes none of them.**

Follow this game. The version starts at 0 and increases only when a move is accepted.

| Request | Decision | Version afterwards | What happens next |
| --- | --- | ---: | --- |
| X at `(0,0)`, version 0 | Accept | 1 | O's turn |
| O at `(0,0)`, version 1 | Occupied | 1 | Still O's turn |
| O at `(1,0)`, version 1 | Accept | 2 | X's turn |
| X at `(0,1)`, version 2 | Accept | 3 | O's turn |
| O at `(1,1)`, version 3 | Accept | 4 | X's turn |
| X at `(0,2)`, version 4 | Accept; X wins | 5 | Game finished |
| O at `(2,2)`, version 5 | Game over | 5 | Final board preserved |

```text
      col 0  1  2
row 0     X  X  X
row 1     O  O  .
row 2     .  .  .
```

O was one move away from winning, but X completed a line first. We do not offer O another turn to “catch up.”

[Open the board walkthrough](learning-labs/tictactoe.html) to step through this game, a draw and a win on the ninth move, or play freely. The guided positions are exported from the Java implementation below. Every step also has a text transcript.

## 2. Give each object a clear responsibility

| Type | Responsibility | What it must not do |
| --- | --- | --- |
| `Game` | Own one board, the next player, result and version; accept or reject moves. | Let callers update these facts separately. |
| `Board` | Store nine cells and inspect lines through the latest move. | Read keyboard input or decide whose turn it is. |
| `Move` | Carry player mark, row, column and expected version. | Change the board itself. |
| `Snapshot` | Return a detached, unmodifiable copy of the position. | Expose the game's mutable array. |
| `MoveResult` | Pair an acceptance/rejection decision with the current snapshot. | Hide a changed board behind an old turn or result. |

`Mark` has `EMPTY`, `X` and `O`. Only X and O may submit moves. `Status` has `IN_PROGRESS`, `X_WON`, `O_WON` and `DRAW`. In a finished snapshot, `nextPlayer` is `EMPTY`, meaning nobody may move.

The input adapter is the console, browser or bot that sends a `Move`. It can ask the game for a snapshot but cannot obtain its private `Board`.

[![A UI or bot submits a versioned Move to Game. Game owns its private Board and returns an immutable Snapshot for display.](designs/lld-16.svg)](designs/lld-16.svg)

There is deliberately no `HumanPlayer extends Player` hierarchy. In this scope, players supply a mark and a coordinate; neither has different game behavior. There is also one fixed winning rule, so a `WinningStrategy` interface would add a name without adding a useful choice.

The design must preserve these **invariants**, meaning facts that remain true after every request:

- Each cell is empty or contains exactly one mark. An accepted move fills exactly one previously empty cell.
- X has either the same number of marks as O, or one more.
- While playing, the next player agrees with those counts. After finishing, there is no next player.
- `version` equals the number of accepted moves, from 0 to 9. An invalid request cannot increase it.
- A win or draw is permanent for this `Game` object.
- Reading or editing a returned value cannot change the live game.

## 3. Accept a move at one boundary

The public operation is `play(new Move(player, row, col, expectedVersion))`. For example, `new Move(Mark.O, 1, 0, 1)` means “O wants row 1, column 0, based on position 1.”

Under the game's lock, the operation follows this order:

1. Reject a finished game.
2. Require X or O as the player.
3. Require the request's version to match the current position.
4. Require the player whose turn it is.
5. Check coordinates before accessing the array, then require an empty cell.
6. Place one mark and increase the version.
7. Record a win if the move completes a line; otherwise record a draw if the board is full; otherwise switch players.
8. Return the decision and a snapshot of that state.

![A request passes game-state, player, version, turn and cell checks before placement. After placement, win is checked before draw and turn change.](learning-figures/tictactoe-flow.svg)

All checks happen before the first mutation. Rejections use a `Decision` value, so normal mistakes can be shown to a player without throwing an exception. Passing a null `Move` is a programming error and fails fast with `NullPointerException`; a request containing a null or `EMPTY` player receives `INVALID_PLAYER`.

The ordering also makes errors predictable. A request with an old version and an occupied cell receives `STALE_VERSION`: the caller should first show the current position. Any request against a finished game receives `GAME_OVER`.

### Why both a lock and a version?

Imagine two X clicks arrive together, both based on version 0. The first gets the lock, places its mark and changes the version to 1. The second obtains the lock afterwards and finds that version 0 is stale. Only one move is accepted.

The lock makes the whole check-and-change sequence indivisible to other callers. A lock around `Board.place` alone would be too narrow: two requests could both pass the earlier turn check.

The version also catches a delayed click. Suppose X's first click succeeded, O then moved, and an old X request finally arrived. Checking only “is it X's turn?” could wrongly accept that old request as X's new move. Its old version reveals the mistake. An invalid occupied-cell request, by contrast, keeps the version unchanged, so O can retry another square against the same position.

![Two X requests expect version 0. One updates the game to version 1 under the Game lock; the other is rejected as stale, leaving one X and O to move.](learning-figures/tictactoe-failure.svg)

Java's [`synchronized` instance method](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.3.6) locks that particular object. Both `play` and `snapshot` use it, so readers cannot see placement halfway through turn and result updates. Separate `Game` objects have separate locks; unrelated games can progress independently.

There is no network or user input inside the lock. Nine cells make this operation short. These locks protect callers sharing the same object in one process; the multi-server follow-up below states the additional boundary needed there.

## 4. Decide whether the latest move won

Before the move, the game had no winner; otherwise it would have rejected the request. Therefore any new winning line must pass through the newly placed mark.

For a move at `(row,col)`, inspect:

- Its entire row and column.
- The main diagonal only if `row == col`.
- The other diagonal only if `row + col == 2`.

For X's winning move at `(0,2)` in our example, row 0 is `X X X`. Column 2 and the other diagonal are also relevant, but one complete line is enough. The main diagonal does not contain `(0,2)` and cannot have become newly winning.

The helper `line(startRow,startCol,rowStep,colStep,player)` walks three cells. A row uses steps `(0,1)`; a column `(1,0)`; diagonals `(1,1)` and `(1,-1)`. If any cell differs from the player, that line is not a win.

### A full board can still be a win

These two positions differ by where the middle-row and bottom-middle marks went. Both contain nine marks.

```text
DRAW                X_WON
X O X               X O X
X O O               O X O
O X X               O X X
```

For the draw, the accepted coordinates are `(0,0), (0,1), (0,2), (1,1), (1,0), (1,2), (2,1), (2,0), (2,2)`, alternating X and O. None of the eight lines has three matching marks.

For the win, they are `(0,0), (0,1), (0,2), (1,0), (1,1), (1,2), (2,1), (2,0), (2,2)`. The ninth move at `(2,2)` completes X's main diagonal. That is why the implementation checks **win before draw**. Both sequences are covered by the runnable checks and the board walkthrough.

### Cost and the counter alternative

On this fixed 3×3 board, move processing and copying nine cells are constant-sized work. If generalized to an N×N board requiring N marks in a complete line, this line checker takes O(N). The board uses O(N²) space, and returning a full copied snapshot takes O(N²) time. It would be misleading to call that whole API O(1) merely because win detection were optimized.

If the interviewer explicitly requires O(1) win detection for full-line N×N games, keep a signed sum for each row and column and for both diagonals: X adds +1; O adds −1. After validating and placing the move, update its row, column and relevant diagonals. An absolute sum of N means every cell in that line belongs to one player. Mixed or incomplete lines cannot reach that sum. This uses O(N) extra counters alongside the O(N²) board needed to reject occupied cells. For nine cells, the direct checker is easier to inspect and already cheap.

## 5. Complete Java 21 implementation

This file contains the rules, value types and private board. It uses only the JDK. `Game` is the only public route to a live board; the private `Board.place` relies on its preceding validation.

The snapshot contains a flat list in row order: index `row * 3 + col`. [`List.copyOf`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/List.html#copyOf(java.util.Collection)) creates an unmodifiable list; its elements here are immutable enum values. A record holding an exposed mutable array would not provide the same protection.

```java
package kb.tictactoe;

import java.util.Arrays;
import java.util.List;
import java.util.Objects;

/** A single-process, two-player, 3-by-3 game. No I/O or external dependencies. */
public final class TicTacToe {
    private TicTacToe() {}
    public static final int SIZE = 3;

    // BEGIN values
    public enum Mark { EMPTY, X, O }
    public enum Status { IN_PROGRESS, X_WON, O_WON, DRAW }
    public enum Decision {
        ACCEPTED, GAME_OVER, INVALID_PLAYER, STALE_VERSION,
        WRONG_TURN, OUT_OF_BOUNDS, OCCUPIED
    }

    public record Move(Mark player, int row, int col, int expectedVersion) {}

    public record Snapshot(List<Mark> cells, Mark nextPlayer,
                           Status status, int version) {
        public Snapshot {
            cells = List.copyOf(cells);
        }

        public Mark cell(int row, int col) {
            if (!inside(row, col)) throw new IllegalArgumentException("Cell outside board");
            return cells.get(row * SIZE + col);
        }
    }

    public record MoveResult(Decision decision, Snapshot snapshot) {
        public boolean accepted() { return decision == Decision.ACCEPTED; }
    }
    // END values

    // BEGIN game
    public static final class Game {
        private final Board board = new Board();
        private Mark nextPlayer = Mark.X;
        private Status status = Status.IN_PROGRESS;
        private int version;

        public synchronized Snapshot snapshot() {
            return view();
        }

        public synchronized MoveResult play(Move move) {
            Objects.requireNonNull(move, "move");
            if (status != Status.IN_PROGRESS) return result(Decision.GAME_OVER);
            if (move.player() == null || move.player() == Mark.EMPTY)
                return result(Decision.INVALID_PLAYER);
            if (move.expectedVersion() != version) return result(Decision.STALE_VERSION);
            if (move.player() != nextPlayer) return result(Decision.WRONG_TURN);
            if (!inside(move.row(), move.col())) return result(Decision.OUT_OF_BOUNDS);
            if (board.at(move.row(), move.col()) != Mark.EMPTY)
                return result(Decision.OCCUPIED);

            board.place(move.row(), move.col(), move.player());
            version++;
            if (board.winsThrough(move.row(), move.col(), move.player())) {
                status = move.player() == Mark.X ? Status.X_WON : Status.O_WON;
                nextPlayer = Mark.EMPTY;
            } else if (version == SIZE * SIZE) {
                status = Status.DRAW;
                nextPlayer = Mark.EMPTY;
            } else {
                nextPlayer = move.player() == Mark.X ? Mark.O : Mark.X;
            }
            return result(Decision.ACCEPTED);
        }

        private Snapshot view() {
            return new Snapshot(board.copyCells(), nextPlayer, status, version);
        }

        private MoveResult result(Decision decision) {
            return new MoveResult(decision, view());
        }
    }
    // END game

    // BEGIN board
    private static final class Board {
        private final Mark[] cells = new Mark[SIZE * SIZE];

        private Board() { Arrays.fill(cells, Mark.EMPTY); }

        private Mark at(int row, int col) { return cells[row * SIZE + col]; }

        private void place(int row, int col, Mark player) {
            cells[row * SIZE + col] = player;
        }

        private List<Mark> copyCells() {
            return List.copyOf(Arrays.asList(cells));
        }

        private boolean winsThrough(int row, int col, Mark player) {
            return line(row, 0, 0, 1, player)
                || line(0, col, 1, 0, player)
                || (row == col && line(0, 0, 1, 1, player))
                || (row + col == SIZE - 1 && line(0, SIZE - 1, 1, -1, player));
        }

        private boolean line(int row, int col, int dr, int dc, Mark player) {
            for (int i = 0; i < SIZE; i++) {
                if (at(row + i * dr, col + i * dc) != player) return false;
            }
            return true;
        }
    }
    // END board

    // BEGIN bounds
    private static boolean inside(int row, int col) {
        return row >= 0 && row < SIZE && col >= 0 && col < SIZE;
    }
    // END bounds
}
```

import static kb.tictactoe.TicTacToe.*;

public final class TicTacToeDemo {
    // BEGIN demo
    public static void main(String[] args) {
        Game game = new Game();
        Move[] requests = {
            new Move(Mark.X, 0, 0, 0),
            new Move(Mark.O, 0, 0, 1), // Occupied: O keeps the turn and version stays 1.

        for (Move request : requests) {
            MoveResult result = game.play(request);

                request.player(), request.row(), request.col(), request.expectedVersion(),
                result.decision(), view.version(), view.status(), view.nextPlayer());

        Snapshot view = game.snapshot();
        for (int row = 0; row < SIZE; row++) {
            for (int col = 0; col < SIZE; col++) {
                System.out.print(view.cell(row, col) == Mark.EMPTY ? ". " : view.cell(row, col) + " ");
            }
            System.out.println();
        }
    }
    // END demo
}

### Failure behavior to say aloud

| Situation | Result and recovery |
| --- | --- |
| Wrong player | `WRONG_TURN`; show whose turn it is. No state change. |
| Cell outside 0–2 | `OUT_OF_BOUNDS`; ask for a valid coordinate before array access. |
| Cell already marked | `OCCUPIED`; the same player tries another cell. |
| Old or future version | `STALE_VERSION`; show the returned current position and let the player choose again. |
| Request after a win or draw | `GAME_OVER`; keep the finished board and offer a new game. |
| Response lost after acceptance | Read the latest snapshot. Retrying the old version cannot place another mark, but it does not return the original acceptance receipt. |
| Application restarts | This in-memory example loses its games. Persist games only if restart recovery is a requirement. |

## 6. Interviewer follow-ups

**How would you add a bot?** Keep it outside `Game`: give it a snapshot and have it choose an empty coordinate for that snapshot's next player and version. A random bot chooses among empty cells; a minimax bot explores possible replies and chooses the best result. Search uses private copies, never the live board. The chosen move still passes through `play`, because the position could have changed while the bot was thinking. A `MoveStrategy` interface becomes useful when the application actually offers interchangeable bots; no special permissions are needed in `Game`.

**What changes for K-in-a-row on an N×N board?** The full-line counter trick no longer proves that K marks are adjacent. From the last move, count consecutive matching marks in both directions along horizontal, vertical and both diagonal axes. Include the placed mark once; a total of at least K wins. Stop each directional walk at a different mark, an edge or after enough marks. Make board size and K validated constructor parameters (`1 <= K <= N`), then extract a `WinRule` interface if multiple rules must coexist. The current implementation deliberately promises only fixed 3×3.

**Could you just scan all eight lines after every move?** Yes. On a 3×3 board that is also clear and fast, and is exactly how the independent test oracle works. Checking only the affected lines explains the relationship between the move and a new win, and scales to O(N) for full-line N×N play. There is no need for a complicated optimization here.

**Does the version make requests idempotent?** It prevents a stale request from making a second change. It does not remember and replay the first response. If a remote product needs an exact retry receipt, add a request ID and a saved decision keyed by that ID, and reject reuse with a different payload. Keep that record in the same transaction as the move. For our small local game, reading the current snapshot is enough after a lost response.

**What if several servers handle one game?** Two copies of a Java object have two independent locks. Choose one authoritative state for each game. For a database-backed version, read the board and version, validate and compute a new position, then conditionally update the entire position where the stored version still equals the expected version. If no row updates, return the latest position as a conflict. Commit board, turn and result together. A load balancer alone cannot provide this guarantee.

**How would undo work?** First specify who may undo and whether a finished game may reopen. Then keep accepted-move history. Under the same game lock, remove the last mark, restore the correct turn and recompute the result. Do not decrement the concurrency version: undo changes the position too, so use a separate move count and a monotonically increasing revision. Otherwise an old request could accidentally match a reused version. Undo is excluded from this implementation.

**Why not expose the board for rendering?** Rendering only needs a snapshot. Giving the caller the backing array lets it overwrite a mark, erase a winner or play O twice without calling validation. Copying nine enum values is a small cost for protecting every invariant.

## 7. Closing answer

“I would start with one `Game` that owns a private 3×3 board, turn, result and version. It validates a move before changing anything, checks the affected lines for a win before checking for a draw, and returns an immutable snapshot. One lock keeps that transition consistent, while the expected version rejects delayed clicks. Human and bot input use the same operation. I would add a configurable win rule, undo or durable shared state only when those requirements are chosen.”
