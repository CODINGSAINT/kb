## Problem

Design a distributed job scheduler – a cloud cron like AWS EventBridge Scheduler or the core of Airflow. Teams register jobs such as "every day at 2:00 send the sales report" or "in 30 minutes, cancel this unpaid order", and the system runs each one on time on a fleet of workers.

With millions of schedules, no single machine can keep them all. And when a worker or scheduler crashes, jobs must still run – but a report must not be emailed twice.

## Requirements

- Register one-off jobs ("at 21:30") and recurring jobs (cron expressions).
- Run each job close to its time (within a few seconds).
- Retry failed runs with backoff; record every run's outcome.
- Survive crashes of schedulers and workers without missing or duplicating runs.
- Scale to tens of millions of schedules.

## Step 1: Clarify the requirements

> **💡 Tip**
> Ask what "run once" means. Exactly-once execution is impossible across machines; agree on at-least-once plus idempotent jobs.

**Candidate:** How many schedules and how many runs?

**Interviewer:** 50 million schedules, about 10,000 runs per second at peak – lots at midnight.

**Candidate:** How precise must timing be?

**Interviewer:** Within a few seconds.

**Candidate:** What does a job do?

**Interviewer:** Call an HTTP endpoint or put a message on a queue.

**Candidate:** If the system is down for 5 minutes, should missed runs fire afterwards?

**Interviewer:** Yes, by default – catch up once.

**Candidate:** Can a job run twice?

**Interviewer:** Avoid it. The target may not be idempotent.

**Functional requirements**

1. Create, update, pause and delete schedules.
2. Fire each due run and deliver it to a worker.
3. Retries with backoff; run history.

**Non-functional requirements**

1. On time within seconds; no missed runs.
2. Duplicates as rare as possible, and detectable by the target.
3. Horizontally scalable; no single point of failure.

## Step 2: Estimate the scale

> **💡 Tip**
> Average rates hide the midnight spike – everyone schedules "0 0 * * *".

```text
Schedules              = 50 million
Runs per day           ≈ 200 million → ~2,300/s average
Midnight spike         ≈ 10,000/s for a minute
Run history            = 200M × 300 bytes ≈ 60 GB/day
```

What it means: finding due runs must be a cheap indexed query on "next fire time", spread across partitions; history needs a write-friendly store with retention.

## Step 3: Define the API

```http
POST /v1/schedules
{ "name": "daily-sales-report", "cron": "0 2 * * *", "timezone": "Asia/Kolkata",
  "target": { "type": "HTTP", "url": "https://reports.internal/run" },
  "retry": { "maxAttempts": 3, "backoff": "PT30S" } }
→ 201 { "scheduleId": "sch_41f", "nextFireAt": "2026-10-28T02:00:00+05:30" }

PATCH  /v1/schedules/sch_41f   { "paused": true }
GET    /v1/schedules/sch_41f/runs
```

Every run sends the target a header `Run-Id: sch_41f@2026-10-28T02:00+05:30` – the schedule plus its intended time.

> **🎯 In the interview**
> That run ID is the trick that makes duplicates harmless: the target can ignore a second delivery with the same ID.

## Step 4: Define the data model

| Table | Key fields |
| --- | --- |
| `schedule` | scheduleId, cron or runAt, timezone, target, retry policy, paused, **nextFireAt**, partition |
| `run` | runId (= scheduleId + fireTime, unique), status (QUEUED / RUNNING / SUCCEEDED / FAILED), attempt, workerId, leaseUntil |

Index: `(partition, nextFireAt)` so each dispatcher can ask "what in my partition is due now?".

> **⚖️ Design choice**
> Store schedules in a sharded SQL or Cassandra table with the `nextFireAt` index. The database is the source of truth; nothing important lives only in a scheduler's memory.

## Step 5: Draw the high-level design

[![High-level design: the schedule API stores schedules; due-time dispatchers, each owning some partitions, find runs whose time has come and put them on an execution queue; workers run them and record the outcome in the execution journal; the target checks the run ID so a repeated run has no extra effect.](designs/hld-15.svg)](designs/hld-15.svg)

**Firing a run**

1. Every second, the dispatcher for partition 7 queries schedules with `nextFireAt <= now`.
2. For each, in one transaction: insert the `run` row (`sch_41f@02:00`) and move `nextFireAt` to the next cron time.
3. It puts the run on the execution queue.
4. A worker takes it, marks it RUNNING with a lease, calls the target with the run ID, and records SUCCEEDED or FAILED.
5. On failure, the run is re-queued with backoff until `maxAttempts`.

![Animation: at 02:00 the dispatcher finds the daily sales report due, creates its run and advances the next fire time to tomorrow in one transaction, queues it, and a worker calls the report service; the worker crashes, its lease expires, and another worker retries with the same run ID, which the report service recognises.](learning-figures/hld-15-fire.gif)

## Step 6: Go deep

### Finding due jobs: the dispatch algorithm

**Option 1: One scheduler scans everything.**

- Good: simple.
- Problem: a single point of failure and a bottleneck at midnight.

**Option 2: Every scheduler scans everything.**

- Good: no single point of failure.
- Problem: every run fires several times.

**Option 3: Partition schedules; each partition has one owner at a time.**

- Good: work spreads across dispatchers; each schedule has one dispatcher.
- Problem: needs leader election per partition (ZooKeeper, etcd or database leases).

> **⚖️ Design choice**
> Option 3. Split schedules into, say, 1,024 partitions. Dispatchers take leases on partitions; if one dies, its leases expire and another dispatcher takes over. A time-ordered index per partition makes "what is due?" cheap.

### Not firing twice

Even with one owner per partition, a dispatcher might pause (garbage collection) while its lease expires and a new owner fires the same run. Two defences:

- The `run` table's unique `runId = scheduleId + fireTime`: a second insert fails, so the run is created once.
- **Fencing tokens:** each lease has an increasing number; writes carrying an old token are rejected.

[![Dispatcher failover: dispatcher A owns partition 7 with lease token 41, pauses and loses the lease; dispatcher B takes over with token 42 and fires the due run; when A wakes, its insert with token 41 is rejected and the unique run ID prevents a second run.](learning-figures/hld-15-fence.svg)](learning-figures/hld-15-fence.svg)

### Workers crash mid-run

A RUNNING run has `leaseUntil`. Workers extend it while working. If a worker dies, the lease expires and the run returns to the queue. This means the target may be called twice for one run – which is why we send the run ID and ask targets to de-duplicate.

> **⚠️ Common mistake**
> Promising exactly-once execution. A worker can finish the call and crash before recording success. The honest guarantee is at-least-once delivery with a stable run ID; the target makes the effect happen once.

### Cron, time zones and catch-up

Compute `nextFireAt` using the schedule's time zone (`Asia/Kolkata`), not the server's. Daylight-saving jumps in other zones can skip or repeat a local time – choose a rule and document it. After an outage, fire each missed run once (or skip, if the schedule says so) rather than replaying hundreds.

### The midnight spike

Spread load by adding small random jitter to schedules that allow it, and scale workers on queue depth. The queue absorbs the burst; dispatching stays fast because it only writes small run rows.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| A dispatcher dies | Its partitions stop firing | Leases expire; another dispatcher takes over within seconds |
| A paused dispatcher wakes up | Could fire stale runs | Fencing tokens and unique run IDs reject it |
| A worker dies mid-run | Run looks stuck | Lease expires; run is retried with the same run ID |
| Target is down | Runs fail | Retry with backoff; after max attempts mark FAILED and alert |
| Midnight spike | Queue grows | Workers autoscale on queue depth; optional jitter |

## Putting it together

- **Store:** schedules with `nextFireAt`, partitioned; runs with a unique run ID.
- **Dispatch:** one leased owner per partition; create the run and advance the schedule in one transaction.
- **Execute:** queue → workers with leases → retries; targets de-duplicate by run ID.

## Interviewer follow-ups

**How do you handle job dependencies, like Airflow DAGs?** A run completes and triggers its children; the scheduler tracks each DAG run's task states. The same leasing and run-ID rules apply.

**How do you support "run every 5 seconds"?** It works, but 5-second schedules at scale are better served by a streaming or queue-based design.

**How do you delete a schedule that is about to fire?** Mark it deleted in the same table; the dispatcher's transaction checks the flag, so it cannot fire after the delete commits.

**Why not just use a delayed-message queue?** Great for one-off delays (SQS delay, RabbitMQ delayed exchange), but recurring cron rules, pausing and history need the schedule table.

## Wrap up

We partitioned schedules by `nextFireAt` with one leased dispatcher per partition, created each run once with a unique run ID, and delivered at least once to targets that de-duplicate.

> **📝 Key takeaways**
> - Index schedules by next fire time; partition them across dispatchers.
> - Create the run and advance the schedule in one transaction.
> - Leases plus fencing tokens stop old owners from acting.
> - At-least-once execution + a stable run ID = an effect that happens once.

## Closing answer

"Schedules live in a partitioned table indexed by next fire time and time zone. Each partition has one dispatcher at a time, chosen by leases with fencing tokens. Every second a dispatcher finds due schedules and, in one transaction, inserts a run with a unique ID – the schedule plus its intended fire time – and advances the next fire time; the run goes on a queue. Workers take runs with a lease, call the target with the run ID and record the outcome, retrying with backoff. If a worker or dispatcher dies, leases expire and others take over. Delivery is at least once, and targets de-duplicate by run ID so the effect happens once."

## Problem

Design a centralised logging system like ELK, Splunk or Datadog Logs. An order service on 2,000 servers writes lines such as `ERROR payment timeout orderId=5521`. At 2 a.m. an on-call engineer searches "payment timeout in the last 15 minutes" and finds the matching lines from every server in a few seconds.

Logs arrive in huge volumes, mostly never read. The system must swallow bursts without slowing the applications, make recent logs searchable quickly, and keep old logs cheaply.

## Requirements

- Collect logs from thousands of servers and containers.
- Search recent logs by text, service, level and time within seconds of them being written.
- Keep 7–15 days searchable, and older logs in cheap storage for a year.
- Never slow down or crash the application because logging is busy.
- Handle traffic bursts (an incident makes services log 10× more).

## Step 1: Clarify the requirements

> **💡 Tip**
> Logging is a pipeline: collect → buffer → index → query → archive. Name the stages early.

**Candidate:** How much log data?

**Interviewer:** About 2 million lines a second, 500 bytes each.

**Candidate:** How quickly must a line be searchable?

**Interviewer:** Within about 30 seconds.

**Candidate:** How long do we keep logs?

**Interviewer:** Searchable for 15 days, archived for a year.

**Candidate:** Is it acceptable to drop logs under extreme load?

**Interviewer:** Debug logs, yes. Errors and audit logs, no.

**Candidate:** Do we need alerts on log patterns?

**Interviewer:** Nice to have.

**Functional requirements**

1. Collect structured and plain-text logs.
2. Search by text, fields and time range; live tail.
3. Retention tiers: hot search, cold archive.

**Non-functional requirements**

1. Searchable within ~30 seconds.
2. Never block or crash the application.
3. Survive 10× bursts; cost-efficient storage.

## Step 2: Estimate the scale

> **💡 Tip**
> Log volume makes storage cost the main design driver.

```text
Ingest            = 2M lines/s × 500 bytes = 1 GB/s ≈ 86 TB/day raw
Compressed (~10×) ≈ 8.6 TB/day
Hot, 15 days      ≈ 130 TB (×2 replicas = 260 TB) + index overhead
Archive, 1 year   ≈ 3 PB raw → ~300 TB compressed in object storage
```

What it means: hot search storage is expensive, so keep it short and move everything else to object storage.

## Step 3: Define the API

```http
POST /v1/logs/bulk   (from agents, compressed batches)
[ { "ts": "2026-10-27T02:03:11.402Z", "service": "orders", "host": "ord-117",
    "level": "ERROR", "msg": "payment timeout", "orderId": "5521", "traceId": "a91f…" } ]

GET /v1/search?q=level:ERROR AND msg:"payment timeout"&from=now-15m&service=orders
GET /v1/tail?service=orders&level=ERROR     (streaming)
```

> **🎯 In the interview**
> Push for **structured logs** (JSON with fields such as service, level, traceId). Fields make filters fast and let you jump from a log line to its trace.

## Step 4: Define the data model

| Store | Contents | Technology |
| --- | --- | --- |
| Buffer | raw batches, partitioned by service | Kafka, a few days' retention |
| Hot index | time-based indices (one per day per service group), inverted index on text and fields | Elasticsearch / OpenSearch, or a column store like ClickHouse |
| Archive | compressed files per hour per service | Object storage (S3), queried rarely |

> **⚖️ Design choice**
> **Time-based indices.** One index per day makes deleting old data trivial (drop the whole index) and lets queries skip days outside their time range.

## Step 5: Draw the high-level design

[![High-level design: agents on application hosts ship logs to an ingest gateway, which writes them to a durable buffer; index workers read the buffer and build searchable time-based segments; the query service searches those segments; old data moves to an archive tier.](designs/hld-16.svg)](designs/hld-16.svg)

**Write path**

1. The app writes to stdout or a local file – fast, never waiting on the network.
2. An **agent** on each host (Fluent Bit, Vector, Filebeat) tails the file, batches lines, compresses them and sends them on.
3. The **ingest gateway** checks the API key and quotas, then writes batches to **Kafka**.
4. **Index workers** read from Kafka, parse fields, and bulk-write to the search cluster.
5. Every hour, a job also writes compressed files to object storage for the archive.

**Read path**

1. The engineer's query hits the query service, which picks the indices for the time range.
2. The search cluster scans only those indices and returns the newest matches first.

![Animation: an incident makes the order service log ten times more; agents keep batching to the ingest gateway, Kafka absorbs the burst, index workers fall behind for a few minutes and then catch up, while the application itself is never slowed.](learning-figures/hld-16-burst.gif)

## Step 6: Go deep

### Absorbing bursts: the ingest algorithm

**Option 1: The app sends logs straight to the search cluster.**

- Good: fewest moving parts.
- Problem: when the cluster is slow, the app's logging calls block – the incident gets worse.

**Option 2: Agent + durable buffer (Kafka) in the middle.**

- Good: the app writes locally; Kafka soaks up bursts; indexers catch up at their own pace.
- Problem: one more system to run.

> **⚖️ Design choice**
> Agent + Kafka. Each layer has a bounded buffer. If everything downstream is jammed, the agent drops DEBUG lines first and keeps ERROR and audit lines – it never blocks the application.

[![Back-pressure ladder: the application writes locally without waiting; the agent batches and, if its buffer fills, drops debug lines first; Kafka holds days of data during a burst; index workers catch up; errors and audit logs are never dropped.](learning-figures/hld-16-backpressure.svg)](learning-figures/hld-16-backpressure.svg)

> **⚠️ Common mistake**
> Using synchronous network logging inside request threads. A logging outage then becomes an application outage. Logging must be fire-and-forget from the app's point of view.

### Making search fast and affordable

- Index only useful fields; store the message text with a full-text index but skip indexing huge payloads.
- Partition by time and service so a 15-minute query touches a tiny slice.
- Keep 2 replicas for hot data; none needed in the archive (object storage is already durable).
- Sample very noisy debug logs (keep 1 in 100) instead of storing them all.

### Retention tiers

| Tier | Age | Where | Query speed |
| --- | --- | --- | --- |
| Hot | 0–2 days | SSD search nodes | seconds |
| Warm | 2–15 days | cheaper disks, fewer replicas | seconds to tens of seconds |
| Archive | 15 days – 1 year | compressed files in S3 | minutes (rehydrate or scan) |

### Connecting logs to traces

Put the `traceId` from OpenTelemetry in every log line. From one error you can find every log line for the same request across ten services.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| Incident burst (10× logs) | Indexers fall behind | Kafka buffers; scale indexers; search lags a few minutes |
| Search cluster down | No search | Kafka keeps data; indexers replay when it returns |
| One service logs in a loop | Floods everyone | Per-service quotas at the gateway; drop or sample over quota |
| Secrets in log lines | Leaked passwords | Redact at the agent with patterns; restrict access by service |
| Disk full on a host | App could crash | Agent rotates files with size limits |

## Putting it together

- **Collect:** app writes locally → agent batches and compresses → gateway → Kafka.
- **Index:** workers bulk-load time-based indices; hot, warm and archive tiers.
- **Protect:** bounded buffers, quotas, drop debug first, never block the app.

## Interviewer follow-ups

**Elasticsearch or ClickHouse?** Elasticsearch excels at free-text search; ClickHouse-style column stores are cheaper for structured fields and aggregations. Many teams use structured logs in a column store.

**How do you alert on logs?** A stream processor counts matching lines per minute (for example ERROR in orders) and fires when a threshold is crossed.

**How do you search the archive?** Rehydrate the needed hours into a temporary index, or query the files directly with a tool like Athena.

**Why not keep everything hot for a year?** Roughly 20× the cost for data almost nobody reads.

## Wrap up

We collected logs with local agents, buffered them in Kafka, indexed them into time-based indices, and moved old data to cheap storage.

> **📝 Key takeaways**
> - The application writes locally and never waits for logging.
> - Kafka absorbs bursts; indexers catch up.
> - Time-based indices make queries and deletion cheap.
> - Hot / warm / archive tiers control cost; drop debug before errors.

"Applications write structured logs locally and never wait on the network. ## Problem

Design a metrics and monitoring system like Prometheus at scale, Datadog metrics or M3. Every service reports numbers – requests per second, error rate, p99 latency, CPU – every 10 seconds. Dashboards draw them as graphs, and an alert pages the on-call engineer when, for example, the checkout error rate stays above 2% for 5 minutes.

Unlike logs, metrics are small numbers, but there are millions of separate series, and queries aggregate over many of them at once.

## Requirements

- Collect numeric metrics with labels (service, region, endpoint) from thousands of services.
- Store them as time series; query and aggregate over time ranges for dashboards.
- Evaluate alert rules continuously and notify the on-call engineer.
- Keep raw data for 15 days and downsampled data for a year.
- Stay up during incidents – that is when people need it most.

## Step 1: Clarify the requirements

> **💡 Tip**
> The key number in metrics is not bytes but **active series** – each unique combination of metric name and labels.

**Candidate:** How many services and series?

**Interviewer:** 5,000 services; about 50 million active series.

**Candidate:** How often are values collected?

**Interviewer:** Every 10 seconds.

**Candidate:** Push or pull?

**Interviewer:** Your choice – explain it.

**Candidate:** How fast must alerts fire?

**Interviewer:** Within a minute of the condition being true.

**Candidate:** How long do we keep data?

**Interviewer:** 15 days at full resolution, a year at lower resolution.

**Functional requirements**

1. Collect counters, gauges and histograms with labels.
2. Query with aggregation (sum, rate, percentiles) over time ranges.
3. Alert rules with notifications.

**Non-functional requirements**

1. Ingest 5 million samples per second.
2. Dashboard queries in under a second for common ranges.
3. Alerting keeps working even if dashboards are slow.

## Step 2: Estimate the scale

> **💡 Tip**
> Time-series compression is remarkable: a sample costs about 1–2 bytes, not 16.

```text
Active series        = 50 million
Samples per second   = 50M / 10 s        = 5 million per second
Raw size per sample  = 8-byte timestamp + 8-byte value = 16 bytes
Compressed           ≈ 1.5 bytes (Gorilla-style delta encoding)
Per day              = 5M × 86,400 × 1.5 B ≈ 650 GB/day
15 days              ≈ 10 TB (plus replicas)
```

What it means: storage is fine thanks to compression. The real limits are active series in memory and query fan-out.

## Step 3: Define the API

```text
# Exposed by each service at /metrics (Prometheus text format)
http_requests_total{service="checkout",endpoint="/pay",status="500"} 1832
http_request_duration_seconds_bucket{service="checkout",le="0.5"} 98211
```

```http
GET /api/v1/query_range?query=sum(rate(http_requests_total{service="checkout",status=~"5.."}[5m]))
                         / sum(rate(http_requests_total{service="checkout"}[5m]))
                        &start=…&end=…&step=30s
```

Alert rule:

```yaml
- alert: CheckoutErrorRateHigh
  expr: checkout_error_ratio > 0.02
  for: 5m
  labels: { severity: page }
```

> **🎯 In the interview**
> Explain counter + `rate()`: services expose a counter that only goes up; the query takes its per-second rate over a window. Restarts reset counters, and `rate()` handles that.

## Step 4: Define the data model

A **series** is a metric name plus a set of labels. It has an ID and a list of (timestamp, value) samples.

| Store | Contents |
| --- | --- |
| Series index | label → series IDs (an inverted index, like search) |
| Head block (memory) | the last ~2 hours of samples, plus a write-ahead log on disk |
| Blocks | immutable 2-hour chunks of compressed samples, later merged into larger blocks |
| Long-term store | downsampled (5-minute, 1-hour) blocks in object storage |

> **⚖️ Design choice**
> A purpose-built time-series database (Prometheus/Thanos, M3, VictoriaMetrics), not a general SQL table. Append-only, time-ordered, compressed blocks are 10× cheaper and much faster.

## Step 5: Draw the high-level design

[![High-level design: instrumented services expose metrics to collectors; ingest applies label and series limits and writes time-series blocks; the query engine reads blocks for dashboards; an alert evaluator runs rules on a schedule; old blocks are downsampled into long-term rollups.](designs/hld-17.svg)](designs/hld-17.svg)

**Collect and store**

1. Each service exposes `/metrics`. A collector **scrapes** it every 10 seconds (pull).
2. Ingest checks limits (max series per service), then appends samples to the head block of the right shard, chosen by hashing the series.
3. Every 2 hours the head block is compressed and flushed; blocks are uploaded to object storage.

**Query and alert**

1. A dashboard query is split by time range and shard; each shard returns partial aggregates; the query engine merges them.
2. The alert evaluator runs every rule every 30 seconds. If a rule stays true for its `for:` duration, it sends the alert to the **alert manager**, which groups, silences and routes it to Slack or PagerDuty.

![Animation: the checkout error ratio rises above 2 percent; the alert enters pending; it stays above the threshold for five minutes and becomes firing; the alert manager groups it and pages the on-call engineer; the ratio falls and the alert resolves.](learning-figures/hld-17-alert.gif)

## Step 6: Go deep

### Push or pull?

**Option 1: Pull (scrape), like Prometheus.**

- Good: the monitoring system controls the rate; a failed scrape itself tells you the target is down.
- Problem: needs service discovery to know what to scrape; awkward for short-lived jobs.

**Option 2: Push, like StatsD or OpenTelemetry exporters.**

- Good: works for short jobs and through firewalls.
- Problem: a misbehaving client can flood you; you need quotas.

> **⚖️ Design choice**
> Pull for long-running services, push (through a gateway with quotas) for batch jobs and serverless functions. Many real systems support both.

### Cardinality: the number one danger

Every unique label combination is a new series held in memory. Adding a label like `userId` turns one series into 10 million.

```text
http_requests_total{service, endpoint, status}       → 5,000 × 20 × 5   = 500,000 series
… plus userId (10M users)                             → 5 trillion series  ✗
```

> **⚠️ Common mistake**
> Putting unbounded values (user IDs, order IDs, full URLs) in labels. Use them in logs or traces; keep labels to small, fixed sets.

[![Cardinality limits: a new series is checked against per-service and per-metric limits; known label values pass; a label with unbounded values such as user IDs is rejected or dropped before it can exhaust memory.](learning-figures/hld-17-cardinality.svg)](learning-figures/hld-17-cardinality.svg)

### Storing samples compactly

Samples arrive in time order, and consecutive values are similar. Store the difference between timestamps (usually exactly 10 s, so it compresses to almost nothing) and XOR consecutive values (Facebook's Gorilla technique). That is how 16 bytes become about 1.5.

### Downsampling for long ranges

A one-year graph does not need 10-second points. A background job turns old raw data into 5-minute and 1-hour summaries (min, max, sum, count) stored in object storage. Year-long queries read the summaries.

### Keep alerting independent

Run alert evaluation close to the data with its own resources, and have a "watchdog" alert that always fires – if the on-call system stops hearing it, the monitoring itself is broken.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| A team adds a `userId` label | Memory explodes | Per-service series limits; reject new series over the limit |
| An ingest shard crashes | Recent samples lost | Write-ahead log; two replicas per shard |
| A huge dashboard query | Slows everything | Query limits, timeouts, cached results, downsampled data |
| Monitoring is down during an incident | Flying blind | Separate, small meta-monitoring and a watchdog alert |
| An alert flaps on and off | Pager fatigue | `for:` duration, grouping and silences |

## Putting it together

- **Collect:** scrape `/metrics` (or push with quotas) → limit series → append to sharded head blocks.
- **Store:** compressed 2-hour blocks → object storage → downsampled rollups.
- **Use:** merged queries for dashboards; rules with `for:` → alert manager → on-call.

## Interviewer follow-ups

**How do you compute p99 latency across 100 servers?** Each server exposes a histogram (counts per latency bucket). Sum the buckets across servers, then estimate the percentile. You cannot average per-server p99s.

**How is this different from logging?** Metrics are pre-aggregated numbers – cheap, fast, good for alerts and trends. Logs are individual events – detailed, expensive, good for investigating.

**How do you scale Prometheus beyond one machine?** Shard scraping across many Prometheus servers and use a global query layer with object-storage blocks (Thanos, Cortex/Mimir).

**How do you avoid missed alerts if one evaluator dies?** Run two evaluators; the alert manager de-duplicates identical alerts.

## Wrap up

We collected labelled numbers into sharded, compressed time-series blocks, guarded cardinality, downsampled old data, and ran alert rules independently of dashboards.

> **📝 Key takeaways**
> - Count active series, not bytes; cardinality is the main risk.
> - Counters + `rate()`, histograms for percentiles.
> - Compressed, time-ordered blocks and downsampling keep storage cheap.
> - Alerts use a `for:` duration and must keep working during incidents.

## Going deeper (optional)

The detailed version separates three clocks – collection time, aggregation windows and rule evaluation – and shows how each adds delay before an alert fires.

[![Collection, aggregation and evaluation have separate timing semantics.](lessons/hld-17-flow.svg)](lessons/hld-17-flow.svg)

Further reading: [Prometheus documentation](https://prometheus.io/docs/introduction/overview/) and [Gorilla: A Fast, Scalable, In-Memory Time Series Database](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf).

## Closing answer

"Each service exposes counters, gauges and histograms with a small, fixed set of labels. Collectors scrape them every 10 seconds – batch jobs push through a gateway – and ingest enforces per-service series limits, because cardinality is the main danger. Samples are sharded by series into an in-memory head block with a write-ahead log, then compressed with delta and XOR encoding into 2-hour blocks in object storage, with downsampled rollups for long ranges. Queries fan out to shards and merge partial aggregates. Alert rules run every 30 seconds and fire only after their `for:` duration, through an alert manager that groups and routes pages, with a watchdog that checks monitoring itself."

## Problem

Design live order tracking like Swiggy, Zomato or Uber's "your driver is 3 minutes away". Ravi, a delivery partner, rides towards Asha's flat. Asha watches a small bike icon move smoothly on her map, with an updated arrival time.

Millions of riders send locations, and each location must reach only the right customer, quickly, without old positions overwriting new ones.

## Requirements

- Delivery partners send their location every few seconds during an active order.
- The customer for that order sees the partner's position update live on a map, with ETA.
- Only the customer (and support staff) of that order may see it.
- Stop sharing when the order is delivered.
- Keep the route for disputes and analytics.

## Step 1: Clarify the requirements

> **💡 Tip**
> This differs from ride matching (HLD-9). There we search for *nearby* drivers; here we push *one* rider's position to *one* customer.

**Candidate:** How many active deliveries at peak?

**Interviewer:** About 1 million at dinner time.

**Candidate:** How often do riders send location?

**Interviewer:** Every 4 seconds while on an order.

**Candidate:** How fresh must the customer's map be?

**Interviewer:** A few seconds behind is fine; it should look smooth.

**Candidate:** Can someone else track a rider?

**Interviewer:** No. Only the customer of the active order and support.

**Candidate:** Do we keep history?

**Interviewer:** Yes, for 90 days.

**Functional requirements**

1. Ingest rider locations for active orders.
2. Push updates to the subscribed customer; show ETA.
3. Store the route history.

**Non-functional requirements**

1. End-to-end delay under ~3 seconds.
2. Strict privacy: tracking only during the order and only for its customer.
3. 250,000 updates per second at peak.

## Step 2: Estimate the scale

> **💡 Tip**
> Count updates in and pushes out. Here they are roughly equal – one rider, one watcher.

```text
Active deliveries      = 1 million
Updates in             = 1M / 4 s        = 250,000 per second
Pushes out             ≈ 250,000 per second (one customer per order, if watching)
Open customer sockets  ≈ 1 million at most
Route history          = 250,000 × 50 bytes × 3 h of peak ≈ 135 GB per evening
```

What it means: the latest position is a hot, in-memory value; history is an append-only stream written in bulk.

## Step 3: Define the API

```http

  ← { "lat": 12.9352, "lng": 77.6245, "etaMinutes": 6, "status": "ON_THE_WAY" }
```

`seq` increases with every update from the rider's app.

> **🎯 In the interview**
> The subscription is per **order**, not per rider. That makes privacy simple: a customer can only open the stream for their own active order.

## Step 4: Define the data model

| Store | Contents | Technology |
| --- | --- | --- |
| Latest location | orderId → (lat, lng, seq, ts) | Redis, TTL of a few minutes |

## Step 6: Go deep

### Never moving backwards: the update algorithm

Mobile networks deliver packets late and out of order. If an old point overwrites a newer one, the bike jumps backwards on Asha's map.

**Option 1: Use the server's arrival time.**

- Good: simple.
- Problem: a delayed old point arrives last and wins.

**Option 2: Use the phone's timestamp.**

- Good: reflects when it was measured.
- Problem: phone clocks drift and can be changed.

**Option 3: A per-session sequence number from the rider app.**

- Good: strictly increasing for this rider and order; easy to compare.
- Problem: a reinstalled app must start a new session.

> **⚖️ Design choice**
> Store a point only if its `seq` is greater than the stored one, in one atomic step (a small Lua script in Redis or a conditional write).

### Pushing to the right customer

Each customer WebSocket server subscribes to the channels of the orders its connected customers are watching. A new point is published on `order:5521`, and only the server holding Asha's socket receives it. No server needs to know about all orders.

[![Who may watch: the customer opens the tracking stream for an order; the service checks that the order is active and belongs to this customer; only then does it subscribe her connection to that order's channel; when the order is delivered, the subscription closes and points stop flowing.](learning-figures/hld-18-access.svg)](learning-figures/hld-18-access.svg)

> **⚠️ Common mistake**
> Letting customers subscribe to a **rider's** location. After delivery, the next customer's order would still expose Ravi's movements to Asha. Tie tracking to the order and close it when the order ends.

### ETA

ETA comes from a routing service (road distance, traffic, the rider's speed) and is recomputed every 15–30 seconds, not on every point. Smooth the displayed value so it doesn't jump between 5 and 7 minutes.

### Reducing load

- Send fewer points when the rider is stationary (at the restaurant).
- If Asha's app is in the background, stop pushing; resume with the latest point when she opens it.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| Points arrive out of order | Icon jumps back | Accept only higher `seq` |
| Rider loses network in a basement | Icon freezes | Show "last updated 40 s ago"; the app buffers and sends recent points when back |
| A WebSocket server dies | Customers disconnected | Reconnect to another server, get the latest point from Redis |
| Redis node fails | Latest points lost | Next update (4 s later) restores them |
| Order delivered | Tracking must stop | Status change closes subscriptions and ignores further points |

## Putting it together

- **Ingest:** check rider and order → store newest point only (by `seq`) → publish → append to history.
- **Push:** per-order channel → the WebSocket server holding the customer → smooth animation.
- **Privacy:** subscribe by order, only while active, only for its customer.

## Interviewer follow-ups

**Why not just poll every 5 seconds from the customer app?** It works for small scale, but 1 million phones polling creates load even when nothing changed. A push over one socket is cheaper and fresher.

**How do support agents see it?** The same per-order stream, authorised by role, and every access is logged.

**How is this related to the ride-matching design?** Same location stream from the rider app, but here it goes to one subscriber instead of into a geo index.

**How do you replay a route for a dispute?** Read the order's points from the history store ordered by `seq`.

## Wrap up

We kept only the newest point per order (by sequence number), pushed it through per-order channels to the authorised customer, and streamed every point to history.

> **📝 Key takeaways**
> - Latest state in memory, full history through a stream.
> - A per-session sequence number stops old points from overwriting new ones.
> - Subscribe by order, not by rider; close tracking when the order ends.
> - Animate between points so the map looks smooth.

Design a generic ticket reservation platform used for concerts, flights, events and trains (like Ticketmaster or an IRCTC-style system). Organisers publish an event with limited inventory – numbered seats, or a count such as "5,000 standing tickets". This lesson builds on BookMyShow (HLD-13). The new parts are: two kinds of inventory, issuing tickets that can't be forged or reused, and serving many organisers on one platform.

## Requirements

- Organisers create events with seated or general-admission inventory.
- Buyers hold tickets for a few minutes, pay, and receive tickets.
- Never sell more than the inventory.
- Issue tamper-proof tickets; each ticket admits exactly one person, once.
- Handle on-sale spikes for popular events.

## Step 1: Clarify the requirements

> **💡 Tip**
> "Generic" is the key word. Ask what kinds of inventory the platform must support.

**Candidate:** Seated events, general admission, or both?

**Interviewer:** Both. A stadium may have seated stands and a standing area.

**Candidate:** How many tickets can one buyer take?

**Interviewer:** Up to 6 per order.

**Candidate:** How is entry checked?

**Interviewer:** Gate staff scan a QR code with a phone app, sometimes offline.

**Candidate:** What's the peak?

**Interviewer:** A big concert: 1 million people for 60,000 tickets in the first minutes.

**Candidate:** Can tickets be transferred?

**Interviewer:** Yes, to another account, which must invalidate the old QR.

**Functional requirements**

1. Publish events with seated and general-admission inventory.
2. Hold, pay, confirm; issue QR tickets; transfer.
3. Check in at the gate exactly once.

**Non-functional requirements**

1. No overselling.
2. Survive on-sale spikes fairly.
3. Gate check-in works even with poor network.

## Step 2: Estimate the scale

> **💡 Tip**
> The interesting number is demand ÷ supply. A 16× ratio means most people will not get a ticket – fairness matters.

```text
Arrivals at on-sale        = 1,000,000 in 10 minutes ≈ 1,700/s
Tickets                    = 60,000
Demand / supply            ≈ 16×
Check-ins on event night   = 60,000 in 2 hours ≈ 8/s average, ~100/s peak at the gates
```

What it means: on-sale needs a waiting room and atomic inventory; check-in is small but must be correct.

## Step 3: Define the API

```http

POST /v1/events/{eventId}/holds  { "items": [ { "section": "Standing", "qty": 2 } ] }

POST /v1/holds/{holdId}/checkout              → payment → order CONFIRMED
GET  /v1/orders/{orderId}/tickets             → ticketId + QR per ticket
POST /v1/tickets/{ticketId}/transfer  { "toUser": "bilal@…" }
POST /v1/checkins  { "ticketId": "...", "gate": "G3" }  → 200 ADMITTED | 409 ALREADY_USED
```

> **🎯 In the interview**
> One hold API covers both inventory kinds: a request names either specific seats or a quantity in a section.

## Step 4: Define the data model

| Table | Key fields |
| --- | --- |
| `seat` (seated sections) | eventId, seatId, status (AVAILABLE / HELD / SOLD), holdId, expiresAt |

> **⚖️ Design choice**

**Buying**

3. She pays. On success, `held -= 2, sold += 2`, and the order is confirmed.
4. The ticket issuer creates 2 tickets, each with a **signed** QR code.

**Entering**

1. At gate G3, staff scan Asha's QR. The app checks the signature, then asks the check-in service to mark the ticket USED.
2. A second scan of the same QR (a screenshot shared with a friend) returns ALREADY_USED.

## Step 6: Go deep

### Two kinds of inventory

**Seated:** a conditional update on the requested seat rows, all or nothing (as in HLD-13).

**General admission:** a counter:

```sql
UPDATE ga_section
   SET held = held + :qty
 WHERE event_id = :event AND section = 'Standing'
   AND sold + held + :qty <= capacity;
-- 1 row → held; 0 rows → sold out
```

For a very hot section, split the capacity into several counter rows ("buckets", e.g. 10 × 500) and pick one at random, so thousands of buyers don't fight over one row.

### Tamper-proof tickets

**Option 1: QR contains just the ticket ID.**

- Good: simple.
- Problem: anyone can guess or forge IDs.

**Option 2: QR contains the ticket ID, version and a digital signature.**

- Good: the scanner verifies the signature with the platform's public key, even offline; changing any byte breaks it.
- Problem: key management.

> **⚖️ Design choice**
> Signed QR codes (ticketId, eventId, version, signature). Transfer increases the version and issues a new QR; the old version is no longer valid.

### Admitting each ticket exactly once

The check-in service inserts into `checkin` with `ticketId` as a unique key and checks `version` matches the current ticket. The first scan inserts; any later scan finds the row and returns ALREADY_USED.

[![Gate check: the scanner verifies the QR signature; it checks the ticket version is current; it records the check-in with a unique ticket ID; the first scan is admitted, a repeated or old-version scan is refused.](learning-figures/hld-19-checkin.svg)](learning-figures/hld-19-checkin.svg)

> **⚠️ Common mistake**
> Treating a valid signature as "may enter". A signature proves we issued the QR, not that it hasn't been used or transferred. Use-once needs a server-side record.

### Offline gates

If a gate loses network, the scanner verifies signatures locally and keeps a local list of scanned IDs, syncing when back online. Duplicates across different offline gates are possible, so venues usually keep one gate online or assign ticket ranges to gates.

### Many organisers

Partition data by event, and give each organiser quotas and isolated rate limits, so one mega on-sale cannot slow down small events.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| 1 million buyers at on-sale | Overload | Waiting room; bucketed counters |
| Buyer abandons checkout | Inventory stuck | Holds expire and return stock |
| Payment after hold expired | Possible oversell | Conditional confirm; refund if stock is gone |
| Screenshot of a QR shared | Two people try to enter | Unique check-in record; second scan refused |
| Transferred ticket's old QR | Seller tries to use it | Version check rejects old versions |

## Putting it together

- **Inventory:** seat rows or section counters, held with conditional updates, expiring holds.
- **Tickets:** signed QR with a version; transfer issues a new version.
- **Entry:** verify signature → check version → unique check-in record.

## Interviewer follow-ups

**How does an airline differ?** Airlines deliberately overbook based on no-show predictions, and a seat is per flight leg – a multi-leg trip must hold every leg or none.

**How do you stop bots?** CAPTCHA and identity checks at the waiting room, per-account and per-card limits, and randomised queue positions for people who arrive before the sale opens.

**How do you handle refunds and cancellations?** Mark the ticket CANCELLED, release inventory back to the section, and refund through the payment workflow.

**How is resale handled?** The same as transfer: a new owner and version; the platform can cap resale prices.

## Wrap up

We supported seated and general-admission inventory with conditional updates, issued signed and versioned tickets, and admitted each ticket exactly once at the gate.

> **📝 Key takeaways**
> - Seats are rows; general admission is a counter; both use conditional updates.
> - Holds expire; confirmation re-checks the hold.
> - A signature proves authenticity; a unique check-in record proves single use.
> - Transfer bumps the ticket version so old QRs stop working.

## Problem

Design a large-scale API gateway like Kong, AWS API Gateway, Zuul or an Envoy-based edge. Every request from the mobile app – `GET /orders/5521`, `POST /payments` – enters through the gateway, which checks who is calling, applies limits, and forwards the request to the right one of 300 backend services.

Because everything passes through it, the gateway must be very fast, must never become the outage, and must stop one slow backend from dragging the others down.

## Requirements

- Route requests to backend services by host, path and version.
- Authenticate callers (JWT, API keys) and pass identity to backends.
- Rate-limit per client and per route.
- Protect backends: timeouts, retries, circuit breakers.
- Change routes and policies without restarts; add little latency (a few ms).

## Step 1: Clarify the requirements

> **💡 Tip**
> Split the gateway into a **data plane** (handles every request, must be fast) and a **control plane** (manages configuration, can be slower). This is the key idea.

**Candidate:** What traffic volume?

**Interviewer:** 1 million requests per second at peak, across regions.

**Candidate:** How many backend services and routes?

**Interviewer:** About 300 services, 5,000 routes.

**Candidate:** Which authentication?

**Interviewer:** OAuth2 JWTs for users, API keys for partners.

**Candidate:** How quickly must route changes take effect?

**Interviewer:** Within about 30 seconds, without dropping requests.

**Candidate:** What latency budget?

**Interviewer:** Under 5 ms added at p99.

**Functional requirements**

1. Route, authenticate, rate-limit, transform headers.
2. Timeouts, retries and circuit breaking per backend.
3. Dynamic configuration; metrics, logs and traces.

**Non-functional requirements**

1. 1 million requests/s, under 5 ms added latency.
2. Highly available: no single point of failure.
3. Bad configuration must never take the gateway down.

## Step 2: Estimate the scale

> **💡 Tip**
> Gateway nodes are CPU-bound (TLS, parsing). Size by requests per core.

```text
Peak traffic            = 1,000,000 requests/s
Per gateway node        ≈ 20,000 requests/s (16 cores, TLS)
Nodes                   = 1M / 20,000 = 50 → ~75 with headroom, spread over 3 regions
Config                  = 5,000 routes × 2 KB ≈ 10 MB (fits in memory on every node)
```

What it means: the gateway is a horizontally scaled, stateless fleet; all routing configuration lives in each node's memory.

## Step 3: Define the API

The data plane has no API of its own – it proxies:

```http
GET https://api.example.com/v2/orders/5521
Authorization: Bearer eyJhbGciOi…
→ forwarded to http://orders-v2.internal/orders/5521
   with headers: X-User-Id: asha, X-Request-Id: 9f2c…, traceparent: …
```

The control plane has an admin API:

```http
PUT /admin/routes/orders-v2
{ "match": { "host": "api.example.com", "pathPrefix": "/v2/orders" },
  "upstream": "orders-v2", "timeoutMs": 800, "retries": 1,
  "rateLimit": { "perClient": "100/s" }, "auth": "jwt" }
```

> **🎯 In the interview**
> Say that backends trust identity headers only from the gateway – on a private network or with mutual TLS – so a client cannot forge `X-User-Id`.

## Step 4: Define the data model

| Store | Contents | Where |
| --- | --- | --- |
| Route and policy config | routes, upstreams, auth and limit settings, version | Control-plane database (etcd / Postgres), pushed to every node's memory |
| Rate-limit counters | client + route → tokens | Local per node, plus Redis for global limits |
| Upstream health | instance → healthy / ejected | In memory on each node, from active and passive checks |
| JWT signing keys | issuer → public keys | Cached in memory, refreshed periodically |

> **⚖️ Design choice**
> Each node keeps a complete **snapshot** of configuration in memory. The request path never calls the control plane, so a control-plane outage does not stop traffic.

## Step 5: Draw the high-level design

[![High-level design: clients call the gateway data plane, which applies the in-memory policy snapshot and forwards to upstream services through per-dependency bulkheads; the control plane validates and publishes new snapshots; every node sends telemetry.](designs/hld-20.svg)](designs/hld-20.svg)

**One request**

1. Asha's app calls `GET /v2/orders/5521`. A load balancer sends it to any gateway node.
2. The node terminates TLS and finds the route in its in-memory table.
3. It validates the JWT locally with cached public keys.
4. It checks the rate limit for Asha's client on this route.
5. It forwards to a healthy `orders-v2` instance with an 800 ms timeout, adding identity and trace headers.
6. It records metrics, an access log line and a trace span.

**Changing configuration**

1. An engineer updates the route through the admin API.
2. The control plane validates it and publishes a new snapshot version.
3. Nodes receive the snapshot, check it, and swap it in atomically; in-flight requests finish on the old one.

![Animation: a request passes through the gateway's filters one by one – TLS, route match, JWT check, rate limit – and is forwarded to the orders service; a second client over its limit is stopped at the rate-limit filter with 429 before reaching any backend.](learning-figures/hld-20-filters.gif)

## Step 6: Go deep

### Rate limiting across 75 nodes: the algorithm

**Option 1: Exact global counter in Redis for every request.**

- Good: precise.
- Problem: a Redis call on every request adds latency and makes Redis critical.

**Option 2: Local limits per node (global limit ÷ number of nodes).**

- Good: no network call.
- Problem: uneven load balancing makes it imprecise.

**Option 3: Local token buckets that sync with a shared store every few hundred milliseconds.**

- Good: fast and close to exact.
- Problem: can overshoot briefly.

> **⚖️ Design choice**
> Local token buckets with periodic sync for most routes; an exact Redis check only for expensive or paid partner limits. (See the Rate Limiter lesson, HLD-2.)

### Protecting backends

- **Timeouts per route:** never wait forever.
- **Retries only for safe requests** (GET, or POST with an idempotency key), with a retry budget – for example at most 10% extra traffic.
- **Circuit breaker:** if `payments` fails 50% of requests for 10 seconds, stop sending to it for a short time and fail fast.
- **Bulkheads:** a limited pool of connections per backend, so a slow `reports` service cannot use up every connection and starve `orders`.

[![Protecting backends: each upstream has its own connection pool; requests get a timeout; failures feed a circuit breaker; when the payments service keeps failing the breaker opens and requests fail fast instead of piling up, while the orders service is unaffected.](learning-figures/hld-20-protect.svg)](learning-figures/hld-20-protect.svg)

> **⚠️ Common mistake**
> Retrying everything at every layer. If the app, the gateway and the service each retry 3 times, one failure becomes 27 calls – the retries cause the outage.

### Safe configuration rollout

A bad route (a typo that matches every path) could break the whole API in seconds. So the control plane validates the config, deploys it to a few canary nodes first, watches error rates, then rolls out everywhere. Nodes keep the last good snapshot and refuse an invalid one.

### Keep the gateway thin

Business logic (aggregating three services into one response) belongs in backend services or a backend-for-frontend, not in the shared gateway. A fat gateway becomes every team's bottleneck.

## Step 7: Find bottlenecks and failure points

| What fails | What happens | How we handle it |
| --- | --- | --- |
| Control plane is down | No config changes | Nodes keep serving from their last snapshot |
| A bad config is published | Could break all traffic | Validation, canary rollout, keep last good snapshot |
| One backend becomes slow | Connections pile up | Timeouts, bulkheads, circuit breaker |
| A client floods the API | Others slowed | Per-client rate limits return 429 |
| A gateway node dies | Its requests fail | Load balancer health checks remove it; stateless nodes |

## Putting it together

- **Data plane:** stateless nodes; TLS → route → auth → limit → forward with timeouts, all from memory.
- **Control plane:** validate, version and publish snapshots; canary rollout.
- **Resilience:** bulkheads, circuit breakers, retry budgets, last-good config.

## Interviewer follow-ups

**API gateway vs service mesh?** The gateway handles north-south traffic (clients into the system); a mesh (Envoy sidecars) handles east-west traffic between services. They share many features.

**How do you do canary releases of a backend?** A route sends 5% of traffic to `orders-v3` and 95% to `orders-v2`, adjusted by weight in the config.

**How do you avoid a JWT validation call per request?** Validate signatures locally with cached public keys (JWKS), refreshed every few minutes.

**Where does TLS terminate?** At the gateway (or the load balancer in front); traffic to backends uses mutual TLS inside the network.

## Wrap up

We split the gateway into a fast, stateless data plane that works from an in-memory snapshot, and a control plane that validates and rolls out configuration safely.

> **📝 Key takeaways**
> - Data plane vs control plane: the request path never waits on configuration.
> - Validate JWTs and rate-limit locally to keep added latency in milliseconds.
> - Timeouts, bulkheads, circuit breakers and retry budgets protect backends.
> - Roll configuration out like code: validate, canary, keep the last good version.

## Closing answer

"I split the gateway into a data plane and a control plane. Data-plane nodes are stateless and scaled horizontally behind a load balancer; each holds the full route and policy snapshot in memory. A request is matched to a route, its JWT is validated locally with cached keys, it is rate-limited with local token buckets synced to a shared store, and it is forwarded with identity and trace headers, a per-route timeout, a bulkhead per upstream, a circuit breaker and a strict retry budget. The control plane validates configuration, publishes versioned snapshots and rolls them out by canary; nodes keep the last good snapshot, so a control-plane outage or a bad config never stops traffic."
