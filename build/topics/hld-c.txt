## Problem

Design a distributed job scheduler (like a cloud cron, Airflow's scheduler core, or Quartz at scale): users register one-off and recurring jobs; the system triggers them on time, runs them on a worker fleet, retries failures and ensures a job isn't run twice by accident. The key topics are **scheduling**, **workers and queues**, **leader election** and **retries/exactly-once semantics**.

## Requirements

**Functional**
- Create jobs: a cron expression or a one-time `runAt`, payload or command, timeout, retry policy, optional dependencies.
- Execute on time (± a few seconds). Track runs (status, logs). Cancel or pause.

**Non-functional**
- Millions of jobs; tens of thousands firing per minute at peaks (on-the-hour spikes).
- No missed runs when nodes die. Avoid duplicate runs (or make them harmless).

## 1. Scope and selected execution model

I support delayed/recurring jobs, retries, cancellation and worker recovery. I choose a durable schedule store, partitioned due-time dispatch and leased worker execution. Timezone, misfire and retry policies are persisted with the schedule.

## 2. Claim and execute algorithm

```text
Schedule: id,rule,zone,nextFire,misfirePolicy
Execution UNIQUE(scheduleId,intendedFireTime): state,leaseOwner,leaseExpiry,fence
Attempt: id,executionId,startedAt,result
claim: conditional READY/expired -> RUNNING, increment fence
complete: conditional matching owner/fence and live lease -> COMPLETED
```

Dispatch inserts each intended occurrence once and enqueues its ID. A worker claims, checkpoints and executes using the occurrence identity and fencing token. A destination rejecting old tokens prevents a resumed expired worker from overwriting newer work; an email-like effect instead needs idempotency/reconciliation support. Three hundred jobs/s lasting two seconds need roughly 600 active slots under those assumptions. Retries retain execution identity but create new attempts and honor the original task deadline. Cancellation stops future claims and requests cooperative running cancellation; it does not erase a side effect already performed.

### Calculate backlog

At 100 jobs/s and a 5-second average runtime, nominal concurrency is about 500. If workers sustain only 80 completions/s, backlog grows 20/s. A larger polling batch does not fix insufficient execution capacity. Keep queue depth, oldest-ready age and running lease age separate.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

- **Job store** (SQL or a partitioned KV) with an index on `next_run_at`.
- **Scheduler**: poll for due jobs (`next_run_at <= now`) in small batches, enqueue a *run* to a queue, and compute the next `next_run_at` (for cron) in the same transaction.
- **Partitioning**: shard jobs by `jobId` hash across N scheduler partitions. Each partition is owned by one scheduler instance via **leader election / leases** (etcd, ZooKeeper, or a DB lease row). That gives horizontal scale without double-dispatch.
- **Workers** pull runs from the queue, heartbeat while running, write results, and ack. Failed runs are retried with backoff, then go to a DLQ.
- An optional **timing wheel** in memory holds jobs due in the next minute for precise firing.

### Key design decisions & trade-offs

**1. Claiming due jobs safely.** Multiple scheduler replicas could pick up the same row. Either use partition ownership via leases, or atomically claim with `UPDATE … SET status='ENQUEUED', owner=? WHERE id=? AND status='SCHEDULED'` / `SELECT … FOR UPDATE SKIP LOCKED`.

**2. Exactly-once is a myth; aim for at-least-once plus idempotency.** A worker can finish the job and crash before acking, so the run is retried. Give each run a `runId` (jobId + scheduled time) that the job uses as an idempotency key.

**3. Worker failure detection.** Workers renew a visibility timeout or heartbeat. If it expires, the run is re-queued. Pick the timeout from the job's expected duration plus margin; too short gives duplicates, too long delays recovery.

**4. Thundering herd at :00.** Many cron jobs fire on the hour. Spread them with jitter when allowed, pre-fetch due jobs slightly early into the timing wheel, and autoscale workers on queue depth.

**5. Missed runs after downtime.** Define a policy per job: run once to catch up, run all missed, or skip.

**6. DAG dependencies.** For workflows, a run becomes ready only when its upstream runs succeed. Store dependencies and evaluate on completion events.

### Scope, guarantees and sizing assumptions

**Correctness requirement:** A schedule firing has a stable identity and stale workers cannot commit after lease ownership changes.

Assume 10 million scheduled jobs distributed evenly over a day: 116 due/s. A million jobs scheduled at midnight create a burst orders of magnitude larger. With 1 KB metadata each, 10 GB raw metadata excludes run history.

### Work through delivery semantics

Most practical schedulers offer at-least-once attempts. Side effects need job-level idempotency or a destination that enforces fencing. A lease alone cannot stop a paused process from acting. Retries should preserve execution identity but create new attempt IDs.

Cron schedules need a timezone and a policy for missed/duplicated local times and downtime: skip, run once or catch up every occurrence. A poison job needs bounded retries and an inspectable final state; infinite immediate retry can starve useful work.

## 6. Interviewer follow-ups

**Is “job started” equivalent to completed?** No. Record attempts, heartbeat/checkpoint and final result.

**Can a scheduler promise one email merely by using a lock?** No. The email boundary must handle retries/uncertainty too.

## 7. Closing answer

I separate schedules, occurrences and attempts. Unique occurrence identities avoid duplicate dispatch, leases recover abandoned execution and fencing/idempotency protects effects from stale workers. At-least-once attempts are explicit; exactly-once external effects require cooperation from the destination.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

1. **Agents** on each host (Fluent Bit, Vector) tail files or stdout, batch, compress and ship. A local disk buffer covers network blips.

**5. Multi-tenancy.** Quotas per tenant on ingest rate and storage, so one noisy service can't evict others' data or starve indexing.

**6. Correlation.** Inject trace IDs everywhere, so logs, metrics and traces link up during an incident.

## 5. Detailed decisions, algorithms and failure behaviour

### Architecture

- **Collection:** pull (Prometheus scrapes `/metrics`) or push (agents, StatsD/OTel). A push gateway is used for short-lived jobs.
- **Ingest:** a distributor hashes the series ID (name + sorted labels) to ingester shards (consistent hashing, replication factor 3). Ingesters keep recent data in memory with a **write-ahead log** and periodically flush immutable **blocks** (2 h) to object storage.
- **Storage format:** per series, timestamps delta-of-delta encoded and values XOR-compressed (Facebook **Gorilla**), giving ~1.3 bytes/sample. An inverted index from label to series IDs answers selectors.
- **Compaction and downsampling:** background jobs merge blocks and create 5-minute and 1-hour rollups (min, max, sum, count, so averages stay correct).
- **Query layer:** fans out to ingesters (recent) and the store (historical), merges, and caches results by time-aligned step.

### Key design decisions & trade-offs

**1. Pull vs. push.** Pull gives easy health detection ("target down") and central control, but needs service discovery and struggles across firewalls and with short jobs. Push suits ephemeral and edge workloads, but you must protect against floods.

**2. Cardinality is the real scaling limit.** Labels like `userId` or `requestId` create millions of series and blow memory and the index. Enforce label limits per metric and reject or aggregate high-cardinality labels at ingest.

**3. Percentiles.** You can't average p99s across hosts. Store **histograms** (fixed buckets, or sketches like DDSketch or t-digest) and compute quantiles at query time from merged buckets.

**4. Downsampling trade-off.** Rollups make year-long queries cheap but lose spikes. Keep min and max alongside avg so peaks remain visible.

**5. Why not a general SQL DB?** Generic B-trees and row storage waste space and write throughput. A TSDB's append-only, time-partitioned, columnar, compressed design is 10–50× more efficient.

### Follow-up questions with answers

**What cannot be eventually consistent here?** The operation establishing this guarantee: Authentication, routing and policy selection derive from trusted configuration and identity, not from forwarded client claims.

**What is the first scaling pressure to test?** Use the actual workload: Assume 100,000 requests/s and 100 microseconds of gateway CPU/request: 10 CPU-seconds/s, roughly 10 fully occupied cores before TLS, filters and headroom. A 10 ms synchronous policy lookup would require about 1,000 concurrent outstanding lookups.

**Which failure would invalidate the naive design?** The configuration plane is unavailable. Continue with a validated last-known-good snapshot within policy rather than fetching configuration on every request. Reject malformed updates atomically; avoid publishing half an auth/routing change.

**Why not introduce every distributed component immediately?** Central gateways simplify shared policy but can become noisy-neighbor bottlenecks. Separate control and data planes, limit plugin work, and isolate large uploads/streaming so buffers do not exhaust all workers.

**How would you demonstrate the design works?** Spoofed identity headers, expired key rotation cache, malformed route update, upstream slow response, retry storm, large body and streaming cancellation. Keep the expected invariant and recovery outcome visible in the results.

### Work through trust boundaries

Strip untrusted identity headers before injecting verified ones. Downstream services still authorize resource-specific actions; a signed-in user is not entitled to every order ID. Bound body size, decompression, headers and connection lifetimes independently.

Retries are safe for operations whose semantics support them, not simply because the gateway sees a timeout. Streaming responses may already have exposed partial output. Canary configuration by route/instance and monitor error changes before broad activation; retain a rollback snapshot.

## 6. Interviewer follow-ups

**Does the gateway replace service authorization?** No. It supplies verified identity and common policy; services own domain permissions.

**Does a circuit breaker add capacity?** No. It limits damage while a dependency is unhealthy.

## 7. Closing answer

I keep routing policy in a validated control-plane snapshot and enforce request budgets in the data plane. Verified identity, bounded concurrency and one retry owner protect upstream services. Resource authorization stays in the owning domain service, and a bad configuration cannot displace the last working snapshot.
