## Problem

Design a distributed job scheduler (like a cloud cron, Airflow's scheduler core, or Quartz at scale): users register one-off and recurring jobs; the system triggers them on time, runs them on a worker fleet, retries failures and ensures a job isn't run twice by accident. The key topics are **scheduling**, **workers and queues**, **leader election** and **retries/exactly-once semantics**.

## Requirements

**Functional**
- Create jobs: a cron expression or a one-time `runAt`, payload or command, timeout, retry policy, optional dependencies.
- Execute on time (± a few seconds). Track runs (status, logs). Cancel or pause.

**Non-functional**
- Millions of jobs; tens of thousands firing per minute at peaks (on-the-hour spikes).
- No missed runs when nodes die. Avoid duplicate runs (or make them harmless).

## Architecture

- **Job store** (SQL or a partitioned KV) with an index on `next_run_at`.
- **Scheduler**: poll for due jobs (`next_run_at <= now`) in small batches, enqueue a *run* to a queue, and compute the next `next_run_at` (for cron) in the same transaction.
- **Partitioning**: shard jobs by `jobId` hash across N scheduler partitions. Each partition is owned by one scheduler instance via **leader election / leases** (etcd, ZooKeeper, or a DB lease row). That gives horizontal scale without double-dispatch.
- **Workers** pull runs from the queue, heartbeat while running, write results, and ack. Failed runs are retried with backoff, then go to a DLQ.
- An optional **timing wheel** in memory holds jobs due in the next minute for precise firing.

## Key design decisions & trade-offs

**1. Claiming due jobs safely.** Multiple scheduler replicas could pick up the same row. Either use partition ownership via leases, or atomically claim with `UPDATE … SET status='ENQUEUED', owner=? WHERE id=? AND status='SCHEDULED'` / `SELECT … FOR UPDATE SKIP LOCKED`.

**2. Exactly-once is a myth; aim for at-least-once plus idempotency.** A worker can finish the job and crash before acking, so the run is retried. Give each run a `runId` (jobId + scheduled time) that the job uses as an idempotency key.

**3. Worker failure detection.** Workers renew a visibility timeout or heartbeat. If it expires, the run is re-queued. Pick the timeout from the job's expected duration plus margin; too short gives duplicates, too long delays recovery.

**4. Thundering herd at :00.** Many cron jobs fire on the hour. Spread them with jitter when allowed, pre-fetch due jobs slightly early into the timing wheel, and autoscale workers on queue depth.

**5. Missed runs after downtime.** Define a policy per job: run once to catch up, run all missed, or skip.

**6. DAG dependencies.** For workflows, a run becomes ready only when its upstream runs succeed. Store dependencies and evaluate on completion events.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** A schedule firing has a stable identity and stale workers cannot commit after lease ownership changes.

Assume 10 million scheduled jobs distributed evenly over a day: 116 due/s. A million jobs scheduled at midnight create a burst orders of magnitude larger. With 1 KB metadata each, 10 GB raw metadata excludes run history.

These are illustrative planning assumptions, not published traffic statistics or benchmark results. Recalculate the model when retention, payload size, tenant mix or peak factor changes. Show units throughout: average QPS is operations divided by seconds, bandwidth is bytes per operation multiplied by operations per second, and stored bytes are arrivals multiplied by retention and record size. Keep decimal GB/TB distinct from binary GiB/TiB when comparing vendor capacity. Replication, indexes, compaction/write amplification, backups and spare capacity are separate multipliers, not free implementation details.

Use the estimate to identify the first bottleneck, not to justify every distributed component. Ask which single key or customer can dominate the average. Measure a simple durable baseline before adding partitions. If a design serves a different workload than the stated assumption, explain the change rather than quietly inventing a larger number.

## API contracts and data ownership

```text
POST /schedules with timezone and misfire policy; cancel schedule; GET /runs/{id}; worker claim/heartbeat/complete
```

```text
Logical records (outline, not complete DDL):
schedule(id,next_at,zone,rule,misfire_policy); run(id,schedule_id,scheduled_at,state,lease_owner,lease_epoch,lease_until)

Primary access/partitioning boundary:
due_time bucket for discovery; job_id/run_id for state and execution idempotency
```

Specify authentication, authorization, body limits and idempotency at the API boundary. The same idempotency key with the same payload returns the original result; the same key with a different payload is a conflict. Persist the payload fingerprint and outcome where retries can cross process restarts. Return stable resource/operation IDs so clients can query a pending or unknown outcome. Use cursor-based continuation for changing datasets and define the sort/snapshot semantics.

An API sketch is incomplete without its authoritative records. Distinguish transactional state from projections and caches. A projection can be rebuilt; the committed ownership/history cannot. Define who may mutate each record and which fields must change atomically. A convenient cache key is not necessarily a safe database partition key, and a healthy load balancer does not choose primary-versus-replica reads on behalf of the database client.

## Build the architecture in stages

**Stage 1 — Correct baseline.** Keep one service boundary around the core transaction, durable records indexed for the dominant access path, explicit dependency adapters and basic operational metrics. Exercise the stated invariant with concurrent requests before introducing asynchronous replicas. Avoid coupling the primary user result to optional analytics, notifications or recommendation work.

**Stage 2 — Measured scaling.** Add stateless request handlers and connection pools to absorb concurrent work. Cache only data whose freshness/authorization policy allows it. Introduce a durable queue when asynchronous work has an independent lifetime; define acceptance and completion separately. Autoscaling handlers cannot fix a single hot partition or an overwhelmed external provider.

**Stage 3 — Partition and isolate.** Partition around due_time bucket for discovery; job_id/run_id for state and execution idempotency. Track ownership with a routing epoch or a database-native partition mechanism. Move virtual buckets or copy/backfill data with a verified cutover, rather than changing a modulo divisor and assuming records move themselves. Isolate bulk/background workloads from the latency-sensitive path and test the busiest tenant independently.

**Stage 4 — Regional resilience when required.** State the recovery point objective (acceptable lost acknowledged data) and recovery time objective (acceptable outage duration). A second region is useful only if it has usable data, credentials, capacity and a tested failover route. Prefer one write authority per conflicting resource until the product genuinely needs multi-writer conflict resolution.

## Trace the critical request

Persist schedule; find due buckets; atomically create/claim a unique firing; assign a worker lease and fencing epoch; execute with a run identity; heartbeat within a bounded lifetime; conditionally commit completion; compute next firing under the chosen recurrence policy.

At each hop name the input, output, timeout and durable fact. A synchronous success response should follow the promised commit point. If work continues in the background, return an operation ID and status rather than implying completion. Publish committed work through a transactional outbox or a comparably reliable mechanism; a database write followed by a best-effort publish has a failure gap.

Do not place optional telemetry on the critical dependency chain. At the same time, “asynchronous” does not mean unbounded, durable or free: select queue capacity, retry deadlines, ordering scope and a poison-message policy. Consumers should record stable event identities or use conditional domain transitions so a redelivery has a safe effect. Broker-level transaction features do not automatically make an external payment, SMS or file write exactly once.

## Deep dive: the decision that changes this system

At-least-once execution is realistic when a worker may perform an effect and crash before recording success. The downstream operation needs the run idempotency key. A fencing epoch must be checked by the resource being modified, not merely logged by the scheduler.

The important partitioning question is not merely where bytes are stored but where conflicting operations meet. Different partitions may progress independently, while operations touching the same authority need ordering or conflict detection. A stale cache/read replica can improve latency, but its allowed staleness must match the operation. A user-facing ownership/payment decision often requires a stronger path than a browsing view.

Do not use “eventual consistency” as a blanket explanation. Name the observable anomaly, the acceptable window and the remedy: stale reads, lost updates, duplicate effects, reordered events, or incomplete projections are different problems. Version/tombstone checks, conditional writes, durable deduplication and reconciliation solve different parts of that list. Include the client-visible response when a guarantee cannot be met.

## Failure and race-condition walkthrough

A paused worker outlives its lease, another worker completes the run, then the old worker resumes. Reject stale completion and stale resource writes. A lock TTL without resource-side epoch validation does not solve this.

| Failure point | Question to answer | Recovery evidence |
|---|---|---|
| Before durable commit | Did anything become authoritative? | No committed operation means a safe fresh attempt |
| Commit succeeds, response is lost | How does the client avoid duplication? | Stable request/operation identity and stored result |
| Cache/projection is stale | Can it decide this operation? | Read policy, version, tombstone or authoritative fallback |
| Worker lease expires | Can the old worker still mutate state? | Fencing epoch checked at the resource boundary |
| Dependency is unavailable | Is work rejected, queued or degraded? | Bounded deadline, queue and explicit product outcome |
| Recovery replays events | How is a repeated effect detected? | Event identity or idempotent domain transition |

A timeout does not prove the remote side failed. Keep unknown outcomes distinct from rejected ones, especially around external side effects. Retry within a shared deadline, with jitter and one clear retry owner. If a gateway, SDK and worker each retry independently, a small outage becomes a load amplifier. Circuit breakers stop some repeated calls but do not create downstream capacity or reverse an already committed effect.

## Security, tenancy and lifecycle

Authorize the resource before reading private records or generating signed references. Derive tenant/principal from authenticated context rather than a freely supplied body field. Scope cache keys, events and deduplication identities by the relevant ownership boundary. Validate untrusted URLs and payloads at egress/parser boundaries. Avoid putting credentials, full personal payloads or signed access tokens in normal logs.

Retention is part of architecture. Define when source records, indexes, object blobs, replicas, caches and backups stop exposing deleted data; deleting one primary row is not a complete lifecycle policy. Keep the minimum history necessary to diagnose/reconcile operations under the product's requirements. Admin repair paths need authorization and audit just as much as public APIs.

## Trade-offs and a starting recommendation

Polling a small due-time range is simple; timing wheels reduce scheduling overhead but need durable recovery. Cron local times need policies for skipped/repeated daylight-saving instants and missed firings after outage.

Present each alternative as a cost paid for a guarantee. SQL versus a KV store is about access paths, consistency and operating constraints, not a slogan that relational databases cannot scale. Caching buys latency at a freshness/invalidation cost. A queue decouples throughput at the cost of lag, replay and monitoring. Cross-region writes buy local write availability at the cost of coordination or application conflict resolution. A system does not become more correct merely by adding a named infrastructure product.

For migrations, version schemas and event payloads; deploy readers that accept both compatible forms before writers emit the new form. Backfill in bounded batches, compare counts/checksums or domain invariants, move a small cohort, monitor, and retain rollback data until the cutover is proven. Rollback must account for writes made during the new version; restoring an old binary alone may not restore an old data model.

## SLOs, failure drills and lab

Start lateness, successful completion, duplicate effects, oldest due job, lease churn and dead-letter age.

**Test matrix:** Leader failover, duplicate tick, lease expiry, stale worker, long job, cancellation race, midnight burst and daylight-saving recurrence.

Build a load generator that models hot keys, retries and realistic arrival bursts rather than a uniform loop over random IDs. Separate p50, p95 and p99 latency, success/error/degraded outcomes, and cache-hit/miss paths. Test at steady state, after cold start, during one component failure and throughout recovery. A system that survives the outage but collapses while replaying backlog has not completed its failure test.

Make a drill reproducible: state the starting dataset, failure time, expected invariant, maximum backlog and recovery criterion. Capture an operation trace that includes versions and identities, then verify the durable result after restart. Verify correctness and data-loss policy in addition to response latency; an API that returns quickly while double-selling or dropping acknowledged work has failed.

## Problem

Design a centralised logging and monitoring system (like ELK, Splunk or Datadog Logs): collect logs from thousands of services and hosts, make them searchable within seconds, alert on patterns and keep them affordably for months. The challenges are **high-volume ingestion**, **buffering with Kafka**, **aggregation**, **tiered storage** and **querying**.

## Requirements

**Functional**
- Ingest structured (JSON) and unstructured logs, with service, host, level and trace ID.
- Full-text and field search over recent data, aggregations (errors per service), live tail.
- Alert rules ("> 100 5xx in 1 min"). Retention per tenant (7 days hot, 1 year cold).

**Non-functional**
- Ingestion must never block or slow the apps. Tolerate bursts (incident storms).
- Searchable within ~10 s of emission.

**Scale:** 10k services emitting 5 TB/day ≈ 60 MB/s average, 5× bursts during incidents. Hot index ~35 TB for 7 days before replication.

## Architecture

1. **Agents** on each host (Fluent Bit, Vector) tail files or stdout, batch, compress and ship. A local disk buffer covers network blips.
2. **Kafka** is the ingestion buffer, partitioned by service. It absorbs bursts and decouples producers from indexers.
3. **Stream processors** parse, enrich (Kubernetes metadata), redact PII, sample noisy debug logs, derive metrics (error counts) and evaluate alert rules on the stream.
4. **Hot store:** Elasticsearch/OpenSearch (or a columnar store like ClickHouse or Loki-style label indexes), with time-based indexes per day for cheap deletion.
5. **Cold store:** compressed Parquet on S3, queryable with Athena/Trino when needed.

## Key design decisions & trade-offs

**1. Full-text index vs. label-only index.** Elasticsearch indexes every token, so search is powerful but storage and CPU cost 1.5–3× the raw size. Loki indexes only labels and scans compressed chunks, which is much cheaper but slower for needle-in-haystack searches. Pick per use case or tier.

**2. Backpressure and loss policy.** When the pipeline is behind, Kafka retention buys hours. Agents drop DEBUG before ERROR. Never block the application thread on logging (async appenders with bounded buffers).

**3. Time-partitioned indexes.** Daily indexes make retention a cheap "drop index". Rollover by size handles hot days. Queries hit only the relevant time ranges.

**4. Metrics derived from logs.** Counting errors by scanning logs at query time is expensive. Derive metrics in the stream and send them to a time-series DB (next topic). Use logs for detail.

**5. Multi-tenancy.** Quotas per tenant on ingest rate and storage, so one noisy service can't evict others' data or starve indexing.

**6. Correlation.** Inject trace IDs everywhere, so logs, metrics and traces link up during an incident.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** Accepted telemetry has a declared durability and loss policy; ingestion acknowledgement does not imply it is searchable yet.

Assume 100,000 services x 10 log events/s x 500 bytes = 500 MB/s, about 43.2 TB/day raw. Compression and sampling change storage substantially and must be measured, not assumed to be free.

## Problem

Design a metrics / time-series monitoring system (like Prometheus at scale, Datadog metrics or M3): collect numeric measurements (CPU, request rate, latency percentiles) from many services, store them efficiently, power dashboards and alerts, and keep long-term history cheaply. The specialist topics are **time-series storage**, **compression**, **aggregation**, **retention and downsampling**, and **cardinality**.

## Requirements

**Functional**
- Ingest `(metric name, labels, timestamp, value)` samples every 10–60 s.
- Query ranges with aggregation (`sum by (service) (rate(http_requests_total[5m]))`), percentiles, dashboards.
- Alert rules evaluated every ~30 s. Retention: raw 15 days, 1-minute rollups for a year.

**Non-functional**
- Write-heavy and append-only. Dashboards return in < 1 s for common queries.

**Scale:** 10M active series × 1 sample/10 s = **1M samples/s**. At ~1.5 bytes per sample after compression, that's ~130 GB/day.

## Architecture

- **Collection:** pull (Prometheus scrapes `/metrics`) or push (agents, StatsD/OTel). A push gateway is used for short-lived jobs.
- **Ingest:** a distributor hashes the series ID (name + sorted labels) to ingester shards (consistent hashing, replication factor 3). Ingesters keep recent data in memory with a **write-ahead log** and periodically flush immutable **blocks** (2 h) to object storage.
- **Storage format:** per series, timestamps delta-of-delta encoded and values XOR-compressed (Facebook **Gorilla**), giving ~1.3 bytes/sample. An inverted index from label to series IDs answers selectors.
- **Compaction and downsampling:** background jobs merge blocks and create 5-minute and 1-hour rollups (min, max, sum, count, so averages stay correct).
- **Query layer:** fans out to ingesters (recent) and the store (historical), merges, and caches results by time-aligned step.

## Key design decisions & trade-offs

**1. Pull vs. push.** Pull gives easy health detection ("target down") and central control, but needs service discovery and struggles across firewalls and with short jobs. Push suits ephemeral and edge workloads, but you must protect against floods.

**2. Cardinality is the real scaling limit.** Labels like `userId` or `requestId` create millions of series and blow memory and the index. Enforce label limits per metric and reject or aggregate high-cardinality labels at ingest.

**3. Percentiles.** You can't average p99s across hosts. Store **histograms** (fixed buckets, or sketches like DDSketch or t-digest) and compute quantiles at query time from merged buckets.

**4. Downsampling trade-off.** Rollups make year-long queries cheap but lose spikes. Keep min and max alongside avg so peaks remain visible.

**5. Why not a general SQL DB?** Generic B-trees and row storage waste space and write throughput. A TSDB's append-only, time-partitioned, columnar, compressed design is 10–50× more efficient.

## Requirements

**Functional**

**4. Adaptive ping rate.** Send more often when moving fast or near the destination, less when stationary. That saves battery and backend load.

**5. Ordering and staleness.** Mobile networks deliver late. Use device timestamps plus sequence numbers and drop pings older than the latest seen.

## Problem

Design a generic ticket or seat reservation platform (concerts, airlines, events, IRCTC-like) where inventory is scarce, demand spikes violently at sale open, and correctness is non-negotiable. Unlike HLD #13 (cinema seat maps), think of it as a reusable **inventory reservation engine** with **strong consistency**, **holds with expiry**, **transactions** and **fair admission under extreme load**.

## Requirements

**Functional**
- Inventory types: assigned seats, or general admission (N identical tickets).
- `hold(items, ttl)`, then `confirm(holdId, payment)` or `release`. Holds auto-expire.
- Purchase limits per user, presale codes, waitlists.

**Non-functional**
- Never oversell. Never charge without a ticket.
- Survive 1M+ users arriving at sale open for 50k tickets, and stay fair (no bot advantage).

## Architecture

- **Edge plus waiting room:** a CDN-hosted queue page issues signed, ordered queue tokens and admits users at a controlled rate to the shop.
- **Reservation service:** stateless API over a strongly consistent **inventory store** (sharded SQL or a single-region strongly consistent DB), partitioned by event.
- **Holds:** rows `(eventId, itemId, status, holdId, expiresAt)`. A hold is a conditional update. A sweeper (or lazy expiry on read) releases expired holds.
- **Checkout:** confirm moves holds to `SOLD` in one transaction after successful payment authorisation. Payment uses idempotency keys and is captured after confirmation.

## Key design decisions & trade-offs

**1. Conditional writes for consistency.**
- Assigned seats: `UPDATE seats SET status='HELD', hold_id=? WHERE event=? AND seat IN (...) AND status='AVAILABLE'`. Success only if the affected row count equals the requested count, in one transaction (all-or-nothing).
- General admission: a counter row `remaining`, with `UPDATE … SET remaining = remaining - n WHERE remaining >= n`. Hot row contention is a problem, so **split the counter into K sub-buckets** (e.g. 50 rows of 1,000) and pick randomly.

**2. Hold TTL trade-off.** Long holds (15 min) are kind to users but lock inventory from others. Short holds (5 min) mean more expired checkouts. Extend the hold once the user is actively in payment.

**3. Fairness and bots.** The waiting room (randomised or FIFO from sale open), per-account limits, CAPTCHA or device attestation, and verified-fan presales. Admission rate equals the measured checkout capacity.

**4. Single-writer per hot event.** For extreme events, route all writes for one event to one partition or actor that processes reservations sequentially in memory with a durable log. That gives no lock contention and deterministic ordering.

**5. Payment and inventory consistency.** Authorise, then confirm the inventory, then capture. If confirm fails, void the authorisation. Reconcile stuck states (hold expired after authorisation) with automatic voids or refunds.

```text
Logical records (outline, not complete DDL):
inventory(event,seat,state,owner_hold,version); hold(id,expires_at,state); booking(id,hold_id,payment_ref,state); outbox

Primary access/partitioning boundary:

```

Specify authentication, authorization, body limits and idempotency at the API boundary. The same idempotency key with the same payload returns the original result; the same key with a different payload is a conflict. Persist the payload fingerprint and outcome where retries can cross process restarts. Return stable resource/operation IDs so clients can query a pending or unknown outcome. Use cursor-based continuation for changing datasets and define the sort/snapshot semantics.

An API sketch is incomplete without its authoritative records. Distinguish transactional state from projections and caches. A projection can be rebuilt; the committed ownership/history cannot. Define who may mutate each record and which fields must change atomically. A convenient cache key is not necessarily a safe database partition key, and a healthy load balancer does not choose primary-versus-replica reads on behalf of the database client.

## Build the architecture in stages

**Stage 1 — Correct baseline.** Keep one service boundary around the core transaction, durable records indexed for the dominant access path, explicit dependency adapters and basic operational metrics. Exercise the stated invariant with concurrent requests before introducing asynchronous replicas. Avoid coupling the primary user result to optional analytics, notifications or recommendation work.

**Stage 2 — Measured scaling.** Add stateless request handlers and connection pools to absorb concurrent work. Cache only data whose freshness/authorization policy allows it. Introduce a durable queue when asynchronous work has an independent lifetime; define acceptance and completion separately. Autoscaling handlers cannot fix a single hot partition or an overwhelmed external provider.

**Stage 3 — Partition and isolate.** Partition around event + section + seat or inventory_bucket; hold_id for exclusive ownership. Track ownership with a routing epoch or a database-native partition mechanism. Move virtual buckets or copy/backfill data with a verified cutover, rather than changing a modulo divisor and assuming records move themselves. Isolate bulk/background workloads from the latency-sensitive path and test the busiest tenant independently.

**Stage 4 — Regional resilience when required.** State the recovery point objective (acceptable lost acknowledged data) and recovery time objective (acceptable outage duration). A second region is useful only if it has usable data, credentials, capacity and a tested failover route. Prefer one write authority per conflicting resource until the product genuinely needs multi-writer conflict resolution.

## Trace the critical request

Throttle admission; select authoritative inventory partition; conditionally reserve with hold ID and expiry; persist response identity; perform payment; confirm only if current hold still owns inventory; publish a ticket with unique redemption identity; handle cancellation by explicit policy.

At each hop name the input, output, timeout and durable fact. A synchronous success response should follow the promised commit point. If work continues in the background, return an operation ID and status rather than implying completion. Publish committed work through a transactional outbox or a comparably reliable mechanism; a database write followed by a best-effort publish has a failure gap.

Do not place optional telemetry on the critical dependency chain. At the same time, “asynchronous” does not mean unbounded, durable or free: select queue capacity, retry deadlines, ordering scope and a poison-message policy. Consumers should record stable event identities or use conditional domain transitions so a redelivery has a safe effect. Broker-level transaction features do not automatically make an external payment, SMS or file write exactly once.

## Deep dive: the decision that changes this system

For general admission use an atomic remaining-capacity decrement plus hold ledger; for assigned seating use unique seat ownership. Both require expiry and late-payment rules. A ticket scanner also needs replay prevention and a policy for offline validation.

The important partitioning question is not merely where bytes are stored but where conflicting operations meet. Different partitions may progress independently, while operations touching the same authority need ordering or conflict detection. A stale cache/read replica can improve latency, but its allowed staleness must match the operation. A user-facing ownership/payment decision often requires a stronger path than a browsing view.

Do not use “eventual consistency” as a blanket explanation. Name the observable anomaly, the acceptable window and the remedy: stale reads, lost updates, duplicate effects, reordered events, or incomplete projections are different problems. Version/tombstone checks, conditional writes, durable deduplication and reconciliation solve different parts of that list. Include the client-visible response when a guarantee cannot be met.

## Failure and race-condition walkthrough

A leader changes during a sale. The new owner must recover committed holds and reject stale epochs, rather than reconstruct availability from an eventually consistent cache. Never clear holds purely from a client countdown.

| Failure point | Question to answer | Recovery evidence |
|---|---|---|
| Before durable commit | Did anything become authoritative? | No committed operation means a safe fresh attempt |
| Commit succeeds, response is lost | How does the client avoid duplication? | Stable request/operation identity and stored result |
| Cache/projection is stale | Can it decide this operation? | Read policy, version, tombstone or authoritative fallback |
| Worker lease expires | Can the old worker still mutate state? | Fencing epoch checked at the resource boundary |
| Dependency is unavailable | Is work rejected, queued or degraded? | Bounded deadline, queue and explicit product outcome |
| Recovery replays events | How is a repeated effect detected? | Event identity or idempotent domain transition |

A timeout does not prove the remote side failed. Keep unknown outcomes distinct from rejected ones, especially around external side effects. Retry within a shared deadline, with jitter and one clear retry owner. If a gateway, SDK and worker each retry independently, a small outage becomes a load amplifier. Circuit breakers stop some repeated calls but do not create downstream capacity or reverse an already committed effect.

## Security, tenancy and lifecycle

Authorize the resource before reading private records or generating signed references. Derive tenant/principal from authenticated context rather than a freely supplied body field. Scope cache keys, events and deduplication identities by the relevant ownership boundary. Validate untrusted URLs and payloads at egress/parser boundaries. Avoid putting credentials, full personal payloads or signed access tokens in normal logs.

Retention is part of architecture. Define when source records, indexes, object blobs, replicas, caches and backups stop exposing deleted data; deleting one primary row is not a complete lifecycle policy. Keep the minimum history necessary to diagnose/reconcile operations under the product's requirements. Admin repair paths need authorization and audit just as much as public APIs.

## Trade-offs and a starting recommendation

Global strong consistency across regions increases coordination cost. Routing one event to a single write authority is often a better starting boundary; browsing and availability previews can be replicated.

Present each alternative as a cost paid for a guarantee. SQL versus a KV store is about access paths, consistency and operating constraints, not a slogan that relational databases cannot scale. Caching buys latency at a freshness/invalidation cost. A queue decouples throughput at the cost of lag, replay and monitoring. Cross-region writes buy local write availability at the cost of coordination or application conflict resolution. A system does not become more correct merely by adding a named infrastructure product.

For migrations, version schemas and event payloads; deploy readers that accept both compatible forms before writers emit the new form. Backfill in bounded batches, compare counts/checksums or domain invariants, move a small cohort, monitor, and retain rollback data until the cutover is proven. Rollback must account for writes made during the new version; restoring an old binary alone may not restore an old data model.

## Problem

Design a large-scale API gateway (like Kong, AWS API Gateway, Zuul or Envoy-based edges): a single entry point that routes millions of requests per second to hundreds of backend services, handling **routing**, **authentication**, **rate limiting**, **load balancing**, **resilience** and **observability** without becoming the bottleneck or a single point of failure.

## Requirements

**Functional**
- Route by host, path, header or version to backend services (with canary splits).
- AuthN (JWT/OAuth2, API keys, mTLS), authZ scopes, rate limits per key or tenant.
- Request and response transformation, CORS, compression, caching of safe GETs.
- Logs, metrics and traces for every request.

**Non-functional**
- Adds < 5 ms p99. Horizontally scalable. Config changes without restarts. No global outage from one bad config.

**Scale:** 2M req/s peak. At ~20k req/s per node, that's ~100+ nodes across regions.

## Architecture

- **Edge:** DNS or anycast to regional load balancers (L4), then a fleet of **stateless gateway nodes** (L7, Envoy/NGINX/Netty-based).
- **Data plane (per node):** TLS termination, then a filter chain (auth, rate limit, transform, route), then the upstream connection pool with load balancing (least-requests / P2C), retries, timeouts and circuit breakers.
- **Control plane:** config store (routes, plugins, keys) pushed to nodes via xDS or watch streams. Versioned, validated and staged for rollout.
- **Dependencies:** service discovery (Consul, Kubernetes endpoints), the auth/JWKS cache, a distributed rate-limit store (Redis), and telemetry exporters (OTel).

## Key design decisions & trade-offs

**1. Keep the hot path local.** JWT verification with cached JWKS keys (no network call). Rate limits use local token buckets synchronised with Redis asynchronously, or Redis with tight timeouts and fail-open. Every remote call on the request path adds latency and a failure mode.

**2. Stateless nodes.** Any node can serve any request. Scale by adding nodes, and drain gracefully on deploy. State (rate counters, sessions) lives outside.

**3. Resilience patterns.** Per-route timeouts and retry budgets (never retry non-idempotent POSTs blindly), circuit breakers and outlier ejection per upstream host, and bulkheads (separate pools per backend so one slow service can't exhaust all connections).

**4. Config safety.** A bad route or regex can take down everything. Validate, canary new config to a few nodes, and auto-roll back on error spikes. Keep the last known good config.

**5. Gateway vs. service mesh vs. BFF.** The gateway handles north-south (external) traffic and cross-cutting edge concerns. The mesh (sidecars) handles east-west mTLS and retries. BFFs do client-specific aggregation. Don't put business logic in the gateway.

**6. Observability.** Inject or propagate trace context and emit RED metrics (rate, errors, duration) per route. Sample access logs at high volume.

## Scope, guarantees and sizing assumptions

**Correctness requirement:** Authentication, routing and policy selection derive from trusted configuration and identity, not from forwarded client claims.

Assume 100,000 requests/s and 100 microseconds of gateway CPU/request: 10 CPU-seconds/s, roughly 10 fully occupied cores before TLS, filters and headroom. A 10 ms synchronous policy lookup would require about 1,000 concurrent outstanding lookups.

These are illustrative planning assumptions, not published traffic statistics or benchmark results. Recalculate the model when retention, payload size, tenant mix or peak factor changes. Show units throughout: average QPS is operations divided by seconds, bandwidth is bytes per operation multiplied by operations per second, and stored bytes are arrivals multiplied by retention and record size. Keep decimal GB/TB distinct from binary GiB/TiB when comparing vendor capacity. Replication, indexes, compaction/write amplification, backups and spare capacity are separate multipliers, not free implementation details.

Use the estimate to identify the first bottleneck, not to justify every distributed component. Ask which single key or customer can dominate the average. Measure a simple durable baseline before adding partitions. If a design serves a different workload than the stated assumption, explain the change rather than quietly inventing a larger number.
