## Problem

A support manager asks for an assistant that can handle: **"Bilal says his refund for order 7710 never arrived – sort it out."** No fixed script covers this. The assistant must look up the order, check the refund, maybe check the payment gateway, decide what's wrong, and either fix it or hand it to a human.

An **agent** is an LLM that chooses its own next step in a loop: think, call a tool, look at the result, repeat. That flexibility is powerful – and dangerous without limits.

## Requirements

- Explain what an agent is, and how it differs from a workflow and a single tool call.
- Explain the agent loop (reason → act → observe) and its stopping conditions.
- Know the common agentic patterns: chaining, routing, parallel, orchestrator-workers, evaluator-optimizer.
- Build a bounded agent loop with Spring AI.
- Control cost, safety and runaway loops in production.

## Step 1: The idea in plain words

| Approach | Who decides the steps? | Example |
| --- | --- | --- |
| **Single call** | Nobody – one question, one answer | "Summarise this email" |
| **Tool calling** | The model picks a tool or two in one request | "Where is order 5521?" (AI-13) |
| **Workflow** | **Your code** fixes the steps; the LLM does each step | Classify ticket → draft reply → check tone |
| **Agent** | **The model** decides the next step each time, until done | "Sort out Bilal's refund" |

The one sentence to remember:

> Use the simplest option that works. Most business problems are workflows; reach for an agent only when the steps genuinely can't be known in advance.

| Term | Plain meaning |
| --- | --- |
| **Agent loop** | Repeat: the model proposes an action → your app runs it → the result goes back. |
| **Observation** | The result of an action that the model sees next. |
| **Stopping condition** | Final answer, step limit, time or cost budget, or a human hand-off. |
| **Guardrail** | Code that checks every proposed action against rules and budgets. |

> **🎯 In the interview**
> Interviewers usually ask: agent vs workflow; how the loop works; how you stop runaway agents; how you make agents safe; which patterns you know.

## Step 2: The agent loop: execution step by step

[![Selected design: the task goes to the model, which proposes one action at a time; a policy and step-budget check approves it, only allowed tools run, every step is recorded in a run journal, and the loop ends with a final answer or a hand-off.](designs/ai-14.svg)](designs/ai-14.svg)

Bilal's refund, step by step (with a limit of 6 steps):

```text
Step 1  think:  I need the order.            act: getOrder(7710)          → DELIVERED, refund requested 12 Oct
Step 2  think:  Check the refund.            act: getRefund(7710)         → INITIATED, ₹1,899, gateway ref R-88
Step 3  think:  Is it stuck at the gateway?  act: gatewayStatus(R-88)     → FAILED: bank account closed
Step 4  think:  Can't retry to a closed account; needs new details → act: handOff("Refund failed: account closed")
Final:  "Bilal's ₹1,899 refund failed because the bank account is closed. I've raised a ticket for
         support to collect new details."
```

Each step: the model proposes **one** action, your code checks it is allowed and within budget, runs it, and records it.

![Animation: the agent loop for Bilal's refund – the model proposes looking up the order, the policy check approves, the result comes back; it proposes checking the refund, then the gateway status, which shows the bank account is closed; it hands off to a human instead of retrying, and finishes within the six-step budget.](learning-figures/ai-14-loop.gif)

### Agentic patterns worth knowing

| Pattern | What it does | Example |
| --- | --- | --- |
| **Prompt chaining** | Fixed sequence of LLM steps | Outline → draft → proofread |
| **Routing** | Classify, then send to a specialised prompt or model | Billing vs technical tickets |
| **Parallelisation** | Run independent LLM calls at once, combine | Check a contract against 5 rules in parallel |
| **Orchestrator-workers** | One LLM splits a task, workers do parts | Research across several sources |
| **Evaluator-optimizer** | One LLM drafts, another critiques, repeat | Improve a translation until it passes checks |

> **⚖️ Design choice**
> For refunds, start with a **workflow** (look up order → refund → gateway → decide) and use an agent only for the messy cases the workflow can't classify. Workflows are cheaper, faster and easier to test.

## Step 3: In code with Spring AI

Spring AI normally runs the tool loop for you (AI-13). For an agent you want **control** over each step – so turn internal execution off and run the loop yourself, with a step limit:

```java
@Service
public class RefundAgent {
    private static final int MAX_STEPS = 6;
    private final ChatModel chatModel;
    private final ToolCallingManager toolCallingManager = ToolCallingManager.builder().build();
    private final RefundTools tools;

    public RefundAgent(ChatModel chatModel, RefundTools tools) {
        this.chatModel = chatModel;
        this.tools = tools;
    }

    public String run(String task) {
        ChatOptions options = ToolCallingChatOptions.builder()
                .toolCallbacks(ToolCallbacks.from(tools))
                .internalToolExecutionEnabled(false)        // we run the loop
                .build();
        Prompt prompt = new Prompt(List.of(
                new SystemMessage("You resolve refund issues. Use tools. Hand off if unsure."),
                new UserMessage(task)), options);

        ChatResponse response = chatModel.call(prompt);
        int steps = 0;
        while (response.hasToolCalls()) {
            if (++steps > MAX_STEPS) return "Stopped after " + MAX_STEPS + " steps; handed to support.";
            checkPolicy(response);                           // your rules: allowed tools, budget
            ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, response);
            prompt = new Prompt(result.conversationHistory(), options);
            response = chatModel.call(prompt);
        }
        return response.getResult().getOutput().getText();
    }
}
```

- `internalToolExecutionEnabled(false)` – Spring AI returns the tool calls to you instead of running them.
- `ToolCallingManager.executeToolCalls` – runs the requested `@Tool` methods and builds the updated conversation.
- The `while` loop is the agent loop; `MAX_STEPS` and `checkPolicy` (your own method) are the guardrails.
- `RefundTools` holds read tools (`getOrder`, `getRefund`, `gatewayStatus`) and a safe action (`handOff`); a risky action like `issueRefund` would require human approval.

## Step 4: Common mistakes

| Mistake | Better |
| --- | --- |
| Using an agent for a fixed process | A workflow – your code decides the order |
| No step, time or cost limit | Cap steps (e.g. 6), wall-clock time and tokens per run |
| Giving every tool to the agent | Only the tools this task needs; read-only by default |
| Risky actions without approval | Human confirmation for money, deletes, external emails |
| No record of what happened | A run journal: every proposed action, check, result |
| Letting the agent loop on the same failing step | Detect repeats; stop or change strategy |

> **⚠️ Common mistake**
> Trusting the agent to "know when to stop". Models can keep calling the same unhelpful tool. Your code must enforce limits and detect loops.

[![A model can keep choosing the same unhelpful step unless the application intervenes.](lessons/ai-14-failure.svg)](lessons/ai-14-failure.svg)

## Step 5: Production concerns

- **Cost:** every step is a model call that resends the growing conversation. 6 steps can cost 10× a single answer.
- **Latency:** 6 sequential steps × ~1.5 s ≈ 9 s – show progress to the user.
- **Evaluation:** a set of realistic tasks with expected outcomes; measure success rate, steps used and hand-off rate.
- **Safety:** least-privilege tools, idempotent actions, approval for side effects, audit log of every action.
- **Resumability:** store the run journal so a crashed run can resume or be reviewed.

## Interviewer follow-ups

**What is ReAct?** A prompting style where the model alternates reasoning ("I should check the gateway") with actions and observations – the basis of most agent loops.

**Agent vs workflow – how do you choose?** If you can draw the flowchart, build a workflow. Use an agent when the path depends on what is discovered along the way.

**How do you test an agent?** Unit-test tools; replay recorded runs with a fake model; run an evaluation set of tasks and check outcomes and step counts.

**How do you stop prompt injection from a tool result?** Treat tool results as data, keep permissions in code, and never let text in a result unlock new tools or actions.

## Wrap up

An agent is a model choosing its next action in a loop; your code supplies the tools, checks each action, and enforces step, time and cost limits.

> **📝 Key takeaways**
> - Prefer workflows; use agents when the steps can't be known in advance.
> - The loop: propose → check → run → observe → repeat.
> - Limits, least-privilege tools and approvals keep agents safe.
> - Record every step so runs can be audited and evaluated.

## Closing answer

"An agent is an LLM that decides its next step in a loop: it proposes an action, my code checks and runs it, and the result goes back until it can answer. That's different from a workflow, where my code fixes the steps – and I prefer workflows when I can draw the flowchart. For agents I use Spring AI with internal tool execution turned off, so I run the loop myself with `ToolCallingManager`, a step limit, time and token budgets, and a policy check on every proposed action. Tools are least-privilege, risky actions need human approval, actions are idempotent, and every step is journaled. I evaluate on realistic tasks, tracking success rate, steps and hand-offs."

## Problem

Your company has five AI apps – a support assistant, an IDE helper, an HR bot and two internal agents. Each one needs to read Jira tickets, query the order service and search Confluence. Today every app writes its own tool code for every system: 5 apps × 3 systems = 15 integrations, all slightly different.

The **Model Context Protocol (MCP)** is an open standard that fixes this: wrap each system once as an **MCP server**, and any MCP-capable app (Claude Desktop, IDEs, your Spring AI apps) can use it.

## Requirements

- Explain what MCP is and the problem it solves.
- Explain hosts, clients and servers, and what a server offers: tools, resources and prompts.
- Explain transports (stdio and HTTP) and the connect-and-discover flow.
- Expose and consume MCP tools with Spring AI.
- Keep control: authentication, which tools are allowed, and user approval.

## Step 1: The idea in plain words

MCP is like **USB-C for AI apps**. Before USB-C, every device had its own cable. With one standard plug, any charger works with any phone. MCP is a standard "plug" between AI applications and tools or data.

| Term | Plain meaning |
| --- | --- |
| **Host** | The AI application the user works in (Claude Desktop, an IDE, your Spring Boot app). |
| **MCP client** | The part of the host that talks to one MCP server. |
| **MCP server** | A small program that exposes a system (Jira, orders, files) in the MCP format. |
| **Tools** | Actions the model can call (`get_order`, `create_ticket`). |
| **Resources** | Data the app can read (files, records) by URI. |
| **Prompts** | Reusable prompt templates offered by the server. |
| **Transport** | How messages travel: **stdio** (local process) or **HTTP** (remote server). Messages are JSON-RPC. |

```text
Without MCP: 5 apps × 3 systems = 15 custom integrations
With MCP:    3 MCP servers + 5 apps that speak MCP = 8 pieces
```

> **🎯 In the interview**
> Interviewers usually ask: what MCP is and why it exists; how it relates to tool calling; host vs client vs server; tools vs resources; how you secure it.

## Step 2: How MCP connects an app to a tool: the execution flow

[![Selected design: the Spring AI host application uses an MCP client to discover and call tools on the orders MCP server over JSON-RPC; the server queries the real order service; the host offers the discovered tools to the model as ordinary tool calls.](designs/ai-15.svg)](designs/ai-15.svg)

1. **Connect:** the host starts or connects to the MCP server (stdio for a local process, HTTP for a remote one).
2. **Initialise:** client and server exchange versions and capabilities.
3. **Discover:** the client asks `tools/list`; the server returns tool names, descriptions and JSON schemas.
4. **Offer to the model:** the host passes these tools to the LLM, exactly like normal tool calling (AI-13).
5. **Call:** when the model asks for `get_order(5521)`, the client sends `tools/call` to the server.
6. **Result:** the server runs it against the real system and returns the result to the host, which gives it to the model.

![Animation: the support assistant's MCP client connects to the orders MCP server, initialises, lists its tools and receives get_order and cancel_order; the model asks for get_order with order 5521; the client sends a tools/call, the server queries the order service and returns the status to the model.](learning-figures/ai-15-flow.gif)

> **⚖️ Design choice**
> MCP standardises **how tools are described and called**. It does not decide **whether** a call is allowed – the host and the server still authenticate users and enforce permissions.

## Step 3: In code with Spring AI

**Exposing an MCP server** (the orders team, once) with `spring-ai-starter-mcp-server-webmvc`:

```java
@Service
public class OrderMcpTools {
    private final OrderService orders;

    public OrderMcpTools(OrderService orders) { this.orders = orders; }

    @Tool(description = "Get the status of an order by order number")
    public OrderStatus getOrder(@ToolParam(description = "Order number") String orderId) {
        return orders.statusForCaller(orderId);   // checks the authenticated caller's access
    }
}

@Configuration
class McpServerConfig {
    @Bean
    ToolCallbackProvider orderTools(OrderMcpTools tools) {
        return MethodToolCallbackProvider.builder().toolObjects(tools).build();
    }
}
```

```properties
spring.ai.mcp.server.name=orders-mcp
spring.ai.mcp.server.version=1.0.0
```

**Consuming MCP servers** in any Spring AI app with `spring-ai-starter-mcp-client`:

```properties
spring.ai.mcp.client.streamable-http.connections.orders.url=https://orders-mcp.internal
spring.ai.mcp.client.stdio.connections.files.command=npx
spring.ai.mcp.client.stdio.connections.files.args=-y,@modelcontextprotocol/server-filesystem,/data/docs
```

```java
@Service
public class SupportAssistant {
    private final ChatClient chatClient;

    public SupportAssistant(ChatClient.Builder builder, ToolCallbackProvider mcpTools) {
        this.chatClient = builder
                .defaultToolCallbacks(mcpTools)       // every tool discovered from MCP servers
                .build();
    }

    public String ask(String question) {
        return chatClient.prompt().user(question).call().content();
    }
}
```

The client starter connects to each configured server, discovers its tools, and exposes them as a `ToolCallbackProvider` – after that, they behave like local `@Tool` methods.

## Step 4: Common mistakes

| Mistake | Better |
| --- | --- |
| Connecting to any MCP server you find | Allow-list trusted servers; review what each exposes |
| Exposing every discovered tool to the model | Filter to the tools this app needs |
| Trusting tool descriptions | A malicious server can hide instructions in descriptions; review and pin servers |
| Server runs with an all-powerful service account | Act as the calling user, or with least privilege |
| Destructive tools with no approval | Require user confirmation for writes |

> **⚠️ Common mistake**
> Thinking "it's MCP, so it's safe". MCP is a protocol, not a security layer. A server's metadata is untrusted input, and the server must still check who is calling.

[![Discovered metadata does not override host or user authority.](lessons/ai-15-failure.svg)](lessons/ai-15-failure.svg)

## Step 5: Production concerns

- **Authentication:** remote MCP servers use OAuth 2.1-style authorisation; pass the user's identity, not a shared super-token.
- **Governance:** keep a registry of approved servers and versions; log every tool call with user, server, tool and result.
- **Latency:** each MCP call is a network hop; keep servers close and responses small.
- **Versioning:** tool schemas change; pin server versions and test before upgrading.
- **Local vs remote:** stdio servers are great for developer tools on a laptop; shared business systems should be remote HTTP servers with proper auth.

## Interviewer follow-ups

**How is MCP different from tool calling?** Tool calling is how a model asks for an action. MCP is a standard way for apps to **discover and call** tools that live in separate servers. MCP tools end up as normal tool calls to the model.

**How is MCP different from a REST API?** A REST API is for programmers; MCP adds descriptions and schemas designed for models, plus discovery, resources and prompts in one standard.

**Tools vs resources?** Tools are actions the model chooses to call; resources are data the application (or user) chooses to attach as context.

**Who created MCP?** Anthropic published it as an open standard in late 2024; it is now supported by many hosts and frameworks, including Spring AI.

## Wrap up

MCP standardises how AI apps discover and call tools in separate servers – build each integration once, use it from every MCP-capable app – while permissions stay with the host and server.

> **📝 Key takeaways**
> - Host → MCP client → MCP server; JSON-RPC over stdio or HTTP.
> - Servers offer tools, resources and prompts; discovery returns schemas.
> - Spring AI has starters for both MCP servers and clients.
> - Allow-list servers, filter tools, authenticate users, approve writes.

## Closing answer

"MCP is an open standard for connecting AI applications to tools and data – a USB-C for AI. A host application runs an MCP client per server; over stdio or HTTP they exchange JSON-RPC messages: initialise, list tools, call tools. Servers expose tools, resources and prompts with descriptions and schemas, so each system is integrated once and reused by every MCP-capable app. In Spring AI, the server starter exposes `@Tool` methods through a `ToolCallbackProvider`, and the client starter discovers tools from configured servers and plugs them into ChatClient. MCP standardises the plumbing, not permissions: I allow-list servers, filter tools, authenticate the real user, and require approval for writes."

## Problem

A product manager asks your assistant: **"Write a one-page brief comparing our refund policy with three competitors', with sources."** One prompt doing everything – searching, reading, comparing, writing, checking – tends to produce a long, shallow answer that mixes facts up.

A **multi-agent** design splits the job between specialised roles: a researcher that gathers evidence, a writer that drafts, a reviewer that checks claims, and a coordinator that runs them. It can be better – or just more expensive. This lesson is about knowing which.

## Requirements

- Explain what a multi-agent system is and when it beats a single agent.
- Describe common structures: orchestrator-workers, sequential hand-offs, evaluator loops.
- Give each role a narrow job, its own tools and a clear output.
- Share a budget and stopping rules across all agents.
- Build a simple orchestrator with Spring AI.

## Step 1: The idea in plain words

Think of a small newsroom. The editor (coordinator) assigns work; a researcher collects facts with sources; a writer turns them into a story; a fact-checker challenges every claim. Each person is focused, and the editor decides when the story is done.

| Term | Plain meaning |
| --- | --- |
| **Agent** | An LLM with a role, instructions and tools, possibly looping (AI-14). |
| **Coordinator / orchestrator** | Splits the task, calls other agents, combines results. |
| **Worker** | An agent with one narrow job (research, write, review). |
| **Hand-off** | Passing a structured result from one agent to the next. |
| **Shared budget** | One limit on steps, tokens and time for the whole run. |

> **Rule of thumb:** start with one agent. Split only when one prompt is clearly overloaded, or parts can run in parallel.

> **🎯 In the interview**
> Interviewers usually ask: why use multiple agents; how agents communicate; how you prevent endless back-and-forth; how cost grows; when a single agent is better.

## Step 2: How the agents work together: the execution flow

[![Selected design: a Java coordinator runs four researchers in parallel, whose facts and sources form an evidence bundle; a writer drafts from the bundle; a reviewer lists unsupported claims; the coordinator allows at most one revision before accepting the final brief.](designs/ai-16.svg)](designs/ai-16.svg)

1. **Coordinator** splits the brief: "research us + 3 competitors", then "write", then "review".
2. **Researchers** (four, in parallel) each return an evidence list: claim + source URL + quote.
3. **Writer** drafts the one-page brief **only** from the evidence bundle.
4. **Reviewer** checks each sentence against the bundle and flags unsupported claims.
5. If the reviewer flags problems, the writer revises **once**. Then the coordinator accepts or returns "needs human review".

![Animation: the coordinator splits the task; four researchers gather evidence in parallel into one bundle; the writer drafts from it; the reviewer flags one claim without a source; the writer fixes it in one revision; the coordinator accepts the brief within the shared budget.](learning-figures/ai-16-team.gif)

### Common structures

**Option 1: Orchestrator-workers.** A coordinator assigns subtasks dynamically.

- Good: flexible; workers can run in parallel.
- Problem: the coordinator is a single, expensive brain that can over-delegate.

**Option 2: Sequential pipeline (hand-offs).** Research → write → review, fixed order.

- Good: predictable, easy to test – really a workflow.
- Problem: can't adapt when a step needs more work.

**Option 3: Evaluator loop.** A writer and a reviewer iterate until the review passes.

- Good: quality improves on each round.
- Problem: can loop forever or "agree" on wrong facts.

> **⚖️ Design choice**
> A **fixed pipeline with parallel research and one review round** for this brief. It gets most of the benefit with predictable cost; the coordinator is plain Java, not another LLM.

## Step 3: In code with Spring AI

Each role is a `ChatClient` with its own system prompt and tools; the coordinator is ordinary Java:

```java
@Service
public class BriefTeam {
    private final ChatClient researcher, writer, reviewer;

    public BriefTeam(ChatClient.Builder b, WebSearchTools search) {
        researcher = b.clone().defaultSystem("Find facts with source URLs and short quotes.")
                .defaultTools(search).build();
        writer   = b.clone().defaultSystem("Write a one-page brief using ONLY the evidence given.").build();
        reviewer = b.clone().defaultSystem("List every sentence not supported by the evidence.").build();
    }

    public String brief(List<String> companies) {
        List<Evidence> bundle = companies.parallelStream()                 // research in parallel
                .map(c -> researcher.prompt().user("Refund policy of " + c)
                        .call().entity(Evidence.class))
                .toList();

        String draft = writer.prompt().user("Evidence: " + bundle).call().content();
        Review review = reviewer.prompt()
                .user("Evidence: " + bundle + "\nDraft: " + draft).call().entity(Review.class);

        if (!review.unsupported().isEmpty()) {                             // one revision only
            draft = writer.prompt().user("Fix these: " + review.unsupported()
                    + "\nEvidence: " + bundle + "\nDraft: " + draft).call().content();
        }
        return draft;
    }

    record Evidence(String company, List<Fact> facts) {}
    record Fact(String claim, String url, String quote) {}
    record Review(List<String> unsupported) {}
}
```

- Each agent has a narrow prompt and only the tools it needs (only the researcher can search).
- Hand-offs are **typed records**, not free text – easier to validate and log.
- The coordinator enforces the "one revision" rule in code.

## Step 4: Common mistakes

| Mistake | Better |
| --- | --- |
| Multi-agent for a simple task | One agent or a workflow first |
| Agents chatting freely with each other | Structured hand-offs with a fixed schema |
| No overall budget | One shared limit on steps, tokens and time |
| Reviewer uses the same missing sources as the writer | Review against the evidence bundle and source links, not the writer's memory |
| Every role gets every tool | Least privilege per role |
| No trace of who said what | Log each agent's input, output and cost |

> **⚠️ Common mistake**
> Treating agreement between agents as proof. If the writer and reviewer both rely on the same wrong assumption, they will happily agree. Check claims against sources, not against each other.

[![Agreement is weak evidence when both roles use the same missing sources.](lessons/ai-16-failure.svg)](lessons/ai-16-failure.svg)

## Step 5: Production concerns

- **Cost:** 4 researchers + writer + reviewer + revision ≈ 7+ model calls, often with long contexts – 5–15× a single call. Measure whether quality improves enough.
- **Latency:** run independent agents in parallel; keep the critical path short.
- **Evaluation:** compare single-agent vs multi-agent on the same task set (accuracy, citations, cost, time).
- **Failure isolation:** if one researcher fails, continue with partial evidence and say so.
- **Model choice:** cheaper models for narrow roles (extraction, review checklists), stronger ones for planning and writing.

## Interviewer follow-ups

**When does multi-agent clearly help?** Parallel, independent subtasks (research many sources), or when separate roles need different tools, permissions or models.

**How do agents communicate?** Through the coordinator, with structured messages. Shared scratchpads are possible but harder to control.

**How do you stop infinite loops between writer and reviewer?** A fixed number of rounds, a shared budget, and a "needs human review" exit.

**Multi-agent vs one agent with many tools?** One agent is simpler and often enough. Split when the prompt gets too long, roles conflict, or you need parallelism.

## Wrap up

A multi-agent system splits a task among narrow roles with structured hand-offs, a shared budget and a coordinator that decides when the work is done – used only when it beats a single agent.

> **📝 Key takeaways**
> - Start with one agent; split for parallelism or genuinely different roles.
> - Narrow prompts, least-privilege tools, typed hand-offs.
> - One shared budget and a fixed number of rounds.
> - Check claims against evidence, not against other agents.

## Problem

Your HR assistant has been live for a month. A manager asks three questions you can't answer: "Is it getting better or worse?", "Why did it tell Asha the wrong leave balance on Tuesday?" and "Is it safe to switch to the cheaper model?"

LLM apps fail quietly – a fluent wrong answer looks just like a right one. **Observability** (seeing what happened on each request) and **evaluation** (measuring quality on known cases) are how you answer those questions.

## Requirements

- Trace every request: prompt, retrieval, tool calls, model, tokens, latency, cost.
- Build an evaluation set and score answers (correctness, faithfulness, relevance, safety).
- Use LLM-as-judge carefully, calibrated against humans.
- Gate releases (prompt, model or retrieval changes) on evaluation results.
- Use Spring AI's observability and evaluators.

## Step 1: The idea in plain words

| Practice | Question it answers | When |
| --- | --- | --- |
| **Tracing** | "What exactly happened on this request?" | Every request, in production |
| **Metrics** | "How are latency, cost and errors trending?" | Continuously, on dashboards |
| **Offline evaluation** | "Is version B better than version A?" | Before every release |
| **Online feedback** | "Are real users satisfied?" | Thumbs up/down, escalations |

| Term | Plain meaning |
| --- | --- |
| **Trace / span** | A record of one request and each step inside it (retrieval, model call, tool). |
| **Evaluation set** | Real questions with expected answers or sources, kept fixed and versioned. |
| **Faithfulness** | Every claim in the answer is supported by the retrieved sources. |
| **LLM-as-judge** | Using a model to score answers against a rubric. |
| **Release gate** | A rule like "no merge if correctness drops more than 2 points". |

> **🎯 In the interview**
> Interviewers usually ask: how you know your LLM app works; what you log; how you evaluate RAG; whether LLM-as-judge is reliable; how you compare models safely.

## Step 2: How evaluation and tracing fit together: the execution flow

[![Selected design: versioned test cases feed an evaluation runner, which calls the system under test; execution traces and scoring rubrics produce scores; human calibration checks the automatic judge; a release gate allows or blocks the change.](designs/ai-17.svg)](designs/ai-17.svg)

**In production, every request produces a trace:**

```text
trace 9f2c…  user=asha  route=/hr/ask  prompt=hr-answer-v7  model=gpt-4o-mini
├─ retrieval       42 ms   topK=4  sources=[Leave v4 §3.2, Leave v4 §3.3, …]
├─ chat model     1,380 ms tokens in=2,310 out=180  cost=₹0.06
└─ validation       3 ms   citations=2 ok
```

**Before a release, the evaluation runner:**

1. Runs all 200 cases in the evaluation set through the new version.
2. Scores each answer: correct? faithful to sources? relevant? safe?
3. Compares with the current version.
4. Passes or blocks the release.

Worked example – switching to a cheaper model:

```text

Correctness              88%            86%
Faithfulness             95%            89%      ← dropped 6 points
"Not found" handled      92%            93%
Cost per answer          ₹0.06          ₹0.02
p95 latency              2.1 s          1.4 s

```

> **⚖️ Design choice**
> Gate on the metrics that matter most for this product (here, faithfulness for HR answers), and look at cost and latency alongside – a cheaper model is only a win if quality holds.

## Step 3: In code with Spring AI

**Observability** – Spring AI emits Micrometer observations for ChatClient calls, advisors, model calls, tool calls and vector store queries. Add Actuator and a tracing bridge (OpenTelemetry), and you get spans and metrics such as `gen_ai.client.token.usage` and `gen_ai.client.operation`:

```properties
management.tracing.sampling.probability=1.0
management.otlp.tracing.endpoint=http://otel-collector:4318/v1/traces
# Prompt and completion content are NOT logged by default (privacy). Enable only in safe environments:
spring.ai.chat.client.observations.log-prompt=false
spring.ai.chat.observations.log-completion=false
```

**Evaluation** – Spring AI includes evaluators that use a model as a judge:

```java
@SpringBootTest
class HrAssistantEvaluationTest {
    @Autowired HrAssistant assistant;
    @Autowired ChatClient.Builder judgeBuilder;
    @Autowired VectorStore vectorStore;

    @ParameterizedTest
    @CsvFileSource(resources = "/eval/hr-questions-v3.csv", numLinesToSkip = 1)
    void answerIsRelevantAndGrounded(String question) {
        List<Document> sources = vectorStore.similaritySearch(question);
        String answer = assistant.ask(question);

        var request = new EvaluationRequest(question, sources, answer);
        assertTrue(new RelevancyEvaluator(judgeBuilder).evaluate(request).isPass(), "relevance");
        assertTrue(new FactCheckingEvaluator(judgeBuilder).evaluate(request).isPass(),
                "grounded in sources");
    }
}
```

- `RelevancyEvaluator` – does the answer address the question, given the context?
- `FactCheckingEvaluator` – is the answer supported by the provided documents?
- In practice, collect scores across all cases and compare aggregates rather than failing on one case.

## Step 4: Common mistakes

| Mistake | Better |
| --- | --- |
| "It looked fine in a few manual tries" | A fixed, versioned evaluation set of real questions |
| Only measuring the final answer | Also measure retrieval (recall@k) and tool success |
| Trusting an LLM judge blindly | Calibrate on 50–100 human-labelled cases; check agreement |
| Logging full prompts with personal data | Redact; restrict access; set retention |
| Averages only | Look at the worst cases and at safety-critical categories separately |
| Changing the eval set with every release | Version it; add cases, don't silently rewrite them |

> **⚠️ Common mistake**
> Letting average scores hide rare but serious failures. A 1% rate of leaking another employee's data is a disaster even if the overall score is 95%. Safety and security cases need their own zero-tolerance gate.

[![Security and rare high-impact cases need separate gates.](lessons/ai-17-failure.svg)](lessons/ai-17-failure.svg)

## Step 5: Production concerns

- **Sampling:** trace 100% of requests at first; sample later if volume is high, but keep all errors.
- **Cost dashboards:** tokens and cost per route, per user group and per model; alert on spikes.
- **Feedback loop:** thumbs-down answers and escalations become new evaluation cases.
- **Drift:** re-run the evaluation set on a schedule – providers update models, and your documents change.
- **Pin versions:** prompt version, model version and index version in every trace, so you can reproduce an answer.

## Interviewer follow-ups

**How do you evaluate a RAG system?** Separately: retrieval (did we fetch the right sources – recall@k) and generation (faithfulness, correctness, relevance), plus "not found" behaviour on questions outside the documents.

**Is LLM-as-judge reliable?** Reasonably, for clear rubrics, once you check it agrees with humans. Use a strong judge model, ask for a short reason, and avoid judging with the same model you're testing when possible.

**How do you debug one bad answer?** Find its trace: which prompt and model version, which chunks were retrieved, which tools ran. Usually the cause is visible there.

**How do you A/B test in production?** Route a small percentage of traffic to the new version, compare feedback, escalations, cost and latency, and keep offline evaluation as the first gate.

## Wrap up

Trace every request with versions, tokens and steps; measure quality on a fixed evaluation set; calibrate automatic judges with humans; and gate releases on the metrics that matter.

> **📝 Key takeaways**
> - Traces explain single answers; evaluation sets compare versions.
> - Score retrieval and generation separately.
> - Calibrate LLM judges against human labels.
> - Gate releases; give safety failures their own zero-tolerance gate.

## Problem

## Requirements

## 1. Threat model and selected controls

I assume users, documents, tool descriptors and tool results may contain hostile instructions. ## 2. Enforcement sequence


For order lookup, the current principal must own the requested order; a model-supplied admin flag is ignored. **Design question:** How can an AI application handle hostile inputs without treating model instructions as its security perimeter?

### Worked reasoning and capacity example

### Design decisions and alternatives

Narrow read-only tools reduce attack surface. Sensitive writes require operation-specific policy and confirmation/review where needed. Avoid embedding long-lived secrets in prompts because model output filtering cannot reliably recover a secret after exposure.

## Problem

## 1. Selected production architecture

## 2. Budget and recovery contracts

```text
RunBudget: absoluteDeadline,input/outputTokens,maxSteps,maxAttempts,maxSpend
Outcome: COMPLETE | NO_EVIDENCE | UNAVAILABLE | CANCELLED | BUDGET_EXHAUSTED
Retry owner: orchestrator; downstream adapter attempts count in the same budget
SideEffect: operationId,payloadHash,state,providerReference,reconciliationState
```

At 50 requests/s and eight seconds average residence, about 400 requests are active. If the allowed provider concurrency is 200, admission/degradation must address the mismatch; an unbounded queue does not add capacity. Three retry layers with three attempts each may create 27 calls, so one shared remaining deadline/attempt counter controls them.

Fallback respects required tools/schema, quality, region and data policy. Cached answers require current permission/evidence equivalence. Cancellation stops unnecessary work where supported; intentionally durable background tasks have a separate explicit contract. A tool effect completed before model timeout is reconciled by its original identity before any whole-run replay. Canary release compares task quality, spend and critical failures, and rollback restores the previous evaluated configuration.

```text
Ingestion/versioning -> lexical/vector index; authenticated request -> budget/memory -> retrieval -> model/tools -> validation -> cited response -> evaluation and operations

Application contracts (design outline):
AskRequest(question,conversationId); CitedAnswer(text,sources,abstained); IngestRun; ToolOperation; EvalCase; UsageRecord
```

Separate DocumentIngestionService, AuthorizedRetriever, AssistantService, OrderLookupTool, ConversationService and EvaluationRunner. Keep controllers thin and side effects in testable application services.

### Worked reasoning and capacity example

For 1,000 requests/day x 2,000 input + 500 output tokens, usage is 2 million input and 0.5 million output tokens/day before retries and tool loops. Set a deployment budget using measured token counts and current provider prices.

### Design decisions and alternatives

Use Java 21 and one explicitly pinned Spring AI API family. Keep API credentials outside source, isolate tenants in evidence and memory, and create a deterministic stub mode so contributors can run core tests without paid calls.

### Failure scenario and safe recovery

An apparently correct answer cites an old policy and the agent then attempts a write based on it. The product must validate source revisions and authorize the proposed action independently; retrieval confidence cannot authorize the write.

### Security, privacy and provenance

A master project is not complete merely because it starts and produces text. Include reproducible fixtures, failure outcomes, deployment configuration and a documented rollback plan.


**Verification criteria:** A release checklist covers answer support, missing-evidence abstention, authorization, source deletion, concurrent conversations, provider errors, schema failures, token budget and cost regression.

### Work through the release review

For 1,000 daily requests averaging 2,000 input and 500 output tokens, plan for two million input and half a million output tokens before retries or additional steps. Measure actual usage and current provider prices rather than promising a fixed monthly bill from these assumptions.

The final answer contract should include text, source IDs/revisions, abstention state and a traceable request ID. Keep business facts from tools distinct from prose interpretation. Publish a short runbook for source deletion, credential rotation, provider outage and rollback to the previous evaluated version.

## 6. Interviewer follow-ups

**Can every feature be an advisor?** Integration middleware can compose context, but ownership, permissions and business actions need explicit application services.

**Does the project need autonomous writes to demonstrate agents?** No. A bounded read-only investigation is easier to inspect and already exercises planning, tools and stop conditions.

## 7. Closing answer

I deliver a documentation assistant with versioned authorized evidence, scoped memory, structured citations and one narrow order-status tool. Deterministic services own permission and business facts; the model explains evidence. Evaluation and failure handling cover the entire path, and adaptive investigation is added only where it beats the fixed workflow.
