## Problem

Explain AI agents: systems where an LLM decides *which* steps to take, calls tools, observes results and iterates toward a goal, as opposed to a fixed pipeline. Cover the agent loop (ReAct), planning, state, reflection, termination and guardrails, the patterns between "workflow" and "fully autonomous agent", and how to build them in Spring AI.

## Requirements

- Workflow vs. agent: predefined control flow vs. model-driven control flow.
- The ReAct loop: reason, act (tool), observe, repeat.
- Planning (plan-then-execute), state and scratchpads, reflection and self-critique.
- Termination conditions, budgets, failure handling, human-in-the-loop.
- Common workflow patterns: chaining, routing, parallelisation, orchestrator-workers, evaluator-optimiser.

## 1. Selected agent loop

I investigate documentation questions requiring adaptive searches. Fixed questions stay on a simpler one-pass workflow. Each run owns its budget, task state and permitted tools; the model proposes actions but cannot widen that scope.

## 2. Complete control algorithm

```text
while RUNNING:
  check deadline, token balance, step/attempt limits
  ask planner for Answer | ToolProposal | NeedsInput
  if Answer: validate evidence; complete or fail with unsupported outcome
  if NeedsInput: persist NEEDS_INPUT and stop
  if ToolProposal: validate allow-list/schema/authority
    record step identity; execute within remaining deadline
    record typed observation; reject repeated no-progress cycles
on exhausted allowance: persist BUDGET_EXHAUSTED and stop
```

A 20-second run spending six seconds on the first model call and five on a tool has nine seconds left, not a fresh 20 for each step. Retries count toward attempts and shared spend. A repeated empty search triggers no-progress termination rather than an infinite loop.

On restart I inspect the step journal and resolve uncertain effects by original operation identity. Read-only tools simplify recovery; writes would need idempotency/reconciliation and the required user policy. I compare the loop with a deterministic workflow on supported completion, latency, cost and unauthorized-action counts before choosing the extra autonomy.

### Calculate the run budget

With a 20-second deadline, a 6-second first model call and 5-second tool call leave 9 seconds for subsequent work, not a new 20 seconds at each step. If the run allows four tools and each tool request can retry three times, define whether retries count toward those four and enforce a separate attempt bound.


## 5. Detailed decisions, algorithms and failure behaviour

### Mechanism and rationale

**Design question:** When does a task need an agent loop rather than one predictable application workflow?

An agent chooses its next step from observations. A workflow follows a predeclared graph. Both still need durable state, bounded execution and explicit terminal outcomes. The loop alternates model decisions, validated tool execution and observations until success, abstention, approval-needed or budget exhaustion.

### Architecture and contracts

```text
Start run -> decide -> validate action -> execute authorized tool -> persist observation/checkpoint -> decide again -> final validation -> terminal result

Application contracts (design outline):
Run(id,step,deadline,maxCalls,budget,status); Decision(finalAnswer|toolCall); Observation(toolCallId,result)
```

Keep a RunState and operation ledger outside the model. A bounded Java while loop is often easier to understand than a new orchestration framework for the first implementation.

### Worked reasoning and capacity example

At an illustrative 1,500 input + 300 output tokens per step, six independent calls consume 10,800 tokens before history replay. If each call includes every preceding observation, total input grows further; sum actual per-step usage.

### Java and Spring AI implementation outline

```java
for (int step = 0; step < maxSteps && !deadlineExpired(); step++) {
  Decision d = decideFromAuthorizedState();
  if (d.isFinal()) return validateFinal(d);
  Observation o = executeAuthorizedAndDeduplicated(d);
  checkpoint(o);
}
return incomplete("Run budget exhausted");
```

### Design decisions and alternatives

Use a deterministic RAG pipeline for simple grounded Q&A. Introduce an agent when branching cannot be specified reasonably in advance and measurable benefit exceeds added cost and failure paths.

### Failure scenario and safe recovery

The agent repeatedly calls the same failing search tool or invents new arguments after each error. Detect repeated action fingerprints, apply per-tool retry policy and terminate with an honest incomplete result.

### Security, privacy and provenance

The model’s claim that it completed a tool action is not proof. Only validated tool outcomes can advance durable workflow state.


**Verification criteria:** Completion quality, tool efficiency, loop termination, unauthorized actions, recovery behavior and total cost. Evaluate traces, not only polished final prose.

- [Spring AI tool-execution boundary](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html).
- [MCP specification, versioned protocol concepts](https://modelcontextprotocol.io/specification/2025-06-18).
- [Original RAG research](https://arxiv.org/abs/2005.11401) and [Transformer research](https://arxiv.org/abs/1706.03762) for background rather than framework instructions.

### Work through restarts

A restart after a tool succeeded but before the result was recorded creates uncertainty. Resume by the original tool-operation identity; do not ask the model to guess whether the action probably happened. Checkpointing helps only when the side-effect boundary supports reconciliation or idempotency.

A fixed workflow is often easier to test for predictable tasks. Compare it with the agent on task success, latency, cost and harmful actions. More steps are not evidence of more reasoning quality. Keep completion grounded in the task's acceptance criteria, not merely the model returning “done.”

I choose a bounded read-only investigation loop only where the next step depends on observations. The run controller enforces deadlines, tokens, attempts and allowed actions, while durable step identities support recovery. Completion requires supported task output, not the model merely saying done.

### Mechanism and rationale

**Design question:** Does splitting a task across several agents improve results enough to justify coordination overhead?

A multi-agent system is a workflow with several model-driven roles and explicit handoffs. Roles alone do not create independent evidence or authority. A supervisor may assign narrow tasks while a reducer merges structured results; every worker needs a bounded context, budget and capability set.

### Architecture and contracts

```text

```

ExecutorService/CompletableFuture can orchestrate independent tasks, but use bounded executors and cancellation. Persist task IDs and typed results rather than passing unlimited chat transcripts among workers.

### Worked reasoning and capacity example

Three workers each making four model calls plus two synthesis calls produce fourteen calls. Parallelism can reduce wall-clock time but typically increases total tokens and quota pressure. Cap per-worker and total run spend.

### Java and Spring AI implementation outline

```java
record WorkerTask(String id, String objective, int maxCalls) {}
```

Use multiple agents for separable subtasks with independently checkable outputs. Prefer one workflow when the task is mostly sequential or all workers repeat the same retrieval.

Two agents disagree using the same stale document. Voting does not make the majority correct. Compare source revisions and assumptions, escalate unresolved contradictions, and keep uncertain statements visible in the final result.

### Security, privacy and provenance

An instruction received from another agent is task data; it does not grant a worker permissions beyond the host’s established user authorization.


**Verification criteria:** Quality relative to single-agent baseline, duplicated calls, handoff errors, evidence coverage, latency and total cost. Track whether a worker exceeded its assigned scope.

## Problem

Explain the security threats specific to LLM applications and how to defend against them in an enterprise: direct and indirect prompt injection, tool and agent abuse, sensitive data leakage (PII, secrets, cross-tenant data), insecure output handling, and denial-of-wallet. Ground this in the OWASP Top 10 for LLM Applications and concrete Spring AI controls.

## Requirements

- Prompt injection: direct (user) and indirect (via documents, web pages, tool results, emails).
- Excessive agency: tools with too much power, missing authorisation and confirmation.
- Data leakage: system-prompt disclosure, PII in prompts and logs, RAG over-sharing, training-data concerns.
- Insecure output handling: model output used in SQL, HTML or shell without sanitisation.
- Resource abuse: token flooding and cost attacks. Defence-in-depth architecture.

## 1. Threat model and selected controls

I assume users, documents, tool descriptors and tool results may contain hostile instructions. Direct and indirect injection affect model behaviour; resource authorization, egress controls and output encoding protect separate boundaries. I choose narrow read-only tools by default and explicit policy for sensitive writes.

## 2. Enforcement sequence

```text
Authenticate -> bound bytes/tokens/files -> authorize evidence access
 -> generate proposed text/action -> validate schema and resource permission
 -> enforce tool/credential/egress policy -> execute or deny

```

For order lookup, the current principal must own the requested order; a model-supplied admin flag is ignored. For URL retrieval, the policy covers allowed destinations, redirects, private-address resolution, time/size/decompression limits and controlled egress. HTML escaping protects a renderer, not an HTTP tool from SSRF.

Secrets unnecessary to the task never enter prompts. External observations remain data even if they claim system authority. A classifier can add detection but cannot be the only permission control. Security tests use a stub model that deliberately requests forbidden actions, proving deterministic rejection independent of model obedience. I separately test cross-tenant evidence, malicious retrieved instructions, changed tool schemas and unauthorized writes; none can be averaged away by good public-question scores.

### Mechanism and rationale

**Design question:** How can an AI application handle hostile inputs without treating model instructions as its security perimeter?

Threat-model entry points: users, retrieved documents, tool descriptors/results, files and model outputs. Authorization and data access live in deterministic application code. Guardrails and classifiers are additional controls with false positives/negatives, not substitutes for least privilege.

### Architecture and contracts


### Worked reasoning and capacity example

A prompt containing 100,000 characters can create parser/context/cost pressure even before a tool executes. Enforce independent byte, token, file-count, decompression and time limits rather than relying on one maximum prompt length.

### Java and Spring AI implementation outline

```java

// Execute this before reading or sending private evidence to a provider.
```

### Design decisions and alternatives

Narrow read-only tools reduce attack surface. Sensitive writes require operation-specific policy and confirmation/review where needed. Avoid embedding long-lived secrets in prompts because model output filtering cannot reliably recover a secret after exposure.

### Failure scenario and safe recovery

An uploaded document instructs the assistant to fetch a private URL and send its contents elsewhere. URL allow-lists, egress controls, resource authorization and data-flow policy block the action even if the model proposes it.

### Security, privacy and provenance

Escaping HTML protects rendering, but it does not prevent an agent from making an unauthorized network request or a retrieved instruction from influencing generation.


**Verification criteria:** Authorization failures blocked, data leakage attempts, unsafe tool execution, false positive rate and audit completeness. Include multi-step attacks spanning tool results and later prompts.

## Problem

Design the architecture of production AI systems in an enterprise: routing between models by task and cost, fallbacks across providers, caching (exact and semantic), handling provider rate limits, controlling cost and latency, and building resilience, so an AI feature behaves like any other critical service (SLOs, graceful degradation, budgets).

## Requirements

- Model routing: by task type, complexity, user tier, data sensitivity.
- Resilience: timeouts, retries with backoff, circuit breakers, multi-provider fallback, degraded modes.
- Caching: response caching, semantic caching, provider prompt caching, embedding caches.

## 1. Selected production architecture

I separate stateless request handling from a bounded run orchestrator, scoped evidence/tools, provider adapters and durable side-effect state. Provider routing uses a capability/policy registry, not merely a matching API shape. Queues and bulkheads have finite capacity.

## 2. Budget and recovery contracts

```text
RunBudget: absoluteDeadline,input/outputTokens,maxSteps,maxAttempts,maxSpend
Outcome: COMPLETE | NO_EVIDENCE | UNAVAILABLE | CANCELLED | BUDGET_EXHAUSTED
Retry owner: orchestrator; downstream adapter attempts count in the same budget
SideEffect: operationId,payloadHash,state,providerReference,reconciliationState
```

At 50 requests/s and eight seconds average residence, about 400 requests are active. If the allowed provider concurrency is 200, admission/degradation must address the mismatch; an unbounded queue does not add capacity. Three retry layers with three attempts each may create 27 calls, so one shared remaining deadline/attempt counter controls them.

Fallback respects required tools/schema, quality, region and data policy. Cached answers require current permission/evidence equivalence. Cancellation stops unnecessary work where supported; intentionally durable background tasks have a separate explicit contract. A tool effect completed before model timeout is reconciled by its original identity before any whole-run replay. Canary release compares task quality, spend and critical failures, and rollback restores the previous evaluated configuration.
