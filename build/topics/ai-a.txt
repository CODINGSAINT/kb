## Problem

Explain prompt engineering as an engineering discipline: how to structure prompts (system vs. user, roles, few-shot examples, templates, grounding) so LLM outputs are accurate, consistent and safe, and how to treat prompts as versioned, tested artefacts in a Java/Spring application.

## Requirements (what you must be able to explain)

- System vs. user vs. assistant messages, and what belongs in each.
- Zero-shot vs. few-shot, and when examples help or hurt.
- Prompt templates with variables, and why string concatenation is dangerous.
- Grounding: answering *only* from supplied context, and citing it.
- Techniques: role prompting, step-by-step reasoning, output constraints, delimiters.
- How you test and version prompts.

## Learn through a concrete example

“Summarize this” leaves audience, length, source boundaries and output shape unclear. A better prompt specifies a task, supplies delimited data and defines a checkable result. Prompt engineering is controlled communication plus evaluation, not collecting magic phrases.

An **instruction** tells the model what to do. **Input data** is material to process, including quoted documents that may contain hostile instructions. An **example** demonstrates the desired mapping. A **prompt version** lets you reproduce behaviour when wording changes.

### Improve one prompt step by step

```text
Task: summarize the supplied incident report for a junior backend developer.
Return: three bullets: impact, cause, prevention; each at most 30 words.
Evidence: use only REPORT below; write unknown when a field is absent.
REPORT id=incident-17 revision=3:
...authorized report text...
```

Start with the task and measure failures. Add examples only when they clarify a recurring error. A few-shot example must not accidentally teach the model to invent a root cause whenever none is supplied.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How can a support assistant produce useful consistent responses when users ask vague or adversarial questions?

Separate durable task instructions, user input and retrieved evidence. Zero-shot supplies the task alone; few-shot includes representative input/output examples. A prompt template versions behavior, but it does not enforce permissions or guarantee factual correctness. Ask for concise justifications and verifiable intermediate results rather than depending on hidden model reasoning.

### Architecture and contracts

```text
Validate question -> assemble versioned task prompt -> include bounded examples/evidence -> model -> parse result -> business validation -> user response

Application contracts (design outline):
PromptVersion(id,template,outputSchema,evaluationSet); SupportAnswer(summary,evidenceIds,needsClarification)
```

Build a fresh request from a shared immutable ChatClient; use template parameters only for untrusted data slots. Keep prompt version and evidence IDs in application trace attributes, with sensitive bodies redacted.

### Worked reasoning and capacity example

Four 250-token examples consume 1,000 tokens before the actual question and retrieved passages. Measure whether their quality improvement justifies that context/cost budget; remove redundant examples rather than shortening the user question arbitrarily.

### Java and Spring AI implementation outline

```java
String answer = client.prompt()
    .system("Answer only from authorized evidence; otherwise say evidence is missing.")
    .user(userQuestion)
    .call().content();
// Add evidence via an application-owned, bounded context builder.
```

### Design decisions and alternatives

Few-shot examples should cover boundary conditions and abstention as well as success. Use deterministic application checks for account ownership and totals. Delimiters make provenance clearer but are not a security boundary against malicious retrieved text.

### Failure scenario and safe recovery

A retrieved page says to ignore the task and reveal credentials. Keep it in a labelled evidence section; do not grant it instruction authority. Prevent secret exposure through tool boundaries and filtered context rather than relying on a stronger-sounding system sentence.

### Security, privacy and provenance

A lower temperature reduces sampling variation but does not make an underspecified task well specified or guarantee identical answers across infrastructure/model changes.

### Hands-on lab and evaluation

**Build:** Create ten ambiguous requests, ten clear requests and ten prompt-injection documents. Compare a vague prompt with a scoped prompt and two carefully selected examples. Publish both successful cases and regressions.

**Measure:** Score completeness, evidence support, schema validity, clarification quality and instruction adherence separately. Hold out examples from the few-shot set to avoid testing memorization.

## Problem

Explain the knobs and API mechanics of calling LLMs: sampling parameters (temperature, top-p, max tokens, stop sequences), streaming vs. blocking calls, token usage and cost, and how to pick a model for a task, all from the perspective of an engineer integrating LLM APIs into Java services.

## Requirements

- Temperature and top-p: what they do mathematically and practically.
- Max tokens, stop sequences, and what happens when output is cut off.
- Streaming (SSE, `Flux<String>`) vs. a single response, and when to use each.
- Reading usage (input/output tokens) and estimating cost and latency.
- Model selection criteria, timeouts and retries for provider APIs.

## Learn through a concrete example

Two requests use the same question but return different text. That can reflect sampling, model changes or different context—not a broken Java HTTP client. Separate the model's generation settings from the application's reliability settings.

**Temperature** influences the sampling distribution. **Top-p** limits sampling to a cumulative-probability subset where supported. **Maximum output tokens** caps response generation. A **timeout** bounds how long your application waits; it does not necessarily undo computation already performed by the provider.

### Calculate cost without hard-coded prices

If a request uses 2,000 input and 500 output tokens, and the selected provider charges `P_in` and `P_out` per million, cost is `(2000×P_in + 500×P_out)/1,000,000`. Use current provider prices and actual usage categories; cached input and reasoning tokens may have separate accounting.

At 100 requests/s with an eight-second average duration, roughly 800 requests are in flight. A token limit is not a concurrency limit. Bound concurrent calls, queue length and total deadline separately.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** Which model request settings matter for cost, response quality, latency and failure recovery?

A chat request contains role-labelled messages and provider-specific options. Temperature rescales sampling logits; top-p truncates the candidate probability mass. Output limits constrain generation length. Some reasoning-capable models have different supported parameters and accounting. Validate capabilities instead of assuming one options object works everywhere.

### Architecture and contracts

```text
Resolve model capability profile -> calculate request budget -> send with deadline -> inspect finish reason and usage -> retry/classify or validate -> respond

Application contracts (design outline):
ModelPolicy(modelId,maxInputBudget,maxOutputBudget,deadline,maxAttempts); Completion(text,finishReason,usage)
```

Use ChatOptions or provider-specific options only when required; keep timeouts and retry budgets in transport/application configuration. Read ChatResponse metadata for usage instead of estimating invoices from string length.

### Worked reasoning and capacity example

For 10,000 requests/day with 2,000 input and 500 output tokens, daily usage is 20 million input and 5 million output tokens. Cost = 20 x input-price-per-million + 5 x output-price-per-million in the provider currency; plug in current prices rather than freezing a promotional number.

### Java and Spring AI implementation outline

```java
var response = client.prompt().user(question).call().chatResponse();
if (response == null) throw new IllegalStateException("Missing model response");
var usage = response.getMetadata().getUsage();
// Record observed usage and inspect finish metadata before accepting output.
```

### Design decisions and alternatives

Change one generation setting at a time on a fixed evaluation corpus. Temperature and top-p interact, so avoid blindly tuning both. Streaming improves perceived latency but does not necessarily reduce total generation work.

### Failure scenario and safe recovery

A request reaches the provider, generates tokens and times out before the client receives a response. A retry may be billed again. Bound attempts and total deadline, record uncertainty, and never retry a workflow that already executed a tool without consulting its operation ledger.

### Security, privacy and provenance

There is no universal fixed tokens-per-word conversion. English heuristics are rough; code, other languages, tool schemas and multimodal inputs tokenize differently.

### Hands-on lab and evaluation

**Build:** Run one prompt with a small output budget and inspect truncation; compare streamed versus nonstreamed first-token and completion time; inject a 429 and apply bounded jittered backoff.

**Measure:** Track time-to-first-token, total time, finish reasons, output truncation, provider errors, retries, input/output usage and cost per successful task.

- [Spring AI 1.1 ChatClient and request APIs](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html).
- [Spring AI tool-execution boundary](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html).
- [MCP specification, versioned protocol concepts](https://modelcontextprotocol.io/specification/2025-06-18).
- [Original RAG research](https://arxiv.org/abs/2005.11401) and [Transformer research](https://arxiv.org/abs/1706.03762) for background rather than framework instructions.

## Work through retries and capabilities

A 429 usually calls for bounded backoff under the same overall deadline. A schema error may need one controlled repair attempt. A timeout after a tool side effect cannot be treated as a fresh harmless request. Assign one retry owner rather than allowing gateway, SDK and application to multiply attempts independently.

Model names are configuration, not proof of support for tools, images, strict schemas or required data residency. Keep a capability matrix and test the fallback route against the same task corpus. A cheaper model can be suitable without being behaviourally equivalent.

## Practise, then check your reasoning

1. **Does low temperature make arithmetic reliable?** No. Calculate exact financial values in code.
2. **Does increasing output allowance increase the context window?** No. It consumes part of the model's permitted budget under its accounting rules.
3. **Exercise:** use a stub provider for 429, truncation, malformed output and slow streaming. Assert bounded attempts and a typed final outcome for each before spending money on a live-model experiment.

## Problem

Explain embeddings and semantic search: how text becomes vectors, why similar meanings land close together, how cosine similarity and nearest-neighbour search work, and how this differs from keyword search. It's the foundation for RAG, recommendations, dedup and clustering.

## Requirements

- What an embedding is (a dense vector of fixed dimension from a model) and what dimensions mean.
- Cosine similarity vs. dot product vs. Euclidean distance.
- Semantic vs. lexical search: strengths and failure modes of each.
- Exact vs. approximate nearest neighbour (HNSW, IVF).
- Practical concerns: model choice, normalisation, chunk size, re-embedding on model change.

## Learn through a concrete example

A user asks “How can I recover access?” while a document says “Reset your password.” Exact keyword matching may miss the connection. An **embedding** maps text into a numeric vector so related language can be nearby under the model's learned representation.

Similarity is useful for retrieving candidates; it is not a probability that the candidate is true, current or authorized. Start with a tiny labelled document set so you can inspect good and bad matches before adding an approximate index.

## See retrieval and a misleading neighbour

![Documents and queries must use a compatible embedding space.](lessons/ai-4-flow.svg)

*Documents and queries must use a compatible embedding space.*

![Tenant and document access filters constrain retrieval independently of the score.](lessons/ai-4-failure.svg)

### Calculate similarity and storage

For vectors `(1,0)` and `(1,1)`, cosine similarity is `1/(1×sqrt(2)) ≈ 0.707`. A zero vector has no defined cosine direction; handle it explicitly. Mismatched dimensions are an input error, not a score of zero.

Ten million 768-dimensional float32 vectors require `10,000,000×768×4 = 30.72 GB` raw numeric storage, before metadata, text, index edges, replicas and headroom. Approximate nearest-neighbour search trades exact recall for speed/memory; measure retrieval quality on your corpus.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** Why should a search for "password recovery" find a document titled "reset credentials", and when should it not?

An embedding model maps text to vectors in its learned space. Compare query and document vectors produced by compatible model/preprocessing versions. Cosine similarity compares angle; dot product and Euclidean distance have different normalization assumptions. Nearest neighbors are candidates for relevance, not verified answers.

### Architecture and contracts

```text
Parse documents -> preserve metadata -> chunk -> embed -> index; query -> embed -> filtered candidate search -> rerank -> source-backed result

Application contracts (design outline):
Chunk(id,documentId,revision,text,tenant,acl); Embedding(modelVersion,dimensions,values); SearchHit(chunkId,score)
```

EmbeddingModel handles vectors; VectorStore stores Document objects with source and authorization metadata. Apply tenant/ACL restrictions during retrieval and again before use.

### Worked reasoning and capacity example

One million vectors x 768 dimensions x 4 bytes = 3.072 GB raw vector storage. Doubling dimensions doubles this component, but index links, payloads, replicas and backup storage are additional.

### Java and Spring AI implementation outline

```java
record SearchHit(String chunkId, double score, String documentVersion) {}
interface AuthorizedSearch {
  java.util.List<SearchHit> find(String tenant, String user, String query, int k);
}
// Identity comes from the application, never from a model-generated filter.
```

### Design decisions and alternatives

Use lexical matching for exact identifiers, names and error codes; combine it with dense retrieval for paraphrases. Tune chunk size/overlap on labelled questions rather than assuming a universal 500-character optimum.

### Failure scenario and safe recovery

Two different embedding model versions have the same dimensions but incompatible spaces. A mixed index can return plausible-looking irrelevant neighbors without throwing an error. Version collections and re-embed documents and queries together.

### Security, privacy and provenance

Vector dimensions are learned coordinates, not human-readable slots for concepts such as vacation or happiness. A high similarity score is not a confidence percentage.

### Hands-on lab and evaluation

**Build:** Create ten paraphrase queries, ten exact-ID queries and ten out-of-domain queries. Compare lexical, dense and hybrid results, including cases where semantic similarity is misleading.

**Measure:** Report recall@k and ranking quality on relevant chunk labels, filter correctness, latency and index memory. Use an exact-search sample as an ANN recall baseline.

- [Spring AI 1.1 ChatClient and request APIs](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html).
- [Spring AI tool-execution boundary](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html).
- [MCP specification, versioned protocol concepts](https://modelcontextprotocol.io/specification/2025-06-18).
- [Original RAG research](https://arxiv.org/abs/2005.11401) and [Transformer research](https://arxiv.org/abs/1706.03762) for background rather than framework instructions.

## Work through model changes

Embeddings from different model versions are not automatically comparable even if their dimensions match. Build a new versioned index, re-embed documents and evaluate before switching query traffic. Keep document revision and chunk identity so a retrieved neighbour can be traced to readable source text.

Pure semantic search can miss exact identifiers such as error code `E1042`. Hybrid lexical/vector retrieval combines different signals, but its scores need an explicit fusion/reranking strategy rather than adding unlike numbers blindly.

## Practise, then check your reasoning

1. **Does similarity 0.9 mean 90% correct?** No. Scores depend on representation, distance metric and corpus.
2. **Can you delete only the source file?** Remove/tombstone its searchable chunks and cached evidence too.
3. **Exercise:** make ten queries with known relevant chunks, including an exact error code and a paraphrase. Measure recall@k and cross-tenant exclusion separately; a search that finds relevant but forbidden content is not successful.

## Problem

Explain Retrieval-Augmented Generation (RAG) end to end: why it exists, the ingestion pipeline (documents → chunks → embeddings → vector store) and the query pipeline (question → retrieve → augment prompt → generate with citations), with a minimal Spring AI implementation and its typical failure modes.

## Requirements

- Why RAG instead of fine-tuning for private and changing knowledge.
- Ingestion: loading, cleaning, chunking, embedding, metadata, storage.
- Query: embedding the question, top-k retrieval, prompt assembly, grounded generation.
- Citations and "I don't know" behaviour. Failure modes and how to evaluate.

## Learn through a concrete example

Your model does not know a policy updated yesterday. Retrieval-augmented generation, or **RAG**, retrieves relevant permitted passages and supplies them with the question. It avoids changing model weights for each document update, but still needs source selection and answer verification.

An **ingestion pipeline** prepares documents. A **retriever** selects evidence. A **grounded answer** is supported by that evidence. A **citation** points to a source; merely printing a valid source ID does not prove the source supports the sentence.

## See the two pipelines

### Trace one answer

Source `leave-policy:v3:chunk4` says “Annual carry-over is capped at five days.” A question asks “Can I carry seven days?” A supported answer says no under that passage and cites it, while noting any missing exception policy. It must not invent an exception because seven sounds reasonable.

With 6,000 tokens available for evidence and chunks averaging 500 tokens, at most about 12 fit before citation wrappers and other overhead. Increasing top-k without budgeting can displace instructions or truncate important passages. Chunk boundaries should preserve meaning, not just count characters.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How can an assistant answer private-document questions without training a model on every document update?

RAG retrieves relevant authorized evidence at inference time and supplies it to a generator. Ingestion and query serving are different pipelines. Retrieval errors and generation errors must be diagnosed separately; a good model cannot cite an absent or forbidden source correctly.

### Architecture and contracts

```text
Versioned source -> parse/chunk/embed -> index; question -> authorize -> retrieve/rerank -> budget context -> generate cited answer -> verify or abstain

Application contracts (design outline):
Question(tenant,user,query); Evidence(chunkId,documentVersion,passage); GroundedAnswer(text,sourceIds,abstained)
```

Use Spring AI Document, EmbeddingModel and VectorStore behind application authorization. QuestionAnswerAdvisor can provide a simple RAG path; the application still owns filtering, source versioning and answer validation.

### Worked reasoning and capacity example

A 12,000-token input allowance minus 1,000 task instructions and 2,000 conversation leaves 9,000 tokens for evidence; eight 700-token chunks use 5,600, leaving room for question and metadata. The top-k setting must obey the token budget, not just a document count.

### Java and Spring AI implementation outline

```java
record Evidence(String id, String revision, String text) {}
record GroundedAnswer(String text, java.util.List<String> sourceIds, boolean abstained) {}
// Reject citations absent from the authorized Evidence list.
// A citation ID must resolve to the exact revision used to answer.
```

### Design decisions and alternatives

Start with a lexical/vector baseline and a small golden dataset. Add query rewriting or reranking only when observed failures justify the extra call and latency. Citation output needs evidence IDs from retrieved records rather than invented URLs.

### Failure scenario and safe recovery

A top-ranked document is obsolete or includes a prompt injection. Filter by tenant, ACL and revision policy; treat source text as evidence only; preserve citations to immutable revisions so answers remain auditable.

### Security, privacy and provenance

RAG does not inherently prevent hallucination. Retrieving more chunks can increase irrelevant context and reduce answer quality.

### Hands-on lab and evaluation

**Build:** Implement a policies assistant with three versions of one policy, one unauthorized document, and a question with no answer. Demonstrate correct version choice and an explicit unsupported-answer response.

**Measure:** Measure retrieval recall, answer support, citation correctness, abstention behavior, authorization violations and freshness separately. A single similarity score cannot replace these checks.

Store document, chunk and revision IDs in the answer trace. On deletion or permission change, enforce current authorization at query time and remove stale index/cached evidence under the lifecycle policy. Treat retrieved text as untrusted data, including instructions embedded in documents.

## Build up capabilities deliberately

First use a deterministic stub response to test the controller. Then test one real model request, then structured output, then retrieval, then memory and tools when the product needs them. Adding everything at once makes a failed answer difficult to diagnose.

Keep application-owned concepts such as `Principal`, `ConversationId`, `Evidence` and `RunBudget` independent of a provider's message JSON. This lets you test permission and lifecycle rules without paid inference. Provider-specific options still matter: an abstraction does not make every model support the same schema, tool or streaming features.

## Practise, then check your reasoning

1. **Does Spring AI run a model locally by itself?** No. It integrates with the configured model backend; a local backend is a separate deployment choice.
2. **Can a successful `.content()` response be trusted as a database fact?** No. Verify against authoritative evidence or use a scoped tool.
3. **Exercise:** implement `/explain` first with a stub, then a configured provider. Test blank input, oversized input, unavailable provider and a private-policy question. Record what your service guarantees and what the model still cannot know.

## Problem

Master Spring AI's `ChatClient`, the fluent, high-level API most applications use: building clients with defaults, composing prompts, getting text, structured entities or streams back, attaching advisors (memory, RAG, logging) and tools, and organising multiple clients in a real Spring Boot service.

## Requirements

- Creating a `ChatClient` from the auto-configured `ChatClient.Builder`, with defaults.
- The fluent request API: `.system()`, `.user()`, params, `.options()`, `.advisors()`, `.tools()`.
- Response types: `.content()`, `.entity(Class)`, `.chatResponse()`, `.stream().content()`.
- Advisors at a conceptual level (detail in topic 12).
- Structuring clients per use case.

## Learn through a concrete example

One endpoint returns a short explanation, another streams a long tutorial, and a third needs a typed answer. `ChatClient` builds the request, while the terminal choice determines how your application consumes the response. Do not treat every result as a `String` if metadata or a structured contract matters.

A **request specification** contains messages/options. A **stream** delivers pieces over time. **Usage metadata** describes observed token consumption where supplied. A **finish reason** helps distinguish normal completion from truncation or another stop condition.

### Compare concrete API shapes

```java
// Spring AI 1.1.8 method excerpts, checked by the API-contract example.
String text = client.prompt().user(question).call().content();
var response = client.prompt().user(question).call().chatResponse();
var chunks = client.prompt().user(question).stream().content();
Explanation typed = client.prompt().user(question).call().entity(Explanation.class);
```

Choose one consumption for one request; running all four lines issues separate requests. A streaming sequence must be subscribed/returned through the reactive pipeline to produce work; do not block an event-loop thread to collect it accidentally.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How do you use ChatClient without losing provider metadata or mixing users’ request state?

ChatClient creates a fluent request over a ChatModel. A completed call can yield text, a typed entity or a ChatResponse containing metadata. A stream returns pieces over time; these are not necessarily words, sentences or complete JSON documents.

### Architecture and contracts

```text
Fresh request spec -> task/system message -> user/evidence messages -> advisors -> call or stream -> metadata and validation -> response

Application contracts (design outline):
ClientFacade.answer(question,conversationKey); CompletionEnvelope(answer,usage,finishReason,promptVersion)
```

Build ChatClient once from the injected builder, then create a new prompt specification for each call. A request-specific conversation ID belongs in advisor parameters after authorization.

### Worked reasoning and capacity example

If 500 output tokens arrive at an illustrative 50 tokens/s after a 1-second prefill, completion takes about 11 seconds. Streaming can show the first piece earlier but cannot make all 500 tokens arrive at once.

### Java and Spring AI implementation outline

```java
reactor.core.publisher.Flux<String> stream = client.prompt()
    .user(question).stream().content();
// Propagate cancellation and bound provider concurrency in the application.
```

### Design decisions and alternatives

Use content() for a simple demonstration, chatResponse() when usage/finish metadata matters, and entity mapping only when the result contract can be validated. Keep streaming text and finalized structured objects as different response modes.

### Failure scenario and safe recovery

A browser disconnects while the model continues generating. Propagate cancellation and bound server work. If a stream ends halfway through a JSON object, do not persist it as a valid final answer.

### Security, privacy and provenance

Logging a fluent request or response can expose user prompts, retrieved documents and secrets. Log IDs, versions, counts and redacted diagnostics by default.

### Hands-on lab and evaluation

**Build:** Implement two endpoints for the same task: a completed validated answer and an SSE text stream. Disconnect a streaming client and inspect cancellation, quota use and trace completion.

**Measure:** Test cross-user request isolation, stream termination, empty responses, provider truncation and usage extraction. Measure successful task cost rather than only request count.

## Trace a stream completely

If chunks are `"Trans"`, `"action"`, `"s..."`, they are transport pieces, not necessarily whole words or sentences. Append in order and handle partial output. Do not expose a partial generated command as an executable action. Structured documents usually need full parsing/validation before business use.

Record time to first token and time to completion separately. A two-second first token followed by a minute-long response is a different experience from a ten-second response delivered all at once. Streaming changes delivery latency, not necessarily total token cost or factual quality.

## Practise, then check your reasoning

1. **Does obtaining text and then obtaining metadata reuse the same call automatically?** Do not assume it. Consume a response object that contains what you need from one call.
2. **Is an interrupted stream a complete answer?** No. Mark it partial/cancelled in UI and persistence.
3. **Exercise:** use a stub stream with three chunks and an error after chunk two. Verify ordering, cancellation, bounded buffering and an explicit incomplete state. Repeat with a normal finish and compare telemetry.
