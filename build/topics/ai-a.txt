## 1. Parameter answer and chosen request policy

Temperature changes sampling from token scores; top-p limits a cumulative-probability candidate set where supported. Neither establishes truth. ## 2. Bounded request contract

```text
ModelRequest: modelVersion,messages,outputCap,sampling,responseSchema,deadline
Outcome: COMPLETE | TRUNCATED | CONTRACT_FAILURE | THROTTLED | TIMEOUT
Usage: actual input/output and provider-specific usage categories
Cost = (inputTokens*inputPrice + outputTokens*outputPrice)/1000000
```

At 2,000 input and 500 output tokens, I calculate using current configured prices rather than hard-coded marketing estimates. At 100 requests/s lasting eight seconds, average in-flight work is roughly 800, so a bounded executor/queue matters independently of token caps.

A truncation finish reason means the requested object may be incomplete; I do not deserialize partial text as a successful business result. A 429 receives bounded backoff within the original deadline. One layer owns retries to avoid multiplication. After a tool effect, a whole-run retry must reuse or reconcile the operation identity. ## Requirements

## 1. Complete embedding answer and selected design

An embedding maps text into a fixed-length vector learned by a model. Related meanings can be close under the configured metric, making paraphrases retrievable without exact keyword overlap. I choose one compatible embedding model for documents and queries, versioned chunks and authorization-filtered nearest-neighbour retrieval.

## 2. Similarity and retrieval algorithm

```text
cosine(a,b) = dot(a,b)/(norm(a)*norm(b))
For (1,0) and (1,1): 1/sqrt(2) = approximately 0.707
Pipeline: authorized document -> chunks -> embed -> index
          authorized query -> embed -> scoped top-k -> rerank -> evidence
```

Zero norms and mismatched dimensions are rejected rather than silently scored. Ten million 768-dimensional float32 vectors occupy 30.72 GB raw; indexes, text, metadata and replicas add cost. Approximate search trades exact recall for resource efficiency, so I measure recall@k against known relevant chunk IDs.

For “recover access,” a password-reset passage can match semantically. For error code E1042, I also retrieve lexically and fuse/rerank candidates under a defined method; unlike raw scores are not blindly added. Model replacement builds a new index and switches query embedding plus index together. Current source permissions apply before forbidden content reaches a model. Deletion retires chunk IDs/cached evidence, and source revision IDs let the answer cite inspectable text rather than an opaque vector.

### Calculate similarity and storage

For vectors `(1,0)` and `(1,1)`, cosine similarity is `1/(1×sqrt(2)) ≈ 0.707`. A zero vector has no defined cosine direction; handle it explicitly. Mismatched dimensions are an input error, not a score of zero.

Ten million 768-dimensional float32 vectors require `10,000,000×768×4 = 30.72 GB` raw numeric storage, before metadata, text, index edges, replicas and headroom. Approximate nearest-neighbour search trades exact recall for speed/memory; measure retrieval quality on your corpus.

### Mechanism and rationale

**Design question:** Why should a search for "password recovery" find a document titled "reset credentials", and when should it not?

An embedding model maps text to vectors in its learned space. Compare query and document vectors produced by compatible model/preprocessing versions. Cosine similarity compares angle; dot product and Euclidean distance have different normalization assumptions. Nearest neighbors are candidates for relevance, not verified answers.

### Auto-configuration is conditional object creation

A Spring **bean** is an object managed by the application container. **Auto-configuration** creates useful beans when its conditions match: classes are available, properties select that integration and an applicable user-defined bean is absent. These conditions are code, not magic discovery of whichever model happens to be running.

Our default properties are explicit:

```properties
server.address=127.0.0.1
server.port=8096
spring.ai.model.chat=none
spring.ai.model.embedding=none
spring.ai.ollama.init.pull-model-strategy=never
spring.ai.retry.max-attempts=1
```

`spring.ai.model.chat=none` disables matching provider chat auto-configuration; it does not forbid our own `ChatModel` bean. We supply that bean ourselves. Embeddings are disabled because this endpoint does not need them. Model pulling is disabled even when we later select the live profile. The retry setting limits the configured retry template to one attempt; it is not an overall request deadline.

The complete entry point supplies the offline bean and a small guard for explicit live model selection:

```java
package kb.springfundamentals;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Profile;
import org.springframework.util.Assert;

@SpringBootApplication
public class FundamentalsApplication {
    public static void main(String[] args) {
        SpringApplication.run(FundamentalsApplication.class, args);
    }

    @Bean
    @Profile("!ollama")
    FixtureChatModel offlineModel() {
        return new FixtureChatModel();
    }

    @Configuration(proxyBeanMethods = false)
    @Profile("ollama")
    static class RequiredOllamaModel {
        RequiredOllamaModel(@Value("${OLLAMA_CHAT_MODEL}") String modelName) {
            Assert.hasText(modelName, "Set OLLAMA_CHAT_MODEL to an installed chat model name");
        }
    }
}
```

`@SpringBootApplication` starts Boot's configuration and component scanning. `@Bean` registers the fixture. `@Profile("!ollama")` means that bean is present when the `ollama` profile is not active. The live-profile guard requires a nonblank model name; it does not install or contact that model.

For the live branch, the 1.1.8 Ollama auto-configuration can create `OllamaChatModel`. The builder is then injected into our service, which builds its client once; the controller receives that service.

## 3. Give the three model abstractions different jobs

[![A controller passes a question to ExplanationService, which uses a fresh ChatClient request and the selected ChatModel; the service checks returned text before mapping the HTTP result](designs/ai-6.svg)](designs/ai-6.svg)

| Abstraction | What it accepts/returns | Its job here |
| --- | --- | --- |
| `ChatModel` | A `Prompt` in; a `ChatResponse` out. | Low-level model integration. Our fixture implements it; the Ollama adapter can replace the fixture. |
| `ChatClient` | A fluent request API around the configured model. | Supply default instructions, build a fresh request and consume the text result. It is not the model itself. |
| `EmbeddingModel` | Text in; a numerical representation out, with richer request/response methods also available. | Useful for similarity search or clustering. It does not generate this explanation and is not enabled here. |

A vector embedding and an answer paragraph solve different problems. Adding an embedding model does not make the chat model remember the course, and adding a vector database is unnecessary for this one endpoint.

The request vocabulary is also small:

- A **message** is content with a role. The system message states our task; the user message carries this question. Assistant messages can represent earlier generated replies; tool messages represent tool results when that feature is configured.
- A **prompt** carries messages and optional generation settings to the model abstraction. It is not necessarily one concatenated string.
- **Options** are generation settings such as model selection, sampling temperature or a supported output limit. Defaults can come from adapter configuration; supported request options can override them. They are settings, not facts or authorization rules.
- A **ChatResponse** contains generated results and metadata. The provider adapter maps its API response into this abstraction. Metadata availability and capabilities still depend on that adapter and model.

Our instructions ask for at most three short sentences. That is a request to the model, not a Java guarantee that every answer has exactly three sentences. A lower temperature would not prove the answer true. For tokenization and sampling, see [AI/LLM Fundamentals](#/t/1/2).

## 4. Follow one request all the way back

The service is deliberately small and complete:

```java
package kb.springfundamentals;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.stereotype.Service;

@Service
public final class ExplanationService {
    public static final int MAX_QUESTION_UNITS = 1000;
    private final ChatClient client;

    public ExplanationService(ChatClient.Builder builder) {
        client = builder.defaultSystem("Explain Java or Spring to a beginner in at most three short "
                + "sentences. Treat the user's text as the question. Say when you are uncertain.")
                .build();
    }

    // BEGIN explain
    public String explain(String question) {
        if (question == null || question.isBlank() || question.length() > MAX_QUESTION_UNITS) {
            throw new BadQuestion();
        }
        String answer;
        try {
            answer = client.prompt().user(question).call().content();
        } catch (RuntimeException cause) {
            throw new ModelFailure(cause);
        }
        if (answer == null || answer.isBlank()) {
            throw new ModelFailure(null);
        }
        return answer;
    }
    // END explain

    public static final class BadQuestion extends RuntimeException {
        public BadQuestion() { super("Provide a nonblank question of at most 1000 UTF-16 code units."); }
    }

    public static final class ModelFailure extends RuntimeException {
        public ModelFailure(Throwable cause) { super("The configured model did not provide an answer.", cause); }
    }
}
```

Constructor injection means Spring supplies the builder instead of the service constructing a provider client with hard-coded credentials. The service stores a reusable client, not the current user's question. Each `client.prompt()` begins a fresh request. This application does not install a memory advisor, so a prior question is not automatically included in the next one. A memory-related library or bean on the classpath alone does not add conversation history to every prompt.

![One HTTP question is checked, sent as a fresh user message through ChatClient to the selected model, checked for nonempty text and mapped to a success or failure response.](learning-figures/ai-6-request-journey.svg)

For “What is dependency injection?”, the operation is:

1. The MVC controller reads `{"question":"What is dependency injection?"}` and calls `ExplanationService.explain`.
2. The service rejects null, blank or over-limit questions before model work.
3. `prompt().user(question)` creates this request's user message alongside the client's default system instruction.
4. `.call().content()` consumes the synchronous response and invokes the configured model through Spring AI's request path. The fixed fixture returns the labelled answer; a live adapter would perform its provider request here.
5. The service rejects null/blank output, then the controller serializes a small `{"answer":"..."}` result.

The 1,000-unit input guard uses Java's `String.length()`, so its unit is UTF-16 code units. It is a small application guard, **not a model token budget**. The same length of source code, emoji and plain English can tokenize differently. A real provider path needs its own token/context and output limits.

The controller maps a rejected question to HTTP 400 with `INVALID_QUESTION`; an empty answer or model-call failure becomes HTTP 502 with `MODEL_FAILURE`. It returns a fixed public error message rather than exposing the exception's provider diagnostic. Malformed JSON uses Spring's normal input-error handling. No fallback invents an answer after a failed call.

This is a synchronous MVC endpoint, so its request thread waits for the call. It is not a WebFlux event-loop example. More threads do not create provider capacity: before exposing it to other users, add authentication, bounded concurrency, an overall deadline, appropriate provider transport timeouts and a request/spending budget. The loopback fixture demonstrates the integration boundary without claiming those production controls are implemented.

### Diagnose the first broken boundary

| Symptom | Likely boundary and concrete next check |
| --- | --- |
| `ChatClient.Builder` cannot be injected | Check that the appropriate auto-configuration dependency is present and enabled, and that a `ChatModel` can be resolved. Importing the BOM alone adds no starter. |
| More than one candidate `ChatModel` | Check active profiles and extra provider starters/beans. Select the intended model explicitly; use a qualifier/manual builder if the product intentionally has several. |
| Ollama profile fails before startup | Check that `OLLAMA_CHAT_MODEL` is present and nonblank, and verify versioned property names. Do not replace the missing value with an arbitrary model default. |
| Startup succeeds but a request fails | Check backend reachability, installed model name and supported options. Startup with no automatic pull is not a successful inference test. |
| HTTP 400 from this endpoint | Supply a nonblank question within the string-size guard; inspect JSON syntax/content type. No model work is needed for those invalid questions. |
| HTTP 502 from this endpoint | The selected model failed or returned no usable text. Show the fixed failure result; inspect a redacted internal diagnostic. Do not present an invented fallback answer. |
| A fluent but incorrect explanation | The transport and object wiring may work while model quality fails. Evaluate the answer against approved references; changing a bean name will not establish truth. |

Use `mvn dependency:tree` to inspect dependency selection. Start the jar with `--debug` to inspect Boot's condition report when a bean is missing. Read the relevant matched/non-matched condition instead of adding duplicate beans until the error disappears. Keep diagnostic output local and avoid enabling prompt/completion payload logging for private questions.

### What the focused tests establish

The [test source](reference-code/learning/spring-fundamentals/src/test/java/kb/springfundamentals/FundamentalsTest.java) checks the real 1.1.8 libraries and Boot contexts, not a reimplementation of their API:

- The default context has one fixture `ChatModel`, different prototype builder instances and no `EmbeddingModel`. One service request invokes that fixture once.
- Separate questions produce separate prompts with system/user roles; a previous question is not copied into the next one.
- Null, blank and 1,001-unit questions stop before model work; the 1,000-unit boundary is accepted.
- Blank model text and model exceptions become a failure; the controller's public error mapping does not expose the fixture diagnostic.
- An Ollama-profile context binds the named adapter and configured options with pulling disabled. It uses a deliberately unusable local address and never invokes the model. Blank live model selection fails startup.

Those are wiring and application-contract checks. They do not prove that an installed model answers correctly, that a real HTTP request succeeds, or that a deployment has adequate privacy, access control, cancellation, cost or latency limits. The complete local app is a starting point with an honest fixture boundary. Live compatibility and a reviewed answer-evaluation set are separate work before exposing it to learners.

## 6. Interviewer follow-ups

**“Does the starter install or run the model?”** No. It adds Java dependencies and auto-configuration for an integration. Our explicit fixture runs inside Java; the optional Ollama adapter needs a separate backend and installed model. The example disables automatic model pulling.

**“Why have both ChatModel and ChatClient?”** `ChatModel` is the lower-level prompt/response abstraction implemented by an adapter. `ChatClient` adds convenient request construction, defaults and access patterns around it. The service depends on a builder configured with that model; it does not choose a provider inside each method call.

**“Can I add two provider starters and let Spring choose?”** Not safely by assumption. Multiple active model beans can make injection ambiguous. Choose one for this app; if multiple backends are a real requirement, name/qualify them and build the corresponding clients deliberately. Provider capabilities and options still need separate tests.

**“Is the injected builder shared between all services?”** In this pinned auto-configuration it has prototype scope, so each injection gets a distinct builder. Our singleton service builds its client once and creates fresh request specifications per question. That does not create per-user conversation memory or a permission boundary.

**“Why is there no EmbeddingModel bean?”** This task generates an explanation. An embedding encoder would be useful for a separate similarity-search task, and may require a different model and configuration. We keep it disabled instead of enabling an unused backend.

**“The offline test passed. What can I tell the team?”** The pinned application compiled and its six fixture/context tests passed in the recorded build. Do not describe it as a tested live model or production deployment. Report the exact code revision, checks and missing integration/evaluation work.

## 3. Consume one response, then read its text and usage

Here is the actual answer method from the complete service:

```java
public Answer answer(String question) {
    checkQuestion(question);
    ChatResponse response=client.prompt().user(question).call().chatResponse();
    if(response==null || response.getResult()==null || response.getResult().getOutput()==null)
        throw new IllegalStateException("Model returned no answer");
    String text=response.getResult().getOutput().getText();
    if(text==null || text.isBlank()) throw new IllegalStateException("Model returned empty text");
    var usage=response.getMetadata().getUsage();
    boolean known=usage!=null && !(usage instanceof EmptyUsage);
    return new Answer(text,known?usage.getPromptTokens():null,known?usage.getCompletionTokens():null);
}
```

Follow one request through it:

1. Reject blank or oversized input before model work. The example's 2,000-character guard is a Java string-size limit, not a token budget.
2. Build a fresh request with this user message.
3. Consume one `ChatResponse` and reject an absent result or empty text.
4. Read text and usage from that **same object**. The fixture reports 12 input and 8 output tokens. Those numbers are synthetic test data, not a model price or tokenizer result.

An important 1.1.8 detail: `call()` returns a response specification. In the tested implementation, constructing it does not invoke the model; consuming it with `content()`, `chatResponse()` or `entity(...)` performs the model work. It is safer to understand that boundary than to infer execution timing from the method name.

If the application needs only text, `.call().content()` is convenient. If it also needs usage, choose `.call().chatResponse()` and read both from the returned object. Building two separate request chains to get text and then metadata makes two invocations, not one response with two views. Do not reuse a consumed request/response specification as a cache.

Tokens are the model's pieces of text; input tokens include instructions and any supplied history as well as the question. Missing usage must remain **unknown**, not “free”. The service treats the framework's `EmptyUsage` as unavailable metadata. Even when usage is present, provider reporting can differ, and an interrupted stream may never deliver final usage. Cost accounting needs an explicit reconciliation strategy; it cannot be derived reliably from the number of English words in an answer.

### Where does blocking work run?

The ordinary `call()` consumption is synchronous. A WebFlux handler should not block its event-loop thread on that work. A `Mono` represents one eventual result; it does not decide by itself which thread performs the work. The demo endpoint moves the synchronous call to Reactor's bounded worker pool:

```java
@PostMapping("/answer")
Mono<StudyAssistant.Answer> answer(@RequestBody Question request) {
    return Mono.fromCallable(()->assistant.answer(request.text()))
        .subscribeOn(Schedulers.boundedElastic());
}
```

Returning a `Mono` does not by itself make a blocking call non-blocking. `fromCallable` defers the service call, and `subscribeOn` selects the worker used for it. The bounded pool protects event-loop responsiveness; it is not a tenant quota or a limit on provider spending. A production endpoint still needs its own concurrency and request budget.

## 4. Structured output needs parsing and application checks

Suppose the UI wants a study card with a concept and a short list of steps. A Java record gives it an explicit shape:

```java
public record StudyCard(String concept, List<String> steps) {}
```

The service asks Spring AI to convert the answer to that type, then checks the actual application rules:

```java
public StudyCard card(String question) {
    checkQuestion(question);
    StudyCard card=cardClient.prompt().user(question).call().entity(StudyCard.class);
    if(card==null || card.concept()==null || card.concept().isBlank()
            || card.steps()==null || card.steps().isEmpty() || card.steps().size()>8
            || card.steps().stream().anyMatch(s->s==null || s.isBlank()))
        throw new IllegalStateException("Model returned an incomplete study card");
    return new StudyCard(card.concept(),List.copyOf(card.steps()));
}
```

There are three different success conditions:

- **Parseable:** the output can be converted from JSON into the Java type.
- **Acceptable to the application:** the concept is nonblank and there are between one and eight nonblank steps.
- **Educationally correct:** the explanation teaches the concept accurately.

Passing the first does not establish the second or third. The fixture tests parsing and field checks. A real educational assistant also needs a reviewed evaluation set, including wrong answers, unsupported claims and deliberately misleading questions. Valid JSON can contain nonsense.

In 1.1.8, `entity(...)` supports conversion through a structured-output converter. Do not assume that every provider is enforcing a native strict schema just because a Java record was passed. Some configurations use format instructions; native schema support and supported schema features are provider/version-specific. Check that live contract separately.

When both the converted entity and metadata are needed, this tested API performs one invocation:

```java
var combined = client.prompt().user(question).call()
    .responseEntity(StudyCard.class);
var card = combined.entity();
var response = combined.response();
```

Apply the same field checks before using `card`. A malformed response becomes a failed extraction. A bounded repair attempt may be appropriate, but it spends more time and tokens and must remain inside the request budget. Do not silently fill missing facts with invented defaults or retry forever until something parses.

## 5. Streaming changes the meaning of completion

[![A prepared stream starts model work on subscription; received chunks stay provisional until normal completion, while cancellation, error or timeout leaves the answer incomplete.](learning-figures/chatclient-stream.svg)](learning-figures/chatclient-stream.svg)

Open the diagram at full size by selecting it.

Streaming can display the first useful text sooner. It does not necessarily reduce total generation time, token usage or cost. The application receives a sequence of chunks rather than one finished string.

```java
public Flux<String> stream(String question) {
    checkQuestion(question);
    return Flux.defer(()->{
        AtomicBoolean hasText=new AtomicBoolean(); // One flag per subscription, never shared between users.
        return client.prompt().user(question).stream().content()
            .doOnNext(chunk->{if(!chunk.isBlank())hasText.set(true);})
            .timeout(Duration.ofSeconds(20)) // First-chunk/gap deadline; not a total time limit.
            .concatWith(Flux.defer(()->hasText.get()?Flux.empty():Flux.error(new IllegalStateException("Model returned no stream text"))));
    });
}
```

`Flux` is a publisher: it describes a sequence that a subscriber can consume. This method does not call `subscribe()` itself; the web framework subscribes when it serves the response. The demo returns server-sent events (SSE), using `text/event-stream` to send events over one HTTP response.

The outer `Flux.defer` creates a fresh request chain for each subscription. That matters for this pinned version: the raw response specification's advisor chain is consumed during execution and should not be reused across subscriptions. The tests cover both that version-specific trap and the safe wrapper. Repeated subscriptions to the safe wrapper still perform new model work; they are not free replays.

The 20-second `timeout` covers the wait for the first chunk and the gap between chunks. It is **not** a total generation deadline. A provider that emits regularly can continue much longer. The per-subscription `hasText` flag also rejects normal completion with no text, metadata-only responses or whitespace alone; an already completed empty publisher would not trigger an idle timeout. Production code still needs an overall deadline, an output-size/token limit and a cancellation policy. Provider HTTP connection/read settings must fit those budgets.

Consider a user closing the page after receiving “Encapsulation means…”. Cancellation should propagate upstream, and the fixture test verifies that it does. The application must label the saved text incomplete. Local cancellation does not prove a remote provider stopped generating or stopped billing; that depends on its API and client behavior.

Once SSE chunks have been sent, the server cannot replace the already-sent HTTP 200 with a new error status. A real client/server protocol should carry a final completion or failure event and preserve partial text honestly. The demo exposes the raw framework stream; a production event envelope, reconnection/replay policy and persistent conversation storage are explicit extensions, not hidden guarantees of `ChatClient`.

### What belongs around the client in a real service?

The chosen application boundary remains small: authenticated request → input/quota checks → `StudyAssistant` → configured model → result validation → safe response. If retrieval, tools or memory are added, their own authorization and failure rules enter that path.

An advisor wraps or enriches execution, for example by adding approved retrieval context or memory. It does not make untrusted text safe automatically. A system instruction is guidance, not a security boundary. Retrieved documents, tool arguments and model-produced links remain untrusted. Enforce access checks in Java, expose only narrow tools, require product approval for side effects and escape output before inserting it into HTML.

Record request IDs, model/version, latency, completion state, available token usage and error category. Avoid logging full student questions or retrieved private documents by default. In this pinned version, the converter's error logger can include rejected output; review framework logging as well as your own code before live use. Choose retention deliberately. Log enough to diagnose an empty answer or failed extraction without turning logs into a second private conversation store.

## 6. Interviewer follow-ups

**Why use `ChatClient` instead of calling `ChatModel` directly?** A direct model call is reasonable for a tiny adapter. `ChatClient` adds convenient request construction, defaults, advisors, conversion and streaming access. Choose it for those application needs, while keeping the provider behind the model abstraction and testing the behavior actually used.

**Is a shared client the same as shared conversation memory?** No. Defaults can be shared, but each request should be fresh. Memory is an explicitly configured feature with an authorized conversation identity. Never accept another user's conversation ID just because it was supplied in a request.

**Should every model error be retried?** No. Bad credentials and unsupported options need configuration fixes. Rate limits and transient transport failures may justify bounded retries with backoff. An unknown remote outcome or a tool side effect needs reconciliation/idempotency, not blind replay. Retrying after partial stream output can duplicate visible text or actions.

**Does structured output prevent prompt injection?** No. It can constrain shape, depending on the provider configuration, but malicious or misleading content can still fit that shape. Validate domain values, authorize tools and keep retrieved/user text from acquiring application authority.

**What proves this is ready for real students?** The tests establish the Java/framework contract. Readiness also needs a reviewed concept-answer evaluation set, live-provider compatibility, privacy controls, cost/latency budgets and user-facing handling of incomplete answers. I would not use a successful mocked call as evidence for those separate claims.

## 7. Closing answer

“I would keep a small application service around a configured ChatModel and use ChatClient to build fresh requests. I would consume one response for text and metadata, validate structured results beyond JSON shape, and treat streams as incomplete until normal completion. The pinned offline example proves the framework path without paid calls; live-provider quality, security and operational budgets are separate checks before exposing it to students.”
