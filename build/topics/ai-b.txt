## Problem

Explain how to get reliable, typed, structured output from LLMs in Java: mapping responses to POJOs or records, JSON schema and native structured-output modes, validating results, and handling the failures (malformed JSON, missing fields, wrong enums) with retries, using Spring AI's output converters and `.entity()`.

## Requirements

- Why free text is a poor integration contract.
- Spring AI's `BeanOutputConverter`, `ListOutputConverter`, `MapOutputConverter` and `.entity()`.
- Provider-native JSON or structured-output modes vs. prompt-based format instructions.
- Validation (Jakarta Bean Validation), retry-with-feedback, and fallbacks.

## Key concepts and learning objective

**Question to answer:** How can model output become a reliable application object instead of fragile text parsing?

There are three separate checks: syntactic JSON validity, schema conformance and business correctness. Native provider schemas can constrain format when supported; framework converters can guide/parse output but cannot prove that a cited document exists or that an amount is valid.

Read this as a system-building exercise, not a glossary to memorize. The running example is an authenticated documentation assistant: it receives a question, finds permitted evidence, answers with source identifiers, and optionally looks up live business data through a narrow read-only tool. Every added component must solve an observed limitation of the simpler version. Begin with a deterministic baseline so that a model is used where language interpretation helps rather than for arithmetic, authorization or database invariants.

## Architecture and contracts

```text
Task + schema -> provider -> parse -> schema/type validation -> domain invariants -> accept, bounded repair or reject

Application contracts (design outline):
SupportAnswer(summary,List<Citation>,needsHuman); Citation(sourceId,quote); ValidationResult(errors)
```

Use Java records for DTOs, entity(YourRecord.class) or an explicit converter, then Bean Validation/application checks. Treat code fragments as integration sketches unless included in the runnable examples project.

Separate policy from integration. Identity, permitted evidence, operation state and budgets belong to the application. The model proposes text or actions; its proposal is not proof of a business fact or permission. Preserve input/source/model/prompt versions so that a bad answer can be reproduced without relying on whichever provider default exists later. Keep the distinction between raw conversation history, the selected prompt context and provider-side caching explicit.

## Worked reasoning and capacity example

If 2% of 10,000 daily responses fail parsing, there are 200 repair candidates. One repair attempt adds up to 200 extra calls/day, and still needs a terminal failure policy. Measure cost and correctness rather than retrying until something parses.

Treat every number here as an illustrative assumption unless it is a unit conversion. A context window is a model-specific token limit, not a fixed page/word count. ## Failure scenario and safe recovery

The response is valid JSON but invents an authorized-looking order ID. Resolve identifiers against the authenticated repository before any action. Never let a successful entity() conversion directly trigger a refund.

Classify the stage that failed. A retrieval miss, unauthorized document, provider timeout, malformed schema, invalid business value and failed external side effect need different handling. Do not turn every exception into a vague “please retry” message. Before retrying, determine whether anything irreversible or billable may already have happened and reuse the original operation identity where the downstream contract supports it.

| Stage | Example symptom | Required response |
|---|---|---|
| Input/context | Oversized or unauthorized material | Reject or reduce before sending it to a model |
| Retrieval | No permitted supporting evidence | Ask for clarification or abstain; do not fabricate a citation |
| Provider | Timeout, throttling or unavailable capability | Bounded retry/fallback under the same run budget |

| Business validation | Invented ID or inconsistent amount | Reject independent of how fluent the answer sounds |

Cancellation should propagate through long streams, search calls and tools where supported. Persist necessary workflow state before acknowledging a pending action. When the deadline expires, return an honest partial/incomplete outcome with the evidence already established; do not let a model invent successful completion to make the response sound finished.

## Security, privacy and provenance

A schema can describe the shape of a tool argument but not establish the caller’s authority to use that argument.

User text, retrieved passages, file contents, tool descriptions and tool results can all contain hostile instructions. Label their origin and keep them as data. Security comes from deterministic resource authorization, narrow capabilities, bounded execution and controlled destinations, with model-oriented guardrails as an additional imperfect layer. A model can request an operation; only the application can authorize and execute it.

Scope evidence, caches and conversation keys by tenant and authenticated user. A high similarity score cannot justify sharing a cached answer from another tenant. Propagate source updates, permission revocations and deletions into indexes and derived summaries under a documented lifecycle policy. Keep citations to stable source revisions so an answer can be checked against the material actually used.

Log trace IDs, operation identities, model/prompt/index versions, counts, durations and validated failure categories by default. Raw prompts, provider tokens, signed URLs and private passages need explicit handling and retention, not indiscriminate debug logging. A secret removed from the final answer can still have leaked through a tool request or a log before that answer was produced.

```java
  String status(String orderId) { return orders.statusForCurrentPrincipal(orderId); }
}
// AuthorizedOrders is an application port, not a model-provided identity.
```

Keep request-specific state out of singleton bean fields. Construct a fresh request specification, derive identity from the authenticated request and pass only authorized bounded data to adapters. Place credentials in environment/secret configuration, never in an example prompt, source file or response. When an API supports multiple result forms, choose the one that retains the metadata needed for this use case instead of discarding finish reason/usage by default.

A minimal application test injects a deterministic model/tool adapter with scripted outputs. That test checks wiring, state, authorization and validation without paying for a provider call. A separate integration test checks the pinned SDK/API shape. A quality evaluation checks whether real model outputs satisfy a versioned task rubric. These are three different kinds of evidence; passing one does not prove the others.

## Design decisions and alternatives

Begin with read-only lookup tools. Side effects need operation IDs and a review/confirmation policy appropriate to the action. Descriptions should explain inputs and output semantics but cannot grant permissions.

Compare the added mechanism with the simplest baseline on the same inputs. Keep changes attributable: prompt text, model version, chunker, index settings, reranker and tool policy should not all change at once. Document which guarantee the new layer buys and which failure modes it introduces. A framework abstracts common plumbing, while provider-specific support for tools, streaming, schemas, context limits and data residency still needs explicit capability checks.

Prefer a fixed workflow when the task has a stable sequence of steps. If an agent selects actions, bound model calls, tool calls, result bytes, elapsed time and spend. For independent subtasks, parallelism can reduce wall-clock latency but increases simultaneous quota use and may increase total cost. Do not hand every tool and every document to every worker simply because they are available.

## Failure scenario and safe recovery

A malicious user asks for another account’s order and provides a plausible userId argument. The tool ignores model-supplied identity and checks order ownership using the authenticated context.

Classify the stage that failed. A retrieval miss, unauthorized document, provider timeout, malformed schema, invalid business value and failed external side effect need different handling. Do not turn every exception into a vague “please retry” message. Before retrying, determine whether anything irreversible or billable may already have happened and reuse the original operation identity where the downstream contract supports it.

| Stage | Example symptom | Required response |
|---|---|---|
| Input/context | Oversized or unauthorized material | Reject or reduce before sending it to a model |
| Retrieval | No permitted supporting evidence | Ask for clarification or abstain; do not fabricate a citation |
| Provider | Timeout, throttling or unavailable capability | Bounded retry/fallback under the same run budget |
| Parsing | Incomplete or invalid structure | Bounded repair or explicit validation failure |
| Business validation | Invented ID or inconsistent amount | Reject independent of how fluent the answer sounds |
| Tool effect | Timeout after possible completion | Query/reconcile operation identity before another action |

Cancellation should propagate through long streams, search calls and tools where supported. Persist necessary workflow state before acknowledging a pending action. When the deadline expires, return an honest partial/incomplete outcome with the evidence already established; do not let a model invent successful completion to make the response sound finished.

## Security, privacy and provenance

A read-only label is descriptive metadata. Enforce read-only behavior in the implementation and database credentials.

User text, retrieved passages, file contents, tool descriptions and tool results can all contain hostile instructions. Label their origin and keep them as data. Security comes from deterministic resource authorization, narrow capabilities, bounded execution and controlled destinations, with model-oriented guardrails as an additional imperfect layer. A model can request an operation; only the application can authorize and execute it.

Scope evidence, caches and conversation keys by tenant and authenticated user. A high similarity score cannot justify sharing a cached answer from another tenant. Propagate source updates, permission revocations and deletions into indexes and derived summaries under a documented lifecycle policy. Keep citations to stable source revisions so an answer can be checked against the material actually used.

Log trace IDs, operation identities, model/prompt/index versions, counts, durations and validated failure categories by default. Raw prompts, provider tokens, signed URLs and private passages need explicit handling and retention, not indiscriminate debug logging. A secret removed from the final answer can still have leaked through a tool request or a log before that answer was produced.

## Hands-on lab and evaluation

**Build:** Implement a read-only stock/order tool; test nonexistent IDs, foreign-tenant IDs, oversized arguments, duplicate calls and a provider timeout following a completed tool.

**Measure:** Task success, correct tool selection, unauthorized attempts blocked, argument validity, duplicate effects and tool latency/error classification.

Create a versioned fixture set containing representative supported questions, missing-evidence questions, ambiguous requests and adversarial inputs. State expected evidence and permitted behavior before running the model. Include at least one case in which the correct behavior is to ask for clarification, refuse access, or stop at a budget rather than return a polished answer. Keep development/few-shot examples separate from the held-out set.

Record per-case outcomes and compare against the baseline. Exact tests work for identifiers, schema constraints, authorization and conservation rules. Human/calibrated rubric checks are useful for relevance and evidence support, but a model judge can prefer fluent unsupported prose. Preserve disagreements and evaluate by tenant/language/document type instead of hiding them in one aggregate score. Report dataset size and limitations rather than promising a universal accuracy percentage.

## Follow-up questions with explained answers

**What does the model actually contribute?** The model proposes a tool name and arguments. The application validates schema, derives authenticated identity, authorizes the resource and executes the tool. Tool result text returns as untrusted data for a later model step; the model never becomes the security principal.

**What belongs in application code?** The contracts and policies around OrderLookup(orderId); ToolContext(tenant,user,requestId); ToolResult(status,data,errorCode). In particular, identity and permission cannot come from a generated argument.

**What is the important trade-off?** Begin with read-only lookup tools. Side effects need operation IDs and a review/confirmation policy appropriate to the action. Descriptions should explain inputs and output semantics but cannot grant permissions.

**What breaks the naive implementation?** A malicious user asks for another account’s order and provides a plausible userId argument. The tool ignores model-supplied identity and checks order ownership using the authenticated context.

**How would you test the fix?** Task success, correct tool selection, unauthorized attempts blocked, argument validity, duplicate effects and tool latency/error classification. Use scripted failures for deterministic checks and a separate versioned corpus for model quality.

Close the exercise by tracing the input, authorized evidence, proposed output/action and final validation result. Point to the run budget and the stop condition. If you cannot identify who enforces authority, what supports each factual claim and how the workflow terminates, the design is still a demonstration rather than a dependable product feature.
