## Problem

Explain how to get reliable, typed, structured output from LLMs in Java: mapping responses to POJOs or records, JSON schema and native structured-output modes, validating results, and handling the failures (malformed JSON, missing fields, wrong enums) with retries, using Spring AI's output converters and `.entity()`.

## Requirements

- Why free text is a poor integration contract.
- Spring AI's `BeanOutputConverter`, `ListOutputConverter`, `MapOutputConverter` and `.entity()`.
- Provider-native JSON or structured-output modes vs. prompt-based format instructions.
- Validation (Jakarta Bean Validation), retry-with-feedback, and fallbacks.

## Key concepts

```java
record LoanDecision(
    @NotNull Decision decision,          // enum APPROVE, REJECT, REFER
    @Min(0) @Max(100) int riskScore,
    @NotBlank String reason,
    List<String> missingDocuments) {}

LoanDecision d = chatClient.prompt()
    .system("Assess the application against the policy. Output only the requested JSON.")
    .user(applicationText)
    .call()
    .entity(LoanDecision.class);   // schema derived from the record, response parsed

List<String> tags = chatClient.prompt().user("5 tags for: " + text)
    .call().entity(new ParameterizedTypeReference<List<String>>() {});
```

| Approach | How it works | Reliability |
|---|---|---|
| Format instructions in the prompt | Converter appends a JSON schema + "respond only with JSON" | Good; occasional prose or markdown fences |
| Native JSON mode / structured outputs | Provider constrains decoding to valid JSON or a schema | Very high syntactic validity |
| Tool/function calling as output | Model "calls" a function whose args are your schema | High; widely supported |

## Design decisions & trade-offs

1. **Prefer records with enums.** Enums constrain categorical answers. Records give immutable, schema-friendly types. Keep schemas small and flat. Deep nesting raises error rates.
2. **Syntactic vs. semantic validity.** Native structured output guarantees valid *JSON*, not valid *content*. Always run Bean Validation plus business rules (a risk score consistent with the decision).
3. **Retry with feedback.** On a parse or validation failure, re-ask once or twice, including the error ("riskScore must be 0–100; you returned 140"). Cap retries and then fall back (`REFER` to a human).
4. **Field descriptions help.** Annotate fields (`@JsonPropertyDescription`) so the generated schema explains intent. That's cheaper than long prompt prose.
5. **Streaming conflict.** You can't validate partial JSON. Use blocking calls for structured output, or stream and validate at the end.
6. **Version your schemas.** Downstream consumers depend on them. Treat changes like API changes.

## Problem

Explain conversation memory for LLM apps: LLMs are stateless, so "memory" means deciding what past conversation (and long-term user facts) to send with each request. Cover Spring AI's `ChatMemory`, conversation IDs, persistence, window and summarisation strategies, and managing the context budget.

## Requirements

- Why the model "forgets", and where memory actually lives (your app).
- Short-term (conversation) vs. long-term (user facts, preferences) memory.
- Spring AI: `ChatMemory`, `MessageWindowChatMemory`, chat memory repositories (in-memory, JDBC, Cassandra, Neo4j), memory advisors.
- Conversation IDs, multi-user isolation, persistence, retention.
- Context-window management: windowing, summarisation, retrieval-based memory.

## Key concepts

```java
@Bean
ChatMemory chatMemory(JdbcChatMemoryRepository repo) {
  return MessageWindowChatMemory.builder()
      .chatMemoryRepository(repo)       // persisted across restarts / instances
      .maxMessages(20)
      .build();
}

String reply = chatClient.prompt()
    .advisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
    .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, userId + ":" + sessionId))
    .user(message)
    .call().content();
```

| Strategy | How | Trade-off |
|---|---|---|
| **Full history** | Send everything | Simple; explodes cost and hits the context limit |
| **Sliding window** | Last N messages | Cheap; forgets early facts |
| **Summary + window** | Summarise older turns into a running summary | Keeps the gist; summaries lose detail and cost a call |
| **Vector memory** | Embed past turns, retrieve relevant ones | Scales to long histories; retrieval may miss |
| **Structured profile** | Extracted facts (name, preferences) stored as data | Precise and auditable; needs extraction logic |

## Design decisions & trade-offs

1. **Conversation ID design.** Scope it as `tenant:user:session`. Never let IDs collide or be guessable, or one user's history leaks into another's prompt.
2. **Persist outside the JVM.** In-memory memory breaks with multiple instances and restarts. Use JDBC or Redis repositories in production.
3. **Message advisor vs. prompt advisor.** `MessageChatMemoryAdvisor` adds history as real messages (best fidelity). `PromptChatMemoryAdvisor` injects history as text into the system prompt (works with models that handle messages poorly). `VectorStoreChatMemoryAdvisor` retrieves relevant past turns.
4. **Budget the context.** Reserve tokens for system prompt + RAG context + history + answer. When history overflows, summarise or drop. Don't silently truncate the middle of a message.
5. **Privacy and retention.** Memory stores personal data. Apply retention TTLs, deletion on request, encryption at rest, and avoid storing secrets the user pasted.
6. **Long-term memory is a product decision.** Remembering facts across sessions needs user consent, visibility ("what do you remember about me?") and edit/delete controls.

3. How do you prevent one user's memory from leaking into another's?

## Requirements

- Index types (HNSW, IVF) and their trade-offs.
- Metadata filtering and why it's essential (multi-tenancy, ACLs, freshness).

## Key concepts

```java
vectorStore.add(List.of(new Document(chunkText,
    Map.of("source", "policy.pdf", "dept", "HR", "version", 3))));

List<Document> hits = vectorStore.similaritySearch(SearchRequest.builder()
    .query("parental leave policy")
    .topK(6)
```

| Store | Strengths | Watch out for |
|---|---|---|
| **PGVector** | It's Postgres: transactions, joins, SQL filters, existing ops and backups; HNSW/IVFFlat | Very large scale needs tuning; vector and OLTP workloads compete |
| **Redis** | Very low latency, already in many stacks | Memory cost at large scale |
| **Elasticsearch / OpenSearch** | Hybrid BM25 + kNN in one engine, rich filters, ops maturity | Heavier to run; JVM tuning |
| **Dedicated (Pinecone, Qdrant, Weaviate, Milvus)** | Built for vectors: scale, filtering, quantisation | Another system to secure, govern and pay for |

## Design decisions & trade-offs

1. **Start with what you operate.** For most enterprise Java teams, PGVector (if Postgres is standard) or OpenSearch (if search already exists) wins on governance, security reviews and backups. Move to a dedicated store when scale or latency demands it.
2. **Filtering semantics.** Pre-filtering (apply the filter, then ANN) is exact but can be slow or have low recall with HNSW. Post-filtering (ANN, then filter) can return fewer than k results. Know which your store does. Highly selective filters (one tenant among 10k) may need per-tenant indexes or partitions.
3. **Metadata design.** Store source, page, section, tenant, ACL groups, language, version and timestamps. Filters enforce access control and freshness. They're your RAG security boundary.
4. **Updates and deletes.** Use stable chunk IDs (`docId#chunkN`) so re-ingestion replaces rather than duplicates. Deleting a document must delete all its chunks.
5. **Index tuning.** HNSW `m` and `ef_construction` trade build time and memory for recall. `ef_search` trades latency for recall per query. Measure recall@k on your data.
6. **Capacity.** Vectors × dimensions × 4 bytes, plus index overhead (often 1.5–2×). Quantisation (int8, binary) cuts memory at some recall cost.

## Problem

Take RAG from demo to production: the techniques that move answer quality from "sometimes right" to dependable. That means smarter chunking with metadata, hybrid search, re-ranking, query rewriting and expansion, context compression, freshness and access control, and evaluation-driven tuning, plus how Spring AI's modular RAG components map onto them.

## Requirements

- Advanced chunking (structure-aware, parent-child, contextual headers).
- Hybrid lexical + semantic retrieval and rank fusion.
- Re-ranking with cross-encoders or LLM rankers.
- Query transformation: rewriting, multi-query, HyDE, conversational compression.
- Operational concerns: incremental ingestion, dedup, ACLs, evals and monitoring.

## Key concepts

| Technique | Problem it fixes |
|---|---|
| **Structure-aware chunking** | Splits at headings and paragraphs; keeps tables whole; prepends "Doc › Section" to each chunk |
| **Parent-child (small-to-big)** | Retrieve small precise chunks, send their larger parent section to the LLM |
| **Hybrid search + RRF** | Vectors miss exact IDs; BM25 misses paraphrases. Reciprocal Rank Fusion: `score = Σ 1/(k + rank_i)` |
| **Re-ranking** | Retrieve 50 cheaply, then a cross-encoder scores (query, chunk) pairs accurately and keeps the top 5 |
| **Query rewriting** | Turns "what about for contractors?" into a standalone query using chat history |
| **Multi-query / HyDE** | Several rephrasings, or a hypothetical answer, embedded to improve recall |
| **Context compression** | Trim retrieved chunks to the relevant sentences, saving tokens |

```java
Advisor rag = RetrievalAugmentationAdvisor.builder()
    .queryTransformers(RewriteQueryTransformer.builder().chatClientBuilder(builder.build().mutate()).build())
    .queryExpander(MultiQueryExpander.builder().chatClientBuilder(builder.build().mutate()).numberOfQueries(3).build())
    .documentRetriever(VectorStoreDocumentRetriever.builder()
        .vectorStore(vectorStore).similarityThreshold(0.6).topK(20).build())
    .build();
```

## Design decisions & trade-offs

1. **Measure before adding complexity.** Build a golden set (≥100 real questions with the expected source docs and answers). Track retrieval recall@k, MRR, answer faithfulness and correctness. Each technique must earn its latency and cost.
2. **Hybrid is the default for enterprise text.** Policies, codes, product names and acronyms need lexical matching. Fuse with RRF (rank-based, so there's no need to normalise scores).
3. **Re-ranking costs latency.** A cross-encoder over 50 candidates adds ~50–200 ms. It's usually the single biggest quality win after chunking.
4. **Query rewriting in multi-turn chat.** Follow-up questions are ambiguous without history, so rewrite them into standalone queries before retrieval.
5. **Ingestion is a pipeline, not a script.** Incremental updates via change detection (hashes), deletes propagate, versions are tracked, PII is handled, and failures are retried and alerted.
6. **Security.** Filter by user entitlements *at retrieval time*, never after generation. Sanitise documents for injected instructions.

## Problem

Explain Spring AI advisors, the interceptor or middleware chain around every `ChatClient` call: how they modify requests and responses, how ordering works, the built-in advisors (memory, RAG, logging, safeguards), and how to write custom advisors for concerns like PII redaction, auditing, caching and guardrails.

## Requirements

- The advisor concept (Chain of Responsibility / around-advice) and the request → model → response flow.
- Built-ins: `MessageChatMemoryAdvisor`, `PromptChatMemoryAdvisor`, `QuestionAnswerAdvisor`, `RetrievalAugmentationAdvisor`, `SimpleLoggerAdvisor`, `SafeGuardAdvisor`.
- Ordering via `getOrder()`, and sharing data between advisors via the advisor context.
- Writing custom `CallAdvisor` / `StreamAdvisor` implementations.

## Key concepts

```java
public class PiiRedactionAdvisor implements CallAdvisor {
  public String getName() { return "piiRedaction"; }
  public int getOrder() { return Ordered.HIGHEST_PRECEDENCE + 100; }   // run early

  public ChatClientResponse adviseCall(ChatClientRequest req, CallAdvisorChain chain) {
    ChatClientRequest redacted = req.mutate()
        .prompt(req.prompt().augmentUserMessage(m -> m.mutate()
            .text(Redactor.mask(m.getText())).build()))
        .build();
    ChatClientResponse resp = chain.nextCall(redacted);   // continue the chain
    audit.log(redacted, resp);                            // after-processing
    return resp;
  }
}
```

| Concern | As an advisor? |
|---|---|
| Memory, RAG context injection | Yes (built in) |
| Logging, auditing, token metrics | Yes (outermost) |
| PII redaction, input guardrails | Yes (early, before memory/RAG persist anything) |
| Response caching | Yes (short-circuit the chain on a hit) |
| Business logic decisions | Usually no; keep that in services |

## Design decisions & trade-offs

1. **Ordering is semantics.** Lower order runs first on the request and last on the response. Redaction must run before memory stores the message, or raw PII lands in your chat history. Logging outermost sees the final request. Make orders explicit constants.
2. **Request-scoped parameters.** Pass per-call data (conversation ID, filter expression, user ID) through advisor params, not thread-locals. It works with streaming and async.
3. **Streaming support.** Implement `StreamAdvisor` too if the advisor must work with `.stream()`. Response-side logic for streams operates on `Flux`, aggregating when you need the whole answer.
4. **Short-circuiting.** Advisors can return without calling the model (cache hit, guardrail block). That's powerful, but log it clearly to avoid "why didn't the model answer?" confusion.
5. **Cross-cutting, not core.** Advisors are like servlet filters or AOP for AI calls. Overloading them with business rules makes behaviour hard to follow.

## Problem

Explain tool (function) calling: how an LLM requests the execution of your code with structured arguments, how the application runs the tool and feeds the result back, how Spring AI exposes Java methods as tools (`@Tool`, `ToolCallback`, `ToolContext`), and how to make tool use safe in an enterprise (authorisation, validation, side effects).

## Requirements

- The tool-calling loop: the model returns `tool_calls`, the app executes, a tool result message goes back, the model writes the final answer.
- Defining tools in Spring AI: `@Tool` methods, `@ToolParam` descriptions, `.tools(...)` / `defaultTools`.
- Passing hidden context (user identity) with `ToolContext`.
- Read vs. write tools, confirmations, idempotency, errors and timeouts.
- Security: least privilege, never trusting model-supplied arguments blindly.

## Key concepts

```java
class AccountTools {
  @Tool(description = "Get the current balance for one of the caller's accounts")
  BigDecimal getBalance(@ToolParam(description = "Account id, e.g. ACC-123") String accountId,
                        ToolContext ctx) {
    String userId = (String) ctx.getContext().get("userId");     // from the server, not the model
    accessPolicy.assertOwns(userId, accountId);                   // authorisation in code
    return accounts.balance(accountId);
  }
}

String answer = chatClient.prompt()
    .user("What's the balance on ACC-123?")
    .tools(new AccountTools())
    .toolContext(Map.of("userId", currentUser.id()))
    .call().content();
```

**The loop:** Spring AI sends tool schemas (name, description, JSON schema of parameters). The model replies with a tool call. Spring AI invokes the method, appends the result, and calls the model again, repeating until a final text answer.

## Design decisions & trade-offs

1. **Descriptions are the API.** The model chooses tools from their names and descriptions. Make them specific ("for the caller's own accounts only"), with typed, well-described parameters. Too many similar tools confuse selection; group or route instead.
2. **Authorisation lives in your code.** The model can be manipulated (prompt injection) into passing someone else's account ID. Identity comes from `ToolContext` or the security context, never from model arguments, and every tool checks entitlements.
3. **Read vs. write tools.** Read-only tools can run automatically. State-changing tools (transfer money, send email) need explicit user confirmation (human-in-the-loop), idempotency keys and audit logs.
4. **Return compact, structured results.** Tool output goes back into the context. Return the fields needed, not 5 MB of JSON. Errors should be informative but safe ("account not found", not stack traces).
5. **Bound the loop.** Cap tool iterations, set per-tool timeouts, and handle partial failures. Otherwise a confused model can loop and burn tokens.
6. **Direct return.** Some tools' results should go straight to the user (`returnDirect`) without another model pass. That saves cost and avoids rephrasing errors.
