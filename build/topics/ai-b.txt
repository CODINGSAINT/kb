## Problem

Explain how to get reliable, typed, structured output from LLMs in Java: mapping responses to POJOs or records, JSON schema and native structured-output modes, validating results, and handling the failures (malformed JSON, missing fields, wrong enums) with retries, using Spring AI's output converters and `.entity()`.

## Requirements

- Why free text is a poor integration contract.
- Spring AI's `BeanOutputConverter`, `ListOutputConverter`, `MapOutputConverter` and `.entity()`.
- Provider-native JSON or structured-output modes vs. prompt-based format instructions.
- Validation (Jakarta Bean Validation), retry-with-feedback, and fallbacks.

## 1. Selected structured-output design

I classify support tickets into an allow-listed category and summary, returning a review flag when evidence is incomplete. I use ChatClient DTO conversion and provider schema support when available. Deterministic code enforces the domain contract after generation.

## 2. DTO and validation algorithm

```java
record Classification(String category, String summary, boolean needsReview) {}
Classification value = client.prompt().user(ticketText)
    .call().entity(Classification.class);
```

The application checks non-null required fields, an allowed category, summary length and evidence rules. An invalid category is rejected even when JSON parsed successfully. Unknown dates remain null/unknown under the explicit schema rather than defaulting to today. The API returns `VALID`, `NEEDS_REVIEW` or `CONTRACT_FAILURE`; it does not silently treat malformed output as an empty success.

I allow one syntax-repair attempt within the same budget and then fail visibly. Critical unsupported decisions do not gain authority through repair. Contract versions are stored with results, and deployments compare a fixed corpus containing malformed, missing, oversized and semantically invalid cases. A model-generated `refundApproved=true` cannot bypass the separate refund service's eligibility and permission checks.

**Design question:** How can model output become a reliable application object instead of fragile text parsing?

## 1. Selected memory model

I resolve the submitted ID against authenticated ownership, acquire the conversation turn lease/version, select bounded history and call the model. ## 5. Detailed decisions, algorithms and failure behaviour

### Mechanism and rationale

**Design question:** How can a chat remember prior turns without leaking another user’s conversation or exhausting context?

Persisted conversation history is application state. Each model request includes a selected view of it; provider-side caches do not replace this store. Window memory drops old turns; summaries compress them; retrieval can recover relevant past facts but adds ranking and privacy concerns.

### Architecture and contracts


A chat-memory advisor can select and insert messages, but the application must authorize the conversation before invoking it. Use the API matching the pinned Spring AI baseline; newer session APIs have different names.

### Worked reasoning and capacity example

Twenty turns averaging 500 tokens each already consume 10,000 tokens before task instructions, retrieval and output allowance. Summaries should have their own budget and revision, not grow without bound.

### Design decisions and alternatives

Key memory by tenant plus authenticated user plus conversation, not a user-supplied conversation ID alone. Store raw history separately from derived summaries, with deletion and retention rules for each.

Two tabs append to one conversation concurrently. Sequence or version the append, and build the response against a known history snapshot. A tool result must match the tool call that produced it; dropping one half creates invalid context.

A summary generated by an LLM can turn uncertainty into a false permanent fact. Keep provenance and allow users to correct retained information.


**Verification criteria:** Measure cross-user leakage, retained facts, summary drift, context tokens and correctness after truncation. Use adversarial conversations that try to claim another tenant’s identity.

Explain Spring AI advisors, the interceptor or middleware chain around every `ChatClient` call: how they modify requests and responses, how ordering works, the built-in advisors (memory, RAG, logging, safeguards), and how to write custom advisors for concerns like PII redaction, auditing, caching and guardrails.

## Requirements

- The advisor concept (Chain of Responsibility / around-advice) and the request → model → response flow.
- Built-ins: `MessageChatMemoryAdvisor`, `PromptChatMemoryAdvisor`, `QuestionAnswerAdvisor`, `RetrievalAugmentationAdvisor`, `SimpleLoggerAdvisor`, `SafeGuardAdvisor`.
- Ordering via `getOrder()`, and sharing data between advisors via the advisor context.
- Writing custom `CallAdvisor` / `StreamAdvisor` implementations.

## 1. Selected advisor composition

I use the pinned Spring AI 1.1 family to compose memory, authorized retrieval and observation around one ChatClient boundary. Application code resolves principal/conversation before advisor execution. Each component receives immutable request-scoped policy; singleton advisors do not hold mutable per-user state.

## 2. Ordering and request contract

```text
ApplicationContext: principal,ownedConversation,evidenceScope,remainingBudget
Effective order: memory selection -> scoped retrieval -> final context check
                -> model -> output validation/telemetry
Memory output: bounded messages; retrieval output: source IDs/revisions/spans
```

I configure and verify ordering using the selected API's ordering contract rather than assuming registration order is always execution order. The final budget check matters because a prior 4,000-token check becomes obsolete if memory adds 3,000 and retrieval adds 8,000 later. Token contributions are attributed to their components.

The same advisor chain is tested with two concurrent users and distinguishable history/evidence. Any cross-request state fails isolation. Retry re-entry cannot duplicate memory writes or business effects; completed-turn persistence stays in the application workflow. Observation records versions, latency and usage with redaction, not unrestricted prompt bodies. This composition reduces duplicated endpoint integration while keeping ownership and failure transitions visible.

### Build a chain you can explain

Write an input/output table before adding advisors: memory receives an owned conversation identity and returns selected messages; retrieval receives an authorized query and returns versioned passages; telemetry records metadata with redacted content. Avoid keeping request-specific mutable data on a singleton advisor instance.

```text
Request context:
  principal: application-owned, never model-generated
  conversation: resolved and authorized before memory lookup
  evidence: source IDs and current access scope
  budget: remaining tokens and deadline after all augmentation
```

## 5. Detailed decisions, algorithms and failure behaviour

### Mechanism and rationale

**Design question:** Where should cross-cutting prompt transformations live without making their order invisible?

Advisors wrap the model interaction and can transform requests and responses. Their order determines whether logging sees raw or redacted text, whether memory precedes retrieval and which errors are visible. A call path and a streaming path may have different contracts.

### Architecture and contracts

```text
Authorization before client -> redaction/budget policy -> memory/context enrichment -> model/tool execution -> output validation -> redacted observations

Application contracts (design outline):
AdvisorPolicy(order,requestTransform,responseTransform); RequestContext(tenant,traceId,budget); ValidatedResponse
```

Use the CallAdvisor/StreamAdvisor interfaces for the selected release and call the next chain exactly as its contract requires. Interface signatures are version-sensitive; the manuscript distinguishes conceptual sequence from compilable example code.

### Worked reasoning and capacity example

Three sequential enrichment calls at 100 ms each add at least 300 ms before the model begins. Parallelize only truly independent authorized work; do not hide this latency behind an innocuous advisor name.

### Java and Spring AI implementation outline

```java
// Conceptual chain; adapt actual interfaces to the pinned Spring AI release.
// authorize -> bound/redact -> retrieve/memory -> model -> validate -> observe
// Tests must verify both request and response order, including exceptions.
```

### Design decisions and alternatives

Use advisors for reusable integration concerns, not as a substitute for domain-service authorization. Document chain order and state ownership. Keep request context immutable or narrowly scoped so concurrent calls cannot contaminate each other.

### Failure scenario and safe recovery

A debug logger is ordered before redaction and captures private evidence. Tests should assert log fields and chain ordering, not merely that the model returns a string.

### Security, privacy and provenance

Retries wrapped around the entire advisor chain may repeat retrieval, memory writes or tool effects. Assign retry ownership deliberately.


**Verification criteria:** Order correctness, exception propagation, stream cancellation, context isolation and redaction coverage. Record advisor latency in traces without raw sensitive content.

### Work through hidden costs

If memory adds 3,000 tokens and retrieval adds 8,000 after an earlier 4,000-token budget check, that check no longer protects a 12,000-token limit with output reserve. Validate the assembled prompt near the final model boundary. Record which component contributed tokens so tuning is explainable.

Retries can re-enter parts of a chain depending on the API. Memory writes or external side effects should not repeat blindly. Test ordering with spies/stubs and a known request, then inspect the actual assembled evidence and final result. The repository's general API compile check does not establish every advisor configuration's runtime behaviour.

## Problem

Explain tool (function) calling: how an LLM requests the execution of your code with structured arguments, how the application runs the tool and feeds the result back, how Spring AI exposes Java methods as tools (`@Tool`, `ToolCallback`, `ToolContext`), and how to make tool use safe in an enterprise (authorisation, validation, side effects).

## Requirements

- The tool-calling loop: the model returns `tool_calls`, the app executes, a tool result message goes back, the model writes the final answer.
- Defining tools in Spring AI: `@Tool` methods, `@ToolParam` descriptions, `.tools(...)` / `defaultTools`.
- Passing hidden context (user identity) with `ToolContext`.
- Read vs. write tools, confirmations, idempotency, errors and timeouts.
- Security: least privilege, never trusting model-supplied arguments blindly.

## 1. Selected tool and authority boundary

I implement a read-only order-status assistant. The model sees a schema for `lookupOrder(orderId)` and can propose it; the application checks the current principal's access before the order service reads data. Identity is application-owned and is not an argument the model can override.

## 2. Spring boundary and flow

```java
import org.springframework.ai.tool.annotation.Tool;
final class OrderTools {
    private final AuthorizedOrderLookup orders;
    OrderTools(AuthorizedOrderLookup orders) { this.orders = orders; }
    @Tool(description="Read status of an order authorized for the current user")
    public OrderStatus lookupOrder(String orderId) {
        return orders.lookupForCurrentPrincipal(orderId);
    }
}
// Registered on the selected ChatClient request using .tools(orderTools).
```

The service validates ID format, ownership, deadline and result bounds. O123 for its owner returns current status evidence; O999 belonging to someone else returns denial without private fields. A timeout is a typed unavailable result, not permission for the model to invent delivery status. Verified identity is explicitly propagated/bound in asynchronous execution rather than assuming thread-local security survives every boundary.

A refund extension would use a separate tool with current eligibility, amount/currency checks, stable refund identity and the product's approval rule. Repeated invocation returns the recorded operation; provider uncertainty is reconciled before another effect. Tool results remain untrusted external data for instruction purposes and cannot expand the caller's authority.

### Define the narrow boundary

```java
import org.springframework.ai.tool.annotation.Tool;

// Integration excerpt: authorizedOrders enforces identity outside model arguments.
final class OrderTools {
    private final AuthorizedOrderLookup authorizedOrders;
    OrderTools(AuthorizedOrderLookup lookup) { this.authorizedOrders = lookup; }
    @Tool(description = "Read the current user's authorized order status")
    OrderStatus lookupOrder(String orderId) {
        return authorizedOrders.lookupForCurrentPrincipal(orderId);
    }
}
```

The model does not get to supply `isAdmin=true` or choose another principal. In asynchronous work, propagate or explicitly bind the verified principal through an application-owned context; do not rely on a thread-local surviving arbitrary executor changes.

## 5. Detailed decisions, algorithms and failure behaviour

### Mechanism and rationale

**Design question:** How can an assistant look up a live order without being allowed to act on arbitrary accounts?

The model proposes a tool name and arguments. The application validates schema, derives authenticated identity, authorizes the resource and executes the tool. Tool result text returns as untrusted data for a later model step; the model never becomes the security principal.

### Architecture and contracts

```text
Model proposes call -> allow-list -> parse/validate -> authorize with server identity -> operation ledger -> execute -> bounded result -> model continuation

Application contracts (design outline):
OrderLookup(orderId); ToolContext(tenant,user,requestId); ToolResult(status,data,errorCode)
```

Spring AI @Tool can expose a narrow method and .tools(instance) can register it for a request. Wrap it in application authorization and bound the result; never expose a generic SQL or shell execution tool to this assistant.

### Worked reasoning and capacity example

A loop with at most four model steps and two tools per step can still request eight side effects. Bound tool count, elapsed time, output bytes and spend independently, not just recursion depth.

### Java and Spring AI implementation outline

```java
final class OrderTools {
  private final AuthorizedOrders orders;
  OrderTools(AuthorizedOrders orders) { this.orders = orders; }
  @org.springframework.ai.tool.annotation.Tool(description="Read one authorized order status")
  String status(String orderId) { return orders.statusForCurrentPrincipal(orderId); }
}
// AuthorizedOrders is an application port, not a model-provided identity.
```

### Design decisions and alternatives

I begin with read-only lookup tools. Side effects need operation IDs and a review/confirmation policy appropriate to the action. Descriptions should explain inputs and output semantics but cannot grant permissions.

### Failure scenario and safe recovery

A malicious user asks for another account’s order and provides a plausible userId argument. The tool ignores model-supplied identity and checks order ownership using the authenticated context.

### Security, privacy and provenance

A read-only label is descriptive metadata. Enforce read-only behavior in the implementation and database credentials.


**Verification criteria:** Task success, correct tool selection, unauthorized attempts blocked, argument validity, duplicate effects and tool latency/error classification.

- [Spring AI 1.1 ChatClient and request APIs](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html).
- [Spring AI tool-execution boundary](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html).
- [MCP specification, versioned protocol concepts](https://modelcontextprotocol.io/specification/2025-06-18).
- [Original RAG research](https://arxiv.org/abs/2005.11401) and [Transformer research](https://arxiv.org/abs/1706.03762) for background rather than framework instructions.

### Work through write tools

A refund tool needs stronger handling than a status lookup: validate amount, eligibility, current state, operation identity and required user review. Persist intent and reconcile provider uncertainty. A model retry after a lost response must not create another refund.

Limit tool count, payload size and duration. Validate tool results before sending them back; external results can contain instructions and should remain data. For the pinned 1.1 API family, use its documented execution behaviour rather than copying a newer-version advisor loop without verification.

## 6. Interviewer follow-ups

**Does `@Tool` make a method safe?** No. It exposes a callable contract; domain authorization and validation remain necessary.

**Should tools return raw database rows?** Return minimal typed data needed for the task, excluding secrets and unrelated personal fields.

## 7. Closing answer

Tool calling separates language intent from deterministic execution. I expose a narrow authorized order lookup, validate every proposed call and return minimal typed evidence. Write tools add explicit eligibility, operation identity and review policy; model arguments never become permission.
