## Problem

Explain how to get reliable, typed, structured output from LLMs in Java: mapping responses to POJOs or records, JSON schema and native structured-output modes, validating results, and handling the failures (malformed JSON, missing fields, wrong enums) with retries, using Spring AI's output converters and `.entity()`.

## Requirements

- Why free text is a poor integration contract.
- Spring AI's `BeanOutputConverter`, `ListOutputConverter`, `MapOutputConverter` and `.entity()`.
- Provider-native JSON or structured-output modes vs. prompt-based format instructions.
- Validation (Jakarta Bean Validation), retry-with-feedback, and fallbacks.

## Learn through a concrete example

A support assistant should return `category`, `priority` and `summary`. Free prose is difficult for downstream code to consume. Structured output asks for a typed shape, but a parseable object can still contain an invalid category or an unsupported decision.

Separate **syntax validation** (is it valid JSON?), **schema validation** (are required fields/types present?) and **business validation** (is this category allowed and justified?). A Java record describes a shape; it does not establish truth.

### Define a useful contract

```java
record Classification(String category, String summary, boolean needsReview) {}

Classification result = client.prompt()
    .user(ticketText).call().entity(Classification.class);
// Then validate category allow-list, summary bounds and review rules.
```

Represent missing evidence explicitly rather than forcing the model to invent required facts. An empty list of citations and `abstained=true` can be valid for an unanswerable question. `null`, empty string and unknown are different concepts; define which fields allow each.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How can model output become a reliable application object instead of fragile text parsing?

There are three separate checks: syntactic JSON validity, schema conformance and business correctness. Native provider schemas can constrain format when supported; framework converters can guide/parse output but cannot prove that a cited document exists or that an amount is valid.

### Architecture and contracts

```text
Task + schema -> provider -> parse -> schema/type validation -> domain invariants -> accept, bounded repair or reject

Application contracts (design outline):
SupportAnswer(summary,List<Citation>,needsHuman); Citation(sourceId,quote); ValidationResult(errors)
```

Use Java records for DTOs, entity(YourRecord.class) or an explicit converter, then Bean Validation/application checks. Treat code fragments as integration sketches unless included in the runnable examples project.

### Worked reasoning and capacity example

If 2% of 10,000 daily responses fail parsing, there are 200 repair candidates. One repair attempt adds up to 200 extra calls/day, and still needs a terminal failure policy. Measure cost and correctness rather than retrying until something parses.

### Java and Spring AI implementation outline

```java
record Extraction(String summary, java.util.List<String> sourceIds) {}
Extraction draft = client.prompt().user(question).call().entity(Extraction.class);
// Next: validate size limits, source existence, authorization and business rules.
```

### Design decisions and alternatives

Prefer small purpose-specific DTOs with bounded lists/strings and explicit optional fields. Enumerations should represent real business values, while unknown/abstained is explicit. Preserve original response identity for debugging under retention policy.

### Failure scenario and safe recovery

The response is valid JSON but invents an authorized-looking order ID. Resolve identifiers against the authenticated repository before any action. Never let a successful entity() conversion directly trigger a refund.

### Security, privacy and provenance

A schema can describe the shape of a tool argument but not establish the caller’s authority to use that argument.

### Hands-on lab and evaluation

**Build:** Feed malformed JSON, missing fields, unknown enum values, oversized lists and semantically invalid IDs through the pipeline. Show which layer rejects each case.

**Measure:** Track syntax success, schema success, domain validity, repair rate, repair cost and accepted incorrect outputs on a labelled set.

## Work through repair and evolution

Allow at most a bounded repair attempt for malformed output and count it in the same request budget. Repeatedly asking until parsing succeeds can hide cost and still produce semantic errors. A strict provider schema improves shape compliance where supported, but resource authorization remains outside generation.

Version the output contract. Adding a required field can break old consumers or archived responses. Keep raw-output retention restricted and redacted where needed; diagnostics should preserve enough schema/version information without collecting every private ticket in general logs.

## Practise, then check your reasoning

1. **Does `entity()` authorize a refund?** No. The domain service validates and executes approved actions.
2. **Should a missing date become today's date?** Only if the contract explicitly defines that default; otherwise preserve unknown.
3. **Exercise:** feed valid JSON with an illegal category, malformed JSON, missing evidence and oversized text. Assert four distinct outcomes and verify bounded repair. A test that only checks successful deserialization misses the important failures.

## Problem

Explain conversation memory for LLM apps: LLMs are stateless, so "memory" means deciding what past conversation (and long-term user facts) to send with each request. Cover Spring AI's `ChatMemory`, conversation IDs, persistence, window and summarisation strategies, and managing the context budget.

## Requirements

- Why the model "forgets", and where memory actually lives (your app).
- Short-term (conversation) vs. long-term (user facts, preferences) memory.
- Spring AI: `ChatMemory`, `MessageWindowChatMemory`, chat memory repositories (in-memory, JDBC, Cassandra, Neo4j), memory advisors.
- Conversation IDs, multi-user isolation, persistence, retention.
- Context-window management: windowing, summarisation, retrieval-based memory.

## Learn through a concrete example

“What did I ask earlier?” requires prior conversation content. Most model calls are stateless from the application's perspective; memory means selecting and supplying stored context. It is not an unlimited transcript and does not update model weights.

A **conversation ID** identifies stored history, a **memory window** selects retained messages, and a **summary** compresses older content with possible information loss. A user's ownership of the conversation must be verified independently of the ID they submit.

### Work a context window

Ten turns averaging 600 tokens are about 6,000 tokens before system messages, evidence and output reserve. Keeping the last ten **messages** is not the same as the last ten **turns**, and neither directly limits tokens. Budget actual selected context and preserve complete tool-call/result pairs where required.

```text
Storage scope: tenantId + userId + conversationId
Request context: instructions + selected history + question + evidence
Persisted turn: requestId + sequence + final output + state
```

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How can a chat remember prior turns without leaking another user’s conversation or exhausting context?

Persisted conversation history is application state. Each model request includes a selected view of it; provider-side caches do not replace this store. Window memory drops old turns; summaries compress them; retrieval can recover relevant past facts but adds ranking and privacy concerns.

### Architecture and contracts

```text
Authenticate conversation ownership -> append user turn -> select bounded history -> model/tool turns -> validate -> append final assistant turn

Application contracts (design outline):
ConversationKey(tenant,user,conversation); Message(role,body,sequence,toolCallId); MemoryPolicy(maxTokens,retention)
```

A chat-memory advisor can select and insert messages, but the application must authorize the conversation before invoking it. Use the API matching the pinned Spring AI baseline; newer session APIs have different names.

### Worked reasoning and capacity example

Twenty turns averaging 500 tokens each already consume 10,000 tokens before task instructions, retrieval and output allowance. Summaries should have their own budget and revision, not grow without bound.

### Java and Spring AI implementation outline

```java
record ConversationKey(String tenant, String user, String conversation) {}
interface ConversationRepository {
  java.util.List<String> authorizedHistory(ConversationKey key, int maxTokens);
}
// Persist roles/tool-call relationships in the real message schema.
```

### Design decisions and alternatives

Key memory by tenant plus authenticated user plus conversation, not a user-supplied conversation ID alone. Store raw history separately from derived summaries, with deletion and retention rules for each.

### Failure scenario and safe recovery

Two tabs append to one conversation concurrently. Sequence or version the append, and build the response against a known history snapshot. A tool result must match the tool call that produced it; dropping one half creates invalid context.

### Security, privacy and provenance

A summary generated by an LLM can turn uncertainty into a false permanent fact. Keep provenance and allow users to correct retained information.

### Hands-on lab and evaluation

**Build:** Create two users with the same supplied conversation ID and verify isolation. Run simultaneous turns, delete a conversation and confirm summaries/retrieval copies follow the deletion policy.

**Measure:** Measure cross-user leakage, retained facts, summary drift, context tokens and correctness after truncation. Use adversarial conversations that try to claim another tenant’s identity.

## Work through concurrent turns

Two tabs send follow-ups to the same conversation simultaneously. Without sequencing, both can answer against the same old history and append in an arbitrary order. Serialize per conversation, use optimistic version checks or explicitly represent branching. Do not pretend arrival timestamps alone define user intent.

A summary can accidentally omit an allergy, a constraint or a quoted negation. Keep critical application facts in typed authoritative state; do not entrust them only to a generated summary. Deletion must consider messages, summaries, vectors and caches under the retention policy.

## Practise, then check your reasoning

1. **Can a conversation ID supplied by the model establish ownership?** No. Resolve it against authenticated application identity.
2. **Does pruning history change old stored messages?** It need not; prompt selection and storage retention are separate policies.
3. **Exercise:** create two users with identical visible conversation labels, race two turns and delete one conversation. Verify isolation, deterministic order and removal from every memory representation you actually use.

## Problem

Explain vector stores: what they add beyond storing arrays of floats (ANN indexes, metadata filtering, hybrid search, CRUD and scaling), how the main options compare (PGVector, Redis, Elasticsearch/OpenSearch, dedicated databases like Pinecone, Weaviate, Qdrant, Milvus), and how Spring AI's `VectorStore` abstraction and filter expressions work.

## Requirements

- Index types (HNSW, IVF) and their trade-offs.
- Metadata filtering and why it's essential (multi-tenancy, ACLs, freshness).
- Choosing a store for an enterprise Java stack.
- Spring AI `VectorStore`, `SearchRequest`, the portable filter expression DSL.

## Learn through a concrete example

A vector store holds embeddings and associated document metadata so the application can retrieve neighbours. It is an index of selected evidence, not a replacement for document lifecycle, access control or a source-of-truth database.

An **index namespace** separates logical collections, a **metadata filter** constrains candidates, and a **document revision** tells you what was embedded. **Approximate search** improves speed by potentially missing some exact nearest neighbours; measure recall rather than assuming an index configuration is universally best.

### Calculate and choose

One million vectors × 1,536 dimensions × four bytes is about 6.144 GB raw values. Index graph/list structures, stored text, metadata, replicas and write headroom add to that. If your documents are small and the corpus modest, an existing database with vector support may be simpler than a new distributed dependency.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How should embeddings be indexed, filtered, updated and migrated in a real application?

A vector store combines numerical vectors, metadata and an index. Exact search establishes a correctness baseline; approximate methods such as HNSW/IVF trade search recall, memory, build time and latency. The storage engine may also support lexical indexes; vectors are not a separate mandatory database category.

### Architecture and contracts

```text
Document revision -> stable chunk IDs -> batch embedding -> versioned index upsert -> filtered search -> source lookup; tombstones and reindex govern updates

Application contracts (design outline):
IndexVersion(embeddingModel,dimension,chunkerVersion,metric); SearchRequest(query,tenant,filter,k); DocumentRevision
```

VectorStore accepts Documents and SearchRequest-like queries in the selected release. Keep store-specific configuration outside domain code; validate metadata filter behavior with integration tests.

### Worked reasoning and capacity example

Five million vectors x 1,536 x 4 bytes = 30.72 GB raw floats. HNSW graph links, metadata, original text, replicas and write buffers add to that. Capacity tests must include the chosen index configuration.

### Java and Spring AI implementation outline

```java
record IndexVersion(String embeddingModel, int dimensions, String chunkerVersion) {}
// Refuse reads/writes when request and index versions are incompatible.
// Build a replacement index before changing the live query encoder.
```

### Design decisions and alternatives

Start with a store that fits operating skills and consistency needs. Use stable content/revision keys for repeatable ingestion; rebuild into a new collection when model/chunker changes. Swap an index alias after validation rather than mixing incompatible vectors.

### Failure scenario and safe recovery

Deletion removes source text but leaves indexed chunks retrievable. Tombstone or delete every related chunk and enforce source authorization/version checks on read; track cleanup completion.

### Security, privacy and provenance

Two models with equal vector dimension are not interchangeable. Distance thresholds are metric/model dependent and must be calibrated on your corpus.

### Hands-on lab and evaluation

**Build:** Create an exact-search baseline, compare ANN recall on a labelled subset, then change embedding dimensions and demonstrate a staged reindex plus rollback.

**Measure:** Recall@k, filtered recall, insert/update lag, deletion propagation, memory and query p99 under concurrent ingestion. Benchmark skewed tenants, not only uniform random vectors.

## Work through filter correctness

Filtering before candidate selection and filtering a small top-k afterward can produce different recall and security properties. A post-filter cannot repair a design that exposes forbidden text to another processing step. Test tenant/resource filters with intentionally nearest forbidden vectors, not merely random fixtures.

Changing embedding models requires a versioned migration. Even equal-dimensional vectors can represent different spaces. Build a new index, test retrieval, switch query embedding and index together, and keep a rollback plan. Index backup and source re-ingestion are different recovery strategies with different time/cost.

## Practise, then check your reasoning

## Problem

Take RAG from demo to production: the techniques that move answer quality from "sometimes right" to dependable. That means smarter chunking with metadata, hybrid search, re-ranking, query rewriting and expansion, context compression, freshness and access control, and evaluation-driven tuning, plus how Spring AI's modular RAG components map onto them.

## Requirements

- Advanced chunking (structure-aware, parent-child, contextual headers).
- Hybrid lexical + semantic retrieval and rank fusion.
- Re-ranking with cross-encoders or LLM rankers.
- Query transformation: rewriting, multi-query, HyDE, conversational compression.
- Operational concerns: incremental ingestion, dedup, ACLs, evals and monitoring.

## Learn through a concrete example

A demonstration answers correctly from one PDF. Production adds thousands of documents, changing permissions, conflicting revisions and questions whose answers are absent. Production RAG makes evidence lifecycle and measurable failure behaviour part of the design rather than treating retrieval as a single library call.

**Recall@k** measures whether relevant evidence appears among retrieved candidates. A **reranker** reorders candidates with a more expensive relevance judgement. **Groundedness** evaluates whether the answer is supported by selected evidence. Improve the failing stage instead of blindly increasing every limit.

### Trace and calculate quality

On 100 answerable questions, relevant evidence may appear for 85. If 75 of those produce supported answers, retrieval recall is 85% while supported end-to-end success is 75% on that set. The conditional generation success is 75/85, about 88.2%. These diagnose different problems; one “accuracy” number hides them.

Reserve a separate unanswerable set. A system that confidently answers every question can score well on answer-present cases while failing dangerously when evidence is missing. Evaluate abstention precision/recall and critical security failures separately.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** What turns a successful RAG demo into a dependable multi-tenant documentation product?

Production RAG is a lifecycle of ingestion, revisioning, retrieval, authorization, evaluation and operations. Hybrid search retrieves lexical and semantic candidates; reranking orders a small candidate set; context assembly removes duplicates and respects token budget.

### Architecture and contracts

```text
Source connector -> revision/ACL capture -> parse/chunk/embed -> staged index -> retrieval -> authorization -> rerank -> citation generation -> support verification

Application contracts (design outline):
```

Use a simple QuestionAnswerAdvisor path as a baseline, then application-owned retrieval/reranking when policy requires it. Do not copy unversioned advisor constructors into a pinned build.

### Worked reasoning and capacity example

Assume 100 queries/s x 8 retrieved chunks x 600 tokens = 480,000 evidence tokens/s before history and output. Reranking all corpus chunks is impossible; first-stage retrieval must bound the candidate pool.

A shared semantic answer cache serves a correct answer to a user lacking access to the supporting documents. Partition caches by authorization domain and verify access on hits; similarity alone is not a safe cache key.

### Security, privacy and provenance

A more complex pipeline can be harder to debug and less reliable. Keep a measurable baseline and change one retrieval/generation component at a time.

### Key concepts and learning objective

## Problem

Explain tool (function) calling: how an LLM requests the execution of your code with structured arguments, how the application runs the tool and feeds the result back, how Spring AI exposes Java methods as tools (`@Tool`, `ToolCallback`, `ToolContext`), and how to make tool use safe in an enterprise (authorisation, validation, side effects).

## Requirements

- The tool-calling loop: the model returns `tool_calls`, the app executes, a tool result message goes back, the model writes the final answer.
- Defining tools in Spring AI: `@Tool` methods, `@ToolParam` descriptions, `.tools(...)` / `defaultTools`.
- Passing hidden context (user identity) with `ToolContext`.
- Read vs. write tools, confirmations, idempotency, errors and timeouts.
- Security: least privilege, never trusting model-supplied arguments blindly.

## Learn through a concrete example

A customer asks “Where is order O123?” The model can interpret the question, but the order service knows the current status. A **tool** is an application function described to the model. The model proposes its name and arguments; application code decides whether and how to execute it.

Start with a read-only lookup. Do not expose a general SQL executor or arbitrary HTTP client when one narrow domain operation meets the need. A tool description improves selection; it is not an authorization rule.

### Define the narrow boundary

```java
import org.springframework.ai.tool.annotation.Tool;

// Integration excerpt: authorizedOrders enforces identity outside model arguments.
final class OrderTools {
    private final AuthorizedOrderLookup authorizedOrders;
    OrderTools(AuthorizedOrderLookup lookup) { this.authorizedOrders = lookup; }
    @Tool(description = "Read the current user's authorized order status")
    OrderStatus lookupOrder(String orderId) {
        return authorizedOrders.lookupForCurrentPrincipal(orderId);
    }
}
```

The model does not get to supply `isAdmin=true` or choose another principal. In asynchronous work, propagate or explicitly bind the verified principal through an application-owned context; do not rely on a thread-local surviving arbitrary executor changes.

## Design details and alternatives

### Key concepts and learning objective

**Question to answer:** How can an assistant look up a live order without being allowed to act on arbitrary accounts?

The model proposes a tool name and arguments. The application validates schema, derives authenticated identity, authorizes the resource and executes the tool. Tool result text returns as untrusted data for a later model step; the model never becomes the security principal.

### Architecture and contracts

```text
Model proposes call -> allow-list -> parse/validate -> authorize with server identity -> operation ledger -> execute -> bounded result -> model continuation

Application contracts (design outline):
OrderLookup(orderId); ToolContext(tenant,user,requestId); ToolResult(status,data,errorCode)
```

Spring AI @Tool can expose a narrow method and .tools(instance) can register it for a request. Wrap it in application authorization and bound the result; never expose a generic SQL or shell execution tool to this assistant.

### Worked reasoning and capacity example

A loop with at most four model steps and two tools per step can still request eight side effects. Bound tool count, elapsed time, output bytes and spend independently, not just recursion depth.

### Java and Spring AI implementation outline

```java
final class OrderTools {
  private final AuthorizedOrders orders;
  OrderTools(AuthorizedOrders orders) { this.orders = orders; }
  @org.springframework.ai.tool.annotation.Tool(description="Read one authorized order status")
  String status(String orderId) { return orders.statusForCurrentPrincipal(orderId); }
}
// AuthorizedOrders is an application port, not a model-provided identity.
```

### Design decisions and alternatives

Begin with read-only lookup tools. Side effects need operation IDs and a review/confirmation policy appropriate to the action. Descriptions should explain inputs and output semantics but cannot grant permissions.

### Failure scenario and safe recovery

A malicious user asks for another account’s order and provides a plausible userId argument. The tool ignores model-supplied identity and checks order ownership using the authenticated context.

### Security, privacy and provenance

A read-only label is descriptive metadata. Enforce read-only behavior in the implementation and database credentials.

### Hands-on lab and evaluation

**Build:** Implement a read-only stock/order tool; test nonexistent IDs, foreign-tenant IDs, oversized arguments, duplicate calls and a provider timeout following a completed tool.

**Measure:** Task success, correct tool selection, unauthorized attempts blocked, argument validity, duplicate effects and tool latency/error classification.

## Work through write tools

A refund tool needs stronger handling than a status lookup: validate amount, eligibility, current state, operation identity and required user review. Persist intent and reconcile provider uncertainty. A model retry after a lost response must not create another refund.

Limit tool count, payload size and duration. Validate tool results before sending them back; external results can contain instructions and should remain data. For the pinned 1.1 API family, use its documented execution behaviour rather than copying a newer-version advisor loop without verification.
