## Problem

Design the game Snake & Ladder. Two or more players take turns rolling a die and moving along a board of 100 cells. Landing at the foot of a ladder takes you up; landing on a snake's head takes you down. The first player to land exactly on 100 wins.

It's a favourite interview warm-up because it is small enough to finish – and it still tests clean classes, a testable random element, and rules such as "what if a ladder ends on a snake?".

## Requirements

- A board of N cells (usually 100) with snakes and ladders.
- 2 or more players take turns in order; everyone starts off the board (cell 0).
- Roll a die, move, follow at most one snake or ladder, then pass the turn.
- You must land exactly on the last cell to win; overshooting means you stay put.
- The game can be replayed and tested with fixed dice rolls.

## Step 1: Clarify the requirements

**Candidate:** How many players and dice?

**Interviewer:** Two to four players, one six-sided die.

**Candidate:** Do you need an exact roll to finish?

**Interviewer:** Yes. If you'd go past 100, you don't move.

**Candidate:** Can a ladder end on a snake's head?

**Interviewer:** Your call – explain it.

**Candidate:** Does rolling a 6 give an extra turn?

**Interviewer:** Not in the basic version. Mention how you'd add it.

**Candidate:** Is it played by people or simulated?

**Interviewer:** Both – we also run simulations to test board designs.

> **🎯 In the interview**
> Ask about exact-finish and chained jumps. They are the two rules people forget, and they shape the `Board` validation and the turn logic.

| Functional | Non-functional |
| --- | --- |
| Board with snakes and ladders | Rules easy to change (extra turn on 6) |
| Turns, moves, winner | Deterministic tests: dice can be fixed |
| Exact finish | Invalid boards rejected at creation |

## Step 2: Identify the core objects

- **Board** – size and a map from start cell to end cell (snakes and ladders).
- **Jump** – one snake or ladder: start and end.
- **Dice** – an interface; `RandomDice` for real games, `FixedDice` for tests and replays.
- **Player** – a name.
- **Game** – positions, the turn order, the winner, and `playTurn()`.
- **Move** – what happened in one turn: roll, from, to, and a note ("ladder", "snake", "needs exact roll").

[![Selected design: the game asks the dice for a roll, moves the current player, asks the board whether the target cell starts a snake or ladder, records the move and passes the turn, or declares the winner on the last cell.](designs/lld-17.svg)](designs/lld-17.svg)

> **⚖️ Design choice**
> Snakes and ladders are the **same thing**: a jump from one cell to another. One `Jump` record and one map replace two class hierarchies – a snake simply has `end < start`.

## Step 3: Design the classes

### Board and Jump

The board validates jumps when it's created: on the board, not from the last cell, one jump per start cell, and no jump ending where another starts.

### Dice

An interface with `roll()`. Injecting it is what makes the game testable.

### Game, Player and Move

`Game` keeps a queue of players for turn order and a map of positions. `playTurn` returns a `Move`, so the UI or a log can show exactly what happened.

[![Class diagram: Game has a Board, a Dice and a queue of Players with positions, and returns a Move per turn; Board has Jumps; RandomDice and FixedDice implement Dice.](learning-figures/lld-17-classes.svg)](learning-figures/lld-17-classes.svg)

## Step 4: Write the code

### Board and Jump

```java
/** A snake (end below start) or a ladder (end above start). */
record Jump(int start, int end) {
    boolean isSnake() { return end < start; }
}

class Board {
    private final int size;
    private final Map<Integer, Integer> jumps = new HashMap<>();

    Board(int size, List<Jump> list) {
        this.size = size;
        for (Jump j : list) {
            if (j.start() <= 1 || j.start() >= size || j.end() < 1 || j.end() > size)
                throw new IllegalArgumentException("Jump off the board: " + j);
            if (jumps.putIfAbsent(j.start(), j.end()) != null)
                throw new IllegalArgumentException("Two jumps start at " + j.start());
        }
        for (Jump j : list)                                 // one jump per landing, no chains
            if (jumps.containsKey(j.end()))
                throw new IllegalArgumentException("Jump ends on another jump: " + j);
    }
    int size()                   { return size; }
    int afterJump(int cell)      { return jumps.getOrDefault(cell, cell); }
}
```

### Dice

```java
interface Dice { int roll(); }

class RandomDice implements Dice {
    private final Random random = new Random();
    public int roll() { return random.nextInt(6) + 1; }
}

/** For tests and replays: returns a fixed sequence of rolls. */
class FixedDice implements Dice {
    private final Iterator<Integer> rolls;
    FixedDice(Integer... rolls) { this.rolls = List.of(rolls).iterator(); }
    public int roll() { return rolls.next(); }
}
```

### Game

```java
record Player(String name) {}

record Move(Player player, int roll, int from, int to, String note) {}

class Game {
    private final Board board;
    private final Dice dice;
    private final Deque<Player> turns;
    private final Map<Player, Integer> position = new HashMap<>();
    private Player winner;

    Game(Board board, Dice dice, List<Player> players) {
        if (players.size() < 2) throw new IllegalArgumentException("Need at least 2 players");
        this.board = board; this.dice = dice; this.turns = new ArrayDeque<>(players);
        players.forEach(p -> position.put(p, 0));           // everyone starts off the board
    }

    Move playTurn() {
        if (winner != null) throw new IllegalStateException(winner.name() + " already won");
        Player p = turns.pollFirst();
        int roll = dice.roll(), from = position.get(p), target = from + roll;
        String note;
        int to;
        if (target > board.size()) { to = from; note = "needs exact roll"; }
        else {
            to = board.afterJump(target);
            note = to > target ? "ladder" : to < target ? "snake" : "";
        }
        position.put(p, to);
        if (to == board.size()) winner = p; else turns.addLast(p);
        return new Move(p, roll, from, to, note);
    }

    Optional<Player> winner() { return Optional.ofNullable(winner); }
    int positionOf(Player p)  { return position.get(p); }
}
```

### Edge cases

| Case | Behaviour |
| --- | --- |
| Fewer than 2 players | Rejected |
| Two players on the same cell | Allowed – no capturing |
| Turn after the game ended | `IllegalStateException` |
| Board with a jump from the last cell, or a chain | Rejected when the board is built |

## Step 5: The tricky part: a jump that lands on a jump

What if the ladder 3→8 ends on a snake's head at 8 (8→2)? Two possible rules:

- **Follow the chain:** 3 → 8 → 2 → maybe another jump… With a careless board, 8→2 and 2→8 loop forever.
- **One jump per landing:** only the first jump applies.

Our `Board` avoids the question by **rejecting** a board where a jump ends on another jump's start. Rules about the board are checked once, when it's built, not on every turn.

![Animation: a board is built with a ladder from 3 to 8 and a snake from 8 to 2; validation notices the ladder ends on the snake's head and rejects the board; a valid board is built instead and Asha's roll of 3 climbs the ladder to 8 and stops there.](learning-figures/lld-17-validate.gif)

> **⚠️ Common mistake**
> Using `new Random()` directly inside `Game`. You can't test "Asha lands on the snake" without controlling the die. Inject a `Dice` and use `FixedDice` in tests.

> **🎯 In the interview**
> If asked to support chains anyway, follow jumps with a limit (say 10) and validate at build time that following never revisits a cell – a small cycle check.

## Step 6: Deep dives

### Extra turn on a 6

In `playTurn`, if `roll == 6` and the player hasn't won, put them back at the **front** of the queue instead of the back. Limit it to three sixes in a row if you like.

### Two dice, different dice

`Dice` is an interface: `TwoDice` returns the sum of two rolls; a "crooked" dice for a test of probability is one more class.

### More players and a UI

`Move` records make it easy to animate each turn or print a log. Players can be humans or bots without changing `Game`.

### Simulating board designs

Run 100,000 games with `RandomDice` and record the number of turns per game – a quick way to check a board isn't too long or too short.

## Interviewer follow-ups

**Why one `Jump` instead of `Snake` and `Ladder` classes?** They have the same data and the same behaviour – move from one cell to another. Separate classes add code, not meaning.

**Why a queue for turns?** Taking the first player and adding them to the back is exactly "round robin", and removing the winner is easy.

**Where would you put the "exact finish" rule if it became optional?** In a small `FinishRule` strategy (exact, bounce back, or allow overshoot) that `Game` calls.

**How do you make the game replayable?** Store the seed or the sequence of rolls; replaying with `FixedDice` gives the same game.

## Wrap up

A Board of validated jumps, an injected Dice, and a Game that moves players in a round-robin queue and records each Move – small, testable and easy to extend.

> **📝 Key takeaways**
> - Snakes and ladders are one concept: a jump.
> - Validate the board once when it's built.
> - Inject the dice so games can be tested and replayed.
> - Turns are a queue; each turn returns a Move record.

## Problem

Design the booking core of a train reservation system like IRCTC. The Bengaluru–Chennai Shatabdi stops at Jolarpettai and Katpadi. Asha books seat S1 from Bengaluru to Jolarpettai. Bilal then books from Jolarpettai to Chennai – and can get **the same seat S1**, because Asha leaves before he boards.

That's what makes trains different from movies or flights: a seat is sold **per stretch of the route**, not once for the whole trip. And a family of four must get seats together for the whole journey, or go on the waitlist.

## Requirements

- A train run (train + date) has a route of stops and a set of seats.
- Book one or more passengers from station A to station B.
- A seat is available if it is free on **every segment** between A and B.
- All passengers in a booking are confirmed together, or the booking is waitlisted.
- Cancelling frees the seat's segments and promotes waitlisted bookings in order.

## Step 1: Clarify the requirements

**Candidate:** Can a seat be sold to different people on different parts of the route?

**Interviewer:** Yes – that's how real trains get full use of seats.

**Candidate:** Do all passengers on one booking need confirmed seats together?

**Interviewer:** Yes. Confirm all or none.

**Candidate:** What happens when no seat is free?

**Interviewer:** Waitlist, in order. Cancellations promote them.

**Candidate:** Coach classes, quotas, berth preferences?

**Interviewer:** Mention them; one class of seats is enough for the design.

**Candidate:** How busy does it get?

**Interviewer:** Tatkal opens at 10 a.m.; thousands book the same train in the first minute.

> **🎯 In the interview**
> Ask whether seats can be reused along the route. The answer changes the core data structure from "a seat is booked" to "a seat is booked for these segments".

| Functional | Non-functional |
| --- | --- |
| Book A → B for 1–6 passengers | Never two people on one seat-segment |
| Waitlist and promotion | All-or-nothing per booking |
| Cancel | Fair, first-come waitlist |

## Step 2: Identify the core objects

- **Route** – the ordered stops; segment *i* runs from stop *i* to stop *i+1*.
- **Journey** – a booking's range of segments, `[from, to)`.
- **Seat** – a number and, for each segment, which booking holds it.
- **Booking** – PNR, passengers, journey, seats and status.
- **BookingStatus** – CONFIRMED, WAITLISTED, CANCELLED.
- **TrainRun** – one train on one date: seats, waitlist, `book` and `cancel`.

[![Selected design: a booking request for a journey from one station to another goes to the train run, which checks each seat's segments for the whole journey, holds enough seats for every passenger together or puts the booking on the waitlist, and promotes the waitlist when a cancellation frees segments.](designs/lld-18.svg)](designs/lld-18.svg)

> **⚖️ Design choice**
> Store availability **per seat, per segment**. A journey is a range of segment numbers, so "is S1 free from Jolarpettai to Chennai?" means "are segments 1 and 2 of S1 empty?".

## Step 3: Design the classes

### Route and Journey

The route turns station names into indexes. Bengaluru → Chennai with four stops is segments 0, 1 and 2.

### Seat

An array with one slot per segment, holding the booking ID or `null`. `isFree(journey)` checks the slots in the range; `hold` and `release` fill or clear them.

### Booking

Passengers, journey, the seats assigned and the status.

### TrainRun

`book` tries to confirm; if that fails it adds the booking to the waitlist queue. `cancel` frees the booking's segments and walks the waitlist in order, confirming anyone who now fits.

```java
        int i = stops.indexOf(station);

        return i;
    }
}

/** The journey Asha asked for, as a range of segments [from, to). */
record Journey(int from, int to) {

        if (from >= to) throw new IllegalArgumentException("Destination is before source");
```

### Seat

```java
class Seat {
    private final String number;
    private final String[] heldBy;                  // one slot per segment; null = free

    Seat(String number, int segments) {
        this.number = number;
        this.heldBy = new String[segments];
    }
    String number() { return number; }

    boolean isFree(Journey j) {
        for (int s = j.from(); s < j.to(); s++) if (heldBy[s] != null) return false;
        return true;
    }
    void hold(Journey j, String bookingId) {
        for (int s = j.from(); s < j.to(); s++) heldBy[s] = bookingId;
    }
    void release(String bookingId) {
        for (int s = 0; s < heldBy.length; s++) {
            if (bookingId.equals(heldBy[s])) heldBy[s] = null;
        }
    }
}
```

### Booking

### TrainRun

```java
class TrainRun {                                    // one train on one date
    private final Route route;
    private final List<Seat> seats = new ArrayList<>();
    private final Deque<Booking> waitlist = new ArrayDeque<>();
    private int nextId = 1;

    TrainRun(Route route, int seatCount) {
        this.route = route;
        int segments = route.stops().size() - 1;
        for (int i = 1; i <= seatCount; i++) seats.add(new Seat("S" + i, segments));
    }

    /** All passengers get seats for the whole journey, or the booking is waitlisted. */
    synchronized Booking book(List<String> passengers, String from, String to) {
        Journey j = new Journey(route.index(from), route.index(to));
        Booking b = new Booking("PNR" + (1000 + nextId++), passengers, j);
        if (!tryConfirm(b)) { b.status = BookingStatus.WAITLISTED; waitlist.addLast(b); }
        return b;
    }

    synchronized void cancel(Booking b) {
        if (b.status == BookingStatus.CANCELLED) return;
        if (b.status == BookingStatus.WAITLISTED) waitlist.remove(b);
        b.seats.forEach(s -> s.release(b.id));
        b.seats.clear();
        b.status = BookingStatus.CANCELLED;
        waitlist.removeIf(this::tryConfirm);        // promote anyone who now fits, in order
    }

    private boolean tryConfirm(Booking b) {
        List<Seat> free = seats.stream().filter(s -> s.isFree(b.journey))
                .limit(b.passengers.size()).toList();
        if (free.size() < b.passengers.size()) return false;
        free.forEach(s -> s.hold(b.journey, b.id));
        b.seats.addAll(free);
        b.status = BookingStatus.CONFIRMED;
        return true;
    }
}
```

## Step 5: The booking algorithm: whole journey, whole group

The rule has two parts:

1. **Whole journey:** a seat counts only if *every* segment of the journey is free on it.
2. **Whole group:** find enough such seats for every passenger; if there aren't enough, take none.

Only after both checks pass are the segments held. Because `book` and `cancel` are `synchronized` on the train run, two Tatkal bookings can't both take the last seat.

![Animation: Asha holds seat S1 for segment 0 and Bilal holds S1 for segments 1 and 2; the family's request for segments 0 to 2 finds only S2 free throughout and is waitlisted; as Ravi, Bilal and Asha cancel, the waitlist is re-checked each time, and only when both seats are free for the whole route is the family confirmed together.](learning-figures/lld-18-segments.gif)

> **⚠️ Common mistake**
> Confirming passengers one at a time. The first two of a family of four get seats, the last two don't, and the family is split across "confirmed" and "waitlisted". Check the whole group first, then hold.

> **🎯 In the interview**
> In a database, a seat-segment is a row (or a bit in a bitmap). Holding a journey is one transaction that updates all the needed rows only if they're all free; across many train runs, partition by train and date.

## Step 6: Deep dives

### Coaches, classes and berth preferences

Group seats into coaches with a class (SL, 3A, 2A). `tryConfirm` filters by class first, then prefers lower berths or seats together, as a pluggable `SeatSelectionStrategy`.

### RAC (shared berths)

IRCTC's RAC lets two passengers share one side-lower berth. Model it as a seat with capacity 2 for RAC bookings – between confirmed and waitlisted.

### Quotas

Tatkal, ladies and senior-citizen quotas reserve some seats for some requests: tag seats with a quota and filter by the request's eligibility.

### Fast availability search

Searching thousands of trains can't scan every seat. Keep a per-train, per-segment count of free seats, updated on booking and cancellation, and use it for the search page; the exact seat check happens only when booking.

## Interviewer follow-ups

**Why segments instead of "booked from A to B" ranges on each seat?** Segments make overlap checks trivial (any slot in the range taken?) and work the same for every journey length.

**How is the waitlist fair?** It's a queue; after each cancellation we try bookings in order. A large group may wait while a smaller later booking fits – you can choose strict order instead if fairness requires it.

**What about two Tatkal bookings at the same moment?** One lock per train run here; in a database, a conditional update on the seat-segment rows so only one transaction wins.

**How do you show availability on the search page?** From the per-segment free counts – approximate, but fast; the booking step is exact.

## Wrap up

Seats are sold per segment, a booking needs every segment of its journey for every passenger, and cancellations free segments and promote the waitlist in order.

> **📝 Key takeaways**
> - A route is a list of stops; a journey is a range of segments.
> - A seat is free for a journey only if every segment in it is free.
> - Confirm the whole group or none; otherwise waitlist.
> - Cancelling frees segments and re-checks the waitlist in order.

## Problem

Design order management for a marketplace like Amazon. Asha orders headphones and 3 USB-C cables from the seller SoundHub, and 4 notebooks from PaperCo, in one checkout. Before anything ships she cancels one cable. SoundHub and PaperCo then send separate parcels, and later she returns one notebook.

One "order" is really several things moving at different speeds. The design must track every unit – ordered, cancelled, shipped, returned – and show an order status that is always consistent with them.

## Requirements

- An order has lines (product, seller, quantity, price) from one or more sellers.
- Each seller ships its own parcel (shipment); an order can be partly shipped.
- Customers can cancel units that haven't shipped, and return units that have.
- Refunds match exactly the units cancelled or returned.
- The order's status is always consistent with its lines and shipments.

## Step 1: Clarify the requirements

**Candidate:** Can one order contain items from several sellers?

**Interviewer:** Yes. Each seller ships separately.

**Candidate:** Can a customer cancel part of a line – one of three cables?

**Interviewer:** Yes, as long as those units haven't shipped.

**Candidate:** After shipping?

**Interviewer:** Then it's a return, not a cancellation.

**Candidate:** What statuses does the customer see?

**Interviewer:** Placed, partly shipped, shipped, delivered, cancelled.

**Candidate:** Do we design payment and warehouses too?

**Interviewer:** No – assume payment is done; focus on lines, shipments and statuses.

> **🎯 In the interview**
> Ask about partial cancellation early. It tells you that status belongs to **units**, not just to the whole order.

| Functional | Non-functional |
| --- | --- |
| Lines from many sellers | Units never double-counted (cancelled *and* shipped) |
| Shipments per seller | Refund = exactly the units cancelled or returned |
| Cancel, return, track | Status never contradicts the details |

## Step 2: Identify the core objects

- **Order** – a customer, its lines, its shipments and refunds.
- **OrderLine** – a product from one seller: ordered quantity, unit price, and how many units are shipped, cancelled and returned.
- **Shipment** – one seller's parcel: which lines and how many units, plus its status.
- **ShipmentStatus** – created, dispatched, delivered.
- **OrderStatus** – placed, partly shipped, shipped, delivered, cancelled – **calculated**, not stored.

[![Selected design: an order holds lines from several sellers; each line splits its units into pending, shipped and cancelled; pending units are packed into one shipment per seller; cancellations and returns produce refunds per unit; the order status is calculated from the lines and shipments.](designs/lld-19.svg)](designs/lld-19.svg)

> **⚖️ Design choice**
> **Derive the order status** from lines and shipments instead of storing it. A stored status can drift ("SHIPPED" while a cable is still pending); a calculated one can't.

## Step 3: Design the classes

### OrderLine

Keeps the invariant: `ordered = pending + shipped + cancelled`. You can cancel only pending units and return only shipped (not yet returned) units.

### Shipment

One per seller per dispatch. It records how many units of each line it carries and its delivery status.

### Order

`planShipments` groups pending units by seller into new shipments. `cancel(sku, qty)` cancels units and adds to the refund. `status()` computes the customer-facing status.

[![Class diagram: an Order has OrderLines and Shipments; each Shipment carries units of OrderLines and has a ShipmentStatus; the Order calculates an OrderStatus; each OrderLine tracks ordered, shipped, cancelled and returned units.](learning-figures/lld-19-classes.svg)](learning-figures/lld-19-classes.svg)

## Step 4: Write the code

### OrderLine

```java
/** One product in an order. Its units are split across pending, shipped and cancelled. */
class OrderLine {
    final String sku, seller;
    final int ordered;
    final long unitPricePaise;
    private int shipped, cancelled, returned;

    OrderLine(String sku, String seller, int qty, long unitPricePaise) {
        this.sku = sku; this.seller = seller; this.ordered = qty;
        this.unitPricePaise = unitPricePaise;
    }
    int pending()   { return ordered - shipped - cancelled; }   // always >= 0
    int shipped()   { return shipped; }
    int cancelled() { return cancelled; }

    void ship(int n) {
        if (n > pending()) throw new IllegalStateException("Only " + pending() + " to ship");
        shipped += n;
    }
    long cancel(int n) {
        if (n > pending()) throw new IllegalStateException("Only " + pending() + " left");
        cancelled += n;
        return n * unitPricePaise;                                // refund
    }
    long returnUnits(int n) {
        if (n > shipped - returned) throw new IllegalStateException("Nothing to return");
        returned += n;
        return n * unitPricePaise;
    }
}
```

### Order

```java
enum OrderStatus { PLACED, PARTLY_SHIPPED, SHIPPED, DELIVERED, CANCELLED }

class Order {
    final String id, customer;
    final List<OrderLine> lines;
    final List<Shipment> shipments = new ArrayList<>();
    private long refundedPaise;

    Order(String id, String customer, List<OrderLine> lines) {
        this.id = id; this.customer = customer; this.lines = List.copyOf(lines);
    }

    /** One shipment per seller for everything not yet shipped or cancelled. */
    List<Shipment> planShipments() {
        Map<String, List<OrderLine>> bySeller = lines.stream().filter(l -> l.pending() > 0)
                .collect(Collectors.groupingBy(l -> l.seller, LinkedHashMap::new,
                        Collectors.toList()));
        List<Shipment> created = new ArrayList<>();
        bySeller.forEach((seller, ls) -> {
            Shipment s = new Shipment(id + "-S" + (shipments.size() + 1), seller);
            ls.forEach(l -> { s.units.put(l, l.pending()); l.ship(l.pending()); });
            shipments.add(s);
            created.add(s);
        });
        return created;
    }

    long cancel(String sku, int qty) {
        long refund = line(sku).cancel(qty);
        refundedPaise += refund;
        return refund;
    }

    /** The status is derived from the lines and shipments, never set by hand. */
    OrderStatus status() {
        int pending = lines.stream().mapToInt(OrderLine::pending).sum();
        int shipped = lines.stream().mapToInt(OrderLine::shipped).sum();
        if (shipped == 0) return pending == 0 ? OrderStatus.CANCELLED : OrderStatus.PLACED;
        if (pending > 0) return OrderStatus.PARTLY_SHIPPED;
        boolean allDelivered = shipments.stream()
                .allMatch(s -> s.status == ShipmentStatus.DELIVERED);
        return allDelivered ? OrderStatus.DELIVERED : OrderStatus.SHIPPED;
    }

    OrderLine line(String sku) {
        return lines.stream().filter(l -> l.sku.equals(sku)).findFirst()
                .orElseThrow(() -> new IllegalArgumentException("No line " + sku));
    }
    long refunded() { return refundedPaise; }
}
```

| --- | --- |

## Step 5: The status algorithm: count units, then decide

`status()` follows a small decision list:

1. Nothing shipped and nothing pending → **CANCELLED**.
2. Nothing shipped, something pending → **PLACED**.
3. Something shipped, something still pending → **PARTLY_SHIPPED**.
4. All non-cancelled units shipped: all parcels delivered → **DELIVERED**, otherwise **SHIPPED**.

Because each unit is in exactly one bucket (pending, shipped or cancelled), the status can't contradict the lines.

![Animation: Asha's order starts with headphones, three cables and four notebooks; one cable is cancelled and refunded; the remaining units are packed into a SoundHub parcel and a PaperCo parcel; a notebook cancellation is refused because it is already in a parcel and becomes a return; when both parcels are delivered the order status becomes delivered.](learning-figures/lld-19-units.gif)

> **⚠️ Common mistake**
> One status field on the order, updated by whoever touched it last. A seller dispatch and a customer cancellation arriving together can leave the order saying "CANCELLED" while a parcel is on its way. Track units per line and derive the status.

> **🎯 In the interview**
> With many services, the cancel and the warehouse pick can race. Make "cancel pending units" a conditional update (`pending >= qty`) on the line, the same row the warehouse updates when it packs units – only one can take the last unit.

## Step 6: Deep dives

### Several warehouses per seller

Group pending units by **(seller, warehouse)** instead of seller. One seller can then send two parcels from Bengaluru and Delhi.

### Payments and refunds

Store each refund as its own record (order, line, units, amount, reason). Refunds are always calculated from units × unit price, so partial refunds are exact.

### Return pickup and inspection

A return has its own small state machine: requested → picked up → inspected → refunded (or rejected). Refund only after inspection if the policy says so.

### Notifications and tracking

Each shipment status change publishes an event; the customer sees per-parcel tracking, while the order status summarises them.

## Interviewer follow-ups

**Why not split the order into one order per seller at checkout?** The customer thinks of one order and one payment. Keep one order; split into shipments underneath.

**Why derive status instead of storing it?** It can't get out of sync. If reading it is expensive, store a cached copy updated in the same transaction as the lines.

**How do you handle a seller who can't fulfil?** Cancel those units on the seller's side – same `cancel` on pending units, with reason "seller unavailable" and an automatic refund.

**How would you scale it?** Orders partitioned by customer; shipments also indexed by seller for seller dashboards; events to analytics and notifications.

## Wrap up

An order is lines of units from many sellers; units are pending, shipped or cancelled; pending units become per-seller shipments; refunds follow units; and the order status is calculated from all of that.

> **📝 Key takeaways**
> - Track units per line: ordered = pending + shipped + cancelled.
> - Cancel only pending units; after shipping it's a return.
> - One shipment per seller (or warehouse).
> - Derive the order status so it can't contradict the details.

"An Order holds OrderLines – product, seller, quantity and unit price – and each line splits its units into pending, shipped and cancelled, with returns tracked against shipped units, so a unit is never counted twice. ## Problem

Design a calendar and meeting scheduler like Google Calendar. Asha wants a 45-minute meeting with Bilal and Chetan tomorrow in the Kaveri room. The system should show conflicts, never double-book the room, and suggest the first time all three are free.

Bilal's weekly standup is "every Monday 9:00 New York time" – which is 18:30 in Bengaluru one week and 19:30 the next, when US clocks change. Time zones are where calendar designs usually break.

## Requirements

- Create events with an organiser, attendees, a time slot and optionally a room.
- A room can never be booked for two overlapping events.
- Show a person's conflicts for a proposed time.
- Find the earliest slot of a given length when all attendees are free.
- Support weekly recurring events in the organiser's time zone.

## Step 1: Clarify the requirements

**Candidate:** Can people be double-booked?

**Interviewer:** Yes – show a warning, but let them decide. Rooms can't be.

**Candidate:** Do we need free-slot suggestions?

**Interviewer:** Yes: "first 45 minutes when everyone's free between 9:30 and 18:00".

**Candidate:** Recurring events?

**Interviewer:** Weekly is enough for now.

**Candidate:** Attendees in different time zones?

**Interviewer:** Yes – the team is in Bengaluru and New York.

**Candidate:** Is a meeting ending at 11:00 a conflict with one starting at 11:00?

**Interviewer:** No, back-to-back is fine.

> Settle three rules early: are slots half-open (end exclusive), can people be double-booked, and in which time zone does a recurring event repeat.

| --- | --- |
| Create events, rooms, attendees | Rooms never double-booked |
| Conflicts and free-slot search | Correct across time zones and DST |

## Step 2: Identify the core objects

- **Slot** – a time range `[start, end)` stored as `Instant`s.
- **Event** – title, organiser, attendees, slot, optional room.
- **WeeklyRule** – day of week, local start time, length and **time zone**; expands into slots.
- **CalendarService** – schedules events, checks room clashes, finds conflicts and free slots.

[![Selected design: a scheduling request goes to the calendar service, which checks the room's events for overlaps, stores the event on every attendee's calendar, reports personal conflicts, searches merged busy times for the first common free slot, and expands weekly rules using a time zone.](designs/lld-20.svg)](designs/lld-20.svg)

> **⚖️ Design choice**
> Store every slot as an **`Instant`** (a point on the global timeline) and keep the **time zone with the rule**, not with the stored times. Comparisons are then always correct; local times appear only when displaying or expanding a rule.

## Step 3: Design the classes

### Slot

Two instants with `overlaps(other)`: `start < other.end && other.start < end`. Because the end is exclusive, 10:00–11:00 and 11:00–11:30 don't overlap.

### Event

An immutable record with the attendees and the optional room.

### WeeklyRule

Turns "every Monday 09:00 in America/New_York" into real instants week by week, letting Java's time zone rules handle daylight saving.

### CalendarService

Keeps events by person and by room. `schedule` refuses room overlaps; `conflictsFor` lists a person's overlapping events; `firstCommonFree` finds the earliest gap.

## Step 4: Write the code

### Slot and Event

```java
/** A time range [start, end). Stored as Instants so time zones can't confuse comparisons. */
record Slot(Instant start, Instant end) {
    Slot {
        if (!start.isBefore(end)) throw new IllegalArgumentException("End before start");
    }
    boolean overlaps(Slot o) { return start.isBefore(o.end) && o.start.isBefore(end); }
}

record Event(String id, String title, String organizer, Set<String> attendees,
             Slot slot, String room) {}
```

### Weekly recurrence

```java
/** "Every Monday 10:00–10:30 in Asia/Kolkata", expanded into concrete slots. */
record WeeklyRule(DayOfWeek day, LocalTime start, Duration length, ZoneId zone) {
    List<Slot> occurrences(LocalDate from, int count) {
        List<Slot> out = new ArrayList<>();
        LocalDate d = from;
        while (d.getDayOfWeek() != day) d = d.plusDays(1);
        for (int i = 0; i < count; i++, d = d.plusWeeks(1)) {
            Instant s = ZonedDateTime.of(d, start, zone).toInstant();  // local → instant
            out.add(new Slot(s, s.plus(length)));
        }
        return out;
    }
}
```

### CalendarService

```java
class CalendarService {
    private final Map<String, List<Event>> byPerson = new HashMap<>();
    private final Map<String, List<Event>> byRoom = new HashMap<>();
    private int nextId = 1;

    /** Rooms can't be double-booked; people get a warning-free invite (they decide). */
    synchronized Event schedule(String title, String organizer, Set<String> attendees,
                                Slot slot, String room) {
        if (room != null && byRoom.getOrDefault(room, List.of()).stream()
                .anyMatch(e -> e.slot().overlaps(slot)))
            throw new IllegalStateException(room + " is already booked then");
        Event e = new Event("EV-" + nextId++, title, organizer, Set.copyOf(attendees),
                slot, room);
        Set<String> everyone = new HashSet<>(attendees);
        everyone.add(organizer);
        everyone.forEach(p -> byPerson.computeIfAbsent(p, k -> new ArrayList<>()).add(e));
        if (room != null) byRoom.computeIfAbsent(room, k -> new ArrayList<>()).add(e);
        return e;
    }

    List<Event> conflictsFor(String person, Slot slot) {
        return byPerson.getOrDefault(person, List.of()).stream()
                .filter(e -> e.slot().overlaps(slot)).toList();
    }

    /** Earliest gap of `length` inside `window` when everyone is free. */
    Optional<Slot> firstCommonFree(Set<String> people, Slot window, Duration length) {
        List<Slot> busy = people.stream()
                .flatMap(p -> byPerson.getOrDefault(p, List.of()).stream())
                .map(Event::slot)
                .filter(s -> s.overlaps(window))
                .sorted(Comparator.comparing(Slot::start))
                .toList();
        Instant cursor = window.start();
        for (Slot b : busy) {
            if (!cursor.plus(length).isAfter(b.start()))            // gap before this meeting
                return Optional.of(new Slot(cursor, cursor.plus(length)));
            if (b.end().isAfter(cursor)) cursor = b.end();          // skip past this meeting
        }
        Instant end = cursor.plus(length);
        if (end.isAfter(window.end())) return Optional.empty();
        return Optional.of(new Slot(cursor, end));
    }
}
```

## Step 5: The free-slot algorithm

To find the first gap of 45 minutes for Asha, Bilal and Chetan:

1. Collect everyone's busy slots inside the window and **sort them by start**: 10:00–11:00, 10:00–11:00, 11:30–12:00, 11:30–12:00.
2. Start a cursor at the window start, 09:30.
3. For each busy slot: if `cursor + 45 min` fits before it starts, that's the answer. Otherwise move the cursor to the end of that busy slot (if later).
4. 09:30 + 45 = 10:15 > 10:00 → no; cursor → 11:00. 11:45 > 11:30 → no; cursor → 12:00.
5. No more meetings: 12:00–12:45 fits inside the window → answer.

This is the classic "merge intervals" idea: sort once, sweep once – O(n log n).

![Animation: busy meetings for three people are sorted on a timeline; a cursor starts at 9:30 and needs 45 minutes; the gap before 10:00 is too short so the cursor jumps to 11:00; the gap before 11:30 is too short so it jumps to 12:00; there the 45-minute slot from 12:00 to 12:45 fits.](learning-figures/lld-20-freeslot.gif)

> **⚠️ Common mistake**
> Storing recurring events as "UTC 13:00 every Monday". When the organiser's country changes its clocks, the meeting silently moves by an hour in their own time. Store the local time **and** the zone ID, and expand with time-zone rules.

> **🎯 In the interview**
> Room booking across servers needs the same atomic check as any booking: a database exclusion constraint (PostgreSQL `EXCLUDE USING gist` on room + time range) makes overlapping room bookings impossible.

## Step 6: Deep dives

### Invitations and responses

Add an `Invitation` per attendee with status (pending, accepted, declined, tentative). Free-slot search can ignore events the person declined.

### Full recurrence rules

Real calendars use iCalendar RRULEs ("every 2nd Tuesday", "last weekday of the month") and exceptions ("skip 25 Dec", "move this one to 11:00"). Store the rule plus a list of exceptions, and expand only the range being viewed.

### Fast day and week views

Keep each person's events in a sorted structure (a `TreeMap` by start, or a database index on (person, start)), so "events this week" is a range query.

### Working hours and time zones per person

Each user has a zone and working hours; the free-slot search intersects the window with every attendee's working hours, converted to instants.

## Interviewer follow-ups

**Why half-open intervals?** So back-to-back meetings don't conflict and adjacent slots tile perfectly with no gaps or overlaps.

**Why not store local date-times?** "10:00" means different moments in Bengaluru and New York. Instants are unambiguous; local times are for display and for rules.

**How do you handle a 500-person all-hands?** Store the event once and reference it from attendees, rather than copying it 500 times; free-slot search for 500 people is rarely needed.

**How would you suggest several options, not just the first?** Keep sweeping after the first match and collect up to N gaps, maybe preferring mid-morning.

## Wrap up

Slots are half-open ranges of instants; rooms are protected by an overlap check; free slots come from sorting busy times and sweeping; recurring events keep their local time and zone and are expanded with time-zone rules.

> **📝 Key takeaways**
> - Store instants; keep the zone with the recurrence rule.
> - Half-open intervals: back-to-back is not a conflict.
> - Rooms are booked atomically; people may be double-booked with a warning.
> - Free-slot search = sort busy slots, sweep with a cursor.
