## Problem

Design the game Snake & Ladder. Two or more players take turns rolling a die and moving along a board of 100 cells. Landing at the foot of a ladder takes you up; landing on a snake's head takes you down. The first player to land exactly on 100 wins.

It's a favourite interview warm-up because it is small enough to finish – and it still tests clean classes, a testable random element, and rules such as "what if a ladder ends on a snake?".

## Requirements

- A board of N cells (usually 100) with snakes and ladders.
- 2 or more players take turns in order; everyone starts off the board (cell 0).
- Roll a die, move, follow at most one snake or ladder, then pass the turn.
- You must land exactly on the last cell to win; overshooting means you stay put.
- The game can be replayed and tested with fixed dice rolls.

## Step 1: Clarify the requirements

**Candidate:** How many players and dice?

**Interviewer:** Two to four players, one six-sided die.

**Candidate:** Do you need an exact roll to finish?

**Interviewer:** Yes. If you'd go past 100, you don't move.

**Candidate:** Can a ladder end on a snake's head?

**Interviewer:** Your call – explain it.

**Candidate:** Does rolling a 6 give an extra turn?

**Interviewer:** Not in the basic version. Mention how you'd add it.

**Candidate:** Is it played by people or simulated?

**Interviewer:** Both – we also run simulations to test board designs.

> **🎯 In the interview**
> Ask about exact-finish and chained jumps. They are the two rules people forget, and they shape the `Board` validation and the turn logic.

| Functional | Non-functional |
| --- | --- |
| Board with snakes and ladders | Rules easy to change (extra turn on 6) |
| Turns, moves, winner | Deterministic tests: dice can be fixed |
| Exact finish | Invalid boards rejected at creation |

## Step 2: Identify the core objects

- **Board** – size and a map from start cell to end cell (snakes and ladders).
- **Jump** – one snake or ladder: start and end.
- **Dice** – an interface; `RandomDice` for real games, `FixedDice` for tests and replays.
- **Player** – a name.
- **Game** – positions, the turn order, the winner, and `playTurn()`.
- **Move** – what happened in one turn: roll, from, to, and a note ("ladder", "snake", "needs exact roll").

[![Selected design: the game asks the dice for a roll, moves the current player, asks the board whether the target cell starts a snake or ladder, records the move and passes the turn, or declares the winner on the last cell.](designs/lld-17.svg)](designs/lld-17.svg)

> **⚖️ Design choice**
> Snakes and ladders are the **same thing**: a jump from one cell to another. One `Jump` record and one map replace two class hierarchies – a snake simply has `end < start`.

## Step 3: Design the classes

### Board and Jump

The board validates jumps when it's created: on the board, not from the last cell, one jump per start cell, and no jump ending where another starts.

### Dice

An interface with `roll()`. Injecting it is what makes the game testable.

### Game, Player and Move

`Game` keeps a queue of players for turn order and a map of positions. `playTurn` returns a `Move`, so the UI or a log can show exactly what happened.

[![Class diagram: Game has a Board, a Dice and a queue of Players with positions, and returns a Move per turn; Board has Jumps; RandomDice and FixedDice implement Dice.](learning-figures/lld-17-classes.svg)](learning-figures/lld-17-classes.svg)

## Step 4: Write the code

### Board and Jump

```java
/** A snake (end below start) or a ladder (end above start). */
record Jump(int start, int end) {
    boolean isSnake() { return end < start; }
}

class Board {
    private final int size;
    private final Map<Integer, Integer> jumps = new HashMap<>();

    Board(int size, List<Jump> list) {
        this.size = size;
        for (Jump j : list) {
            if (j.start() <= 1 || j.start() >= size || j.end() < 1 || j.end() > size)
                throw new IllegalArgumentException("Jump off the board: " + j);
            if (jumps.putIfAbsent(j.start(), j.end()) != null)
                throw new IllegalArgumentException("Two jumps start at " + j.start());
        }
        for (Jump j : list)                                 // one jump per landing, no chains
            if (jumps.containsKey(j.end()))
                throw new IllegalArgumentException("Jump ends on another jump: " + j);
    }
    int size()                   { return size; }
    int afterJump(int cell)      { return jumps.getOrDefault(cell, cell); }
}
```

### Dice

```java
interface Dice { int roll(); }

class RandomDice implements Dice {
    private final Random random = new Random();
    public int roll() { return random.nextInt(6) + 1; }
}

/** For tests and replays: returns a fixed sequence of rolls. */
class FixedDice implements Dice {
    private final Iterator<Integer> rolls;
    FixedDice(Integer... rolls) { this.rolls = List.of(rolls).iterator(); }
    public int roll() { return rolls.next(); }
}
```

### Game

```java
record Player(String name) {}

record Move(Player player, int roll, int from, int to, String note) {}

class Game {
    private final Board board;
    private final Dice dice;
    private final Deque<Player> turns;
    private final Map<Player, Integer> position = new HashMap<>();
    private Player winner;

    Game(Board board, Dice dice, List<Player> players) {
        if (players.size() < 2) throw new IllegalArgumentException("Need at least 2 players");
        this.board = board; this.dice = dice; this.turns = new ArrayDeque<>(players);
        players.forEach(p -> position.put(p, 0));           // everyone starts off the board
    }

    Move playTurn() {
        if (winner != null) throw new IllegalStateException(winner.name() + " already won");
        Player p = turns.pollFirst();
        int roll = dice.roll(), from = position.get(p), target = from + roll;
        String note;
        int to;
        if (target > board.size()) { to = from; note = "needs exact roll"; }
        else {
            to = board.afterJump(target);
            note = to > target ? "ladder" : to < target ? "snake" : "";
        }
        position.put(p, to);
        if (to == board.size()) winner = p; else turns.addLast(p);
        return new Move(p, roll, from, to, note);
    }

    Optional<Player> winner() { return Optional.ofNullable(winner); }
    int positionOf(Player p)  { return position.get(p); }
}
```

### Edge cases

| Case | Behaviour |
| --- | --- |
| Fewer than 2 players | Rejected |
| Two players on the same cell | Allowed – no capturing |
| Turn after the game ended | `IllegalStateException` |
| Board with a jump from the last cell, or a chain | Rejected when the board is built |

## Step 5: The tricky part: a jump that lands on a jump

What if the ladder 3→8 ends on a snake's head at 8 (8→2)? Two possible rules:

- **Follow the chain:** 3 → 8 → 2 → maybe another jump… With a careless board, 8→2 and 2→8 loop forever.
- **One jump per landing:** only the first jump applies.

Our `Board` avoids the question by **rejecting** a board where a jump ends on another jump's start. Rules about the board are checked once, when it's built, not on every turn.

![Animation: a board is built with a ladder from 3 to 8 and a snake from 8 to 2; validation notices the ladder ends on the snake's head and rejects the board; a valid board is built instead and Asha's roll of 3 climbs the ladder to 8 and stops there.](learning-figures/lld-17-validate.gif)

> **⚠️ Common mistake**
> Using `new Random()` directly inside `Game`. You can't test "Asha lands on the snake" without controlling the die. Inject a `Dice` and use `FixedDice` in tests.

> **🎯 In the interview**
> If asked to support chains anyway, follow jumps with a limit (say 10) and validate at build time that following never revisits a cell – a small cycle check.

## Step 6: Deep dives

### Extra turn on a 6

In `playTurn`, if `roll == 6` and the player hasn't won, put them back at the **front** of the queue instead of the back. Limit it to three sixes in a row if you like.

### Two dice, different dice

`Dice` is an interface: `TwoDice` returns the sum of two rolls; a "crooked" dice for a test of probability is one more class.

### More players and a UI

`Move` records make it easy to animate each turn or print a log. Players can be humans or bots without changing `Game`.

### Simulating board designs

Run 100,000 games with `RandomDice` and record the number of turns per game – a quick way to check a board isn't too long or too short.

## Interviewer follow-ups

**Why one `Jump` instead of `Snake` and `Ladder` classes?** They have the same data and the same behaviour – move from one cell to another. Separate classes add code, not meaning.

**Why a queue for turns?** Taking the first player and adding them to the back is exactly "round robin", and removing the winner is easy.

**Where would you put the "exact finish" rule if it became optional?** In a small `FinishRule` strategy (exact, bounce back, or allow overshoot) that `Game` calls.

**How do you make the game replayable?** Store the seed or the sequence of rolls; replaying with `FixedDice` gives the same game.

## Wrap up

A Board of validated jumps, an injected Dice, and a Game that moves players in a round-robin queue and records each Move – small, testable and easy to extend.

> **📝 Key takeaways**
> - Snakes and ladders are one concept: a jump.
> - Validate the board once when it's built.
> - Inject the dice so games can be tested and replayed.
> - Turns are a queue; each turn returns a Move record.

"I model a Board with a size and a map of jumps – snakes and ladders are the same Jump record, a snake just goes down. ## Problem

Design the booking core of a train reservation system like IRCTC. The Bengaluru–Chennai Shatabdi stops at Jolarpettai and Katpadi. Asha books seat S1 from Bengaluru to Jolarpettai. Bilal then books from Jolarpettai to Chennai – and can get **the same seat S1**, because Asha leaves before he boards.

That's what makes trains different from movies or flights: a seat is sold **per stretch of the route**, not once for the whole trip. And a family of four must get seats together for the whole journey, or go on the waitlist.

## Requirements

- A train run (train + date) has a route of stops and a set of seats.
- Book one or more passengers from station A to station B.
- A seat is available if it is free on **every segment** between A and B.
- All passengers in a booking are confirmed together, or the booking is waitlisted.
- Cancelling frees the seat's segments and promotes waitlisted bookings in order.

## Step 1: Clarify the requirements

**Candidate:** Can a seat be sold to different people on different parts of the route?

**Interviewer:** Yes – that's how real trains get full use of seats.

**Candidate:** Do all passengers on one booking need confirmed seats together?

**Interviewer:** Yes. Confirm all or none.

**Candidate:** What happens when no seat is free?

**Interviewer:** Waitlist, in order. Cancellations promote them.

**Candidate:** Coach classes, quotas, berth preferences?

**Interviewer:** Mention them; one class of seats is enough for the design.

**Candidate:** How busy does it get?

**Interviewer:** Tatkal opens at 10 a.m.; thousands book the same train in the first minute.

> **🎯 In the interview**
> Ask whether seats can be reused along the route. The answer changes the core data structure from "a seat is booked" to "a seat is booked for these segments".

| Functional | Non-functional |
| --- | --- |
| Book A → B for 1–6 passengers | Never two people on one seat-segment |
| Waitlist and promotion | All-or-nothing per booking |
| Cancel | Fair, first-come waitlist |

## Step 2: Identify the core objects

- **Route** – the ordered stops; segment *i* runs from stop *i* to stop *i+1*.
- **Journey** – a booking's range of segments, `[from, to)`.
- **Seat** – a number and, for each segment, which booking holds it.
- **Booking** – PNR, passengers, journey, seats and status.
- **BookingStatus** – CONFIRMED, WAITLISTED, CANCELLED.
- **TrainRun** – one train on one date: seats, waitlist, `book` and `cancel`.

[![Selected design: a booking request for a journey from one station to another goes to the train run, which checks each seat's segments for the whole journey, holds enough seats for every passenger together or puts the booking on the waitlist, and promotes the waitlist when a cancellation frees segments.](designs/lld-18.svg)](designs/lld-18.svg)

> **⚖️ Design choice**
> Store availability **per seat, per segment**. A journey is a range of segment numbers, so "is S1 free from Jolarpettai to Chennai?" means "are segments 1 and 2 of S1 empty?".

## Step 3: Design the classes

### Route and Journey

The route turns station names into indexes. Bengaluru → Chennai with four stops is segments 0, 1 and 2.

### Seat

An array with one slot per segment, holding the booking ID or `null`. `isFree(journey)` checks the slots in the range; `hold` and `release` fill or clear them.

### Booking

Passengers, journey, the seats assigned and the status.

### TrainRun

`book` tries to confirm; if that fails it adds the booking to the waitlist queue. `cancel` frees the booking's segments and walks the waitlist in order, confirming anyone who now fits.

[![Class diagram: TrainRun has a Route, Seats and a waitlist of Bookings; a Booking has passengers, a Journey, seats and a BookingStatus; each Seat records which booking holds each segment.](learning-figures/lld-18-classes.svg)](learning-figures/lld-18-classes.svg)

### Route and Journey

        int i = stops.indexOf(station);
        if (i < 0) throw new IllegalArgumentException("Train doesn't stop at " + station);
        return i;
    }
}

/** The journey Asha asked for, as a range of segments [from, to). */
record Journey(int from, int to) {
    Journey {
        if (from >= to) throw new IllegalArgumentException("Destination is before source");

### Seat

```java
class Seat {
    private final String number;
    private final String[] heldBy;                  // one slot per segment; null = free

    Seat(String number, int segments) {
        this.number = number;
        this.heldBy = new String[segments];
    }
    String number() { return number; }

    boolean isFree(Journey j) {
        for (int s = j.from(); s < j.to(); s++) if (heldBy[s] != null) return false;
        return true;
    }
    void hold(Journey j, String bookingId) {
        for (int s = j.from(); s < j.to(); s++) heldBy[s] = bookingId;
    }
    void release(String bookingId) {
        for (int s = 0; s < heldBy.length; s++) {
            if (bookingId.equals(heldBy[s])) heldBy[s] = null;
        }
    }
}
```

### Booking

### TrainRun

```java
class TrainRun {                                    // one train on one date
    private final Route route;
    private final List<Seat> seats = new ArrayList<>();
    private final Deque<Booking> waitlist = new ArrayDeque<>();
    private int nextId = 1;

    TrainRun(Route route, int seatCount) {
        this.route = route;
        int segments = route.stops().size() - 1;
        for (int i = 1; i <= seatCount; i++) seats.add(new Seat("S" + i, segments));
    }

    /** All passengers get seats for the whole journey, or the booking is waitlisted. */
    synchronized Booking book(List<String> passengers, String from, String to) {
        Journey j = new Journey(route.index(from), route.index(to));
        Booking b = new Booking("PNR" + (1000 + nextId++), passengers, j);
        if (!tryConfirm(b)) { b.status = BookingStatus.WAITLISTED; waitlist.addLast(b); }
        return b;
    }

    synchronized void cancel(Booking b) {
        if (b.status == BookingStatus.CANCELLED) return;
        if (b.status == BookingStatus.WAITLISTED) waitlist.remove(b);
        b.seats.forEach(s -> s.release(b.id));
        b.seats.clear();
        b.status = BookingStatus.CANCELLED;
        waitlist.removeIf(this::tryConfirm);        // promote anyone who now fits, in order
    }

    private boolean tryConfirm(Booking b) {
        List<Seat> free = seats.stream().filter(s -> s.isFree(b.journey))
                .limit(b.passengers.size()).toList();
        if (free.size() < b.passengers.size()) return false;
        free.forEach(s -> s.hold(b.journey, b.id));
        b.seats.addAll(free);
        b.status = BookingStatus.CONFIRMED;
        return true;
    }
}
```

## Step 5: The booking algorithm: whole journey, whole group

The rule has two parts:

1. **Whole journey:** a seat counts only if *every* segment of the journey is free on it.
2. **Whole group:** find enough such seats for every passenger; if there aren't enough, take none.

Only after both checks pass are the segments held. Because `book` and `cancel` are `synchronized` on the train run, two Tatkal bookings can't both take the last seat.

![Animation: Asha holds seat S1 for segment 0 and Bilal holds S1 for segments 1 and 2; the family's request for segments 0 to 2 finds only S2 free throughout and is waitlisted; as Ravi, Bilal and Asha cancel, the waitlist is re-checked each time, and only when both seats are free for the whole route is the family confirmed together.](learning-figures/lld-18-segments.gif)

> **⚠️ Common mistake**
> Confirming passengers one at a time. The first two of a family of four get seats, the last two don't, and the family is split across "confirmed" and "waitlisted". Check the whole group first, then hold.

> **🎯 In the interview**
> In a database, a seat-segment is a row (or a bit in a bitmap). Holding a journey is one transaction that updates all the needed rows only if they're all free; across many train runs, partition by train and date.

## Step 6: Deep dives

### Coaches, classes and berth preferences

Group seats into coaches with a class (SL, 3A, 2A). `tryConfirm` filters by class first, then prefers lower berths or seats together, as a pluggable `SeatSelectionStrategy`.

### RAC (shared berths)

IRCTC's RAC lets two passengers share one side-lower berth. Model it as a seat with capacity 2 for RAC bookings – between confirmed and waitlisted.

### Quotas

Tatkal, ladies and senior-citizen quotas reserve some seats for some requests: tag seats with a quota and filter by the request's eligibility.

### Fast availability search

Searching thousands of trains can't scan every seat. Keep a per-train, per-segment count of free seats, updated on booking and cancellation, and use it for the search page; the exact seat check happens only when booking.

## Interviewer follow-ups

**Why segments instead of "booked from A to B" ranges on each seat?** Segments make overlap checks trivial (any slot in the range taken?) and work the same for every journey length.

**How is the waitlist fair?** It's a queue; after each cancellation we try bookings in order. A large group may wait while a smaller later booking fits – you can choose strict order instead if fairness requires it.

**What about two Tatkal bookings at the same moment?** One lock per train run here; in a database, a conditional update on the seat-segment rows so only one transaction wins.

**How do you show availability on the search page?** From the per-segment free counts – approximate, but fast; the booking step is exact.

## Wrap up

Seats are sold per segment, a booking needs every segment of its journey for every passenger, and cancellations free segments and promote the waitlist in order.

> **📝 Key takeaways**
> - A route is a list of stops; a journey is a range of segments.
> - A seat is free for a journey only if every segment in it is free.
> - Confirm the whole group or none; otherwise waitlist.
> - Cancelling frees segments and re-checks the waitlist in order.

## Problem

Design Amazon's order management: from a cart, create an order that may hold items from several sellers and warehouses; reserve inventory, take payment, split into shipments, track each shipment, and support cancellation and returns. It brings together a **State machine**, **Observer** and **Strategy** (fulfilment and payment), plus consistency across inventory and payment.

## Requirements

**Functional**
- Place an order: validate the cart, reserve inventory, charge, confirm.
- Split into shipments by warehouse and seller, each with its own lifecycle.
- Cancel (fully or one item) before shipping. Return and refund after delivery.
- Notify the customer on every change.

**Non-functional**
- No overselling and no double charging: inventory reservation and payment stay consistent, and order placement is idempotent.
- State changes follow the order lifecycle only, with a full audit history.
- Handles sale-day peaks: high write throughput, with notifications sent asynchronously.
- New payment methods and fulfilment types plug in without rewriting order flow.

## 1. Scope and chosen solution

I support multi-line orders with split shipments, cancellation before dispatch and returns after delivery. An Order owns accepted terms; each line tracks quantities; warehouse and payment integrations have stable operation references. I choose quantity accounting rather than a single SHIPPED flag.

## 2. Commands and conservation

```text
submit(checkoutId,acceptedQuote) -> Order
reserve(lineId,reservationId,quantity)
ship(eventId,lineId,shipmentId,quantity)
cancel(commandId,lineId,quantity)
returnItem(returnId,lineId,quantity,evidence)
Invariant: cancelled + shipped <= ordered; returned <= shipped
```

Every line transition locks its current version, checks remaining eligible quantity, deduplicates the operation/event and commits quantity plus outbox fact. For ordered 3, cancelled 1 and shipped 2, remaining-to-fulfil is zero. A repeated shipment event cannot increment shipped again. Cancellation racing dispatch competes for the same remaining units; the loser becomes a rejection or a return workflow. Capture-per-shipment and refunds reference actual captured amounts; a never-captured authorization is released instead of refunded. Returns append evidence without deleting original shipment history.

## 3. Final design diagram

### Worked calculation and implementation

For an order line with quantity 3, track ordered, cancelled, shipped and returned quantities explicitly. If one unit is cancelled and two ship, fulfilment is complete even though shipped quantity is less than the original three. Returns refer to shipped units and do not rewrite the original order quantity.

```text
OrderLine: ordered=3, cancelled=1, shipped=2, returned=0
Constraints: cancelled + shipped <= ordered
             returned <= shipped
Remaining to fulfil = ordered - cancelled - shipped = 0
```

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Order` | id, customer, `List<OrderLine>`, payment, status, address snapshot |
| `OrderLine` | product, seller, qty, price snapshot, line status |
| `OrderState` | `CREATED → PAYMENT_PENDING → CONFIRMED → PARTIALLY_SHIPPED → SHIPPED → DELIVERED`; `CANCELLED`, `RETURN_REQUESTED → RETURNED` |
| `Shipment` | lines, warehouse, carrier, tracking; `PACKED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED` |
| `FulfilmentStrategy` | Nearest warehouse, fewest shipments, cheapest |
| `InventoryService` | `reserve(lines, ttl)`, `commit`, `release` |
| `OrderEventPublisher` | Observer hub: `OrderConfirmed`, `ShipmentDelivered`, … |

### Design decisions & trade-offs

**1. Order status is derived from shipments and lines.** With partial shipping, an order is "shipped" only when all shipments are. Derive aggregate status from children rather than setting it independently. That prevents contradictions like "order DELIVERED, shipment still in transit".

**2. Transactional flow as a saga.** Reserve inventory (with a TTL), then charge payment, then commit inventory and confirm. On payment failure, release the inventory. Each step has a compensating action, so you can explain it without a distributed transaction.

**3. Observer for side effects.** The state machine publishes events. Email, SMS, loyalty points and analytics subscribe. Adding "notify the seller" doesn't touch `Order`.

**4. Snapshots.** Copy price, title and address into the order. Later catalogue or address edits must not rewrite history.

**5. Guarded transitions.** `cancel()` is legal only before `SHIPPED` (per line). A transition table plus `canTransition(from, to)` stops illegal moves, and an optimistic version field handles concurrent updates such as a warehouse "packed" racing a customer "cancel".

### Ownership, boundaries and invariants

**Central design question:** An order is a durable commercial record whose fulfillment and payment can progress independently.

Order snapshots buyer, lines, address, currency and totals. OrderLine references a purchased SKU snapshot. InventoryReservation, PaymentAttempt and Shipment carry separate lifecycle state. OrderCoordinator applies business policy; TaxPolicy and ShippingPolicy return deterministic quotes.

**Correctness rule:** The total equals the sum of immutable line amounts, tax, discounts and delivery under a defined rounding policy. A shipment cannot exceed purchased quantities, and retries cannot create a second paid order.

```text
orders(id,request_key,total_minor,status,version); line(id,qty,shipped_qty,cancelled_qty); shipment; payment_attempt; refund
```

### End-to-end execution trace

Validate quote; reserve inventory; create a pending order; authorize payment; confirm or compensate stock; capture according to fulfillment policy; split into shipments; record delivery; process partial refunds as separate auditable records.

### Concurrency and recovery walkthrough

Cancellation crosses shipment handoff. Compare order-line fulfillment quantities and cancel only unshipped units; compensation may become return/refund after the boundary. Late payment callbacks are deduplicated and reconciled.

### Policy choices and extension seams

One giant enum for every shipment/payment combination becomes unmaintainable. Separate state axes plus invariants give clearer composition. Saga coordination belongs in application logic, not in every OrderLine getter.

### Edge cases that change the design

Two warehouses can partially fulfill one order. Refund arithmetic must account for prorated discounts and taxes. A retry with a reused idempotency key and changed cart payload is a conflict.

**Topic-specific cases:** Duplicate checkout; inventory compensation; partial shipment; cancellation boundary; duplicate webhook; partial refund conservation; immutable price snapshots.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through integration failures

A duplicate warehouse event must not increment `shipped` twice. Use event identity and the line's legal remaining quantity. A reservation timeout that later succeeds needs reconciliation by reservation reference, especially if another warehouse was already asked to fulfil the same item.

Payments follow capture policy: authorize at order placement, perhaps capture per shipment. Refunds must reference captured amounts; a cancelled, never-captured line may need authorization release rather than a refund. Store the financial evidence instead of inferring it from shipping status.

## 6. Interviewer follow-ups

**Can an order be completed with a cancelled line?** Yes, if every unit has a final documented fulfilment disposition.

**Should a return delete a shipment?** No. The shipment happened; the return is a later event.

I make fulfilment quantitative at order-line level and derive the order summary. Immutable commercial snapshots, versioned quantity transitions and idempotent warehouse events preserve partial shipments, cancellations and returns. Financial capture/refund follows actual recorded fulfilment policy rather than one overloaded status.

## Problem

Design a calendar and meeting scheduler like Google Calendar: create events, invite attendees, detect conflicts, find free slots common to all attendees, book rooms, and handle recurring meetings and RSVPs. The core is **interval algorithms** (overlap detection and free-slot search) plus **concurrency** when two people book the same room.

## Requirements

**Functional**
- Create, update and cancel meetings with attendees, a time range, a room and an optional recurrence.
- Detect conflicts for attendees and rooms. Suggest the earliest common free slot of length D.
- RSVP (accept, decline, tentative). Notifications and reminders.

**Non-functional**
- A room can never be double-booked. Searching across many attendees must be fast.

## 1. Scope and chosen solution

I schedule meetings with rooms, attendees and recurring local-time rules. Concrete occurrences store instants; recurring definitions store local time, ZoneId and an explicit gap/overlap policy. I materialize a bounded future horizon and extend it, avoiding an impossible infinite expansion.

## 2. Reservation and edit transaction

```text
create(eventId,organizer,start,end,room,attendees) -> EventVersion
reschedule(eventId,expectedVersion,newInterval,newRoom) -> Version | Conflict
respond(invitationId,eventVersion,attendee,answer) -> AttendanceState
conflict(a,b) = a.start < b.end && b.start < a.end
```

The room transaction serializes interval allocation and the event version change. A failed reschedule keeps the original reservation intact. 10:00–11:00 and 11:00–12:00 coexist; 10:30–11:30 conflicts. Editing one recurrence creates an exception; “this and future” splits the series under explicit identity/version rules. Responses to an old invitation version do not overwrite the new version's attendance. A 09:00 Europe/London weekly rule is re-expanded using timezone rules, not by adding a fixed UTC offset forever. Late notifications refer to event versions and cannot resurrect cancelled occurrences.

An **event** is a user's scheduling intent; an **occurrence** is one dated instance of a recurring event; a **resource reservation** claims a room over an interval. Separate personal invitations from the room's exclusive allocation.

### Selected algorithm

```text
Overlap(a,b) = a.start < b.end AND b.start < a.end
10:00-11:00 vs 11:00-12:00: no overlap
10:00-11:00 vs 10:30-11:30: overlap
```

Store instants for concrete occurrences and a `ZoneId` plus local rule for recurrence. Some local times are missing or duplicated during clock changes; choose a policy and show it to the organizer rather than silently shifting an important meeting.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Interval` (record) | start, end (half-open `[s, e)`), `overlaps(other)` |
| `Meeting` | id, organiser, attendees, interval, room, recurrence rule |
| `Calendar` | Per user: `TreeMap<Instant, Meeting>` keyed by start |
| `Room` + `RoomCalendar` | Same structure, plus capacity and features |
| `ConflictChecker` | `hasConflict(calendar, interval)` in O(log n) |
| `SlotFinder` | Merge busy intervals across attendees, scan the gaps |
| `RecurrenceRule` | RRULE-like; expands occurrences lazily within a window |
| `Invitation` | attendee, RSVP status |

### Design decisions & trade-offs

**1. Overlap in O(log n).** With a calendar sorted by start and no internal overlaps (true for rooms), check `floorEntry(newStart)` (does it end after `newStart`?) and `ceilingEntry(newStart)` (does it start before `newEnd`?). People *can* have overlapping events, so use an interval tree, or accept the O(log n + k) scan for a person.

**2. Common free slot.** Gather all attendees' busy intervals in `[from, to]`, sort by start, merge the overlapping ones, then walk the gaps and return the first gap ≥ D (respecting working hours). That's O(M log M) for M intervals. It's the classic "merge intervals" pattern from DSA.

**3. Room booking atomicity.** Lock per room (`ConcurrentHashMap<RoomId, ReentrantLock>`), re-check the conflict and insert. In a database: a range-exclusion constraint, or `INSERT … WHERE NOT EXISTS (overlapping)` under serializable isolation.

**4. Recurring meetings.** Store the rule plus exceptions, not 520 copies. Expand on read within the query window. Editing "this and following" splits the rule into two series.

**5. Time zones.** Store instants in UTC and the organiser's zone with the rule. "9am every Monday" must survive DST shifts, so expand recurrence in the event's zone.

### Ownership, boundaries and invariants

**Central design question:** Meeting time is an interval plus a time-zone interpretation; recurrence is a rule, not an infinite row list.

Calendar owns Events and access rules. Event contains organizer, attendees, start/end instants and display zone. RecurrenceRule defines repeated local times; OccurrenceOverride changes or cancels a single instance. AvailabilityService merges busy intervals; Invitation tracks response independently.

**Correctness rule:** End is after start, resource calendars cannot contain overlapping confirmed reservations, and an occurrence identity remains stable when one instance is edited. Personal calendars may intentionally allow overlaps.

```text
event(id,start_instant,end_instant,zone,recurrence_rule,version); occurrence_override(event_id,original_start,status); invitation(event_id,attendee,response)
```

### End-to-end execution trace

Validate organizer permissions and interval; expand only the requested recurrence horizon; check resource conflicts; save event and invitation intent atomically; notify after commit; track accept/decline responses with versions; apply single-occurrence overrides separately.

### Concurrency and recovery walkthrough

Two organizers reserve one room for overlapping intervals. An authoritative room-schedule lock or range exclusion constraint decides the winner. Availability lookup alone is advisory.

### Policy choices and extension seams

Persisting local recurrence rule plus zone preserves a recurring 09:00 meeting across daylight-saving changes. Persisting only UTC repetitions can shift local time. Strategy can rank suggested slots; it must not bypass room constraints.

### Edge cases that change the design

A daylight-saving gap may make a local time nonexistent, while an overlap makes it ambiguous. Choose and display a resolution policy. Half-open intervals allow back-to-back meetings. All-day events should use dates rather than pretending every day is exactly 24 hours.

**Topic-specific cases:** Adjacent slots; room conflict; personal overlap policy; daylight-saving gap/overlap; single-occurrence edit; duplicate invitation; unauthorized calendar access.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through edits and concurrency

Two organizers can race for an empty room. A preflight availability search is useful but cannot establish the reservation. The room's transaction/interval constraint decides. Changing room or time should release the old reservation only if acquiring the new one succeeds atomically under the chosen storage design.

Editing one occurrence creates an exception; editing “this and future” may split the recurring series. Expanding an infinite series into database rows is impossible, so use a bounded scheduling horizon and extend it with conflict handling. Version invitations so late responses to an old time do not overwrite responses to the replacement event.

## 6. Interviewer follow-ups

**Does a declined attendee response free the room?** No. The organizer's event owns it until cancellation or modification.

**Does storing UTC solve recurrence?** It solves concrete instants, not recurring local-time intent.

## 7. Closing answer

I separate event intent, dated occurrences and exclusive room allocation. Half-open intervals define conflicts, timezone-aware recurrence preserves local intent, and versioned edits acquire replacement reservations before releasing old ones. Invitation responses cannot silently alter room ownership.
