## Problem

Design Snake & Ladder: N players take turns rolling dice and move along a board of 100 cells; snakes send you down, ladders send you up, and the first to reach 100 wins. Interviewers use it to test a **game-engine abstraction**: clean entities, configurable rules and **Strategy** for dice and rule variations.

## Requirements

**Functional**
- Configurable board size, snakes and ladders (validated: no cycles, nothing starting at the end cell).
- 2+ players in a turn queue. One or more dice.
- Rule variants: exact roll needed to finish, extra turn on a 6, three 6s forfeits the turn.
- Report each move and the winner. Optionally continue to rank all players.

**Non-functional**
- Deterministic and testable: dice and randomness are injectable (seeded).
- Rule variants are configurable without changing the game loop.
- The board is validated once at setup, not during play.

## Learn through a concrete example

A player on square 97 rolls 5 on a 100-square board. Do they stay at 97, bounce back, or finish? Different rules produce different valid games. The design must state the rule before hiding it in an `if` statement.

The **board** stores snakes and ladders, the **dice source** produces a roll, and the **game** owns turn order and player positions. Randomness is an input boundary, so tests should supply predetermined rolls rather than hope the right number appears.

## See a turn and chained jumps

![The game applies movement policy before resolving a jump.](lessons/lld-17-flow.svg)

*The game applies movement policy before resolving a jump.*

![Validate jump chains or restrict the board to one jump per landing.](lessons/lld-17-failure.svg)

*Validate jump chains or restrict the board to one jump per landing.*

### Build and reason

```java
// Rule sketch: exact landing; an overshoot leaves the position unchanged.
int advance(int current, int roll, int lastSquare) {
    if (roll < 1 || roll > 6) throw new IllegalArgumentException();
    int target = current + roll;
    return target > lastSquare ? current : target;
}
```

For a board with six-sided dice, the expected single roll is `(1+2+3+4+5+6)/6 = 3.5`. That is not the expected net movement once snakes, ladders and overshoot rules apply. Avoid replacing the actual board process with this average when explaining game duration.

## Design details and alternatives

### Key abstractions

| Type | Responsibility |
|---|---|
| `Game` | Turn loop, winner detection |
| `Board` | size, `Map<Integer, Integer> jumps` (start → end) |
| `Jump` (or `Snake`/`Ladder` subtypes) | start, end; a snake has end < start |
| `Player` | name, position |
| `Dice` (Strategy) | `StandardDice(count)`, `CrookedDice` (only even numbers), `FixedDice` for tests |
| `RuleSet` | `ExactFinishRule`, `ExtraTurnOnSix`, `ThreeSixesForfeit` |
| `BoardFactory` | Builds a board from config and validates it |

```java
int move(Player p, int roll) {
    int target = p.position() + roll;
    if (target > board.size()) return p.position();     // exact-finish rule
    return board.jumps().getOrDefault(target, target);   // O(1) snake/ladder
}
```

### Design decisions & trade-offs

**1. Snakes and ladders are the same thing.** Both are a jump from `start` to `end`. One `Map<Integer, Integer>` handles both in O(1). Separate classes add nothing except display labels. This is a nice "avoid needless inheritance" point.

**2. Dice as a Strategy.** It makes the game testable: inject `FixedDice(4, 2, 6)` to script a game. Variants (two dice, crooked dice) don't touch `Game`.

**3. Rules as composable objects.** Rule toggles change between house variants. A list of `Rule` objects consulted in order (`afterRoll`, `canFinish`, `grantsExtraTurn`) keeps the turn loop stable.

**4. Turn order.** Use a `Deque<Player>`: poll, play, offer back (unless they finished or forfeit). With an extra-turn rule, re-offer to the front.

**5. Board validation.** Reject jumps that start at 1 or 100, jumps that land on another jump's start (chains), and two jumps from the same cell. Fail at construction, not mid-game.

### Ownership, boundaries and invariants

**Central design question:** Make game rules explicit, especially overshoot and whether special squares chain.

Board maps starting squares to Jump targets; Game owns Players and current turn. Dice is an injected source of bounded values. MovePolicy handles exact-finish rules; TurnPolicy handles extra turns. Randomness is a dependency so tests can be deterministic.

**Correctness rule:** Player positions stay within board bounds, every jump target is valid, and terminal games stop accepting moves. A malformed jump cycle cannot cause an infinite turn.

```text
game(id,board_size,current_player,version); player(id,position); jump(from_square,to_square); turn(id,roll,result)
```

### State machine and command contracts

```text
READY -> RUNNING -> WON; each turn carries a sequence and one accepted roll
```

### End-to-end execution trace

Verify current player; obtain a dice value from the configured dice; compute tentative square; apply overshoot policy; resolve the allowed snake/ladder behavior with a visited set if chaining is supported; commit the final position; declare victory or advance turn.

### Concurrency and recovery walkthrough

Two roll commands for the same turn use different random values. A turn request ID and aggregate version prevent both from advancing the game; persist the chosen roll before returning success.



### Policy choices and extension seams

A map from square to destination is sufficient for snakes and ladders. Subclasses for every snake add little value. Strategy becomes useful for house rules, number of dice or finish behavior.

### Edge cases that change the design

Reject jumps from or to invalid squares, duplicate jump origins and forbidden start/end cells. Decide whether landing on a ladder leads to another jump. Do not quietly hard-code a popular house rule as the only valid ruleset.

### Verification and a practical lab

**Topic-specific cases:** Deterministic dice; overshoot; exact finish; cycle detection; extra-turn rule; duplicate roll command; board configuration validation.

**Lab:** Use scripted rolls to land on a snake, a ladder and an overshoot in consecutive turns. Then enable chained jumps and inject a cycle to verify validation.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

## Work through extension seams

Represent jumps as data `start -> end`; validate endpoints inside the board and forbid a zero-length jump. If the chosen rules allow at most one jump per turn, document that instead of accidentally chaining jumps because the implementation uses recursion.

Rules such as “roll six again” and “three sixes lose the turn” belong in a turn policy with an explicit roll history. They do not belong in the physical dice implementation. A replay log should store actual rolls and committed moves so results remain reproducible even if a random generator changes.

## Practise, then check your reasoning

1. **How do you test a ladder landing?** Inject a roll that reaches its starting square and assert the final destination.
2. **Should a winner keep receiving turns?** No. Define whether the game ends at first victory or ranks all players, then enforce that terminal policy.
3. **Exercise:** replay `[3,6,2]` from known positions, test the 97+5 boundary and reject a cyclic jump map. No test should depend on luck or sleeping.

## Problem

Design a train reservation system like IRCTC: search trains between stations on a date, check availability per class, book seats for several passengers, handle waitlists and RAC, and cancel. The distinctive challenge is **segment-based seat allocation**: one seat can be sold Delhi→Agra and again Agra→Bhopal on the same journey. It all has to be correct under heavy **concurrency** (Tatkal rush).

## Requirements

**Functional**
- Search trains by source, destination and date. Show classes, fare and availability.
- Book up to 6 passengers on one PNR, with berth preferences.
- Allocate a confirmed seat, else RAC, else a waitlist position. Cancellations promote waitlisted passengers.
- Cancellation and refund rules depend on time to departure.

**Non-functional**
- No overlapping allocation of a seat on any segment. Fair under huge spikes.

## Learn through a concrete example

A train visits A, B, C and D. One passenger books seat 12 from A to C; another can use the same seat from C to D. Marking seat 12 as globally booked wastes valid capacity. Occupancy belongs to journey segments on one dated train run.

A **route** defines ordered stops, a **run** is a train on a date, and a **reservation** owns seat capacity between two stop indices. For run R, A–C occupies `[0,2)` and C–D occupies `[2,3)`, which do not overlap.

## See segment ownership

![A seat must be free for every occupied segment in the requested interval.](lessons/lld-18-flow.svg)

*A seat must be free for every occupied segment in the requested interval.*

![Reserve the full requested journey or nothing.](lessons/lld-18-failure.svg)

*Reserve the full requested journey or nothing.*

### Build and calculate

For a route with S stops, each seat has S−1 travel segments. A bitset can represent segment occupancy for a fixed run; interval records can be clearer when route lengths vary. Both require an atomic check-and-reserve operation.

```text
Existing seat 12: A-C = [0,2)
New request C-D = [2,3): allowed
New request B-D = [1,3): overlaps, reject for this seat
```

## Design details and alternatives

### Key abstractions

| Type | Responsibility |
|---|---|
| `Station`, `Train`, `Route` (ordered stops) | Static data |
| `TrainRun` | Train + date: the bookable instance |
| `Coach`, `Seat` | Layout, class and berth type |
| `SeatInventory` | Per seat, a bitset of occupied segments (stop i → i+1) |
| `Booking` / `PNR` | passengers, status per passenger: `CNF`, `RAC`, `WL` |
| `WaitlistQueue` | Per run and class, FIFO; promotion on cancellation |
| `AllocationStrategy` | Berth preference, keep a group together, minimise fragmentation |

### Design decisions & trade-offs

**1. Segments, not seats.** Number the stops 0..k. A journey from stop `a` to `b` occupies segments `[a, b)`. Each seat keeps a `BitSet` (or `long` bitmask when k ≤ 64). It's available iff `(mask & journeyMask) == 0`, and booking does `mask |= journeyMask`. That's O(1) per seat check.

**2. Allocation strategy.** Prefer seats whose occupied segments are adjacent to the journey (best fit), so long journeys aren't blocked by scattered short bookings. This is the interval-scheduling or fragmentation trade-off, and it's worth mentioning.

**3. Concurrency.** Lock per `(TrainRun, Class)` partition, not globally. Within the lock: find seats, set the masks, write the booking. At scale: a sharded inventory service per train run with a single writer per partition (an actor or queue model), which gives fairness and no lock storms during Tatkal.

**4. Waitlist and RAC.** When there are no confirmed seats, use RAC (a shared side-lower berth, two passengers), then WL. On cancellation: free the segment bits, then promote RAC → CNF and WL → RAC in FIFO order, inside the same partition lock.

**5. PNR status per passenger.** One PNR can be partly confirmed. Model status on each passenger, not on the booking.

### Ownership, boundaries and invariants

**Central design question:** A train seat is occupied over station segments, so availability cannot be one boolean for the entire journey.

TrainRun identifies a dated journey; Route has ordered Stations. Coach and Seat describe physical inventory. Reservation contains origin and destination indexes, passenger and status. SegmentInventory tracks occupied legs; AllocationPolicy handles class and adjacency preferences.

**Correctness rule:** A seat can be sold to two passengers only when their half-open segment intervals do not overlap. A reservation from station i to j occupies legs i through j-1.

```text
run(id,service_date,route_version); seat(run_id,seat_id,occupied_mask,version); reservation(id,from_index,to_index,hold_id,status)
```

### State machine and command contracts

```text
AVAILABLE segments -> HELD -> CONFIRMED -> CANCELLED; waitlist WAITING -> OFFERED -> CONFIRMED
```

### End-to-end execution trace

Validate station order and dated run; find seats with every requested segment free; atomically claim the segment set; create an expiring hold; confirm after payment; release only those segments on cancellation and promote waitlisted passengers according to policy.

### Concurrency and recovery walkthrough

Requests A-to-C and B-to-D both see the same seat. Their bit masks overlap on B-to-C; atomic mask update or locked segment rows permits one. A-to-B and B-to-C can safely share the seat.



### Policy choices and extension seams

A bitset is compact for a short fixed route; relational segment rows make constraints and reporting clearer. Waiting lists require fairness and partial allocation rules; a universal seat-level free flag cannot model them.

### Edge cases that change the design

Route changes and coach substitutions need migration policies for existing reservations. Store service date and station zones explicitly. Cancellation after partial journey must not resell already traversed segments as future inventory.

### Verification and a practical lab

**Topic-specific cases:** Overlapping and adjacent segments; multi-seat atomicity; waitlist order; partial cancellation; late payment; route-version mismatch.

**Lab:** For A-B-C-D, reserve A-C and test B-D rejection plus C-D acceptance. Cancel A-C and verify only A-B and B-C are released.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

## Work through waitlists and cancellation

Waitlist priority must be defined for the whole requested interval. Freeing A–B does not satisfy a passenger waiting for A–D. A cancellation releases only the original booking's segments, then reevaluates eligible waiting requests under the fairness policy.

Two allocation workers must not both observe a free bitset and write independent updates. Lock the run-seat allocation or perform a versioned conditional update. Multi-passenger adjacent-seat requests need all-or-nothing allocation if the product promises seating together.

Keep route indices with a route version; changing a timetable's stop order must not reinterpret issued tickets. Price and cancellation fee snapshots preserve the contract even when tariffs later change.

## Practise, then check your reasoning

1. **Can the same seat have two tickets on a run?** Yes, for non-overlapping intervals.
2. **Does cancelling A–C also free C–D?** No. That may belong to another passenger.
3. **Exercise:** book A–C and C–D, reject B–D, cancel A–C, then accept A–B without affecting C–D. Race two requests for the last available segment and assert a single owner.

## Problem

Design Amazon's order management: from a cart, create an order that may hold items from several sellers and warehouses; reserve inventory, take payment, split into shipments, track each shipment, and support cancellation and returns. It brings together a **State machine**, **Observer** and **Strategy** (fulfilment and payment), plus consistency across inventory and payment.

## Requirements

**Functional**
- Place an order: validate the cart, reserve inventory, charge, confirm.
- Split into shipments by warehouse and seller, each with its own lifecycle.
- Cancel (fully or one item) before shipping. Return and refund after delivery.
- Notify the customer on every change.

**Non-functional**
- No overselling and no double charging: inventory reservation and payment stay consistent, and order placement is idempotent.
- State changes follow the order lifecycle only, with a full audit history.
- Handles sale-day peaks: high write throughput, with notifications sent asynchronously.
- New payment methods and fulfilment types plug in without rewriting order flow.

## Learn through a concrete example

An online order contains a book from warehouse A and a charger from warehouse B. The book ships first. A single order-level `SHIPPED` flag cannot say whether both items shipped, whether the charger was cancelled, or which amount can be refunded.

Separate the **order** from its **lines**, **inventory reservations**, **shipments** and **payment operations**. An order summarizes the commercial agreement; fulfilment facts belong at the line/quantity level. Start with one transactional order store and explicit integrations.

## See split fulfilment

![Ordered quantities are partitioned across fulfilment outcomes.](lessons/lld-19-flow.svg)

*Ordered quantities are partitioned across fulfilment outcomes.*

![A line cannot be both newly cancelled and dispatched for the same units.](lessons/lld-19-failure.svg)

*A line cannot be both newly cancelled and dispatched for the same units.*

### Build and calculate

For an order line with quantity 3, track ordered, cancelled, shipped and returned quantities explicitly. If one unit is cancelled and two ship, fulfilment is complete even though shipped quantity is less than the original three. Returns refer to shipped units and do not rewrite the original order quantity.

```text
OrderLine: ordered=3, cancelled=1, shipped=2, returned=0
Constraints: cancelled + shipped <= ordered
             returned <= shipped
Remaining to fulfil = ordered - cancelled - shipped = 0
```

## Design details and alternatives

### Key abstractions

| Type | Responsibility |
|---|---|
| `Order` | id, customer, `List<OrderLine>`, payment, status, address snapshot |
| `OrderLine` | product, seller, qty, price snapshot, line status |
| `OrderState` | `CREATED → PAYMENT_PENDING → CONFIRMED → PARTIALLY_SHIPPED → SHIPPED → DELIVERED`; `CANCELLED`, `RETURN_REQUESTED → RETURNED` |
| `Shipment` | lines, warehouse, carrier, tracking; `PACKED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED` |
| `FulfilmentStrategy` | Nearest warehouse, fewest shipments, cheapest |
| `InventoryService` | `reserve(lines, ttl)`, `commit`, `release` |
| `OrderEventPublisher` | Observer hub: `OrderConfirmed`, `ShipmentDelivered`, … |

### Design decisions & trade-offs

**1. Order status is derived from shipments and lines.** With partial shipping, an order is "shipped" only when all shipments are. Derive aggregate status from children rather than setting it independently. That prevents contradictions like "order DELIVERED, shipment still in transit".

**2. Transactional flow as a saga.** Reserve inventory (with a TTL), then charge payment, then commit inventory and confirm. On payment failure, release the inventory. Each step has a compensating action, so you can explain it without a distributed transaction.

**3. Observer for side effects.** The state machine publishes events. Email, SMS, loyalty points and analytics subscribe. Adding "notify the seller" doesn't touch `Order`.

**4. Snapshots.** Copy price, title and address into the order. Later catalogue or address edits must not rewrite history.

**5. Guarded transitions.** `cancel()` is legal only before `SHIPPED` (per line). A transition table plus `canTransition(from, to)` stops illegal moves, and an optimistic version field handles concurrent updates such as a warehouse "packed" racing a customer "cancel".

### Ownership, boundaries and invariants

**Central design question:** An order is a durable commercial record whose fulfillment and payment can progress independently.

Order snapshots buyer, lines, address, currency and totals. OrderLine references a purchased SKU snapshot. InventoryReservation, PaymentAttempt and Shipment carry separate lifecycle state. OrderCoordinator applies business policy; TaxPolicy and ShippingPolicy return deterministic quotes.

**Correctness rule:** The total equals the sum of immutable line amounts, tax, discounts and delivery under a defined rounding policy. A shipment cannot exceed purchased quantities, and retries cannot create a second paid order.

```text
orders(id,request_key,total_minor,status,version); line(id,qty,shipped_qty,cancelled_qty); shipment; payment_attempt; refund
```

### State machine and command contracts

```text
Order PENDING -> CONFIRMED -> PARTIALLY_FULFILLED -> FULFILLED; separate payment and refund statuses
```

### End-to-end execution trace

Validate quote; reserve inventory; create a pending order; authorize payment; confirm or compensate stock; capture according to fulfillment policy; split into shipments; record delivery; process partial refunds as separate auditable records.

### Concurrency and recovery walkthrough

Cancellation crosses shipment handoff. Compare order-line fulfillment quantities and cancel only unshipped units; compensation may become return/refund after the boundary. Late payment callbacks are deduplicated and reconciled.



### Policy choices and extension seams

One giant enum for every shipment/payment combination becomes unmaintainable. Separate state axes plus invariants give clearer composition. Saga coordination belongs in application logic, not in every OrderLine getter.

### Edge cases that change the design

Two warehouses can partially fulfill one order. Refund arithmetic must account for prorated discounts and taxes. A retry with a reused idempotency key and changed cart payload is a conflict.

### Verification and a practical lab

**Topic-specific cases:** Duplicate checkout; inventory compensation; partial shipment; cancellation boundary; duplicate webhook; partial refund conservation; immutable price snapshots.

**Lab:** Fulfill one of two lines, cancel the remainder and receive a duplicate payment webhook. Show final quantities, stock release and refund records.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

## Work through integration failures

A duplicate warehouse event must not increment `shipped` twice. Use event identity and the line's legal remaining quantity. A reservation timeout that later succeeds needs reconciliation by reservation reference, especially if another warehouse was already asked to fulfil the same item.

Payments follow capture policy: authorize at order placement, perhaps capture per shipment. Refunds must reference captured amounts; a cancelled, never-captured line may need authorization release rather than a refund. Store the financial evidence instead of inferring it from shipping status.

## Practise, then check your reasoning

1. **Can an order be completed with a cancelled line?** Yes, if every unit has a final documented fulfilment disposition.
2. **Should a return delete a shipment?** No. The shipment happened; the return is a later event.
3. **Exercise:** order three units, cancel one, ship two in separate events, replay the first event and return one. Verify quantity bounds and the exact captured/refundable amounts after each step.

## Problem

Design a calendar and meeting scheduler like Google Calendar: create events, invite attendees, detect conflicts, find free slots common to all attendees, book rooms, and handle recurring meetings and RSVPs. The core is **interval algorithms** (overlap detection and free-slot search) plus **concurrency** when two people book the same room.

## Requirements

**Functional**
- Create, update and cancel meetings with attendees, a time range, a room and an optional recurrence.
- Detect conflicts for attendees and rooms. Suggest the earliest common free slot of length D.
- RSVP (accept, decline, tentative). Notifications and reminders.

**Non-functional**
- A room can never be double-booked. Searching across many attendees must be fast.

## Learn through a concrete example

Leena books meeting room R from 10:00 to 11:00. Another meeting starts at 11:00. These can coexist under half-open intervals, but a 10:30–11:30 request conflicts. A calendar is not merely a list of timestamps: recurrence, timezones and ownership change what “the same time” means.

An **event** is a user's scheduling intent; an **occurrence** is one dated instance of a recurring event; a **resource reservation** claims a room over an interval. Separate personal invitations from the room's exclusive allocation.

## See reservation and a daylight-saving complication

![Room ownership is decided independently of email invitations.](lessons/lld-20-flow.svg)

*Room ownership is decided independently of email invitations.*

![Expand recurring occurrences using a timezone identifier and policy.](lessons/lld-20-failure.svg)

*Expand recurring occurrences using a timezone identifier and policy.*

### Build and reason

```text
Overlap(a,b) = a.start < b.end AND b.start < a.end
10:00-11:00 vs 11:00-12:00: no overlap
10:00-11:00 vs 10:30-11:30: overlap
```

Store instants for concrete occurrences and a `ZoneId` plus local rule for recurrence. Some local times are missing or duplicated during clock changes; choose a policy and show it to the organizer rather than silently shifting an important meeting.

## Design details and alternatives

### Key abstractions

| Type | Responsibility |
|---|---|
| `Interval` (record) | start, end (half-open `[s, e)`), `overlaps(other)` |
| `Meeting` | id, organiser, attendees, interval, room, recurrence rule |
| `Calendar` | Per user: `TreeMap<Instant, Meeting>` keyed by start |
| `Room` + `RoomCalendar` | Same structure, plus capacity and features |
| `ConflictChecker` | `hasConflict(calendar, interval)` in O(log n) |
| `SlotFinder` | Merge busy intervals across attendees, scan the gaps |
| `RecurrenceRule` | RRULE-like; expands occurrences lazily within a window |
| `Invitation` | attendee, RSVP status |

### Design decisions & trade-offs

**1. Overlap in O(log n).** With a calendar sorted by start and no internal overlaps (true for rooms), check `floorEntry(newStart)` (does it end after `newStart`?) and `ceilingEntry(newStart)` (does it start before `newEnd`?). People *can* have overlapping events, so use an interval tree, or accept the O(log n + k) scan for a person.

**2. Common free slot.** Gather all attendees' busy intervals in `[from, to]`, sort by start, merge the overlapping ones, then walk the gaps and return the first gap ≥ D (respecting working hours). That's O(M log M) for M intervals. It's the classic "merge intervals" pattern from DSA.

**3. Room booking atomicity.** Lock per room (`ConcurrentHashMap<RoomId, ReentrantLock>`), re-check the conflict and insert. In a database: a range-exclusion constraint, or `INSERT … WHERE NOT EXISTS (overlapping)` under serializable isolation.

**4. Recurring meetings.** Store the rule plus exceptions, not 520 copies. Expand on read within the query window. Editing "this and following" splits the rule into two series.

**5. Time zones.** Store instants in UTC and the organiser's zone with the rule. "9am every Monday" must survive DST shifts, so expand recurrence in the event's zone.

### Ownership, boundaries and invariants

**Central design question:** Meeting time is an interval plus a time-zone interpretation; recurrence is a rule, not an infinite row list.

Calendar owns Events and access rules. Event contains organizer, attendees, start/end instants and display zone. RecurrenceRule defines repeated local times; OccurrenceOverride changes or cancels a single instance. AvailabilityService merges busy intervals; Invitation tracks response independently.

**Correctness rule:** End is after start, resource calendars cannot contain overlapping confirmed reservations, and an occurrence identity remains stable when one instance is edited. Personal calendars may intentionally allow overlaps.

```text
event(id,start_instant,end_instant,zone,recurrence_rule,version); occurrence_override(event_id,original_start,status); invitation(event_id,attendee,response)
```

### State machine and command contracts

```text
Event CONFIRMED -> CANCELLED; invitation NEEDS_ACTION -> ACCEPTED | DECLINED | TENTATIVE
```

### End-to-end execution trace

Validate organizer permissions and interval; expand only the requested recurrence horizon; check resource conflicts; save event and invitation intent atomically; notify after commit; track accept/decline responses with versions; apply single-occurrence overrides separately.

### Concurrency and recovery walkthrough

Two organizers reserve one room for overlapping intervals. An authoritative room-schedule lock or range exclusion constraint decides the winner. Availability lookup alone is advisory.



### Policy choices and extension seams

Persisting local recurrence rule plus zone preserves a recurring 09:00 meeting across daylight-saving changes. Persisting only UTC repetitions can shift local time. Strategy can rank suggested slots; it must not bypass room constraints.

### Edge cases that change the design

A daylight-saving gap may make a local time nonexistent, while an overlap makes it ambiguous. Choose and display a resolution policy. Half-open intervals allow back-to-back meetings. All-day events should use dates rather than pretending every day is exactly 24 hours.

## Work through edits and concurrency

Two organizers can race for an empty room. A preflight availability search is useful but cannot establish the reservation. The room's transaction/interval constraint decides. Changing room or time should release the old reservation only if acquiring the new one succeeds atomically under the chosen storage design.

Editing one occurrence creates an exception; editing “this and future” may split the recurring series. Expanding an infinite series into database rows is impossible, so use a bounded scheduling horizon and extend it with conflict handling. Version invitations so late responses to an old time do not overwrite responses to the replacement event.
