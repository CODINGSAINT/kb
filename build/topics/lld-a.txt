## Problem

Design a parking lot system in Java with multiple floors, several vehicle and spot types, ticketing at entry, and payment at exit. This tests clean entity modelling, **Factory** and **Strategy**, and whether the design stays open for change (EV charging, new vehicle types, new pricing).

## Requirements

**Functional**
- Multiple floors, each with spots of type `COMPACT`, `LARGE`, `MOTORBIKE`, `EV`.
- Vehicles: car, bike, truck. Each fits certain spot types.
- At entry, assign a spot and issue a ticket. At exit, compute the fee, take payment and free the spot.
- Show available spots per floor and type on a display board.

**Non-functional**
- Several gates operate at the same time, so spot assignment must be thread-safe.
- Adding a vehicle type, spot type or pricing rule shouldn't mean rewriting existing classes.

## Key abstractions

| Type | Responsibility |
|---|---|
| `ParkingLot` (singleton per site) | Owns floors and gates. Facade: `park(vehicle)` and `unpark(ticket)` |
| `ParkingFloor` | Holds spots, indexed by type into free lists |
| `ParkingSpot` | id, `SpotType`, `occupiedBy`. `assign` and `release` |
| `Vehicle` (abstract) → `Car, Bike, Truck` | Plate number and `VehicleType` |
| `Ticket` | id, vehicle, spot, entry time, status |
| `SpotAllocator` (Strategy) | `NearestFirst`, `LowestFloorFirst`, `EvPreferred` |
| `FeeStrategy` (Strategy) | `HourlyFee`, `FlatWeekendFee`, `VehicleTypeMultiplier` |
| `VehicleFactory` / `SpotFactory` | Build objects from type enums |
| `Payment` | Cash, card or UPI behind a `PaymentProcessor` interface |

```java
public interface SpotAllocator {
    Optional<ParkingSpot> allocate(List<ParkingFloor> floors, VehicleType type);
}
public interface FeeStrategy {
    Money calculate(Ticket ticket, Instant exitTime);
}
```

## Design decisions & trade-offs

**1. Vehicle-to-spot compatibility as data, not `instanceof`.** Keep a `Map<VehicleType, List<SpotType>>`, for example a bike fits MOTORBIKE first, then COMPACT. A new vehicle type then means adding a map entry, not changing branching code.

**2. Allocation is a Strategy.** "Nearest to the gate" vs. "fill the lowest floor first" is a business choice that changes per site. Inject it rather than hard-coding it.

**3. Concurrency at assignment.** Two gates must never assign the same spot. Options:
- `synchronized` on the floor's free list for the type. This is simple and contention is low.
- A `ConcurrentLinkedQueue<ParkingSpot>` per type, where `poll()` is atomic. This is lock-free and the cleanest choice.
- Spot-level CAS (`AtomicReference<Vehicle>`) if you scan instead of using free lists.

**4. Pricing is a Strategy, possibly composed.** A `CompositeFee` can apply a base hourly rate, a vehicle multiplier and a weekend discount in sequence. That adds a Decorator flavour and avoids one god-method.

**5. Ticket as the source of truth.** Exit uses the ticket ID, which avoids searching for the vehicle and lets you handle lost tickets with a lookup by plate.

**6. Display board via Observer.** Spots publish `SpotFreed` and `SpotTaken` events. The board subscribes to them, so the lot doesn't know the display exists.

## Ownership, boundaries and invariants

**Central design question:** Assign a compatible physical spot exactly once, then keep ticketing and charging separate from allocation.

ParkingLot contains Floors and ParkingSpots. Vehicle and SpotType are values. AllocationPolicy chooses among compatible free spots; Ticket records vehicle, spot and entry instant. PricingPolicy computes a quote from a tariff snapshot. PaymentPort is an external boundary.

**Correctness rule:** At most one open ticket owns a spot, and a vehicle cannot acquire a second open ticket through a retried entry request. Free counts are projections of spot state, not an independent source of truth.

Begin with a single-process, testable domain model. Treat database durability, multiple JVMs, and hardware/provider calls as explicit extensions; do not claim that a Java lock gives system-wide correctness. An aggregate is the object boundary within which a command preserves its invariants. It is not necessarily an entire application or database table. Identify which values may be observed stale and which decision must be serialized before drawing a class hierarchy.

The storage outline below is a design vocabulary rather than complete executable DDL. Choose actual column types, foreign keys, indexes and retention after naming the access paths. Keep domain identities stable across retries and keep historical commercial facts immutable.

```text
spot(id,floor,type,state,version); ticket(id,vehicle_id,spot_id,entry_at,tariff_version,status,entry_request_id)
```

## State machine and command contracts

```text
FREE -> OCCUPIED -> FREE; ticket OPEN -> PAYMENT_PENDING -> PAID -> CLOSED
```

For every arrow write five things: the actor allowed to request it, the input, its precondition, the state it changes, and the durable result returned. A controller should translate input and errors, while the aggregate owns legal transitions. A policy calculates a decision without secretly writing another aggregate. External adapters translate a provider or device response into a typed outcome, including unknown outcomes.

Use a command envelope containing an operation ID, target identity, expected version where relevant, and validated arguments. Return an immutable result containing the committed version and domain outcome. Reject invalid input before a state change, but repeat mutable-state checks inside the serialization boundary. A preflight check outside a lock can improve user feedback; it cannot establish the invariant.

Do not represent every failure with `false`. Distinguish invalid input, conflict, unavailable resource, dependency failure and unknown external outcome. That distinction controls whether a client should correct input, refresh state, retry with the same identity or wait for reconciliation. A retry with a new operation identity is a new command, even when the user thinks it is the old request.

## End-to-end execution trace

Validate vehicle and gate; look up the entry request ID; find compatible candidates; claim one atomically; create the ticket in the same transaction; return its immutable ID. At exit compute the quote, request payment outside the spot lock, persist the payment result, then release the spot exactly once.

Trace one successful call through API, application service, aggregate, repository and adapter. Record the first durable fact and the exact point at which success can be acknowledged. Then replay the call with the same identity. The second response should describe the original result rather than create another effect. If the operation has no external side effect and is naturally idempotent, explain that simpler property instead of adding an unnecessary request table.

Snapshot immutable output for clients. Returning a mutable internal collection allows UI code to violate invariants without calling a command. Copy lists/sets or expose read-only views with documented lifetime; remember that an unmodifiable collection can still contain mutable elements. Keep repository concerns behind interfaces so a deterministic in-memory implementation can demonstrate the domain without pretending it models multi-process transactions.

## Concurrency and recovery walkthrough

Two entry gates both see the last free spot. A conditional FREE-to-OCCUPIED update determines the winner. A process lock is sufficient only for one JVM; multiple gates backed by different JVMs need the database constraint or equivalent authority.

Write an interleaving table before selecting a synchronization primitive:

| Step | Request A | Request B | Required observation |
|---|---|---|---|
| 1 | Reads version v | Reads version v | Both observations may be individually valid |
| 2 | Validates and attempts commit | Waits or attempts commit | One authority decides conflicts |
| 3 | Commits version v+1 | Rechecks or loses compare-and-set | B cannot rely on its old precondition |
| 4 | Returns committed result | Returns conflict or retries within policy | Retries preserve operation identity |

For one JVM, synchronize the whole check-and-update operation on the owning aggregate, or use a single-owner event loop. Thread-safe containers protect their own methods; they do not make a sequence across several objects atomic. For database-backed replicas, use conditional updates, uniqueness/exclusion constraints or row locks in a transaction. Pick a consistent lock ordering when a command owns several resources. Release locks before a slow network call, and model the pending state needed to resume later.

Recovery starts from recorded state, not from a guess about which line of Java probably ran. Persist the operation intent and classify external results. If a process fails after a provider or device acts, query/reconcile by its original reference. Do not claim rollback can reverse cash movement, a sent SMS or an already captured payment. Compensation is a new operation that can itself fail and needs its own identity and state.

## Policy choices and extension seams

Nearest-spot allocation is simple but can starve some floors; balanced allocation spreads congestion. Strategy is useful for allocation and tariffs, while a factory that merely creates every entity adds little. Snapshot the tariff so a price change does not rewrite an active ticket.

Add an interface where there are two meaningful behaviors or an unreliable boundary, not for every noun. Prefer composition when a rule changes independently of entity identity. Keep state-dependent validation close to the state owner. Patterns are useful vocabulary for a chosen responsibility: Strategy for a replaceable policy, State for legal transitions, Adapter for an external system. A diagram full of pattern names is weaker than a small model with clear mutation rules.

Time, money and randomness deserve explicit types. Use `Instant` for an absolute event time and a `ZoneId` when local calendar meaning matters. Use a monotonic elapsed-time source for duration-based quotas; wall clocks can move. Represent money in a defined currency using integral minor units or an explicit decimal/rounding policy. Guard addition/multiplication overflow and do not convert through binary floating-point. Inject a clock or dice source so tests can reproduce a boundary without sleeps or luck.

## Edge cases that change the design

A payment timeout is not a decline: keep a pending exit and reconcile the provider result. Support a lost-ticket policy explicitly. Release on confirmed exit, not merely on payment initiation. Reconstruct display-board counts after a restart.

Input validation is not the only boundary. Also bound collection sizes, pending work, callback retries and retained history. Authenticate the actor before loading private state and authorize the specific resource before applying a command. Log operation IDs, versions and state transitions; avoid logging secrets or entire payment/identity payloads. Monitoring should make a stuck pending state visible rather than converting it silently into success.

## Design decisions & trade-offs

**1. LOOK/SCAN inside each car.** A car keeps moving in its current direction, serving every stop on the way (`TreeSet.ceiling(currentFloor)`), and reverses only when nothing is left ahead. This avoids FCFS zig-zagging and starvation.

**2. Choosing a car for a hall call.** Pick by cost: an idle car pays its distance; a car moving toward the floor in the same direction pays its distance; anything else pays a penalty. `NearestCar` is the baseline, and the Strategy interface lets you add zoning (cars 1–2 serve floors 1–20) without touching the controller.

**3. State pattern for behaviour.** "Ignore movement while the doors are open" and "reject requests in Maintenance" live in state classes, not in `if` blocks inside `Elevator.step()`.

**4. Concurrency model.** Button presses happen on many threads. Put them on a `BlockingQueue<Request>`. One controller thread assigns them. Each elevator runs its own loop thread with a thread-safe stop set (or confined state plus messages). Avoid one global lock around all elevators.

**5. Simulation vs. real time.** Model a `tick()` per car so it's testable. Real hardware triggers events instead.

## Problem

Design a movie booking system like BookMyShow: browse cities, cinemas, movies and shows, pick seats and pay. The core interview challenge is **concurrency on seat selection**: two users must never book the same seat, and seats held by an abandoned checkout must free up automatically.

## Requirements

**Functional**
- Search movies by city. List shows per cinema and screen. Show a seat map.
- Select seats, hold them for a few minutes, pay, and confirm the booking.
- Cancel bookings (with a refund policy) and release unpaid holds after a TTL.

**Non-functional**
- No double booking, ever.
- Seat holds must expire without a manual cleanup step.

## Key abstractions

| Type | Responsibility |
|---|---|
| `Movie`, `Cinema`, `Screen`, `Seat` | Catalogue and static layout |
| `Show` | movie + screen + start time. Owns `ShowSeat`s |
| `ShowSeat` | seat for a particular show. Status: `AVAILABLE`, `LOCKED`, `BOOKED` |
| `SeatLockProvider` | `lock(show, seats, user, ttl)`, `unlock` and `validate` |
| `Booking` | user, show, seats, amount. State: `PENDING → CONFIRMED / CANCELLED / EXPIRED` |
| `PaymentService` | Strategy per method, plus idempotency key |
| `PricingStrategy` | seat category, weekday/weekend, dynamic pricing |

## Design decisions & trade-offs

**1. Lock then pay, not pay then lock.** Hold seats when the user selects them, with a TTL of about 5 minutes. Confirm with payment. If payment happens first, two users can both pay for the same seat.

**2. Implementing the lock (in-process LLD).**
```java
class InMemorySeatLockProvider implements SeatLockProvider {
    private final ConcurrentHashMap<SeatKey, SeatLock> locks = new ConcurrentHashMap<>();
    public synchronized boolean lock(Show s, List<Seat> seats, String user, Duration ttl) {
        if (seats.stream().anyMatch(x -> isLocked(s, x))) return false;  // all-or-nothing
        seats.forEach(x -> locks.put(new SeatKey(s, x), new SeatLock(user, now().plus(ttl))));
        return true;
    }
}
```
All-or-nothing matters: a user selecting 4 seats shouldn't get 3. Sort seat keys before locking if you use per-seat locks, so two threads can't deadlock.

**3. Expiry.** Do a lazy check (`expiresAt < now` means it's free) plus a scheduled sweeper that moves `PENDING` bookings to `EXPIRED`. In a distributed setup this becomes Redis `SET NX PX` per seat, or a DB row with `status, locked_until` and a conditional `UPDATE … WHERE status='AVAILABLE'`.

**4. Booking as a State machine.** Only `PENDING` can become `CONFIRMED`, and only if the lock is still held by this user. Re-validate the lock at confirmation time, because the TTL may have passed during a slow payment.

**5. Idempotent payment callbacks.** Gateways retry. Key the confirmation on `paymentId` so a duplicate callback can't double-confirm.

Movie, Theatre, Screen, Seat and Show describe inventory. ShowSeat is the sellable resource because the same chair belongs to different shows. Hold contains user, seats and expiry; Booking contains a price snapshot and payment reference. SeatSelectionPolicy and PaymentPort stay outside seat state.

**Correctness rule:** For a particular show-seat, at most one unexpired hold or confirmed booking owns it. All seats of a multi-seat request are claimed together or none are.

## Concurrency and recovery walkthrough

|---|---|---|---|
| 1 | Reads version v | Reads version v | Both observations may be individually valid |
| 2 | Validates and attempts commit | Waits or attempts commit | One authority decides conflicts |

## Problem

Design an ATM: card insertion, PIN entry, balance check, withdrawal, deposit and cash dispensing. This is the textbook problem for the **State** pattern (what the ATM accepts depends on where you are in the flow) and **Chain of Responsibility** (splitting an amount across note denominations).

## Requirements

**Functional**
- Insert card, then enter PIN (3 attempts, then the card is retained), then choose a transaction.
- Withdraw (within limits, in multiples of the smallest note), deposit, check balance, change PIN.
- Dispense the correct mix of notes, print a receipt, eject the card.

**Non-functional**
- Money must never be dispensed without a successful debit, and a debit must never happen without dispensing. You need a compensating action.
- The hardware (dispenser, card reader) is unreliable.

## Key abstractions

| Type | Responsibility |
|---|---|
| `ATM` | Context: holds the current `ATMState` and hardware components |

## Design decisions & trade-offs

**1. State pattern.** Each state overrides only the events it accepts. `Idle.insertCard` moves to `CardInserted`. `CardInserted.enterPin` either moves to `Authenticated` or counts a failure. Illegal actions fail loudly in one place.

**2. Chain of Responsibility for dispensing.**
```java
abstract class NoteHandler {
    NoteHandler next; int denom; int available;
    void dispense(int amount, Map<Integer,Integer> out) {
        int n = Math.min(amount / denom, available);
        if (n > 0) out.put(denom, n);
        int rest = amount - n * denom;
        if (rest > 0) { if (next == null) throw new CannotDispense(); next.dispense(rest, out); }
    }
}
```
Do a dry run first, and only debit if the plan succeeds. Adding a ₹200 note is one new handler.

**3. Debit and dispense consistency.** Order: plan the notes, then debit at the bank, then dispense. If the dispenser fails after the debit, call `bank.reverse(txId)` (a compensating transaction), and log for reconciliation. Use idempotent transaction IDs so retries don't double-debit.

**4. Security.** PIN verification happens at the bank, never locally. The ATM only sends an encrypted PIN block. Lock out after 3 failures.

**Lab:** Book adjacent intervals [10:00,11:00) and [11:00,12:00), then add a 30-minute cleaning buffer and show which request must change.

Test the invariant after each transition, not only the final happy-path response. Include two independent aggregate instances to catch accidental static/global state. Run a race test with a barrier so both contenders begin from the same observation. Use a fake clock to cross expiry boundaries exactly. Test an adapter that throws before acting and one that acts then times out; these are different failure cases. A property-based sequence test can generate valid and invalid commands and check conservation/ownership after every step.

The Java examples in `examples/reference-invariants/ReferenceInvariants.java` demonstrate selected executable mechanisms: half-open intervals, exact equal splits, expiring ownership and a token bucket. They are deliberately small examples of invariants, not complete implementations of every system. The original topic code above remains a design sketch unless explicitly marked runnable. Explain which repository/adapter must provide a production guarantee before copying a sketch into a service.

## Follow-up answers and review checklist

**Where is the first correctness boundary?** The aggregate or durable conditional update that establishes this rule: Confirmed reservations for the same vehicle must not overlap: existing.start < requested.end and requested.start < existing.end. Maintenance intervals also consume availability.

**What changes when a second process is added?** In-process locks no longer cover all writers. Move the decisive check to a shared authoritative transaction or partition owner, while retaining local encapsulation for readability.

**What happens when a response is lost?** Query the operation identity or repeat the same idempotent command. Return the known committed outcome; if an external effect is uncertain, preserve and reconcile that uncertainty.

**What should be extracted into a pattern?** Start from the actual extension seam: Assigning a concrete car early simplifies conflicts but reduces flexibility; booking a category requires capacity accounting and later assignment. A policy should calculate fees while the agreement aggregate owns legal transitions.

**What is the best next exercise?** Book adjacent intervals [10:00,11:00) and [11:00,12:00), then add a 30-minute cleaning buffer and show which request must change.

Before calling this design complete, narrate one command, one contention race and one restart. Point to the exact fields that prevent duplicate ownership or invalid transitions. State which parts are single-JVM demonstrations and which require transactional persistence. A reviewer should be able to derive tests from your invariants without reading your implementation.
