## Problem

Design a parking lot system. Cars, motorcycles and trucks arrive at an entry gate, get a ticket and park in a suitable spot. When they leave, the exit gate calculates the fee from the ticket and frees the spot.

This is the most common warm-up question in low-level design interviews. The interviewer wants to see clean classes, sensible responsibilities, and how easily your design handles change.

## Requirements

- The lot has several floors. Each spot is small, medium or large.
- Motorcycles, cars and trucks can park. A vehicle can use a spot of its size or bigger.
- The entry gate issues a ticket; the exit gate charges a fee and frees the spot.
- Fee: ₹40 for the first hour, ₹20 for every further hour that has started.
- Several gates work at the same time.

## Step 1: Clarify the requirements

Never start drawing classes straight away. Spend a few minutes agreeing on scope. A short conversation might look like this:

**Candidate:** Which vehicles do we support?

**Interviewer:** Motorcycles, cars and trucks.

**Candidate:** Are spots sized? Can a car park in a large spot?

**Interviewer:** Spots are small, medium or large. A vehicle can take a spot of its own size or bigger.

**Candidate:** If several spots fit, which one do we give?

**Interviewer:** Your choice. Explain it.

**Candidate:** I'll give the smallest spot that fits, on the lowest floor. That keeps large spots free for trucks. How is the fee calculated?

**Interviewer:** ₹40 for the first hour, then ₹20 for each hour that has started.

**Candidate:** Do we need payments, reservations or a display board?

**Interviewer:** Payment can be a simple step. Skip reservations. Mention the display board if you have time.

> **🎯 In the interview**
> Write the agreed requirements down. They become your checklist, and they stop the scope from growing while you design.

From that conversation, the requirements are:

| Functional | Non-functional |
| --- | --- |
| Park a vehicle in the smallest suitable free spot | Two gates must never give out the same spot |
| Issue a ticket at entry | Fee rules should be easy to change |
| Calculate the fee and free the spot at exit | Adding a new vehicle or spot type should be easy |
| Reject entry when no suitable spot is free | |

## Step 2: Identify the core objects

Pick out the nouns from the requirements and keep the ones that hold data or rules:

- **Vehicle** – what is parking: a motorcycle, a car or a truck.
- **ParkingSpot** – one space in the lot, with a floor, a number and a size.
- **Ticket** – proof of entry: which vehicle, which spot, and when it arrived.
- **FeeStrategy** – the rule that turns parking time into a fee.
- **ParkingLot** – the coordinator that the gates talk to.

How they connect:

[![Selected design: entry and exit gates call ParkingLot; ParkingLot finds a free ParkingSpot that holds the Vehicle, issues a Ticket and asks the FeeStrategy for the fee.](designs/lld-2.svg)](designs/lld-2.svg)

> **⚖️ Design choice**
> Gates and display boards do not get their own copy of free spots. They all ask `ParkingLot`. One owner of the spot data means two gates can never disagree about which spots are free.

## Step 3: Design the classes

### Vehicle

Every vehicle has a licence plate and a size. The three vehicle types differ only by size, so each subclass just reports its size.

[![Class diagram: Vehicle is an abstract class with a licence plate and getSize(); Motorcycle returns SMALL, Car returns MEDIUM and Truck returns LARGE. Size is an enum of SMALL, MEDIUM and LARGE.](learning-figures/lld-2-vehicles.svg)](learning-figures/lld-2-vehicles.svg)

> **⚖️ Design choice**
> We use one `Size` enum for both vehicles and spots. "Can this vehicle fit?" becomes a simple comparison: the spot's size must be the same as, or bigger than, the vehicle's size.

### ParkingSpot

A spot knows its floor, number and size, and whether a vehicle is in it. It answers one question: *can this vehicle park here right now?*

### Ticket

A ticket records the vehicle, the spot and the entry time. The exit gate needs nothing else to calculate the fee.

### FeeStrategy

Pricing rules change often: weekend rates, monthly passes, airport pricing. So we put the rule behind an interface. `ParkingLot` only knows it can ask "what is the fee from this time to that time?"

### ParkingLot

`ParkingLot` is what the gates call. It has two main methods: `parkVehicle` and `unparkVehicle`. It keeps the spots and the tickets currently in use.

Here is the complete picture:

[![Complete class diagram: ParkingLot holds ParkingSpots, issues Tickets and uses a FeeStrategy, implemented by HourlyFeeStrategy. A Ticket references one Vehicle and one ParkingSpot. A ParkingSpot can hold one Vehicle. Motorcycle, Car and Truck extend Vehicle.](learning-figures/lld-2-classes.svg)](learning-figures/lld-2-classes.svg)

## Step 4: Write the code

### Vehicle

```java
enum Size { SMALL, MEDIUM, LARGE }   // order matters: a vehicle fits a spot of its size or bigger

abstract class Vehicle {
    private final String licensePlate;
    protected Vehicle(String licensePlate) { this.licensePlate = licensePlate; }
    String getLicensePlate() { return licensePlate; }
    abstract Size getSize();
}

class Motorcycle extends Vehicle {
    Motorcycle(String plate) { super(plate); }
    Size getSize() { return Size.SMALL; }
}

class Car extends Vehicle {
    Car(String plate) { super(plate); }
    Size getSize() { return Size.MEDIUM; }
}

class Truck extends Vehicle {
    Truck(String plate) { super(plate); }
    Size getSize() { return Size.LARGE; }
}
```

### ParkingSpot

```java
class ParkingSpot {
    private final int floor;
    private final int number;
    private final Size size;
    private Vehicle vehicle;            // null when the spot is free

    ParkingSpot(int floor, int number, Size size) {
        this.floor = floor; this.number = number; this.size = size;
    }

    boolean isFree()             { return vehicle == null; }
    boolean canFit(Vehicle v)    { return isFree() && size.compareTo(v.getSize()) >= 0; }
    void park(Vehicle v)         { vehicle = v; }
    void free()                  { vehicle = null; }
    Size getSize()               { return size; }
    int getFloor()               { return floor; }
    String label()               { return "Floor " + floor + ", spot " + number; }
}
```

`canFit` uses the enum order: `MEDIUM.compareTo(SMALL)` is positive, so a motorcycle fits a medium spot. A truck does not fit a medium spot.

### Ticket

```java
class Ticket {
    private final String id;
    private final Vehicle vehicle;
    private final ParkingSpot spot;
    private final Instant entryTime;

    Ticket(String id, Vehicle vehicle, ParkingSpot spot, Instant entryTime) {
        this.id = id; this.vehicle = vehicle; this.spot = spot; this.entryTime = entryTime;
    }
    String getId()          { return id; }
    Vehicle getVehicle()    { return vehicle; }
    ParkingSpot getSpot()   { return spot; }
    Instant getEntryTime()  { return entryTime; }
}
```

### FeeStrategy

```java
interface FeeStrategy {
    long calculateFee(Instant entry, Instant exit);   // in rupees
}

/** ₹40 for the first hour (or part of it), ₹20 for every further hour that has started. */
class HourlyFeeStrategy implements FeeStrategy {
    public long calculateFee(Instant entry, Instant exit) {
        long minutes = Duration.between(entry, exit).toMinutes();
        long hours = Math.max(1, (minutes + 59) / 60);   // round up to whole hours, minimum 1
        return 40 + (hours - 1) * 20;
    }
}
```

Check the rule with real numbers:

| Time parked | Hours charged | Fee |
| --- | --- | --- |
| 50 minutes | 1 | ₹40 |
| 1 hour 1 minute | 2 | ₹60 |
| 2 hours 35 minutes | 3 | ₹80 |

### ParkingLot

```java
class ParkingLot {
    // Sorted by size, then floor, so the first spot that fits is the best one.
    private final List<ParkingSpot> spots;
    private final Map<String, Ticket> activeTickets = new HashMap<>();
    private final FeeStrategy feeStrategy;
    private int nextTicket = 1;

    ParkingLot(List<ParkingSpot> spots, FeeStrategy feeStrategy) {
        this.spots = new ArrayList<>(spots);
        this.spots.sort(Comparator.comparing(ParkingSpot::getSize)
                                  .thenComparing(ParkingSpot::getFloor));
        this.feeStrategy = feeStrategy;
    }

    /** Called by an entry gate. Returns a ticket, or throws if no suitable spot is free. */
    synchronized Ticket parkVehicle(Vehicle vehicle, Instant now) {
        for (ParkingSpot spot : spots) {
            if (spot.canFit(vehicle)) {
                spot.park(vehicle);
                Ticket ticket = new Ticket("T-" + nextTicket++, vehicle, spot, now);
                activeTickets.put(ticket.getId(), ticket);
                return ticket;
            }
        }
        throw new IllegalStateException("No free spot for a " + vehicle.getSize() + " vehicle");
    }

    /** Called by an exit gate. Frees the spot and returns the fee to pay. */
    synchronized long unparkVehicle(String ticketId, Instant now) {
        Ticket ticket = activeTickets.remove(ticketId);
        if (ticket == null) {
            throw new IllegalArgumentException("Unknown or already used ticket");
        }
        ticket.getSpot().free();
        return feeStrategy.calculateFee(ticket.getEntryTime(), now);
    }
}
```

Try it with three vehicles arriving at 9:00 in a lot with one small, two medium and one large spot:

```text
KA-01-AB-1234 (car)        -> Floor 1, spot 2   (medium)
KA-05-XY-9876 (motorcycle) -> Floor 1, spot 1   (small)
MH-12-TR-4455 (truck)      -> Floor 2, spot 9   (large)
```

The car leaves at 9:50 and pays ₹40. Its spot is free again for the next car.

## Step 5: Two gates at the same time

The lot has two entry gates. Two cars arrive together, and only one medium spot is left. Without protection, this can happen:

1. Gate A checks the spot: free.
2. Gate B checks the same spot: still free.
3. Both gates park their car there.

![Animation: two cars arrive at gates A and B when one medium spot is left; gate A enters parkVehicle first and takes the spot while gate B waits; gate B then finds no suitable spot and the driver is told the lot is full.](learning-figures/lld-2-gates.gif)

That is why `parkVehicle` and `unparkVehicle` are `synchronized`. Checking a spot and taking it happen as one step, so only one gate at a time can run them.

> **⚠️ Common mistake**
> Locking only inside `ParkingSpot.park()` is not enough. The check (`canFit`) and the change (`park`) must be inside the same lock, or both gates can pass the check before either one parks.

> **🎯 In the interview**
> If asked about several servers: `synchronized` only protects one JVM. With several servers, keep spots in a database and take a spot with one conditional update, such as `UPDATE spot SET vehicle = ? WHERE id = ? AND vehicle IS NULL`. If no row was updated, another gate got there first.

## Step 6: Deep dives

### Adding a new spot or vehicle type

Suppose the lot adds electric-vehicle spots with chargers. Add an `EV` value or an `ElectricCar` class, and a rule for which spots it may use. `ParkingLot`, `Ticket` and the fee code do not change, because they only talk to `Vehicle`, `ParkingSpot` and `FeeStrategy`.

### Changing the price

Weekend pricing is a new class:

```java
class WeekendFeeStrategy implements FeeStrategy {
    public long calculateFee(Instant entry, Instant exit) { /* flat ₹100 per day */ return 100; }
}
```

Pass it to `ParkingLot` instead of `HourlyFeeStrategy`. No other code changes. This is the **Strategy pattern**.

### Finding a spot faster

`parkVehicle` scans the spot list: fine for a few hundred spots. For a lot with thousands of spots, keep a separate queue of free spots for each size. Taking a spot becomes "poll the small queue; if empty, poll the medium queue…", and freeing a spot adds it back to its queue. Both are O(1) instead of O(number of spots).

### A display board

Each floor's board shows free spots by size. The board should *read* the count from `ParkingLot`, or be notified when a spot changes (the **Observer pattern**). It must never decide availability itself.

## Interviewer follow-ups

**Why not one class per spot type, like `CompactSpot` and `LargeSpot`?** They would behave identically; only the size differs. An enum field is simpler. Use subclasses only when the behaviour differs, for example an EV spot that also starts a charging session.

**What if a ticket is lost?** Find the active ticket by licence plate (add a map from plate to ticket) and charge a lost-ticket fee set by the business.

**What if the driver pays but takes a long time to leave?** Common rule: after paying, the driver has 10–15 minutes to exit. Store the payment time on the ticket; if the exit is later than that, charge the extra time.

**What if the same ticket is used twice?** `unparkVehicle` removes the ticket from `activeTickets`. A second attempt finds nothing and is rejected.

**Is `ParkingLot` a Singleton?** There is one lot per application, so in Spring it would be a singleton bean. Avoid a hand-written static Singleton – it makes testing harder.

## Wrap up

We designed a parking lot with five clear parts: `Vehicle`, `ParkingSpot`, `Ticket`, `FeeStrategy` and `ParkingLot`.

> **📝 Key takeaways**
> - One owner (`ParkingLot`) for spot data, so gates never disagree.
> - One `Size` enum makes "does it fit?" a simple comparison.
> - Fee rules sit behind `FeeStrategy`, so pricing changes need no other edits.
> - Checking and taking a spot happen inside one lock; across servers, use a conditional database update.

The complete, runnable code is in [ParkingLotDemo.java](reference-code/learning/kb/parking/ParkingLotDemo.java). It parks the three vehicles above, checks the fee table and rejects a reused ticket. For a production-depth version with payment retries and multi-gate recovery, see the [advanced Parking.java](reference-code/lld-three/Parking.java).

## Closing answer

"I'd model `Vehicle` with motorcycle, car and truck subclasses that report a size, and `ParkingSpot` with a floor, number and size. A vehicle fits a spot of its size or bigger. `ParkingLot` is the single coordinator the gates call: `parkVehicle` gives the smallest suitable spot on the lowest floor and returns a ticket, and `unparkVehicle` frees the spot and asks a `FeeStrategy` for the fee. Both methods are synchronized so two gates can't take the same spot; across servers I'd use a conditional database update. New vehicle types, spot types and pricing rules can all be added without changing the core."

## Problem

Design the software that handles requests for several elevators in a building. Someone waiting on a floor presses Up or Down. Someone inside a car selects a destination. The system must choose a car, decide its next stop and open the doors at the right time.

We will use a Java simulation to make those decisions clear. It moves between whole floors; real motors, brakes and their safety controls belong to the device controller.

## Requirements

- Support several cars in one building.
- Keep floor Up/Down requests separate from destinations selected inside a car.
- Avoid adding the same active request again when a button is pressed repeatedly.
- Serve stops in a sensible direction instead of reversing for every new request.
- Prevent travel with open doors, an obstruction, a failed travel permission or an overload.
- Let another car collect waiting passengers if the assigned car becomes unavailable.

## 1. Start with one elevator journey

Car A is at floor 0. It has cabin requests for floors **3 and 7**. Someone on floor **2 presses Up**, and someone on floor **5 presses Down**.

The useful stop order is:

**2 Up → 3 → 7 → 5 Down.**

A picks up the person at 2 while travelling upward, then serves its cabin requests at 3 and 7. It passes floor 5 on the way up because that person wants to go down. After 7, it reverses and offers a downward ride at 5.

[![Car A serves the Up call at two and cabin destinations three and seven before returning to serve Down at five](lld-figures/elevator-sweep.svg)](lld-figures/elevator-sweep.svg)

Stopping at 5 on the upward trip must not clear the Down request. Passing the correct floor is not enough; the car must offer the requested direction.

This example shows two separate decisions: **which car should take a call**, and **which stop that car should serve next**. The first is the building's job. The second belongs to each car's plan.

## 2. Give the building and each car different jobs

| Class | Its job |
| --- | --- |
| `SystemController` | Remember active floor calls, choose cars and handle events. |
| `Request` | Remember one floor/direction request and its current assignment. |
| `Car` | Keep one car's floor, direction, doors, load and plan. |
| `SweepPlan` | Decide that car's next stop. |
| `DispatchPolicy` | Provide a rule for choosing a car. |
| `EtaPolicy` | Choose the car predicted to offer pickup first. |

[![The system controller keeps floor calls and chooses cars, while each car owns its stop plan and supplies a read-only snapshot for selection](designs/lld-3.svg)](designs/lld-3.svg)

### A floor call does not tell us the destination

`hallCall(2, UP)` means someone at 2 wants to go upward. It does not say whether the person wants floor 3, 7 or 9. That destination becomes known after boarding, through a cabin button such as `cabinCall("A", 7)`.

A floor call can be moved to another car's plan. A cabin destination stays with its car because the passenger is already inside it.

Another press of the active `2 Up` button returns the same call. It does not prove another passenger arrived. A simultaneous `2 Down` call is different and remains active until a car offers that direction.

### What a car remembers

- Its current floor and travel direction.
- The direction being offered when its doors open.
- Door state: closed, opening, open or closing.
- Measured load and capacity.
- Whether it is available, whether a door obstruction is detected, and whether travel is permitted.
- Cabin destinations and assigned floor calls.

The code calls the travel-permission signal `interlock`. For this model it is a boolean supplied by the device side. The scheduling code must respect it rather than assume closed doors always mean travel is permitted.

## 3. Choose a car by its journey, not just its distance

Consider a separate two-car example:

- A is at 0, with cabin destinations 3 and 6.
- B is at 3, heading towards its cabin destination 1.
- A person at 2 presses Up.

B is only one floor away. But it must finish its downward stop, close its doors, return to 2 and open again. A can offer an upward pickup sooner.

[![Two elevator shafts show why car A can collect an Up call sooner than nearby car B, which first needs to finish a downward stop](lld-figures/elevator-building.svg)](lld-figures/elevator-building.svg)

Our simulator counts **ticks**, meaning individual actions rather than seconds. Moving one floor is one action. Beginning to open and finishing opening are separate actions.

| Car | Actions before pickup at 2 | Count |
| --- | --- | ---: |
| A | 0→1, 1→2, start opening, finish opening | 4 |
| B | 3→2, 2→1, start opening, finish opening, start closing, finish closing, 1→2, start opening, finish opening | 9 |

`EtaPolicy` tries the current plan on a copy of each car's state. It picks the eligible car with the smaller count; a stable car ID breaks a tie. Trying a copy does not move the actual car.

This estimate uses the calls already known. It does not predict future passengers or real travel/dwell time. A real system can replace the estimate with measured timings while keeping the same request and car classes.

If every car is full, blocked or unavailable, the request stays waiting. It is tried again when a car's state changes or the next simulation tick runs.

## 4. Decide the next stop without unnecessary reversals

Return to A's first journey: cabin destinations 3 and 7, floor calls `2 Up` and `5 Down`.

While going up, choose the nearest cabin destination or Up call at or above the current floor. Keep serving those stops before reversing. Once there is no further upward demand, reverse and follow the corresponding Down rule.

If there are only Down calls above the car, travel to the highest of them and start serving downward there. The reverse case works the same way below the car. An idle car starts towards a nearest request, using the lower floor to break a tie.

This is a **LOOK-style sweep**: the car turns around when the remaining requests call for it. It does not travel to the top or bottom merely because that is the end of the building.

In the Java method, `ceiling(floor)` means the first requested floor at or above this floor. `floor(floor)` means the first at or below it. Cabin destinations appear in both directions because those passengers are already inside. Floor calls appear only in their requested direction.

```java
// source: Elevators.java#look
        Goal next(int floor, Direction heading) {
            TreeSet<Integer> up = new TreeSet<>(cabin);
            up.addAll(halls(Direction.UP));
            TreeSet<Integer> down = new TreeSet<>(cabin);
            down.addAll(halls(Direction.DOWN));
            if (up.isEmpty() && down.isEmpty()) {
                return null;
            }
            if (heading == Direction.IDLE) {
                TreeSet<Integer> all = new TreeSet<>(up);
                all.addAll(down);
                int closest = all.stream()
                    .min(Comparator.comparingInt((Integer f) -> Math.abs(f - floor))
                        .thenComparingInt(f -> f))
                    .orElseThrow();
                if (closest == floor) {
                    Direction boarding = halls(Direction.UP).contains(floor) ? Direction.UP
                        : halls(Direction.DOWN).contains(floor) ? Direction.DOWN : Direction.IDLE;
                    return new Goal(floor, boarding);
                }
                return next(floor, closest > floor ? Direction.UP : Direction.DOWN);
            }
            if (heading == Direction.UP) {
                Integer matching = up.ceiling(floor);
                if (matching != null) {
                    return new Goal(matching, Direction.UP);
                }
                if (!down.isEmpty() && down.last() > floor) {
                    return new Goal(down.last(), Direction.DOWN);
                }
                if (down.contains(floor)) {
                    return new Goal(floor, Direction.DOWN);
                }
                return next(floor, Direction.DOWN);
            }
            Integer matching = down.floor(floor);
            if (matching != null) {
                return new Goal(matching, Direction.DOWN);
            }
            if (!up.isEmpty() && up.first() < floor) {
                return new Goal(up.first(), Direction.UP);
            }
            if (up.contains(floor)) {
                return new Goal(floor, Direction.UP);
            }
            return next(floor, Direction.UP);
        }
```

`Goal` contains a target floor and the direction to offer when opening there. That direction matters when clearing a floor call.

The first journey now has a clear explanation:

| At this point | Decision |
| --- | --- |
| A starts at 0 | Travel towards the first matching stop, 2 Up. |
| Doors open at 2 | Clear 2 Up if there is room. Keep any 2 Down call. |
| Doors open at 3 | Remove the cabin destination 3. |
| A passes 5 while going Up | Keep 5 Down active. |
| Doors open at 7 | Remove cabin destination 7; then reverse. |
| Doors open at 5 while offering Down | Clear 5 Down. With nothing left, close and become idle. |

One global queue of floors would lose these distinctions. FIFO order can cause repeated reversals; always taking the lowest floor can send an upward journey backwards too soon.

## 5. Doors, capacity and a failed car

### A route does not give permission to move

The door follows this cycle:

**Closed → Opening → Open → Closing → Closed.**

If something blocks the closing door, it reopens. While an open door is blocked, it stays open. A car moves only when it is available, its doors are closed, the obstruction signal is clear, travel is permitted and the load is not over capacity.

[![Four door states show the normal cycle and obstruction reopening; movement also requires clear sensors, travel permission and a load within capacity](lld-figures/elevator-doors.svg)](lld-figures/elevator-doors.svg)

**Full and overloaded mean different things.** A full car can carry its current passengers to their destinations, but should not receive new pickups. An overloaded car must not travel.

The simulation receives load readings through `load(carId, passengers)`. Button presses do not change that reading. It does not guess how many people entered or left.

Here is one step of the car's control logic. Each branch performs one action and returns an event describing what happened:

```java
// source: Elevators.java#tick
        Tick tick() {
            int from = floor;
            Action action;
            List<HallTask> pickups = List.of();
            if (mode == Mode.OUT_OF_SERVICE) {
                action = Action.OUT_OF_SERVICE;
            } else if (door == Door.OPENING) {
                door = Door.OPEN;
                action = Action.OPENED;
                plan.cabin.remove(floor);
                if (load < capacity) {
                    pickups = plan.hall.values().stream()
                        .filter(h -> h.key.floor == floor && h.key.direction == boarding)
                        .toList();
                }
            } else if (door == Door.OPEN) {
                if (obstructed || load > capacity) {
                    action = Action.BLOCKED;
                } else {
                    door = Door.CLOSING;
                    action = Action.CLOSING;
                }
            } else if (door == Door.CLOSING) {
                if (obstructed || load > capacity) {
                    door = Door.OPENING;
                    action = Action.OPENING;
                } else {
                    door = Door.CLOSED;
                    action = Action.CLOSED;
                }
            } else if (load > capacity) {
                door = Door.OPENING;
                action = Action.OPENING;
            } else if (obstructed || !interlock) {
                action = Action.BLOCKED;
            } else {
                Goal next = plan.next(floor, heading);
                if (next == null) {
                    heading = Direction.IDLE;
                    action = Action.IDLE;
                } else if (next.floor == floor) {
                    boarding = next.boarding;
                    heading = boarding;
                    door = Door.OPENING;
                    action = Action.OPENING;
                } else {
                    heading = next.floor > floor ? Direction.UP : Direction.DOWN;
                    floor += heading == Direction.UP ? 1 : -1;
                    action = Action.MOVED;
                }
            }
            return new Tick(id, action, from, floor, heading, pickups);
        }
```

Opening the doors completes cabin stops. It offers floor pickups only for the requested direction and only with room. The controller checks the assignment before marking those calls served.

The model knows only whole-floor positions. For example, it can begin reopening after an overload at its current model floor. Handling a real car between floors belongs to the device controller, not this floor-step simulation.

### Give a waiting call to another car without losing it

Suppose call 41 is `2 Up`, assigned to A. A becomes unavailable before offering pickup. The controller keeps call 41, removes it from A's plan and gives it to B.

But A might still send a delayed message saying it served call 41. We need to recognise that A's assignment is old.

We attach an **assignment number**, called `epoch` in the code:

1. A owns call 41 with number 1.
2. Releasing that assignment moves the number to 2.
3. B receives the call with number 3.
4. A's late message for number 1 is rejected.

[![Call 41 keeps its identity and waiting age while assignment numbers change, so a late message from the old car cannot clear the replacement's call](lld-figures/elevator-ownership.svg)](lld-figures/elevator-ownership.svg)

The acknowledgement must match the current car and assignment number. It must also come from a car with open doors at the correct floor, offering the correct direction, with room to board.

```java
// source: Elevators.java#ownership
        public synchronized boolean acknowledgePickup(long callId, String carId, long epoch) {
            Request request = requests.get(callId);
            Car car = car(carId);
            if (request == null || request.state != CallState.ASSIGNED
                    || !carId.equals(request.carId) || request.epoch != epoch) {
                return false;
            }
            if (car.door != Door.OPEN || car.floor != request.key.floor
                    || car.boarding != request.key.direction || car.load >= car.capacity
                    || car.mode != Mode.NORMAL) {
                return false;
            }
            request.state = CallState.SERVED;
            active.remove(request.key, request.id);
            car.plan.hall.remove(callId, new HallTask(callId, request.key, epoch));
            return true;
        }
        public synchronized void outOfService(String carId) {
            Car car = car(carId);
            car.mode = Mode.OUT_OF_SERVICE;
            releaseHallCalls(car);
            dispatch();
            // Cabin destinations remain: existing passengers require an operator recovery procedure.
        }
        private void releaseHallCalls(Car car) {
            for (HallTask task : new ArrayList<>(car.plan.hall.values())) {
                Request request = requests.get(task.callId);
                if (request != null && request.state == CallState.ASSIGNED
                        && car.id.equals(request.carId) && request.epoch == task.epoch) {
                    request.state = CallState.WAITING;
                    request.carId = null;
                    request.epoch++;
                }
            }
            car.plan.hall.clear();
        }
```

The call keeps its original creation time, so reassignment does not make a long-waiting person look newly arrived. A full car, a blocked door or a failed travel permission also releases unserved floor calls for another car.

Cabin destinations remain in an unavailable car. Another elevator can collect people waiting at floor 2; copying the destination 7 cannot transfer passengers already inside A. Those passengers need an operator's recovery procedure.

## 6. Interviewer follow-ups

### When should the floor button go out?

When the currently assigned car offers pickup: doors open, correct floor and direction, available with spare capacity. Assigning a car or passing the floor is not enough. After service, a new button press creates a new call identity.

### Why not run one independent thread for every car?

Separate device threads are possible, but shared requests still need one clear owner. Here the controller's short synchronized methods keep assigning a call and adding it to a plan together. A larger design could give each car a message queue; it would still need acknowledged assignments and their numbers.

### Could a call wait too long while new requests keep arriving?

Yes. Considering waiting calls oldest-first does not by itself stop a busy sweep from extending forever. To provide a waiting-time guarantee, add a maximum waiting-time rule or limit how far new arrivals may extend a sweep. The current finite-plan simulation does not claim that guarantee under endless traffic.

### Is replaying every route efficient enough?

It is easy to explain for a small building. For each waiting call, the selector tries each car's known plan. More cars, stops and waiting requests make that work grow. The implementation also retains served-call history, which needs archiving in a long-running system. If measurement shows a problem, keep a separate waiting list and replace replay with a faster route-time estimate through `DispatchPolicy`.

### How would destination-dispatch elevators differ?

They ask for the destination before boarding. The dispatcher can group passengers by destination, but the request now contains more information and repeated presses may have a different meaning. Car, door and load rules still help; the conventional Up/Down request model needs to change.

### What happens after a controller restart?

A production system needs saved calls/assignments and must compare them with current device state before continuing. It must not blindly replay an old travel command. This Java example keeps its state in memory and implements the scheduling rules, not restart recovery or emergency operating procedures.

## 7. Closing answer

“I would separate choosing a car from ordering that car's stops. Floor requests remember a direction; cabin requests stay with the car. Each car follows a directional sweep, and its door/load checks decide whether it may move. A call is served only by a valid pickup from its current assignment. If a car fails, waiting calls move to another car without losing their identity or waiting age.”

## Problem

Design the booking part of a movie-ticket app such as BookMyShow. Users pick a show, choose seats on a seat map, pay, and get a ticket.

The interesting part is not the movie catalogue. It is this: two people tap the same seats at the same moment. Only one of them may get those seats, and nobody should pay for seats they did not get.

## Requirements

- Browse movies and shows; see the seat map for one show.
- Hold up to 8 seats for 5 minutes while the user pays.
- Confirm the booking after payment; release the seats if payment fails or time runs out.
- Never sell the same seat for the same show twice.
- Seat price depends on the seat type (silver, gold, recliner).

## Step 1: Clarify the requirements

**Candidate:** Is a seat the same thing in every show?

**Interviewer:** No. Seat A7 at 7 pm and seat A7 at 10 pm are sold separately.

**Candidate:** Can a booking get only some of the seats the user picked?

**Interviewer:** No. All the seats or none.

**Candidate:** How long do we keep seats for a user while they pay?

**Interviewer:** Five minutes. After that they go back on sale.

**Candidate:** Does every seat cost the same?

**Interviewer:** No. Gold seats cost more than silver.

**Candidate:** Should I design for one server first?

**Interviewer:** Yes. Then tell me what changes with many servers.

> **🎯 In the interview**
> The first answer – "a seat is different in every show" – decides your most important class. Ask it early.

| Functional | Non-functional |
| --- | --- |
| Show the seat map for a show | The same seat is never sold twice |
| Hold up to 8 seats for 5 minutes | A booking gets all its seats or none |
| Confirm after payment; release on failure or timeout | Payment never blocks other customers |
| Price by seat type | Pricing and payment providers are easy to change |

## Step 2: Identify the core objects

- **Movie** – the film: title and length.
- **Screen** and **Seat** – the hall and its physical seats. Seat A7 is furniture; it never changes.
- **Show** – one movie on one screen at one time.
- **ShowSeat** – seat A7 *for this show*. This is the thing we actually sell.
- **Booking** – one user's seats for one show, with an amount and a status.
- **BookingService** – the only class that changes who owns a seat.
- **PaymentService** – the payment provider, behind an interface.

## Step 3: Design the classes

### Catalogue: Movie, Screen, Seat

These only describe things. They never change during a booking, so simple Java records are enough.

### ShowSeat

A `ShowSeat` knows its price and its status: AVAILABLE, HELD or BOOKED. When it is held, it remembers which booking holds it and until when.

### Show

A show creates one `ShowSeat` for every seat in its screen, priced by seat type. It is also what we lock, so different shows never wait for each other.

### Booking

A booking records the user, the show, the chosen seats, the amount and when the hold ends. Its status moves from PENDING to CONFIRMED or EXPIRED.

### BookingService and PaymentService

`BookingService` has two jobs: `holdSeats` and `confirm`. It talks to the payment provider through `PaymentService`, so Razorpay or UPI can be swapped in later.

### ShowSeat

```java
class ShowSeat {
    private final Seat seat;
    private final long pricePaise;                           // ₹250 = 25,000 paise
    private SeatStatus status = SeatStatus.AVAILABLE;
    private String heldBy;                                   // booking that holds it
    private Instant holdExpiresAt;

    ShowSeat(Seat seat, long pricePaise) { this.seat = seat; this.pricePaise = pricePaise; }

    boolean isAvailable(Instant now) {
        if (status == SeatStatus.HELD && !now.isBefore(holdExpiresAt)) {
            release();                                       // an expired hold counts as free
        }
        return status == SeatStatus.AVAILABLE;
    }

    void hold(String bookingId, Instant until) {
        status = SeatStatus.HELD; heldBy = bookingId; holdExpiresAt = until;
    }
    boolean isHeldBy(String bookingId) {
        return status == SeatStatus.HELD && bookingId.equals(heldBy);
    }
    void book()    { status = SeatStatus.BOOKED; holdExpiresAt = null; }
    void release() { status = SeatStatus.AVAILABLE; heldBy = null; holdExpiresAt = null; }

    long getPricePaise()   { return pricePaise; }
    SeatStatus getStatus() { return status; }
}
```

`isAvailable` treats an expired hold as free. So even if nobody cleans up old holds, a seat is never stuck.

### BookingService

```java
class BookingService {
    private static final Duration HOLD_TIME = Duration.ofMinutes(5);
    private static final int MAX_SEATS = 8;
    private final Map<String, Booking> bookings = new HashMap<>();
    private final PaymentService payments;
    private int nextId = 1;

    BookingService(PaymentService payments) { this.payments = payments; }

    Booking holdSeats(String user, Show show, List<String> seatNumbers, Instant now) {
        if (seatNumbers.isEmpty() || seatNumbers.size() > MAX_SEATS) {
            throw new IllegalArgumentException("Choose 1 to " + MAX_SEATS + " seats");
        }
        synchronized (show) {                                   // one show at a time
            List<ShowSeat> chosen = new ArrayList<>();
            for (String number : seatNumbers) {                 // 1. check every seat
                ShowSeat seat = show.getSeat(number);
                if (!seat.isAvailable(now)) {
                    throw new IllegalStateException("Seat " + number + " is not available");
                }
                chosen.add(seat);
            }
            String id = "booking-" + nextId++;                  // 2. then hold all of them
            Instant until = now.plus(HOLD_TIME);
            chosen.forEach(seat -> seat.hold(id, until));
            long total = chosen.stream().mapToLong(ShowSeat::getPricePaise).sum();
            Booking booking = new Booking(id, user, show, chosen, total, until);
            bookings.put(id, booking);
            return booking;
        }
    }

    Booking confirm(String bookingId, Instant paidAt) {
        Booking booking = bookings.get(bookingId);
        // Payment can take seconds, so it runs without holding the show lock.
        boolean paid = payments.charge(bookingId, booking.getAmountPaise());
        synchronized (booking.getShow()) {
            boolean stillOurs = booking.getSeats().stream()
                                       .allMatch(s -> s.isHeldBy(bookingId));
            if (paid && stillOurs && !booking.isExpired(paidAt)) {
                booking.getSeats().forEach(ShowSeat::book);
                booking.setStatus(BookingStatus.CONFIRMED);
            } else {
                if (paid) payments.refund(bookingId, booking.getAmountPaise());
                booking.getSeats().stream().filter(s -> s.isHeldBy(bookingId))
                       .forEach(ShowSeat::release);
                booking.setStatus(BookingStatus.EXPIRED);
            }
            return booking;
        }
    }
}
```

Read `holdSeats` in two halves. The loop only **checks**. If A8 is taken, we throw before touching A7, so nothing is half-held. Only when every seat passed do we **hold** them all.

Try it. Asha holds two gold seats, A7 and A8, at ₹250 each:

| What happens | Result |
| --- | --- |
| Asha holds A7, A8 | Booking for ₹500, both seats HELD for 5 minutes |
| Bilal tries A8 and F1 | Rejected – A8 is held. F1 stays AVAILABLE |
| Asha pays within 5 minutes | Booking CONFIRMED, A7 and A8 BOOKED |
| Chetan holds F1 but pays after 7 minutes | Hold expired; Bilal took F1 meanwhile. Chetan is refunded |

## Step 5: Two users, same seats

Asha and Bilal tap Continue on A7 and A8 at the same instant. Without protection:

1. Asha's request checks A7: available.
2. Bilal's request checks A7: still available.
3. Asha's request holds A7.
4. Bilal's request also holds A7 – **double booking**.

![Animation: Asha and Bilal ask for A7 and A8 at once; Asha gets the show lock first and holds both seats; Bilal then gets the lock, finds the seats held and is rejected with nothing changed.](learning-figures/lld-4-race.gif)

`synchronized (show)` makes check-and-hold one step. Bilal's request waits, then finds A7 held and is rejected. Requests for other shows use other locks and never wait.

> **⚠️ Common mistake**
> Calling the payment provider while holding the show lock. Every other customer of that show would wait for the bank. That is why `confirm` charges first and only then takes the lock.

`confirm` checks again after payment because the world may have changed: if the hold expired and someone else took the seat, a late payment must not steal it back. We refund instead.

> **🎯 In the interview**
> With several servers, `synchronized` is not enough. Let the database decide: one statement holds all seats only if they are free.

```sql
UPDATE show_seat
SET    status = 'HELD', booking_id = :bookingId, hold_until = :holdUntil
WHERE  show_id = :showId AND seat_number IN (:seats)
  AND  (status = 'AVAILABLE' OR (status = 'HELD' AND hold_until <= now()));
```

If fewer rows are updated than seats requested, roll back – someone else got at least one seat.

## Step 6: Deep dives

### Different prices for weekends or recliners

Move pricing behind a `PricingStrategy` interface. Weekend pricing or a recliner surcharge becomes a new class; `BookingService` does not change. This is the **Strategy pattern**.

### Notifications

When a booking is confirmed, send an email and SMS and add loyalty points. Make these **observers** of the "booking confirmed" event, so adding one never touches booking code.

### Cleaning up expired holds

`isAvailable` already treats expired holds as free. A background job that releases them every few seconds just keeps the seat map fresh for everyone else.

### A live seat map for thousands of users

Read seat status from a cache and push updates over WebSocket. The map may be a second out of date – the hold re-checks the truth.

## Interviewer follow-ups

**Why hold seats before payment?** Without a hold, two users could both pay for A7, and one must be refunded. A short hold is a clear promise: "these seats are yours for 5 minutes".

**What if payment succeeds but our server crashes before confirming?** The provider calls our webhook (or we poll it) with the booking ID. If the booking still holds its seats, confirm; otherwise refund. Using the booking ID as the payment's idempotency key means a retry never charges twice.

**Why lock per show and not one lock for everything?** Seats in different shows never conflict. One global lock would make every show wait for every other show.

**How would you add cancellation?** Allow it for a CONFIRMED booking before the show starts: mark it CANCELLED, release its seats, and refund using a refund policy.

**Isn't `synchronized` slow?** The locked section touches at most 8 seats in memory – microseconds. The slow part, payment, is outside it.

## Wrap up

We modelled the catalogue, the sellable `ShowSeat`, and one writer, `BookingService`, that holds and confirms seats safely.

> **📝 Key takeaways**
> - A `ShowSeat` exists per seat per show – that is what you sell.
> - Check every seat first, then hold all of them: all or nothing.
> - A per-show lock stops two users holding the same seat; with many servers, use a conditional update.
> - Pay outside the lock, then confirm only if the booking still holds its seats.

## Problem

Design the software for an ATM. A customer inserts a card, enters a PIN, checks the balance or withdraws cash, and takes the card back.

Interviewers love this question because the machine behaves differently depending on what has already happened. You cannot withdraw before entering a PIN, and you cannot insert a second card while one is inside. A good design makes those mistakes impossible.

## Requirements

- Insert a card and enter a PIN. Three wrong PINs end the session.
- After a correct PIN: check balance or withdraw cash.
- Withdrawals are multiples of ₹100, up to ₹20,000.
- Dispense ₹500, ₹200 and ₹100 notes.
- Never debit the account without giving the cash.

## Step 1: Clarify the requirements

**Candidate:** Who checks the PIN and keeps the balance – the ATM or the bank?

**Interviewer:** The bank. The ATM never stores either.

**Candidate:** Which operations do we need?

**Interviewer:** Balance and cash withdrawal.

**Candidate:** What happens after wrong PINs?

**Interviewer:** Three wrong PINs end the session and return the card.

**Candidate:** Which notes does the machine hold?

**Interviewer:** ₹500, ₹200 and ₹100.

**Candidate:** What if the cash fails to come out after the account is debited?

**Interviewer:** The customer must not lose money.

> **💡 Tip**
> For any "machine" question – ATM, vending machine, elevator – draw the states before the classes. The states are the design.

| Functional | Non-functional |
| --- | --- |
| Insert card, enter PIN, balance, withdraw, eject | Impossible to withdraw before a correct PIN |
| End the session after three wrong PINs | Never debit without dispensing |
| Dispense with ₹500/₹200/₹100 notes | Easy to add operations such as deposits |

## Step 2: Identify the states and core objects

The ATM is always in one of three states:

| State | What the customer can do |
| --- | --- |
| **Idle** | Insert a card |
| **Has card** | Enter a PIN, or cancel |
| **Authenticated** | Check balance, withdraw, take the card |

[![ATM state machine: Idle moves to HasCard when a card is inserted; HasCard moves to Authenticated on a correct PIN and back to Idle after three wrong PINs or cancel; Authenticated handles balance and withdrawal and returns to Idle when the card is ejected.](learning-figures/lld-5-states.svg)](learning-figures/lld-5-states.svg)

The core objects:

- **ATM** – the machine. It remembers the current state and the inserted card.
- **ATMState** – one class per state, each deciding what an action means *in that state*.
- **BankService** – the bank: checks PINs, holds balances, debits and reverses.
- **CashDispenser** – the notes inside the machine.
- **Card** – the card number read from the card.

[![Selected design: the ATM delegates every action to its current ATMState, reads the Card, asks the BankService to authenticate and debit, and asks the CashDispenser to plan and dispense notes.](designs/lld-5.svg)](designs/lld-5.svg)

> **⚖️ Design choice**
> We use the **State pattern** instead of a big `switch (status)` in every method. Each state is its own class, so adding an "Out of service" state is one new class, not edits in every method.

## Step 3: Design the classes

### ATMState and its three states

`ATMState` has one method per customer action. `IdleState`, `HasCardState` and `AuthenticatedState` each implement all five, but only the actions that make sense in that state do real work. The others show a helpful message.

### ATM

The ATM forwards every action to its current state. States move the ATM to the next state with `setState`.

### BankService

An interface, because the bank is an external system. The ATM never sees a PIN check or a balance rule – it only asks.

### CashDispenser

Knows how many notes of each value it holds, plans which notes to give, and dispenses them.

```java
class HasCardState implements ATMState {
    private static final int MAX_ATTEMPTS = 3;

    public void enterPin(ATM atm, String pin) {
        if (atm.bank.authenticate(atm.getCard(), pin)) {
            atm.resetWrongPins();
            atm.setState(new AuthenticatedState());
            atm.show("Choose an operation");
        } else if (atm.addWrongPin() >= MAX_ATTEMPTS) {
            ejectCard(atm);

        } else {
            atm.show("Wrong PIN, try again");
        }
    }
    public void ejectCard(ATM atm) {
        atm.setCard(null);
        atm.resetWrongPins();
        atm.setState(new IdleState());
    }
    public void insertCard(ATM atm, Card card) { atm.show("A card is already inserted"); }
    public void checkBalance(ATM atm)          { atm.show("Enter your PIN first"); }
    public void withdraw(ATM atm, int amount)  { atm.show("Enter your PIN first"); }
}
```

Look at `withdraw` here: it cannot reach the bank. Withdrawing before a PIN is impossible by design, not blocked by an `if` someone might forget.

### AuthenticatedState

```java
class AuthenticatedState implements ATMState {
    private static final int MAX_WITHDRAWAL = 20_000;
    private int nextTxn = 1;

    public void withdraw(ATM atm, int amount) {
        if (amount <= 0 || amount % 100 != 0 || amount > MAX_WITHDRAWAL) {
            atm.show("Enter a multiple of Rs 100, up to Rs " + MAX_WITHDRAWAL);
            return;
        }
        // 1. Can the machine make this amount from the notes it has?
        Optional<Map<Integer, Integer>> plan = atm.dispenser.plan(amount);
        if (plan.isEmpty()) {
            atm.show("This ATM cannot dispense that amount");
            return;
        }
        String txnId = "txn-" + nextTxn++;
        // 2. The bank checks the balance and debits in one step.
        if (!atm.bank.debit(atm.getCard(), amount, txnId)) {
            atm.show("Insufficient balance");
            return;
        }
        try {
            atm.dispenser.dispense(plan.get());                // 3. give the cash
            atm.show("Please take your cash");
        } catch (IllegalStateException jammed) {
            atm.bank.reverse(txnId);                           // 4. undo the debit
            atm.show("Could not dispense. Your account was not charged");
        }
    }
    public void checkBalance(ATM atm) {
        atm.show("Balance: Rs " + atm.bank.getBalance(atm.getCard()));
    }
    public void ejectCard(ATM atm) {
        atm.setCard(null);
        atm.setState(new IdleState());
        atm.show("Thank you");
    }
    public void insertCard(ATM atm, Card card) { atm.show("A card is already inserted"); }
    public void enterPin(ATM atm, String pin)  { atm.show("Already authenticated"); }
}
```

The withdrawal order matters:

1. **Plan the notes first.** If the machine cannot make the amount, stop before touching the account.
2. **Debit at the bank.** The bank checks the balance and debits in one step.
3. **Dispense.**
4. **If the cash jams, reverse the debit** using the same transaction ID.

> **⚠️ Common mistake**
> Debiting first and checking notes later. If the machine cannot make the amount, you now need a reversal for a failure you could have predicted.

### CashDispenser

```java
class CashDispenser {
    // Largest note first: {500 -> count, 200 -> count, 100 -> count}
    private final TreeMap<Integer, Integer> notes = new TreeMap<>(Comparator.reverseOrder());
    private boolean jammed;

    CashDispenser(Map<Integer, Integer> loaded) { notes.putAll(loaded); }

    /** Greedy: take as many of the largest note as possible, then the next. */
    Optional<Map<Integer, Integer>> plan(int amount) {
        Map<Integer, Integer> plan = new LinkedHashMap<>();
        int remaining = amount;
        for (Map.Entry<Integer, Integer> e : notes.entrySet()) {
            int use = Math.min(remaining / e.getKey(), e.getValue());
            if (use > 0) { plan.put(e.getKey(), use); remaining -= use * e.getKey(); }
        }
        return remaining == 0 ? Optional.of(plan) : Optional.empty();
    }

    void dispense(Map<Integer, Integer> plan) {
        if (jammed) throw new IllegalStateException("Dispenser jammed");
        plan.forEach((note, count) -> notes.merge(note, -count, Integer::sum));
    }
    void jam() { jammed = true; }
}
```

Try it with ₹10,000 in the account and a machine holding ten ₹500 and ten ₹200 notes, but no ₹100 notes:

| Action | Result |
| --- | --- |
| Withdraw before inserting a card | "Insert your card first" |
| Insert card, withdraw before PIN | "Enter your PIN first" |
| Wrong PIN, then correct PIN | Authenticated |
| Withdraw ₹2,700 | 5 × ₹500 + 1 × ₹200. Balance ₹7,300 |
| Withdraw ₹600 | Greedy takes ₹500, cannot make ₹100 → "cannot dispense" |
| Withdraw ₹1,000 while jammed | Debit reversed. Balance still ₹7,300 |
| Three wrong PINs | Card returned, back to Idle |

![Animation: one ATM session moves from Idle to HasCard on card insertion, stays in HasCard after a wrong PIN, moves to Authenticated on the correct PIN, performs balance and withdrawal, and returns to Idle when the card is ejected.](learning-figures/lld-5-states.gif)

## Step 5: When greedy is not enough

The ₹600 case above is worth explaining in the interview. Greedy took one ₹500 note and was stuck with ₹100 – yet 3 × ₹200 works.

The fix: try each possible number of the largest note, from high to low, and plan the rest the same way. With only three note sizes this tiny search is instant. Coin-change dynamic programming is the general version.

> **🎯 In the interview**
> Present greedy first – it is the expected answer – then say "it fails when a cassette runs out; I'd switch to a small search". That shows you know the limit.

## Step 6: Deep dives

### Adding deposits

Add `deposit(atm, amount)` to `ATMState`. Implement it in `AuthenticatedState`; the other states show a message. No other class changes.

### Out of service

Add `OutOfServiceState`, entered when cash runs out or an engineer opens the machine. Every action shows "Out of service".

### Daily withdrawal limits

The bank already knows today's withdrawals, so the limit belongs in `bank.debit`, not in the ATM.

### Chain of Responsibility for notes

Many courses build one handler per note size that passes the remainder on. It reads nicely, but it is greedy in disguise and has the same ₹600 problem.

## Interviewer follow-ups

**Why not store the PIN on the card or in the ATM?** Anyone reading the card or the machine's memory would learn it. The keypad encrypts the PIN and the bank checks it; the ATM only learns yes or no.

**What if two people use the same account at two ATMs?** The bank checks and debits in one atomic step, so two machines can never both spend the last ₹1,000.

**What if the network to the bank fails during a withdrawal?** Do not dispense. If the ATM does not know whether the debit happened, it records the withdrawal as uncertain and the bank reconciles it later.

**Why is `BankService` an interface?** The bank is outside our system. An interface lets us test with a fake bank and switch bank networks without touching the states.

## Wrap up

We designed the ATM around its three states, kept PINs and balances at the bank, and ordered the withdrawal so money is never lost.

> **📝 Key takeaways**
> - Draw the states first; implement them with the State pattern.
> - The bank owns PINs and balances behind a `BankService` interface.
> - Withdraw in this order: plan notes, debit, dispense, reverse on failure.
> - Greedy note planning is the first answer – know the case where it fails.

## Closing answer

"I'd model the ATM with the State pattern: Idle, HasCard and Authenticated, each its own class, and the `ATM` forwards every action to its current state. That makes illegal actions, like withdrawing before a PIN, impossible by design. The bank owns PINs and balances behind a `BankService` interface. A withdrawal validates the amount, plans the notes first, asks the bank to debit in one step, dispenses, and reverses the debit with the same transaction ID if the cash jams. Greedy note planning works until a cassette runs out; then I'd use a small search. New operations or an out-of-service state are new methods or classes."

## Problem

Design a car rental system like Zoomcar or Hertz. A customer searches for a car type for some dates, reserves a car, picks it up and returns it later. The branch needs an hour to clean each car between customers.

The real question hides in the dates: two customers must never be promised the same car for overlapping times, and a late return must be charged fairly.

## Requirements

- Search available cars by type and dates.
- Reserve a car, pick it up, return it, or cancel before pickup.
- Keep one hour after every rental for cleaning.
- Charge ₹1,800 for each started day booked and ₹200 for each started hour late.
- Several staff members can make bookings at the same time.

## Step 1: Clarify the requirements

**Candidate:** Does the customer reserve a car type or a specific car?

**Interviewer:** They search by type; the system assigns a specific car.

**Candidate:** Do they return it to the same branch?

**Interviewer:** Yes, for now.

**Candidate:** Is there a gap between two rentals of the same car?

**Interviewer:** One hour for cleaning.

**Candidate:** How do we charge?

**Interviewer:** ₹1,800 for each started day, plus ₹200 for each started hour late.

**Candidate:** Can two people book at the same moment?

**Interviewer:** Yes. Make sure they can't get the same car for the same time.

> **🎯 In the interview**
> Ask about the cleaning gap. It is easy to miss, and it changes the availability check.

| Functional | Non-functional |
| --- | --- |
| Search by type and dates | The same car is never promised twice for overlapping times |
| Reserve, pick up, return, cancel | Pricing rules are easy to change |
| Charge per started day plus late hours | Search stays fast for a big fleet |

## Step 2: Identify the core objects

- **Vehicle** – one physical car, with a registration, a type and a status (available, rented, in maintenance).
- **Reservation** – one customer's booking of one car for one time range.
- **PricingStrategy** – the rule that turns a reservation into a bill.
- **Invoice** – the bill: base amount and late fee.
- **RentalService** – the coordinator: search, reserve, pick up, return, cancel.

[![Selected design: RentalService searches the fleet of Vehicles, creates Reservations that book a vehicle's time slot, and asks the PricingStrategy for an Invoice.](designs/lld-6.svg)](designs/lld-6.svg)

> **⚖️ Design choice**
> Keep vehicle status and reservations separate. The status says what the car is doing *now*; reservations say what is promised for the *future*. A car can be available today and fully booked next weekend.

## Step 3: Design the classes

### Vehicle

A car's registration and type never change; its status does. Hatchback, sedan and SUV differ only by data here, so an enum is enough – no subclasses.

### Reservation

A reservation holds the customer, the car, a start and an end, and a status: confirmed, picked up, returned or cancelled. Its key method answers: *does this booking clash with another time range?*

### PricingStrategy and Invoice

Pricing changes often (weekend rates, memberships), so it sits behind an interface. The default charges per started day plus per started late hour.

### RentalService

Keeps the fleet and a calendar of reservations per car. Every change goes through it.

[![Class diagram: RentalService searches Vehicles and manages Reservations; a Reservation links a customer to one Vehicle for a start and end time; PricingStrategy produces an Invoice.](learning-figures/lld-6-classes.svg)](learning-figures/lld-6-classes.svg)

### Reservation and the overlap algorithm

```java
class Reservation {
    static final Duration CLEANING = Duration.ofHours(1);

    private final String customer;
    private final Vehicle vehicle;
    private final Instant start, end;              // the time range [start, end)
    private ReservationStatus status = ReservationStatus.CONFIRMED;

    Reservation(String customer, Vehicle vehicle, Instant start, Instant end) {
        this.customer = customer; this.vehicle = vehicle;
        this.start = start; this.end = end;
    }

    boolean isActive() {
        return status == ReservationStatus.CONFIRMED
            || status == ReservationStatus.PICKED_UP;
    }

    /** Two ranges overlap when each starts before the other ends (cleaning included). */
    boolean overlaps(Instant otherStart, Instant otherEnd) {
        return start.isBefore(otherEnd.plus(CLEANING))
            && otherStart.isBefore(end.plus(CLEANING));
    }

    Vehicle getVehicle()                 { return vehicle; }
    Instant getStart()                   { return start; }
    Instant getEnd()                     { return end; }
    ReservationStatus getStatus()        { return status; }
    void setStatus(ReservationStatus s)  { status = s; }
}
```

Example: Asha books the car KA-01-MJ-4521 from 09:00 to 11:00. With cleaning, the car is **blocked from 09:00 to 12:00**.

- Bilal asks for 11:00–14:00: it overlaps the blocked time, so the car is not available.
- Bilal asks for 12:00–15:00: it starts exactly when the block ends, so the car is available.

[![Timeline: Asha's rental from 09:00 to 11:00 plus cleaning until 12:00 blocks the car; a request starting at 11:00 overlaps and is rejected, a request starting at 12:00 is allowed.](learning-figures/lld-6-intervals.svg)](learning-figures/lld-6-intervals.svg)

> **⚠️ Common mistake**
> Checking only "does the new start fall inside an old booking?". That misses a new booking that completely surrounds an old one. Check both sides: each range must start before the other ends.

### Pricing

```java
record Invoice(long baseRupees, long lateFeeRupees) {
    long total() { return baseRupees + lateFeeRupees; }
}

interface PricingStrategy {
    Invoice invoice(Reservation r, Instant returnedAt);
}

/** Rs 1,800 per started day booked, plus Rs 200 per started hour late. */
class DailyRatePricing implements PricingStrategy {
    public Invoice invoice(Reservation r, Instant returnedAt) {
        Duration booked = Duration.between(r.getStart(), r.getEnd());
        long days = startedUnits(booked, Duration.ofDays(1));
        Duration late = returnedAt.isAfter(r.getEnd())
                ? Duration.between(r.getEnd(), returnedAt) : Duration.ZERO;
        long lateHours = startedUnits(late, Duration.ofHours(1));
        return new Invoice(days * 1_800, lateHours * 200);
    }

    static long startedUnits(Duration d, Duration unit) {   // 25 hours -> 2 started days
        long whole = d.dividedBy(unit);
        return d.equals(unit.multipliedBy(whole)) ? whole : whole + 1;
    }
}
```

Asha booked 09:00–11:00 (one started day, ₹1,800) and came back at 12:10 – 70 minutes late, two started hours, ₹400. Total ₹2,200.

### RentalService

```java
class RentalService {
    private final List<Vehicle> fleet;
    private final Map<Vehicle, List<Reservation>> calendar = new HashMap<>();
    private final PricingStrategy pricing;

    RentalService(List<Vehicle> fleet, PricingStrategy pricing) {
        this.fleet = fleet;
        this.pricing = pricing;
    }

    List<Vehicle> search(VehicleType type, Instant start, Instant end) {
        return fleet.stream()
                .filter(v -> v.getType() == type)
                .filter(v -> v.getStatus() != VehicleStatus.IN_MAINTENANCE)
                .filter(v -> isFree(v, start, end))
                .toList();
    }

    Reservation reserve(String customer, Vehicle vehicle, Instant start, Instant end) {
        if (!start.isBefore(end)) {
            throw new IllegalArgumentException("End must be after start");
        }
        synchronized (vehicle) {                           // check and insert together
            if (!isFree(vehicle, start, end)) {
                throw new IllegalStateException(vehicle.getRegistration() + " is not free");
            }
            Reservation r = new Reservation(customer, vehicle, start, end);
            calendar.computeIfAbsent(vehicle, v -> new ArrayList<>()).add(r);
            return r;
        }
    }

    private boolean isFree(Vehicle vehicle, Instant start, Instant end) {
        return calendar.getOrDefault(vehicle, List.of()).stream()
                .filter(Reservation::isActive)
                .noneMatch(r -> r.overlaps(start, end));
    }

    void pickup(Reservation r) {
        synchronized (r.getVehicle()) {
            if (r.getStatus() != ReservationStatus.CONFIRMED
                    || r.getVehicle().getStatus() != VehicleStatus.AVAILABLE) {
                throw new IllegalStateException("Vehicle not ready");
            }
            r.setStatus(ReservationStatus.PICKED_UP);
            r.getVehicle().setStatus(VehicleStatus.RENTED);
        }
    }

    Invoice returnVehicle(Reservation r, Instant returnedAt, boolean damaged) {
        synchronized (r.getVehicle()) {
            if (r.getStatus() != ReservationStatus.PICKED_UP) {
                throw new IllegalStateException("Not on rent");
            }
            r.setStatus(ReservationStatus.RETURNED);
            r.getVehicle().setStatus(damaged ? VehicleStatus.IN_MAINTENANCE
                                             : VehicleStatus.AVAILABLE);
            return pricing.invoice(r, returnedAt);
        }
    }

    void cancel(Reservation r) {
        synchronized (r.getVehicle()) {
            if (r.getStatus() != ReservationStatus.CONFIRMED) {
                throw new IllegalStateException("Only a confirmed reservation can be cancelled");
            }
            r.setStatus(ReservationStatus.CANCELLED);     // stops blocking the calendar
        }
    }
}
```

The search result is only a suggestion. Between search and reserve, someone else may take the car – so `reserve` checks again inside `synchronized (vehicle)`. Bookings for different cars never wait for each other.

| What happens | Result |
| --- | --- |
| Asha reserves 09:00–11:00 | Confirmed |
| Bilal tries 11:00–14:00 | Rejected – clashes with cleaning |
| Bilal reserves 12:00–15:00 | Confirmed |
| Asha returns at 12:10 | Invoice ₹1,800 + ₹400 = ₹2,200 |
| Bilal cancels | The 12:00 slot is free again |

## Step 5: Two bookings at the same moment

Two staff members try to reserve the same car for overlapping times at the same moment:

1. Desk A checks the calendar: free.
2. Desk B checks the calendar: still free.
3. Both add a reservation – the car is promised twice.

`synchronized (vehicle)` makes "check and insert" one step for that car. Desk B waits, then sees Desk A's booking and is rejected.

> **🎯 In the interview**
> With several servers, lock the car's row in the database (`SELECT ... FOR UPDATE`) while checking and inserting, or use a database constraint that forbids overlapping ranges (PostgreSQL has exclusion constraints).

## Step 6: Deep dives

### A late return blocks the next customer

Asha is late, and Bilal's pickup time arrives. The car is still RENTED, so `pickup` fails. Offer Bilal another free car of the same type; if there is none, cancel his booking free of charge. Asha pays the late fee.

### Weekend or membership pricing

Write another `PricingStrategy`. `RentalService` does not change – this is the **Strategy pattern**.

### Faster search for a big fleet

Keep each car's reservations sorted by start time; you only need to check the neighbours of the requested range. An interval tree does this in O(log n).

### Add-ons and notifications

Child seats and GPS become a list of add-ons on the reservation, each with a price. "Your car is ready" and "you are late" messages are **observers** of reservation events.

## Interviewer follow-ups

**Why reserve a specific car and not just "an SUV"?** It makes availability a simple per-car check. Promising only a type means counting capacity across overlapping times, which is harder. Customers still *search* by type.

**What if the car comes back damaged?** Mark it IN_MAINTENANCE so search skips it, charge damage through an inspection step, and move its future reservations to other cars.

**Where do time zones fit?** Store times as `Instant` (UTC). Convert to the branch's time zone only for display.

**Why a strict `isBefore`?** A booking ending at 12:00 and one starting at 12:00 must not clash. `<=` would reject a perfectly valid booking.

## Wrap up

We modelled cars, reservations and invoices, and made availability a simple interval-overlap check guarded by one lock per car.

> **📝 Key takeaways**
> - Vehicle status is *now*; reservations are the *future*.
> - Two ranges overlap when each starts before the other ends – include the cleaning buffer.
> - Check and insert under one lock per car (or a row lock in the database).
> - Pricing is a Strategy: per started day plus per started late hour.
