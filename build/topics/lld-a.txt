## Problem

Design the software for a parking lot. A vehicle arrives, gets a suitable parking spot and receives a ticket. Before leaving, the driver pays the fee. The spot becomes available when the vehicle leaves.

The design must also handle ordinary problems: two cars arriving together, a payment screen being clicked twice, or a payment taking too long to respond.

## Requirements

- Support motorcycles, cars and trucks across several floors.
- Give each vehicle one suitable, available spot and one ticket.
- Let several entry and exit gates use the same parking information.
- Charge ₹40 for the first hour and ₹20 for each extra hour that has started.
- Give the driver ten minutes to leave after a successful payment.
- Keep earlier payments when calculating any extra amount due.
- Handle repeated requests without issuing another ticket or charging again.

We will first solve this for one running Java application. The last section explains what changes when several servers share the work.

## 1. Start with one car

Imagine a car arriving at Gate A at 09:00. The lot gives it compact spot **C17** and ticket **S17**.

Those two IDs mean different things. C17 identifies a place in the building. S17 identifies this car's visit. Tomorrow another car can use C17, but it must get a different ticket.

| What happens | What the software records |
| --- | --- |
| Car enters at 09:00 | S17 started at 09:00 and is using C17. |
| Driver pays ₹40 at 09:59 | S17 has paid ₹40 and may leave before 10:09. |
| Car leaves at 10:01 | Close S17 and make C17 available. |
| Another car arrives | Create a new visit, even if it gets C17. |

[![Two entry gates share a parking lot with occupied, available and disabled bays; ticket S17 currently holds spot C17](lld-figures/parking-layout.svg)](lld-figures/parking-layout.svg)

The main rule is simple: **a spot stays occupied until the car leaves. Paying the fee does not free it.**

## 2. Give each class one clear job

We need these objects:

| Class | Its job | Example |
| --- | --- | --- |
| `Vehicle` | Identify the vehicle and its size. | Car CAR-17 |
| `Spot` | Describe one physical parking space. | C17, floor 0, compact |
| `Session` | Remember one visit: vehicle, spot, arrival, payment and exit. | Ticket S17 |
| `Attempt` | Remember one attempt to collect money. | Payment P17 for ₹40 |
| `Lot` | Keep these records together and handle entry, payment and exit. | The lot shared by both gates |

`Session` is the name used in the Java code for a parking visit. The ticket shows its ID. We keep the visit separate from the payment because a driver may need a second payment after staying longer.

Three small interfaces cover rules that can change:

- `AllocationPolicy` chooses a spot. Our rule uses the smallest suitable size first, then floor, location order and ID to break ties.
- `Tariff` calculates the total fee. A visit keeps the rate it received on entry.
- `PaymentPort` lets our code ask a payment service to collect money or check an earlier payment.

An **interface** describes what a component can do. It lets us change a rule or payment service without rewriting the whole lot.

[![Lot uses a spot-selection rule, records visits and payments, and calls a separate payment service](designs/lld-2.svg)](designs/lld-2.svg)

The allocation rule accepts these combinations:

| Vehicle | Suitable spots |
| --- | --- |
| Motorcycle | Motorcycle, compact or large |
| Car | Compact or large |
| Truck | Large |

A car should normally get a compact spot before a large one. That leaves large spots for trucks. If the business later prefers the nearest floor instead, we change `AllocationPolicy`.

The gates and display boards do not keep their own separate lists of free spots. They ask `Lot`. Otherwise Gate A could think C17 is free while Gate B has already given it away.

## 3. Entry: choose a spot and reserve it together

Gate A sends an entry request containing the vehicle and request ID **E17**. This ID identifies the action at the gate; S17 will identify the visit created by that action.

The entry method does this:

1. If E17 was already handled, return its existing ticket. If E17 is being reused for a different vehicle, reject it.
2. Check that this vehicle is not already inside under another ticket.
3. Find a suitable spot that is available and has not been disabled.
4. Create S17 and record that C17 belongs to this visit.
5. Return the ticket.

Why must choosing and reserving happen together? Suppose C17 is the last compact spot. Both gates might read a display that says “one spot free.” If both choose C17 before either records its use, two cars receive the same space.

A **lock** prevents this. Only one entry method at a time may choose and reserve a spot. The next method checks availability again after getting the lock.

[![Gate A reserves the last suitable spot while Gate B waits, then Gate B checks the updated records instead of also assigning C17](lld-figures/parking-race.svg)](lld-figures/parking-race.svg)

In Java, `synchronized` puts that lock around this method. These are the records it uses:

- `entries`: entry request ID → visit ID, so a retry can find its ticket.
- `sessions`: visit ID → visit details.
- `occupancy`: spot ID → visit ID, so each occupied spot has a known owner.
- `activeVehicles`: registration → visit ID, so one vehicle cannot enter twice.

```java
// source: Parking.java#enter
        public synchronized SessionView enter(String entryKey, Vehicle vehicle) {
            requireKey(entryKey);
            Objects.requireNonNull(vehicle);

            String previous = entries.get(entryKey);
            if (previous != null) {
                Session visit = session(previous);
                if (!visit.vehicle.equals(vehicle)) {
                    throw new IllegalArgumentException("Entry key payload conflict");
                }
                return visit.view();
            }
            if (activeVehicles.containsKey(vehicle.registration)) {
                throw new IllegalStateException("Vehicle already inside");
            }

            List<Spot> free = spots.values().stream()
                .filter(spot -> !disabled.contains(spot.id))
                .filter(spot -> !occupancy.containsKey(spot.id))
                .toList();
            Spot spot = allocator.choose(vehicle, free);
            if (!free.contains(spot) || !fits(vehicle.kind, spot.kind)) {
                throw new IllegalStateException("Allocation policy returned invalid spot");
            }

            String id = Objects.requireNonNull(ids.get());
            if (id.isBlank() || sessions.containsKey(id)) {
                throw new IllegalStateException("Session identity collision");
            }
            Session visit = new Session(id, vehicle, spot, clock.instant(), tariff);
            sessions.put(id, visit);
            occupancy.put(spot.id, id);
            activeVehicles.put(vehicle.registration, id);
            entries.put(entryKey, id);
            return visit.view();
        }
```

The final line returns a `SessionView`: a copy of the details the caller may read. The caller cannot edit the lot's records through that response. The helper `requireKey` checks that the request ID is present; `allocator.choose` applies the selection rule described above.

Notice that all four records are updated before the method returns. Another gate cannot observe a reserved spot with no ticket behind it.

If the response is lost, Gate A retries **E17**. It receives **S17** again. It does not get another spot. A request ID is useful only if the gate reuses it for a retry; inventing a new ID each time loses that protection.

## 4. Payment: explain the amount, then collect it once

Before charging, show the driver a quote. For S17 at 09:59, the amount due is ₹40.

The rule “each extra hour that has started” needs a precise meaning:

| Time parked | Fee |
| --- | ---: |
| Less than one hour | ₹40 |
| Exactly one hour | ₹40 |
| One hour and one second | ₹60 |
| Two hours and 35 minutes | ₹80 |

An immediate exit still pays the first-hour minimum. The Java implementation handles even smaller time boundaries, but the business rule is the same.

Money is stored as whole **paise**, not a decimal number of rupees: ₹40 is 4,000 paise. That keeps the calculation exact.

The payment call is `pay("S17", "P17", 4000)`. It means: “For visit S17, collect the approved 4,000 paise under payment ID P17.” If the current amount has changed, the method asks for a new approval before collecting it.

### Do not make every gate wait for one card payment

A payment service may take several seconds to reply. The lot must still allow other vehicles to enter during that time.

So payment has three steps:

1. Under the lot's lock, save P17 and mark the visit as awaiting its result.
2. Release the lock and call the payment service using P17.
3. Take the lock again and save the result. Add the payment to S17 only once.

[![Payment records are updated under a short lock while the slow payment-service call runs outside it, allowing another gate to continue](lld-figures/parking-payment.svg)](lld-figures/parking-payment.svg)

A repeated P17 request returns the saved attempt. It does not start another collection. The payment service must also use P17 to recognise a repeated call.

### A slow response does not tell us whether money moved

There are three useful outcomes:

| Result | What we do |
| --- | --- |
| Confirmed | Add ₹40 to the visit's paid amount and give it an exit deadline. |
| Definitely declined | Keep the car parked. The driver may start another payment. |
| Unknown, for example after a timeout | Keep P17 unresolved and ask the service about P17. Do not start another charge. |

Consider the last case. The bank may have collected ₹40 even though our application missed the reply. Immediately trying again with a new payment ID could collect another ₹40.

Instead, `reconcile("P17")` asks what happened to the original payment. If it confirms collection, we record that result. If it still cannot tell us, the attempt stays unresolved. “We have not found the result yet” must not be treated as “definitely declined.”

This repeat-safe behaviour is called **idempotency**. The name is less important than the promise: retrying the same action must not issue another ticket or collect another payment.

## 5. Exit: use the payment, then release the right spot

S17 was paid at 09:59. Its ten-minute exit period lasts until 10:09. If the car leaves at 10:01, it pays nothing more, even though the second parking hour has started.

If the car is still there at 10:10, the exit period has expired. The total fee is now ₹60, but the visit has already paid ₹40:

**Amount still due = ₹60 − ₹40 = ₹20.**

After collecting that ₹20, the visit has paid ₹60 in total and gets a new ten-minute exit period. Retrying the old P17 payment must not renew its old deadline.

[![A forty-rupee payment at 09:59 permits exit before 10:09; at 10:10 only twenty rupees more is due after crediting the earlier payment](lld-figures/parking-fees.svg)](lld-figures/parking-fees.svg)

At exactly 10:09, the old period has ended. If it expires while the total fee is still covered by earlier payments, the system can grant a fresh period without asking the payment service to collect zero rupees.

When the car leaves, a trusted gate event calls `confirmExit("S17", "X17")`. The method checks payment, deadline and spot ownership before closing the visit:

```java
// source: Parking.java#exit
        public synchronized SessionView confirmExit(String sessionId, String exitEventId) {
            requireKey(exitEventId);
            Session visit = session(sessionId);
            String previous = exits.get(exitEventId);
            if (previous != null && !previous.equals(sessionId)) {
                throw new IllegalArgumentException("Exit event payload conflict");
            }
            if (visit.state == SessionState.CLOSED) {
                return visit.view();
            }
            if (visit.state != SessionState.PAID || !clock.instant().isBefore(visit.exitBy)) {
                throw new IllegalStateException("Payment or additional payment required");
            }
            if (!sessionId.equals(occupancy.get(visit.spot.id))) {
                throw new IllegalStateException("Spot ownership mismatch");
            }

            occupancy.remove(visit.spot.id);
            activeVehicles.remove(visit.vehicle.registration, sessionId);
            visit.state = SessionState.CLOSED;
            exits.put(exitEventId, sessionId);
            return visit.view();
        }
```

`exitEventId` identifies the gate event. It must not be reused for a different visit. The `occupancy` check also matters: it confirms that this ticket still owns this spot.

For example, suppose S17 has closed and C17 now holds a new visit, S18. A delayed exit message for S17 must not free C17 again. The method sees that S17 is already closed and returns its old result. S18 is left alone.

The car's registration is also removed from the active-vehicle list, so it may enter again on a later visit.

## 6. Interviewer follow-ups

### What if the gate fails after we issue a ticket?

Keep the ticket and reservation. Retry the same entry request instead of issuing another ticket. If the car never entered, an attendant can check the gate evidence and cancel the unused visit. A missing network reply alone is not enough evidence to free the spot.

### What if payment succeeds but the exit barrier does not open?

Keep the confirmed payment and the occupied spot. The gate can retry access for the same ticket, or an attendant can resolve the fault. If the exit period expires, the chosen business rule decides whether to extend it or charge a difference. A broken barrier must not erase the payment record.

### Why not keep just a `paid` flag on the ticket?

A flag cannot tell us how much was paid, whether another payment is needed, or whether an earlier collection is still uncertain. S17 may already have paid ₹40 while a ₹20 top-up is pending. Separate payment attempts let us remember both facts.

### What changes when we have several servers?

`synchronized` protects threads using this `Lot` object. It does not lock another server's memory. Several servers need a shared database that checks and records the spot assignment together. The database must reject a second active claim for C17, even if both servers tried it at once.

For recovery after a restart, save tickets, spot claims and payment attempts in that database. Save a payment ID before calling the payment service. On recovery, check unresolved IDs with the service instead of blindly charging again. The supplied Java example keeps records in memory; this database step is an extension.

### Where are the replaceable design patterns?

`AllocationPolicy` and `Tariff` use **Strategy**: each puts a changeable rule behind an interface. For example, “smallest suitable spot” can become “nearest suitable spot.” Neither change should rewrite entry, payment or exit. We do not need a separate subclass for every vehicle/spot combination.

### What does the complete payment method look like?

The implementation below follows the three payment steps above. `Attempt` is the saved payment request. `finish` records its outcome once. A repeated key returns the saved result, and an unresolved attempt prevents a second collection under a new key.

```java
// source: Parking.java#payment
        public PaymentView pay(String sessionId, String paymentKey, long approvedDueMinor) {
            Attempt work;
            synchronized (this) {
                requireKey(paymentKey);
                if (approvedDueMinor < 0) {
                    throw new IllegalArgumentException("Negative approval");
                }
                Session visit = session(sessionId);
                Attempt old = attempts.get(paymentKey);
                if (old != null) {
                    if (!old.sessionId.equals(sessionId) || old.amount != approvedDueMinor) {
                        throw new IllegalArgumentException("Payment key payload conflict");
                    }
                    return old.view(); // A duplicate cannot start a second provider call.
                }
                if (visit.state == SessionState.CLOSED) {
                    throw new IllegalStateException("Session closed");
                }
                if (visit.state == SessionState.PAYMENT_PENDING
                        || visit.state == SessionState.PAYMENT_UNKNOWN) {
                    throw new IllegalStateException("Resolve original payment first");
                }
                if (visit.state == SessionState.PAID && clock.instant().isBefore(visit.exitBy)) {
                    if (approvedDueMinor != 0) {
                        throw new IllegalStateException("Quote changed; approve the current amount");
                    }
                    Attempt covered = new Attempt(paymentKey, sessionId, quote(sessionId));
                    covered.state = PaymentState.CONFIRMED;
                    covered.reference = "ALREADY_COVERED";
                    attempts.put(paymentKey, covered);
                    return covered.view(); // Does not extend grace.
                }

                Quote current = quote(sessionId);
                if (current.dueMinor != approvedDueMinor) {
                    throw new IllegalStateException("Quote changed; approve the current amount");
                }
                work = new Attempt(paymentKey, sessionId, current);
                attempts.put(paymentKey, work);
                visit.activePayment = paymentKey;
                visit.state = SessionState.PAYMENT_PENDING;
                if (work.amount == 0) {
                    return finish(paymentKey, new ProviderReply(
                        PaymentState.CONFIRMED, "COVERED_BY_PRIOR_PAYMENTS"));
                }
            }

            ProviderReply reply;
            try {
                reply = payments.charge(work.key, work.amount);
            } catch (RuntimeException uncertain) {
                reply = new ProviderReply(PaymentState.UNKNOWN, null);
            }
            return finish(work.key, reply); // The payment-service call held no lot lock.
        }
        public PaymentView reconcile(String paymentKey) {
            synchronized (this) {
                Attempt saved = attempt(paymentKey);
                if (saved.state == PaymentState.CONFIRMED || saved.state == PaymentState.DECLINED) {
                    return saved.view();
                }
            }
            ProviderReply reply;
            try {
                reply = payments.lookup(paymentKey);
            } catch (RuntimeException uncertain) {
                reply = new ProviderReply(PaymentState.UNKNOWN, null);
            }
            return finish(paymentKey, reply);
        }
```

For N spots, the simple entry implementation scans the available spots in O(N) time. That is a clear starting design for a small lot. If this becomes slow, keep searchable lists by spot type and floor. Updating those lists must still happen together with assigning or releasing a spot.

## 7. Closing answer

“I would give each visit its own ticket and make the lot responsible for assigning spots. Choosing a spot and recording its use happen under one lock, so two gates cannot promise the same space. Payments have their own IDs, so retries do not collect twice. We remember the amount already paid and free the spot only when that visit leaves. Different allocation and pricing rules fit behind small interfaces.”

That is the complete path: **arrive → assign a spot → pay → leave → reuse the spot**. The extra checks protect the same path when requests repeat or devices fail.

## Problem

Design the software that handles requests for several elevators in a building. Someone waiting on a floor presses Up or Down. Someone inside a car selects a destination. The system must choose a car, decide its next stop and open the doors at the right time.

We will use a Java simulation to make those decisions clear. It moves between whole floors; real motors, brakes and their safety controls belong to the device controller.

## Requirements

- Support several cars in one building.
- Keep floor Up/Down requests separate from destinations selected inside a car.
- Avoid adding the same active request again when a button is pressed repeatedly.
- Serve stops in a sensible direction instead of reversing for every new request.
- Prevent travel with open doors, an obstruction, a failed travel permission or an overload.
- Let another car collect waiting passengers if the assigned car becomes unavailable.

## 1. Start with one elevator journey

Car A is at floor 0. It has cabin requests for floors **3 and 7**. Someone on floor **2 presses Up**, and someone on floor **5 presses Down**.

The useful stop order is:

**2 Up → 3 → 7 → 5 Down.**

A picks up the person at 2 while travelling upward, then serves its cabin requests at 3 and 7. It passes floor 5 on the way up because that person wants to go down. After 7, it reverses and offers a downward ride at 5.

[![Car A serves the Up call at two and cabin destinations three and seven before returning to serve Down at five](lld-figures/elevator-sweep.svg)](lld-figures/elevator-sweep.svg)

Stopping at 5 on the upward trip must not clear the Down request. Passing the correct floor is not enough; the car must offer the requested direction.

This example shows two separate decisions: **which car should take a call**, and **which stop that car should serve next**. The first is the building's job. The second belongs to each car's plan.

## 2. Give the building and each car different jobs

| Class | Its job |
| --- | --- |
| `SystemController` | Remember active floor calls, choose cars and handle events. |
| `Request` | Remember one floor/direction request and its current assignment. |
| `Car` | Keep one car's floor, direction, doors, load and plan. |
| `SweepPlan` | Decide that car's next stop. |
| `DispatchPolicy` | Provide a rule for choosing a car. |
| `EtaPolicy` | Choose the car predicted to offer pickup first. |

[![The system controller keeps floor calls and chooses cars, while each car owns its stop plan and supplies a read-only snapshot for selection](designs/lld-3.svg)](designs/lld-3.svg)

### A floor call does not tell us the destination

`hallCall(2, UP)` means someone at 2 wants to go upward. It does not say whether the person wants floor 3, 7 or 9. That destination becomes known after boarding, through a cabin button such as `cabinCall("A", 7)`.

A floor call can be moved to another car's plan. A cabin destination stays with its car because the passenger is already inside it.

Another press of the active `2 Up` button returns the same call. It does not prove another passenger arrived. A simultaneous `2 Down` call is different and remains active until a car offers that direction.

### What a car remembers

- Its current floor and travel direction.
- The direction being offered when its doors open.
- Door state: closed, opening, open or closing.
- Measured load and capacity.
- Whether it is available, whether a door obstruction is detected, and whether travel is permitted.
- Cabin destinations and assigned floor calls.

The code calls the travel-permission signal `interlock`. For this model it is a boolean supplied by the device side. The scheduling code must respect it rather than assume closed doors always mean travel is permitted.

## 3. Choose a car by its journey, not just its distance

Consider a separate two-car example:

- A is at 0, with cabin destinations 3 and 6.
- B is at 3, heading towards its cabin destination 1.
- A person at 2 presses Up.

B is only one floor away. But it must finish its downward stop, close its doors, return to 2 and open again. A can offer an upward pickup sooner.

[![Two elevator shafts show why car A can collect an Up call sooner than nearby car B, which first needs to finish a downward stop](lld-figures/elevator-building.svg)](lld-figures/elevator-building.svg)

Our simulator counts **ticks**, meaning individual actions rather than seconds. Moving one floor is one action. Beginning to open and finishing opening are separate actions.

| Car | Actions before pickup at 2 | Count |
| --- | --- | ---: |
| A | 0→1, 1→2, start opening, finish opening | 4 |
| B | 3→2, 2→1, start opening, finish opening, start closing, finish closing, 1→2, start opening, finish opening | 9 |

`EtaPolicy` tries the current plan on a copy of each car's state. It picks the eligible car with the smaller count; a stable car ID breaks a tie. Trying a copy does not move the actual car.

This estimate uses the calls already known. It does not predict future passengers or real travel/dwell time. A real system can replace the estimate with measured timings while keeping the same request and car classes.

If every car is full, blocked or unavailable, the request stays waiting. It is tried again when a car's state changes or the next simulation tick runs.

## 4. Decide the next stop without unnecessary reversals

Return to A's first journey: cabin destinations 3 and 7, floor calls `2 Up` and `5 Down`.

While going up, choose the nearest cabin destination or Up call at or above the current floor. Keep serving those stops before reversing. Once there is no further upward demand, reverse and follow the corresponding Down rule.

If there are only Down calls above the car, travel to the highest of them and start serving downward there. The reverse case works the same way below the car. An idle car starts towards a nearest request, using the lower floor to break a tie.

This is a **LOOK-style sweep**: the car turns around when the remaining requests call for it. It does not travel to the top or bottom merely because that is the end of the building.

In the Java method, `ceiling(floor)` means the first requested floor at or above this floor. `floor(floor)` means the first at or below it. Cabin destinations appear in both directions because those passengers are already inside. Floor calls appear only in their requested direction.

```java
// source: Elevators.java#look
        Goal next(int floor, Direction heading) {
            TreeSet<Integer> up = new TreeSet<>(cabin);
            up.addAll(halls(Direction.UP));
            TreeSet<Integer> down = new TreeSet<>(cabin);
            down.addAll(halls(Direction.DOWN));
            if (up.isEmpty() && down.isEmpty()) {
                return null;
            }
            if (heading == Direction.IDLE) {
                TreeSet<Integer> all = new TreeSet<>(up);
                all.addAll(down);
                int closest = all.stream()
                    .min(Comparator.comparingInt((Integer f) -> Math.abs(f - floor))
                        .thenComparingInt(f -> f))
                    .orElseThrow();
                if (closest == floor) {
                    Direction boarding = halls(Direction.UP).contains(floor) ? Direction.UP
                        : halls(Direction.DOWN).contains(floor) ? Direction.DOWN : Direction.IDLE;
                    return new Goal(floor, boarding);
                }
                return next(floor, closest > floor ? Direction.UP : Direction.DOWN);
            }
            if (heading == Direction.UP) {
                Integer matching = up.ceiling(floor);
                if (matching != null) {
                    return new Goal(matching, Direction.UP);
                }
                if (!down.isEmpty() && down.last() > floor) {
                    return new Goal(down.last(), Direction.DOWN);
                }
                if (down.contains(floor)) {
                    return new Goal(floor, Direction.DOWN);
                }
                return next(floor, Direction.DOWN);
            }
            Integer matching = down.floor(floor);
            if (matching != null) {
                return new Goal(matching, Direction.DOWN);
            }
            if (!up.isEmpty() && up.first() < floor) {
                return new Goal(up.first(), Direction.UP);
            }
            if (up.contains(floor)) {
                return new Goal(floor, Direction.UP);
            }
            return next(floor, Direction.UP);
        }
```

`Goal` contains a target floor and the direction to offer when opening there. That direction matters when clearing a floor call.

The first journey now has a clear explanation:

| At this point | Decision |
| --- | --- |
| A starts at 0 | Travel towards the first matching stop, 2 Up. |
| Doors open at 2 | Clear 2 Up if there is room. Keep any 2 Down call. |
| Doors open at 3 | Remove the cabin destination 3. |
| A passes 5 while going Up | Keep 5 Down active. |
| Doors open at 7 | Remove cabin destination 7; then reverse. |
| Doors open at 5 while offering Down | Clear 5 Down. With nothing left, close and become idle. |

One global queue of floors would lose these distinctions. FIFO order can cause repeated reversals; always taking the lowest floor can send an upward journey backwards too soon.

## 5. Doors, capacity and a failed car

### A route does not give permission to move

The door follows this cycle:

**Closed → Opening → Open → Closing → Closed.**

If something blocks the closing door, it reopens. While an open door is blocked, it stays open. A car moves only when it is available, its doors are closed, the obstruction signal is clear, travel is permitted and the load is not over capacity.

[![Four door states show the normal cycle and obstruction reopening; movement also requires clear sensors, travel permission and a load within capacity](lld-figures/elevator-doors.svg)](lld-figures/elevator-doors.svg)

**Full and overloaded mean different things.** A full car can carry its current passengers to their destinations, but should not receive new pickups. An overloaded car must not travel.

The simulation receives load readings through `load(carId, passengers)`. Button presses do not change that reading. It does not guess how many people entered or left.

Here is one step of the car's control logic. Each branch performs one action and returns an event describing what happened:

```java
// source: Elevators.java#tick
        Tick tick() {
            int from = floor;
            Action action;
            List<HallTask> pickups = List.of();
            if (mode == Mode.OUT_OF_SERVICE) {
                action = Action.OUT_OF_SERVICE;
            } else if (door == Door.OPENING) {
                door = Door.OPEN;
                action = Action.OPENED;
                plan.cabin.remove(floor);
                if (load < capacity) {
                    pickups = plan.hall.values().stream()
                        .filter(h -> h.key.floor == floor && h.key.direction == boarding)
                        .toList();
                }
            } else if (door == Door.OPEN) {
                if (obstructed || load > capacity) {
                    action = Action.BLOCKED;
                } else {
                    door = Door.CLOSING;
                    action = Action.CLOSING;
                }
            } else if (door == Door.CLOSING) {
                if (obstructed || load > capacity) {
                    door = Door.OPENING;
                    action = Action.OPENING;
                } else {
                    door = Door.CLOSED;
                    action = Action.CLOSED;
                }
            } else if (load > capacity) {
                door = Door.OPENING;
                action = Action.OPENING;
            } else if (obstructed || !interlock) {
                action = Action.BLOCKED;
            } else {
                Goal next = plan.next(floor, heading);
                if (next == null) {
                    heading = Direction.IDLE;
                    action = Action.IDLE;
                } else if (next.floor == floor) {
                    boarding = next.boarding;
                    heading = boarding;
                    door = Door.OPENING;
                    action = Action.OPENING;
                } else {
                    heading = next.floor > floor ? Direction.UP : Direction.DOWN;
                    floor += heading == Direction.UP ? 1 : -1;
                    action = Action.MOVED;
                }
            }
            return new Tick(id, action, from, floor, heading, pickups);
        }
```

Opening the doors completes cabin stops. It offers floor pickups only for the requested direction and only with room. The controller checks the assignment before marking those calls served.

The model knows only whole-floor positions. For example, it can begin reopening after an overload at its current model floor. Handling a real car between floors belongs to the device controller, not this floor-step simulation.

### Give a waiting call to another car without losing it

Suppose call 41 is `2 Up`, assigned to A. A becomes unavailable before offering pickup. The controller keeps call 41, removes it from A's plan and gives it to B.

But A might still send a delayed message saying it served call 41. We need to recognise that A's assignment is old.

We attach an **assignment number**, called `epoch` in the code:

1. A owns call 41 with number 1.
2. Releasing that assignment moves the number to 2.
3. B receives the call with number 3.
4. A's late message for number 1 is rejected.

[![Call 41 keeps its identity and waiting age while assignment numbers change, so a late message from the old car cannot clear the replacement's call](lld-figures/elevator-ownership.svg)](lld-figures/elevator-ownership.svg)

The acknowledgement must match the current car and assignment number. It must also come from a car with open doors at the correct floor, offering the correct direction, with room to board.

```java
// source: Elevators.java#ownership
        public synchronized boolean acknowledgePickup(long callId, String carId, long epoch) {
            Request request = requests.get(callId);
            Car car = car(carId);
            if (request == null || request.state != CallState.ASSIGNED
                    || !carId.equals(request.carId) || request.epoch != epoch) {
                return false;
            }
            if (car.door != Door.OPEN || car.floor != request.key.floor
                    || car.boarding != request.key.direction || car.load >= car.capacity
                    || car.mode != Mode.NORMAL) {
                return false;
            }
            request.state = CallState.SERVED;
            active.remove(request.key, request.id);
            car.plan.hall.remove(callId, new HallTask(callId, request.key, epoch));
            return true;
        }
        public synchronized void outOfService(String carId) {
            Car car = car(carId);
            car.mode = Mode.OUT_OF_SERVICE;
            releaseHallCalls(car);
            dispatch();
            // Cabin destinations remain: existing passengers require an operator recovery procedure.
        }
        private void releaseHallCalls(Car car) {
            for (HallTask task : new ArrayList<>(car.plan.hall.values())) {
                Request request = requests.get(task.callId);
                if (request != null && request.state == CallState.ASSIGNED
                        && car.id.equals(request.carId) && request.epoch == task.epoch) {
                    request.state = CallState.WAITING;
                    request.carId = null;
                    request.epoch++;
                }
            }
            car.plan.hall.clear();
        }
```

The call keeps its original creation time, so reassignment does not make a long-waiting person look newly arrived. A full car, a blocked door or a failed travel permission also releases unserved floor calls for another car.

Cabin destinations remain in an unavailable car. Another elevator can collect people waiting at floor 2; copying the destination 7 cannot transfer passengers already inside A. Those passengers need an operator's recovery procedure.

## 6. Interviewer follow-ups

### When should the floor button go out?

When the currently assigned car offers pickup: doors open, correct floor and direction, available with spare capacity. Assigning a car or passing the floor is not enough. After service, a new button press creates a new call identity.

### Why not run one independent thread for every car?

Separate device threads are possible, but shared requests still need one clear owner. Here the controller's short synchronized methods keep assigning a call and adding it to a plan together. A larger design could give each car a message queue; it would still need acknowledged assignments and their numbers.

### Could a call wait too long while new requests keep arriving?

Yes. Considering waiting calls oldest-first does not by itself stop a busy sweep from extending forever. To provide a waiting-time guarantee, add a maximum waiting-time rule or limit how far new arrivals may extend a sweep. The current finite-plan simulation does not claim that guarantee under endless traffic.

### Is replaying every route efficient enough?

It is easy to explain for a small building. For each waiting call, the selector tries each car's known plan. More cars, stops and waiting requests make that work grow. The implementation also retains served-call history, which needs archiving in a long-running system. If measurement shows a problem, keep a separate waiting list and replace replay with a faster route-time estimate through `DispatchPolicy`.

### How would destination-dispatch elevators differ?

They ask for the destination before boarding. The dispatcher can group passengers by destination, but the request now contains more information and repeated presses may have a different meaning. Car, door and load rules still help; the conventional Up/Down request model needs to change.

### What happens after a controller restart?

A production system needs saved calls/assignments and must compare them with current device state before continuing. It must not blindly replay an old travel command. This Java example keeps its state in memory and implements the scheduling rules, not restart recovery or emergency operating procedures.

## 7. Closing answer

“I would separate choosing a car from ordering that car's stops. Floor requests remember a direction; cabin requests stay with the car. Each car follows a directional sweep, and its door/load checks decide whether it may move. A call is served only by a valid pickup from its current assignment. If a car fails, waiting calls move to another car without losing their identity or waiting age.”

## Problem
Design the booking part of a movie-ticket application. Two customers can choose the same seats on their screens. Only one may own them, a customer must get the whole chosen set or none, and a slow payment must never sell the same seat twice.

## Requirements
- Browse movies, cinemas, screens and shows; view a show's seats and prices.
- Hold up to eight seats together, pay for the hold, retrieve the booking and cancel under a stated policy.
- Preserve seat ownership under concurrent requests, repeated requests, expiry and late payment callbacks.
- Start with a complete Java design for one process, then explain the transaction needed when several application servers share inventory.

## 1. Start with two customers and two seats

Asha and Bilal both select **A7 and A8 for the 7 pm show**. Each seat costs ₹250. Both screens may say “available”, because neither customer has reserved anything yet. Asha presses Continue first. The server holds both seats for her for two minutes and freezes the price at **₹500**. Bilal's request then receives a conflict. He gets neither seat and is not sent to payment for this cart.

That is the central design decision: **the server changes ownership when it creates a hold, not when it draws the seat map**. Availability on a screen is advice. A successful hold is a promise with an expiry time.

In an interview, I would clarify four points before drawing classes:

| Question | Chosen answer | What it changes |
| --- | --- | --- |
| Are seats assigned? | Yes, for a particular show | A7 in the matinee is different inventory from A7 at 7 pm |
| Can a cart partially succeed? | No | Claim every chosen seat in one operation |
| How long is a hold? | Two minutes for this example | At the exact deadline it is expired; this is a product policy, not a universal duration |
| What if payment finishes late? | Release at the deadline; refund a capture received afterwards | A payment success alone cannot resurrect released inventory |

For this answer, cancellation is allowed before the show starts and refunds the full captured amount. The Java mechanism models eligible cancellations; a real endpoint must check the show's start time and refund policy before calling it. Refund settlement, tax rules, search ranking and cinema onboarding are outside this object's scope. I would state those boundaries rather than hide them behind unfinished methods.

**The rules we must preserve:** one owner per `(showId, seatNumber)`; a cart owns all its seats or none; a quote does not change during a hold; expired and cancelled reservations never become confirmed; repeating an operation does not create another charge, ticket or refund intent.

[Step through both arrival orders and a late payment](learning-labs/index.html?topic=booking). The seats visibly change owner as the tested Java service runs. This is a recorded execution with Previous/Next controls, not a live payment integration. A complete text trace is available on the same page.

## 2. Give each object one clear job

[![A customer calls BookingService, which owns holds and show-seat allocations; payment runs outside its lock and late captures create refund intents.](learning-figures/booking-ownership.svg)](learning-figures/booking-ownership.svg)

Open the diagram at full size by selecting it.

The important relationship in this picture is between the hold and the show-seat allocation. They must change together. The payment provider is outside that operation because a network call may be slow or return no definite answer.

| Type | Responsibility and important data |
| --- | --- |
| `Movie`, `Cinema`, `Screen`, `Show` | Catalogue. A show connects one movie, one screen and one start time. A screen's physical seat layout is reused by many shows. |
| `Seat(show, number)` | Identity of one sellable seat for one show. It is a Java record, so equality includes both values. |
| Internal `Hold` | The mutable reservation: owner, sorted seat list, frozen price, deadline, reservation state and payment state. Only `BookingService` mutates it. |
| `Reservation` | An immutable owner-facing snapshot, including `refundState` and `refundAmountPaise`. The caller cannot change the service's state by editing it. |
| `Attempt` | The stable payment key and amount for one reservation. Repeated attempts to send the same intent reuse this key. |
| `Receipt` | An authenticated provider outcome bound to that attempt. Request parameters from a browser are never trusted as proof of payment. |
| `Refund` | A request to return a particular captured charge. Its existence means “refund needed”, not “money has reached the bank account”. |
| `Reconciliation` | Contradictory provider evidence, with reservation, attempt, charge and amount, for a worker to investigate before taking a financial action. |

The service stores two related maps: reservation ID to internal hold, and show-seat to owning reservation ID. It also remembers successful request keys and refund intents. An owner's snapshot says `PENDING` with the actual captured refund amount once that work is recorded; `NOT_REQUIRED` means no refund intent exists. It never reports settlement as completed. Public seat browsing uses `availability(show)`, which omits customer identities; `seats(show)` is an internal diagnostic view for the trace. The catalogue can use a separate read-only repository because it does not decide who owns inventory.

I would expose these application operations:

```text
POST /shows/{showId}/holds
  authenticated customer; Idempotency-Key; body { seatNumbers: ["A7", "A8"] }
  -> reservation ID, frozen amount, expiry, state; conflict if any seat is unavailable

POST /reservations/{id}/payment
  authenticated owner -> one stable payment intent, not a new charge for each retry

GET /reservations/{id}
  authenticated owner -> current reservation and payment states

POST /reservations/{id}/cancellation
  authenticated owner + checked cancellation policy -> terminal reservation + refund status

POST /payments/provider-callback
  verified provider signature + server-side receipt binding -> apply provider outcome
```

An **idempotency key** identifies one logical request despite retries. It is scoped to the customer. If Asha retries the same key with the same seats in a different order, she gets the same reservation. Reusing it for a different cart is an error. If that reservation has expired, the retry returns its expired state; a fresh cart needs a fresh key. Silently making a new hold would change the meaning of her original request.

## 3. Reserve the whole cart before talking to payment

Here is the actual reservation method from the runnable implementation. All service mutations use the same monitor (`synchronized`), so another thread cannot observe a half-written cart.

```java
public synchronized Reservation hold(String customer, String requestKey, String show, List<String> requested) {
    text(customer); text(requestKey); text(show); Objects.requireNonNull(requested);
    if (requested.isEmpty() || requested.size()>8 || new HashSet<>(requested).size()!=requested.size())
        throw new IllegalArgumentException("choose 1..8 distinct seats");
    requested.forEach(BookingService::text);
    List<String> seats=requested.stream().sorted().toList();
    Request request=new Request(customer,requestKey);
    Fingerprint fingerprint=new Fingerprint(show,seats);
    if (requests.containsKey(request)) {
        if (!fingerprints.get(request).equals(fingerprint)) throw new IllegalArgumentException("key reused with another cart");
        Hold old=holds.get(requests.get(request)); expire(old,clock.instant()); return old.view();
    }
    Instant now=clock.instant(); long total=0;
    for (String number:seats) {
        Seat seat=new Seat(show,number);
        Long price=prices.get(seat);
        if (price==null) throw new IllegalArgumentException("unknown show-seat");
        UUID owner=owners.get(seat);
        if (owner!=null) expire(holds.get(owner),now);
        if (owners.containsKey(seat)) throw new IllegalStateException("seat unavailable: "+number);
        total=Math.addExact(total,price);
    }
    // Validation above changes no new ownership. Only a completely available cart reaches here.
    Hold hold=new Hold(customer,show,seats,total,now.plus(holdFor));
    holds.put(hold.id,hold);
    for (String number:seats) owners.put(new Seat(show,number),hold.id);
    requests.put(request,hold.id); fingerprints.put(request,fingerprint);
    return hold.view();
}
```

Read the method in three parts. First, it checks the request and handles a successful prior request with the same key. Second, it checks every seat and adds the prices in paise, using overflow-checked integer arithmetic. Third, only after the entire set is available, it assigns every seat to the new reservation. Rejecting A8 must not leave A9 held from a partially completed cart.

The sorted, immutable seat list gives equivalent retries the same meaning. The eight-seat limit is a chosen cart policy that bounds the work; it is not a limitation of object-oriented design. The price comes from server inventory, never from the amount submitted by a browser.

This is deliberately a small, complete object rather than a class hierarchy for every noun. There is one place responsible for the ownership rule. That follows single responsibility more usefully than adding an abstract factory before we have a real variation to support. A payment adapter is a sensible future interface because providers differ; a `SeatFactoryFactory` would add no useful capability here.

### What changes when there are several servers?

Java's monitor protects one service instance. It cannot coordinate servers A and B. I would move the same atomic decision into a database transaction, using pre-created inventory rows keyed by `(show_id, seat_number)`:

```sql
-- Protocol outline, not an executable database adapter in this example.
BEGIN;
-- First create a lockable request identity, even on its first use.
INSERT INTO booking_request(customer_id, request_key, payload_hash, status)
VALUES (:customer, :key, :fingerprint, 'PROCESSING')
ON CONFLICT (customer_id, request_key) DO NOTHING;
SELECT * FROM booking_request
WHERE customer_id = :customer AND request_key = :key FOR UPDATE;
-- Compare the fingerprint; replay a completed result if present.
-- Otherwise lock selected inventory rows in a consistent order.
SELECT show_id, seat_number, owner_reservation, expires_at, state, price_paise
FROM show_seat
WHERE show_id = :show AND seat_number IN (:chosen_seats)
ORDER BY show_id, seat_number
FOR UPDATE;
-- Check the exact row count, expiry and availability of the whole cart.
-- Insert the reservation, assign every seat and complete the request row.
COMMIT;
```

The request insert uses a unique `(customer_id, request_key)` and waits for a conflicting transaction to finish. Under PostgreSQL READ COMMITTED, the following row-lock statement can read the winner's committed row. A missing-row `SELECT FOR UPDATE` alone would lock nothing. The initial `PROCESSING` row is never committed separately: the successful request result, reservation and seats commit together, or all roll back. A crash before commit leaves no abandoned claim. Compare the stored fingerprint before replaying so the key cannot identify another cart. Deadlocks or serialization failures require a bounded retry of the **whole transaction** under the same key. Inventory-changing writers, including expiry, cancellation and receipts, must use a compatible inventory lock order.

A primary key prevents duplicate seat rows; it does **not** by itself stop two updates from assigning the existing row to different owners. The check and ownership change must be inside the transaction. PostgreSQL's [row-lock documentation](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS) explains what `FOR UPDATE` protects. The database adapter is an extension boundary, not a distributed guarantee established by the local Java tests.

The seat-map cache may lag. This is acceptable because its job is to help a customer choose; the transactional hold operation remains authoritative. Never confirm from a cached availability response.

## 4. Keep reservation state separate from payment state

“Has this customer got the seats?” and “Did we receive the money?” are different questions. Combining them into one enum makes timeout and late-callback cases difficult to represent.

[![A live hold can confirm before expiry, expire at its deadline or cancel; late captures on terminal reservations create one refund intent and never reacquire seats.](learning-figures/booking-states.svg)](learning-figures/booking-states.svg)

Open the diagram at full size by selecting it.

Reservation state is `HELD`, `CONFIRMED`, `EXPIRED` or `CANCELLED`. Payment state is `NOT_STARTED`, `PENDING`, `UNKNOWN`, `DECLINED` or `CAPTURED`. A reservation can be `EXPIRED` while its payment is `CAPTURED`; that is exactly the case that needs a refund. A confirmed reservation does not expire when the old hold deadline passes.

The payment path has three stages:

1. Under the short service lock, `beginPayment` checks ownership and expiry, then creates or returns the stable attempt key and frozen amount.
2. Outside the lock, the adapter sends the payment request using that key. A timeout means **unknown**, because the provider might have captured money before the response was lost. The adapter queries/reconciles the same intent instead of inventing a new charge key.
3. Under the lock again, `acceptReceipt` checks the attempt binding, applies the result and decides whether it can confirm. Signature verification and provider lookups happen at the adapter boundary, not by trusting a client field saying `paid=true`.

The implementation is below. A first consistent capture follows the reservation diagram. Contradictory provider evidence is different: the service records a deduplicated `Reconciliation`, then throws a typed `ReceiptConflict` carrying that evidence. It does not silently confirm or refund a second, conflicting claim.

```java
public synchronized Attempt beginPayment(String customer, UUID id) {
    Hold hold=owned(customer,id); expire(hold,clock.instant());
    if (hold.state!=State.HELD) throw new IllegalStateException("hold is not payable");
    if (hold.attempt==null) { hold.attempt="reservation/"+id; hold.payment=Payment.PENDING; }
    return new Attempt(id,hold.attempt,hold.total);
}
// No provider call runs under the service monitor. The caller sends Attempt.key as its idempotency key.
public synchronized Reservation acceptReceipt(UUID id, Receipt receipt) {
    Objects.requireNonNull(receipt);
    Hold hold=required(id);
    if (hold.attempt==null || !hold.attempt.equals(receipt.attemptKey()))
        throw new IllegalArgumentException("receipt does not match the payment attempt");
    if (!Set.of(Payment.UNKNOWN,Payment.DECLINED,Payment.CAPTURED).contains(receipt.result()))
        throw new IllegalArgumentException("not a provider outcome");
    expire(hold,clock.instant());
    if (receipt.result()==Payment.CAPTURED) {
        text(receipt.chargeId());
        if (receipt.amountPaise()<=0) throw new IllegalArgumentException("positive captured amount");
        UUID previous=charges.get(receipt.chargeId());
        if (previous!=null && !previous.equals(id)) throw conflict(hold,receipt,"charge already belongs to another reservation");
        if (hold.charge!=null) {
            if (!hold.charge.equals(receipt.chargeId()) || hold.chargedAmount!=receipt.amountPaise())
                throw conflict(hold,receipt,"conflicting capture: reconcile with provider");
            return hold.view(); // Identical callback is a no-op, even after cancellation.
        }
        if (hold.payment==Payment.DECLINED) throw conflict(hold,receipt,"conflicting terminal payment: reconcile");
        charges.put(receipt.chargeId(),id); hold.charge=receipt.chargeId();
        hold.chargedAmount=receipt.amountPaise(); hold.payment=Payment.CAPTURED;
        if (hold.state==State.HELD && receipt.amountPaise()==hold.total) hold.state=State.CONFIRMED;
        else {
            if (hold.state==State.HELD) { hold.state=State.CANCELLED; release(hold); }
            refund(hold,receipt.amountPaise()==hold.total?"paid after release":"captured amount differs from quote");
        }
    } else if (hold.payment!=Payment.CAPTURED && hold.payment!=Payment.DECLINED) {
        hold.payment=receipt.result();
        if (hold.payment==Payment.DECLINED && hold.state==State.HELD) { hold.state=State.CANCELLED; release(hold); }
    }
    return hold.view();
}
```

A capture with the wrong amount cannot buy a ticket. This implementation cancels a still-live hold and creates a refund intent for the **actual captured amount**, not the expected quote. A duplicated identical capture is a no-op, including after cancellation. A stale decline cannot downgrade a capture already accepted.

In a persistent implementation, the reservation update and refund intent belong in one database transaction. A worker sends the refund with a stable refund key, records its provider ID and retries uncertain outcomes. This is an **outbox**: a durable record of an action still to perform. The authenticated callback adapter also owns conflicts: catch `ReceiptConflict`, durably quarantine its attempt/charge/amount evidence in a successful transaction, and only then acknowledge delivery. Do not put the evidence only in the failed transaction that rolls back. A reconciler checks the provider's actual intent before choosing a financial action. The local maps demonstrate owned work and deduplication; they disappear on restart and do not settle refunds or prove durable quarantine.

## 5. Walk through the race that usually breaks a booking system

| Time since Asha's hold | Event | Seat owner and resulting action |
| --- | --- | --- |
| 0 seconds | Asha holds A7 and A8 and starts payment | Asha; quote ₹500 |
| 119 seconds | The provider response is still uncertain | Asha; payment `UNKNOWN`, hold still valid |
| Exactly 120 seconds | Another operation checks expiry | No owner; Asha's reservation becomes `EXPIRED` |
| 120 seconds | Bilal successfully holds both seats | Bilal, under a new reservation ID |
| 121 seconds | Asha's capture callback arrives | Bilal stays owner; Asha stays expired; create one ₹500 refund intent |
| 122 seconds | The same callback is delivered again | No new booking and no additional refund intent |

The expiry boundary is `now >= expiresAt`. The release operation also compares the reservation ID. It does not just say “mark A7 available”, because by then A7 may belong to Bilal.

```java
private void expire(Hold hold, Instant now) {
    if (hold.state==State.HELD && !now.isBefore(hold.expires)) { hold.state=State.EXPIRED; release(hold); }
}
private void release(Hold hold) {
    // Compare owner as well as seat: an old callback must never release a newer hold.
    for (String number:hold.seats) owners.remove(new Seat(hold.show,number),hold.id);
}
```

Expiry is lazy in this small implementation: a hold is checked when read, paid, cancelled or encountered during another hold request. A background sweep can make the displayed map fresher, but correctness cannot depend on that sweep running exactly on time. Every operation that might confirm or acquire ownership must check the deadline itself.

The server clock is injected so deadline tests are deterministic. In a shared database, use the database's time consistently for transactional decisions; do not let independent browser clocks decide ownership. A payment capture that happened before the deadline but was learned afterwards is refunded under our chosen firm-deadline policy. A product that wants a payment grace period must explicitly extend ownership before expiry and accept that other customers wait longer.

### Keep the design simple, then strengthen the right boundary

A global monitor is easy to reason about for an interview and this small executable example. Its cost is that unrelated shows contend. Per-show locks reduce that contention, but their lifecycle and lock order become part of the design; a database-backed service usually uses row-level transactions instead. A queue can absorb demand for a blockbuster, but it still needs an authoritative seat-allocation operation.

One Redis lock per seat is not enough: a cart can acquire A7 and fail on A8, or the lease can expire while payment is still running. If Redis is used, the entire multi-seat decision, ownership token checks and recovery rules need a coherent atomic protocol. A cache is not automatically a simpler substitute for a transactional inventory table.

The in-memory request history and refund map grow forever and disappear on restart. A real service persists them, defines retention based on retry/reconciliation windows, and restores pending work after a crash. Monitor hold-conflict rate, expiry rate, callbacks with no matching attempt, captured-but-unfulfilled reservations and oldest pending refund. Those metrics reveal broken customer promises more directly than server CPU alone.

## 6. Interviewer follow-ups

**Why hold seats before payment?** Otherwise two customers can both pay for the same seats, leaving the service to disappoint one afterwards. A short hold trades temporary blocked inventory for a clear ownership promise. The deadline limits abandoned-cart impact.

**Can we guarantee exactly one provider charge?** The service guarantees one payment intent key per reservation. Preventing duplicate remote charges also depends on the provider honoring that key over the required retry period. If its idempotency window expires, reconcile by provider intent/charge ID before retrying; a local map is not proof of remote exactly-once execution.

**What happens if payment succeeds and the application crashes before confirmation?** The durable reservation remains held or later expires. A verified callback or reconciliation job finds the intent and either confirms the still-owned seats or records a refund. The reservation, receipt processing and outbox must be persisted; the teaching process deliberately has no crash durability.

**Can we give Asha her seats back after Bilal holds them?** No. Asha's reservation is terminal and her old owner token has no authority over Bilal's cart. Refund Asha or offer a new, separately accepted booking. Do not silently change Bilal's inventory to repair a previous payment race.

**Which patterns are doing useful work?** Immutable records protect returned data; one application service owns state transitions; a payment adapter isolates provider-specific I/O; an outbox makes refund work recoverable in the persistent version. The State pattern could replace the enum if transitions became complex, but four states do not justify a hierarchy on their own.

## 7. Closing answer

“I would model inventory by show and seat, reserve a complete cart atomically, and return an immutable reservation with a frozen quote, deadline and pending-refund status. Payment uses one stable intent outside the inventory lock. Only a matching, paid, unexpired hold can confirm. A first consistent late capture records refund work without touching a newer owner; contradictory provider evidence goes to owned reconciliation work. Several servers need these decisions and work records inside durable transaction protocols.”

## Problem

Design an ATM that lets a customer insert a card, authenticate, check a balance and withdraw cash.

Suppose the customer asks for $60. The bank reserves $60, the machine starts dispensing three $20 notes, and then the device reply times out. Did the customer receive nothing, two notes or all three? The timeout does not tell us. Refunding the whole amount or sending another cash command could both be wrong.

The design therefore needs to remember what it knows, preserve what is uncertain and resolve the original withdrawal before starting another one.

## Requirements

I will choose a small, explicit scope:

- One ATM serves one card session at a time, using one bank and one currency, US dollars.
- The machine contains $20 and $50 notes. Amounts are represented as integer cents, never floating point. A request must be positive, in $10 increments and at most $500; the machine must still find an exact available note combination.
- The bank authenticates the card and PIN evidence and owns account balances. The ATM owns its note inventory and withdrawal records.
- A session can view its available balance and request a withdrawal. Under our chosen policy, three explicit authentication denials end the session and request card ejection. A bank outage does not count as a wrong PIN.
- Each withdrawal has one stable ID. Retrying it returns the saved result; reusing it for another amount or session is rejected.
- Reserve funds before sending a cash command. Settle the bank hold for the amount finally confirmed as delivered; release the unused part of the hold.
- Unknown bank or device outcomes remain unresolved. Block further cash withdrawals until they are resolved. A jammed or quarantined note is unavailable until maintenance.

Deposits, transfers, PIN changes, fees, other banks, currency conversion and receipt-printer hardware are outside this solution. The runnable Java mechanism uses local records and deterministic bank/device fixtures. The recovery section below explains the durable records required before connecting real cash hardware; a process lock and an in-memory map do not survive power loss.

## 1. Start with the customer's $60

Assume the account has $100, with no other holds. The machine has three $20 notes and one $50 note, worth $110 in total.

Two kinds of balance now matter:

- **Ledger balance:** money recorded in the account, initially $100.
- **Available balance:** ledger balance minus active holds. A $60 hold leaves $40 available while the withdrawal is being resolved.

A hold reserves spending power. It is not yet the final debit. The bank must reserve atomically because the same account may also be used at another ATM or by another payment channel.

There are also two separate inventories: money in the customer's bank account and notes inside this physical machine. A Java transaction cannot atomically update both the bank and the physical world.

Here is the withdrawal that will carry the design:

| Event | Bank | ATM cash | Withdrawal W17 |
| --- | --- | --- | --- |
| Customer requests $60 | Ledger $100; held $0 | Available: 3×$20, 1×$50 | Choose 3×$20. |
| Bank confirms hold | Ledger $100; held $60 | Reserve 3×$20; only 1×$50 remains available. | Cash command may now start. |
| Device outcome is unknown | Keep the hold. | Keep all three notes reserved. | `CASH_UNKNOWN`; no new cash command. |
| Customer retries W17 | No new hold. | No new dispense. | Return the same unresolved result. |
| Final evidence says two notes were delivered and one was quarantined | Debit $40, close the $60 hold and release the other $20. | Record 2×$20 delivered; keep 1×$20 quarantined. | `PARTIAL`, delivered $40. |

The final account balance is $60, with no remaining hold. The customer received $40. One $20 note remains in the machine but is unavailable for another withdrawal. The available cassette still contains its $50 note.

[Open the ATM walkthrough](learning-labs/atm.html) to follow these exact Java states, compare proven zero delivery with an unknown result, or inspect a lost bank reply. Every scenario has a complete text transcript.

## 2. Give the bank, session and dispenser different jobs

| Component | Responsibility | Important boundary |
| --- | --- | --- |
| Card reader | Detect insertion, supply an opaque card reference and attempt ejection. | A card reference is not a copied card secret. Failed ejection blocks another session. |
| Secure PIN input | Obtain PIN input through the hardware/security integration and provide opaque evidence for authentication. | The domain model does not receive, log or compare PIN digits. |
| ATM session | Track card insertion, authentication and account authority for the current customer. | Ending the card session does not erase an unresolved withdrawal. |
| Bank port | Authenticate, read balances, reserve funds and settle a reservation idempotently. | It owns global account correctness; the ATM does not cache an authoritative balance. |
| Cash inventory and planner | Choose and reserve an exact note combination, then account for the outcome. | Reserved or quarantined notes are unavailable to another withdrawal. |
| Dispenser port | Execute one cash command and report or query its outcome. | A command acknowledgement, notes presented and notes taken are different facts. |
| Withdrawal record | Bind ID, session, account, amount, note plan, phase and final evidence. | Retries and reconciliation refer to this record instead of creating another withdrawal. |

[![The card reader and secure PIN input feed the ATM session. A withdrawal record connects the bank's hold and settlement with an exact cash reservation and a dispenser command whose outcome can be queried.](designs/lld-5.svg)](designs/lld-5.svg)

The Java `Machine` coordinates these small components. An enum is enough for four session states: `IDLE`, `CARD_INSERTED`, `AUTHENTICATED` and `CARD_ERROR`. An authentication denial keeps the customer at PIN entry until the chosen attempt limit; successful authentication enables account operations. Ejection clears account authority. If ejection fails, the machine enters `CARD_ERROR` and cannot accept a new card.

There is no need for a subclass per screen or a transaction framework for four methods. If the product later has many state-specific events, a State pattern may help organize them. The state rules must be clear before introducing that pattern.

### Facts that must stay true

- Never send a cash command without a confirmed funds reservation for that withdrawal.
- One live withdrawal record initiates at most one physical cash command. A retry or an inconclusive device lookup cannot initiate another.
- Each note is available, reserved, delivered out of the machine or quarantined. Do not put an uncertain or jammed note back in the available cassette.
- Final device evidence must account for every reserved note by denomination: **delivered + reusable + quarantined = planned**.
- Settle only a confirmed delivered amount, between zero and the requested amount. Repeat the same settlement ID and amount if its response is lost.
- A withdrawal's identity, account, amount and final evidence cannot silently change.

## 3. Find an exact note plan before touching the bank

A large-note-first greedy chain is not enough for our chosen cassettes. For $60, it would take the $50 note, then fail to make the remaining $10. Three $20 notes are available, so rejecting that request would be a mistake.

The planner tries each possible $50 count, starting with the largest available count. For each choice, it asks whether the remainder can be made entirely from available $20 notes:

```text
$60 with 1×$50: remainder $10 -> impossible
$60 with 0×$50: remainder $60 -> 3×$20 -> exact plan
```

The maximum request is $500, so there are at most eleven possible $50 counts to try. With these two denominations, the first feasible plan also uses the fewest notes: for a fixed amount, using more $50 notes reduces the total note count. We do not claim this algorithm works unchanged for arbitrary denominations.

```java
public record Notes(int twenties, int fifties) {
    public static final Notes NONE = new Notes(0, 0);
    public Notes {
        if (twenties < 0 || fifties < 0) throw new IllegalArgumentException("Negative note count");
    }
    public long valueCents() { return 2_000L * twenties + 5_000L * fifties; }
    public Notes plus(Notes other) {
        return new Notes(Math.addExact(twenties, other.twenties), Math.addExact(fifties, other.fifties));
    }
    public Notes minus(Notes other) { return new Notes(twenties - other.twenties, fifties - other.fifties); }
}

/** Try every feasible $50 count, largest first; the remaining amount must be $20 notes. */
public static Optional<Notes> plan(int amountCents, Notes available) {
    if (amountCents <= 0 || amountCents > 50_000 || amountCents % 1_000 != 0)
        throw new IllegalArgumentException("Amount must be $10 increments, greater than 0, at most $500");
    for (int fifties = Math.min(available.fifties(), amountCents / 5_000); fifties >= 0; fifties--) {
        int rest = amountCents - 5_000 * fifties;
        if (rest % 2_000 == 0 && rest / 2_000 <= available.twenties())
            return Optional.of(new Notes(rest / 2_000, fifties));
    }
    return Optional.empty();
}
```

`plan` only calculates. `CashInventory.reserve` then removes the selected notes from available inventory and records them against W17 under the machine's lock. If no exact plan exists, return `NO_NOTES` without asking the bank for a hold. Having enough total cash is insufficient: a machine containing only a $50 note cannot pay $20.

## 4. Run a recoverable withdrawal

The normal sequence is:

1. Require an authenticated session and a valid request. Look up the stable withdrawal ID before starting new work.
2. Reserve an exact note plan and create the withdrawal record, including its account and session. Record that bank authorization is pending before making that call.
3. Ask the bank to reserve the requested funds using W17. A definite decline releases the unspent note reservation. An unknown result keeps the reservation and enters `FUNDS_UNKNOWN`; no cash command has started.
4. After a confirmed hold, record `DISPENSING` before invoking the dispenser with command ID W17.
5. If delivery is unknown or the reported counts do not account for the plan, enter `CASH_UNKNOWN`. Keep the whole hold and note reservation.
6. When final evidence accounts for the notes, move reusable notes back to available inventory and jammed/rejected notes to quarantine. Save the delivered amount.
7. Settle W17 for that delivered amount. The bank atomically debits it and releases the unused hold. A lost settlement response enters `SETTLEMENT_UNKNOWN`; repeat the same bank settlement to confirm it, without touching the dispenser again.
8. Report `COMPLETED`, `PARTIAL` or `NO_CASH` only after settlement is confirmed.

![The ATM reserves an exact note plan, obtains a bank hold and sends one cash command. Unknown outcomes keep reservations; final delivery evidence leads to idempotent settlement of the delivered amount.](learning-figures/lld-5-flow.svg)

Our bank port deliberately promises an idempotent reservation and a single idempotent `settle(id, deliveredAmount)` operation that both debits delivered cash and closes the remaining hold. The teaching hold does not expire on its own. A real bank adapter must establish an equivalent contract; inventing a debit/credit pair in the ATM does not provide it.

### Keep the three uncertain outcomes separate

| Saved phase | What is uncertain | Next action |
| --- | --- | --- |
| `FUNDS_UNKNOWN` | Whether the bank granted the hold. No cash command has been initiated. | Query the original bank reservation. Dispense only after confirmation. |
| `DISPENSING` or `CASH_UNKNOWN` | Whether and how many notes reached the customer. | Query the original device command or escalate to physical reconciliation. Keep funds and notes reserved. |
| `SETTLING` or `SETTLEMENT_UNKNOWN` | Cash delivery is known; bank settlement is not confirmed. | Repeat/query the same idempotent bank settlement for the saved delivered amount. Never dispense again. |

A transport timeout is not a final “none delivered” report. Even a report labelled final is unusable if, for example, only one of three planned notes is accounted for.

![A lost dispenser reply preserves the $60 hold and three-note reservation. A retry sends no cash. Final evidence of two delivered twenties and one quarantined twenty settles $40 and leaves the jammed note unavailable.](learning-figures/lld-5-unknown.svg)

The device adapter's `Report` means **final customer delivery**, with every other reserved note classified as reusable or quarantined. It cannot simply treat a low-level “dispense” callback as “customer received cash.” The [CEN-hosted XFS cash-dispenser reference](https://www.cencenelec.eu/media/CEN-CENELEC/AreasOfWork/CEN%20sectors/Digital%20Society/CWA%20Download%20Area/XFS/CWA16926_Release3.40/TrackChanges/cwa-16926-64.pdf) distinguishes presentation, items taken and retraction. Our small Java port combines the evidence it needs into a teaching contract; it is not an implementation of that device API.

`PinEvidence` contains a reference supplied by a trusted secure-input integration, not PIN digits or a reversible toy encoding. This is the full request/reconciliation entry point:

```java
public synchronized WithdrawalView withdraw(String id, int amountCents) {
    requireAuthenticated(); requireKey(id);
    Withdrawal old = withdrawals.get(id);
    if (old != null) {
        if (!old.sessionId.equals(sessionId) || old.requestedCents != amountCents)
            throw new IllegalArgumentException("Withdrawal ID payload conflict");
        return old.view();
    }
    if (cashBlocked()) throw new IllegalStateException("Cash operation unresolved or machine needs service");
    Optional<Notes> selected = cash.reserve(id, amountCents);
    Withdrawal op = new Withdrawal(id, sessionId, account, amountCents, selected.orElse(null));
    withdrawals.put(id, op);
    if (selected.isEmpty()) return op.view();
    activeId = id;
    handleHold(op, bank.reserve(id, account, amountCents));
    return op.view();
}

/** Trusted maintenance operation; a customer UI must not expose this as an unrestricted endpoint. */
public synchronized WithdrawalView reconcile(String id) {
    Withdrawal op = Objects.requireNonNull(withdrawals.get(id), "Unknown withdrawal");
    if (op.terminal()) return op.view();
    switch (op.stage) {
        case FUNDS_UNKNOWN -> handleHold(op, bank.lookupHold(id));
        case DISPENSING, CASH_UNKNOWN -> handleReport(op, dispenser.lookup(id));
        case SETTLING, SETTLEMENT_UNKNOWN -> settle(op);
        default -> throw new IllegalStateException("Unexpected phase");
    }
    return op.view();
}
```

The old-ID branch returns before any new bank or hardware action. A same-ID request with a different amount or session is rejected. Validation errors before creating a record do not consume that ID. The caller must preserve the same ID when retrying; creating W18 after losing W17's response would describe a different withdrawal, which is why unresolved cash work also blocks new IDs on this machine.

`reconcile` is a trusted maintenance operation, not an unrestricted customer endpoint. It can continue after the card has been ejected because the withdrawal keeps the account reference independently of the session.

The remaining transitions are small enough to show in full:

```java
private void handleHold(Withdrawal op, HoldStatus result) {
    if (result == null || result == HoldStatus.UNKNOWN) { op.stage = Stage.FUNDS_UNKNOWN; return; }
    if (result == HoldStatus.DECLINED) {
        cash.release(op.id); op.stage = Stage.DECLINED; activeId = null; return;
    }
    op.stage = Stage.DISPENSING; // Record intent before the first external cash command.
    handleReport(op, dispenser.dispense(op.id, op.plan));
}

private void handleReport(Withdrawal op, Report report) {
    if (report == null || !report.accountsFor(op.plan)) {
        op.stage = Stage.CASH_UNKNOWN; // Do not refund, free notes or issue a new cash command.
        return;
    }
    op.evidence = report;
    cash.accountFor(op.id, report);
    needsService |= report.quarantined().valueCents() > 0;
    op.stage = Stage.SETTLING;
    settle(op);
}

private void settle(Withdrawal op) {
    int deliveredCents = Math.toIntExact(op.evidence.delivered().valueCents());
    if (bank.settle(op.id, deliveredCents) != Settlement.APPLIED) {
        op.stage = Stage.SETTLEMENT_UNKNOWN;
        return;
    }
    op.stage = deliveredCents == op.requestedCents ? Stage.COMPLETED
        : deliveredCents == 0 ? Stage.NO_CASH : Stage.PARTIAL;
    activeId = null;
}
```

Final note accounting happens once, before settlement. A settlement retry uses the saved evidence and does not remove inventory again. Under our conservative policy, any quarantined note requires maintenance before another cash withdrawal, even after the money has been settled.

The machine synchronizes its operations because there is one card session and one physical cash path. In this focused example, calls to its ports have bounded deadlines and return explicit unknown outcomes. The bank fixture has its own atomic reservation boundary for shared account funds. A [Java instance lock](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.4.3.6) protects only callers sharing that object; it does not lock a bank, another JVM or a motor.

### What the in-memory example cannot recover

The map remembers operations only while the process runs. Connecting real cash hardware requires a durable withdrawal journal. Store at least:

```text
withdrawal_id, machine_id, session_ref, account_ref, requested_cents,
reserved_note_counts, bank_reservation_ref, phase, device_command_id,
final_delivered/reusable/quarantined_counts, settlement_amount, receipt
```

Persist the reservation and phase before each external effect. In particular, commit a cash-command intent **before** invoking the motor. If that write cannot be confirmed, do not send cash. On restart, take cash service out of use, load unresolved records and reconcile their original bank/device IDs before serving another withdrawal.

A crash after cash-command intent creates an awkward window: the command might never have been sent, or it might have delivered cash before the process died. Both cases have the same local phase. Query the device journal; do not infer non-delivery from a missing reply. If the device cannot prove a final outcome or safely identify an original command across restart, keep the machine blocked and perform bank/device/operator reconciliation. A fresh command ID does not solve that uncertainty.

No software transaction can pull back notes the customer already took. Durable records, explicit device evidence and the bank's settlement contract are the pieces that make recovery possible; this local example does not claim to supply a certified ATM stack.

## 6. Interviewer follow-ups

**Why hold first instead of debit and blindly refund on failure?** A hold reserves funds without prematurely treating the requested amount as delivered. Later evidence can settle all, part or none. A device timeout is not proof that a refund is due; blindly refunding it can give the customer both cash and a restored balance. The bank must support the chosen settlement contract or provide an equivalent specified protocol.

**When may you safely release all reserved funds and notes?** After a definite bank decline before any cash command, or after final device evidence proves zero delivery and accounts for every note. Only notes confirmed reusable return to the available cassette. Notes in a reject bin or jam remain quarantined even when no customer cash was delivered.

**What if the bank hold expires while the device outcome is unknown?** Our chosen port has no automatic expiry. For a real adapter, hold lifetime and late settlement are explicit bank-contract requirements. Reaching a local timeout cannot make a physical delivery disappear or justify forgetting the withdrawal. Keep reconciling the original operation and handle any expired authorization through the bank's supported exception process; do not claim a normal hold still exists after its authority has expired.

**Are stable IDs enough to make physical cash exactly once?** No. Our live-process record prevents repeated command initiation. Recovery also needs a durable record and a device protocol that can identify and query the original command. A Java map cannot promise that a device forgets nothing after power loss. If that protocol is unavailable, uncertain cases require physical reconciliation rather than automatic resend.

**What happens if two withdrawals compete for the last notes or the same bank balance?** This single ATM serializes cash reservation and withdrawal progression. The bank atomically checks available funds and creates each hold, so other machines cannot spend the same funds. A process lock at one ATM is not the bank's global account lock. The test exercises the local bank fixture's atomic behavior; a real bank adapter must provide that contract.

**Should a slow bank call hold the machine lock?** This example does so to keep one physical cash path easy to inspect; the adapters must use bounded waits. A responsive production UI would record a pending phase under the lock, release it for I/O, then apply the result under the lock only if it still matches that withdrawal and phase. Ejecting a card must not cancel a command already sent. Do not introduce another device command while the first is unresolved.

**Why not use Chain of Responsibility for each denomination?** A greedy chain gives the wrong answer for our $60 example. The important abstraction is a side-effect-free exact planner over bounded cassette counts, followed by a reservation. For many denominations, use bounded dynamic programming or backtracking with explicit limits. Change the algorithm only when the denomination set justifies it; physical dispense remains one recorded operation, not one independent command per handler.

**What if printing the receipt fails?** Keep the saved withdrawal result and offer an on-screen or later receipt for W17. Printing failure does not refund confirmed cash or initiate another withdrawal. The receipt must say unresolved while evidence or settlement is unknown; it must not confidently claim cash was or was not delivered.

## 7. Closing answer

“I would separate the card session from a withdrawal that can outlive it. The ATM reserves an exact note plan, asks the bank to hold funds and records one stable cash command. Final delivery evidence determines how much to settle; unknown outcomes keep the funds and notes reserved and block further cash. Retries return the original operation, and reconciliation queries its bank and device IDs. Before connecting real hardware, I would persist each phase and verify the bank/device recovery contracts, because a Java rollback cannot undo cash already handed to a customer.”

## Problem

Design a car rental system like Zoomcar or Hertz: customers search vehicles by location and date range, reserve them, pick up, return (possibly at another branch) and pay. The key challenges are **inventory availability over time ranges**, pricing as a **Strategy**, and vehicle creation with a **Factory**.

## Requirements

**Functional**
- Search available vehicles by branch, type and `[from, to]` range.
- Reserve, modify and cancel. Pick up and return, with mileage and fuel or charge recorded.
- Price by vehicle type, duration, add-ons (GPS, insurance), late fees and one-way drop.

**Non-functional**
- No overlapping reservations for the same vehicle.
- New vehicle categories and pricing rules plug in without changes to existing code.

## 1. Scope and chosen solution

I reserve a specific vehicle at a branch for a half-open time interval, then create a rental agreement at handover. Category-only overbooking is excluded from this version. Vehicle identity is stable; a reservation owns planned time, while an agreement owns actual pickup/return evidence and charges.

## 2. Contracts and allocation

```text
reserve(requestId,vehicleId,start,end,customerId,quoteId) -> Reservation
pickup(reservationId,inspection,odometer) -> RentalAgreement
returnVehicle(agreementId,inspection,odometer,now) -> FinalInvoice
Unavailable interval = [pickup, plannedReturn + preparationBuffer)
```

Under a vehicle allocation lock/transaction, I recheck interval overlap, validate the quote, and insert the reservation once. Overlap is `a.start < b.end && b.start < a.end`; checking only start dates is incorrect. PostgreSQL can enforce non-overlap for blocking states with an exclusion constraint using `tstzrange` and a GiST equality operator class for vehicle ID. All state changes that affect availability use that same authority.

Pickup changes CONFIRMED to ACTIVE and snapshots condition/fuel. Return records actual usage before marking PREPARING, then READY after inspection. At ₹1,800 per started 24 hours, 49 hours costs ₹5,400 before other stated charges. A late return creates a readiness conflict with the next reservation; the service allocates a replacement or flags an exception instead of treating the original promise as fulfilled.

`modifyReservation` locks the affected vehicle allocations, excludes the reservation's own interval from the overlap check, validates a replacement quote and commits the new interval only if it fits. A failed modification preserves the original allocation. Cancellation before pickup marks the reservation CANCELLED and releases its interval under the same authority. After pickup the operation is an early return against the active agreement, not deletion of the reservation; actual usage, fees and return condition remain recorded.

A *half-open interval* `[start,end)` includes its start and excludes its end. Two reservations overlap when `a.start < b.end && b.start < a.end`. Equality at the boundary does not overlap, but cleaning may extend the unavailable interval.

### Worked calculation and implementation

Use `Vehicle`, `Reservation`, `RentalAgreement`, `Inspection` and `RateQuote`. Do not put historical price in a mutable `Vehicle.dailyRate` field. The agreement preserves what this customer accepted.

```java
// Half-open interval rule; validate start < end at construction.
boolean overlaps(Instant aStart, Instant aEnd,
                 Instant bStart, Instant bEnd) {
    return aStart.isBefore(bEnd) && bStart.isBefore(aEnd);
}
```

At ₹1,800 per started 24-hour period, a 49-hour rental is three periods and ₹5,400 before taxes and extras. A calendar-day tariff gives different results around midnight; name the policy rather than accidentally deriving it from integer division. Store pickup timezone when local branch opening hours matter.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Vehicle` (abstract) → `Car`, `SUV`, `Bike`, `EV` | Registration number, type, branch, status |
| `VehicleFactory` | Creates vehicles from a type and attributes |
| `Branch` | Location and the vehicles currently there |
| `Inventory` | `isAvailable(vehicle, range)` and `findAvailable(branch, type, range)` |
| `Reservation` | customer, vehicle, range, add-ons. State: `CONFIRMED → FULFILLED / CANCELLED`; actual usage is on RentalAgreement |
| `PricingStrategy` | `DailyRate`, `HourlyRate`, `SurgePricing`, decorated by `AddOnDecorator` |
| `Invoice`, `Payment` | Final bill including damages and late fees |

### Design decisions & trade-offs

**1. Availability is about time ranges, not a status flag.** A car can be free today and booked next week, so `status=AVAILABLE` is wrong. Store reservations per vehicle in a `TreeMap<LocalDateTime, Reservation>` keyed by start time. To check `[from, to)`, look at `floorEntry(to)` and see whether it ends after `from`. That is O(log n).

**2. Preventing double booking.** Synchronise per vehicle (lock striping with `ConcurrentHashMap<VehicleId, Object>`), then re-check overlap and insert. In a database this becomes an exclusion constraint (Postgres `tstzrange &&`) or a `SELECT … FOR UPDATE` on the vehicle row.

**3. Pricing composition.** Base Strategy (daily, hourly, surge) plus Decorators for add-ons (`InsuranceAddOn(GpsAddOn(DailyRate))`). Each piece is independently testable, and new add-ons don't touch existing classes.

**4. One-way rentals.** On return, the vehicle's branch changes. That affects future availability by location, so search must consider where the vehicle *will be* at `from`, not where it is now. Keep it simple: a vehicle is searchable at the branch of its last reservation's drop-off.

**5. Reservation as a State machine.** You can only pick up a `BOOKED` reservation within the grace window. Late return moves to `RETURNED` with a late-fee line item.

### Ownership, boundaries and invariants

**Central design question:** Availability is an interval constraint for a specific vehicle, not a boolean on a vehicle type.

Vehicle records asset identity and service status; VehicleType groups attributes. Reservation owns a half-open rental interval and quote. RentalAgreement records pickup/return inspection. PricingPolicy, EligibilityPolicy and PaymentPort express changing rules without duplicating lifecycle state.

**Correctness rule:** Confirmed reservations for the same vehicle must not overlap: existing.start < requested.end and requested.start < existing.end. Maintenance intervals also consume availability.

```text
reservation(id,vehicle_id,start_at,end_at,status,quote_version); agreement(id,reservation_id,pickup_reading,return_reading)
```

### End-to-end execution trace

Find suitable vehicles; quote with immutable dates and tariff; atomically reserve an available interval; authorize deposit; confirm; at pickup check licence and vehicle readiness; record odometer/fuel; at return calculate charges from recorded facts and close the agreement.

### Concurrency and recovery walkthrough

Two requests inspect the same free date range. Lock the vehicle schedule or use a database range exclusion constraint; checking then inserting without an authority is unsafe. Process vehicle locks in stable ID order for multi-vehicle reservations.

### Policy choices and extension seams

Assigning a concrete car early simplifies conflicts but reduces flexibility; booking a category requires capacity accounting and later assignment. A policy should calculate fees while the agreement aggregate owns legal transitions.

### Edge cases that change the design

Back-to-back rentals require turnaround time. Time zones and daylight-saving changes affect displayed pickup times; store instants plus location zone. Late returns may conflict with later reservations and require reallocation rather than silently extending a booking.

**Topic-specific cases:** Overlap detection; boundary-touching intervals; maintenance block; deposit timeout; late return; duplicate pickup; pricing across a daylight-saving boundary.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through failure and extensions

If a customer returns the car late, the next confirmed reservation may become unfulfillable. Keep reservation obligations separate from actual vehicle readiness; offer a replacement or flag an exception. Silently extending the earlier reservation's end can hide the conflict.

Two concurrent bookings need interval exclusion at the authoritative allocation boundary. A Java check on each server is insufficient. At small scale, serialize allocation for one vehicle in a transaction; at category-pool scale, enforce capacity over intervals rather than pretending an unassigned category booking owns a specific registration number.

## 6. Interviewer follow-ups

**Does 10:00–12:00 overlap 12:00–14:00?** Not under half-open intervals; add preparation time before deciding physical availability.

**Where does a damage charge belong?** On the rental's return inspection/adjustment record, linked to evidence and a pricing rule, not on all future bookings for that car.

## 7. Closing answer

I keep future reservation promises separate from actual rentals. Vehicle interval allocation includes preparation time, pricing is frozen in the accepted quote, and return inspection determines readiness. That preserves history and makes late-return conflicts visible instead of silently double-booking the next customer.
