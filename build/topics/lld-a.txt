## Problem

Design a parking lot system in Java with multiple floors, several vehicle and spot types, ticketing at entry, and payment at exit. This tests clean entity modelling, **Factory** and **Strategy**, and whether the design stays open for change (EV charging, new vehicle types, new pricing).

## Requirements

**Functional**
- Multiple floors, each with spots of type `COMPACT`, `LARGE`, `MOTORBIKE`, `EV`.
- Vehicles: car, bike, truck. Each fits certain spot types.
- At entry, assign a spot and issue a ticket. At exit, compute the fee, take payment and free the spot.
- Show available spots per floor and type on a display board.

**Non-functional**
- Several gates operate at the same time, so spot assignment must be thread-safe.
- Adding a vehicle type, spot type or pricing rule shouldn't mean rewriting existing classes.

## 1. Scope and chosen solution

I support a multi-floor lot with several gates, vehicle-to-spot compatibility, ticket issuance, time-based fees and payment-assisted exit. I start in one process. `ParkingLot` coordinates allocation, while `PricingPolicy`, `PaymentPort` and `GatePort` isolate changeable pricing and physical/external actions. The invariant is one active session per occupied spot, and one settled financial intent per exit.

## 2. Contracts, records and ownership

```text
enter(entryRequestId, vehicle, now) -> Ticket(sessionId, spotId, enteredAt)
quoteExit(sessionId, now) -> Quote(quoteId, amountPaise, tariffVersion, expiresAt)
payExit(sessionId, quoteId, paymentRequestId) -> PaymentPending | ExitGranted
confirmExit(sessionId, gateEventId) -> Closed

ParkingSession: id, vehicleId, spotId, enteredAt, status, finalQuote, version
Occupancy: spotId PRIMARY KEY, activeSessionId UNIQUE
PaymentIntent: requestId UNIQUE, sessionId, quoteId, payloadHash, result
```

`enter` locks the allocation boundary, finds a compatible free spot, records occupancy and session together, then returns the ticket. Repeating the same entry identity returns that ticket. A gate failure leaves a visible allocated session for retry/operator recovery; it does not allocate another spot.

For exit, I lock the session, persist the accepted quote and payment intent, release the lock and call the provider. A callback reacquires the session, records the known payment outcome once, and grants gate access after success. A timeout remains pending until queried by the same provider reference. `confirmExit` closes the session and removes occupancy atomically. ₹40 for the first hour plus ₹20 per started additional hour gives ₹60 at 61 minutes; money is stored as 6,000 paise and that result is retained with its tariff version.

### Core implementation

Use a compatibility policy rather than `vehicle.type == spot.type`: a motorcycle might be allowed in a car spot, depending on the lot's rules. Keep that decision separate from the allocation algorithm, which might choose the nearest compatible spot.

```java
// Single-JVM algorithm sketch; the same lock covers search and allocation.
synchronized Ticket park(Vehicle vehicle, Instant enteredAt) {
    Spot spot = spots.stream()
        .filter(s -> s.isFree() && compatibility.accepts(vehicle, s))
        .findFirst().orElseThrow(LotFull::new);
    Ticket ticket = new Ticket(newTicketId(), spot.id(), enteredAt);
    spot.occupy(ticket.id());
    activeTickets.put(ticket.id(), ticket);
    return ticket;
}
```

`ConcurrentHashMap` would protect individual map calls, but would not make the spot search, allocation and ticket insertion atomic. In a durable version, use one transaction and a uniqueness rule for active spot occupancy; update counts only after the claim succeeds.

### Design decisions & trade-offs

**1. Vehicle-to-spot compatibility as data, not `instanceof`.** Keep a `Map<VehicleType, List<SpotType>>`, for example a bike fits MOTORBIKE first, then COMPACT. A new vehicle type then means adding a map entry, not changing branching code.

**2. Allocation is a Strategy.** "Nearest to the gate" vs. "fill the lowest floor first" is a business choice that changes per site. Inject it rather than hard-coding it.

**3. Concurrency at assignment.** Two gates must never assign the same spot. Options:
- `synchronized` on the floor's free list for the type. This is simple and contention is low.
- A `ConcurrentLinkedQueue<ParkingSpot>` per type, where `poll()` is atomic. This is lock-free and the cleanest choice.
- Spot-level CAS (`AtomicReference<Vehicle>`) if you scan instead of using free lists.

**4. Pricing is a Strategy, possibly composed.** A `CompositeFee` can apply a base hourly rate, a vehicle multiplier and a weekend discount in sequence. That adds a Decorator flavour and avoids one god-method.

**5. Ticket as the source of truth.** Exit uses the ticket ID, which avoids searching for the vehicle and lets you handle lost tickets with a lookup by plate.

**6. Display board via Observer.** Spots publish `SpotFreed` and `SpotTaken` events. The board subscribes to them, so the lot doesn't know the display exists.

### Ownership, boundaries and invariants

**Central design question:** Assign a compatible physical spot exactly once, then keep ticketing and charging separate from allocation.

ParkingLot contains Floors and ParkingSpots. Vehicle and SpotType are values. AllocationPolicy chooses among compatible free spots; Ticket records vehicle, spot and entry instant. PricingPolicy computes a quote from a tariff snapshot. PaymentPort is an external boundary.

**Correctness rule:** At most one open ticket owns a spot, and a vehicle cannot acquire a second open ticket through a retried entry request. Free counts are projections of spot state, not an independent source of truth.

```text
spot(id,floor,type,state,version); ticket(id,vehicle_id,spot_id,entry_at,tariff_version,status,entry_request_id)
```

### End-to-end execution trace

Validate vehicle and gate; look up the entry request ID; find compatible candidates; claim one atomically; create the ticket in the same transaction; return its immutable ID. At exit compute the quote, request payment outside the spot lock, persist the payment result, then release the spot exactly once.

### Concurrency and recovery walkthrough

Two entry gates both see the last free spot. A conditional FREE-to-OCCUPIED update determines the winner. A process lock is sufficient only for one JVM; multiple gates backed by different JVMs need the database constraint or equivalent authority.

### Policy choices and extension seams

Nearest-spot allocation is simple but can starve some floors; balanced allocation spreads congestion. Strategy is useful for allocation and tariffs, while a factory that merely creates every entity adds little. Snapshot the tariff so a price change does not rewrite an active ticket.

### Edge cases that change the design

A payment timeout is not a decline: keep a pending exit and reconcile the provider result. Support a lost-ticket policy explicitly. Release on confirmed exit, not merely on payment initiation. Reconstruct display-board counts after a restart.

**Topic-specific cases:** Compatibility rejects an oversized vehicle; simultaneous claims have one winner; duplicate entry returns one ticket; payment failure retains occupancy; repeated exit does not free twice.

### Work through exit and pricing

Suppose the policy is ₹40 for the first hour, then ₹20 for each started additional hour. Entry at 09:10 and exit at 10:11 is 61 minutes: charge ₹60. At exactly 10:10 the charge is ₹40. Document the boundary before writing `ceil`, and store amounts in paise so ₹60 is `6000`, not a floating-point approximation.

Keep `quoteExit(ticketId, now)` separate from `completeExit(paymentReference)`. A quoted fee is not proof of payment. Record the applied pricing-policy version with the final amount so tomorrow's tariff update cannot change yesterday's receipt. An entrance gate that fails to open after allocation needs an explicit operator/retry path; blindly allocating another spot leaks the original allocation.

When payment is external, use `PAYMENT_PENDING`, `PAID` and `CLOSED` states. A timeout means the payment outcome may be unknown. Query the original payment reference before charging again. Release the physical spot only at the product's defined exit point, not whenever a payment HTTP call returns.

## 6. Interviewer follow-ups

**Can the floor display reserve a spot?** No. It is a read model and can be stale. The allocation operation establishes ownership.

**Two exit requests use the same ticket. Should they charge twice?** No. Persist the settled result and return it on repeats; reject a different payment intent after settlement.

## 7. Closing answer

My design makes the parking session the visit record and the spot allocation the exclusive ownership decision. I freeze the final tariff result, reconcile uncertain payments by their original reference, and release a spot according to an explicit exit event. Displays can lag without allocating the same spot twice.

## Problem

Design an elevator system for a building with N floors and M elevators. Users press hall buttons (up or down) and car buttons (a destination floor). The system decides which elevator serves which request. This tests the **State** pattern, scheduling as **Strategy**, and **concurrency** between button events and moving cars.

## Requirements

**Functional**
- Hall calls (`floor`, `direction`) and car calls (`destination`).
- Assign hall calls to the best elevator. Each car serves its stops in an efficient order.
- Doors open and close, with an overload check and an emergency stop.
- Display the current floor and direction.

**Non-functional**
- Requests arrive concurrently from many buttons.
- Swappable scheduling (rush-hour mode, energy-saving mode).

## 1. Scope and chosen solution

I design dispatch and car-control software for a ten-floor building with two cars. Hall requests carry floor and direction; car requests carry destination and car identity. I choose one dispatcher and a single-owner event loop per car. This provides ordered state changes without a lock around slow physical motion. Certified hardware interlocks enforce actual motor safety; this model specifies the software's responsibilities.

## 2. Events and selected scheduling algorithm

```text
HallCall(floor,direction) -> outstanding call ID, coalesced by floor/direction
Assign(callId,carId,assignmentVersion) -> accepted or car unavailable
CarButton(carId,destination) -> queued stop
SensorEvent(carId,sequence,floor,doorSafe,load) -> state update

Dispatcher score = estimated pickup travel + intermediate dwell + aging penalty
Car plan = ordered upward and downward stop sets (LOOK-style)
```

On a hall call, I exclude out-of-service/full cars, estimate pickup using their existing direction/stops, and assign the lowest-cost eligible car. Aging lowers the effective cost of long-waiting calls so nearby traffic does not starve them. Within a car, I serve reachable stops in the current direction, reverse only when no relevant stop remains, and handle a stop at the current floor before selecting `higher`/`lower`.

The car transitions `IDLE -> MOVING -> STOPPED -> DOOR_OPEN -> DOOR_CLOSING`; only confirmed closed-and-safe doors permit `MOVING`. Obstruction returns to `DOOR_OPEN`. When a car fails, I cancel its assignment version and requeue unserved hall calls; late arrival events cannot clear the replacement car's assignment. A 0-to-2 pickup takes about six travel seconds at an assumed three seconds/floor, whereas a downward car at 3 serving 1 first also incurs reversal and a door dwell. Direction-aware ETA therefore beats distance alone.

### Core implementation

Keep `CarState(currentFloor, direction, doorState, serviceMode)` and ordered stop sets. A LOOK-like policy serves requested stops in the current direction and reverses after the last relevant stop; it need not travel to the building's extreme floor like a literal SCAN sweep.

```java
// Scheduling-policy sketch, not hardware control code.
OptionalInt nextStop(CarSnapshot car, NavigableSet<Integer> stops) {
    Integer ahead = car.direction() == UP
        ? stops.higher(car.floor()) : stops.lower(car.floor());
    if (ahead != null) return OptionalInt.of(ahead);
    Integer behind = car.direction() == UP
        ? stops.lower(car.floor()) : stops.higher(car.floor());
    return behind == null ? OptionalInt.empty() : OptionalInt.of(behind);
}
```

A stop at the current floor must be handled before calling this function. Otherwise `higher`/`lower` skips it. Keep hall-call direction with the assignment so clearing an Up call does not incorrectly clear a Down call at the same floor.

### Design decisions & trade-offs

**1. LOOK/SCAN inside each car.** A car keeps moving in its current direction, serving every stop on the way (`TreeSet.ceiling(currentFloor)`), and reverses only when nothing is left ahead. This avoids FCFS zig-zagging and starvation.

**2. Choosing a car for a hall call.** Pick by cost: an idle car pays its distance; a car moving toward the floor in the same direction pays its distance; anything else pays a penalty. `NearestCar` is the baseline, and the Strategy interface lets you add zoning (cars 1–2 serve floors 1–20) without touching the controller.

**3. State pattern for behaviour.** "Ignore movement while the doors are open" and "reject requests in Maintenance" live in state classes, not in `if` blocks inside `Elevator.step()`.

**4. Concurrency model.** Button presses happen on many threads. Put them on a `BlockingQueue<Request>`. One controller thread assigns them. Each elevator runs its own loop thread with a thread-safe stop set (or confined state plus messages). Avoid one global lock around all elevators.

**5. Simulation vs. real time.** Model a `tick()` per car so it's testable. Real hardware triggers events instead.

### Work through a dispatch decision

Car A is on floor 0 moving up with stops at 3 and 6. Car B is on floor 3 moving down to 1. A new Up call arrives at 2. Nearest-distance-only chooses B: it is one floor away while A is two floors away. But B must finish its downward service and reverse before serving an upward pickup; A can insert floor 2 on its current path. A sensible cost includes travel direction, planned stops, load and time already waited. State the example costs explicitly rather than calling a strategy “optimal.”

## Requirements

**Functional**
- Search movies by city. List shows per cinema and screen. Show a seat map.
- Select seats, hold them for a few minutes, pay, and confirm the booking.
- Cancel bookings (with a refund policy) and release unpaid holds after a TTL.

**Non-functional**
- No double booking, ever.
- Seat holds must expire without a manual cleanup step.

## 1. Scope and chosen solution

I design reserved-seat booking for a specific show, including an all-or-nothing multi-seat hold, payment, confirmation and expiry. Static `Seat` describes the physical layout; `ShowSeat(showId,seatId)` owns availability for one screening. I choose a relational transaction for allocation and a separate idempotent payment workflow.

## 2. Schema and complete reservation transaction

```text
ShowSeat PK(showId,seatId): status, holdId, expiresAt, bookingId
Hold PK(holdId): customerId, showId, expiresAt, quotedAmount, currency, state
Booking PK(bookingId): holdId UNIQUE, customerId, acceptedPrice, state
PaymentIntent PK(intentId): holdId, providerRef UNIQUE, state, payloadHash

holdSeats(requestId,showId,seatIds,customer) -> Hold | Conflict
confirmPayment(providerRef) -> Booking | RefundRequired | Pending
```

`holdSeats` begins a transaction, locks all requested show-seat rows in sorted seat order, verifies every row is free or expired, writes one hold identity to every seat, and commits. If any seat is unavailable, the transaction rolls back all claims. A request identity with a different payload is rejected; a true retry returns its original hold.

Confirmation locks the hold and the same seat rows, verifies `now < expiresAt`, ownership of every seat, and successful payment evidence. It inserts one booking, changes all seats to SOLD and commits. Expiry competes for these same rows and releases only matching expired hold tokens. If payment completed after ownership was lost, the financial result becomes paid-but-unfulfilled and initiates one refund intent; it never overrides a newer hold. A7 and A8 at ₹250 each produce a frozen ₹500 quote, so price changes during payment cannot alter accepted terms.

For browsing, `GET /movies?city=...` and `GET /shows/{id}/seats` return catalogue/read-model data; neither claims seats. `cancelBooking(bookingId,requestId)` authorizes the owner and cutoff policy, locks the booking and its seats, marks the booking cancelled, releases only seats owned by it, and writes one refund intent in the same transaction. The refund may remain pending while the seat is available again: the customer is still owed that recorded refund. A repeated cancellation returns the original disposition. A cancelled hold with a later successful charge follows the same paid-but-unfulfilled compensation path.

### Design decisions & trade-offs

**1. Lock then pay, not pay then lock.** Hold seats when the user selects them, with a TTL of about 5 minutes. Confirm with payment. If payment happens first, two users can both pay for the same seat.

**2. Implementing the lock (in-process LLD).**
```java
class InMemorySeatLockProvider implements SeatLockProvider {
    private final ConcurrentHashMap<SeatKey, SeatLock> locks = new ConcurrentHashMap<>();
    public synchronized boolean lock(Show s, List<Seat> seats, String user, Duration ttl) {
        if (seats.stream().anyMatch(x -> isLocked(s, x))) return false;  // all-or-nothing
        seats.forEach(x -> locks.put(new SeatKey(s, x), new SeatLock(user, now().plus(ttl))));
        return true;
    }
}
```
All-or-nothing matters: a user selecting 4 seats shouldn't get 3. Sort seat keys before locking if you use per-seat locks, so two threads can't deadlock.

**3. Expiry.** Do a lazy check (`expiresAt < now` means it's free) plus a scheduled sweeper that moves `PENDING` bookings to `EXPIRED`. In a distributed setup this becomes Redis `SET NX PX` per seat, or a DB row with `status, locked_until` and a conditional `UPDATE … WHERE status='AVAILABLE'`.

**4. Booking as a State machine.** Only `PENDING` can become `CONFIRMED`, and only if the lock is still held by this user. Re-validate the lock at confirmation time, because the TTL may have passed during a slow payment.

**5. Idempotent payment callbacks.** Gateways retry. Key the confirmation on `paymentId` so a duplicate callback can't double-confirm.

### Ownership, boundaries and invariants

**Central design question:** A seat hold is temporary ownership with an expiry; payment does not magically make it a booking.

Movie, Theatre, Screen, Seat and Show describe inventory. ShowSeat is the sellable resource because the same chair belongs to different shows. Hold contains user, seats and expiry; Booking contains a price snapshot and payment reference. SeatSelectionPolicy and PaymentPort stay outside seat state.

**Correctness rule:** For a particular show-seat, at most one unexpired hold or confirmed booking owns it. All seats of a multi-seat request are claimed together or none are.

```text
show_seat(show_id,seat_id,state,hold_id,expires_at,version); booking(id,hold_id,payment_id,status,amount_minor)
```

### End-to-end execution trace

Validate show and seat IDs; lock seats in a deterministic order; reclaim expired holds according to database time; atomically create one hold; collect payment without holding row locks; on callback verify hold owner, expiry and payment identity; atomically confirm the entire booking.

### Concurrency and recovery walkthrough

Two users choose the same pair of seats while the expiry worker runs. Conditional ownership transitions use hold IDs and versions, so a late worker cannot clear a newer hold. A late payment callback cannot confirm seats now owned by another booking.

### Policy choices and extension seams

Pessimistic row locking is easy for small seat sets; optimistic version checks suit low contention but require whole-request retries. A Redis countdown is a UI convenience, not the sales authority. Reject or refund a late success according to a documented policy.

### Edge cases that change the design

A callback may arrive twice or before the client receives its payment result. Persist provider event identity and use a booking idempotency key. Seat maps can be stale; the confirmation response, not the map colour, establishes ownership.

**Topic-specific cases:** All-or-none multi-seat allocation; expired hold cannot confirm; repeated callback has one effect; a newer hold survives an old expiry job; prices remain stable.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through payment and expiry

Let H21 expire at 10:05:00. Define valid ownership as `now < expiresAt`; at exactly 10:05:00, it is expired. Both payment confirmation and the cleanup worker must use this rule. Cleanup timing does not establish validity: a row still labelled HELD at 10:05:02 is not an entitlement to confirm.

If the payment provider reports success after the hold was lost, do not sell somebody else's seat. Record the paid-but-unfulfilled outcome, then refund or ask the customer to select new seats according to product policy. The payment reference is unique so a duplicated webhook cannot create a second booking or refund.

For ₹250 per seat, A7 and A8 cost ₹500 before documented fees. Save this quoted amount and its currency on the hold. Repricing seats between hold and confirmation makes the customer approve one amount and pay another. Seat availability from a cached theatre map is a hint; only the reservation transaction can promise ownership.

## 6. Interviewer follow-ups

**Can two customers hold different seats in the same show?** Yes. Lock the relevant show-seat rows rather than the entire cinema unless simplicity at tiny scale justifies the coarser lock.

**Can a hold reserve A7 but fail on A8?** Not when the product promises adjacent seats as one selection. Roll back the transaction if any seat is unavailable.

## 7. Closing answer

I use show-seat rows as the allocation authority, expiring token-owned holds for the payment interval, and an atomic all-seat confirmation. Payment is a separate durable workflow. A late payment or stale expiry callback cannot steal or release a newer customer's hold.

## Problem

Design an ATM: card insertion, PIN entry, balance check, withdrawal, deposit and cash dispensing. This is the textbook problem for the **State** pattern (what the ATM accepts depends on where you are in the flow) and **Chain of Responsibility** (splitting an amount across note denominations).

## Requirements

**Functional**
- Insert card, then enter PIN (3 attempts, then the card is retained), then choose a transaction.
- Withdraw (within limits, in multiples of the smallest note), deposit, check balance, change PIN.
- Dispense the correct mix of notes, print a receipt, eject the card.

**Non-functional**
- Money must never be dispensed without a successful debit, and a debit must never happen without dispensing. You need a compensating action.
- The hardware (dispenser, card reader) is unreliable.

## 1. Scope and chosen solution

I support authenticated balance lookup and cash withdrawal at one ATM. Bank balances remain authoritative at the bank; cassette inventory belongs to the machine. The ATM never stores a clear PIN. Session control, note planning, bank access and physical dispensing are separate responsibilities so each failure can be represented.

## 2. Withdrawal contract and execution

```text
withdraw(operationId, accountToken, amountMinor) -> WithdrawalState
Withdrawal: id, amount, reservedNotePlan, bankRef, deviceRef, state, deliveredNotes
States: CREATED -> AUTHORIZED -> DISPENSING -> COMPLETED
                                -> PARTIAL | UNKNOWN -> RECONCILED
Device result: COMPLETE | PARTIAL | NONE | UNKNOWN
```

I validate amount/currency, compute a bounded feasible note plan, reserve those notes, and persist the withdrawal before external actions. I authorize funds with the bank using the operation identity. A definite decline releases unused inventory. After authorization, I persist DISPENSING before issuing the device command and record the device's evidence. A known full delivery settles under the bank protocol; no delivery releases/voids according to known authorization state; partial and unknown delivery enter reconciliation.

For ₹2,500, five ₹500 notes are feasible only if five notes are available. Three delivered notes mean ₹1,500 physically left the machine even if the requested amount was larger. Inventory is decremented by known delivery; unknown counts remain reserved until device-journal reconciliation. On restart I inspect unresolved withdrawals and the dispenser journal before serving a new dispense. A lost HTTP reply is retried by operation identity and cannot trigger a fresh cash command. Note selection uses bounded change-making when denominations are arbitrary; a greedy method would fail for amount 6 with notes 4 and 3 despite 3+3 being feasible.

## 3. Final design diagram

Keep two separate truths: the **bank ledger** records money movement; the **cash cassette inventory** records physical notes. A Java object cannot make a network request and a physical motor action one atomic transaction. That gap is the central design lesson, not a reason to pretend all failures can be rolled back.

### Core implementation

Represent the session as states such as `IDLE`, `AUTHENTICATED`, `WITHDRAWING`, `RECONCILING` and `EJECTING_CARD`. Keep PIN validation in an adapter; never store the PIN on `Account` or print it in a trace. The ATM receives a limited authorization result, not a copy of the bank's security secrets.

For a ₹2,500 withdrawal with ₹500 and ₹100 notes, five ₹500 notes work when available. Greedy selection is not universally sufficient for arbitrary denominations and inventory constraints: with denominations 4 and 3 and amount 6, greedy takes 4 and gets stuck although 3+3 works. Use bounded change-making or a documented denomination policy.

```java
// Device boundary sketch: UNKNOWN is a first-class result.
enum DispenseStatus { COMPLETE, PARTIAL, NONE, UNKNOWN }
record DispenseReport(String operationId, DispenseStatus status,
                      Map<Integer, Integer> deliveredNotes) {}
```

The inventory update uses delivered counts, not requested counts. A partial report and an unknown report require different reconciliation procedures.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `ATM` | Context: holds the current `ATMState` and hardware components |
| `ATMState` | `Idle`, `CardInserted`, `Authenticated`, `TransactionSelected`, `OutOfService` |
| `CardReader`, `Keypad`, `Screen`, `Printer` | Hardware interfaces |
| `CashDispenser` | Chain: `Note2000Handler → Note500Handler → Note100Handler` |
| `BankService` | `authenticate`, `getBalance`, `debit`, `credit`, `reverse` |
| `Transaction` | `Withdrawal`, `Deposit`, `BalanceInquiry` (Command) |

```java
abstract class ATMState {
    void insertCard(ATM atm, Card c) { throw new IllegalStateException(); }
    void enterPin(ATM atm, String pin) { throw new IllegalStateException(); }
    void selectTx(ATM atm, TxType t) { throw new IllegalStateException(); }
    void ejectCard(ATM atm) { throw new IllegalStateException(); }
}
```

### Design decisions & trade-offs

**1. State pattern.** Each state overrides only the events it accepts. `Idle.insertCard` moves to `CardInserted`. `CardInserted.enterPin` either moves to `Authenticated` or counts a failure. Illegal actions fail loudly in one place.

**2. Chain of Responsibility for dispensing.**
```java
abstract class NoteHandler {
    NoteHandler next; int denom; int available;
    void dispense(int amount, Map<Integer,Integer> out) {
        int n = Math.min(amount / denom, available);
        if (n > 0) out.put(denom, n);
        int rest = amount - n * denom;
        if (rest > 0) { if (next == null) throw new CannotDispense(); next.dispense(rest, out); }
    }
}
```
Do a dry run first, and only debit if the plan succeeds. Adding a ₹200 note is one new handler.

**3. Debit and dispense consistency.** Order: plan the notes, then debit at the bank, then dispense. If the dispenser fails after the debit, call `bank.reverse(txId)` (a compensating transaction), and log for reconciliation. Use idempotent transaction IDs so retries don't double-debit.

**4. Security.** PIN verification happens at the bank, never locally. The ATM only sends an encrypted PIN block. Lock out after 3 failures.

### Ownership, boundaries and invariants

**Central design question:** Cash movement and account debiting form a recoverable protocol across hardware and banking systems.

AtmSession owns the authenticated interaction. AccountGateway authorizes debits; CashInventory records denomination counts; CashDispenser reports note movement through sensors. WithdrawalJournal persists operation IDs and uncertain outcomes. CardReader and PinVerifier are ports, not domain inheritance trees.

**Correctness rule:** Never report a successful withdrawal before both the debit outcome and dispensed cash are known. Note counts cannot become negative. A retried withdrawal identifier cannot debit twice.

```text
withdrawal(id,account_ref,requested_minor,dispensed_minor,authorization_ref,status); cassette(denomination,count,reserved)
```

### End-to-end execution trace

Authenticate with bounded PIN retries; select account and amount; reserve a feasible denomination combination; journal the intent; request bank authorization; dispense; persist the sensor result; settle or reverse the authorization using the same operation identity; print a receipt reflecting the known outcome.

### Concurrency and recovery walkthrough

Two withdrawal sessions compete for the last set of notes. Reserve note inventory atomically, release only the unconsumed reservation, and reconcile actual counts after partial dispense. Keep bank network calls outside the inventory lock.

### Policy choices and extension seams

Greedy denomination selection may fail when a valid combination exists; bounded search or dynamic programming can be used with cassette limits. State makes session progress explicit; Chain of Responsibility may select notes but must not hide insufficiency or partial movement.

### Edge cases that change the design

Power loss after cash leaves the dispenser but before a receipt needs durable recovery. A bank timeout means unknown, not safe-to-repeat. Never log PINs or card secrets. Partial dispense requires a specific compensation workflow, not a blind full refund.

**Topic-specific cases:** Insufficient denominations despite sufficient total cash; repeated withdrawal ID; bank timeout; jammed cassette; partial dispense; restart from each journal state.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through a partial delivery

W17 requests five ₹500 notes. Device evidence says three notes were delivered and two remained in a jammed cassette. The customer received ₹1,500. Record the exact reported counts and reconcile the ₹2,500 authorization according to the bank/device protocol; do not silently mark the entire withdrawal successful. Real settlement rules depend on the acquiring bank and hardware, so this is an educational boundary model rather than a certified ATM protocol.

Reserve a note plan before dispensing so another session cannot consume the same physical inventory. One machine may serialize withdrawals through a single session controller. The bank still needs its own atomic funds authorization because the same account can be used at other ATMs or for online payments.

On restart, inspect the durable withdrawal journal and device journal before accepting another withdrawal. If an operator refills or removes a cassette, record a cash-reconciliation event instead of overwriting counts without a trail. Availability is less important than avoiding an untracked second cash delivery.

## 6. Interviewer follow-ups

**Does `synchronized withdraw()` protect the bank account globally?** No. It only serializes callers using that JVM's object. The bank's ledger/authorization service owns global funds correctness.

**Should a dispenser timeout be retried with a new ID?** No. That can dispense twice. Query or reconcile the existing operation.

## 7. Closing answer

I model a withdrawal as a journalled operation across bank authorization and a physical dispenser. Exact note inventory and explicit COMPLETE/PARTIAL/NONE/UNKNOWN outcomes prevent the design from pretending that a software rollback can undo delivered cash. Recovery resolves the original operation before another dispense.

## Problem

Design a car rental system like Zoomcar or Hertz: customers search vehicles by location and date range, reserve them, pick up, return (possibly at another branch) and pay. The key challenges are **inventory availability over time ranges**, pricing as a **Strategy**, and vehicle creation with a **Factory**.

## Requirements

**Functional**
- Search available vehicles by branch, type and `[from, to]` range.
- Reserve, modify and cancel. Pick up and return, with mileage and fuel or charge recorded.
- Price by vehicle type, duration, add-ons (GPS, insurance), late fees and one-way drop.

**Non-functional**
- No overlapping reservations for the same vehicle.
- New vehicle categories and pricing rules plug in without changes to existing code.

## 1. Scope and chosen solution

I reserve a specific vehicle at a branch for a half-open time interval, then create a rental agreement at handover. Category-only overbooking is excluded from this version. Vehicle identity is stable; a reservation owns planned time, while an agreement owns actual pickup/return evidence and charges.

## 2. Contracts and allocation

```text
reserve(requestId,vehicleId,start,end,customerId,quoteId) -> Reservation
pickup(reservationId,inspection,odometer) -> RentalAgreement
returnVehicle(agreementId,inspection,odometer,now) -> FinalInvoice
Unavailable interval = [pickup, plannedReturn + preparationBuffer)
```

Under a vehicle allocation lock/transaction, I recheck interval overlap, validate the quote, and insert the reservation once. Overlap is `a.start < b.end && b.start < a.end`; checking only start dates is incorrect. PostgreSQL can enforce non-overlap for blocking states with an exclusion constraint using `tstzrange` and a GiST equality operator class for vehicle ID. All state changes that affect availability use that same authority.

Pickup changes CONFIRMED to ACTIVE and snapshots condition/fuel. Return records actual usage before marking PREPARING, then READY after inspection. At ₹1,800 per started 24 hours, 49 hours costs ₹5,400 before other stated charges. A late return creates a readiness conflict with the next reservation; the service allocates a replacement or flags an exception instead of treating the original promise as fulfilled.

`modifyReservation` locks the affected vehicle allocations, excludes the reservation's own interval from the overlap check, validates a replacement quote and commits the new interval only if it fits. A failed modification preserves the original allocation. Cancellation before pickup marks the reservation CANCELLED and releases its interval under the same authority. After pickup the operation is an early return against the active agreement, not deletion of the reservation; actual usage, fees and return condition remain recorded.

A *half-open interval* `[start,end)` includes its start and excludes its end. Two reservations overlap when `a.start < b.end && b.start < a.end`. Equality at the boundary does not overlap, but cleaning may extend the unavailable interval.

Use `Vehicle`, `Reservation`, `RentalAgreement`, `Inspection` and `RateQuote`. Do not put historical price in a mutable `Vehicle.dailyRate` field. The agreement preserves what this customer accepted.

```java
// Half-open interval rule; validate start < end at construction.
boolean overlaps(Instant aStart, Instant aEnd,
                 Instant bStart, Instant bEnd) {
    return aStart.isBefore(bEnd) && bStart.isBefore(aEnd);

```

At ₹1,800 per started 24-hour period, a 49-hour rental is three periods and ₹5,400 before taxes and extras. A calendar-day tariff gives different results around midnight; name the policy rather than accidentally deriving it from integer division. ## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Vehicle` (abstract) → `Car`, `SUV`, `Bike`, `EV` | Registration number, type, branch, status |
| `VehicleFactory` | Creates vehicles from a type and attributes |
| `Branch` | Location and the vehicles currently there |
| `Inventory` | `isAvailable(vehicle, range)` and `findAvailable(branch, type, range)` |
| `Reservation` | customer, vehicle, range, add-ons. State: `CONFIRMED → FULFILLED / CANCELLED`; actual usage is on RentalAgreement |
| `PricingStrategy` | `DailyRate`, `HourlyRate`, `SurgePricing`, decorated by `AddOnDecorator` |
| `Invoice`, `Payment` | Final bill including damages and late fees |

### Design decisions & trade-offs

**1. Availability is about time ranges, not a status flag.** A car can be free today and booked next week, so `status=AVAILABLE` is wrong. Store reservations per vehicle in a `TreeMap<LocalDateTime, Reservation>` keyed by start time. To check `[from, to)`, look at `floorEntry(to)` and see whether it ends after `from`. That is O(log n).

**2. Preventing double booking.** Synchronise per vehicle (lock striping with `ConcurrentHashMap<VehicleId, Object>`), then re-check overlap and insert. In a database this becomes an exclusion constraint (Postgres `tstzrange &&`) or a `SELECT … FOR UPDATE` on the vehicle row.

**3. Pricing composition.** Base Strategy (daily, hourly, surge) plus Decorators for add-ons (`InsuranceAddOn(GpsAddOn(DailyRate))`). Each piece is independently testable, and new add-ons don't touch existing classes.

**4. One-way rentals.** On return, the vehicle's branch changes. That affects future availability by location, so search must consider where the vehicle *will be* at `from`, not where it is now. Keep it simple: a vehicle is searchable at the branch of its last reservation's drop-off.

**5. Reservation as a State machine.** You can only pick up a `BOOKED` reservation within the grace window. Late return moves to `RETURNED` with a late-fee line item.

### Ownership, boundaries and invariants

**Central design question:** Availability is an interval constraint for a specific vehicle, not a boolean on a vehicle type.

Vehicle records asset identity and service status; VehicleType groups attributes. Reservation owns a half-open rental interval and quote. RentalAgreement records pickup/return inspection. PricingPolicy, EligibilityPolicy and PaymentPort express changing rules without duplicating lifecycle state.

**Correctness rule:** Confirmed reservations for the same vehicle must not overlap: existing.start < requested.end and requested.start < existing.end. Maintenance intervals also consume availability.

```text
reservation(id,vehicle_id,start_at,end_at,status,quote_version); agreement(id,reservation_id,pickup_reading,return_reading)
```

### End-to-end execution trace

Find suitable vehicles; quote with immutable dates and tariff; atomically reserve an available interval; authorize deposit; confirm; at pickup check licence and vehicle readiness; record odometer/fuel; at return calculate charges from recorded facts and close the agreement.

### Concurrency and recovery walkthrough

Two requests inspect the same free date range. Lock the vehicle schedule or use a database range exclusion constraint; checking then inserting without an authority is unsafe. Process vehicle locks in stable ID order for multi-vehicle reservations.

### Policy choices and extension seams

Assigning a concrete car early simplifies conflicts but reduces flexibility; booking a category requires capacity accounting and later assignment. A policy should calculate fees while the agreement aggregate owns legal transitions.

### Edge cases that change the design

Back-to-back rentals require turnaround time. Time zones and daylight-saving changes affect displayed pickup times; store instants plus location zone. Late returns may conflict with later reservations and require reallocation rather than silently extending a booking.

**Topic-specific cases:** Overlap detection; boundary-touching intervals; maintenance block; deposit timeout; late return; duplicate pickup; pricing across a daylight-saving boundary.

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through failure and extensions

If a customer returns the car late, the next confirmed reservation may become unfulfillable. Keep reservation obligations separate from actual vehicle readiness; offer a replacement or flag an exception. Silently extending the earlier reservation's end can hide the conflict.

Two concurrent bookings need interval exclusion at the authoritative allocation boundary. A Java check on each server is insufficient. At small scale, serialize allocation for one vehicle in a transaction; at category-pool scale, enforce capacity over intervals rather than pretending an unassigned category booking owns a specific registration number.

## 6. Interviewer follow-ups

**Does 10:00–12:00 overlap 12:00–14:00?** Not under half-open intervals; add preparation time before deciding physical availability.

**Where does a damage charge belong?** On the rental's return inspection/adjustment record, linked to evidence and a pricing rule, not on all future bookings for that car.

## 7. Closing answer

I keep future reservation promises separate from actual rentals. Vehicle interval allocation includes preparation time, pricing is frozen in the accepted quote, and return inspection determines readiness. That preserves history and makes late-return conflicts visible instead of silently double-booking the next customer.
