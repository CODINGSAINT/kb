## Problem

Design a paid, multi-floor parking lot with several entry and exit gates. Allocate suitable spots, issue tickets, calculate charges, process payment and release a spot when its vehicle actually leaves. Explain what happens when gates race or payment outcomes are uncertain.

## Requirements

- Motorcycles, cars and trucks; motorcycle, compact and large spots across multiple floors.
- Multiple gates use the same allocation authority; one active visit owns each occupied spot.
- Entry returns a ticket identifying the visit and spot. Displays show availability without granting reservations.
- A versioned tariff calculates fees in INR minor units. The customer approves the amount before collection.
- Successful payment grants a ten-minute exit window; expired windows require only any unpaid difference.
- Unknown payment outcomes are reconciled; retries must not collect twice.
- The implementation is single-process and in-memory. Hardware adapters and durable multi-server storage are explicit extensions.

## 1. The answer I would present

I would separate **physical allocation**, **the parking visit**, and **financial collection**. A `Spot` is one physical location. A `Session` records one vehicle's stay and owns that spot until exit. An `Attempt` records one collection intent and its outcome. Combining all three into `spot.occupied` and `ticket.paid` loses the information needed for retries, partial progress and old exit events.

My aggregate boundary is a `Lot` instance. Its short synchronized operations protect spot/session ownership and payment-state transitions. The provider call happens outside that monitor, because a slow card transaction must not stop another entrance from issuing a ticket. This is a deliberate simple implementation for a modest number of gates, not a claim that one Java monitor coordinates different servers.

I select the smallest compatible spot first, then the lowest floor, walking order and stable ID. A motorcycle can use any of the three types; a car uses compact or large; a truck uses large. This preserves large capacity before optimizing walking distance. If the business prefers the nearest floor regardless of spot size, it replaces the allocation policy without changing ownership or ticket issuance.

The base design uses immutable vehicle/spot values rather than empty subclasses such as `CompactSpot` and `LargeSpot`. Different data does not by itself require inheritance. Policies have interfaces where behaviour really changes: allocation, tariff and external payment. Admin identity, accessible-permit eligibility, EV charging, pre-booked reservations and season passes can be added, but they do not need to complicate the first paid-visit flow.

## 2. The domain model, contracts and pricing decision

| Type | Responsibility | Correctness detail |
|---|---|---|
| `Spot` | ID, floor, order and size category | Physical identity remains stable between visits |
| `Vehicle` | Canonical registration and kind | One active visit per registration in this lot |
| `Session` | Entry, assigned spot, tariff snapshot, state, cumulative paid amount and exit deadline | The visit owns occupancy |
| `AllocationPolicy` | Select a compatible candidate from currently free spots | Pure and fast; cannot secretly reserve another resource |
| `Tariff` | Calculate total charge for the stay | Versioned, immutable policy retained at entry |
| `Quote` | Total, paid credit, amount due, tariff version and quote time | A display quote is revalidated before payment |
| `PaymentPort` | Collect or look up one provider operation | Definitive decline differs from unknown/not found |
| `Attempt` | Stable payment key, session, accepted quote, amount, status and receipt reference | Retry identity includes the approved amount |
| `Lot` | Serialize ownership and state changes; return immutable views | Provider I/O stays outside its monitor |

The central maps are `spotId -> sessionId`, `sessionId -> Session`, `entryKey -> sessionId`, `registration -> activeSessionId` and `paymentKey -> Attempt`. A floor groups locations and display results; I do not need a separate locking object for every floor in this version. That avoids a second lock order until throughput justifies it.

The public contract is:

```text
enter(entryKey, vehicle) -> SessionView(ticket identity, spot, entry time)
quote(sessionId) -> Quote(totalMinor, paidMinor, dueMinor, tariffVersion, quotedAt)
pay(sessionId, paymentKey, approvedDueMinor) -> PaymentView
reconcile(paymentKey) -> PaymentView
confirmExit(sessionId, exitEventId) -> CLOSED SessionView
```

Session and payment are separate state machines. An attempt may be DECLINED while the visit remains PARKED. A visit may have paid credit while a later top-up is unknown. Closing the visit is a physical exit decision, not a synonym for provider acceptance.

Here are the exact contracts from the runnable example:


### A precise tariff instead of ambiguous “hourly pricing”

I choose ₹40 for the first started hour and ₹20 for each additional started hour. An immediate exit still incurs the first-hour minimum. All arithmetic is in paise: ₹40 is 4,000; ₹20 is 2,000. Currency is fixed to INR in this model, so an amount is never accidentally added to a different currency.

| Duration | Started hours | Total |
|---|---:|---:|
| 0 minutes | Minimum one | ₹40 |
| Exactly 60 minutes | 1 | ₹40 |
| 60 minutes plus one nanosecond | 2 | ₹60 |
| 2 hours 35 minutes | 3 | ₹80 |

`Duration.toHours()` truncates; using it alone would undercharge partial hours. Floating-point rupee calculations introduce unnecessary rounding risk. The implementation ceilings at nanosecond precision and checks arithmetic overflow:

```java
// source: Parking.java#tariff
    /** One currency (INR/paise). First hour is charged even for an immediate exit. */
    public record HourlyTariff(String version,long firstHourMinor,long extraHourMinor) implements Tariff {
        public HourlyTariff {
            if(version==null||version.isBlank()||firstHourMinor<0||extraHourMinor<0)throw new IllegalArgumentException("Invalid tariff");
        }
        @Override public long totalMinor(Duration stay) {
            if(stay.isNegative())throw new IllegalArgumentException("Clock precedes entry");
            // Ceiling at nanosecond precision: exactly 60 minutes is one hour, 60m+1ns is two.
            long seconds=stay.getSeconds(),hours=seconds/3600;
            if(seconds%3600!=0 || stay.getNano()!=0)hours=Math.addExact(hours,1);
            hours=Math.max(1,hours);
            return Math.addExact(firstHourMinor,Math.multiplyExact(hours-1,extraHourMinor));
        }
    }
```

I retain the tariff chosen at entry. Changing tomorrow's rate does not silently alter an already accepted visit. A business that prices by current exit rates could choose that policy instead, but it would need to communicate and record that contract explicitly.

## 4. Complete entry, payment and exit execution

### Entry: choose and claim under one authority

An entrance sends `entryKey=E17` for car KA01AB1234. Inside the lot monitor I first check whether E17 already produced a visit. If so, the same vehicle gets the existing ticket; a different payload under E17 is rejected. A registration already inside under another key is also rejected.

I then select from non-disabled, unoccupied spots, validate the policy's result and create one session identity. The occupancy claim, session, active-registration index and retry mapping are recorded together before returning the ticket. The injected ID source is checked for collisions before any map changes.

```java
// source: Parking.java#enter
        public synchronized SessionView enter(String entryKey,Vehicle vehicle) {
            requireKey(entryKey);Objects.requireNonNull(vehicle);
            String previous=entries.get(entryKey);
            if(previous!=null) {
                Session s=session(previous);
                if(!s.vehicle.equals(vehicle))throw new IllegalArgumentException("Entry key payload conflict");
                return s.view();
            }
            if(activeVehicles.containsKey(vehicle.registration))throw new IllegalStateException("Vehicle already inside");
            List<Spot> free=spots.values().stream().filter(s->!disabled.contains(s.id)&&!occupancy.containsKey(s.id)).toList();
            Spot spot=allocator.choose(vehicle,free);
            if(!free.contains(spot)||!fits(vehicle.kind,spot.kind))throw new IllegalStateException("Allocation policy returned invalid spot");
            String id=Objects.requireNonNull(ids.get());
            if(id.isBlank()||sessions.containsKey(id))throw new IllegalStateException("Session identity collision");
            Session s=new Session(id,vehicle,spot,clock.instant(),tariff);
            sessions.put(id,s);occupancy.put(spot.id,id);activeVehicles.put(vehicle.registration,id);entries.put(entryKey,id);
            return s.view();
        }
```

There is no separate “check free now, occupy later” window. Suppose both gates previously saw C17 free:

| Order | Gate A | Gate B | Authoritative observation |
|---|---|---|---|
| 1 | Calls `enter(E17, carA)` | Calls `enter(E18, carB)` | Both may have seen a stale display |
| 2 | Enters the lot monitor | Waits | A selects and claims C17 |
| 3 | Returns ticket S17 | Acquires the monitor | B sees C17 owned by S17 |
| 4 | Opens its barrier using S17 | Selects another compatible spot or gets full | At most one active session owns C17 |

[![The two-gate timeline serializes selection and occupancy insertion in one critical section; the second gate rechecks after the first commit.](lld-figures/parking-race.svg)](lld-figures/parking-race.svg)

A thread-safe map alone would not make that sequence atomic. A static singleton would not fix it either; singleton controls construction, not a multi-step invariant, and it makes testing two independent lots harder.

If the physical entrance fails after ticket issuance, the allocation remains recorded. Retrying the same entry key returns that allocation; it does not leak a second spot. An operator/device reconciliation path can cancel a provably unused admission, but it must not free a spot merely because a network reply timed out.

### Payment: reserve the intent, call outside the lock, record the outcome

The customer sees a quote and approves its `dueMinor`. `pay` revalidates that amount under the monitor. If a tariff boundary changed the amount between display and payment, it returns a changed-quote failure before calling the provider. It does not charge an unexpected higher fee simply because the server can calculate one.

Inside the first critical section I record one attempt and mark the session PAYMENT_PENDING. Only then do I release the monitor and call `PaymentPort.charge` with the stable key. A duplicate arriving while that call is blocked sees PENDING and returns; it does not launch another collection. A different key is rejected until the outstanding intent is resolved.

After I/O, a second short critical section applies the result:

- **CONFIRMED:** add this amount once to cumulative paid credit, record receipt evidence and grant the exit window.
- **DECLINED:** retain the occupied spot and paid credit, return the session to PARKED, and allow a newly approved attempt with a new key.
- **UNKNOWN:** retain the original attempt and ownership. Do not collect again or claim the car is entitled to leave.

[![Payment preparation and finalization use short lot critical sections, while the slow provider call runs outside them so another entry gate can continue.](lld-figures/parking-payment.svg)](lld-figures/parking-payment.svg)

The following method includes those boundaries, duplicate handling, amount approval and zero-due handling:

```java
// source: Parking.java#payment
        public PaymentView pay(String sessionId,String paymentKey,long approvedDueMinor) {
            Attempt work;
            synchronized(this) {
                requireKey(paymentKey);if(approvedDueMinor<0)throw new IllegalArgumentException("Negative approval");
                Session s=session(sessionId);Attempt old=attempts.get(paymentKey);
                if(old!=null) {
                    if(!old.sessionId.equals(sessionId)||old.amount!=approvedDueMinor)throw new IllegalArgumentException("Payment key payload conflict");
                    return old.view(); // A duplicate cannot start a second provider call.
                }
                if(s.state==SessionState.CLOSED)throw new IllegalStateException("Session closed");
                if(s.state==SessionState.PAYMENT_PENDING||s.state==SessionState.PAYMENT_UNKNOWN)
                    throw new IllegalStateException("Resolve original payment first");
                if(s.state==SessionState.PAID && clock.instant().isBefore(s.exitBy)) {
                    if(approvedDueMinor!=0)throw new IllegalStateException("Quote changed; approve the current amount");
                    Attempt covered=new Attempt(paymentKey,sessionId,quote(sessionId));covered.state=PaymentState.CONFIRMED;covered.reference="ALREADY_COVERED";
                    attempts.put(paymentKey,covered);return covered.view(); // Does not extend grace.
                }
                Quote q=quote(sessionId);
                if(q.dueMinor!=approvedDueMinor)throw new IllegalStateException("Quote changed; approve the current amount");
                work=new Attempt(paymentKey,sessionId,q);
                attempts.put(paymentKey,work);s.activePayment=paymentKey;s.state=SessionState.PAYMENT_PENDING;
                if(work.amount==0)return finish(paymentKey,new ProviderReply(PaymentState.CONFIRMED,"COVERED_BY_PRIOR_PAYMENTS"));
            }
            ProviderReply reply;
            try { reply=payments.charge(work.key,work.amount); }
            catch(RuntimeException uncertain) { reply=new ProviderReply(PaymentState.UNKNOWN,null); }
            return finish(work.key,reply); // Provider I/O completed without holding the lot lock.
        }
        public PaymentView reconcile(String paymentKey) {
            synchronized(this) {
                Attempt a=attempt(paymentKey);
                if(a.state==PaymentState.CONFIRMED||a.state==PaymentState.DECLINED)return a.view();
            }
            ProviderReply reply;
            try {reply=payments.lookup(paymentKey);}catch(RuntimeException uncertain){reply=new ProviderReply(PaymentState.UNKNOWN,null);}
            return finish(paymentKey,reply);
        }
```

For this contract, a provider's DECLINED means a definitive rejected operation. “Reference not found yet,” a transport timeout or an in-progress lookup must be UNKNOWN/PENDING, not a definitive decline. Otherwise a retry with a new key could collect while the original operation later succeeds.

`reconcile` looks up the original payment key. Confirmation then applies the amount once. A later duplicate reconciliation returns the recorded final result. A provider violating its own final-outcome contract needs an operational exception investigation; it is not legitimate for application code to guess which inconsistent receipt represents truth.

### Exit: verify entitlement and release only this visit's spot

Payment does not physically remove a vehicle. `confirmExit` is called from a trusted exit event after validating the ticket, with a unique event identity. It requires PAID and `now < exitBy`, checks that the occupancy map still names this session, removes that ownership and closes the session in one operation.

```java
// source: Parking.java#exit
        public synchronized SessionView confirmExit(String sessionId,String exitEventId) {
            requireKey(exitEventId);Session s=session(sessionId);String previous=exits.get(exitEventId);
            if(previous!=null&&!previous.equals(sessionId))throw new IllegalArgumentException("Exit event payload conflict");
            if(s.state==SessionState.CLOSED)return s.view();
            if(s.state!=SessionState.PAID||!clock.instant().isBefore(s.exitBy))
                throw new IllegalStateException("Payment or additional payment required");
            if(!sessionId.equals(occupancy.get(s.spot.id)))throw new IllegalStateException("Spot ownership mismatch");
            occupancy.remove(s.spot.id);activeVehicles.remove(s.vehicle.registration,sessionId);
            s.state=SessionState.CLOSED;exits.put(exitEventId,sessionId);return s.view();
        }
```

If a delayed exit event for S17 arrives after S17 closed and C17 was allocated to S18, it returns S17's closed result. It never blindly sets C17 to free. Checking visit identity, not just spot ID, prevents a stale callback from releasing a new customer's allocation.

### Paid grace and additional fees, worked end to end

The chosen rule grants ten minutes from payment confirmation. A vehicle enters at 09:00 and pays at 09:59: the collected amount is ₹40 and its deadline is 10:09. It may leave at 10:01 without a new charge even though a second billing hour has begun. At exactly the deadline the grant is expired because the validity interval is half-open.

If it remains until 10:10, the chargeable stay totals ₹60 and paid credit is ₹40. The next approved amount is **₹20**, not another ₹60. Once that top-up succeeds the session's paid credit is ₹60 and a new ten-minute exit grant begins. Repeating the original payment key does not extend its deadline or charge again.

[![The fee timeline shows a forty-rupee payment at 09:59, an exit grant until 10:09, and only twenty rupees additional due at 10:10 after crediting the earlier payment.](lld-figures/parking-fees.svg)](lld-figures/parking-fees.svg)

If the grace expires while the accumulated tariff is still fully covered, a newly requested zero-due grant needs no provider call. The system records that no-charge attempt and its new deadline. This avoids inventing a zero-value card transaction while retaining a traceable decision.

## 5. Concurrency, failures and a production extension

### The exact lock boundary and its cost

The lot monitor covers selection/claim, identity checks, quote-to-attempt preparation, payment finalization and exit release. It does not cover card-network calls, barrier motor waits or display listeners. The executable test blocks a provider call and proves a second entrance can still progress.

The simple allocator scans N spots and selects a minimum in O(N). Entry also builds a free candidate list. Availability queries scan rather than trusting a mutable count. This is intentional for a readable in-memory solution. If measurements justify it, I would maintain ordered free-spot indexes per size/floor; their updates must still occur atomically with the ownership transition.

Moving to floor-level locks increases concurrency but adds cross-floor selection and registry coordination. I would define a stable lock order and handle a lost claim by retrying selection. Replacing one monitor with several locks without a consistency protocol can create a faster double-booking bug.

### What survives a crash, and what does not

The included example is in-memory. It cannot honestly recover paid visits after a process restart. A durable version stores sessions, occupancy, entry identities, accepted quotes and payment intents transactionally. The provider key is recorded before collection; unresolved intents are scanned and reconciled on recovery. An external charge cannot be reversed by rolling back a local transaction.

For multiple server replicas, the authoritative database enforces one active occupancy per spot and, under this policy, one active visit per registration. Conditional writes/row locks and unique request identities replace the JVM monitor's global role. The repository transaction performs find/claim/session creation together; a display cache cannot become the allocation authority.

### Operational cases with defined outcomes

| Event | Chosen outcome |
|---|---|
| No compatible spot although some other type is free | Reject as no compatible capacity; do not issue a ticket |
| Same entry key and same vehicle | Return the recorded visit |
| Same entry/payment identity with another payload | Conflict; do not reinterpret old intent |
| Card declined | Spot remains occupied; another approved attempt can follow |
| Card result unknown | Block a new collection; reconcile original reference |
| Payment succeeds but barrier is unavailable | Retain PAID/grace and gate evidence; retry access or operator recovery |
| Grace expires | Quote the remaining difference and require approval |
| Old exit event after reassignment | Return old closed result without touching new ownership |
| Admin disables an occupied spot | Reject in this base API; evacuation/maintenance is a separate workflow |
| Clock precedes entry | Reject invalid billing duration rather than manufacture a negative charge |

Time comes from an injected `Clock`. That makes exact boundaries testable and supplies absolute timestamps for records. A deployed service also needs a trusted time/clock-adjustment policy; wall-clock timestamps and monotonic elapsed timers solve different problems.

The [complete implementation](reference-code/lld-three/Parking.java) and [checks](reference-code/lld-three/ThreeChecks.java) cover simultaneous entrances, amount approval, duplicate/in-flight payments, declined and unknown outcomes, reconciliation, grace credits, tariff snapshots and stale exit replay. No real provider or personal vehicle data is used.

## 6. Interviewer follow-ups

**Why is this not a Singleton?** The physical business may have one lot, but that does not require global process state. Constructor injection lets two lots, two tests or two simulations coexist. Exclusivity is enforced by the ownership operation, not by restricting how many Java objects can be constructed.

**Where do floor, entrance and exit objects belong?** A floor is useful for layout/query grouping, and gate adapters translate device events into the lot's commands. They do not each keep independent occupancy truth. I can add `FloorView`, `EntranceAdapter` and `ExitAdapter` without letting three components disagree about which session owns a spot.

**How would I support EV or accessible spaces?** I would add capabilities and eligibility constraints, then extend the compatibility/allocation policy. Vehicle size, charging need and permit eligibility are different dimensions; a deep inheritance tree for every combination would grow unnecessarily. The atomic claim remains the same.

**How would I handle a lost ticket?** An authorized attendant resolves the active visit from verified vehicle/entry evidence, applies a documented lost-ticket tariff or adjustment, and creates one approved payment intent. It does not create a second session or free an arbitrary spot by registration string alone. This needs staff authorization and audit beyond the base public commands.

**What if two exits try to charge one ticket?** Preparation serializes at the session. One intent becomes pending; an identical retry observes it and another identity conflicts. The provider key supplies downstream deduplication/reconciliation as well. The exit operation later closes only this session once.

**Could a slow allocation strategy hold the whole lot?** Yes, which is why the injected strategy's contract is pure, bounded, local computation. A remote occupancy query is not allowed inside it. If selection becomes expensive, I introduce transactional indexes or candidate hints followed by an authoritative claim, not network I/O under the monitor.

**How would I issue receipts?** `PaymentView` includes the retained quote, accepted amount, payment key, status and provider reference. A receipt is produced from confirmed evidence and tariff version. An UNKNOWN response may show a pending acknowledgement, but cannot be printed as a successful collection receipt.

**What would I monitor?** Allocation conflicts/full responses, occupancy reconciliation, pending-payment age, duplicate intents, provider latency and failures, grace top-ups and gate failures. A successful HTTP response count alone cannot reveal occupied spots with no active visit or captured payments with unresolved local state.

## 7. Closing answer

“I would use a visit-based model with an atomic spot claim, immutable tariff/quote evidence and one stable identity per entry, payment and exit. The short lot lock protects ownership; slow collection happens outside it. Unknown financial outcomes are reconciled, paid credit is preserved across top-ups, and only an authorized physical exit releases the visit's spot. Allocation and tariff strategies make business changes replaceable without moving correctness into displays or device panels.”

For an interview presentation I would first establish those three identities, draw the layout and domain ownership, implement entry atomically, then work through a payment timeout and the grace-period arithmetic. That demonstrates the object model and the failure semantics behind it instead of ending with a list of patterns.

## Problem

Design the low-level software for a building with several elevators. A person can request an upward or downward ride from a floor; a passenger inside a car can select a destination. Show how the system assigns calls, orders stops, operates doors and handles a car becoming unavailable.

The interesting question is not how to put floor numbers in a queue. It is how a request remains owned until an eligible car actually offers the requested ride, while every movement respects the car's state.

This answer includes a runnable Java 21 **floor-event simulator**. Its ticks are logical events, not seconds. It does not drive motors, model a car between floors, or implement a certified safety controller. Separating that boundary makes the scheduling answer more precise: software may request travel, but real hardware must independently enforce its safety interlocks.

## Requirements

I would clarify these points, then proceed with the following explicit contract rather than waiting for the interviewer to supply every detail.

| Question | Decision for this design | Why it affects the model |
| --- | --- | --- |
| Conventional buttons or destination dispatch? | Conventional hall Up/Down buttons; destination chosen inside the car | A hall call does not yet know the destination or passenger count. |
| Building and fleet? | One building, 2–100 indexed floors, several independently identified cars | Floor 0 has no Down button; the top floor has no Up button. |
| What does another press mean? | Coalesce an active `(floor, direction)` call | Ten presses are not evidence of ten passengers. Opposite directions remain separate. |
| What is a successful pickup? | The assigned, available car opens at that floor, for that direction, with spare capacity | Merely passing the floor or assigning a car must not extinguish the call. |
| How are stops ordered? | Directional collective service using a LOOK-style sweep | Serve eligible stops along a direction, then reverse when no further demand requires continuing. |
| How is a car selected? | Earliest simulated pickup over the known plan; stable car ID breaks ties | Nearest floor alone ignores direction and existing stops. |
| Which state can block travel? | Door not closed, obstruction, failed interlock, overload or out-of-service mode | Scheduling preference cannot override a movement guard. |
| What happens on a fault? | Release unserved hall calls for reassignment; retain cabin destinations for operator recovery | Waiting passengers can use another car; onboard passengers cannot be transferred in a map. |
| Concurrency model? | One controller owns mutable fleet state; short synchronized event methods | Assignment, stop insertion and acknowledgement remain one coherent operation. |

Fire service, emergency evacuation, express/zoned cars, real acceleration and braking, access control and persistence are extensions. They require explicit additional policies; they are not silently claimed by this implementation.

## 1. The answer I would present

“I would split the system into a **fleet dispatcher** and **per-car control state**. The dispatcher owns the hall-call ledger and selects a car. Each car owns its cabin stops, assigned hall stops, direction, door state and measured load. The car follows a directional sweep, but can advance only when the movement guards allow it. A hall call is completed by a validated pickup event, not by dispatching it.”

That split answers two different decisions. **Dispatch** means choosing *which car*. **Scheduling** means deciding *which stop that car serves next*. A class called `ElevatorManager` that does both through one unsorted request list hides this distinction.

[![Selected fleet design: the controller assigns hall calls, each car owns its sweep plan, and door/load guards control travel](designs/lld-3.svg)](designs/lld-3.svg)

Consider a ten-floor building. Car A is at 0 with cabin destinations 3 and 6. Car B is at 3 with a cabin destination of 1. Someone at 2 presses Up. B is physically closer, but its current service is downward. The implemented estimator chooses A: pickup takes **4 model ticks for A versus 9 for B**. Those are derived from the same stop and door rules used to run the simulator, rather than an unexplained distance multiplier.

[![Two elevator shafts show A below an Up call at floor two and B travelling down; the known-plan simulation predicts four versus nine pickup events](lld-figures/elevator-building.svg)](lld-figures/elevator-building.svg)

For A: move 0→1, move 1→2, begin opening, finish opening and acknowledge pickup. For B: move 3→2→1, open, finish opening, begin closing, finish closing, move 1→2, begin opening, finish opening. Future arrivals, travel time and variable dwell are not included. In a real building the score would use measured time estimates; the ownership contract would stay the same.

## 2. The object model and invariants

### Hall calls and cabin calls are different facts

`HallKey(2, UP)` means “someone at floor 2 wants an upward ride.” `cabinCall("A", 7)` means “someone already in A wants floor 7.” The first belongs to the building until served; the second belongs to A. A hall call is assignable to another car. A cabin destination is not.

The application deliberately has no `HallRequest(source, destination)` constructor. That would invent information the conventional interface cannot collect. Destination-control elevators would be a valid **different requirement**, with a different request contract.

```java
// source: Elevators.java#contracts
    public enum Direction { UP, DOWN, IDLE }
    public enum Door { CLOSED, OPENING, OPEN, CLOSING }
    public enum Mode { NORMAL, OUT_OF_SERVICE }
    public enum CallState { WAITING, ASSIGNED, SERVED }
    public enum Action { IDLE, MOVED, OPENING, OPENED, CLOSING, CLOSED, BLOCKED, OUT_OF_SERVICE }
    public record HallKey(int floor,Direction direction) {}
    public record HallTask(long callId,HallKey key,long epoch) {}
    public record CallView(long id,HallKey key,long createdTick,CallState state,String carId,long epoch) {}
    public record CarSnapshot(String id,int floor,int capacity,int load,Direction heading,Direction boarding,
                              Door door,Mode mode,boolean obstructed,boolean interlock,
                              List<Integer> cabin,List<HallTask> hall) {
        public CarSnapshot { cabin=List.copyOf(cabin);hall=List.copyOf(hall); }
    }
    public record Tick(String carId,Action action,int from,int to,Direction heading,List<HallTask> pickups) {
        public Tick {pickups=List.copyOf(pickups);}
    }
    public interface DispatchPolicy { String choose(HallTask candidate,List<CarSnapshot> cars); }
    private record Goal(int floor,Direction boarding) {}
```

`CarSnapshot` and `Tick` defensively copy their lists. A dispatch policy can inspect a snapshot without receiving a reference to a mutable queue. `HallTask` includes an **epoch**, the version of an assignment. It prevents an old car's late acknowledgement from completing a call that has since been reassigned.

[![Elevator object model separates the system call ledger and dispatch strategy from each car's private plan, door state and load](lld-figures/elevator-domain.svg)](lld-figures/elevator-domain.svg)

| Owner | State and responsibilities | State it must not own |
| --- | --- | --- |
| `SystemController` | Cars, active hall-key index, call identities, assignment versions, event clock | Passenger guesses inferred from button presses |
| `Request` | ID, original creation tick, floor/direction, state, assigned car, epoch | A mutable reference into another car's queue |
| `Car` | Floor, travel heading, boarding direction, doors, mode, sensor load, interlock and plan | Global completion decisions about another car's request |
| `SweepPlan` | Deduplicated cabin destinations and assigned hall tasks; next eligible goal | Motor commands or global car selection |
| `DispatchPolicy` / `EtaPolicy` | Pure choice from immutable snapshots | Changes to ownership while calculating a score |

The key invariants are concrete enough to test:

1. At most one active hall call exists for a particular `(floor, direction)`.
2. An assigned call has one current car and epoch; the car's task matches both.
3. A cabin destination is removed when that car opens there. A hall call is removed only by a matching pickup acknowledgement.
4. `MOVED` implies normal mode, closed doors, clear obstruction, satisfied interlock and load no greater than capacity.
5. A full car can still transport its onboard passengers, but cannot be assigned another pickup. An overloaded car cannot travel.
6. Reassignment retains the call's original identity and creation age; stale owners cannot complete it.
7. A snapshot cannot mutate the live plan.

**Direction is not door state.** A car may be stationary with its door open while boarding Up passengers. `boarding` records the ride being offered at that stop; `heading` selects the sweep. Keeping those facts explicit prevents “door open at floor 2” from accidentally completing both Up and Down calls.

## 3. Final design and public contract

The complete source is [Elevators.java](reference-code/lld-three/Elevators.java); the exact executable scenarios are in [ThreeChecks.java](reference-code/lld-three/ThreeChecks.java). Code excerpts below are taken directly from that compiling implementation.

| Command | Meaning and observable result |
| --- | --- |
| `hallCall(floor, direction)` | Validate the button; return the existing active call or create and dispatch one. |
| `cabinCall(carId, floor)` | Deduplicate a destination in that car. Reject an out-of-service car. |
| `tick()` | Advance each car by one model event, validate generated pickup acknowledgements, then retry waiting dispatch. |
| `load(carId, passengers)` | Apply a sensor reading; at/full capacity release unserved hall assignments. |
| `obstruction(carId, true)` | Block travel/reopen during closing and release hall assignments so other cars can serve them. |
| `interlock(carId, false)` | Forbid travel and release unserved hall assignments. |
| `outOfService(carId)` | Stop that car's simulation; requeue hall calls while retaining cabin stops. |
| `snapshot(carId)` / `call(id)` | Return immutable observations, including assignment identity/version. |

### Coalesce first, assign atomically

`active` indexes a hall key to its current call ID. This is separate from `requests`, the history/ledger. An additional Up press at floor 2 returns the same call while it is waiting or assigned. After service, a new press creates a new identity. That also makes a late acknowledgement for a previous visit harmless.

```java
// source: Elevators.java#dispatch
        public synchronized CallView hallCall(int floor,Direction direction) {
            validFloor(floor);
            if(direction==null||direction==Direction.IDLE||floor==0&&direction==Direction.DOWN||floor==floors-1&&direction==Direction.UP)
                throw new IllegalArgumentException("Impossible hall direction");
            HallKey key=new HallKey(floor,direction);Long existing=active.get(key);
            if(existing!=null)return requests.get(existing).view();
            Request r=new Request(++nextId,key,tick);requests.put(r.id,r);active.put(key,r.id);dispatch();return r.view();
        }
        private void dispatch() {
            // Linked insertion order is oldest-first; an existing active call retains its age.
            for(Request r:requests.values())if(r.state==CallState.WAITING) {
                HallTask candidate=new HallTask(r.id,r.key,r.epoch+1);
                String id=policy.choose(candidate,cars.values().stream().map(Car::snapshot).toList());
                if(id==null)continue;Car c=car(id);
                if(c.mode!=Mode.NORMAL||c.load>=c.capacity||c.obstructed||!c.interlock)throw new IllegalStateException("Policy returned ineligible car");
                r.epoch++;r.carId=id;r.state=CallState.ASSIGNED;
                c.plan.hall.put(r.id,new HallTask(r.id,r.key,r.epoch));
            }
        }
```

All those mutations happen inside the controller monitor. A policy must be pure and must not perform network I/O while it is invoked there. This implementation calculates from a bounded local snapshot. A slower external optimizer would need a separate calculation phase and a version check before accepting its proposal.

The policy scores every eligible car by cloning its snapshot, inserting a probe task and running the **same** `Car.tick()` rules until the probe is picked up. It returns infinity for an unavailable, full, obstructed or interlock-blocked car. If no car is eligible, the call remains `WAITING`; it is not discarded and no fake car ID is assigned.

### Why these patterns fit

`DispatchPolicy` is **Strategy**: replace ETA selection with a measured-time, energy-aware or zone-aware policy without rewriting ownership. Door and call enums describe explicit **state machines**. This small implementation uses guarded transitions rather than one class per state; a large maintenance controller could extract state objects if transitions become too complex. A pattern name is justified by a real variation point, not by a requirement to use every pattern.

Cars are instances, not a process-wide Singleton. Two building controllers can run independently in one test. Displays subscribe to observations in a production adapter; they do not mutate a stop list to make a button light look correct.

## 4. Directional scheduling, with a complete trace

### Why a queue or a sorted set alone is insufficient

A FIFO queue can make a car reverse for each new arrival. A single globally sorted floor set always picking the minimum can send an upward-moving car backward while passengers still need a higher floor. Two sets without hall direction can open for Down passengers on the way Up and wrongly mark them served.

The selected rule is a **LOOK-style directional sweep**, also called directional collective service here. LOOK reverses at the last required stop instead of travelling to the building endpoint merely because it exists. The implementation additionally distinguishes the boarding direction of hall calls.

While going Up, select the nearest cabin or Up hall stop at/above the current floor. If there are no such stops but Down calls remain above, continue to the highest of those floors and offer a downward ride there. If there is no reason to continue upward, reverse and apply the symmetric Down rule. An idle car chooses a nearest demand, with a stable lower-floor tie break, to start its sweep.

```java
// source: Elevators.java#look
        Goal next(int floor,Direction heading) {
            TreeSet<Integer> up=new TreeSet<>(cabin);up.addAll(halls(Direction.UP));
            TreeSet<Integer> down=new TreeSet<>(cabin);down.addAll(halls(Direction.DOWN));
            if(up.isEmpty()&&down.isEmpty())return null;
            if(heading==Direction.IDLE) {
                TreeSet<Integer> all=new TreeSet<>(up);all.addAll(down);
                int closest=all.stream().min(Comparator.comparingInt((Integer f)->Math.abs(f-floor)).thenComparingInt(f->f)).orElseThrow();
                if(closest==floor)return new Goal(floor,halls(Direction.UP).contains(floor)?Direction.UP:
                    halls(Direction.DOWN).contains(floor)?Direction.DOWN:Direction.IDLE);
                return next(floor,closest>floor?Direction.UP:Direction.DOWN);
            }
            if(heading==Direction.UP) {
                Integer matching=up.ceiling(floor);
                if(matching!=null)return new Goal(matching,Direction.UP);
                if(!down.isEmpty()&&down.last()>floor)return new Goal(down.last(),Direction.DOWN);
                if(down.contains(floor))return new Goal(floor,Direction.DOWN);
                return next(floor,Direction.DOWN);
            }
            Integer matching=down.floor(floor);
            if(matching!=null)return new Goal(matching,Direction.DOWN);
            if(!up.isEmpty()&&up.first()<floor)return new Goal(up.first(),Direction.UP);
            if(up.contains(floor))return new Goal(floor,Direction.UP);
            return next(floor,Direction.UP);
        }
```

The `ceiling`/`floor` operations include the current floor, so a request at the present floor can open the doors without an unnecessary trip. A cabin stop is eligible in either direction because its rider is already onboard. A hall call is eligible only for the direction offered there.

[![A directional sweep serves Up at two, cabin stops three and seven, then Down at five; passing floor five upward does not complete its Down call](lld-figures/elevator-sweep.svg)](lld-figures/elevator-sweep.svg)

Here is an entire plan, not just a queue declaration:

| Step | Car state / pending demand | Decision |
| --- | --- | --- |
| Start | A at 0, cabin `{3,7}`, hall `2↑` and `5↓` | Head Up; 2 is the first matching stop. |
| Open at 2 | Spare capacity, boarding Up | Serve `2↑`; remove only that hall task. |
| Continue | Cabin 3 and 7 remain, hall `5↓` remains | Open at 3 for its cabin destination. |
| Pass 5 | Still heading Up, cabin 7 remains | Keep `5↓` active. Passing is not pickup. |
| Open at 7 | Last upward demand is satisfied | The next demand is below; reverse. |
| Open at 5 Down | Current owner/epoch, capacity and direction match | Serve `5↓`; with no demand left, become idle after closing. |

The resulting opening sequence is exactly **`2:UP, 3:UP, 7:UP, 5:DOWN`**, asserted in the runnable checks. If both `2↑` and `2↓` exist, opening Up completes only `2↑`. The Down call remains independently visible and assigned.

This policy does not claim optimality under arbitrary future traffic. Calls are considered oldest-first when waiting for assignment, and reassignment preserves age. Continuous new upward demand can still delay a Down call. A production fairness extension would cap a sweep or impose a maximum waiting-time threshold and re-evaluate assignments. Its tests would need adversarial ongoing arrivals, not just a static batch.

## 5. Door transitions, faults and recovery

### Scheduling never bypasses the movement guard

An arrival begins opening; a later tick completes it. Opening is the event at which cabin stops and eligible hall pickups can be acknowledged. After an unblocked dwell event the doors begin closing, then become closed on the next event. These discrete events make every transition visible in a trace.

[![Door cycle has closed, opening, open and closing states; an obstruction reopens, overload holds, and movement requires all guards](lld-figures/elevator-doors.svg)](lld-figures/elevator-doors.svg)

```java
// source: Elevators.java#tick
        Tick tick() {
            int from=floor;Action action;List<HallTask> pickups=List.of();
            if(mode==Mode.OUT_OF_SERVICE)action=Action.OUT_OF_SERVICE;
            else if(door==Door.OPENING) {
                door=Door.OPEN;action=Action.OPENED;plan.cabin.remove(floor);
                if(load<capacity)pickups=plan.hall.values().stream()
                    .filter(h->h.key.floor==floor&&h.key.direction==boarding).toList();
            }else if(door==Door.OPEN) {
                if(obstructed||load>capacity)action=Action.BLOCKED;
                else {door=Door.CLOSING;action=Action.CLOSING;}
            }else if(door==Door.CLOSING) {
                if(obstructed||load>capacity){door=Door.OPENING;action=Action.OPENING;}
                else {door=Door.CLOSED;action=Action.CLOSED;}
            }else if(load>capacity){door=Door.OPENING;action=Action.OPENING;}
            else if(obstructed||!interlock)action=Action.BLOCKED;
            else {
                Goal next=plan.next(floor,heading);
                if(next==null){heading=Direction.IDLE;action=Action.IDLE;}
                else if(next.floor==floor){boarding=next.boarding;heading=boarding;door=Door.OPENING;action=Action.OPENING;}
                else {heading=next.floor>floor?Direction.UP:Direction.DOWN;floor+=heading==Direction.UP?1:-1;action=Action.MOVED;}
            }
            return new Tick(id,action,from,floor,heading,pickups);
        }
```

The guard is stronger than checking `door == CLOSED`: the car must also be in normal mode, have a clear obstruction input, a true interlock and no overload. A closed-door interlock fault produces `BLOCKED`; it does not pretend the car arrived at the next floor. A closing obstruction transitions to `OPENING`. While open, obstruction or overload holds the door open. In this floor-event model an overload detected while closed begins opening at the current model floor.

**Full and overloaded are different.** At `load == capacity`, the car may leave with its existing passengers and service cabin stops, but it offers no hall pickup. At `load > capacity`, it cannot move. Button presses do not update load; a separate sensor event supplies the measurement. The demo does not simulate passenger boarding counts or automatically decrement them at cabin stops.

Real hardware reports richer position and sensor states, including between-floor conditions. A production adapter must map them into a certified controller's commands and acknowledgements. The model's one-floor movement is an interview scheduling abstraction, not an emergency-stop procedure.

### Reassign a call without accepting a stale completion

Suppose call 41 at `2↑` is assigned to A at epoch 1. A fails. The controller marks the call waiting at epoch 2 and removes its old task. Dispatch assigns B at epoch 3. A delayed “picked up 41, epoch 1” must not turn off B's hall call.

[![Assignment timeline shows A at epoch one, waiting at epoch two, B at epoch three and an old acknowledgement rejected without resetting call age](lld-figures/elevator-ownership.svg)](lld-figures/elevator-ownership.svg)

```java
// source: Elevators.java#ownership
        public synchronized boolean acknowledgePickup(long callId,String carId,long epoch) {
            Request r=requests.get(callId);Car c=car(carId);
            if(r==null||r.state!=CallState.ASSIGNED||!carId.equals(r.carId)||r.epoch!=epoch)return false;
            if(c.door!=Door.OPEN||c.floor!=r.key.floor||c.boarding!=r.key.direction||c.load>=c.capacity||c.mode!=Mode.NORMAL)return false;
            r.state=CallState.SERVED;active.remove(r.key,r.id);
            c.plan.hall.remove(callId,new HallTask(callId,r.key,epoch));return true;
        }
        public synchronized void outOfService(String carId) {
            Car c=car(carId);c.mode=Mode.OUT_OF_SERVICE;releaseHallCalls(c);dispatch();
            // Cabin destinations remain: existing passengers require an operator recovery procedure.
        }
        private void releaseHallCalls(Car c) {
            for(HallTask h:new ArrayList<>(c.plan.hall.values())) {
                Request r=requests.get(h.callId);
                if(r!=null&&r.state==CallState.ASSIGNED&&c.id.equals(r.carId)&&r.epoch==h.epoch) {
                    r.state=CallState.WAITING;r.carId=null;r.epoch++;
                }
            }
            c.plan.hall.clear();
        }
```

The check requires the current call state, owner and epoch **and** actual car state: correct floor, open door, offered direction, spare capacity and normal mode. An acknowledgement is evidence to validate, not a command to erase a request unconditionally. A retry after successful service returns false and has no further effect.

Fault release does not delete the request or replace its creation tick. Waiting age therefore remains observable. Cabin stops stay in the failed car because those passengers require an operator recovery procedure. Another car can collect waiting people at floor 2; it cannot fulfil a destination for someone trapped in A merely by inheriting the number 6.

### Failure and recovery decisions

| Event | Exact selected behavior | Why |
| --- | --- | --- |
| Repeated hall press | Return the active call identity | Coalesces button noise without inventing occupancy. |
| Bottom Down / top Up | Reject before creating a call | The ride direction is impossible in this building. |
| All cars unavailable/full | Retain `WAITING`; retry on subsequent state/tick events | No request is lost or assigned to an ineligible car. |
| Car becomes full | Release its unserved hall tasks, retain cabin stops | Protect capacity while continuing onboard service. |
| Obstruction during closing | Reopen; release hall tasks for other cars | Does not move or endlessly claim pickups it cannot offer. |
| Interlock fails | Block movement and release hall assignments | A scheduling score cannot override a sensor guard. |
| Assigned car fails | Preserve call/age; increment epoch and reassign | Enables recovery while invalidating old ownership. |
| Old car sends pickup | Reject mismatched owner/epoch | Prevents a late event from clearing the replacement's work. |
| Application restarts | In-memory demo has no recovery claim | A production ledger needs durable events, sequence numbers and sensor reconciliation. |

The runnable checks cover the exact four-stop trace, coalescing, opposite directions at one floor, the 4-versus-9 dispatch example, full/overload behavior, obstruction reopening, fault reassignment and late acknowledgement rejection. Fifty seeded finite workloads check that their static call batches drain. Every observed movement is checked against the pre-movement door/mode/load/interlock state. Those checks substantiate this simulator's contract; they are not a proof of real elevator safety or arbitrary-traffic fairness.

## 6. Interviewer follow-ups

### Why not choose the nearest car?

Distance is only a lower bound on pickup effort. A car one floor away going in the wrong direction may need to finish a trip, open and close, then return. The worked example demonstrates that counterexample with executable event counts. ETA selection still uses an estimate over current knowledge; it cannot predict unknown passengers or future requests.

### Why not give every car a thread?

The important concurrency boundary is ownership, not thread count. Here one controller serializes short events, so adding a call to the ledger and to a car plan is atomic. Separate device threads can deliver events into that owner. If each car has its own event loop, assignment becomes a message protocol with an acknowledged epoch; direct concurrent mutation of both maps would be the wrong shortcut.

### What is the complexity?

Let `C` be cars, `R` retained ledger records, `S` active stops/tasks per car and `T` simulated events until pickup. The straightforward implementation rebuilds directional sets in `O(S log S)` during next-goal selection. One ETA choice is bounded by `O(C × T × S log S)` with a 10,000-event cutoff; dispatch can do this for each waiting call. It scans the retained ledger, so even a tick with no new waiting calls has `O(R)` dispatch overhead. Memory includes history `O(R)` plus car plans. That is acceptable for this deliberately small interview simulator, not a fleet-scale performance claim.

For a larger service, keep a separate pending index, archive completed requests, maintain directional floor indexes incrementally and replace event replay with a validated route-time estimator. The snapshot/strategy interface provides that seam; the current code does not silently implement it.

### Can an Up request starve while demand keeps arriving?

Oldest-first assignment alone is not a complete fairness guarantee once a call has been placed into a car's sweep. I would bound waiting time, cap a sweep's extension and periodically reconsider overdue pickups, preserving assignment epochs. Define the desired bound and traffic assumptions before claiming starvation freedom. The current tests use finite batches and support only that narrower progress claim.

### What if two cars reach the same floor together?

Only the current owner and epoch can acknowledge that hall call. Two independently assigned directions can be served separately. An unassigned car opening nearby does not erase the call. A deliberate opportunistic-pickup feature would first transfer ownership atomically and publish a new epoch; it should not be smuggled into a display callback.

### How do destination dispatch and priority passengers change this?

Destination dispatch knows the destination before boarding, so it can group compatible trips and assign a particular car to a passenger request. That changes the request identity and coalescing semantics. Priority service also needs a defined precedence and starvation policy. Both can reuse car/door guards but require their own dispatcher contract; simply adding a `priority` integer to the current hall key is insufficient.

### Would persistence make this production-ready?

Persistence is necessary for surviving a controller restart, but not sufficient. I would durably record call/assignment events, use monotonic per-device event sequences, reconcile the recovered plan against actual car/door/sensor state, and keep the hardware safety controller authoritative. Restart must not replay an old movement command blindly. Fire, maintenance and rescue modes need approved operating procedures beyond this model.

### Which types actually need extension points?

Car selection clearly varies, so `DispatchPolicy` is an interface. The sweep and door transitions are fixed for this scoped answer, so they remain private implementation details. If the requirements introduce multiple scheduling rules or device protocols, extract those boundaries then. Avoid inheritance trees such as `UpElevator` and `DownElevator`: one physical car changes direction throughout its lifetime.

## 7. Closing answer

“I would keep an explicit hall-call ledger, a replaceable fleet dispatch policy and a private directional plan per car. The car's state machine enforces the travel guards. Completion requires an open-door pickup by the current owner/version; faults requeue hall work without losing age or erasing onboard destinations. That gives a complete conventional-elevator scheduling answer with clear concurrency, recovery and hardware boundaries.”

In the interview I would spend the first minutes establishing hall versus cabin calls, draw the fleet and door states, walk the four-stop trace, then show stale-assignment recovery. I would use the remaining time for ETA cost and fairness trade-offs. That sequence explains the decisions behind the code instead of presenting a pile of class names.

## Problem

Design a movie booking system like BookMyShow: browse cities, cinemas, movies and shows, pick seats and pay. The core interview challenge is **concurrency on seat selection**: two users must never book the same seat, and seats held by an abandoned checkout must free up automatically.

## Requirements

**Functional**
- Search movies by city. List shows per cinema and screen. Show a seat map.
- Select seats, hold them for a few minutes, pay, and confirm the booking.
- Cancel bookings (with a refund policy) and release unpaid holds after a TTL.

**Non-functional**
- No double booking, ever.
- Seat holds must expire without a manual cleanup step.

## 1. Scope and chosen solution

I design reserved-seat booking for a specific show, including an all-or-nothing multi-seat hold, payment, confirmation and expiry. Static `Seat` describes the physical layout; `ShowSeat(showId,seatId)` owns availability for one screening. I choose a relational transaction for allocation and a separate idempotent payment workflow.

## 2. Schema and complete reservation transaction

```text
ShowSeat PK(showId,seatId): status, holdId, expiresAt, bookingId
Hold PK(holdId): customerId, showId, expiresAt, quotedAmount, currency, state
Booking PK(bookingId): holdId UNIQUE, customerId, acceptedPrice, state
PaymentIntent PK(intentId): holdId, providerRef UNIQUE, state, payloadHash

holdSeats(requestId,showId,seatIds,customer) -> Hold | Conflict
confirmPayment(providerRef) -> Booking | RefundRequired | Pending
```

`holdSeats` begins a transaction, locks all requested show-seat rows in sorted seat order, verifies every row is free or expired, writes one hold identity to every seat, and commits. If any seat is unavailable, the transaction rolls back all claims. A request identity with a different payload is rejected; a true retry returns its original hold.

Confirmation locks the hold and the same seat rows, verifies `now < expiresAt`, ownership of every seat, and successful payment evidence. It inserts one booking, changes all seats to SOLD and commits. Expiry competes for these same rows and releases only matching expired hold tokens. If payment completed after ownership was lost, the financial result becomes paid-but-unfulfilled and initiates one refund intent; it never overrides a newer hold. A7 and A8 at ₹250 each produce a frozen ₹500 quote, so price changes during payment cannot alter accepted terms.

For browsing, `GET /movies?city=...` and `GET /shows/{id}/seats` return catalogue/read-model data; neither claims seats. `cancelBooking(bookingId,requestId)` authorizes the owner and cutoff policy, locks the booking and its seats, marks the booking cancelled, releases only seats owned by it, and writes one refund intent in the same transaction. The refund may remain pending while the seat is available again: the customer is still owed that recorded refund. A repeated cancellation returns the original disposition. A cancelled hold with a later successful charge follows the same paid-but-unfulfilled compensation path.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `Movie`, `Cinema`, `Screen`, `Seat` | Catalogue and static layout |
| `Show` | movie + screen + start time. Owns `ShowSeat`s |
| `ShowSeat` | seat for a particular show. Status: `AVAILABLE`, `HELD`, `SOLD` |
| `SeatLockProvider` | `lock(show, seats, user, ttl)`, `unlock` and `validate` |
| `Booking` | user, show, seats, amount. State: `CONFIRMED → CANCELLED`; pending/expired states belong to Hold |
| `PaymentService` | Strategy per method, plus idempotency key |
| `PricingStrategy` | seat category, weekday/weekend, dynamic pricing |

### Design decisions & trade-offs

**1. Lock then pay, not pay then lock.** Hold seats when the user selects them, with a TTL of about 5 minutes. Confirm with payment. If payment happens first, two users can both pay for the same seat.

**2. Implementing the lock (in-process LLD).**
```java
class InMemorySeatLockProvider implements SeatLockProvider {
    private final ConcurrentHashMap<SeatKey, SeatLock> locks = new ConcurrentHashMap<>();
    public synchronized boolean lock(Show s, List<Seat> seats, String user, Duration ttl) {
        if (seats.stream().anyMatch(x -> isLocked(s, x))) return false;  // all-or-nothing
        seats.forEach(x -> locks.put(new SeatKey(s, x), new SeatLock(user, now().plus(ttl))));
        return true;
    }
}
```
All-or-nothing matters: a user selecting 4 seats shouldn't get 3. Sort seat keys before locking if you use per-seat locks, so two threads can't deadlock.

**3. Expiry.** Do a lazy check (`expiresAt < now` means it's free) plus a scheduled sweeper that moves `PENDING` bookings to `EXPIRED`. In a distributed setup this becomes Redis `SET NX PX` per seat, or a DB row with `status, locked_until` and a conditional `UPDATE … WHERE status='AVAILABLE'`.

**4. Booking as a State machine.** Only `PENDING` can become `CONFIRMED`, and only if the lock is still held by this user. Re-validate the lock at confirmation time, because the TTL may have passed during a slow payment.

**5. Idempotent payment callbacks.** Gateways retry. Key the confirmation on `paymentId` so a duplicate callback can't double-confirm.

### Ownership, boundaries and invariants

**Central design question:** A seat hold is temporary ownership with an expiry; payment does not magically make it a booking.

Movie, Theatre, Screen, Seat and Show describe inventory. ShowSeat is the sellable resource because the same chair belongs to different shows. Hold contains user, seats and expiry; Booking contains a price snapshot and payment reference. SeatSelectionPolicy and PaymentPort stay outside seat state.

**Correctness rule:** For a particular show-seat, at most one unexpired hold or confirmed booking owns it. All seats of a multi-seat request are claimed together or none are.

```text
show_seat(show_id,seat_id,state,hold_id,expires_at,version); booking(id,hold_id,payment_id,status,amount_minor)
```

### End-to-end execution trace

Validate show and seat IDs; lock seats in a deterministic order; reclaim expired holds according to database time; atomically create one hold; collect payment without holding row locks; on callback verify hold owner, expiry and payment identity; atomically confirm the entire booking.

### Concurrency and recovery walkthrough

Two users choose the same pair of seats while the expiry worker runs. Conditional ownership transitions use hold IDs and versions, so a late worker cannot clear a newer hold. A late payment callback cannot confirm seats now owned by another booking.

### Policy choices and extension seams

Pessimistic row locking is easy for small seat sets; optimistic version checks suit low contention but require whole-request retries. A Redis countdown is a UI convenience, not the sales authority. Reject or refund a late success according to a documented policy.

### Edge cases that change the design

A callback may arrive twice or before the client receives its payment result. Persist provider event identity and use a booking idempotency key. Seat maps can be stale; the confirmation response, not the map colour, establishes ownership.

**Topic-specific cases:** All-or-none multi-seat allocation; expired hold cannot confirm; repeated callback has one effect; a newer hold survives an old expiry job; prices remain stable.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through payment and expiry

Let H21 expire at 10:05:00. Define valid ownership as `now < expiresAt`; at exactly 10:05:00, it is expired. Both payment confirmation and the cleanup worker must use this rule. Cleanup timing does not establish validity: a row still labelled HELD at 10:05:02 is not an entitlement to confirm.

If the payment provider reports success after the hold was lost, do not sell somebody else's seat. Record the paid-but-unfulfilled outcome, then refund or ask the customer to select new seats according to product policy. The payment reference is unique so a duplicated webhook cannot create a second booking or refund.

For ₹250 per seat, A7 and A8 cost ₹500 before documented fees. Save this quoted amount and its currency on the hold. Repricing seats between hold and confirmation makes the customer approve one amount and pay another. Seat availability from a cached theatre map is a hint; only the reservation transaction can promise ownership.

## 6. Interviewer follow-ups

**Can two customers hold different seats in the same show?** Yes. Lock the relevant show-seat rows rather than the entire cinema unless simplicity at tiny scale justifies the coarser lock.

**Can a hold reserve A7 but fail on A8?** Not when the product promises adjacent seats as one selection. Roll back the transaction if any seat is unavailable.

## 7. Closing answer

I use show-seat rows as the allocation authority, expiring token-owned holds for the payment interval, and an atomic all-seat confirmation. Payment is a separate durable workflow. A late payment or stale expiry callback cannot steal or release a newer customer's hold.

## Problem

Design an ATM: card insertion, PIN entry, balance check, withdrawal, deposit and cash dispensing. This is the textbook problem for the **State** pattern (what the ATM accepts depends on where you are in the flow) and **Chain of Responsibility** (splitting an amount across note denominations).

## Requirements

**Functional**
- Insert card, then enter PIN (3 attempts, then the card is retained), then choose a transaction.
- Withdraw (within limits, in multiples of the smallest note), deposit, check balance, change PIN.
- Dispense the correct mix of notes, print a receipt, eject the card.

**Non-functional**
- Money must never be dispensed without a successful debit, and a debit must never happen without dispensing. You need a compensating action.
- The hardware (dispenser, card reader) is unreliable.

## 1. Scope and chosen solution

I support authenticated balance lookup and cash withdrawal at one ATM. Bank balances remain authoritative at the bank; cassette inventory belongs to the machine. The ATM never stores a clear PIN. Session control, note planning, bank access and physical dispensing are separate responsibilities so each failure can be represented.

## 2. Withdrawal contract and execution

```text
withdraw(operationId, accountToken, amountMinor) -> WithdrawalState
Withdrawal: id, amount, reservedNotePlan, bankRef, deviceRef, state, deliveredNotes
States: CREATED -> AUTHORIZED -> DISPENSING -> COMPLETED
                                -> PARTIAL | UNKNOWN -> RECONCILED
Device result: COMPLETE | PARTIAL | NONE | UNKNOWN
```

I validate amount/currency, compute a bounded feasible note plan, reserve those notes, and persist the withdrawal before external actions. I authorize funds with the bank using the operation identity. A definite decline releases unused inventory. After authorization, I persist DISPENSING before issuing the device command and record the device's evidence. A known full delivery settles under the bank protocol; no delivery releases/voids according to known authorization state; partial and unknown delivery enter reconciliation.

For ₹2,500, five ₹500 notes are feasible only if five notes are available. Three delivered notes mean ₹1,500 physically left the machine even if the requested amount was larger. Inventory is decremented by known delivery; unknown counts remain reserved until device-journal reconciliation. On restart I inspect unresolved withdrawals and the dispenser journal before serving a new dispense. A lost HTTP reply is retried by operation identity and cannot trigger a fresh cash command. Note selection uses bounded change-making when denominations are arbitrary; a greedy method would fail for amount 6 with notes 4 and 3 despite 3+3 being feasible.

## 3. Final design diagram

Keep two separate truths: the **bank ledger** records money movement; the **cash cassette inventory** records physical notes. A Java object cannot make a network request and a physical motor action one atomic transaction. That gap is the central design lesson, not a reason to pretend all failures can be rolled back.

### Core implementation

Represent the session as states such as `IDLE`, `AUTHENTICATED`, `WITHDRAWING`, `RECONCILING` and `EJECTING_CARD`. Keep PIN validation in an adapter; never store the PIN on `Account` or print it in a trace. The ATM receives a limited authorization result, not a copy of the bank's security secrets.

For a ₹2,500 withdrawal with ₹500 and ₹100 notes, five ₹500 notes work when available. Greedy selection is not universally sufficient for arbitrary denominations and inventory constraints: with denominations 4 and 3 and amount 6, greedy takes 4 and gets stuck although 3+3 works. Use bounded change-making or a documented denomination policy.

```java
// Device boundary sketch: UNKNOWN is a first-class result.
```

The inventory update uses delivered counts, not requested counts. A partial report and an unknown report require different reconciliation procedures.

## 5. Detailed decisions, algorithms and failure behaviour

### Key abstractions

| Type | Responsibility |
|---|---|
| `ATM` | Context: holds the current `ATMState` and hardware components |
| `ATMState` | `Idle`, `CardInserted`, `Authenticated`, `TransactionSelected`, `OutOfService` |
| `CardReader`, `Keypad`, `Screen`, `Printer` | Hardware interfaces |
| `CashDispenser` | Chain: `Note2000Handler → Note500Handler → Note100Handler` |
| `BankService` | `authenticate`, `getBalance`, `debit`, `credit`, `reverse` |
| `Transaction` | `Withdrawal`, `Deposit`, `BalanceInquiry` (Command) |

```java
abstract class ATMState {
    void insertCard(ATM atm, Card c) { throw new IllegalStateException(); }
    void enterPin(ATM atm, String pin) { throw new IllegalStateException(); }
    void selectTx(ATM atm, TxType t) { throw new IllegalStateException(); }
    void ejectCard(ATM atm) { throw new IllegalStateException(); }
}
```

### Design decisions & trade-offs

**1. State pattern.** Each state overrides only the events it accepts. `Idle.insertCard` moves to `CardInserted`. `CardInserted.enterPin` either moves to `Authenticated` or counts a failure. Illegal actions fail loudly in one place.

**2. Chain of Responsibility for dispensing.**
```java
abstract class NoteHandler {
    NoteHandler next; int denom; int available;
    void dispense(int amount, Map<Integer,Integer> out) {
        int n = Math.min(amount / denom, available);
        if (n > 0) out.put(denom, n);
        int rest = amount - n * denom;
        if (rest > 0) { if (next == null) throw new CannotDispense(); next.dispense(rest, out); }
    }
}
```
Do a dry run first, and only debit if the plan succeeds. Adding a ₹200 note is one new handler.

**3. Debit and dispense consistency.** Order: plan the notes, then debit at the bank, then dispense. If the dispenser fails after the debit, call `bank.reverse(txId)` (a compensating transaction), and log for reconciliation. Use idempotent transaction IDs so retries don't double-debit.

**4. Security.** PIN verification happens at the bank, never locally. The ATM only sends an encrypted PIN block. Lock out after 3 failures.

### Ownership, boundaries and invariants

**Central design question:** Cash movement and account debiting form a recoverable protocol across hardware and banking systems.

AtmSession owns the authenticated interaction. AccountGateway authorizes debits; CashInventory records denomination counts; CashDispenser reports note movement through sensors. WithdrawalJournal persists operation IDs and uncertain outcomes. CardReader and PinVerifier are ports, not domain inheritance trees.

**Correctness rule:** Never report a successful withdrawal before both the debit outcome and dispensed cash are known. Note counts cannot become negative. A retried withdrawal identifier cannot debit twice.

```text
withdrawal(id,account_ref,requested_minor,dispensed_minor,authorization_ref,status); cassette(denomination,count,reserved)
```

### End-to-end execution trace

Authenticate with bounded PIN retries; select account and amount; reserve a feasible denomination combination; journal the intent; request bank authorization; dispense; persist the sensor result; settle or reverse the authorization using the same operation identity; print a receipt reflecting the known outcome.

### Concurrency and recovery walkthrough

Two withdrawal sessions compete for the last set of notes. Reserve note inventory atomically, release only the unconsumed reservation, and reconcile actual counts after partial dispense. Keep bank network calls outside the inventory lock.

### Policy choices and extension seams

Greedy denomination selection may fail when a valid combination exists; bounded search or dynamic programming can be used with cassette limits. State makes session progress explicit; Chain of Responsibility may select notes but must not hide insufficiency or partial movement.

### Edge cases that change the design

Power loss after cash leaves the dispenser but before a receipt needs durable recovery. A bank timeout means unknown, not safe-to-repeat. Never log PINs or card secrets. Partial dispense requires a specific compensation workflow, not a blind full refund.

**Topic-specific cases:** Insufficient denominations despite sufficient total cash; repeated withdrawal ID; bank timeout; jammed cassette; partial dispense; restart from each journal state.

### Further reading

- [Java 21 concurrency contracts](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) — synchronization and executor semantics.
- [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — database guarantees differ from process locks.

### Work through a partial delivery

W17 requests five ₹500 notes. Device evidence says three notes were delivered and two remained in a jammed cassette. The customer received ₹1,500. Record the exact reported counts and reconcile the ₹2,500 authorization according to the bank/device protocol; do not silently mark the entire withdrawal successful. Real settlement rules depend on the acquiring bank and hardware, so this is an educational boundary model rather than a certified ATM protocol.

Reserve a note plan before dispensing so another session cannot consume the same physical inventory. One machine may serialize withdrawals through a single session controller. The bank still needs its own atomic funds authorization because the same account can be used at other ATMs or for online payments.

On restart, inspect the durable withdrawal journal and device journal before accepting another withdrawal. If an operator refills or removes a cassette, record a cash-reconciliation event instead of overwriting counts without a trail. Availability is less important than avoiding an untracked second cash delivery.

## 6. Interviewer follow-ups

**Does `synchronized withdraw()` protect the bank account globally?** No. It only serializes callers using that JVM's object. The bank's ledger/authorization service owns global funds correctness.

**Should a dispenser timeout be retried with a new ID?** No. That can dispense twice. Query or reconcile the existing operation.

## 7. Closing answer

I model a withdrawal as a journalled operation across bank authorization and a physical dispenser. Exact note inventory and explicit COMPLETE/PARTIAL/NONE/UNKNOWN outcomes prevent the design from pretending that a software rollback can undo delivered cash. Recovery resolves the original operation before another dispense.

## Problem

Design a car rental system like Zoomcar or Hertz: customers search vehicles by location and date range, reserve them, pick up, return (possibly at another branch) and pay. The key challenges are **inventory availability over time ranges**, pricing as a **Strategy**, and vehicle creation with a **Factory**.

## Requirements

**Functional**
- Search available vehicles by branch, type and `[from, to]` range.
- Reserve, modify and cancel. Pick up and return, with mileage and fuel or charge recorded.
- Price by vehicle type, duration, add-ons (GPS, insurance), late fees and one-way drop.

**Non-functional**
- No overlapping reservations for the same vehicle.
- New vehicle categories and pricing rules plug in without changes to existing code.

## 1. Scope and chosen solution

I reserve a specific vehicle at a branch for a half-open time interval, then create a rental agreement at handover. Category-only overbooking is excluded from this version. Vehicle identity is stable; a reservation owns planned time, while an agreement owns actual pickup/return evidence and charges.

## 2. Contracts and allocation

```text
reserve(requestId,vehicleId,start,end,customerId,quoteId) -> Reservation
pickup(reservationId,inspection,odometer) -> RentalAgreement
returnVehicle(agreementId,inspection,odometer,now) -> FinalInvoice
Unavailable interval = [pickup, plannedReturn + preparationBuffer)
```

Under a vehicle allocation lock/transaction, I recheck interval overlap, validate the quote, and insert the reservation once. Overlap is `a.start < b.end && b.start < a.end`; checking only start dates is incorrect. PostgreSQL can enforce non-overlap for blocking states with an exclusion constraint using `tstzrange` and a GiST equality operator class for vehicle ID. All state changes that affect availability use that same authority.

Pickup changes CONFIRMED to ACTIVE and snapshots condition/fuel. Return records actual usage before marking PREPARING, then READY after inspection. At ₹1,800 per started 24 hours, 49 hours costs ₹5,400 before other stated charges. A late return creates a readiness conflict with the next reservation; the service allocates a replacement or flags an exception instead of treating the original promise as fulfilled.

`modifyReservation` locks the affected vehicle allocations, excludes the reservation's own interval from the overlap check, validates a replacement quote and commits the new interval only if it fits. A failed modification preserves the original allocation. Cancellation before pickup marks the reservation CANCELLED and releases its interval under the same authority. After pickup the operation is an early return against the active agreement, not deletion of the reservation; actual usage, fees and return condition remain recorded.

### Design decisions & trade-offs

**1. Availability is about time ranges, not a status flag.** A car can be free today and booked next week, so `status=AVAILABLE` is wrong. Store reservations per vehicle in a `TreeMap<LocalDateTime, Reservation>` keyed by start time. To check `[from, to)`, look at `floorEntry(to)` and see whether it ends after `from`. That is O(log n).

**2. Preventing double booking.** Synchronise per vehicle (lock striping with `ConcurrentHashMap<VehicleId, Object>`), then re-check overlap and insert. In a database this becomes an exclusion constraint (Postgres `tstzrange &&`) or a `SELECT … FOR UPDATE` on the vehicle row.

**3. Pricing composition.** Base Strategy (daily, hourly, surge) plus Decorators for add-ons (`InsuranceAddOn(GpsAddOn(DailyRate))`). Each piece is independently testable, and new add-ons don't touch existing classes.

**4. One-way rentals.** On return, the vehicle's branch changes. That affects future availability by location, so search must consider where the vehicle *will be* at `from`, not where it is now. Keep it simple: a vehicle is searchable at the branch of its last reservation's drop-off.

**5. Reservation as a State machine.** You can only pick up a `BOOKED` reservation within the grace window. Late return moves to `RETURNED` with a late-fee line item.

### Ownership, boundaries and invariants

**Central design question:** Availability is an interval constraint for a specific vehicle, not a boolean on a vehicle type.

Vehicle records asset identity and service status; VehicleType groups attributes. Reservation owns a half-open rental interval and quote. RentalAgreement records pickup/return inspection. PricingPolicy, EligibilityPolicy and PaymentPort express changing rules without duplicating lifecycle state.

**Correctness rule:** Confirmed reservations for the same vehicle must not overlap: existing.start < requested.end and requested.start < existing.end. Maintenance intervals also consume availability.


### End-to-end execution trace

Find suitable vehicles; quote with immutable dates and tariff; atomically reserve an available interval; authorize deposit; confirm; at pickup check licence and vehicle readiness; record odometer/fuel; at return calculate charges from recorded facts and close the agreement.

### Concurrency and recovery walkthrough

Two requests inspect the same free date range. Lock the vehicle schedule or use a database range exclusion constraint; checking then inserting without an authority is unsafe. Process vehicle locks in stable ID order for multi-vehicle reservations.

### Policy choices and extension seams

Assigning a concrete car early simplifies conflicts but reduces flexibility; booking a category requires capacity accounting and later assignment. A policy should calculate fees while the agreement aggregate owns legal transitions.

### Edge cases that change the design

Back-to-back rentals require turnaround time. Time zones and daylight-saving changes affect displayed pickup times; store instants plus location zone. Late returns may conflict with later reservations and require reallocation rather than silently extending a booking.

**Topic-specific cases:** Overlap detection; boundary-touching intervals; maintenance block; deposit timeout; late return; duplicate pickup; pricing across a daylight-saving boundary.

**Where does a damage charge belong?** On the rental's return inspection/adjustment record, linked to evidence and a pricing rule, not on all future bookings for that car.

## 7. Closing answer

I keep future reservation promises separate from actual rentals. Vehicle interval allocation includes preparation time, pricing is frozen in the accepted quote, and return inspection determines readiness. That preserves history and makes late-return conflicts visible instead of silently double-booking the next customer.
