## Problem

Design a two-player game of chess as an object model in Java. The exercise asks for classes, relationships and the rule engine, not a UI or an AI opponent. The real test is whether piece behaviour, game state and move validation each live in the right place, and whether the design survives follow-ups like "add undo" or "add a chess clock".

## Requirements

**Functional**
- 8×8 board, standard initial setup, two players (White moves first).
- Validate a move for the piece type and the board state: blocking pieces, captures, and not leaving your own king in check.
- Special moves: castling, en passant, pawn promotion.
- Detect check, checkmate and stalemate. Also support resignation and draw by agreement.
- Keep a move history (needed for en passant, castling rights, and undo).

**Non-functional / scope**
- Single process, in-memory. No persistence, no networking.
- Extensible: new variants (Chess960, a different promotion rule) shouldn't need edits all over the codebase.

## 1. Scope and chosen solution

I am designing a standard two-player chess engine in one JVM. The public operation is `makeMove(playerId, expectedVersion, from, to, promotion)`. I include special moves, check/checkmate, stalemate, resignation and draw agreement. Network matchmaking and a computer opponent are outside this engine. A complete tournament-rules extension also needs the specific claimable and automatic draw rules; I do not equate an incomplete rule subset with full FIDE compliance.

I choose composition: immutable `Piece(kind, side)` values, one `PositionState`, and movement policies selected by kind. `Game` owns the current position and history. `AttackMap` computes attacked squares directly; it does not call legal-move generation recursively. This lets a pinned enemy piece still contribute attacks under chess rules.

## 2. Public contract and commit algorithm

```text
makeMove(playerId, expectedVersion, Move) -> Accepted(position, version)
Errors: WrongPlayer, StaleVersion, InvalidSquare, IllegalMove, GameFinished

Under the per-game lock:
  verify version, active result and player's turn
  validate pseudo-legal geometry and special-move preconditions
  copy the complete position and apply all move effects
  reject if moving side's king is attacked in the trial
  store before-position in history; commit trial and increment version
  evaluate opponent's legal replies; set checkmate/stalemate if applicable
```

For e2–e4, the board changes, the en-passant target becomes e3 and Black receives the turn in one accepted transition. A rejected request leaves every field and version unchanged. A copy touches 64 squares; a simple all-piece legal-reply scan is acceptable here. Per-game serialization prevents two moves against version 12 both becoming position 13. Separate games use separate locks. Undo restores the entire saved position, including rights and counters, rather than merely moving the piece backward.

I start with **one in-memory game**, two human players and no network. A *value object* represents a value, such as square a1; an *entity* has an identity, such as this particular game. An *invariant* is a rule that must hold after every accepted move. Here, one invariant is that the moving side's king is not attacked after the move.

### Core implementation

Represent the board with 64 squares. Use immutable `Piece(kind, colour)` values and keep castling rights and en-passant target in `PositionState`, rather than mutating shared piece objects. A shallow board copy is safe only when its elements are immutable. Avoid bitboards until you can explain and test the array version.

```java
// Domain algorithm sketch; rules and types are supplied by the game engine.
MoveResult tryMove(PositionState live, Move request) {
    requireCorrectTurn(live, request);
    requirePseudoLegal(live, request);
    PositionState trial = applyToCopy(live, request);
    if (attacked(trial, trial.kingOf(live.turn()), live.turn().opponent()))
        return MoveResult.illegal("King would remain in check");
    return MoveResult.accepted(finishTurn(trial));
}
```

Notice that attack detection must not recursively ask whether the attacker can make a legal move: that would ask about its king, then the other king, indefinitely. Implement attack geometry directly, including pawn diagonals, king adjacency and sliding-piece blockers.

## 5. Detailed decisions, algorithms and failure behaviour

### One coherent ownership model

| Type | Owns or computes | Why it is separate |
|---|---|---|
| `Game` | Current position, version and committed history | All public moves pass through one transition authority |
| `PositionState` | Board, turn, castling rights, en-passant target and counters | A trial position must include every rule-relevant value |
| `Square` | Validated file and rank | Invalid coordinates fail before board access |
| `Piece` | Immutable kind and colour | Copies cannot share accidentally mutable `hasMoved` state |
| `Move` | From, to and optional promotion choice | A request is not yet an accepted board mutation |
| `MoveGenerator` | Pseudo-legal movement and occupancy | Piece geometry remains testable without turn orchestration |
| `AttackMap` | Attacks on a square in a specified position | King safety must not recursively depend on legal move generation |
| `HistoryEntry` | Before-position or exact reversible delta | Undo restores rights and counters as well as pieces |

This chapter chooses immutable pieces and copied trial positions. A mutable piece hierarchy with `hasMoved` can also be designed, but then board copies must deeply copy those pieces and undo must restore their flags. Do not mix the two strategies accidentally. In the chosen model, castling rights are explicit position data, not inferred only from where a rook currently stands.

```java
enum Side { WHITE, BLACK }
enum Kind { KING, QUEEN, ROOK, BISHOP, KNIGHT, PAWN }
record Piece(Kind kind, Side side) {}
record Square(int file, int rank) {
    Square {
        if (file < 0 || file >= 8 || rank < 0 || rank >= 8)
            throw new IllegalArgumentException("Outside the board");
    }
}
record Move(Square from, Square to, Kind promotion) {}
```

These value definitions are complete Java fragments; the move algorithm still needs a rules engine and immutable/copying board implementation. Promotion validation allows only QUEEN, ROOK, BISHOP or KNIGHT on a qualifying pawn move. A null promotion means no promotion was requested, not permission to bypass the rule.

### Generate candidates, then establish legality

A rook ray walks one square at a time in each orthogonal direction. Empty squares are candidates; the first opposing piece can be captured, then the ray stops; a friendly piece stops it without becoming a destination. A knight checks a fixed set of offsets and does not inspect intervening squares. A pawn's forward movement and attack diagonals are different rules.

After constructing the trial, find the moving side's king and evaluate the opponent's attacks. Kings are never actually captured to determine victory. If the position is legal, commit the trial, change turn and evaluate the next side. An attacked king with no legal replies is checkmate; no legal replies without attack is stalemate. Check itself is a property of an active position, not a terminal state.

### Choose copying before optimizing make/unmake

An array copy touches 64 squares. For a teaching engine this is easy to inspect and cheap enough to begin with; do not claim a measured speed without benchmarking. Search engines exploring millions of positions may prefer compact bitboards and make/unmake deltas, but that optimization introduces more restoration paths.

For history, a full before-position is simpler than a compact reversible delta. A delta must store captured piece and capture square, original pawn for promotion, rook movement for castling, prior castling rights, prior en-passant target, prior halfmove counter and prior side. One missing field can make undo appear correct on screen while changing the next legal moves.

### Draws need an explicit scope

The beginner engine supports stalemate, resignation and draw by agreement. A fuller ruleset distinguishes claimable repetition/fifty-move draws from automatic conditions and includes dead positions. Do not call the engine a complete tournament implementation until those rules are specified and tested. Repetition identity needs the side to move and relevant castling/en-passant rights, not just piece placement.

### Local correctness and a network extension

In one JVM a per-game lock can surround expected-version validation and commit. A separate game should not block unrelated games. For multiple writing servers, move that decisive version check into a shared transactional authority. Keep clocks, sockets and persistence out of piece geometry so a deterministic rules test does not require a running server.

For further reading, use the [Java 21 value and concurrency APIs](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/package-summary.html) for implementation mechanics and the [FIDE Laws of Chess](https://handbook.fide.com/chapter/e012023) for game semantics. A programming API is not a source of chess rules.

### Work through the boundary cases

After e2–e4, record e3 as the en-passant target for the immediately following turn. A later move clears that right. Undo must restore the previous target, castling rights, halfmove clock, captured piece and side to move—not just move a piece backward.

Castling requires more than a safe destination: the king cannot start in check or cross an attacked square. For en passant, remove the captured pawn before checking king safety; that removal can uncover a rook attack. Promotion changes piece kind as part of the same move and must support a knight, bishop or rook as well as a queen.

For a network extension, accept `gameId`, `expectedVersion` and a client move identity. Two moves using version 12 cannot both advance the game to version 13. A per-game lock works in one JVM; a database version condition is needed when multiple servers can write the same game. Keep network synchronization outside pure chess-rule evaluation.

## 6. Interviewer follow-ups

**White king e1, White rook e2, Black rook e8: can White play Re2–f2?** No. The rook has a geometrically valid move, but the resulting position exposes the king along the e-file.

**Is no legal move always checkmate?** No. If the side to move is not attacked, it is stalemate. Checkmate needs both an attacked king and no legal reply.

## 7. Closing answer

I would keep one versioned Game as the mutation boundary, immutable pieces inside a copied PositionState, separate geometric move generation from attack detection, and commit only a king-safe result. Exact position snapshots make undo reliable. I would optimize representation only after the legal-move tests pass.

## Problem

Design a URL shortener like bit.ly or TinyURL. Given a long URL, return a short alias such as `https://sho.rt/aZ3kQ9`. Visiting the alias redirects to the original URL. The interview usually centres on **ID generation**, **read-heavy scaling** and **data modelling**.

## Requirements

**Functional**
- `POST /urls {longUrl, customAlias?, expiresAt?}` returns `shortUrl`.
- `GET /{code}` returns an HTTP redirect to `longUrl`.
- Optional: custom aliases, expiry, per-link click analytics, and deleting your own links.

**Non-functional**
- Very read-heavy, around **100:1** reads to writes.
- Redirect latency of **< 50 ms p99**, and high availability (a broken short link is a broken link everywhere).
- Codes must be unique, short, and **not trivially enumerable** if links are private.

**Back-of-envelope (state assumptions out loud)**
- 100M new URLs/month ≈ **40 writes/s** on average. At 100:1 that is **≈ 4,000 redirects/s**, with peaks around 10–20k/s.
- 5 years × 1.2B/yr = **6B records**. At ~500 bytes each that is **≈ 3 TB**, which fits on a sharded KV store easily.
- Code length: base62 gives 62⁶ ≈ 56.8B and 62⁷ ≈ 3.5T. **7 characters** leaves plenty of headroom.

## 1. Scope, assumptions and selected architecture

I support creation, redirect, custom aliases, expiration and owner deletion. I choose random seven-character Base62 with a database uniqueness constraint, PostgreSQL initially, Redis cache-aside when read load warrants it, and asynchronous click analytics. A single authoritative write region avoids multi-writer alias conflicts. The detailed sizing below uses 100 million creations/month and a 100:1 redirect ratio as interview assumptions, not measured traffic.

## 2. API and authoritative records

```text
POST /urls {longUrl,customAlias?,expiresAt?} + Idempotency-Key -> 201 {code,shortUrl}
GET /{code} -> 302 Location; absent/expired -> documented 404/410 policy
DELETE /urls/{code} + owner identity -> 204 or denied
url_mapping PK(code): long_url, owner_id, expires_at, active, version
create_request UNIQUE(owner_id,key): payload_hash, code, committed_result
```

Creation validates input, allocates a candidate, and atomically persists mapping plus request result. A collision retries with a new random candidate; an alias conflict returns 409. Redirect checks cached expiry/status, uses the authoritative database on a miss, and publishes analytics outside the response dependency. Cache population failure after a database commit does not undo creation. I choose a documented bounded revocation window unless the product requires an authoritative status check; TTL by itself is not immediate revocation. The architecture, exact calculations and race analyses below complete these choices.

#### Create

`302` is often preferable when links may change or be revoked. A `301` is suitable for truly permanent redirects but can be aggressively cached by browsers. The cache policy must match expiry and revocation guarantees.

Other endpoints: `GET /urls/{code}` for metadata, `DELETE /urls/{code}` for owned links, and `GET /urls/{code}/stats` for analytics.

### 5. Short-code generation

#### Option A: Database sequence + Base62

Allocate a unique integer from a database and encode it in Base62.

**Pros:** straightforward uniqueness, easy implementation. **Cons:** centralized allocation unless ranges are leased; sequential codes are predictable.

#### Option B: Random Base62

Generate a cryptographically secure random code and insert it with a unique constraint. Retry on collision.

- Six characters: `62^6 ≈ 56.8 billion` possibilities.
- Seven characters: `62^7 ≈ 3.52 trillion` possibilities.
- Random generation **does not eliminate collisions**; the unique insert is essential.
- A larger namespace or longer code reduces collisions as the number of records grows.

**Pre-generated code pool:** Generate codes ahead of time, deduplicate them, and reserve each code **atomically** from a pool when creating a link. This removes collision handling from the request path, but collision detection still happens during pool preparation, and the pool needs replenishment and reliable allocation. An atomic `pop`/claim and durable assignment prevent two workers from using the same code.

#### Option C: Snowflake-like distributed ID + Base62

A common 64-bit layout reserves one sign bit and uses:

```text
| unused sign: 1 | timestamp: 41 | worker ID: 10 | sequence: 12 |
```

- **Timestamp:** milliseconds since a custom epoch.
- **Worker ID:** identifies the generator; 10 bits allow 1,024 IDs for workers.
- **Sequence:** counter within one millisecond on one worker; 12 bits allow 4,096 values (0–4095).

```text
timestamp + unique worker ID + per-millisecond sequence
    -> bit-field ID -> Base62 encoding -> URL code
```

Two workers may use the same timestamp and sequence because their worker IDs differ. On one worker, the sequence increments within a millisecond and resets when the millisecond advances. On sequence exhaustion, wait for the next millisecond rather than wrapping. Handle clock rollback and worker-ID leasing safely.

**Why 12 bits, not 10 or 15?** It's a trade-off in a fixed bit budget:

| Sequence bits | IDs/ms/worker | Worker bits if timestamp stays 41 | Worker IDs |
|---|---:|---:|---:|
| 10 | 1,024 | 12 | 4,096 |
| 12 | 4,096 | 10 | 1,024 |
| 15 | 32,768 | 7 | 128 |

These are theoretical allocation capacities, not real hardware throughput guarantees. For this URL shortener's ~40 average writes/s, even 10 sequence bits is ample; 12 is a conventional balanced default.

**Caveats:** A full Snowflake-style numeric ID can require up to **11 Base62 characters**, not always seven. Base62 is encoding, **not encryption**: raw Snowflake codes may be enumerable. Use a keyed reversible permutation or a random-code approach if enumeration resistance matters.

### 6. Data model

```sql
CREATE TABLE url_mapping (
    code        VARCHAR(16) PRIMARY KEY,
    long_url    TEXT NOT NULL,
    user_id     BIGINT,
    created_at  TIMESTAMP NOT NULL,
    expires_at  TIMESTAMP,
    is_active   BOOLEAN NOT NULL DEFAULT TRUE
);
CREATE INDEX idx_url_mapping_user ON url_mapping(user_id, created_at);
```

- Lookup key: `code`.
- Store expiry/status alongside the destination so the redirect path can validate them.
- Keep click aggregates outside the mapping row to avoid write contention.
- A relational DB (PostgreSQL) is convenient for ownership and transactions; a distributed KV store (e.g., DynamoDB) is a natural fit for massive primary-key lookups. Choose based on operational constraints and required consistency.

#### Sharding

A simple conceptual routing rule is `hash(code) % shardCount`; a production system may use consistent hashing, virtual shards, or the distributed database's native partitioning. Naively changing `shardCount` with modulo requires substantial remapping.

### 7. Primary, replicas, and consistency

**Write:** API → authoritative primary/write path → commit → cache populate/invalidate → response.

**Read:** API → Redis → if miss, database read → validate expiry/status → cache → redirect.

Read replicas increase capacity but can lag. Immediately after creation, a cache miss routed to a stale replica may incorrectly return `404`. Mitigate through write-through cache population, primary reads for recent codes, replication-position tracking, or database consistency options.

An HTTP load balancer does not ordinarily choose database primary versus replica: the database client, proxy, or repository/routing layer does that. Async replication can also lose recently acknowledged writes during failover unless the durability policy is strong enough.

### 8. Redis cache-aside

Example cache entry:

```text
key:   url:aZ3kQ9p
value: {longUrl: "https://example.com/...", expiresAt: null, isActive: true}
TTL:   3600 seconds (illustrative)
```

```text
GET /code -> Redis lookup
  hit -> validate expiry/status -> redirect or reject
  miss -> database -> validate -> populate cache -> redirect or reject
```

- Cache hot mappings, not necessarily all historical records.
- Use short negative caching for nonexistent codes, with invalidation on creation.
- Avoid stampedes with request coalescing, jittered TTLs, and bounded database fallback.
- Deletions and expiry need invalidation and expiry checks; TTL alone cannot guarantee immediate revocation.
- Redis replicas can be stale, so read-routing policy matters for recently changed links.

### 9. Detailed creation flow

1. Client sends `POST /urls` with long URL and optional alias/expiry.
2. Gateway routes to any healthy stateless instance.
3. Service validates URL scheme (`http`/`https`), length, abuse rules, auth, and tier limits.
4. Generate a code or validate a custom alias.
5. Atomically persist mapping; uniqueness constraint prevents duplicate aliases.
6. Populate/invalidate cache after successful commit.
7. Return `201 Created` and the short URL.

If Redis is unavailable, creation may still succeed if durable storage committed and database fallback is supported. Use idempotency keys to handle timeouts after commit.

### 10. Detailed redirect flow

1. Client requests `GET /{code}`.
2. Service validates the code and checks Redis.
3. On hit, validate active/expiry status and redirect.
4. On miss, fetch authoritative mapping from the correct shard, avoiding stale replicas when necessary.
5. Cache valid mapping and return `302 Location`.
6. Publish click analytics asynchronously, without waiting on analytics availability on the normal redirect path.

Return a consistent `404` or `410` for absent, expired, or revoked links according to product policy.

### 11. Asynchronous click analytics

```text
URL service -> 302 response -> Browser
URL service -> asynchronous click event -> Kafka -> Consumer -> Analytics store
```

Example event:

```json
{"eventId":"evt-123","code":"aZ3kQ9p","timestamp":"2026-10-15T10:00:00Z","referrer":"https://example.org","country":"IN","deviceType":"mobile"}
```

Avoid synchronous increments on the primary mapping row. Analytics can be best-effort or use durable buffering/outbox for stronger delivery guarantees. Kafka consumers should handle duplicate delivery if accurate counts matter. Minimize personal-data collection.

### 12. Expiration, deletion, and cache invalidation

- Enforce expiry at read time; background cleanup is for storage hygiene, not correctness.
- On delete: authorize owner → mark inactive/delete in DB → invalidate Redis → purge CDN if used.
- Immediate revocation may require stronger cache invalidation or status checks than a long TTL provides.
- A stale CDN/browser-cached permanent redirect can undermine deletion guarantees.

### 13. Availability and failure scenarios

| Failure | Expected behavior / mitigation |
|---|---|
| API instance fails | LB removes unhealthy node; other stateless nodes continue |
| Redis shard fails | Replica failover or bounded DB fallback; prevent DB stampede |
| Replica lags | Use primary/consistent reads for new or recently modified mappings |
| Primary fails | Failover; durability depends on replication/ack policy |
| Kafka unavailable | Redirect continues; buffer or drop analytics per product guarantee |
| Region fails | Global routing to healthy region; replication/RPO/RTO must be explicit |
| Cache cold | Controlled warm-up, request coalescing, DB concurrency limits |

I start with one authoritative write region, multi-AZ database replication, and regional caches. Multi-region active-active writes add uniqueness and conflict-resolution complexity.

### 14. Latency budget and observability

Illustrative cache-hit budget, **not a performance guarantee**:

| Stage | Target |
|---|---:|
| Gateway/routing | 5 ms |
| Service processing | 3 ms |
| Redis lookup | 2 ms |
| Response processing | 5 ms |
| Network/other overhead | 10 ms |
| **Illustrative total** | **25 ms** |

A database cache miss adds latency. Measure p50/p95/p99 separately for cache hits and misses, cache hit ratio, DB lookup p99, replication lag, Kafka lag, errors, and hot-key skew. Connection pooling, request coalescing, and avoiding synchronous analytics help meet the `<50 ms p99` target.

### 15. Security and abuse prevention

- Allow only appropriate URL schemes; reject dangerous schemes and malformed input.
- Scan malicious destinations and enforce creation rate limits.
- Authenticate owners for link edits/deletes; unguessable codes do **not** replace authorization.
- Protect against enumeration, spam, and abusive redirect chains.
- Limit collection/retention of IP-derived data and referrers.

### 16. Architecture trade-offs

| Decision | Trade-off | Starting choice |
|---|---|---|
| ID generation | Random+unique constraint vs distributed numeric ID | Random for compact, hard-to-guess codes; Snowflake for decentralized allocation |
| Persistence | Relational vs distributed KV | KV for simple massive code lookups; relational when transaction/ownership features dominate |
| Caching | Speed vs staleness/revocation | Redis cache-aside, explicit invalidation |
| Analytics | Latency vs delivery reliability | Async stream, explicit best-effort/durable policy |
| Redirect status | 301 cacheability vs 302 flexibility | 302 for revocable/editable links |
| Regions | Simple single writer vs multi-writer complexity | Single authoritative write region initially |

#### Final memory aid

1. **Generate** a unique code.
2. **Persist** the mapping durably.
3. **Cache** hot mappings for read-heavy redirects.
4. **Route** reads/writes with consistency in mind.
5. **Stream** analytics outside the hot path.
6. **Survive** failures without losing acknowledged links.

# Grokking-style improvements: Interview-ready extension

> This extension uses a progressive, trade-off-driven teaching structure. It is original material, not a reproduction of any proprietary course.

### 19. Clarifying questions and scope

Ask the interviewer before drawing boxes:

1. Can links be edited or deleted? If yes, prefer temporary redirects and plan cache invalidation.
2. Are custom aliases and expirations required? They affect uniqueness and metadata.
3. Is analytics best-effort or guaranteed? It determines whether durable buffering is necessary.
4. Is the service global? Specify whether 50 ms p99 is measured at the edge, service, or end-to-end.
5. Must codes resist enumeration? Sequential/Snowflake-derived codes alone do not provide that property.

**In scope:** create and resolve URLs, optional expiry/custom aliases, basic analytics. **Out of scope for MVP:** billing, advanced campaign analytics, QR generation, branded domains, and complex moderation dashboards.

### 20. Capacity model: traffic, bandwidth, cache and storage

Use the original assumptions: 100M new URLs/month, 100:1 redirects to creates, 500 bytes per logical mapping, 5-year retention.

| Quantity | Derivation | Approximate result |
|---|---|---|
| Average writes | 100M / (30×86400) | 38.6/s |
| Average reads | 100×38.6 | 3,860/s |
| Peak reads | Assumed 5× average | ~19,300/s |
| Logical mapping storage | 6B×500 B | 3 TB decimal |
| Replicated mapping bytes | 3× logical | 9 TB, before indexes, logs, headroom |
| Write ingress | 38.6×1 KB/request (assumption) | ~39 KB/s |
| Redirect egress | 3,860×0.5 KB/response (assumption) | ~1.9 MB/s |
| Cache for 10M hot mappings | 10M×~300 B/cache entry (assumption) | ~3 GB raw; provision more for Redis overhead and replicas |

These numbers are **illustrative**: actual payloads, hot-set size, network egress, and Redis memory amplification must be measured. At a 95% cache hit rate, ~3,860 reads/s produces ~193 database reads/s on average; at 99%, ~39/s. A 20k/s peak produces ~1,000 DB reads/s at 95% hit rate.

### 21. Build the architecture incrementally

#### Stage 1 — Correct MVP

```text
Client -> URL API -> Primary database
```

A single service and indexed database can comfortably support an MVP. Generate unique codes, persist atomically, then return them. Keep the initial design simple and measure first.

#### Stage 2 — Optimize the read-heavy path

```text
Clients -> Load balancer -> Stateless URL services
URL services -> Redis cache
URL services -> Durable mapping store
```

Use Redis cache-aside to serve popular redirects. The database remains the source of truth. Protect the database when Redis fails or a hot key expires.

#### Stage 3 — Partition, replicate, and isolate analytics

```text
Clients -> Regional routing -> URL services -> Regional cache
URL services -> Partition router -> Shard primaries -> Replicas
URL services -> Event stream -> Analytics consumers
```

Sharding is a **later-stage scaling decision**, not a requirement merely because a system has many users. Define the threshold (data volume, write throughput, availability, operational needs) that would trigger it.

### 22. Code-generation decision: numbers and edge cases

**Random Base62:** With an alphabet of 62 characters, 7-character codes have ~3.52 trillion possibilities. The approximate probability of at least one collision across *n* independently sampled codes is `1 - exp(-n(n-1)/(2N))`, where `N=62^7`. At 100 million generated codes, a collision somewhere is effectively certain; that does **not** mean every request has a high collision risk. Near 100M occupied codes, the next random draw collides with probability about `100M / 3.52T ≈ 0.00284%`, assuming uniform distribution. Enforce a unique constraint and retry.

**Pre-generated pool:** Reserve codes atomically and replenish in advance. Define what happens when a reservation succeeds but the mapping write fails: return the code to the pool only when safe, or accept wasted codes. Avoid relying on an ephemeral queue as the sole record of reserved identifiers.

**Snowflake-like IDs:** Decentralized and collision-free only if worker IDs are unique and clocks/sequence rollover are correctly handled. A 63-bit positive value needs up to 11 Base62 characters. For a product that prioritizes very short, difficult-to-guess links, random 7–8 character codes may be preferable. For distributed generation and roughly time-ordered IDs, Snowflake is attractive.

**Recommendation for this workload:** I start with random Base62 + unique insert, or a well-managed pre-generated pool if tail latency from retries is a concern. Choose Snowflake when distributed ID generation is a strong operational requirement; don't claim it inherently yields shorter codes.

### 23. Partitioning and resharding

A partition key of `hash(code)` balances mapping records when codes are well distributed. Never use raw timestamp as the partition key: time-ordered IDs can create hot write partitions. A **virtual-shard directory** (`hash(code) → virtual bucket → physical shard`) lets operators move buckets gradually without changing client-visible codes.

**Migration outline:** allocate destination shard → copy historical rows → stream or dual-write changes with ordering guarantees → validate checksums/counts → atomically switch bucket ownership → retain rollback window → retire old copies. A shard migration is an operational workflow, not just a hash function.

### 24. Consistency and race-condition walkthroughs

**Create then immediate redirect:** An acknowledged write may not yet exist on a read replica. Read from the primary for new keys, use a consistent database option, or populate the cache after commit while retaining a primary fallback. Do not depend exclusively on best-effort cache population.

**Delete versus cache fill:** Reader misses Redis and fetches an active mapping; owner deletes it; reader then repopulates Redis with stale data. Mitigate with versioned cache entries/tombstones and conditional writes, or accept a bounded revocation window explicitly.

**Custom alias races:** Two users submit the same alias simultaneously. A unique database constraint (or atomic conditional put) is the authority; an application-level availability check is not sufficient.

**Idempotent create:** Store the `(user, idempotency key) → result` relation durably, with a payload hash and expiry. Repeated requests return the original result; the same key with a different payload should be rejected.

### 25. Hot keys, cache stampedes, and regional resilience

A viral link can dominate requests. Redis cluster throughput does not guarantee one popular key spreads across shards. Options include edge/CDN caching for links with safe caching policies, request coalescing, local short-lived in-process caching, and replication. Each adds a revocation-versus-speed trade-off.

**Failure policy:** Redis down → bounded DB fallback with circuit breakers and concurrency caps; Kafka down → continue redirects while buffering/dropping analytics according to product requirements; regional failure → fail over to a region with sufficiently fresh data. State **RPO** (acceptable data loss) and **RTO** (recovery time), rather than saying merely “high availability.”

### 26. SLOs and practical verification

- **Availability:** e.g., 99.95% successful redirect requests monthly (example target).
- **Latency:** service-side p99 under 50 ms, measured separately for cache hits and misses; end-to-end browser time includes network and DNS.
- **Correctness:** zero duplicate custom aliases; expired/revoked links do not redirect beyond the documented consistency window.
- **Durability:** acknowledged creates survive the documented failover scenarios.

**Load-test matrix:** normal 4k redirects/s, peak 20k/s, 1 hot code receiving a large fraction of traffic, Redis node loss, cold-cache restart, primary failover, replication lag, and Kafka outage. Measure error rate, DB saturation, cache hit ratio, p99, and stale redirects.

### 27. Interviewer follow-ups with concise answers

**Why not use the database auto-increment key?** It is perfectly acceptable at MVP scale; central allocation or range leasing becomes relevant only when the write path or operational topology requires it.

**Why 302 instead of 301?** A 302 avoids permanently caching a redirect that may later change or be revoked. Cache headers and clients still matter.

**Can a cache hit return an expired URL?** Not if the cache entry includes expiry and the application validates it before redirecting. Revocation is harder because invalidation can race.

**Do you need Kafka to return redirects?** No. Click tracking must not sit on the critical path. Kafka is an optional asynchronous analytics pipeline.

**How do you choose SQL vs NoSQL?** The key-value access pattern suits either. Choose based on transactional needs, operating model, scaling characteristics, consistency and cost—not on a generic claim that SQL cannot scale.

**How do you avoid collisions?** For random codes use atomic unique inserts and retry; for pre-generated codes reserve atomically; for Snowflake ensure worker-ID uniqueness and safe clock handling.

**What would you implement first?** One stateless API, a durable indexed store, secure random code generation with a uniqueness constraint, and basic metrics. Add Redis after profiling the redirect workload.

### 28. A more effective 45-minute interview narrative

1. **0–5 minutes:** clarify mutable links, custom aliases, expiry, analytics guarantees, and global scope.
2. **5–10 minutes:** calculate read/write QPS, five-year storage, and choose a realistic p99 definition.
3. **10–18 minutes:** present MVP APIs, schema, and ID generation; explain why the first design is simple.
4. **18–28 minutes:** add Redis, replication, and partitioning only as scaling pressures arise.
5. **28–38 minutes:** deep dive into collision safety, stale replicas, delete/cache races, and viral hot keys.
6. **38–45 minutes:** failures, multi-region RPO/RTO, observability, and a final trade-off summary.

**Closing sentence:** “I would start with a simple durable mapping service, use Base62 for compact codes, scale the read path with caching, and add partitioning and regional resilience as measured traffic and availability needs justify them.”

## Problem

Explain how a language model processes a request, then design a small private-document assistant that answers with evidence and acknowledges missing evidence. Separate model behavior from application-owned storage, permissions and tools.

## Requirements

- Explain tokens, context, attention, training, inference and model limitations.
- Account for context budget, latency and cost with explicit assumptions.
- Distinguish prompting, retrieval, fine-tuning, memory, tools and agents.
- Translate concepts into Java/Spring application boundaries and measurable exercises.
- Preserve tenant isolation and never treat fluent text as proof of truth or authority.

## 1. Complete conceptual answer and selected application

A language model estimates a distribution for the next token conditioned on earlier tokens. Training adjusts weights to reduce prediction error; inference uses those weights without learning each submitted conversation into them. Tokenization maps text to model-specific IDs, embeddings represent those IDs numerically, and transformer layers mix context before the output head produces vocabulary scores.

In attention, queries and keys produce scaled scores `QKᵀ/√d`; softmax weights combine values V. A causal mask prevents an autoregressive position from reading future tokens. This explains contextual representation, not guaranteed reasoning or factual truth. During decoding the selected token is appended and the process repeats until a stop/limit. KV caching reuses intermediate attention state; it is not the application's persistent user memory.

I apply this to a private-document assistant: the application authenticates, selects permitted context, budgets tokens, invokes the model and validates evidence. The same model can discuss public Java concepts but cannot know yesterday's private policy unless authorized evidence is supplied.

## 2. Request contract and budget

```text
Ask(question,conversationId) -> Answer(text,sourceIds,abstained,usage)
Prompt = task instructions + selected history + question + permitted evidence
Illustrative total allowance 16000:
  output 2000 + instructions 1000 + history 3000 + question/margin 1000
  leaves 9000 tokens for evidence under this simplified accounting
```

The context limit and tokenizer depend on the model; tokens are not fixed words/pages. I count with the configured tokenizer where supported and account for provider-specific reasoning/caching categories. Missing evidence produces abstention, not an invented policy. Prompting changes request context, retrieval supplies documents, tools fetch live facts, and fine-tuning changes weights for learned behaviour; these are distinct mechanisms. Exact eligibility/financial arithmetic stays in deterministic Java services.

## 5. Detailed decisions, algorithms and failure behaviour

### Mechanism and rationale

**Design question:** Why can a fluent model answer a public question but invent the answer to a private company-policy question?

Training changes weights; inference conditions on the supplied context without updating those weights. Tokenization maps text to model-specific integer units. Transformer attention mixes information across token positions; autoregressive decoding predicts successive tokens. A KV cache reuses intermediate attention state but is neither an editable business database nor permanent conversation memory.

### Architecture and contracts

```text
User question -> authenticated context builder -> token budget -> model request -> streamed draft -> grounding/validation -> answer with evidence or explicit abstention

Application contracts (design outline):
AskRequest(question,conversationId); Answer(text,citations,abstained); Usage(inputTokens,outputTokens,modelVersion)
```

ChatClient performs model calls; an application-owned context builder enforces identity and budgets before it calls the client. Store conversation history explicitly, separate from model weights and provider caches.

### Worked reasoning and capacity example

For an illustrative 16,000-token window, reserve 2,000 output + 1,000 instructions + 3,000 history + 1,000 safety margin, leaving 9,000 retrieval tokens. Ten million vectors x 768 dimensions x 4 bytes is 30.72 GB of raw float32 values, not the complete index size.

### Java and Spring AI implementation outline

```java
record Budget(int context, int instructions, int history, int output, int margin) {
  int evidence() {
    int left = context - instructions - history - output - margin;
    if (left < 0) throw new IllegalArgumentException("Context budget exceeded");
    return left;
  }
}
```

### Design decisions and alternatives

Use ordinary rules for exact eligibility checks, retrieval for changing private documents, tools for current authoritative facts, and a bounded agent only when the next step genuinely depends on prior results. A larger context is not a guarantee that the model will use every fact correctly.

### Failure scenario and safe recovery

The model gives a confident answer unsupported by the retrieved policy. Treat fluency as unrelated to evidence. Require source identifiers and check that cited passages support the claim; abstain when missing. An embedding score is not a calibrated probability of truth.

### Security, privacy and provenance

AI, machine learning, deep learning and generative modelling are related categories, not one perfect universal nesting diagram. Not every language model is a Transformer, and not every generative model is a language model.


**Verification criteria:** Compare a prompt-only baseline with grounded answers on known, missing and adversarial questions. Track supported-answer rate, abstention precision, context overflow, first-token latency and token usage.

### Separate the mechanisms before combining them

| Need | First mechanism to consider | What it does not establish |
|---|---|---|
| Explain a general concept | Prompted model response | Factual correctness |
| Answer from changing private documents | Authorized retrieval plus evidence | Automatic permission or truth |
| Read current order status | Narrow application tool | Permission from the model |
| Preserve prior conversation | Application-owned memory | Weight updates or infinite context |
| Adapt recurring behaviour/style | Prompting, then evaluate fine-tuning if justified | Fresh private facts by default |

I begin with a stub model that returns a fixed answer so request validation and UI states can be tested without inference. Then add a real model and compare grounded answers on a versioned set of questions. Arithmetic and authorization remain deterministic application work.

## 6. Interviewer follow-ups

**If the model remembers your name in the same conversation, did its weights change?** Usually no. The application/provider likely included relevant history or stored memory.

**Does temperature zero prove truth?** No. It changes sampling; systematic unsupported answers can remain.

## 7. Closing answer

I explain an LLM as a trained conditional sequence model, then keep private facts, permissions and exact calculations in application-owned systems. Tokens, context and sampling explain generation; retrieval and tools supply missing evidence. Fluent continuation is never itself proof of a business fact.
