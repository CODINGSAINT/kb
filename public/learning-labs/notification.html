    Timeout after acceptance

    1. A ready delivery is claimed at epoch1; a fresh preference gate authorizes one immutable provider request.
    2. The fake provider accepts once, then returns a simulated timeout. Locally the state is RETRY_WAIT with uncertainty; externally one acceptance exists.
    3. At 999 ms the retry is not due. At 1,000 ms a new claim uses the same key, target and bytes.
    4. Inside the fake's 60-second replay window, its original message ID returns. Two calls yield one acceptance, not proof of delivery or read.

    Opt-out while queued work waits

    1. A worker claims the delivery without yet authorizing an external call.
    2. The customer disables email before the final gate.
    3. Authorization suppresses the work; provider calls remain zero. An already authorized/in-flight request could not be recalled.

    Stale worker after lease recovery

    1. A's epoch1 call is accepted externally, but its local completion is delayed.
    2. At 29,999 ms its lease still prevents another claim. At 30,000 ms B takes epoch2 and treats the prior send as uncertain.
    3. A's late completion returns STALE, leaving B's dispatch state intact. The acceptance evidence is still retained locally.
    4. B resolves with the same provider key inside its replay window. The fake ledger still contains one actual acceptance.

    No safe replay contract

    1. The adapter records a zero safe-replay window, then the fake accepts before its response is lost.
    2. The uncertain outcome becomes DEAD_LETTER/reconciliation work.
    3. Another queue copy does not call the provider again. A reconciler needs evidence or a recorded decision; inventing a new key is not a safe generic repair.

    The boundary of this demonstration

    The code models local dispatch decisions, a controlled clock and fake provider behavior. It does not implement a durable outbox, broker, database lease, real contact verification, delivered receipt or human-read detection. Production must preserve evidence and ownership with durable transactions and the actual provider's contract.
