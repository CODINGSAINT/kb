Can an old reader refill the cache?

Follow one product-card update, then separate a late fill's age from its insertion time. Finally, see why an evicted key needs a new slot identity.

Three independent checks: a source version orders data; a generation retires pending work; a slot incarnation survives eviction safely. A ten-second maximum age limits copies even when invalidation is delayed.

    Read the decisions as text

    Invalidation retires the old reader

    1. At t=0, A obtains slot 1 / generation 0 and the origin fixture supplies v41, INR 499.00. The cache has a metadata slot, no value yet.
    2. At t=1, invalidation for committed v42 advances the generation and raises the minimum accepted version to 42.
    3. At t=2, A's late v41 fill returns INVALIDATED. Its old generation no longer has permission.
    4. A fresh ticket and v42 / INR 549.00 fill successfully. Their age starts at this new ticket's issue time.
    5. An older v41 invalidation is already covered and leaves the newer copy intact.

    A delayed fill does not get a new TTL

    1. A ticket issued at t=0 starts a ten-second maximum age, before reading the origin.
    2. At t=9, its fill succeeds with only 1,000 ms remaining.
    3. At t=9.999, a hit has only 1 ms remaining; a read does not reset it.
    4. At t=10, equality expires the value and returns MISS. The metadata floor can remain.
    5. The same old fill returns TOO_OLD. Only a new ticket and a fresh source read can renew freshness.

    Eviction retires old permission

    1. Two slots contain A and B, with three payload bytes each: two slots and six bytes are full.
    2. Reading A moves it to the most-recent end; B becomes oldest.
    3. Loading C evicts B. The retained order is A, C and payload remains six bytes.
    4. Replacing A with four bytes evicts C to satisfy the byte bound; one slot/four bytes remain.
    5. Evicting A and recreating it produces slot 4. A ticket for former slot 1 returns RETIRED_SLOT, even if both generations were zero.

    What the recorded states establish

    These are actual operations on one bounded Java cache node, with controlled monotonic time and product versions supplied as test inputs. They do not implement routing, source transactions, replica promotion, network partitions or distributed clock health. Those boundaries are explained in the article and need separate checks.
