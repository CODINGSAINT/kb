When does a revoked link stop?

A cache key can be deleted while an old read is still in flight. Follow that race, then see how expiry shortens the same cache permission.

Chosen policy: a server-owned snapshot can serve until its original deadline, at most 30 seconds from the authority read on this model's clock. Browser responses use 302 and no-store.

    Revocation races a late fill

    1. t=0: an authority read obtains active version 1, with its cache permission ending at t=30. The read is held in flight.
    2. t=5: the owner commits revoked version 2 and invalidates the cache.
    3. t=6: the old active fill arrives. It still ends at t=30, so a cache hit can issue 302 under this bounded policy.
    4. t=29: a stale cached redirect is still allowed. This is the explicit cost of the chosen window.
    5. t=30: equality ends permission. The service rejects the old copy, reads revoked version 2 and returns 410.
    6. t=31: installing the old fill fails; cache insertion never renews its permission. Requests still return 410.

    Expiry shortens the cache permission

    1. t=0: a link expiring at t=10 gets a deadline of min(t=30, t=10), so the first authority-based request returns 302 and caches only until t=10.
    2. t=9: the cache permission and expiry checks both pass; return 302.
    3. t=10: equality fails both checks. The retained authority row is expired; return 410 without waiting for cleanup.
    4. t=12: replaying the original create request returns the original code. It does not revive it; resolving it still returns 410.

    The boundary of this demonstration

    The Java model uses one injected clock and local synchronization. A deployment needs a monitored clock-error budget, fresh authoritative reads and durable transactions. Already issued redirects or an older browser-cached redirect cannot be recalled. This walkthrough does not simulate browser caching or prove a distributed availability/latency guarantee.
